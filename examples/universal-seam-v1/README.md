# Universal Seam Fixture v1

This is a small, fictional, offline practice fixture for the first mapped
universal-core route. It is designed to teach one invariant:

> A visible reply, branch label, tool-shaped block, or parser success does not
> by itself prove the requested task, target, action, or structured state.

The fixture has no account, model call, network request, credential, real
repository, file mutation, command execution, commit, push, publication, or
external side effect. It does not copy a vendor issue, prompt, log, screenshot,
or tool protocol. The dated research record only informed the four *categories*
of fictional seam; this fixture is original project material.

## What to do

For each record in `cases.json`, identify the exact mismatch, write the one
smallest safe check, and keep the supplied status meaning narrow:

| Status | Meaning in this fixed fixture |
| --- | --- |
| `verified_in_fixture` | The supplied local values directly establish the named mismatch. |
| `blocked` | The target or authority evidence conflicts, so the next action must stop. |
| `not_run` | The record supplies no execution receipt; no action has been demonstrated. |
| `inferred` | The supplied values show a discrepancy, but a live protocol diagnosis needs a product-specific adapter. |

Run the deterministic checker from the repository root:

```powershell
$py = (Get-Command python -ErrorAction Stop).Source
& $py scripts\validate_universal_seam_fixture.py
& $py scripts\test_universal_seam_fixture.py
```

The validator checks the fixture contract; the test script proves the checker
rejects a missing case, a widened status, a weak stop condition, and an
overclaim in the boundary. Neither command calls a model or a service.

## A bounded record card

```text
Task: Classify one seam in the supplied fictional record.
Read first: cases.json and expected/acceptance.json.
Allowed action: Compare the fixed values and write a local decision note.
Do not: use a network, account, secret, real repository, live tool, command,
commit, push, or publication target.
Acceptance: Name the mismatch, the unsupported inference, the smallest safe
check, the stop condition, and the supplied narrow status.
Receipt: Case ID, observed fields, decision, unverified list, and whether a
future platform adapter is required.
Stop: A live product behavior, permission, schema, or external state would be
needed to continue.
```

## What this fixture cannot establish

A pass means only that the repository's fixed fictional records match the
acceptance contract. It does not reproduce an external report, prove an issue
is current, diagnose a platform, show that an action ran, prove a learner can
apply the method, or establish safety, portability, or production readiness.
