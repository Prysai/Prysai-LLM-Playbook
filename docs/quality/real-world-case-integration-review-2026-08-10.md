# 真实问题案例教学化质量审查（2026-08-10）

## 审查范围与结论

本审查只覆盖：

- `book/chapters/05-choose-the-codex-surface.md`（第五章《选择正确的 Codex 工作面》）；
- `book/labs/lab-007-action-boundaries.md`（实验 007《行动边界分级》）；
- `book/chapters/13-action-boundaries.md`（第十三章《文件、终端、浏览器与 GitHub 的行动边界》）；
- `docs/research/field-problems-codex.md`（《Codex 真实用户问题现场研究》）。

审查标准是：真实报告是否被改写成可教学的“症状 → 证据 → 最小排查 → 停止 → 降级/安全替代”链路；是否明确报告者、研究者、官方确认和本项目复现的边界；是否能由读者沿文件链接回到原始记录。

总体判断：当前稿件已经建立了正确的安全骨架，尤其是实验 007 和第十三章已经能教读者停止扩权、保存基线、区分登录/授权/执行/验证，并把用户报告标为“非本地复现、非官方根因”。但整合仍不均匀：第五章主要是问题入口，第十三章有较完整的案例链，研究记录则主要是证据档案，四处尚未共享同一套案例字段。当前适合标为 `candidate`，不宜称为“已验证的现实故障手册”。

## 1. 逐文件审查

### 1.1 第五章：入口和决策框架成立，案例链仍偏摘要

已有内容：

- “现实问题入口”列出 FP-01 至 FP-05、FP-12，并明确它们不是产品说明书，版本和 workaround 需要重新核对（第五章“现实问题入口”）。
- “产品支持、账户授权与本次可用是三层证据”（第五章“一、概念”第 2 节）把认证、资源、模型、工具和具体动作拆开。
- 五道门、`surface-decision.md`、`passed / failed / not_observed`、Cloud setup/agent 分段和失败变体，已经提供证据与停止框架（第五章“二、决策”“四、证据”“五、失败”）。

主要缺口：

- FP 编号只在入口段成组出现，没有把 FP-01、FP-02、FP-03、FP-04、FP-05、FP-12 分别展开为“用户看到了什么、哪一段证据缺失、最小排查是什么、何时停止、可否降级”。读者可以学会决策卡，但不能从本章直接演练某一个现实症状。
- 第五章的失败表按抽象类型写“登录成功但资源不可读”“Cloud setup 成功但 agent 失败”，没有回指对应研究编号。因此 `FP-02` 的 token exchange、`FP-03` 的 Enterprise host、`FP-04` 的多组织 connector 和 `FP-05` 的 updater 凭据边界没有进入同一条教学链。
- 章节的易变事实表有官方 URL、访问日期和复核责任人，但现实案例入口没有同样的案例级日期/版本/证据等级字段。研究记录中的版本和 workaround 不能通过一个总链接自动传递到正文。
- “停止扩权”已经出现（第五章“失败”末段），但“降级”没有被命名为可交付状态。应明确例如：认证链失败时降级为本地离线任务；Enterprise host 不明时降级为只读元数据核对；updater 失败时降级为记录版本/手动等待官方发布，而不是修改 updater。

判断：第五章没有明显把某条用户报告直接写成官方事实；问题在于案例被压缩成入口索引，尚未成为可执行的病例卡。

### 1.2 实验 007：四段状态和停止链最完整，但案例元数据不足

已有内容：

- “本实验要解决的真实问题”明确指出登录、可访问、获准、已执行、已验证不能压成一个词，并引用 FP-02、FP-03、FP-04、FP-11。
- “症状卡” S-02、S-03、S-04、S-11 已经具备症状、暂时可记录事实、不得推出的结论和安全下一步（实验 007“症状卡”）。
- “最小排查顺序”从冻结范围、保存基线到定位阶段、只读核对、最小可逆动作、比较工作面、验证或停止，形成了清楚链路。
- “停止条件”明确禁止扩大 roots、force push、force reinstall、持久安装、真实外部账户和未核对的组织/host；“停止后的安全替代”也给出了保存证据、说明缺口、提出更小检查或隔离检查的降级动作。
- 实验状态为 `draft`，`last_verified` 写明未运行；这避免把练习设计误写成真实运行证据。

主要缺口：

- 症状卡只有 FP 编号，没有逐卡显示原始 URL、创建日期、访问日期、版本/平台、证据等级和当前 Issue 状态。虽然 S-02 等说明“原始 URL 和日期以研究记录为准”，但学员脱离研究文件阅读时无法判断证据新鲜度。
- “证据等级”在统一注记中只写“用户报告；本地复现：未做；官方根因：未确认”，没有区分 FP-02 的单一报告、FP-03/04 的用户环境对照、FP-11 的单一事件叙述。教学上应保留这种强弱差异，不要让四张卡看起来同等可靠。
- 实验教的是安全模拟夹具，不是外部系统复现；这一点已写清，但“降级”主要以安全下一步表达，没有在状态卡中提供 `degraded_to` 或“当前可继续的低风险任务”字段。补一个字段即可让“停止后怎么办”更可观察。
- 实验 007 的来源表只列研究文件和原始 URL，研究索引中的“建议章节”没有回指实验 007；跨文件导航因此是单向的。

判断：实验 007 已基本把报告转成教学链，是四处中最接近验收标准的文件；剩下的是案例元数据和“降级结果”的结构化记录。

### 1.3 第十三章：案例链可教学，但引用编号和案例元数据不一致

已有内容：

- “现实问题入口”明确引用 FP-03、FP-04、FP-11，并说明都是用户报告、非本地复现、非官方根因。
- “失败或边界案例”案例一至四分别给出观察证据、错误处理、fail-closed 停止点、低风险替代动作和不能宣称的结论，已经形成完整的症状—证据—排查—停止—降级链。
- 案例一（FP-02）把浏览器成功、token exchange、首个只读请求分段；案例二（FP-03/FP-04）把 host、组织、仓库、branch、installation 分段；案例四（FP-11）把源码修改、依赖安装、配置变化、重启和线上验证分段。这些是可以保留的教学主干。
- 第 13 章“失败或边界案例”后半段还覆盖了多目录写权限、WSL 代理、HTTP 507、子 Agent handoff、Provider 工具缺失等后续问题，并大多标注“用户报告、未本地复现、未确认根因”。

主要缺口：

- 案例一至四正文没有稳定显示创建日期、访问日期、产品版本和证据等级；读者需要跳到研究文件才能知道 FP-02 为 0.147.0、FP-03/04 为具体 App build、FP-11 缺完整产品版本。这违反了本项目对易变案例“带日期、版本、范围”的实际可复核要求。
- 案例三引用 `openai/codex#37522` 和 `#34352`，但这两个记录位于 `docs/research/field-problems-surface-2026-08-10.md`，不在本审查范围内的 `field-problems-codex.md`。第十三章的现实问题入口和来源段没有给出这两个 FP-S 编号，造成“正文有案例、主研究索引无记录”的断链。
- 第 13 章第 221–225 行的 FUP-02、FUP-03、FUP-04、FUP-05、FUP-01 只以主题描述出现，没有显式写出 FUP 编号、原始 URL 或到 `field-problems-follow-up-2026-08-10.md` 的锚点。尤其是“一个 2026-08-10 访问的 Issue”这一浏览器案例没有可追溯编号。
- 第 213–216 行重复出现“公共仓库与个人沙盒切换”和“外部内容注入动作”，属于正文重复，不是证据错误，但会稀释案例后的整改重点。
- “这是常见的边界滑移”（案例四）从单一公开事件推到“常见”，应改成“这是本报告呈现的一种边界滑移模式”，除非另有多来源统计证据。

判断：第十三章的教学结构已经足够强；主要风险不是安全原则错误，而是引用元数据不随案例移动，以及新增研究没有进入统一索引。

### 1.4 `field-problems-codex.md`：证据档案稳健，但标题和字段有因果过度压缩

已有内容：

- 文件开头把状态标为 `candidate`，明确不是官方故障清单、不是本地复现报告；“证据边界与标记”区分用户报告、独立用户复现、官方确认、本地复现和推测。
- 每条 FP 通常包含原始 URL、日期、环境、证据区分、现实解决方式、应放入章节和不确定项；这已经满足研究记录的基本可审计结构。
- “跨问题观察”明确说不替代单条证据；“研究限制”说明主要只覆盖 GitHub Issues，没有覆盖 Reddit、Stack Overflow 或 OpenAI 社区，且没有执行外部命令。这些边界写法是正确的。

仍需整改的地方：

- 一些标题把报告者的根因推断写成了标题事实：FP-01《MCP OAuth 回调丢失 RFC 9207 `iss`》、FP-05《Windows updater 忽略现有 GitHub CLI token》、FP-06《Skill discovery 忽略文件 symlink》、FP-07《显式 Skill 调用错误地依赖隐式列表》。正文的“推测”字段其实已经降级了这些结论，但标题会先于正文塑造读者判断。标题应改为“报告：……”“用户观察：……”或改用纯症状描述。
- FP-06 把“独立用户复现”用于同一 issue 作者自己做的普通文件/硬链接对照；正文随后又说明是“单一用户复现”。这不是第三方独立复现，应改成“报告者自述对照观察”。
- FP-09 的“后续串扰”来自评论者报告，正文已说没有服务端日志；标题可以保留“可能”，但应在教学引用处明确“评论中的二次报告”，不能和作者主症状并列为同等证据。
- 各条没有统一的显式字段 `症状 / 可观察证据 / 最小排查 / 停止条件 / 降级路径`。当前“现实解决方式”有时是用户 workaround，有时是 Field Guide 的安全建议；虽已用文字区分，仍容易在章节摘录时混用。建议把两者拆成 `reported_workaround` 和 `safe_degradation`。
- FP-01 的标题与正文不完全一致：正文描述回调包含 `iss` 但登录失败，尚未证明是“回调丢失”。FP-05、FP-06、FP-07 同样应避免在标题层面预置内部根因。

判断：研究记录本身没有把 12 条报告统一写成官方确认；真正需要修的是标题语义和可供章节复用的字段化结构。

## 2. 哪些地方仍可能把用户报告误写成事实

以下不是说正文已经声称“官方确认”，而是指出读者可能先读到的措辞需要降级：

| 位置 | 风险措辞 | 问题 | 精确整改方向 |
|---|---|---|---|
| `docs/research/field-problems-codex.md`，FP-01/05/06/07 标题 | “丢失”“忽略”“依赖” | 把报告者/评论者的根因解释放进标题 | 改为“报告：回调含 `iss` 但认证失败”“报告：updater 未使用现有 CLI token”等症状标题 |
| `book/labs/lab-007-action-boundaries.md`，“本实验要解决的真实问题” | “现实中的失败往往不是……” | 从少量 Issue 概括用户群体的普遍模式 | 改为“这些公开报告显示的一种重复模式是……”并保留 FP-02/03/04/11 |
| `book/chapters/13-action-boundaries.md`，案例四 | “这是常见的边界滑移” | 当前可见证据至少包含单一事件报告，不能支持频率判断 | 改为“这是该报告呈现的一种边界滑移模式” |
| `book/chapters/13-action-boundaries.md`，第 119 行附近 | “一个 2026-08-10 访问的 Issue” | 无编号、URL、证据等级，无法判断是哪条报告 | 写出 FP/FUP 编号并链接对应研究文件；保留“未本地复现” |

相反，以下内容目前写法合格，应保持：第五章入口的“不是产品说明书”；实验 007 的统一注记；第十三章案例一至四的“不能宣称”；研究文件开头的证据边界和每条的“不确定项”。

## 3. 案例缺失的版本、日期和证据等级

### 需要在章节/实验中补齐

- 第五章 FP-01–05、FP-12 的入口：至少显示“原始研究编号、报告日期、研究访问日期、主要版本/平台、证据等级、当前状态”。
- 实验 007 S-02、S-03、S-04、S-11：每张症状卡补 `source_id`、`source_url`、`reported_at`、`checked_at`、`surface_and_version`、`evidence_level`。不要把所有卡都只显示成同一个“用户报告”。
- 第十三章案例一至四：补 FP-02、FP-03/FP-04、FP-S-05/FP-S-06、FP-11 的日期、版本、Issue 状态和“本项目未复现”。
- 第十三章新增的 Provider、第二目录、WSL 代理、507、handoff 案例：分别标 FUP-02、FUP-03、FUP-04、FUP-05、FUP-01，并链接后续研究文件。

### 研究文件需要补齐

- 为每条 FP 增加统一的 `symptom`、`observed_evidence`、`minimum_triage`、`stop_condition`、`safe_degradation` 字段，保留现有“用户 workaround”但单独命名。
- 把 `independent_user_reproduction` 改成更细的证据值：`reporter_self_comparison`、`third_party_report`、`maintainer_confirmation`、`local_reproduction`。这样 FP-06 不会把同一作者的对照试验误读为独立复现。
- 对标题中的因果词做一次全表审查；标题只写症状，根因只放在 `hypothesis`/`不确定项`。

## 5. 精确、短小的整改清单

按优先级执行：

1. 先改研究记录标题：FP-01、FP-05、FP-06、FP-07 只写报告症状；FP-06 的证据等级改为“报告者自述对照观察”。
2. 给研究记录增加五个复用字段：`symptom`、`evidence`、`minimum_triage`、`stop`、`safe_degradation`；将用户 workaround 与安全降级分开。
3. 给实验 007 四张症状卡补 FP 编号、原始 URL、日期、版本/平台、证据等级，并增加 `degraded_to` 或等价字段。
4. 给第五章入口增加逐 FP 链接和一行降级动作；至少覆盖 FP-02、FP-03、FP-04、FP-05。
5. 给第十三章案例一至四和第 221–225 行的后续案例补精确研究编号、链接、版本/日期和“未本地复现”标签。
6. 把第十三章“常见的边界滑移”改成不作频率断言的措辞，并删除第 213–216 行重复条目。
7. 更新三份研究索引，使 FP、FP-S、FUP 与章节/实验双向可追溯；完成后再运行项目既定验证命令。

本审查不改变书稿、实验、研究记录或索引；它只作为主代理后续整改的质量门槛。当前结论：现实案例整合为 `candidate`，教学链条部分达到可审查状态，但在统一元数据、因果措辞和跨文件索引修正前，不应标为 `verified` 或 `production-ready`。
