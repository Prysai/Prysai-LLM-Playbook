# ADR-0017: Make the reader shell consume canonical navigation

## Status

Accepted

## Date

2026-08-11

## Context

The repository has two legitimate reading surfaces: raw Markdown on GitHub and
the dependency-free reader under `site/`. The Markdown source needs visible
previous/next links for readers who stay in the repository, while the reader
needs a sidebar, progress label, and adjacent-chapter controls that preserve
the selected locale and URL hash. Maintaining those relationships in HTML,
JavaScript, and chapter files independently would recreate the drift that the
canonical navigation source was introduced to prevent.

The reader also has to distinguish content identity from a file path. A
localized page is the same chapter identity with a different available source;
it is not a new chapter merely because its filename changes. When a requested
translation is missing, the reader must show the available source and state the
fallback instead of implying that translation is complete.

## Decision

1. Treat `docs/governance/book-navigation.yaml` as the only source of chapter
   order, part membership, stable chapter IDs, titles, and adjacent-chapter
   relationships.
2. Project that source into `site/locale-manifest.js` through
   `scripts/build_site_locale_manifest.py`. The generated `book_navigation`
   payload is data for the reader; it is not hand-maintained page markup.
3. Let `site/reader.js` resolve a chapter by `content_id`, choose the requested
   locale when a ready source exists, and fall back to the current English
   source with an explicit status message when it does not.
4. Build previous/next links from the canonical ordered array. The first
   chapter has only a next link, middle chapters have both links, and the last
   chapter has only a previous link. All links retain the active locale token;
   hash fragments are preserved when changing language or following a source
   link.
5. Keep the raw Markdown footer generated by
   `scripts/build_book_navigation.py`. The reader shell and raw source are two
   renderers of the same navigation contract, not two competing navigation
   sources.

## Alternatives considered

### Hand-maintain a reader sidebar and chapter footers separately

Rejected. The two surfaces would eventually disagree about order, titles, or
the end-of-book behavior, especially after a chapter is added or renamed.

### Use filename suffixes as the reader's identity

Rejected. `-EN`, `-ZH`, and other suffixes identify source variants, not
different learning objects. Stable content IDs are required for reliable
fallback and locale-preserving links.

### Hide missing translations behind a silent fallback

Rejected. A working link is not evidence that the target language exists.
Visible fallback status keeps the language contract honest and makes migration
work auditable.

## Consequences

- A change to chapter order starts in one governance file and regenerates both
  raw Markdown navigation and reader data.
- The reader can offer an app-like reading flow without introducing a full
  documentation framework or a second build system.
- Locale coverage remains explicit: a route may be available while its body is
  still pending translation or independent review.
- The generated manifest must be checked with
  `scripts/build_site_locale_manifest.py --check` before publication.
