# ADR-0012: Add visual teaching cards and observable case artifacts

## Status

Accepted

## Date

2026-08-11

## Context

The Field Guide now has a reading-product layer, but its central ideas are
still mostly encountered as prose. The user asked for teaching visuals and for
examples that show what a Skill-related workflow produces. A visual can reduce
the reading load, but it can also create a false sense of proof: a polished
image is not a runtime log, and a convincing mockup is not customer evidence.

## Decision

### 1. Use original, inspectable teaching cards

Visual explanations may be stored under `assets/teaching/`. Prefer original SVG,
HTML, CSS, or other inspectable project-native assets when the visual is a
diagram, workflow, or teaching card. Use raster generation only when the
requested visual genuinely needs a bitmap. Every project-bound visual gets an
asset-register entry and an evidence boundary.

The first cards explain:

- model choice as a bounded smoke test; and
- the path from a Skill contract to an observable output.

### 2. Pair demonstrations with a source/evidence chain

An example that claims to show a Skill's effect must separate:

```text
input brief → Skill-shaped context → downstream artifact → rendered evidence
```

The chain may be synthetic, but it must say so. A screenshot proves only the
rendered state and recorded viewport. It does not prove automatic Skill
execution, customer preference, market validity, conversion, legal approval,
or production readiness.

### 3. Use disposable local sandboxes for risky or illustrative outputs

Domain examples that could be mistaken for real business material belong in a
clearly named sandbox. The sandbox must have no secrets, personal data, live
analytics, external network dependency, lead capture, or irreversible action.
The example page must label synthetic inputs and include a visible boundary
between what the artifact demonstrates and what it cannot establish.

### 4. Keep status and source ownership unchanged

Visual cards, screenshots, and case studies are presentation/evidence layers.
They do not replace `docs/governance/content-status.yaml`, the learning path,
Skill validators, evaluation fixtures, or research source records. A case can
link to a chapter, lab, and Skill, but it cannot silently promote their status.

## Alternatives considered

### Use external stock images or copied screenshots

Rejected for this slice. Permission, privacy, provenance, and future link
stability would be unclear, and external imagery would add little teaching
value compared with an inspectable local artifact.

### Use an AI-generated bitmap for every teaching visual

Rejected as a default. A diagram or workflow is more useful when readers can
inspect the labels and reproduce the structure. Bitmap generation remains an
option for photographic or illustrative assets when the built-in image tool is
available and the license/asset boundary is recorded.

### Claim that the static page was generated by the Skill

Rejected. The Product Context Skill's documented contract shaped the case, but
the context draft and page are hand-authored. Runtime invocation evidence is
not available, so the case says so explicitly.

## Consequences

- Readers get faster visual entry points into abstract concepts.
- A domain example can be inspected from brief through screenshot.
- The repository must maintain source, license, privacy, and evidence records
  for visual assets.
- Visual polish cannot be used to raise a draft, candidate, or case to
  `verified` without the relevant evidence.
