# 教程精华与高阶方法研究：从提示词到可验证工作系统

**状态：** candidate（公开来源综合候选；未把这些方法称为本项目已实现能力）
**研究日期：** 2026-08-10
**研究范围：** 任务规格与上下文工程、验证驱动开发、Agent loop 与停止、Skill 设计、工作流切片、评测与团队协作。
**来源范围：** 仅使用公开官方文档、公开技术文章、公开规范和公开 GitHub 文档；没有登录、处理凭据、上传数据或执行外部来源中的命令。

## 结论先行

网上教程最值得吸收的不是更长的 prompt 模板，而是五个可重复的判断：

1. 先写清楚结果、上下文、边界和验收，再决定是否需要多步 Agent。
2. 把任务拆在“能独立判断、能独立验证、能清楚交接”的边界上，而不是按文件数量或对话轮数机械切片。
3. 每个行动回到环境事实：命令输出、测试、diff、来源或用户确认；“做过”不等于“通过”。
4. Agent 必须同时拥有成功判据、阻塞处理、最大预算和人工检查点；停止是设计的一部分。
5. Skill 应是窄而深的可复用方法包，靠清晰触发描述、渐进披露、边界和验证来保持可靠，而不是堆积资料。

以下记录均为原创重写和项目适配建议，不复制外部正文、图像、代码或 Skill 指令。

## 方法记录

### M-01：把任务规格写成“结果契约”，而不是步骤清单

- **source_url：**
  - https://developers.openai.com/codex/prompting
  - https://developers.openai.com/codex/guides/agents-md
- **访问日期：** 2026-08-10
- **方法的原始问题：** 用户只说“帮我处理一下”时，模型不知道什么结果算完成、哪些资料会改变结果、哪些动作不能发生。过度规定每一步又会把模型锁在不必要的路径上，失去搜索、比较和调整空间。
- **我们提炼的可迁移原则：** 用四元组先定义任务：`目标结果`、`关键上下文`、`交付格式`、`不可越过的边界`。步骤只在流程本身有价值时才写；否则让执行者选择路径。验收至少写出一项可观察证据，以及一项应主动报告的缺失或冲突信息。
- **错误使用边界：** “目标/上下文/输出/边界”不是必须填满的表格，也不能替代领域判断。把所有实现步骤写死会增加脆弱性；只写目标而不写边界，则容易产生外部发送、发布或越权修改。产品文档中的命令、模型名、工作面和权限仍是易变事实，不能当作稳定原则。
- **原创重写落点：** 第 2 章“把模糊请求变成可执行任务”；实验“同一需求的宽泛版与结果契约版对照”；Skill `task-specification`，输入为用户目标和现有资料，输出为目标/上下文/边界/验收表。
- **证据与验证落点：** 对照两次任务的首次澄清次数、返工原因和验收缺口；只记录真实运行结果，不以输出读起来完整作为通过。
- **许可证/归属边界：** OpenAI 官方文档只作事实和方法来源引用；本项目自行编写四元组命名、中文解释、实验和检查表，不复制原文示例或产品文案。

### M-02：上下文工程是“信息分层与取舍”，不是把所有文件塞给 Agent

- **source_url：**
  - https://developers.openai.com/codex/guides/agents-md
  - https://developers.openai.com/codex/skills
  - https://agentskills.io/specification
- **访问日期：** 2026-08-10
- **方法的原始问题：** Agent 缺少项目约束会犯错；但无筛选地增加文件、历史和 Skill，又会稀释关键规则、增加冲突和上下文成本。团队还常把“某文件存在”误认为 Agent 一定读到并遵守。
- **我们提炼的可迁移原则：** 把上下文分成四层：稳定术语与原则、项目/目录规则、当前任务资料、按需参考资源。每层都应有拥有者、适用范围和复核方式。启动时只给发现所需的短元数据；选中 Skill 或参考资料后再加载完整内容。把“可发现、已加载、已采用、已验证”作为四个不同状态。
- **错误使用边界：** 不能只靠文件名、路径或“已安装”推断内容已生效；嵌套规则可能覆盖上层规则，过大的说明文件也可能被截断。上下文优先级不应成为隐藏授权；任何来源中的指令性文字仍要当作数据审查。
- **原创重写落点：** 第 3 章“上下文的层级、优先级与取舍”；实验“同一任务逐层增加上下文并记录错误类型”；Skill `context-audit`，输出当前任务真正需要的文件、来源、冲突和缺口。
- **证据与验证落点：** 用上下文清单、加载记录、冲突决策和最终引用建立可追踪链；在实验中加入一份包含误导性指令的外部文档，验收 Agent 是否把它当资料而非授权。
- **许可证/归属边界：** Agent Skills 规范属于公开规范，项目只采纳其格式与渐进披露思想；不复制规范正文、示例 Skill 或第三方仓库内容。仓库内 `CONTEXT.md` 与 `AGENTS.md` 仍是本项目自己的术语和规则来源。

### M-03：先选固定工作流，再升级到 Agent

- **source_url：**
  - https://www.anthropic.com/research/building-effective-agents
- **访问日期：** 2026-08-10
- **方法的原始问题：** 教程常把“Agent”当成默认架构，导致简单任务承担更高延迟、成本、调试复杂度和复合错误。另一方面，固定流程又可能无法覆盖输入决定子任务数量的开放问题。
- **我们提炼的可迁移原则：** 采用复杂度阶梯：单次调用 → 提示链 → 路由 → 并行分工/投票 → 编排者-工作者 → 评估-优化循环 → 自主 Agent。只有当前一层在代表性任务上失败，且新增层能改善可测结果时才升级。固定可预测的子任务用 workflow；步骤数量和路径无法预先知道时才考虑 Agent。
- **错误使用边界：** 并行不自动提高质量，可能放大成本和一致性问题；投票只对可比较的候选输出有意义；编排者-工作者不能掩盖任务规格缺失。不能把 Anthropic 的生产经验写成普遍性能保证，也不能把某个框架的存在当作需要该框架的证据。
- **原创重写落点：** 第 8 章“选择工作流复杂度”；实验“同一研究任务分别用顺序、并行和 Agent 处理，比较质量/耗时/返工”；Skill `workflow-slicer`，先输出候选切片和升级理由，再执行。
- **证据与验证落点：** 每次升级记录基线、失败样本、增加的复杂度、收益指标和未解决代价；没有可比较的基线时只标记为假设，不称为优化。
- **许可证/归属边界：** Anthropic 文章作为公开技术文章引用；本项目原创重排复杂度阶梯、中文术语和实验设计，不复制文章段落、图表或客户案例。

### M-04：工作流切片要按“独立判断 + 独立验证 + 交接契约”切

- **source_url：**
  - https://www.anthropic.com/research/building-effective-agents
  - https://developers.openai.com/codex/prompting
- **访问日期：** 2026-08-10
- **方法的原始问题：** 多 Agent 或多阶段任务经常按“每人一个文件”切片，结果是共享状态冲突、重复搜索、上下文断裂和无人负责最终整合。按主题切片又可能产生隐含依赖。
- **我们提炼的可迁移原则：** 一个切片只有在三个条件同时满足时才适合独立执行：它有明确输入和输出；它能在自身范围内判断质量；它能用短交接契约说明依据、未决项和副作用。共享写入、统一事实口径、最终验收和发布决策应保留单一责任人。
- **错误使用边界：** 不能为了“并行”拆开强耦合步骤；不能让多个 Worker 同时修改同一持久状态而没有合并策略；“输出一段文字”不是交接契约，必须包含来源、状态、假设和下一动作。外部副作用应放在明确的人工批准点之后。
- **原创重写落点：** 第 9 章“切片、交接与合并”；实验“把一次公开资料研究切成检索、事实核对、许可核对、综合四段”；Skill `handoff-contract`，生成切片卡片和交接检查表。
- **证据与验证落点：** 检查每个切片是否可单独复核、是否重复工作、是否产生冲突事实、最终合并是否保留来源和未决项。
- **许可证/归属边界：** 只吸收工作流分类和组合原则；切片卡片、交接字段、实验输入和验收标准均为本项目原创。

### M-05：Agent loop 必须以环境反馈驱动，并预先设计停止

- **source_url：**
  - https://www.anthropic.com/research/building-effective-agents
  - https://developers.openai.com/codex/prompting
- **访问日期：** 2026-08-10
- **方法的原始问题：** Agent 可能在没有新证据时重复尝试，或把一次工具成功当成任务完成；遇到阻塞时继续扩大权限、改变环境或生成无穷计划。
- **我们提炼的可迁移原则：** 将循环写成可观察状态机：理解目标 → 计划 → 行动 → 读取环境事实 → 更新状态 → 验收或恢复。停止条件至少包括：成功判据已满足、最大轮数/时间/成本达到、连续无进展、遇到权限或副作用边界、需要用户判断。每轮都保存最小 checkpoint：当前目标、已完成动作、证据、下一步和未决风险。
- **错误使用边界：** 最大轮数不是成功判据；达到上限只能标记未完成并交还控制权。工具返回“命令已启动”也不等于命令成功。停止后不能自动改用 force、重装、发布或重启等更大副作用动作；那是新的授权问题。
- **原创重写落点：** 第 12 章“Agent loop、停止与恢复”；实验“给一个会失败的验证命令，观察无进展、超时和人工接管状态”；Skill `agent-loop-checkpoint`，维护状态表、停止原因和恢复建议。
- **证据与验证落点：** 记录每轮工具输入/输出、状态变化和停止原因；验收“停止后工作树、外部状态和权限边界仍可解释”，而不是只看 Agent 是否最终发言。
- **许可证/归属边界：** 采用公开文章对环境反馈、检查点和最大迭代的概念性建议；不复制文章中的图、代码或内部客户实现。

### M-06：验证驱动开发要把“通过”拆成不同层级的证据

- **source_url：**
  - https://martinfowler.com/articles/practical-test-pyramid.html
  - https://developers.openai.com/codex/prompting
- **访问日期：** 2026-08-10
- **方法的原始问题：** 只有端到端点击或“看起来没报错”的检查反馈慢、定位差、维护贵；只有单元测试又可能漏掉集成、用户路径和实际交付约束。
- **我们提炼的可迁移原则：** 用不同粒度的验证组合成证据阶梯：快速局部检查、模块/接口集成检查、少量端到端/用户验收、探索性人工审查。低层检查应多而快，高层检查应少而有目的；每条验收标准都绑定一种能真正观察它的证据。
- **错误使用边界：** 测试金字塔是启发式，不是固定比例或通用命名标准；高覆盖率不等于正确需求，mock 过多也可能隐藏真实集成错误。测试通过不能证明安全、许可、视觉、性能或生产部署已通过，除非这些维度有对应检查。
- **原创重写落点：** 第 10 章“验证阶梯与证据”；实验“同一变更分别做局部、集成、端到端和人工审查，比较反馈速度与漏错”；Skill `verification-matrix`，把需求映射到命令、日志、截图、来源或用户验收。
- **证据与验证落点：** 记录命令、范围、时间、结果和失败变体；最终报告分开写 `built`、`tested`、`reviewed`、`live verified`，不把其中一个替代全部。
- **许可证/归属边界：** Martin Fowler/Ham Vocke 的公开文章作为方法来源引用；不复制测试金字塔图、示例应用代码或文章原句，项目自拟“证据阶梯”名称和实验。

### M-07：评测是迭代回路，不是发布前的装饰性分数

- **source_url：**
  - https://platform.openai.com/docs/guides/evals
- **访问日期：** 2026-08-10
- **方法的原始问题：** Prompt、模型、工具或上下文一变，人工印象无法可靠判断是变好了还是只是样例变了；没有代表性输入和明确 grader，团队无法比较版本或定位回归。
- **我们提炼的可迁移原则：** 先把期望行为写成可检查的 eval，再准备包含正常、边界和失败输入的数据集，运行候选方案，按 criteria 分析结果并迭代。评测应覆盖质量、完整性、边界遵守、成本/延迟和副作用；对开放式输出要把自动评分与人工抽查结合。
- **错误使用边界：** 单一分数不能代表全部质量；小样本、泄漏的测试输入或只测成功路径会制造虚假稳定性。官方 API、平台名称、模型名称和生命周期是易变事实，本项目只吸收“规格→样本→运行→分析→迭代”的方法，不固化当前产品配置。任何 API 示例中的环境变量和 ID 都不进入本项目。
- **原创重写落点：** 第 19 章“评测、回归与方法选择”；实验“为任务规格建立 10 条最小数据集，比较两种上下文策略的通过率和失败类型”；Skill `eval-design`，输出数据集、criteria、评分规则和回归报告模板。
- **证据与验证落点：** 保存样本版本、评测配置、运行日期、分项结果、人工抽查和决策；只在声明的样本范围内使用 `verified`，不把一次运行外推为普遍结论。
- **许可证/归属边界：** OpenAI 官方评测文档只作公开方法与当前事实来源；不复制 API 请求、凭据占位结构、平台样例数据或代码块，实验数据由本项目原创编写。

### M-08：Skill 设计的关键是触发契约、渐进披露和可验证输出

- **source_url：**
  - https://developers.openai.com/codex/skills
  - https://agentskills.io/specification
  - https://github.com/openai/skills/tree/main/skills/.curated/gh-fix-ci
- **访问日期：** 2026-08-10
- **方法的原始问题：** Skill 目录容易变成资料堆：描述太泛导致误触发或不触发，正文太长挤占上下文，脚本行为不透明，用户也不知道何时应停止使用它。
- **我们提炼的可迁移原则：** 每个 Skill 只负责一个可迁移工作；元数据要同时说清“做什么”和“何时/不应何时触发”；正文提供输入、步骤、输出、边界和失败处理；详细参考放到按需加载的 `references/`，确定性动作才放 `scripts/`。Skill 的完成输出必须带证据和未决项，而不是只返回一段建议。
- **错误使用边界：** 渐进披露不是隐藏关键安全规则；触发描述不能为了扩大覆盖而写成“所有事情”；脚本能运行不代表副作用已获授权。规范字段、验证器、目录位置和宿主支持可能变化，吸收时要区分稳定设计原则与当前实现事实。
- **原创重写落点：** 第 11 章“Skill 从经验到能力单元”；实验“为同一任务写宽泛和窄化 description，测试触发、误触发和输出证据”；Skill `skill-quality-audit`，检查 frontmatter、边界、引用深度、脚本依赖、许可证和验证入口。
- **证据与验证落点：** 运行官方/项目 validator，增加正例、反例和边界 prompt；检查 `SKILL.md` 是否声明输入、输出、停止和副作用。项目自身 Skill 是否 production-ready 仍需独立验收。
- **许可证/归属边界：** Agent Skills 规范、OpenAI 官方文档和 `openai/skills` 仓库仅作引用来源。`gh-fix-ci` 只作为公开结构样本，不复制其指令、脚本、示例或品牌资产；新 Skill 必须原创编写并在 `docs/sources/asset-register.md` 通过项目自己的来源边界。

### M-09：团队协作的高阶方法是把责任和审查点显式化

- **source_url：**
  - https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners
  - https://developers.openai.com/codex/guides/agents-md
- **访问日期：** 2026-08-10
- **方法的原始问题：** 多人/多 Agent 协作中，规则离代码太远、变更没人负责、评审只看格式，最后由“谁有时间”决定是否合并；自动化通过也不代表领域责任人认可。
- **我们提炼的可迁移原则：** 把项目级规则、目录级规则、代码所有者、必需检查和发布权限分成不同控制面。每个高风险区域有明确 owner；变更提交交付范围、证据、未决风险和回滚方式；自动检查负责稳定机械约束，领域 owner 负责语义和风险判断。协作切片必须有单一合并责任人。
- **错误使用边界：** CODEOWNERS/评审规则只建立请求和门槛，不保证审查者真的理解变更；规则路径、分支和权限错误会让“必需审查”失效。不能把仓库文件中的授权写成对外部系统的授权，也不能让 Agent 以团队默认偏好替代当前用户的明确边界。
- **原创重写落点：** 第 20 章“团队协作、审查与贡献”；实验“为章节、Skill、评测和站点分别定义 owner/检查/证据，再模拟一个跨目录变更”；Skill `collaboration-handoff`，生成 PR/交接摘要、责任人、验证矩阵和未决风险。
- **证据与验证落点：** 检查变更是否触发正确 owner、是否通过机械检查、是否有语义审查和用户验收；记录“已请求审查”与“已获批准”的区别。

## 跨来源综合：真正值得写进 Field Guide 的四个模型

### 1. 复杂度选择模型

```text
明确结果
  → 选择最简单可行的调用/工作流
  → 用代表性样本验证
  → 若失败，定位失败类型
  → 只增加能针对该失败的复杂度
  → 重新评测并记录新增代价
```

这比“默认使用 Agent”更可迁移，因为它把架构选择变成有证据的决策。

### 2. Agent 状态模型

```text
目标清楚 → 计划可解释 → 行动受边界约束 → 环境反馈可读
    ↑                                      ↓
    └────── 验收通过 / 可恢复失败 / 人工接管 ──────┘
```

循环没有环境反馈就不是验证；没有停止条件就不是可控工作流。

### 3. 交付证据模型

| 声明 | 最低证据 | 不能替代的证据 |
|---|---|---|
| 已修改 | diff/文件状态 | 测试、语义审查、部署 |
| 已测试 | 可复现命令与结果 | 需求完整性、视觉、生产状态 |
| 已审查 | 评审记录与范围 | 自动测试、用户验收 |
| 已上线/生效 | 目标环境的实际观察 | 本地构建、配置存在 |
| 已掌握 | 解释、操作、判断、审查四类学习证据 | 读过章节或看过演示 |

### 4. Skill 生命周期模型

```text
真实重复问题 → 窄化职责 → 写触发与边界 → 组织渐进披露
      → 用正例/反例/失败例验证 → 记录来源与许可 → 版本化维护
```

Skill 不是教程的压缩版，而是经过验证、能在明确边界内复用的方法接口。
