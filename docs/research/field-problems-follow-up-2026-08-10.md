### FUP-01：子 Agent 被创建，但任务消息没有到达

- **source_url：** https://github.com/openai/codex/issues/37822
- **访问日期：** 2026-08-10；Issue 创建于 2026-08-10，页面当时显示 Open。
- **原问题转述：** 报告者称 root agent 使用 `spawn_agent` 或 `followup_task` 后，子 Agent 确实被创建并被唤醒，但看不到任务文本，只收到系统级上下文，因而回复“等待任务”。报告者还称同一问题在桌面端和 CLI、不同 `fork_turns` 设置下出现。
- **可观察证据：** 子 Agent 的运行状态存在，但其输入计数为空或任务正文缺失；root → sub-agent 的交接失败，sub-agent → root 的回复路径可能仍然存在。这里的加密字段、接收端实现和根因都是报告者的诊断，不能写成已确认的框架缺陷。
- **适合插入：** 第 10 章“切片与交接”；第 12 章“Agent 状态与停止”；实验 013 的“交接消息完整性”失败变体；团队协作章节的 handoff contract。
- **应教用户做的排查：**
  1. 给子 Agent 一个无副作用、可判定的回显任务，例如要求返回固定短词。
  2. 保存 root 侧的调用参数、目标 Agent 标识、发送时间和返回状态；不要保存秘密或完整会话。
  3. 在子 Agent 侧确认收到的实际输入，而不是只看“已创建/已运行”状态。
  4. 对比“创建成功”“任务文本到达”“子 Agent 执行”“结果返回”四个断言。
  5. 若任务文本缺失，停止依赖该 Agent 的后续切片，交付为 `blocked`，改用人工交接或单 Agent 流程；不要让子 Agent 猜测任务。
  6. 只在明确改变版本、provider、编排方式或输入后重试，并保留新的证据。
- **证据边界：** 这是用户报告，未证明所有 `spawn_agent` 调用都会丢失消息，也未证明具体内部字段是根因。

### FUP-02：自定义 Provider 会话只暴露极少工具

- **source_url：** https://github.com/openai/codex/issues/37718
- **访问日期：** 2026-08-10；Issue 创建于 2026-08-09，页面当时显示 Open。
- **原问题转述：** 报告者使用 API Key 和自定义 Responses-compatible provider 时，Codex 会话只显示 `image_gen` 等有限能力，shell、文件系统、浏览器和 web 工具没有注册。报告者称同一模型直接调用 provider 可以产生工具调用，因此怀疑问题位于 Codex 会话的工具暴露或动态工具集合，而不是简单的模型不可用。
- **可观察证据：** 会话启动记录中的动态工具数量为零或工具列表明显短于预期；“配置被接受”“模型能返回 function call”和“当前 Codex 会话实际注册了工具”是不同断言。Issue 中的版本回归和内部配置判断仍是报告者观察。
- **适合插入：** 第 5 章“工作面与 Provider”；第 7 章“Skill、Plugin、MCP 与工具”；第 9 章“证据分层”；第 19 章“能力评测”；实验 013 的“能力矩阵”失败变体。
- **应教用户做的排查：**
  1. 在新建、最小配置的会话中先询问或记录实际可用工具清单。
  2. 分别记录 provider、认证方式、模型、Codex 版本、插件状态和权限配置。
  3. 先做无副作用的单 Agent 文本请求，再检查是否真的能调用目标工具。
  4. 将“provider 原生 API 支持工具”与“Codex 会话注册工具”分开测试。
  5. 若工具未注册，禁止继续执行文件、浏览器或外部服务任务；降级为纯文本规划，或切换到已明确支持的工作面。
  6. 不通过修改权限、安装不明插件或粘贴密钥来“恢复”工具。
- **证据边界：** 该 Issue 不能证明所有自定义 provider 都缺工具，也不能证明某一版本的固定回归原因。

### FUP-03：项目配置的第二个目录没有进入新任务的工作区权限

- **source_url：** https://github.com/openai/codex/issues/37731
- **访问日期：** 2026-08-10；Issue 创建于 2026-08-09，页面当时显示 Open。
- **原问题转述：** 报告者在项目中配置了两个本地仓库，但重新启动桌面端并创建新任务后，任务上下文和可写权限只包含主目录。第二个目录可以被更宽泛的读取能力看到，但写入时需要额外批准。
- **可观察证据：** 新任务收到的 workspace roots、可写路径和实际目标目录不一致；项目设置存在不等于新任务已经继承；能读不等于能写。报告者的具体权限注入机制和产品根因尚未被官方确认。
- **适合插入：** 第 4 章“上下文、权限与 Agent”；第 8 章“生命周期与工作区”；第 13 章“行动边界”；实验 013 的“目标路径/权限不一致”边界案例。
- **应教用户做的排查：**
  1. 在任务开始前列出项目配置中的所有目录和预期动作。
  2. 在新任务中分别核对实际 workspace roots、可读路径、可写路径和当前工作目录。
  3. 对主目录和第二目录各做一次只读存在性检查，不先尝试写入。
  4. 用临时无敏感文件做最小写入探针；若触发审批，记录为权限事实，不要自动批准扩大范围。
  5. 比较重启前后、旧任务与新任务的权限快照，判断是配置未继承、工作面不同还是任务授权不同。
  6. 在目标路径未确认前停止编辑；必要时要求用户明确批准准确目录和动作。
- **证据边界：** 这是单个 macOS 用户报告，不代表所有多目录项目都会丢失写权限，也不代表读取权限的具体来源已经确定。

### FUP-04：WSL Agent 通过 HTTP 代理时环境变量可能失真

- **source_url：** https://github.com/openai/codex/issues/37662
- **访问日期：** 2026-08-10；Issue 创建于 2026-08-09，页面当时显示 Open。
- **原问题转述：** 原始检索中发现的同日代理问题报告了 Windows 桌面端连接 WSL Agent 时，HTTP 代理相关的大写环境变量在 Agent 环境中变为空，导致网络连接失败；报告者称在项目 `.codex/.env` 中提供对应变量后恢复连接。该问题与 Computer Use 的 `spawn EPERM` 不同；本条只讨论 WSL/代理环境传递，不能把同一 Issue 的不同报告混为一谈。
- **可观察证据：** Windows 端配置、WSL 端实际环境、代理变量大小写和值、Agent 的网络请求结果不一致。环境文件能改变连接结果并不等于它是官方推荐修复，也不证明所有代理都会受影响。
- **适合插入：** 第 5 章“工作面与环境”；第 8 章“生命周期前置检查”；第 13 章“命令和环境边界”；实验 013 的“环境事实与工具事实分离”失败变体。
- **应教用户做的排查：**
  1. 不在日志中显示代理密码、token 或完整认证 URL；只记录变量是否存在、协议、主机和端口是否符合脱敏格式。
  2. 分别检查 Windows 宿主、WSL shell、Agent 进程实际看到的代理变量。
  3. 先运行 DNS/连通性和最小官方端点检查，再运行 Codex Agent 请求；区分网络不可达、认证失败和工具会话失败。
  4. 比较大小写变量、项目级 `.codex/.env` 和继承环境，但每次只改变一个条件。
  5. 若需要把代理凭据写入环境文件，先确认文件位置、权限、忽略规则和清理方式；没有明确授权时不要创建或修改持久配置。
  6. 记录“网络已通”不能证明“Codex Agent 已认证”或“工具调用已成功”。
- **证据边界：** 代理变量传递、`.codex/.env` 效果和根因来自用户报告；不要把它写成跨平台固定规则或官方支持承诺。

### FUP-05：长时间没有任何事件，随后 HTTP 507 并自动重试

- **source_url：** https://github.com/openai/codex/issues/37837
- **访问日期：** 2026-08-10；Issue 创建于 2026-08-10，页面当时显示 Open。
- **原问题转述：** 报告者称桌面端一次 Responses 请求长时间没有可见 reasoning、消息或工具事件，约数分钟后返回 HTTP 507；客户端随后自动重试，重试很快成功。用户界面只显示等待状态，无法知道是模型推理、网络等待、上游错误还是重试。
- **可观察证据：** 请求开始时间、首个响应事件时间、HTTP 状态、是否重试、重试前后是否产生外部副作用和上下文大小。报告者明确没有把 507 文本解释为物理磁盘已满；该因果判断不能写入教材。
- **适合插入：** 第 8 章“验证闭环”；第 9 章“运行证据”；第 12 章“停止、预算与重试”；第 19 章“首轮通过、最终通过与返工”；实验 013 的“长等待与幂等性”失败变体。
- **应教用户做的排查：**
  1. 为长任务记录请求开始、首个事件、工具调用、响应头、最终状态和重试时间；不记录秘密或完整 prompt。
  2. 在达到预设等待阈值后暂停判断，区分“仍在运行”“无事件”“已失败”和“已自动重试”。
  3. 在重试前检查工作树、外部状态、已生成文件和最后一个 checkpoint，判断第一次请求是否可能已经产生副作用。
  4. 只有在动作幂等、状态已复核且重试条件改变或明确安全时才重试。
  5. 长上下文任务先保存可恢复摘要，必要时拆成更小切片，不把缩小上下文写成保证修复。
  6. 若状态仍不明，交付为 `unverified` 或 `blocked`，而不是把自动重试成功等同于第一次请求成功。
- **证据边界：** 该 Issue 是单次环境报告；不能推出 HTTP 507 的服务端根因、固定超时时间或所有自动重试都不安全。
