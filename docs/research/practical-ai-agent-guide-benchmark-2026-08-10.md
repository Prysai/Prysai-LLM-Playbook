# 实用 AI Agent 教程结构基准研究

- 研究日期：2026-08-10
- 研究状态：candidate / reference-only
- 研究目标：比较高质量公开 AI agent、Codex 和软件工程教程的目录、练习、案例、验证方式与不足，为 `Codex: From First Task to Real Work` 提炼可迁移的内容结构。
- 研究边界：只观察公开页面、公开仓库和公开许可证说明；不复制正文、提示词、代码、图片、品牌资产或页面实现。
- 方法说明：以下结论先记录可观察事实，再给出结构推断；没有用户测试或学习效果数据的地方标记为 `unknown`，不把页面数量或示例数量当作教学效果证据。

## 1. 结论摘要

四个来源各自解决不同的教学问题：

| 来源 | 最强的结构资产 | 练习/案例形态 | 验证机制 | 对本项目的主要启发 | 主要不足 |
|---|---|---|---|---|---|
| OpenAI Codex CLI | 快速安装、入口分流、产品能力边界、贡献工作流 | Quickstart 与受邀贡献流程 | 本地格式化、构建、测试、CI；要求聚焦变更 | 将“产品入口”和“真实交付流程”分开，并给每个能力标注适用边界 | 更像产品文档，不是完整学习路径；缺少统一练习、失败样例和学习者验收量表 |
| Anthropic Claude Code | `gather context → take action → verify results` 的 Agent loop；按任务组织 recipes | 探索代码库、修 Bug、重构、测试、PR、文档等短任务 | 测试、构建、lint、脚本差异、截图、Stop hook、二次审查 | 把每个 Agent 任务写成可观察循环，明确“给 Agent 一个可判定的检查” | 示例以提示语和成功工作流为主，缺少跨环境的固定输入、失败对照和学习者独立评分 |
| Model Context Protocol | 从协议概念到 server/client、tools/resources/prompts、安全、版本、贡献 | 天气服务器、资源与提示模板、多服务器流程、Inspector/调试 | schema 生成、`npm run check`、格式化、SDK/协议测试、PR 检查 | 把“能力扩展”拆成接口、权限、用户确认、运行与兼容性验证 | 偏规范和实现者视角；对初学者的完整端到端 Agent 任务和领域迁移不足 |
| The Rust Programming Language | 从入门概念到可运行项目，再到测试、并发、异步和多线程 Web Server | Guessing Game、I/O/`grep` 项目、测试、最终 Web Server | `mdbook build`、`mdbook test`、代码/文本格式化、CI、stable/beta/nightly | 采用递进式前置依赖、阶段性项目、测试章节和最终综合项目 | 面向确定性编程语言；不能直接覆盖 Agent 的非确定性、权限、证据和模型版本漂移 |

综合判断：本项目不应再做一个“按产品功能罗列页面”的手册，也不应只做一个 WorkBuddyGuide 式的长篇蓝皮书或案例目录。更合适的骨架是“问题入口 → 最小概念与边界 → 低风险实验 → 故意失败 → 证据验收 → 真实案例 → 迁移任务 → 维护卡片”。它把 Claude Code 的循环、Rust Book 的递进和综合项目、MCP 的接口/安全/兼容性层、Codex 的工作流与贡献门槛合并为一个以能力为单位的 Field Guide。

## 2. 比较维度与判定规则

每个候选资料按以下六个问题阅读：

1. 目录是按产品功能、任务工作流、协议层，还是按学习者能力递进？
2. 学习者实际要做什么：复制命令、完成练习、运行项目，还是提交贡献？
3. 案例是否包含输入、前置条件、权限、失败路径、产出和替代场景？
4. “完成”由什么证明：页面描述、命令退出码、测试、截图、评审，还是用户验收？
5. 资料是否把稳定原则与会漂移的产品事实分开？
6. 资料的缺口能否用原始来源、许可证和复现实验补齐？

本项目内部目标与此比较直接对齐：`docs/charter.md` 的愿景是把“会生成内容”迁移为可观察、可验证的协作流程；`docs/book-architecture.md` 要求概念、判断、操作、实验、复盘和迁移闭环；`CONTEXT.md` 要求稳定术语与易变事实分离。下文的建议只针对结构，不改变这些项目术语。

## 3. 来源 A：OpenAI Codex CLI

### 3.1 可观察结构

公开仓库 README 的入口顺序是：Codex CLI 定位 → IDE/桌面/Web 分流 → Quickstart → 安装与运行 → ChatGPT 登录/API key → 文档、贡献、安装构建和开源基金。贡献文档另起一条“受邀外部贡献”路径，包含 issue 先行、测试、用户行为文档、原子提交、全量本地检查、PR 模板和审查流程。

这是一种“产品入口 + 工程协作边界”的双层结构：新手先完成安装和第一次运行；有经验的使用者按开发工作流进入测试、文档和贡献。它没有把模型、工具、权限和 Agent loop 组织成完整的学习章节，而是把这些内容留给独立文档页。

### 3.2 练习与案例

- Quickstart 的练习粒度是安装、启动、登录并开始使用；README 本身没有固定的学习者任务清单或练习仓库。
- 贡献路径的案例是一个受邀 PR：从 issue、topic branch、聚焦修改、测试、文档、原子提交到 review。
- “模型元数据更新”是一个很好的边界案例：它要求明确输入模态、同步客户端能力信号并增加测试，说明产品文档可以把跨表面一致性写成任务约束。

### 3.3 验证方式

可观察验证包括安装命令能否完成、CLI 能否运行、格式化/构建/测试是否通过、CI 是否通过、PR 是否包含 What/Why/How，以及变更是否得到维护者邀请。贡献文档明确要求“测试在改动前失败、改动后通过”这一类证据，但没有为普通学习者提供统一的验收表或失败样例。

### 3.4 不足与迁移价值

不足：安装器、登录方式、产品表面和模型元数据都容易变动；文档适合“如何使用当前产品”，不等于“如何理解 Agent 工作”；Quickstart 的成功信号主要是工具启动，而不是任务交付质量；没有公开的、可重复的学习者前后测数据。

可迁移做法：为本项目每个产品事实卡增加“入口、权限、版本、可观察证据、失败时退出方式”；为贡献者路线单独设置“先判断是否应改动，再写内容，再运行验证”的实验。不可迁移做法：不要把当前安装命令、登录流程或产品名称写成稳定原理。

## 4. 来源 B：Anthropic Claude Code 文档

### 4.1 可观察结构

Claude Code 把教学入口分为 Overview、Quickstart、How Claude Code works、Common workflows、Best practices，以及 Skills、MCP、hooks、权限和其他扩展。其核心解释是三阶段 Agent loop：收集上下文、采取行动、验证结果；页面同时强调这三个阶段会循环，而不是一次性线性执行。

Common workflows 以短 recipe 组织“理解陌生代码库、修 Bug、重构、写测试、创建 PR、更新文档、在非代码目录工作、跨会话恢复和并行 worktree”。Best practices 再把这些 recipe 提炼为更高阶规则：具体说明约束、先计划后执行、提供可判定的验证、展示证据、在合适时使用独立审查。

### 4.2 练习与案例

它的练习不是课程式作业，而是可直接放入真实仓库的任务配方，例如：先读 `src/auth/` 再制定 OAuth 计划；给定复现命令和错误栈修 Bug；写测试并运行；用截图比较 UI；用 plan mode 探索后再实施。案例短、迁移成本低，能让读者迅速从“问答”进入“工作流委托”。

### 4.3 验证方式

验证是该资料最可借鉴的部分：测试、构建、lint、fixture 差异、浏览器截图、Stop hook、目标条件和独立 verification subagent 都被当作“能让 Agent 自己读懂 pass/fail 的检查”。文档还要求展示运行的命令、返回结果或截图，而不是只说“已完成”。权限模式、checkpoint、rewind 和可恢复会话则把风险控制放进工作流。

### 4.4 不足与迁移价值

不足：多数 recipe 假设读者已经有代码库、测试命令和判断任务质量的能力；提示语示例比固定实验数据更丰富，学习者容易“照着说”而没有建立独立诊断能力；没有一个跨任务的能力等级、证据包格式或统一失败分类；文档中的具体命令、产品模式和可用工具会随版本变化。

可迁移做法：每个本项目实验都应显式写出“上下文、行动、验证、停机/回滚”四段；验收不仅要求产物，还要求记录命令、退出码、差异、截图或人工确认；为同一任务提供正常、边界和故意失败三个分支。不要直接复制其提示语，应该将其工作流原则改写成中文任务协议和项目内实验。

## 5. 来源 C：Model Context Protocol（MCP）官方资料

### 5.1 可观察结构

MCP 官方文档的导航从“什么是 MCP、架构、servers、clients、versioning”进入“连接本地/远程 server、构建 server、SDK、security、Inspector、debugging、examples”。Server concepts 页面又按 tools、resources、prompts 和 user interaction model 组织，并用旅行预订、旅行规划和多服务器协作作为示例。

与一般产品 Quickstart 不同，MCP 把“能力是什么”和“能力如何通过协议暴露”拆开：工具负责执行，资源提供上下文，提示模板提供用户可调用的参数化工作流；权限、确认和活动日志属于用户界面/宿主的控制面，而不是工具描述的附属说明。

### 5.2 练习与案例

官方 Build an MCP server 教程以天气服务器为贯穿案例，提供 Node/TypeScript 前置条件、项目初始化、配置、构建和在宿主中连接的步骤；文档同时列出多语言 SDK、官方 Inspector 和调试入口。多服务器旅行规划案例展示了从资源获取、工具调用、提示模板到最终流程的组合。

### 5.3 验证方式

验证横跨三层：实现层运行构建和类型检查；协议层依据 schema 和版本；贡献层运行 `npm run check`、格式化、schema 生成和 CI。官方贡献指南要求先 fork、建分支、在改动后运行检查、对 schema 变更重新生成 JSON Schema/文档，并在 PR 中说明变更。它还通过版本页面和 deprecation/compatibility 机制把“能运行”与“兼容哪个协议版本”区分开。

### 5.4 不足与迁移价值

不足：教程明显偏实现者和协议维护者；天气服务器是通用演示，不足以训练读者判断真实业务中的最小权限、数据敏感度和副作用；工具、资源和提示的定义很清楚，但“一个学习者如何评价 Agent 是否选对工具、是否过度调用、是否在证据不足时停下”没有统一评分标准；协议版本和 SDK 版本会产生额外复现负担。

可迁移做法：本项目讲 Skill、工具、Connector 或 MCP 时，统一采用“能力接口 → 输入/输出 → 权限与副作用 → 用户确认 → 运行日志 → 兼容版本 → 失败恢复”的卡片；案例必须至少有一个只读路径和一个需要确认的写入路径。不要把某个 SDK 的样板代码当作稳定教学资产，也不要把协议仓库的许可证自动推导到其全部示例、图片或第三方依赖。

## 6. 来源 D：The Rust Programming Language（Rust Book）

### 6.1 可观察结构

Rust Book 的目录是严格递进的：Getting Started → Guessing Game → 基础概念 → ownership/structs/enums/modules/collections/error handling → generics/traits/lifetimes → automated tests → I/O project → iterators/closures → Cargo/crates → concurrency/async → advanced features → multithreaded Web Server → appendices。它将“概念学习”和“综合项目”交替安排，最终项目回收前面多个章节的知识。

### 6.2 练习与案例

练习包含可运行的 Guessing Game、测试章节中的单元测试/测试组织、I/O 项目中的命令行 `grep`，以及最终多线程 Web Server。I/O 项目特别适合作为结构参照：它明确列出前置概念、逐步增加功能、重构模块和错误处理、加入测试、读取环境变量、把错误写到 stderr，并把最终代码与真实工具 `ripgrep` 对照。

### 6.3 验证方式

仓库提供 `mdbook build`、`mdbook test`、格式化、拼写检查和 CI；在线版本按 stable、beta、nightly 区分。贡献指南规定编辑 canonical `src`、使用 `rustfmt`/`dprint`、在报告问题前检查 main 与既有 issue/PR，并明确翻译和出版快照的边界。这是“内容本身也有可构建、可测试、可维护证据”的强范例。

### 6.4 不足与迁移价值

不足：它训练的是确定性程序设计，测试通常可以稳定重放；Agent 工作则可能受到模型版本、上下文、权限、工具结果和外部服务状态影响；Rust Book 关注程序正确性，但不负责解释模型幻觉、工具滥用、提示注入、未完成声明或证据链。它的长线稳定性也意味着产品特性更新不会像 Agent 产品文档一样及时。

可迁移做法：采用“概念最小集 → 小项目 → 测试/失败 → 综合项目”的递进，同时把教程源文件、实验脚本和验证器作为可构建资产管理；将 Rust 的确定性测试思想扩展为 Agent 的“固定输入、运行记录、行为断言、人工审查”组合。不要照搬语言章节顺序，而应按 Agent 能力依赖重排。

## 7. 与 WorkBuddyGuide 的区分

本项目已有对 WorkBuddyGuide 的结构研究；本节只提炼差异，不复制其正文、案例、提示词、图片、页面样式或品牌表达。WorkBuddyGuide 的公开形态更接近“连续蓝皮书 + 真实任务 Case 集 + 社区投稿入口”：长篇主线负责阅读，Case 负责从任务沉淀为可复用内容，网站导航提供按问题进入的入口，投稿模板把场景、步骤、结果、验收和安全字段结构化。

它的可迁移资产是双入口导航、案例生命周期、投稿字段和内容/部署分层；它不是本项目的替代结构。两者的核心区别应保持为：

| 维度 | WorkBuddyGuide 的可观察重心 | 本项目应保持的重心 |
|---|---|---|
| 主线 | 蓝皮书分篇分章，按工作任务扩展 | GPT、Codex、工具、Skill、Agent、工作流和证据的稳定概念关系 |
| 实践 | 真实工作 Case 与社区投稿 | 低风险、可观察、可逆的实验，加上正常/失败/边界/迁移四类证据 |
| 质量门槛 | Case 模板、PR/投稿与内容审核 | 每章学习目标、最小实验、故意失败、验收清单、事实卡和运行记录 |
| 内容生命周期 | Case 可沉淀为 Skill、自动化或多 Agent 系统 | 能力单元有 `candidate → reproduced → accepted → maintained` 状态，且不能以“看起来成功”替代运行证据 |
| 组织对象 | 章节与案例为主要导航单元 | `task → capability unit → prerequisites → lab → evaluation → source/fact card → owner/review` 映射 |
| 独特问题 | 如何把经验和案例汇入一个蓝皮书生态 | 如何让学习者从“会问模型”升级到“能设计边界、观察行动、审查证据、迁移方法” |

## 8. 可迁移的结构改进建议

### 8.1 把章节改成能力单元，而不是功能清单

推荐固定模板：

1. 真问题：读者为什么会在真实任务中失败。
2. 学习目标：能解释什么、完成什么、拒绝什么。
3. 最小概念：只引入完成本实验所需的术语与边界。
4. 判断卡：给出至少两个方案、取舍、权限和停止条件。
5. 最小实验：低风险、可观察、可重置，先读后写。
6. 故意失败：制造错误上下文、越权请求、错误工具结果或不完整输出。
7. 证据包：命令/输入版本、运行日志、产物差异、测试/检查结果、人工审查记录。
8. 迁移任务：换一个领域或工具，要求读者自己重写验收标准。
9. 事实卡：URL、访问日期、版本/commit、适用范围、owner、下次复核日期。

这样既吸收 Claude Code 的闭环，也吸收 Rust Book 的递进和项目回收，同时保留本项目已有的解释、操作、判断、审查四类证据。

### 8.2 建立“任务入口”和“能力入口”两套索引

任务入口回答“我现在要修 Bug、写文档、接工具还是审查结果？”；能力入口回答“我需要上下文管理、权限边界、工具选择、失败诊断、验证、贡献治理中的哪一项？”两者必须指向同一个能力单元，避免复制两份正文。每个入口都应显示前置条件、风险级别、预估产物和验证门槛。

### 8.3 把 Agent loop 变成可记录的实验协议

每个实验最少记录：目标、允许读取的范围、允许写入的范围、工具/连接器、用户确认点、模型/产品事实版本、Agent 的计划、实际行动、反馈、重试、停止原因、最终证据。读者必须能判断“失败发生在理解、计划、工具、执行、验证还是交付”，而不只是看到一段漂亮对话。

### 8.4 建立四层验收，而不是单一“通过/失败”

- 事实验收：引用和版本是否准确，稳定原则是否与易变事实分开。
- 行为验收：实验是否在声明的权限、输入和环境下完成。
- 结果验收：测试、差异、构建、截图或用户验收是否支持具体结论。
- 审查验收：读者能否发现一个故意错误、越权副作用、未完成声明或不可复现步骤。

只有前两层可称为 `candidate`；四层都通过才可称为 `verified`。涉及安全、发布、版本和组织流程时，还需要额外的 `production-ready` 门槛。

### 8.5 将失败和复盘作为一级内容

官方产品文档擅长展示“怎样开始”，但学习迁移通常发生在“为什么这次不该继续”。每个实验至少提供一个可控失败：缺少前置文件、工具返回过期数据、权限不足、测试命令不存在、模型声称完成但没有差异、版本不兼容或外部服务不可用。复盘必须要求读者写出下一次的停止条件和证据补充，而不是只给标准答案。

### 8.6 为易变事实单独建卡，不把更新压扁成一个版本号

模型名称、价格、CLI 命令、权限默认值、MCP 版本、SDK 安装方式和产品入口都应在事实卡中记录来源、访问日期、范围和责任人。章节正文只保留稳定决策原则；当事实变化时，影响分析应能反查到章节、实验、翻译和团队规范。

## 9. 本项目的内容缺口

以下不是对四个外部资料的简单复述，而是以本项目现有 charter、book architecture 和质量目标为准的缺口清单：

1. **首次安全实验仍需纵向切片。** 需要一个从只读上下文观察开始，经过最小工具调用、故意失败、证据包和回滚的完整 lab，而不是把概念分散在多个章节。
2. **需要统一 Agent 运行记录格式。** 当前概念已覆盖计划、行动、反馈、重试和证据，但还需要一个可复用的记录模板，让不同章节能比较失败阶段。
3. **需要工具/Skill/MCP 的同一判定框架。** 读者应能看到三者在能力、输入、权限、副作用、触发、版本和验证上的差异，而不是按名称分别介绍。
4. **需要提示注入与不可信内容实验。** 应将网页、工具响应、仓库文件和用户材料视为数据，演示其中的指令式文字为何不能自动升级为权限。
5. **需要非确定性评估。** 除测试退出码外，应加入固定任务集、重复运行、行为断言、人工评分和不确定性记录，避免一次成功被误判为能力掌握。
6. **需要真实交付案例的状态迁移。** 至少覆盖 `candidate → reproduced → accepted → maintained`，并记录何时因为证据不足、许可不清或外部事实漂移而退回。
7. **需要贡献者实验。** 贡献者应练习查重、确认 canonical source、去除秘密、运行验证、说明未验证项、处理失败和安全回滚；这比单独阅读贡献规范更能形成能力。
8. **需要双语一致性检查。** 公共 showcase 可默认英文并提供中文切换，但当前主学习路径仍是简体中文；翻译文件、术语表和审阅证据必须分开跟踪，不能用一个语言切换按钮暗示已完成双语。
9. **需要跨平台运行矩阵。** Windows、macOS/Linux、桌面、终端、浏览器、认证和 CI 的证据应分开记录；“构建成功”不应替代运行时、授权、桌面和浏览器验证。
10. **需要内容维护实验。** 读者应能根据一个易变事实卡判断哪些章节、lab、翻译和团队文件需要复核，并演示复核后的证据，而不是只更新页脚日期。

## 10. 本项目的独特增量

与产品 Quickstart、Agent 工作流文档、协议规范、语言教材和 WorkBuddyGuide 相比，本项目可以明确拥有以下增量：

- **概念边界增量：** 用稳定术语区分 GPT、模型、Codex、上下文、工具、Skill、Plugin/Connector/MCP、Agent、工作流、证据和学习路径，解释它们如何共同影响行为。
- **证据增量：** 把解释证据、操作证据、判断证据和审查证据组合成掌握标准，并把“未知”和“未运行”保留下来。
- **安全增量：** 将最小权限、外部副作用、用户确认、提示注入、秘密管理、回滚和停止条件置于每个实践单元，而不是作为末尾免责声明。
- **迁移增量：** 同一方法必须在工程、研究、文档、设计、营销或团队治理中的另一任务上重写，证明学到的是决策结构而非某个产品命令。
- **维护增量：** 将课程版本、外部事实版本和实际运行记录分层，允许“内容已更新但实验未重跑”“构建通过但运行未验证”等真实状态存在。
- **组织增量：** 把个人技能沉淀、团队 `AGENTS.md`/规范、贡献审查、质量评估和发布门禁连接成一条生命周期，而不是只教单机使用。

## 11. 推荐的最小可行课程骨架

推荐先做一条纵向路线验证结构，再扩展章节数量：

```text
问题入口：让 Agent 在一个受限目录中完成只读调查
  → 概念：GPT / Codex / 上下文 / 工具 / Agent loop
  → 判断：读权限、写权限、确认点、停止条件
  → 实验：记录计划、工具调用、反馈和证据
  → 故意失败：错误文件、过期事实、越权写入、虚假完成声明
  → 验收：事实 + 行为 + 结果 + 审查四层证据
  → 迁移：把同一协议改写为一个真实工程或研究任务
  → 沉淀：能力单元、事实卡、团队规范和维护责任
```

这个纵向切片通过后，再按四条学习路线展开：首次认识 Codex、真实工作交付、能力扩展与 Agent 协作、组织级治理。每条路线都应回到同一套能力单元和证据协议，避免形成互相重复的“工具目录”。
