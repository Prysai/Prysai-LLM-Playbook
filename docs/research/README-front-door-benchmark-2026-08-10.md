# 高质量开源知识库/教程项目的 GitHub README 首页门面基准研究

**研究日期：** 2026-08-10（America/Los_Angeles）
**研究状态：** candidate / reference-only
**研究问题：** 高质量开源知识库、教程和 AI 工具指南，如何让 GitHub README 的首页区域承担“门面”职责，并把读者送到正确的网站、语言和阅读路径？
**研究范围：** Docusaurus、VitePress、The Rust Programming Language、MDN Web Docs、Hugging Face Course、OpenAI Cookbook 六个仍公开可访问的官方仓库/官方站点。
**观察维度：** README 首屏顺序、语言切换、阅读路径、网站与仓库分工、状态透明化。

本报告只记录公开页面中可以直接观察到的结构事实，再给出针对本项目的原创推断和可执行建议。没有复制外部正文、代码、图片、截图、品牌资产或页面实现；项目名称、文件名、按钮名、版本号和 URL 仅用于事实索引。没有进行用户测试、转化率分析、维护者访谈或后台发布链核查，因此不把“看起来清晰”写成学习效果证据。

## 1. 结论先行

### 1.1 README 的门面职责不是“把网站全文再贴一遍”

六个项目共同呈现出一个稳定模式：

    项目身份与边界
        ↓
    现在可以做什么 / 去哪里开始
        ↓
    网站、源文件、贡献入口之间的关系
        ↓
    版本、语言、维护或运行前置条件
        ↓
    可检查的状态与下一步

README 最有价值的工作不是承载所有教程正文，而是减少第一次访问时的五个不确定性：

1. 这是什么，服务谁？
2. 我现在应该读网站、仓库文件，还是运行示例？
3. 我应该按顺序读、按任务跳读，还是按主题浏览？
4. 语言入口是否真的有对应内容？
5. 哪些部分是当前版本、进行中、未运行或需要额外前置条件？

### 1.2 六个项目的主要分工不同

| 项目 | README 首屏的主要角色 | 官方网站的主要角色 | 最强的透明化信号 |
|---|---|---|---|
| Docusaurus | 产品定位、快速试用、安装、贡献和许可证桥接 | 展示 Docusaurus 能做什么，并提供文档、版本、语言和搜索入口 | 站点版本选择器、发布公告、README 中的构建/CI/包版本信号 |
| VitePress | 极短的包/项目说明，直接把读者送往文档站 | 用 hero、Guide、Reference、Quickstart 和语言菜单承载完整门面 | alpha 版本、stable 旧版入口、测试/发布 badge 与部署预览说明 |
| Rust Book | 明确这是书籍源文件，并同时服务读者和维护者 | 线性、可导航的完整阅读产品 | stable/beta/nightly 分流、Rust 版本/edition、CI、翻译进行中说明 |
| MDN Web Docs | 说明内容仓库、使命、本地构建和贡献方式 | 按 Web 技术、学习、工具和参考任务组织大型知识库 | active、machine-translated、retired locale 分层 |
| Hugging Face Course | 说明课程内容源、章节/语言目录、翻译和部署流程 | 课程阅读器，提供章节路径、测验、代码入口和语言切换 | 语言表逐项标记 WIP，页面链接回精确源文件 |
| OpenAI Cookbook | 极短的站点导流、运行前置条件和语言说明 | 以主题、精选、热门、全量列表和日期做任务型索引 | 每个条目带主题/日期；README 明确 API key 是运行前置条件 |

综合判断：本项目属于“学习产品 + 可审计仓库”，不能完全照搬框架项目的极简 README，也不应把 README 变成整本书。适合本项目的门面是：保留结果导向的阅读路由和证据边界，同时把仓库/网站/语言/状态关系压缩成一个首访者能快速理解的入口协议。

### 1.3 对本项目最重要的四条结论

1. **首屏先给选择，再给解释。** 先让读者按真实结果或问题进入，再解释 GPT、Codex、Tools、Skills 和 Agents 的概念关系。
2. **语言切换是内容契约，不是装饰。** 一个语言按钮只能证明存在入口；不能证明整套正文、章节锚点、实验和评测都已经翻译并审校。
3. **网站负责发现和阅读，仓库负责来源和证据。** 两边必须互相链接到同一个 content_id、locale 和状态，而不是各自维护一套相似但会漂移的目录。
4. **状态至少要拆成两条轴。** 项目/文档版本状态，与章节、实验、翻译和评测成熟度不是同一个事实；badge 也不能代替范围、日期和证据说明。

## 2. 方法、证据等级与边界

### 2.1 取样方法

本轮直接访问了每个项目的 GitHub 仓库 README 和官方阅读站或官方机制页。README 首屏观察以 GitHub 公开页面中 README 正文的起始区域为对象，不把 GitHub 自身的仓库导航当作项目内容。网站观察记录页面首屏可见的导航、版本、语言、主要 CTA、目录和内容分组。

所有来源均在 **2026-08-10** 访问。由于 README、版本号、站点目录、翻译覆盖和条目日期都可能变化，以下事实只代表该访问日期的公开状态。

### 2.2 证据标记

| 标记 | 含义 |
|---|---|
| fact | 能在项目官方仓库、官方文档或官方站点直接核对 |
| observed | 2026-08-10 在公开页面 DOM/可见文本/链接中观察到 |
| inference | 根据一个或多个事实推导出的设计判断 |
| recommendation | 面向本项目的可执行建议，不是外部项目的原话 |
| unknown | 公开资料不足以确认，例如用户是否因此更容易学会 |

### 2.3 不把这些信号误当质量证明

- star、fork、贡献者数量和页面数量只能说明公开规模，不能证明教程质量或学习效果。
- CI、npm、部署和版本 badge 只能支持对应范围内的工程状态，不能证明正文内容、翻译质量或读者已经掌握。
- 语言菜单只能证明菜单存在或某个 URL 可访问，不能证明所有章节、实验、代码和评测已经完成。
- 网站可以正常打开，不等于仓库源码、外部依赖、构建、运行和发布缓存全链路都已验证。

## 3. 六个项目的逐项观察

### A. Docusaurus：README 是“快速试用 + 文档站桥接”

**来源与访问日期**

- [D1] GitHub README：<https://github.com/facebook/docusaurus#readme>（访问：2026-08-10）
- [D2] 官方首页：<https://docusaurus.io/>（访问：2026-08-10）
- [D3] 官方国际化机制：<https://docusaurus.io/docs/i18n/introduction>（访问：2026-08-10）

#### README 首屏

fact / observed：README 正文从项目名、说明性图像和一句项目定位开始，随后很快给出一个短教程入口和在线 playground 入口，再进入安装、文档、贡献、社区和许可证。它没有把 Docusaurus 的全部配置文档放在 README 中，而是把“立即试一下”和“进入正式文档”放在前面。

inference：对一个文档框架来说，README 的首要任务是降低试用门槛并建立项目可信度；真正解释框架能力的内容交给网站。README 因而更像“产品包装背面的路线图”，不是教程正文。

#### 语言与阅读路径

observed：官方首页顶部有版本入口、英语语言入口、搜索和文档导航；首屏同时提供开始使用和 demo 两类动作。首页的能力介绍按 MDX、React 定制、翻译、文档版本和搜索分组。语言菜单现场可见 English、Français、Português (Brasil)、한국어 和中文（中国）等入口。

fact：国际化文档把“配置 locale → 放置翻译文件 → 构建并部署”作为流程，且把 Markdown/MDX 正文翻译、React/主题界面文案和插件数据分开。文档明确说明自动 locale 检测不由 Docusaurus 负责，部署策略由托管方决定；每个 locale 和插件有对应的翻译目录。

inference：语言切换被建模为可部署的内容产物，而不是一个只改变 UI 文案的客户端偏好。它也提醒本项目：语言状态要同时覆盖正文、导航、界面字符串和部署 URL。

#### 网站与仓库分工

observed：README 通过 docusaurus.io、教程和文档链接把用户送到站点；站点承担产品展示、版本选择、语言选择、搜索和文档阅读；仓库 README 保留安装、贡献和许可证边界。

#### 状态透明化

observed：站点首屏显示当前文档版本入口和版本发布公告，并保留旧版本入口；README 顶部有包版本、测试/CI、部署等工程信号，也把仓库代码许可证与文档许可证分开链接。

inference：它没有用一个“项目质量分数”概括一切，而是让版本、构建、部署和许可证各自承担窄范围的状态声明。这比一个没有范围说明的“稳定/完成”标签更可审计。

#### 对本项目的可执行建议

recommendation：

1. 保留一个短的“立即开始”入口和一个“访问展示页/完整阅读站”入口；不要把首页的全部能力说明复制到 GitHub README。
2. 在语言入口旁显示 locale 的内容状态，而不是只显示语言名称；至少区分 source、translated、WIP、not available。
3. 将项目状态、网站版本、章节状态、实验运行状态和翻译状态分开表达；每个状态旁链接到对应的 YAML、研究报告或质量记录。
4. 若未来生成多语言站点，正文翻译、导航文案、实验入口和搜索索引都应有各自的覆盖检查，不能只检查 README 文件是否存在。

### B. VitePress：极简 README，把“门面”让给文档站

**来源与访问日期**

- [V1] GitHub README：<https://github.com/vuejs/vitepress#readme>（访问：2026-08-10）
- [V2] 官方首页：<https://vitepress.dev/>（访问：2026-08-10）
- [V3] 官方国际化机制：<https://vitepress.dev/guide/i18n>（访问：2026-08-10）

#### README 首屏

fact / observed：README 的核心顺序非常短：一句项目定义，链接到文档站，再列出 changelog、贡献指南、许可证和支持者。它没有在仓库首页上放入安装教程、长目录或大段背景。

inference：这是“工具包型项目”的极简门面策略：README 只回答“它是什么、文档在哪里、如何参与”，让站点承担首屏产品表达。对 VitePress 这样的站点生成器，这种分工尤其自然。

#### 语言与阅读路径

observed：官方站点首屏有 Guide、Reference、版本入口、搜索、Quickstart、GitHub 和语言菜单；现场可见简体中文、葡萄牙语、俄语、西班牙语、韩语、波斯语和日语入口。站点把“先理解工具”和“查配置参考”分成两条导航，而不是把所有页面放进一条列表。

fact：国际化文档要求按 locale 组织目录和配置，并说明根路径不会自动重定向到某个语言目录；需要由服务器配置重定向，cookie 只能作为辅助的语言偏好持久化方式。

inference：可分享的 locale URL 是主身份，自动检测或 cookie 是辅助。这个边界与本项目已有的“语言 URL 可寻址、不能静默假装翻译完成”的原则一致。

#### 网站与仓库分工

observed：README 将文档站作为唯一主要阅读入口；站点则以 hero、Quickstart、Guide、Reference、版本和语言菜单完成产品叙事。仓库首页还保留 changelog、贡献指南和许可证，便于维护者从站点回到工程源。

#### 状态透明化

observed：站点导航显眼地显示 2.0.0-alpha.19，同时保留 1.6.4 旧版入口；README 可见测试、npm next、nightly 等信号，且贡献/部署说明提到 preview。项目没有用“全部文档已稳定”这种笼统表述掩盖 alpha 版本。

inference：对外门面最小并不等于状态最少。VitePress 把版本轨道放到读者最容易看到的位置，从而降低读者误以为当前版本是稳定版的风险。

#### 对本项目的可执行建议

recommendation：

1. 可以借鉴其“README 不复制网站”的克制，但本项目是学习系统，必须比 VitePress 多保留一张结果导向的阅读路由表。
2. 对章节/实验内容使用与版本轨道类似的显眼状态：例如 source、candidate、draft、verified、not_run；不要把 candidate 藏在文末。
3. 所有语言入口使用稳定的 content_id + locale + path 映射；?lang=、localStorage 或 cookie 只保存偏好，不承担内容身份。
4. 当站点存在 alpha、迁移中或只读旧版时，在入口层直接标记版本/迁移状态，而不是让读者通过失效链接自行发现。

### C. The Rust Programming Language：README 同时服务读者、构建者和维护者

**来源与访问日期**

- [R1] GitHub README：<https://github.com/rust-lang/book#readme>（访问：2026-08-10）
- [R2] 官方在线书：<https://doc.rust-lang.org/book/>（访问：2026-08-10）
- [R3] 官方翻译附录：<https://doc.rust-lang.org/book/appendix-06-translation.html>（访问：2026-08-10）

#### README 首屏

fact / observed：README 一开始明确这是书籍的源文件，并告诉读者可以免费在线阅读；随后说明 stable、beta、nightly 在线版本和代码清单下载，再进入 Requirements、Building、Contributing、Translations 和 Spellchecking。

inference：它没有把“读者入口”和“维护者入口”完全拆到两个仓库。README 先建立阅读承诺，再把构建、测试、贡献和语言治理放在同一个可信度层。这适合一份需要长期维护、可本地复现的教程源仓库。

#### 语言与阅读路径

observed：在线书的目录是明显的线性路径：前言、入门、基础概念、项目、测试、并发/异步、高级特性，最后以多线程 Web Server 综合项目收束。站点首屏优先显示完整目录，而不是一张营销式卡片墙。

fact：翻译附录明确列出多个语言项目，并说明大多数仍在进行中；README 也说明翻译工作通过专门标签和 issue 进入，而当前多语言合并受 mdBook 支持边界影响。

inference：Rust Book 的语言策略很诚实：在线主线稳定，翻译作为独立维护项目暴露，不把“有翻译仓库”当作“本书已完成多语言发布”。

#### 网站与仓库分工

observed：仓库 README 提供源文件、构建命令、测试命令和代码清单下载；官方站点提供带目录、锚点和搜索的阅读产物。仓库是可复现生产链，网站是读者阅读面。

#### 状态透明化

observed：README 把 stable、beta、nightly 分开，并提醒不同发行渠道的更新节奏；在线书正文显示所假定的 Rust 版本和 edition；仓库有 CI 状态；贡献段落还说明印刷版约束可能导致修复周期较长。

inference：它把“内容版本”“工具版本”“构建状态”“维护节奏”和“翻译状态”分别说清楚。读者因此知道一段代码适用于什么环境，也知道某类贡献为什么不会立即进入线上书。

#### 对本项目的可执行建议

recommendation：

1. README 首屏应明确“仓库是内容源、site 是阅读/发现产物”，并提供“在线阅读”和“本地复现/构建”两个不同入口。
2. 对易变事实卡、章节正文、实验代码和评测夹具分别标注适用版本、访问日期或复核日期；不要用一个项目版本代替所有内容版本。
3. 继续保留线性学习路径，但在其旁边提供按真实任务跳读的入口；两条路径最后都汇合到同一个能力单元。
4. 将维护节奏、已知未完成项和翻译限制写进门面层；这类“为什么现在没有完成”的解释本身就是信任资产。

### D. MDN Web Docs：README 是内容仓库说明，网站是大型任务分类器

**来源与访问日期**

- [M1] GitHub README：<https://github.com/mdn/content#readme>（访问：2026-08-10）
- [M2] 官方 Web 文档入口：<https://developer.mozilla.org/en-US/docs/Web>（访问：2026-08-10）
- [M3] 官方本地化治理页：<https://developer.mozilla.org/en-US/docs/MDN/Community/Translated_content>（访问：2026-08-10）

#### README 首屏

fact / observed：README 先说明 MDN Web Docs 是开放协作的 Web 技术内容项目，再说明使命、站点本地构建方式、内容/工程/翻译贡献和联系渠道。它更像“内容源仓库的工作说明”，而不是面向初学者的 Web 教程首页。

inference：当网站内容规模很大时，仓库 README 的门面目标不是替代网站目录，而是让贡献者知道内容从哪里来、怎样本地预览、如何加入维护。读者应被送到网站的信息架构，而不是被迫从仓库目录开始学习。

#### 语言与阅读路径

observed：官方 Web 入口按 HTML、CSS、JavaScript、Web APIs 等技术域分组，并把 Guides、Tutorials、Reference、Accessibility、Performance、Privacy、Security 和 Glossary 等内容类型分开。它提供的是“按问题/主题/内容类型浏览”的路径，而不是一条适合所有人的单线课程。

fact：本地化治理页把 locale 分为 active、machine-translated 和 retired。active locale 有维护团队和社区入口；机器翻译 locale 在独立仓库；已退休 locale 被归档并从网站隐藏。

inference：这是六个项目里最清楚的“状态透明化”样例之一：语言身份、维护责任、翻译方式和是否对读者开放被拆成了不同状态，而不是一个笼统的“支持 X 语言”。

#### 网站与仓库分工

observed：仓库的 README、贡献指南和本地启动命令面向内容/工程贡献者；网站提供面向开发者的参考、学习和工具入口；本地化内容还有单独的翻译仓库与指南。不同表面之间由官方链接连接，但没有把所有维护细节塞进阅读首页。

#### 状态透明化

observed：网站页面用 locale URL 标识英语版本；治理页面公开 locale 的维护分类、团队和仓库归属。README 的“内容源”定位与网站的“已发布阅读内容”定位不同，但二者没有被混写成同一成熟度。

## 4. 横向比较：README 门面应回答什么

### 4.1 首屏信息顺序

六个项目可以归纳为三种门面模式：

| 模式 | 代表项目 | 首屏适用对象 | 可迁移规则 |
|---|---|---|---|
| **极简桥接型** | VitePress、OpenAI Cookbook | 网站已经是主要阅读产品，仓库主要承担源代码/Notebook/贡献 | README 只保留身份、网站、运行前置条件、贡献和许可证 |
| **源仓库说明型** | MDN、Hugging Face Course | 仓库内容会被构建成大型知识产品，翻译/构建/贡献本身需要透明 | README 先说明内容源，再给读者入口和维护者入口，公开翻译/构建状态 |
| **学习与工程双入口型** | Rust Book、Docusaurus | 读者需要清晰阅读路线，同时维护者需要本地构建、版本和贡献说明 | README 先给读者可行动入口，再给源文件、版本、构建、测试和维护边界 |

inference：本项目最接近第三种，但还多一个维度：它要把“学习等级”和“真实任务入口”汇合到同一能力单元。因此 README 需要比 VitePress 多一个结果路由，比 Rust Book 多一层证据/状态索引。

### 4.2 语言切换不是同一种能力

| 层级 | 能证明什么 | 不能证明什么 | 本项目应记录 |
|---|---|---|---|
| README 语言链接 | 某个 locale 文件或入口被公开链接 | 正文完整、已审校、所有内部链接可用 | locale、canonical source、translation status |
| 网站语言菜单 | 站点提供一个切换控件或 locale URL | 当前章节、实验、搜索和 UI 全部覆盖 | content_id、target path、coverage、fallback rule |
| 翻译目录 | 仓库有翻译源文件 | 这些文件已构建、发布或仍被维护 | source revision、last reviewed、owner、next review |
| active/WIP/retired 分类 | 维护责任和发布策略有区别 | 内容本身一定没有错误 | owner、scope、evidence status |

recommendation：本项目的语言按钮旁应让读者看见“这条入口能读到什么”。例如“中文：章节源已提供；实验 3 个仍为迁移中”比单独的“中文”更接近真实承诺。若这会让首屏过重，可以把完整覆盖表链接到 locale matrix，但首屏至少要给出总状态。

### 4.3 网站与仓库的职责边界

| 读者问题 | README/仓库应该回答 | 网站应该回答 |
|---|---|---|
| 项目是什么 | 独立定位、范围、非目标、维护者 | 用首屏叙事和示例让人理解价值 |
| 从哪里开始 | 结果路由、先修条件、预计产物 | 直接进入可读页面并保留下一步 |
| 内容是否真实存在 | canonical 文件、content_id、源版本 | 页面 URL、目录、搜索和页面状态 |
| 能否贡献 | 构建、测试、来源、许可证、贡献流程 | 当前页面如何反馈/编辑，必要时回到仓库 |
| 是否完成 | 项目/内容/翻译/运行状态及其来源 | 对读者可见的阅读与实验可用状态 |

inference：最可靠的双表面关系不是“网站看起来漂亮、仓库看起来完整”，而是每个公开入口都能在另一面找到同一内容身份和状态。这样网站负责降低阅读成本，仓库负责降低审计成本。

### 4.4 状态透明化的最小模型

建议把公开状态拆成以下字段，而不是使用一个总标签：

    project_status       项目总体：draft / candidate / verified / production-ready
    surface_status       README、site、book、local build 各自是否存在/可用
    content_status       某章、实验、Skill 或研究报告的成熟度
    run_status            实验/评测是否实际运行，是否 not_run
    translation_status    source / translated / WIP / unavailable / retired
    claim_status          事实是否有一手来源、访问日期、范围和复核责任
    last_reviewed         最近一次核查日期
    next_review           下一次复核窗口或触发条件
    owner                 维护责任

fact：本项目现有 README 和 site 说明已经使用 candidate、draft、not_run、English default、Chinese toggle、迁移中等边界词。
recommendation：下一步不是增加更多 badge，而是让这些字段在 README、site 内容目录、locale matrix 和质量记录之间使用同一命名，并由检查脚本验证它们没有互相矛盾。

## 5. 对本项目的可执行改进路线

以下建议只针对本项目，不是对外部项目的复制方案。它们基于本仓库当前 README、site README 和现有治理/研究文件的公开结构提出；本轮没有实施这些修改。

### P0：稳定 GitHub README 的第一屏

1. **第一屏只保留一个主承诺、一个结果路由和一个信任状态。**
   当前 README 已经有项目定位、语言切换、candidate 状态和 Start with a result 表，这是正确基线。下一轮应把“访问展示页”和“完成第一个安全任务”明确成两个互补动作，避免项目索引、研究目录、语言治理和维护说明同时争夺第一行动。

2. **把结果路由补成可决策的四字段。**
   每条首屏入口至少显示：适合谁/前置条件、预计时间、会留下什么产物、用什么证据判断完成。现有“需要什么 → 从哪里开始 → 离开什么”表可以继续作为骨架，但应让读者不用打开第二个页面就知道第一步的成本和产物。

3. **在首屏明确“仓库 vs site”。**
   用一句短说明固定关系：仓库保存可审计源和状态，site 提供可浏览的发现层；两边的链接都回到同一个内容身份。不要让新读者通过猜测判断 README、book/ 和 site/ 谁才是 canonical source。

### P1：把语言和状态变成可验证契约

4. **为每个公开内容入口固定内容身份。**
   使用现有的 content_id 思路，把 content_id、locale、canonical source、site URL、source revision、translation status、content status 和 last reviewed 作为同一条记录。README 的语言链接、site 卡片、章节文件和评测索引都从这条记录生成或校验。

5. **首屏只显示总状态，详情链接到状态源。**
   README 可保留 candidate 和一句范围说明；具体章节/实验/语言覆盖放入状态源。每个状态词都要能追溯到 docs/governance/content-status.yaml、docs/governance/locale-matrix.yaml、质量记录或对应研究报告，而不是靠手工更新多处文案。

6. **禁止静默回退造成语言错觉。**
   当中文、英文或其他 locale 的目标章节不存在时，入口要明确显示“源语言可读”“翻译迁移中”或“尚未提供”。站点可以提供回到 source locale 的动作，但不能把英文正文标在中文页面身份下。

7. **把翻译覆盖拆到内容类型。**
   至少分开章节、实验、Skill、评测、研究报告和 UI 文案。一个 locale 有 README 不代表有完整学习路径；有章节译文也不代表实验验收和失败边界已经可用。

### P1：让网站与仓库互相证明

8. **每个 site 卡片回链到精确源文件，每个 README 路由进入可读页面。**
   不要只回到仓库根目录；链接应能定位到 chapter/lab/Skill/evaluation 的具体文件或稳定内容 ID。网站显示的标题、locale 和状态应来自同一源数据，避免站点出现“看得到但找不到源”的内容。

9. **将网站的“发现层”与仓库的“审计层”分开呈现。**
   site 首页可以按真实问题、学习等级、内容类型和最近更新组织；README 则保留 source、版本、状态、贡献和证据边界。研究目录、治理台账和外部事实源不必全部放在首屏，但必须有可信度层入口。

10. **对“站点可用”与“学习内容已验证”使用不同标签。**
    本地站点构建成功或页面能打开，只能支持 surface/build 状态；它不能把实验从 not_run 推成 verified，也不能把翻译从 WIP 推成完成。README 和 site 应同时显示这两个维度中与当前入口相关的那一项。

### P2：把维护和易变事实纳入门面

11. **易变事实采用条目级复核。**
    模型名、产品入口、命令、版本、权限、外部服务和价格等事实，应带一手 URL、访问日期、适用范围、owner 和 next review。README 只放摘要，详细事实卡放入研究/治理文件。

12. **把“为什么尚未完成”写成边界说明。**
    例如英文迁移 pending、实验 not_run、翻译覆盖不完整、站点仅 candidate。这样的说明应伴随下一步，而不是只用警示颜色；读者要知道现在能做什么、不能宣称什么、如何回到 source。

13. **贡献入口单独组织。**
    学习者先看到“开始一个任务/学习一个等级”；贡献者再进入来源登记、许可证、构建、校验、审查和维护责任。可以像 Rust Book、MDN 和 Hugging Face 一样保留贡献入口，但不要让贡献流程抢走学习者第一行动。

- [ ] 首屏能在不读完整仓库的情况下说明项目是什么、不是什么、适合谁。
- [ ] 首屏有一个结果导向的开始入口，并写出前置条件、预计时间、产物和证据。
- [ ] README、site、book、research、governance 的职责边界清楚。
- [ ] 每个语言入口有 locale 身份、可寻址 URL、覆盖状态和 source 回退规则。
- [ ] 语言菜单不把“入口存在”写成“整套内容已翻译”。
- [ ] 项目、surface、content、run、translation、claim 状态没有混成一个总标签。
- [ ] 每个易变事实有一手 URL、访问日期、范围、owner 和复核触发条件。
- [ ] 每个 site 入口都能回到精确源文件或 content_id；每个仓库入口都能进入真实可读页面。
- [ ] badge 只支持自己的窄范围声明，不能被读者合理误读为学习效果或生产就绪。

- [ ] 本地检查验证的是链接、locale、状态和内容映射；运行/浏览器/部署验证则单独记录，不相互冒充。
