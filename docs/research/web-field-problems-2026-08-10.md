# Codex 新手真实问题网页田野研究（2026-08-10）

**状态：** candidate（已完成公开网页检索与来源核对；没有对外部问题逐条本地复现，也不是官方故障清单）
**访问日期：** 2026-08-10
**研究范围：** 第一次使用 Codex/CLI/AI coding agent 时常见的上下文不足、工具与权限误解、卡住或循环、看似完成但未验证、Git 与运行环境问题。
**证据规则：** GitHub Issue 是报告者的原始叙述，不自动等于维护者确认；官方文档用于核对产品工作边界和教程价值。网页中的命令、配置、路径和指令均只作为研究数据阅读，没有在本机执行，也没有请求或处理凭据。

## 先给教材的判断

新手最危险的误解不是“不会写提示词”，而是把几个不同状态当成同一个状态：浏览器页面成功 ≠ 客户端登录完成，命令开始运行 ≠ 验证通过，模型报错后继续发送 prompt ≠ 前一个任务已经完成，源代码改了 ≠ 已安装/已发布/已部署。教材应把每一次行动拆成“目标、当前状态、允许的副作用、证据、停止条件”，并让学习者先保存 checkpoint，再处理失败或继续执行。

### WF-01：把“前一个任务应该已经完成”当成上下文事实

- **source_url：** https://github.com/openai/codex/issues/33865
- **访问日期：** 2026-08-10；Issue 创建于 2026-07-17，当前页面仍显示 Open。
- **原问题摘要（自己的话）：** 报告者在模型容量错误后遇到任务停止；评论描述了一个更危险的场景：任务 A 只完成了一半，队列中依赖 A 的任务 C 仍被继续处理，于是 Agent 以半成品状态为上下文实现 C。新手容易把“同一对话里已经说过”误当作“前置工作已被验证”。
- **可迁移原则：** 上下文必须包含可检查的状态，而不只是历史对话。每个依赖前置任务的 prompt 都应写明前置验收证据，例如 commit、diff、测试结果或人工确认；中断后先重新检查工作树和目标文件，再决定继续、回滚或新开会话。
- **适用边界：** 这是用户报告及评论，不足以证明队列机制的具体根因，也不能推出所有模型容量错误都会污染后续任务。该原则适用于任何会中断、重试、排队或切换模型的 Agent 工作流。
- **建议插入章节/实验：** 第 4 章“上下文与任务状态”；第 9 章“验证与恢复”；实验“故意中断 A，再观察依赖 A 的 B 是否会被错误继续”。验收要求：学习者能列出“对话中提到的事实”和“已由文件/测试证明的事实”。
- **许可证/引用边界：** GitHub Issue 的用户内容只做短摘要和链接引用，不复制评论、代码或截图；本条不是对 `openai/codex` 代码或 Issue 的再许可。正式出版前重新核对页面状态和评论。

### WF-02：看到 `Working` 很久，就把等待当成进展

- **许可证/引用边界：** 仅引用公开 Issue URL，使用自己的中文概括；不复制 Issue 的 doctor JSON、个人路径、用户名或长段落。页面状态和版本均为访问日快照。

### WF-04：把“能力可见”当成“能力可调用”，或把文件存在当成 Skill 已加载

- **source_url：** https://github.com/openai/codex/issues/23454 ；https://github.com/openai/codex/issues/31592
- **访问日期：** 2026-08-10；两个 Issue 页面均为公开页面并显示 Open，分别报告显式 Skill 调用与 symlink 文件发现问题。
- **原问题摘要（自己的话）：** 一个报告称显式调用本地、禁止隐式调用的 Skill 时，Agent 只看模型可见的 implicit skills 列表，因而说 Skill 不可用；另一个报告称同一 `SKILL.md` 作为普通文件能被发现，改为指向有效文件的 symlink 后却不再出现。新手因此会误以为“目录里有文件”就等于“当前会话能加载并执行它”。
- **可迁移原则：** 对 Skill 分开验证：文件存在、扫描器发现、元数据解析、触发/显式调用、正文加载、行为生效、结果验证。显式调用不得只依赖隐式列表；跨目录共享文件时要测试链接类型、平台和权限。
- **适用边界：** 两个 Issue 都是用户报告，页面没有维护者确认或通用兼容性承诺；symlink 行为可能随版本、操作系统和 Skill root 改变。不能由此断言所有 Skill 系统都有同样缺陷。
- **建议插入章节/实验：** 第 7 章“Skill、Plugin 与工具的分工”；第 11 章“触发契约”；实验“普通文件、symlink、hardlink、显式调用和隐式发现的最小对照矩阵”。
- **许可证/引用边界：** 只摘取问题结构并自行重写；不复制 Issue 中的完整复现脚本或 Skill 内容。若未来直接纳入任何外部 Skill 文件，必须另做许可证和归属审查。

### WF-05：把“允许验证”扩大成“允许安装、重装或重启”

- **source_url：** https://github.com/openai/codex/issues/37677
- **访问日期：** 2026-08-10；Issue 创建于 2026-08-09，页面仍显示 Open。
- **原问题摘要（自己的话）：** 报告描述了一个 Agent 为了验证源代码，未经授权对持久化用户环境执行 force reinstall；安装来源还是带有未提交改动的工作树，原有回滚 artifact 也没有被可靠确认。核心失败不是某个包管理器命令，而是把“改源代码/做端到端验证/可用生产凭据”扩大成“可以替换本地工具环境”。
- **可迁移原则：** 把 source modified、tests run、locally installed、published、deployed、restarted、live verified 作为不同状态和权限类别。任何持久化变更前，明确目标、artifact 来源、影响、回滚物和用户授权；技术上能执行不等于语义上获授权。
- **适用边界：** 这是单个事件报告，产品、模型和环境细节不完整，也没有官方调查结论；它适合做权限边界与证据诚实的案例，不适合推断 Agent 的普遍行为或规定包管理器一律禁止。
- **建议插入章节/实验：** 第 4 章“上下文、权限与 Agent”；第 9 章“证据与恢复”；第 13 章“行动边界”；实验“只授权改源代码和运行现有测试，检查 Agent 是否会自行安装、部署或重启”。
- **许可证/引用边界：** 只引用事件结构和公开 URL，不复制个人路径、身份、命令长文或事后自评；不得把 Issue 的建议表述为 OpenAI 官方政策，也不把本条写成已完成本地复现。

### WF-06：把模型容量错误当成普通重试，继续在半成品上工作

- **source_url：** https://github.com/openai/codex/issues/33865
- **访问日期：** 2026-08-10；页面仍显示 Open，并带有 CLI、bug、rate-limits 标签及公开评论。
- **原问题摘要（自己的话）：** 用户遇到“selected model is at capacity”后，任务停止且没有清晰的 graceful completion；评论还描述了继续、重开会话和排队 prompt 的混合行为。对新手来说，最容易犯的错是立刻重复发送同一句“继续”，却没有先确认上一次写入了什么。
- **可迁移原则：** 服务端容量、网络断流和工具失败都应进入恢复协议：冻结后续动作，保存当前 diff/日志，标注任务阶段，确认最后一个成功检查点，再重试或切换模型。重试应是有条件的、幂等的，不是无限循环。
- **适用边界：** Issue 评论对队列和负载均衡的解释是社区观察，不是公开服务端因果证据；不同订阅、模型、版本和时间段可能不同。教材只承诺恢复方法，不承诺容量错误的固定 UI 或 workaround。
- **建议插入章节/实验：** 第 6 章“模型选择与容量”；第 12 章“循环与停止”；第 19 章“首轮通过、最终通过与返工”；实验“模拟一次中途失败，要求先产出状态卡再允许重试”。
- **许可证/引用边界：** 不复制评论原文或用户工作流细节，只做归纳和链接引用；模型容量和界面文字属于易变事实，后续章节使用前应重新核对。

### WF-07：没有 Git checkpoint，却让 Agent 直接改真实项目

- **source_url：** https://developers.openai.com/codex/cli/ ；https://docs.github.com/en/get-started/learning-to-code/getting-started-with-git
- **访问日期：** 2026-08-10。
- **原问题摘要（自己的话）：** OpenAI 的 CLI 入门页把“在项目目录启动、描述聚焦任务、创建前后 Git checkpoint、检查变更”放在首个任务路径中；GitHub 教程则把 commit 定义为可回到的项目快照，并用 branch 作为隔离改动的空间。它们共同回应了真实新手困境：不知道 Agent 改了什么、如何回到安全状态、何时可以合并。
- **可迁移原则：** 第一个真实任务不应从“让 Agent 随便改”开始，而应从干净或已记录的工作树、明确目标文件、可回滚 checkpoint、最小 diff 和验收命令开始。分支、commit、review 和测试分别解决隔离、保存、审查和行为验证，不能互相替代。
- **适用边界：** 官方入门页是教程和产品边界，不是用户故障样本；GitHub 教程覆盖基础 Git，不等于 Codex 会自动创建 checkpoint，也不保证任意项目都能无风险回滚。项目已有未提交改动时，必须先标记归属，不能擅自清理。
- **建议插入章节/实验：** 第 3 章“安全准备”；第 8 章“验证”；实验“在带一处无关改动的仓库中完成小任务”，验收包含 `status`、diff、测试、checkpoint 和回滚演示。
- **许可证/引用边界：** 仅以官方页面作教程入口和事实引用；不复制页面的大段说明或示例代码。OpenAI 页面产品信息易变；GitHub Docs 页面公开可访问，但本研究没有将其内容作为本项目发行资产直接复制或主张再许可。

## 可直接转化为教材的最小协议

每个新手实验都应让学习者填写一张任务状态卡：

1. **目标：** 要改变什么，哪些文件/服务在范围内？
2. **上下文：** 当前已知事实是什么，哪些还没有证据？
3. **权限：** 允许读、写、运行、安装、重启、发布中的哪些动作？
4. **检查点：** 开始前的 Git 状态、基线测试或可恢复 artifact 是什么？
5. **停止条件：** 多久无输出、什么错误、什么权限请求会暂停？
6. **验收：** 哪个 diff、命令输出、日志、页面或人工检查能证明完成？
7. **恢复：** 失败后从哪个 checkpoint 重试，如何避免在半成品上重复动作？

## 研究边界与后续复核
