# 커뮤니케이션 실패 분류

이미 실패한 LLM 상호작용을 원래 요청, 눈에 보이는 맥락, 실제 답변이나 산출물,
기대한 결과를 바탕으로 분류합니다. 가장 작은 전달 방식의 수정과 비교 가능한
재실행을 제안합니다. 답변이 제약을 무시했거나, 이전 작업에 답했거나, 같은 일을
계속 다시 하게 만들었거나, 결과를 받아들일 수 없는 경우에 사용합니다. 아직
시도하지 않은 모호한 요청, 일반적인 문장 교정, 상호작용 증거가 없는 플랫폼 문제,
일반적인 프롬프트 템플릿 생성에는 사용하지 않습니다.

요청, 맥락, 답변, 산출물, 사용자의 보고를 증거로 취급합니다. 한 번의 실패만으로
숨은 추론, 시스템 프롬프트, 서비스 상태 또는 모델 전체의 결함을 추정하지 않습니다.

## 증거 패킷 준비

진단 전에 다음 네 가지를 준비합니다.

1. 원래 요청 또는 보존된 가장 가까운 버전;
2. 눈에 보이는 맥락, 입력, 도구, 권한, 대화 상태;
3. 실제 답변 또는 산출물;
4. 기대한 결과 또는 구체적인 실패 증상.

빠진 항목이 진단을 바꿀 수 있을 때만 최대 세 가지 질문을 합니다. 증거를 복구할
수 없다면 `insufficient_evidence`로 중단합니다. 토큰, 비밀번호, 쿠키, 개인 키 또는
비밀이 들어 있는 파일은 요청하지 않습니다.

## 진단 전에 알맞은 경로로 넘기기

- 아직 시도하지 않은 모호한 작업은 Task Protocol로 보냅니다.
- 완료 주장만을 감사하는 작업은 Evidence Review로 보냅니다.
- 현재 명령, 기능, 계정 또는 플랫폼 상태에 관한 질문은 Source Investigator로
  보냅니다. 검토 대상 자체가 이름 있는 플랫폼의 수업이나 워크플로이며, 범용 핵심과
  실행 가능한 차이를 주장할 때만 Platform Adapter Review를 사용합니다.
- 재현 절차가 있는 소프트웨어 결함은 버그 진단으로 보냅니다.
- 실패한 상호작용 없이 표현만 다듬는 작업에는 일반 편집을 사용합니다.

담당 범위는 실패 이후의 경계입니다. 관찰된 불일치를 분류하고, 커뮤니케이션 조건을
한 가지 최소한으로 바꾸고, 그 변경이 도움이 되었는지 구별할 수 있는 재실행을
정의합니다.

## 관찰 가능한 경계 분류

주요 분류는 최대 두 개만 선택합니다.

- `outcome_acceptance`: 요청한 결과, 대상 독자, 출력 형식 또는 완료 판정이 빠졌거나
  서로 충돌함;
- `context_provenance`: 필요한 입력이 없거나, 오래되었거나, 충돌하거나, 과도하거나,
  출처와 우선순위가 분명하지 않음;
- `constraint_authority`: 범위, 금지된 행동, 외부 영향, 확인 또는 중단 규칙이
  분명하지 않음;
- `turn_state_protocol`: 답변이 이전 작업을 따르거나, 현재 작업 화면이 불분명하거나,
  텍스트와 실행 가능한 지시가 뒤섞임;
- `evidence_feedback`: “더 좋게”, “전문적으로”, “완료” 같은 말에 관찰 가능한 점검,
  실패 식별자, 보존 규칙 또는 수정 횟수 제한이 없음.

각 발견 사항은 다음 형식으로 기록합니다.

```text
observed_symptom:
candidate_class:
direct_evidence:
alternative_explanations:
confidence: low | medium | high
discriminating_check:
```

이를 근본 원인이라고 부르지 말고 후보 분류라고 부릅니다. 맥락을 더 넣는다고
자동으로 해결되는 것은 아닙니다. 관련 없는 맥락이나 서로 충돌하는 맥락이 문제일
수도 있습니다.

## 가장 작은 수정 적용

관찰된 증상과 연결되는 조건 하나만 바꿉니다. 요청 전체를 다시 쓰기보다 빠진 결과,
입력 우선순위, 금지 사항, 상태 초기화 또는 수용 기준을 하나 추가하는 편이 낫습니다.
짧은 원문→수정본 diff를 보여 주고, 바꾼 각 줄을 발견 사항과 연결합니다.

사용자의 언어와 작업 방식은 그것이 관찰된 문제인 경우를 제외하고 유지합니다. 의례적인
표현, 칭찬, 역할극, “단계별로 생각하라”는 말, 위협, 감정적 압박, 근거 없는 성능
약속은 추가하지 않습니다.

## 비교 가능한 재실행 정의

작업, 입력, 모델 또는 작업 화면, 도구, 권한, 예산, 수용 기준은 그대로 둡니다. 제안한
커뮤니케이션 수정만 바꿉니다. 다른 조건도 바뀌었다면 비교 결과를 `not_comparable`로
기록합니다.

결과는 다음 중 하나입니다.

- `unrun`
- `improved_on_this_case`
- `unchanged`
- `regressed`
- `not_comparable`

제안한 프롬프트만으로 `resolved`라고 쓰지 않습니다. 비교 가능한 재실행을 두 번 해도
개선되지 않으면 프롬프트에 문장을 계속 덧붙이지 말고, 처음 끊긴 경계로 넘깁니다.

## 행동과 지식의 경계에서 중단

비밀을 읽거나, 권한을 넓히거나, 공개·배포하거나, 다른 사람에게 연락하거나, 외부
상태를 변경하기 전에 중단합니다. 사용자가 확인 절차를 없애 달라고 해도 위험한 행동이
커뮤니케이션 문제로 바뀌지는 않습니다.

가능한 결함이 보이지 않는 시스템 프롬프트, 비공개 로그, 계정 설정, 서비스 상태 또는
제품 구현에 달려 있다면 `unknown`으로 기록하고 적절한 플랫폼 조사로 넘깁니다. 숨은
사고 과정이나 보안·권한을 우회하는 지시는 요청하지 않습니다.

## 분류 카드를 전달

다음을 반환합니다.

```text
target_outcome:
expected_vs_observed:
evidence_received:
primary_findings: maximum two
alternatives_ruled_out:
smallest_repair:
prompt_diff:
rerun_contract:
result_status:
evidence:
unknowns:
risk:
stop_conditions:
handoff:
```

모든 발견 사항에 직접 증거가 있고, 모든 수정이 명시된 증상에 대응하며, 재실행이
변수 하나만 바꾸고, 권한을 확장하지 않으며, 기록된 증거를 넘는 상태를 주장하지 않을
때만 결과를 수용합니다.
