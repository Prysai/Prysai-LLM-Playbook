# 中文共通編輯訊號

這些是審稿線索，不是禁詞表，也不能用來判定文字是否由 AI 產生。先確認目標
語系、文件場景與作者語氣，再判斷一組現象是否造成實際閱讀成本。單一詞語、
破折號、排比、設問或過於工整的句子都不是充分證據。

若目標是台灣繁體中文，必須同時讀取
[locales/zh-Hant-TW.md](locales/zh-Hant-TW.md)。其他中文語系應另用該地區的
用詞、標點與專業慣例，不要把台灣規則套用到所有中文。

## 高可信度訊號

### 空泛開場與旁白

- 「在當今快速發展／日新月異的……時代」
- 「隨著……不斷發展」卻沒有交代具體變化
- 「眾所周知」「毋庸置疑」「值得注意的是」
- 「從本質上來說」「事實上」後面只接普通陳述
- 技術文件開頭先說「讓我們深入探討／一起來看看」

直接進入條件、問題或操作。若背景確實影響專案，寫出那項變化及其影響。

### 無依據的宣傳與過寬承諾

- 革命性、顛覆性、劃時代、次世代、業界領先
- 強大、完善、全面、卓越、極致、智慧、高效
- 無縫、零門檻、一站式、全方位、開箱即用
- 「適用於所有場景」「滿足各類需求」「徹底解決」

先找可驗證依據。沒有依據就改寫成功能、限制、步驟或可觀察結果；不要用另一個
較弱的形容詞取代原本的宣傳詞。

### 抽象商業語言

- 賦能、引領、助力、打造、構建新生態
- 聚焦痛點、降本增效、閉環、抓手、底座、矩陣
- 「釋放……潛力」「開啟……新篇章」「重新定義……」
- 「提供更好的體驗」卻沒有說明改了什麼

換成誰使用什麼功能完成什麼事情。若詞語是專案、引用來源或特定產業正式採用的
術語，保留原文。

### 模板式節奏

- 多段反覆使用「不僅……更……」「不是……而是……」
- 每段固定三項並列、四字格口號或同一種總結句
- 「無論你是……還是……都能……」列舉過寬受眾
- 結尾一律上升到願景、未來、可能性或生態
- 用短句堆疊製造重量，例如「更快。更準。更可靠。」
- 每段先摘要、再重述、最後再說一次結論

修正機械式重複，不是消滅排比、對比或節奏。真正的因果和範圍不能為了變短而
刪除。

### 虛構的親密、權威或作者立場

- 沒有來源卻寫「我們都曾遇過」「你一定知道」
- 沒有測試卻寫「實務證明」「深受開發者信賴」
- 為了「像人」而新增個人故事、情緒、偏好或強烈意見
- 把未確認的推測改成肯定語氣

自然感不能靠捏造經驗。若原文沒有第一手立場，就不要替作者補一個。

## 常見誤判

以下形式本身通常不需要改：

- 為避免歧義而重複 API 名稱、步驟或安全警告；
- 規格、錯誤訊息與變更紀錄中的平行結構；
- 中文省略主詞，或以系統、API、命令作為技術主體；
- 承載範圍的「通常」「僅」「可能」「預設」「至少」；
- 說明因果或步驟所需的轉折詞與連接詞；
- 引文、品牌語句、社群慣用語與作者刻意使用的幽默；
- 教學為避免操作錯誤而保留的必要重述。

只有在形式和其他問題共同出現，並造成含糊、冗長、失真或聲調不合時才修改。

## 語意與結構保真

逐項比對修改前後：

- 主詞、受詞、責任歸屬與引用來源；
- 數字、日期、版本、比較級與量化範圍；
- 條件、例外、否定、機率、風險與相容性限定；
- 因果關係、時間順序與操作步驟；
- 直接引文、法律文字、安全要求與授權條款；
- 程式碼、命令、API、錯誤訊息、URL、錨點與預留位置；
- Markdown 標題、表格、清單、程式碼區塊與 frontmatter。

受保護內容疑似有誤時，提出問題或另列建議，不要混在一般潤稿中悄悄修正。

## 中文開源專案檢查

- README 首屏先說產品做什麼、服務誰、如何開始，不先堆願景。
- 將「簡單易用」換成實際步驟；將「高效」換成已有證據的行為或指標。
- 對安全、隱私、效能與相容性聲明保留必要條件與限制。
- PR 與 issue 分開陳述觀察、判斷、取捨和驗證，不宣傳例行工作。
- 錯誤訊息交代發生什麼、影響什麼、下一步是什麼，不責怪使用者。
- 翻譯保持資訊對齊，但句法、語氣與術語應符合目標語系。
