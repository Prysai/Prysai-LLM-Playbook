# 台灣繁體中文編輯層（`zh-Hant-TW`）

本檔只處理台灣繁體中文的用字、標點、語域與在地慣例。內容與邏輯仍以
[../../SKILL.md](../../SKILL.md) 的保真流程為準。

## 何時套用

符合下列任一條件時套用：

- 使用者明確指定繁體中文、台灣中文或 `zh-Hant-TW`；
- 檔案已有穩定的台灣用語與繁體字慣例；
- 專案明確將台灣列為這份在地化內容的目標市場。

只有「文字是繁體」並不足以推定目標是台灣。香港、澳門與其他繁體中文語系應使用
各自的 locale pack。來源中的官方名稱、引文、品牌、UI 標籤或搜尋關鍵字即使使用
簡體字，也不應自動轉換。

## 編輯順序

1. 先鎖定產品名、程式碼、命令、連結、版本、數字、條件、否定與引文。
2. 修正會讓台灣讀者誤解的詞義或明顯的地區用語。
3. 統一一般敘述的繁體字與中文標點。
4. 依 README、文件、PR、UI 等場景調整語氣。
5. 最後再處理節奏與贅詞；不要為了「自然」改動受保護內容。

## 字形與標點

- 一般敘述使用正體字與全形中文標點：`，。；：？！`。
- 中文引文優先使用 `「」`，巢狀引文使用 `『』`。若專案已有一致格式、引用需
  逐字保留，或工具要求 ASCII 引號，沿用原格式。
- 程式碼、CLI 命令、路徑、URL、email、版本號、正規表示式與資料格式維持半形。
- 中英文與數字之間是否留空格，依專案既有 style guide 決定；不要把個人排版偏好
  當成台灣中文的硬性規則。
- 省略號、破折號、括號與冒號只在格式混亂或影響理解時統一，不進行全檔機械替換。
- 標題可不加句號；完整句子的清單項目是否加句號，以同層級一致為準。

## 地區詞彙

下表是需要檢查的候選詞，不是無條件取代規則。

| 來源詞或語境 | 台灣常用候選 | 判斷方式 |
| --- | --- | --- |
| 软件／硬件 | 軟體／硬體 | 官方產品名除外 |
| 默认 | 預設 | `default branch` 可寫「預設分支」 |
| 配置 | 設定、組態、設定檔 | 依動作、系統架構或檔案種類選擇 |
| 信息 | 資訊、訊息 | `information` 與 `message` 不同 |
| 数据 | 資料、數據 | 一般 data 用「資料」；統計量可用「數據」 |
| 文件 | 檔案、文件 | filesystem object 用「檔案」；document 用「文件」 |
| 代码 | 程式碼 | `code of conduct` 是「行為準則」 |
| 日志 | 紀錄、日誌、log | 依 UI、專案術語與資料型態選擇 |
| 网络／服务器 | 網路／伺服器 | 官方品牌用語除外 |
| 用户 | 使用者 | 引文、UI 原文與組織慣例除外 |
| 项目 | 專案、項目 | project 與 list item 不同 |
| 仓库 | 儲存庫、repository | 優先沿用專案或平台既有譯名 |
| 依赖 | 相依性、相依套件 | 依抽象關係或 package 選擇 |
| 组件／插件 | 元件／外掛、插件 | `plugin` 是否翻譯由產品詞彙表決定 |
| 扩展 | 擴充功能、延伸 | 依名詞或動詞語境選擇 |
| 激活／禁用 | 啟用／停用 | 帳號或授權流程有時用「啟用」 |
| 反馈／支持 | 回饋／支援 | 「支持一項主張」仍可用「支持」 |
| 运行 | 執行、運作 | command 用「執行」；system state 可用「運作」 |
| 创建／获取 | 建立／取得 | `fetch`、`get` 仍依 API 語意 |
| 加载／保存 | 載入／儲存 | `save changes` 可寫「儲存變更」 |
| 访问 | 存取、造訪 | data access 與 website visit 不同 |
| 字符串／数组／对象 | 字串／陣列／物件 | 以專案語言社群慣例為準 |
| 函数／参数／返回 | 函式／參數／回傳 | `return key` 不是一律「回傳」 |
| 线程／进程 | 執行緒／處理程序 | 保留 API 與作業系統正式名稱 |
| 缓存／内存 | 快取／記憶體 | `in-memory` 可寫「記憶體內」 |
| 兼容 | 相容 | 保留精確的版本與平台範圍 |
| 视频／芯片 | 影片／晶片 | 官方媒體類型或品牌除外 |
| 打印／鼠标／屏幕 | 列印／滑鼠／螢幕 | `print()` 函式不得翻譯 |
| 通过 | 透過、通過 | 手段用「透過」；測試結果用「通過」 |
| 优化 | 改善、最佳化、優化 | 寫出改善項目；避免空泛承諾 |

遇到詞表未涵蓋的用語時，依序查：

1. 專案自己的繁中 UI、詞彙表與既有文件；
2. 上游產品或平台的台灣官方譯名；
3. 同領域台灣技術社群的穩定用法；
4. 原詞，並在首次出現時補上必要說明。

不要為了「純中文」翻譯已被台灣開發者穩定使用的 API、套件、命令或英文術語。

## 場景與語氣

### README 與首頁

- 第一段交代工具做什麼、給誰用，以及最關鍵的已驗證差異。
- 用一個可執行範例取代成串形容詞。
- 可使用「你」，但不要每句都直接喊話或預設讀者感受。

### 文件與教學

- 清楚分開先決條件、動作、預期輸出與失敗後的處理方式。
- 指令可直接用「執行」「開啟」「確認」，不必每步都寫「請」。
- 保留能避免操作錯誤的重述、條件和轉折。

### Issue、PR 與技術討論

- 分開寫觀察到的現象、目前判斷、取捨與驗證結果。
- 未確認的原因使用「可能」「目前看來」等範圍詞。
- 不把例行實作寫成成就敘事，也不替維護者預設共識。

### Release note 與 changelog

- 寫出使用者看得到的行為差異、影響範圍與必要動作。
- `breaking change`、棄用與遷移步驟不可弱化。
- 歷史紀錄除非有事實錯誤或使用者指定，不為統一文風而重寫。

### UI 與錯誤訊息

- 優先交代發生什麼、影響什麼、下一步能做什麼。
- 按鈕使用能預測結果的動詞；不要為品牌感犧牲辨識度。
- 不責怪使用者，不在動作完成前宣稱成功。

### 社群、法律與安全文字

- 社群文字可以溫暖，但不要套入制式熱情、宏大願景或虛構共鳴。
- 法律條款、授權、行為準則、安全步驟與揭露時程預設逐字保留。
- 若使用者真的要修改政策，只指出語意與風險差異，不把它當一般潤稿。

## 誤判防護

保留以下合理形式：

- 技術文件為了可搜尋性重複完整產品名或 API 名稱；
- 逐步操作中的平行句型；
- 錯誤訊息、規格和測試案例的固定結構；
- 為相容性、安全或法律精度而使用較正式的語氣；
- 作者刻意的台灣口語、幽默、語助詞或中英夾用；
- 引用他人文字時保留原地區用語。

不要刻意加入錯字、口頭禪、破碎句或不規則標點來假裝真人。

## 交付前檢查

- 是否仍是 `zh-Hant-TW`，而不是只把簡體字轉成繁體字？
- 是否保留所有主詞、數字、版本、否定、條件、例外與引用來源？
- 是否誤改官方名稱、UI 標籤、SEO 關鍵字、命令或程式碼？
- 是否把不同含義的來源詞機械換成同一個台灣詞？
- 是否符合文件場景，而不是所有內容都變成同一種聊天語氣？
- 是否能指出每項較大修改解決的具體問題？
