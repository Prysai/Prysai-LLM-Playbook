# 작업 프로토콜

하나의 작업을 실행 가능하고 감사 가능한 상태로 만드는 가장 작은 계약을 작성합니다.
이 Skill은 경계를 정하며 작업 자체를 실행하지 않습니다.

## 발동 경계와 인계

“개선해 줘”, “만들어 줘”, “조사해 줘”, “연결해 줘”처럼 범위, 권한, 수용 기준 또는
부작용이 불분명한 모호한 동사를 맡습니다.

다음과 같은 경우에는 넘깁니다.

- `$skill`이 명시됨: 해당 경로를 유지하고 필수 안전 질문만 추가;
- 완전한 프로토콜이 이미 있고 실행을 요청함: Workflow Orchestrator 또는 적절한
  분야 경로로 인계;
- 기존 결과가 사실인지 질문함: Evidence Review;
- 남은 일이 출처 발견임: Research Router;
- 남은 일이 제품 포지셔닝임: Product Context;
- 남은 일이 Skill 선택 또는 설치임: Skill Selector.

자기 자신을 다시 호출하지 않습니다. 인계 경로는 적을 수 있지만 다른 Skill이 돌아온
뒤 사용자가 범위를 바꾸지 않았다면 프로토콜을 재구성하지 않습니다.

## 필수 입력과 누락 처리

`goal`, `background`, `inputs`, `constraints`, `allowed_actions`,
`acceptance_evidence`, `failure_handling`, `delivery_format`을 수집합니다. `risk`도
`R0`, `R1`, `R2`, `R3` 중 하나로 분류하고, 공유 상태나 외부 상태를 바꿀 수 있다면
`owner`, `checkpoint`, `rollback`, `confirmation`을 기록합니다. 모르는 내용은
가정하지 말고 `missing`으로 표시합니다. 위험이 낮은 로컬 입력은 먼저 확인하고,
범위·위험·구현 선택·수용 기준을 바꾸는 질문만 합니다. 외부 대상, 비밀 포함, 운영
환경, 되돌릴 수 없는 작업 또는 소유권과 관련된 정보가 비어 있으면 `blocked on
<field>`를 반환하고 실행하지 않습니다.

프로토콜을 준비 완료로 표시하기 전에 다음 위험 게이트를 적용합니다.

| 위험 | 필요한 계약 | 기본 행동 |
|---|---|---|
| `R0` | 정확한 읽기 범위, 입력, 수용 확인, 쓰기 금지 | 설명 또는 읽기 전용 검사만 수행 |
| `R1` | 정확한 로컬 대상, 허용된 쓰기·명령, 체크포인트, 롤백 대상, 되돌릴 수 있는 수용 확인 | 로컬의 가역적 작업만 수행 |
| `R2` | 정확한 공유·외부 대상, 데이터 노출, 담당자, 작업별 확인, 체크포인트, 롤백, 증거 담당자 | 지정된 확인이 기록될 때까지 차단 |
| `R3` | `R2`의 모든 항목과 제한된 목적, 독립 확인, 비가역·운영·비밀·광범위 권한 작업 직전의 명시적 확인 | 즉시 중단; 이 프로토콜만으로 실행하지 않음 |

`read`, `edit`, `run`, `network`, `commit`, `push`, `publish`, `deploy`, `restart`,
`secret` 접근은 `allowed`, `not_allowed`, `confirmation_required` 중 하나의 상태를
가지는 별도 작업 기록으로 적습니다. 광범위한 권한, 토큰, 로그인 또는 이전 승인은
목록에 없는 작업을 허용하지 않습니다. 여러 작업을 요청받았다면 각 단계의 위험,
대상, 확인, 체크포인트, 롤백, 수용 증거를 나눕니다.

## 작성 순서

1. 결과와 혜택을 받는 사람을 밝힙니다.
2. 파일, 시스템, 계정, 버전, 기간을 한정합니다.
3. 허용된 읽기, 쓰기, 명령, 네트워크 호출, 커밋, 푸시, 공개를 분리합니다.
4. 위험 수준을 정하고 정확한 대상, 담당자, 확인 지점, 체크포인트, 롤백, 관찰 가능한
   수용 증거를 정의합니다.
5. 가정과 불확실한 점을 표시하고 다음 인계 경로를 정합니다.

각 수용 주장에 대해 그것을 증명할 관찰 가능한 산출물이나 명령 출력, 그리고 그 출력이
증명하지 못하는 경계를 적습니다. 프로토콜은 실행 증거가 아닙니다. 요청되었거나,
계획되었거나, 시작되었거나, 그럴듯한 텍스트가 돌아왔다는 이유만으로 완료로 표시하지
않습니다.

## 위험, 부작용, 확인

`R0`는 설명·읽기 전용, `R1`은 되돌릴 수 있는 로컬 변경, `R2`는 외부 서비스나 공유
저장소 변경, `R3`는 운영 환경·비가역·비밀·광범위 권한 작업입니다. 프로토콜에는
부작용을 설명할 수 있지만 실행에는 정확한 대상과 작업에 대한 명시적 승인이 필요합니다.
“모든 권한”에 대한 확인은 좁은 대상을 대신하지 못합니다. 프로토콜에 비밀을 넣지
않습니다. `R2`/`R3` 확인은 대상과 작업을 정한 뒤에 해야 합니다. 성공한 빌드, 로그인,
드라이런은 뒤이은 쓰기, 푸시, 공개, 배포, 재시작을 승인하지 않습니다.

## 강제 중단

수혜자나 결과가 없거나, 소유권이 불분명하거나, 수용을 관찰할 수 없거나, 비밀이
노출되거나, 대상이 모호하거나, 비가역 작업에 확인이 없거나, 프로젝트 규칙과 요청이
충돌하면 `blocked`를 반환합니다. 실패한 조건과 중단 이유를 보존합니다. 한 가지 명시된
조건이 바뀌고 새 확인 방법이 제시된 경우에만 재시도할 수 있습니다. 그렇지 않으면
무한히 반복하지 말고 `blocked` 또는 `unverified`를 반환합니다. 위험이나 범위를 바꾸는
누락 필드를 추측한 기본값으로 채우지 않습니다.

## 고정 출력

정확히 다음을 반환합니다.

1. `protocol_status` (`ready_to_execute` 또는 `blocked_on`)
2. `goal`
3. `background`
4. `inputs_and_unknowns`
5. `constraints`
6. `allowed_actions_and_permissions` — 상태, 대상, 위험, 데이터 노출, 확인 요건을
   분리한 작업 기록
7. `acceptance_evidence`
8. `failure_handling`
9. `delivery_format`
10. `handoff`
11. `risk`
12. `owner_and_confirmation` — 결정 담당자, 확인 지점, 확인되지 않은 작업
13. `checkpoint_and_rollback` — 관찰 가능한 산출물, 복구 대상, 복구 판단
14. `content_status`

## 증거와 상태 매핑

모든 필드가 갖춰지기 전에는 `draft`, 로컬 완전성 검사를 통과했지만 실행 전이면
`candidate`, 명시된 수용 증거를 관찰한 뒤에만 `verified`, 운영·롤백·유지보수·소유권
게이트까지 통과한 뒤에만 `production-ready`입니다. 필수 필드를 위험 게이트와 대조하고,
각 작업을 정확한 대상과 권한 상태에 비교하며, 모든 수용 주장을 관찰 가능한 검사까지
추적합니다. `R2`와 `R3`에서는 확인 지점, 체크포인트, 롤백, 데이터 노출 기록을 따로
확인합니다. 프로토콜이 준비된 것만으로 작업이 끝났다고 표시하지 않습니다.
