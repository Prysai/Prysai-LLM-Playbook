# タスク・プロトコル

一つのタスクを実行可能で監査できる状態にするために、最小限の契約を作ります。
この Skill は境界を定義するもので、タスク自体を実行するものではありません。

## 起動条件と引き継ぎ

「改善する」「作る」「調べる」「接続する」など、範囲、権限、受け入れ条件、
副作用が明確でない依頼を担当します。

次の場合は引き継ぎます。

- 明示的に `$skill` が指定されている：その経路を保ち、安全上必須の質問だけを
  追加する。
- 完全なプロトコルがあり、利用者が実行を求めている：Workflow Orchestrator または
  適切な分野の経路に渡す。
- 既存の結果が本当かを尋ねている：Evidence Review。
- 残っている作業が出典の発見である：Research Router。
- 残っている作業が製品の位置付けである：Product Context。
- 残っている作業が Skill の選択またはインストールである：Skill Selector。

自分自身を呼び出してはいけません。引き継ぎ先は示せますが、別の Skill から
戻った後に、利用者が範囲を変えない限りプロトコルを再構築しません。

## 必須入力と不足項目の扱い

`goal`、`background`、`inputs`、`constraints`、`allowed_actions`、
`acceptance_evidence`、`failure_handling`、`delivery_format` を集めます。さらに
`risk` を `R0`、`R1`、`R2`、`R3` のいずれかに分類し、共有状態または外部状態を
変えうる場合は `owner`、`checkpoint`、`rollback`、`confirmation` を記録します。
不明な点は仮定せず `missing` と記録します。ローカルで低リスクの入力は先に確認し、
範囲、リスク、実装の選択、受け入れ条件が変わる質問だけをします。外部、秘密情報、
本番、不可逆操作、所有権に関する不足がある場合は `blocked on <field>` を返し、
実行しません。

プロトコルを準備完了とする前に、次のリスクゲートを適用します。

| リスク | 必要な契約 | 初期アクション |
|---|---|---|
| `R0` | 正確な読み取り範囲、入力、受け入れ確認、書き込み禁止 | 説明または読み取り専用の確認のみ |
| `R1` | 正確なローカル対象、許可された書き込み・コマンド、チェックポイント、復元先、可逆な受け入れ確認 | ローカルで可逆な操作のみ |
| `R2` | 正確な共有・外部対象、データ公開、担当者、操作ごとの確認、チェックポイント、ロールバック、証拠担当者 | 指定された確認が記録されるまでブロック |
| `R3` | `R2` の全項目に加え、限定した目的、独立した確認、不可逆・本番・秘密情報・広い権限の操作直前の明示的確認 | 停止。このプロトコルだけでは実行を許可しない |

`read`、`edit`、`run`、`network`、`commit`、`push`、`publish`、`deploy`、
`restart`、`secret` へのアクセスは、`allowed`、`not_allowed`、
`confirmation_required` のいずれかを持つ別々のアクション記録にします。広い
権限、トークン、ログイン、以前の承認は、一覧にない操作を許可しません。複数の
操作を頼まれた場合は、リスク、対象、確認、チェックポイント、ロールバック、
受け入れ証拠を分けた段階に分割します。

## 作成の順番

1. 結果と、その恩恵を受ける人を示す。
2. ファイル、システム、アカウント、バージョン、期間を限定する。
3. 許可された読み取り、書き込み、コマンド、ネットワーク、コミット、プッシュ、
   公開を分ける。
4. リスクを割り当て、正確な対象、担当者、確認地点、チェックポイント、
   ロールバック、観測可能な受け入れ証拠を定義する。
5. 仮定と不明点を示し、次の引き継ぎ先を決める。

受け入れに関する主張ごとに、それを証明する観測可能な成果物またはコマンド出力と、
それで証明できない境界を記載します。プロトコルは実行の証拠ではありません。依頼
された、計画された、開始された、もっともらしい文が返った、という理由だけで完了
とはしません。

## リスク、副作用、確認

`R0` は説明または読み取り専用、`R1` は可逆なローカル変更、`R2` は外部サービスや
共有リポジトリの変更、`R3` は本番、不可逆、秘密情報、広い権限を伴う操作です。
プロトコルで副作用を記述することはできますが、実行には正確な対象と操作に対する
明示的な許可が必要です。「すべての権限」への確認は限定された対象の代わりに
なりません。プロトコルに秘密を含めません。`R2`/`R3` の確認は、対象と操作を固定
した後に行います。ビルド、ログイン、ドライランの成功は、後続の書き込み、プッシュ、
公開、デプロイ、再起動の確認にはなりません。

## 強制停止

受益者または結果がない、所有権が不明、受け入れを観測できない、秘密が公開される、
対象が曖昧、不可逆操作の確認がない、プロジェクト規則と依頼が衝突する場合は
`blocked` を返します。失敗した条件と停止理由を残します。再試行は、明示した条件が
一つ変わり、新しい確認方法を示した場合だけ許可します。それ以外は無限に再試行せず、
`blocked` または `unverified` を返します。リスクや範囲が変わる不足項目を、推測した
既定値で埋めません。

## 固定の出力

次の順で、ちょうどこれを返します。

1. `protocol_status`（`ready_to_execute` または `blocked_on`）
2. `goal`
3. `background`
4. `inputs_and_unknowns`
5. `constraints`
6. `allowed_actions_and_permissions` — 状態、対象、リスク、データ公開、確認要件を
   分けたアクション記録
7. `acceptance_evidence`
8. `failure_handling`
9. `delivery_format`
10. `handoff`
11. `risk`
12. `owner_and_confirmation` — 決定の担当者、確認地点、未確認の操作
13. `checkpoint_and_rollback` — 観測可能な成果物、復元先、復旧の判断
14. `content_status`

## 証拠と状態の対応

すべての項目がそろうまでは `draft`、ローカルの完全性確認を通過したが未実行なら
`candidate`、指定した受け入れ証拠を観測した後だけ `verified`、本番、ロールバック、
保守、所有権のゲートまで通過した後だけ `production-ready` とします。必須項目を
リスクゲートと照合し、各アクションを正確な対象と権限状態に比べ、受け入れ主張を
観測可能な確認までたどります。`R2` と `R3` では確認地点、チェックポイント、
ロールバック、データ公開の記録を別々に確認します。プロトコルの準備ができただけで
タスク完了とはしません。
