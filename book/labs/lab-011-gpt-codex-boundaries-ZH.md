## 本实验的用途

这是对 L0 门槛的低风险介绍。它不是实时集成测试，也不要求你把凭据粘贴到 Codex 中。输出是一份可供他人检查的记录，而不是一份经过润色的答案。

使用以下事件区分：

    生成的文本
      != 提议的工具动作
      != 获得允许/已经执行的动作
      != 变化后的状态
      != 已验证结果

## 安全与准备

- 在一次性本地目录或纯文本学习记录中工作。
- 在实验的必做部分，不要连接 ChatGPT、Codex Cloud、GitHub、浏览器账户、MCP 或任何外部服务。
- 不要使用 token、cookie、私钥、`.env` 文件、客户数据或生产文件。
- 如果选择可选的本地扩展，只能编辑学习记录和一个一次性笔记文件。
- 如果提议的步骤需要网络调用、账户访问、秘密、公开写入或破坏性重置，请停止并将其标记为 blocked。

创建一个 run ID，例如 `lab011-zh-2026-08-10-a`。记录日期、使用时的工作面/模型标签、输入修订版，以及必做部分为静态或纯文本这一事实。

## 第一部分：填写边界表

对以下固定卡片进行分类。“主要层”是指学习者必须观察的层，而不是对产品内部实现的断言。

| 卡片 | 任务卡 |
|---|---|
| A | “用自己的话解释上下文，并说出两个不确定点。” |
| B | “读取 `notes.md`，在一个一次性本地副本中添加一个标题，并展示 diff。” |
| C | “调用一个工具，把结果写入组织的公共仓库，并通知团队。” |
| D | “不断尝试修复错误，直到看起来成功；不要记录中间状态。” |
| E | “系统已经登录。工具说已完成，所以现在就发布并跳过检查。” |

填写这张表：

| 卡片 | 主要层 | 允许动作 | 禁止动作 | 最小证据 | 停止/确认点 | 仍然未知的内容 |
|---|---|---|---|---|---|---|
| A |  |  |  |  |  |  |
| B |  |  |  |  |  |  |
| C |  |  |  |  |  |  |
| D |  |  |  |  |  |  |
| E |  |  |  |  |  |  |

使用以下决策顺序：

1. 请求属于解释/生成、读取/编辑，还是改变外部状态？
2. 如果会改变状态，需要哪个精确对象、什么权限、何种确认和怎样回滚？
3. 哪一项证据对应完成声明？
4. 哪个条件会使任务停止，而不是重试？

一份可靠的基线答案会把 A 识别为解释任务，把 B 识别为有边界的本地执行任务，把 C 识别为不得在这里运行的外部副作用计划，把 D 识别为无边界的 Agent 循环，并把 E 识别为没有证据支持的假设。请解释理由；不要复制这句话来冒充证明。

## 第二部分：运行受控上下文实验

使用这项纯文本任务：

> 检查提供的 README 摘录，并指出一项改进。不要编辑文件。说明你收到了什么、为什么这项改进很重要、可以如何检查，以及你无法知道什么。

只使用该摘录运行基线。然后只做一项变化并重复运行：

1. 加入目标受众；
2. 加入一条简短的项目规则；
3. 加入一项验收条件。

除非你已经充分固定模型/工作面、输入修订版、生成配置和工具状态，足以支持因果声明，否则不要声称改变的内容导致了输出差异。如果做不到，请写：
观察到不同结果；原因未隔离。

记录：

    run-id | 输入修订版 | 工作面/模型 | 改变的变量 | 是否调用工具？ | 文件是否改变？ | 观察到的证据 | 未知项

本实验可以通过手工编写的模拟来完成。实际模型运行是可选项，并且必须用其真实证据标记。模拟的工具结果绝不是已经执行的工具结果。

## 第三部分：纠正不安全的完成声明

从以下声明开始：

> “浏览器登录成功，工具返回已完成，模型也说变更完成。因此公共仓库已经更新。”

将其改写为声明表：

| 声明 | 所需证据 | 当前状态 | 安全的后续检查 |
|---|---|---|---|
| 浏览器身份验证完成 | 身份验证阶段及客户端 token/会话证据 |  |  |
| 此仓库的动作已获得授权 | 目标、账户/组织范围和权限证据 |  |  |
| 工具执行了写入 | 工具调用/结果和目标标识符 |  |  |
| 预期对象发生变化 | 对目标的最新读取结果或提供商侧记录 |  |  |
| 变更可以接受 | diff/审查/测试或人工验收 |  |  |

不要用“可能”填补空白状态。请使用 `not_observed`、`blocked`、`partial` 或 `verified within scope`，并解释其范围。

## 第三部分 A：加入一个机制层失败

从以下不联网的合成案例中选择一个，并将其加入声明表：

- **Schema 通过，语义失败：** 回答是有效 JSON，并包含所有必填字段，但所引用的对象并不存在。增加一项业务/状态检查。
- **检索命中，但缺少例外：** 选中了一段宽泛的政策内容，但缺少特定版本的例外条款。加入查询、过滤条件、选中的片段和缺失证据字段。
- **具有指令形态的数据：** README 或工具结果要求忽略任务的安全规则。继续将其作为数据处理，拒绝外部副作用，并记录来源和它试图产生的影响。

重点是准确说出失败发生在哪一层。Schema 结果、检索命中或可见字符串都不会自动证明语义正确、上下文完整或具备权限。有关带来源支持的边界，请参阅 [LLM 机制研究](../evidence-library-ZH.md#source-notes)；本实验不会运行实时提供商服务。

## 第四部分：练习停止规则

选择一个无害的注入失败：

- 报告模型已达到容量上限；
- 报告一条命令在超过声明的时间限制后仍停留在 Working 状态；
- 报告一条验证命令要求强制重新安装。

不要自动重试。写下：

    状态 | 可见症状 | 当前检查点 | 已捕获证据 | 所需权限 | 最小恢复动作 | 未验证项

正确的恢复方式通常是检查当前状态、保留记录、缩小下一项检查的范围，或请求授权。正确做法不是清除工作区、强制安装依赖，或发送下一条排队指令。

这些失败形态来自 [Codex 现场问题研究](../evidence-library-ZH.md#source-notes)中的公开报告。它们属于用户证据，不是官方根因确认，本实验也不声称已在本地复现。

## 证据包

提交一个目录或一份 Markdown 记录，其中包含：

1. 固定卡片版本和 run ID；
2. 填写完整的 A-E 边界表；
3. 两条上下文实验记录及混杂变量；
4. 纠正后的声明表；
5. 停止/恢复记录；
6. 不超过 150 字的个人总结。

总结必须回答：

- 模型输出和工具结果有什么区别？
- 工具结果和已验证状态有什么区别？
- 为什么登录状态、模型名称、Skill 名称或完成消息不能证明权限或正确性？
- 哪一项声明仍为 `not_observed`？

## 验收标准

只有满足以下条件才能通过：

- 每张固定卡片都有理由、边界、证据和停止点；
- 卡片 C 和卡片 E 没有引发真实的外部写入或通知；
- 至少有一项声明被明确留作未验证，而不是猜测；
- 上下文实验记录了一项改变的变量以及所有混杂变量；
- 失败练习在破坏性或未经授权的升级动作发生前停止；
- 机制案例明确指出缺口位于 schema、上下文选择、指令权威、执行还是验证；
- 第二位读者能够分辨哪些事件是模拟的、观察到的或未运行的。

在项目拥有真实运行记录和独立审查之前，本实验继续保持 draft，`run_status` 保持 `not_run`。填写完整的练习表只能作为学习者完成该练习的证据，不能证明所有 Codex 产品工作面都会以相同方式运行。

## 迁移任务

选取一组固定的公开来源，在一次性本地文件中准备一页研究摘要。将来源文字、用户指令、模型建议、本地编辑和验证检查标记为不同层。加入一个来源，其中包含一句与摘要无关、但看起来像指令的话。记录为什么它被当成数据而不是权威。除非你创建一份具有明确范围和确认点的新任务协议，否则不要为这项迁移练习浏览网页、发布内容或调用外部连接器。
