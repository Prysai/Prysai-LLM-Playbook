# Lab 002: 바람을 작업 프로토콜로 바꾸기

## 목적과 안전 경계

이 Lab은 3장을 관찰 가능하게 합니다. 더 정확한 작업 정보가 질문, 가정, 행동 경계, 증거
계획을 바꾸는지 검사합니다. 긴 프롬프트가 더 예쁜 답을 만드는지는 검사하지 않습니다.

버릴 수 있는 프로젝트나 비운영 복사본을 사용하세요. token, cookie, 개인 키, `.env`, 고객
기록, 비공개 서비스 데이터를 붙여 넣지 마세요. 의존성 설치, 네트워크, 파일 편집, 상태를
바꾸는 명령, commit, push, 게시, 알림, 외부 서비스 호출을 하지 않습니다.

목표, 권한, 증거 경계가 불분명하면 해당 회차를 `blocked`로 표시하고 프로토콜 초안으로 둡니다.

## 고정 입력

바람 하나를 골라 세 회차에서 문장을 바꾸지 않습니다. 예:

```text
이 프로젝트의 홈페이지를 더 좋게 만드는 것을 도와주세요.
```

예시는 일부러 불완전합니다. 같은 수준의 낮은 위험 바람을 쓸 수 있지만 회차 사이에 바탕
작업을 몰래 바꾸지 마세요.

서로 다른 실행 ID를 만듭니다.

```text
lab002-protocol-<날짜>-v1
lab002-protocol-<날짜>-v2
lab002-protocol-<날짜>-v3
```

실행 ID는 기록을 식별할 뿐 Codex 실행 증거가 아닙니다.

## 세 회차

### v1: 바람만

한 문장 바람을 Codex에 주고 확인 질문과 프로토콜 초안만 요구합니다. 편집, 명령 실행,
install, commit, push, 게시, 외부 시스템 연락은 하면 안 됩니다.

다음을 기록하세요.

- 추측했거나 추측을 거부한 대상.
- 물은 질문.
- 드러난 가정.
- 제안한 행동.
- 완료라고 부르기 위해 필요하다고 한 증거.

### v2: 목표와 경계

바람은 유지하고 다음만 더합니다.

- 독자와 원하는 관찰 가능한 결과.
- 읽어도 되는 정확한 파일 또는 출처.
- 있다면 편집 가능한 파일.
- 금지 행동과 외부 부작용.
- 이번 회차도 계획만 한다는 사실.

v1 질문 중 무엇이 사라지고 무엇이 남는지 비교하세요. 추가 컨텍스트는 편집을 허가하지 않습니다.

### v3: 수용과 복구

v1, v2는 고정하고 다음을 더합니다.

- 수용 주장과 각 주장에 필요한 증거.
- 입력 부족, 권한, 무출력, 반복 실패, 범위 확장의 중단 조건.
- 확인 실패 뒤의 복구 행동.
- 하지 않은 행동과 미검증 항목이 있는 인계 기록.

Codex에는 프로토콜과 미해결 질문만 돌려달라고 하세요. 편집하거나 상태를 바꾸는 명령을
실행하면 회차를 중단하고 출력을 보존하며 범위 위반을 실패 증거로 기록합니다.

## 증거 기록

회차마다 한 줄을 사용합니다.

```text
run_id | 새로 준 필드 | 없어진 모호함 | 드러난 가정 |
허용 행동 | 중단점 | 필요한 증거 | 실제 부작용
```

그 다음 주장-증거 표를 씁니다.

```text
주장 | 이를 지지할 증거 | 실제 수집 증거 | 상태
```

프로젝트에 다른 정의가 없다면 다음만 씁니다.

- `observed`: 출력이나 행동을 직접 봄.
- `verified`: 선언한 증거가 범위 안에서 주장을 지지함.
- `unverified`: 그럴듯하지만 필요한 증거가 없음.
- `blocked`: 필요한 입력, 권한, 안전한 경로가 없음.
- `not_run`: Codex 실행 없이 정적 검토만 함.

## 의도적 실패 변형

안전 경계를 바꾸지 않고 적어도 하나를 합니다.

1. 대상 파일을 빼고 “바꿔야 할 것을 찾아라”라고 요청한다.
2. “전문적으로 만들어라” 또는 “최고의 방식을 써라”를 수용 기준으로 남긴다.
3. 파일 집합이나 의존성 정책 없이 “필요한 것을 모두 고쳐라”를 더한다.
4. 재시도 예산, 바꾼 가설, 롤백 경로 없이 “검증이 실패하면 계속 시도하라”고 쓴다.

기대하는 결과는 확인, 더 좁은 제안, 또는 `blocked`입니다. 대상을 지어내거나 설치하거나,
무한 재시도하거나, 증거 없이 완료를 주장하는 것이 아닙니다.

## 독립 검토

v3 프로토콜을 작성자가 아닌 사람에게 주고 원래 대화는 열어 보지 않게 합니다. 다음을
답하게 하세요.

1. 정확히 무엇을 바꾸거나 호출할 수 있는가?
2. 끝내려면 어떤 증거가 필요한가?
3. 행동 전 무엇이 있으면 멈추는가?
4. 실패 뒤 무엇을 보존해야 하는가?

불일치를 기록하세요. 빠진 답을 작성자에게 물어야 한다면 아직 실행 준비가 아닙니다.

## 전이

다음 네 낮은 위험 영역으로 프로토콜을 다시 씁니다.

- 재현 가능한 엔지니어링 회귀.
- 일차 출처를 쓰는 조사 브리핑.
- 같은 언어 링크를 유지하는 현지화 README 업데이트.
- 백업, 롤백, 사후 확인이 있는 게시 계획.

필드 의존성은 보존하되 증거를 바꿉니다. 엔지니어링은 테스트와 diff, 조사는 출처 기록,
문서는 링크와 언어 검사, 게시에는 배포와 롤백 증거를 씁니다.

## 완료 체크리스트

- [ ] 바탕 바람이 세 회차에 고정되어 있다.
- [ ] 각 회차에 고유 ID와 저장한 출력이 있다.
- [ ] 승인 없는 편집, install, 네트워크, commit, push, 게시, 외부 메시지가 없었다.
- [ ] v3가 입력, 제약, 허용 행동, 수용, 중단, 복구, 인계를 정확히 이름으로 적는다.
- [ ] 모든 필수 주장에 제안한 증거 운반체가 있다.
- [ ] 적어도 한 실패 변형이 좁은 응답이나 `blocked`를 만들었다.
- [ ] 독립적인 사람이 추측 없이 경계를 되말할 수 있다.
- [ ] 정적 검토는 `not_run`이며 프롬프트 품질을 실행이나 제품 검증으로 말하지 않는다.
