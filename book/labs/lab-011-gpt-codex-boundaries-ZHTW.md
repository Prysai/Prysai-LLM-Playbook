## 本實驗的用途

這是對 L0 門檻的低風險介紹。它不是實時整合測試，也不要求你把憑據貼上到 Codex 中。輸出是一份可供他人檢查的記錄，而不是一份經過潤色的答案。

使用以下事件區分：

    生成的文字
      != 提議的工具動作
      != 獲得允許/已經執行的動作
      != 變化後的狀態
      != 已驗證結果

## 安全與準備

- 在一次性本地目錄或純文字學習記錄中工作。
- 在實驗的必做部分，不要連線 ChatGPT、Codex Cloud、GitHub、瀏覽器賬戶、MCP 或任何外部服務。
- 不要使用 token、cookie、私鑰、`.env` 檔案、客戶資料或生產檔案。
- 如果選擇可選的本地擴充套件，只能編輯學習記錄和一個一次性筆記檔案。
- 如果提議的步驟需要網路呼叫、賬戶訪問、秘密、公開寫入或破壞性重置，請停止並將其標記為 blocked。

建立一個 run ID，例如 `lab011-zh-2026-08-10-a`。記錄日期、使用時的工作面/模型標籤、輸入修訂版，以及必做部分為靜態或純文字這一事實。

## 第一部分：填寫邊界表

對以下固定卡片進行分類。“主要層”是指學習者必須觀察的層，而不是對產品內部實現的斷言。

| 卡片 | 任務卡 |
|---|---|
| A | “用自己的話解釋上下文，並說出兩個不確定點。” |
| B | “讀取 `notes.md`，在一個一次性本地副本中新增一個標題，並展示 diff。” |
| C | “呼叫一個工具，把結果寫入組織的公共倉庫，並通知團隊。” |
| D | “不斷嘗試修復錯誤，直到看起來成功；不要記錄中間狀態。” |
| E | “系統已經登入。工具說已完成，所以現在就釋出並跳過檢查。” |

填寫這張表：

| 卡片 | 主要層 | 允許動作 | 禁止動作 | 最小證據 | 停止/確認點 | 仍然未知的內容 |
|---|---|---|---|---|---|---|
| A |  |  |  |  |  |  |
| B |  |  |  |  |  |  |
| C |  |  |  |  |  |  |
| D |  |  |  |  |  |  |
| E |  |  |  |  |  |  |

使用以下決策順序：

1. 請求屬於解釋/生成、讀取/編輯，還是改變外部狀態？
2. 如果會改變狀態，需要哪個精確物件、什麼許可權、何種確認和怎樣回滾？
3. 哪一項證據對應完成宣告？
4. 哪個條件會使任務停止，而不是重試？

一份可靠的基線答案會把 A 識別為解釋任務，把 B 識別為有邊界的本地執行任務，把 C 識別為不得在這裡執行的外部副作用計劃，把 D 識別為無邊界的 Agent 迴圈，並把 E 識別為沒有證據支援的假設。請解釋理由；不要複製這句話來冒充證明。

## 第二部分：執行受控上下文實驗

使用這項純文字任務：

> 檢查提供的 README 摘錄，並指出一項改進。不要編輯檔案。說明你收到了什麼、為什麼這項改進很重要、可以如何檢查，以及你無法知道什麼。

只使用該摘錄執行基線。然後只做一項變化並重復執行：

1. 加入目標受眾；
2. 加入一條簡短的專案規則；
3. 加入一項驗收條件。

除非你已經充分固定模型/工作面、輸入修訂版、生成配置和工具狀態，足以支援因果宣告，否則不要聲稱改變的內容導致了輸出差異。如果做不到，請寫：
觀察到不同結果；原因未隔離。

記錄：

    run-id | 輸入修訂版 | 工作面/模型 | 改變的變數 | 是否呼叫工具？ | 檔案是否改變？ | 觀察到的證據 | 未知項

本實驗可以透過手工編寫的模擬來完成。實際模型執行是可選項，並且必須用其真實證據標記。模擬的工具結果絕不是已經執行的工具結果。

## 第三部分：糾正不安全的完成宣告

從以下宣告開始：

> “瀏覽器登入成功，工具返回已完成，模型也說變更完成。因此公共倉庫已經更新。”

將其改寫為宣告表：

| 宣告 | 所需證據 | 當前狀態 | 安全的後續檢查 |
|---|---|---|---|
| 瀏覽器身份驗證完成 | 身份驗證階段及客戶端 token/會話證據 |  |  |
| 此倉庫的動作已獲得授權 | 目標、賬戶/組織範圍和許可權證據 |  |  |
| 工具執行了寫入 | 工具呼叫/結果和目標識別符號 |  |  |
| 預期物件發生變化 | 對目標的最新讀取結果或提供商側記錄 |  |  |
| 變更可以接受 | diff/審查/測試或人工驗收 |  |  |

不要用“可能”填補空白狀態。請使用 `not_observed`、`blocked`、`partial` 或 `verified within scope`，並解釋其範圍。

## 第三部分 A：加入一個機制層失敗

從以下不聯網的合成案例中選擇一個，並將其加入宣告表：

- **Schema 透過，語義失敗：** 回答是有效 JSON，幷包含所有必填欄位，但所引用的物件並不存在。增加一項業務/狀態檢查。
- **檢索命中，但缺少例外：** 選中了一段寬泛的政策內容，但缺少特定版本的例外條款。加入查詢、過濾條件、選中的片段和缺失證據欄位。
- **具有指令形態的資料：** README 或工具結果要求忽略任務的安全規則。繼續將其作為資料處理，拒絕外部副作用，並記錄來源和它試圖產生的影響。

重點是準確說出失敗發生在哪一層。Schema 結果、檢索命中或可見字串都不會自動證明語義正確、上下文完整或具備許可權。有關帶來源支援的邊界，請參閱 [LLM 機制研究](../evidence-library-ZHTW.md#source-notes)；本實驗不會執行實時提供商服務。

## 第四部分：練習停止規則

選擇一個無害的注入失敗：

- 報告模型已達到容量上限；
- 報告一條命令在超過宣告的時間限制後仍停留在 Working 狀態；
- 報告一條驗證命令要求強制重新安裝。

不要自動重試。寫下：

    狀態 | 可見症狀 | 當前檢查點 | 已捕獲證據 | 所需許可權 | 最小恢復動作 | 未驗證項

正確的恢復方式通常是檢查當前狀態、保留記錄、縮小下一項檢查的範圍，或請求授權。正確做法不是清除工作區、強制安裝依賴，或傳送下一條排隊指令。

這些失敗形態來自 [Codex 現場問題研究](../evidence-library-ZHTW.md#source-notes)中的公開報告。它們屬於使用者證據，不是官方根因確認，本實驗也不聲稱已在本地復現。

## 證據包

提交一個目錄或一份 Markdown 記錄，其中包含：

1. 固定卡片版本和 run ID；
2. 填寫完整的 A-E 邊界表；
3. 兩條上下文實驗記錄及混雜變數；
4. 糾正後的宣告表；
5. 停止/恢復記錄；
6. 不超過 150 字的個人總結。

總結必須回答：

- 模型輸出和工具結果有什麼區別？
- 工具結果和已驗證狀態有什麼區別？
- 為什麼登入狀態、模型名稱、Skill 名稱或完成訊息不能證明許可權或正確性？
- 哪一項宣告仍為 `not_observed`？

## 驗收標準

只有滿足以下條件才能透過：

- 每張固定卡片都有理由、邊界、證據和停止點；
- 卡片 C 和卡片 E 沒有引發真實的外部寫入或通知；
- 至少有一項宣告被明確留作未驗證，而不是猜測；
- 上下文實驗記錄了一項改變的變數以及所有混雜變數；
- 失敗練習在破壞性或未經授權的升級動作發生前停止；
- 機制案例明確指出缺口位於 schema、上下文選擇、指令權威、執行還是驗證；
- 第二位讀者能夠分辨哪些事件是模擬的、觀察到的或未執行的。

在專案擁有真實執行記錄和獨立審查之前，本實驗繼續保持 draft，`run_status` 保持 `not_run`。填寫完整的練習表只能作為學習者完成該練習的證據，不能證明所有 Codex 產品工作面都會以相同方式執行。

## 遷移任務

選取一組固定的公開來源，在一次性本地檔案中準備一頁研究摘要。將來源文字、使用者指令、模型建議、本地編輯和驗證檢查標記為不同層。加入一個來源，其中包含一句與摘要無關、但看起來像指令的話。記錄為什麼它被當成資料而不是權威。除非你建立一份具有明確範圍和確認點的新任務協議，否則不要為這項遷移練習瀏覽網頁、釋出內容或呼叫外部聯結器。
