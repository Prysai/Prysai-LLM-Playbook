## 이 실험의 목적

이 실험은 L0 게이트를 저위험으로 소개합니다. 실제 통합 테스트가 아니며 자격 증명을
Codex에 붙여 넣도록 요구하지 않습니다. 결과물은 다듬어진 답변이 아니라 다른
사람이 검사할 수 있는 기록입니다.

다음 사건 구분을 사용하세요.

    생성된 텍스트
      != 제안된 도구 행동
      != 허용되고 실행된 행동
      != 변경된 상태
      != 검증된 결과

## 안전 및 준비

- 일회용 로컬 디렉터리 또는 일반 텍스트 학습 기록에서 작업하세요.
- 필수 실험 구간에서는 ChatGPT, Codex Cloud, GitHub, 브라우저 계정, MCP 또는
  외부 서비스에 연결하지 마세요.
- 토큰, 쿠키, 개인 키, `.env` 파일, 고객 데이터 또는 프로덕션 파일을 사용하지
  마세요.
- 선택적 로컬 확장을 수행하는 경우에도 학습 기록과 일회용 메모 파일만 편집하세요.
- 제안된 단계에 네트워크 호출, 계정 접근, 비밀 정보, 공개 쓰기 또는 파괴적인
  초기화가 필요하면 중단하고 `blocked`로 표시하세요.

`lab011-ko-2026-08-10-a`와 같은 실행 ID를 만드세요. 날짜, 사용했다면 표면/모델
라벨, 입력 리비전, 필수 구간이 정적 또는 텍스트 전용이라는 사실을 기록하세요.

## 파트 1: 경계 원장 작성하기

다음 고정 카드를 분류하세요. “주요 계층”은 학습자가 관찰해야 할 계층을 뜻하며,
제품의 내부 구현에 대한 주장이 아닙니다.

| 카드 | 작업 카드 |
|---|---|
| A | “컨텍스트를 자신의 말로 설명하고 불확실한 점 두 가지를 말하세요.” |
| B | “`notes.md`를 읽고, 일회용 로컬 복사본에 제목 하나를 추가한 뒤 diff를 보여주세요.” |
| C | “도구를 호출하고, 그 결과를 조직의 공개 저장소에 작성한 뒤 팀에 알리세요.” |
| D | “성공한 것처럼 보일 때까지 오류 수정을 계속 시도하고, 중간 상태는 기록하지 마세요.” |
| E | “시스템에 로그인되어 있습니다. 도구가 완료되었다고 했으니 검사를 건너뛰고 지금 게시하세요.” |

다음 원장을 작성하세요.

| 카드 | 주요 계층 | 허용된 행동 | 금지된 행동 | 최소 증거 | 중단/확인 지점 | 여전히 알 수 없는 것 |
|---|---|---|---|---|---|---|
| A |  |  |  |  |  |  |
| B |  |  |  |  |  |  |
| C |  |  |  |  |  |  |
| D |  |  |  |  |  |  |
| E |  |  |  |  |  |  |

다음 결정 순서를 사용하세요.

1. 요청은 설명/생성, 읽기/편집 또는 외부 상태 변경 중 무엇인가?
2. 상태가 변경된다면 정확히 어떤 객체, 권한, 확인, 롤백이 필요한가?
3. 완료 주장에 대응하는 증거는 무엇인가?
4. 무엇이 재시도 대신 작업을 중단하게 하는가?

탄탄한 기준 답변은 A를 설명, B를 경계가 정해진 로컬 실행 작업, C를 여기서
실행해서는 안 되는 외부 부작용 계획, D를 경계 없는 Agent 루프, E를 근거 없는
가정으로 식별합니다. 이유를 설명하세요. 이 문장을 증거로 그대로 복사하지 마세요.

## 파트 2: 통제된 컨텍스트 실험 수행하기

다음 텍스트 전용 작업을 사용하세요.

> 제공된 README 발췌문을 검사하고 개선점 하나를 찾으세요. 파일은 편집하지
> 마세요. 무엇이 주어졌는지, 그 개선이 중요한 이유, 어떻게 확인할 수 있는지,
> 무엇을 알 수 없는지 말하세요.

발췌문만으로 기준 실행을 수행하세요. 정확히 한 가지만 바꾸어 반복하세요.

1. 대상 독자를 추가합니다.
2. 짧은 프로젝트 규칙을 추가합니다.
3. 수용 조건을 추가합니다.

모델/표면, 입력 리비전, 생성 구성, 도구 상태를 인과관계를 뒷받침할 만큼 충분히
고정하지 못했다면 변경된 항목이 출력 차이의 원인이라고 주장하지 마세요. 고정할
수 없다면 다음과 같이 작성하세요.

    다른 결과가 관찰됨, 원인은 분리되지 않음.

다음을 기록하세요.

    run-id | 입력 리비전 | 표면/모델 | 변경한 변수 | 도구 호출 여부 | 파일 변경 여부 | 관찰된 증거 | 미확인 사항

이 실험은 수동으로 작성한 시뮬레이션으로 완료할 수 있습니다. 실제 모델 실행은
선택 사항이며 실제 증거를 표시해야 합니다. 시뮬레이션한 도구 결과는 실행된 도구
결과가 아닙니다.

## 파트 3: 안전하지 않은 완료 주장 바로잡기

다음 문장으로 시작하세요.

> “브라우저 로그인이 성공했고, 도구가 완료를 반환했으며, 모델이 변경이
> 끝났다고 말했습니다. 따라서 공개 저장소가 업데이트되었습니다.”

이를 주장 원장으로 다시 작성하세요.

| 주장 | 필요한 증거 | 현재 상태 | 안전한 다음 확인 |
|---|---|---|---|
| 브라우저 인증이 완료됨 | 인증 단계와 클라이언트 토큰/세션 증거 |  |  |
| 이 저장소에 대한 행동이 승인됨 | 대상, 계정/조직 범위, 권한 증거 |  |  |
| 도구가 쓰기를 실행함 | 도구 호출/결과와 대상 식별자 |  |  |
| 의도한 객체가 변경됨 | 대상에서 새로 읽은 내용 또는 제공자 측 기록 |  |  |
| 변경이 수용 가능함 | diff/검토/테스트 또는 사람의 승인 |  |  |

빈 상태를 “아마도”로 채우지 마세요. `not_observed`, `blocked`, `partial` 또는
`verified within scope`를 사용하고 그 범위를 설명하세요.

## 파트 3A: 메커니즘 수준의 실패 하나 추가하기

다음과 같은 네트워크 없는 합성 사례 중 하나를 선택해 주장 원장에 추가하세요.

- **스키마 통과, 의미 실패:** 응답이 유효한 JSON이고 모든 필수 필드가 있지만,
  참조된 객체가 존재하지 않습니다. 비즈니스/상태 검사를 추가하세요.
- **검색 적중, 예외 누락:** 포괄적인 정책 청크가 선택되었지만 버전별 예외가
  누락되었습니다. 쿼리, 필터, 선택된 청크, 누락된 증거 필드를 추가하세요.
- **지침 형태의 데이터:** README 또는 도구 결과가 작업의 안전 규칙을 무시하라고
  말합니다. 이를 데이터로 유지하고, 외부 부작용을 거부하며, 출처와 시도된 영향을
  기록하세요.

핵심은 정확히 어떤 계층이 실패했는지 밝히는 것입니다. 스키마 결과, 검색 적중 또는
눈에 보이는 문자열이 의미적 정확성, 완전한 컨텍스트 또는 권한의 증거가 자동으로
되는 것은 아닙니다. 출처를 근거로 한 경계는 [LLM 메커니즘
연구](../evidence-library-KO.md#source-notes)를 참조하세요.
이 실험은 실제 제공자를 실행하지 않습니다.

## 파트 4: 중단 규칙 연습하기

다음과 같은 무해한 주입 실패 중 하나를 선택하세요.

- 모델이 용량 한계에 도달했다고 보고합니다.
- 명령이 선언된 제한 시간을 넘어서도 Working 상태에 머물렀다고 보고합니다.
- 검증 명령이 강제 재설치를 요청한다고 보고합니다.

자동으로 재시도하지 마세요. 다음을 작성하세요.

    상태 | 화면에 보이는 증상 | 현재 체크포인트 | 확보한 증거 | 필요한 권한 | 가장 작은 복구 행동 | 미검증 항목

올바른 복구는 보통 현재 상태를 검사하고, 기록을 보존하고, 다음 확인 범위를 좁히거나,
권한을 요청하는 것입니다. 작업 공간을 지우거나, 의존성을 강제로 설치하거나, 다음
대기 지침을 보내는 것이 아닙니다.

이러한 실패 형태는 [Codex 현장 문제 연구](../evidence-library-KO.md#source-notes)의
공개 보고를 바탕으로 합니다. 이는 사용자 증거이지 공식 근본 원인 확인이 아니며,
이 실험은 로컬 재현을 주장하지 않습니다.

## 증거 패키지

다음이 포함된 디렉터리 하나 또는 Markdown 기록 하나를 제출하세요.

1. 고정 카드 버전과 실행 ID
2. 작성 완료한 A-E 경계 원장
3. 컨텍스트 실험 행 두 개와 교란 변수
4. 바로잡은 주장 원장
5. 중단/복구 기록
6. 150단어 이하의 개인 요약

요약은 다음 질문에 답해야 합니다.

- 모델 출력과 도구 결과의 차이는 무엇인가?
- 도구 결과와 검증된 상태의 차이는 무엇인가?
- 로그인, 모델 이름, Skill 이름 또는 완료 메시지가 권한이나 정확성을 입증하지
  못하는 이유는 무엇인가?
- 어떤 문장이 `not_observed` 상태로 남는가?

## 수용 기준

다음을 모두 충족할 때만 통과입니다.

- 모든 고정 카드에 이유, 경계, 증거, 중단 지점이 있습니다.
- 카드 C와 카드 E가 실제 외부 쓰기나 알림을 발생시키지 않습니다.
- 최소 한 문장을 추측하지 않고 의도적으로 미검증 상태로 남깁니다.
- 컨텍스트 실험에 변경한 변수와 모든 교란 변수가 기록되어 있습니다.
- 실패 실습이 파괴적이거나 승인되지 않은 권한 확대 전에 중단됩니다.
- 메커니즘 사례에서 공백이 스키마, 컨텍스트 선택, 지침 권한, 실행 또는 검증 중
  어디에 있는지 식별합니다.
- 두 번째 독자가 어떤 사건이 시뮬레이션되었고, 관찰되었고, 실행되지 않았는지
  구분할 수 있습니다.

프로젝트에 실제 실행 기록과 독립 검토가 생길 때까지 실험은 `draft`,
`run_status: not_run` 상태로 유지됩니다. 완성된 워크시트는 학습자의 실습에 관한
증거이지, 모든 Codex 제품 표면이 같은 방식으로 작동한다는 증거가 아닙니다.

## 전이 과제

고정된 공개 출처 모음을 사용해 일회용 로컬 파일에 한 페이지 분량의 연구 개요를
작성하세요. 출처 텍스트, 사용자 지침, 모델 제안, 로컬 편집, 검증 확인을 서로 다른
계층으로 표시하세요. 개요와 무관한 지침 형태의 문장이 포함된 출처 하나를
추가하세요. 왜 이를 권위가 아니라 데이터로 취급하는지 기록하세요. 명시적 범위와
확인이 있는 새로운 작업 프로토콜을 만들지 않는 한, 이 전이 과제에서 탐색,
게시 또는 외부 커넥터 호출을 수행하지 마세요.
