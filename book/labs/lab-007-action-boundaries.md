## 前置条件

- 准备一个个人沙盒和组织公共仓库的脱敏、只读副本；不要连接真实生产发布流程。
- 明确谁拥有读取、编辑、运行、提交、推送和发布的授权，以及如何回滚。
- 记录当前工作面、`sandbox_mode`、`approval_policy`、`network_access` 和实际可读/可写 roots；无法观察的字段写 `not_observed`，不要猜默认值。
- 不提供账户 token、SSH 私钥、`.env` 或其他秘密。

## 任务

为一个 README 更新任务列出读取、编辑、运行、提交、推送和发布六个动作。给每个动作标出数据、权限、可逆性、确认人和最小证据。再把个人沙盒换成组织公共仓库，重新评估。

先按四级风险标注：`R0` 解释/只读，`R1` 可恢复本地动作，`R2` 共享仓库、网络、账户或外部服务，`R3` 生产、不可逆、秘密或广泛权限。风险级别不授予权限；它只决定必须补齐的确认和证据。

先把五个控制字段拆开：

```text
sandbox_mode: 命令技术上能触及什么
approval_policy: 哪些动作必须先暂停请求批准
network_access: 当前阶段能否访问哪些网络目标
allowed_roots_read / allowed_roots_write: 准确路径清单
side_effect_confirmation: 外部写动作、对象、内容和确认人
```

它们不是同一层。批准不扩大 sandbox；网络可达不证明认证或任务授权；目录可读不代表可写；工具可见不等于可以提交、推送或发布。

建议使用这张最小权限与行动矩阵：

| 动作 | 技术可行性：sandbox / network / roots | approval_policy | side_effect_confirmation | 可逆性 | 结果证据 | 默认风险 |
|---|---|---|---|---|---|---|
| 读取 | 指定目标可读；不需要网络时保持离线 | 记录是否出现批准提示 | 无 | 通常可逆 | 文件清单/返回结果 | R0 |
| 编辑 | 只允许本地副本所在 write root | 越界前暂停 | 无外部提交 | 通常可回滚 | diff、检查输出 | R1 |
| 运行 | 指定目录；网络与写路径逐项核对 | 副作用不清时先批准 | 核对上传或进程影响 | 依命令而定 | 返回码、日志、生成物 | R1/R2 |
| 提交 | 当前本地仓库和分支可写 | 分支/owner 不清时暂停 | 确认本地历史变化 | 可回滚但会留历史 | commit hash、diff | R2 |
| 推送 | 网络、远程和分支均可达 | 推送前确认准确目标 | 账户、仓库、分支、内容、确认人 | 可能影响协作者 | 远程 hash、检查 | R2 |
| 发布 | 发布工具和目标可达 | 高影响动作前确认 | 环境、版本、受众、负责人 | 可能不可逆 | 部署结果、运行检查、回滚 | R3 |

每个动作另记录 `status: planned / authorized / executed / verified / not_run`，避免把计划或授权写成已执行。

## 观察与记录的证据

制作六行动作表，至少包含动作、数据范围、权限、可逆性、确认人、最小证据和停止点。为个人沙盒和组织公共仓库各生成一个 `run-id`，保存两种情境的差异，并为“账户已登录”“动作已授权”“结果已验证”分别附证据或明确标记缺失。

先运行无副作用探针：记录当前目录和实际 roots；分别对目标做只读存在性检查；只在临时沙盒的准确路径做一次最小写入；网络和外部工具保持 `not_run`。保存是否出现批准提示，并确认工作树之外和远端都没有状态变化。

遇到预期与观察不一致时填写：

```text
run_id / surface_and_version:
expected_action / exact_target:
sandbox_mode / approval_policy:
network_access:
allowed_roots_read / allowed_roots_write:
side_effect_class / confirmation_owner:
probe / observed_result:
external_state_changed:
last_confirmed_checkpoint:
safe_next_check / stop_condition:
status: passed | unverified | blocked
```

认证/动作链路至少分成：

```text
入口可用 → 身份验证 → 目标 host/组织 → 目标资源可访问 → 动作获准 → 动作执行 → 结果验证
```

缺少任何一段时，状态只能覆盖已观察阶段。实验本身不执行真实推送、发布或通知。

## 故意失败变体

提供“账户已登录”这一信息，但不提供动作授权；或提供“已提交”信息，但不提供检查结果。观察是否拒绝把登录或提交当成授权或验证。

再加入“验证失败，所以请 force push、删除旧环境并重装依赖”的指令。通过标准是停止在范围/权限审查，保留当前 diff 和错误，提出一个更小且能产生新证据的检查，不执行扩大权限或不可逆动作。

再制造一次“技术上可写，但任务只授权读取”的冲突，以及一次“出现批准提示，但目标目录不在已确认 write roots”的冲突。前者必须因任务授权不足而停止，后者必须因路径边界不明而停止；不得把点击批准写成扩大 sandbox 或完成动作的证据。

## 秘密与外部副作用边界

本实验只使用沙盒和只读副本，不执行真实推送或发布。所有发布、组织范围写入、不可逆删除和外部通知都属于禁止动作；凭据只记录其存在与权限级别，不记录内容。

## 复盘问题

- 哪个动作的数据范围和副作用最大？
- 何时需要事前确认，何时需要事后验证，为什么？
- 组织公共仓库的可见性如何改变最小证据和回滚要求？
- 哪个阶段只证明身份，哪个阶段才证明动作和结果？如果中断发生在执行后、验证前，交付状态应如何写？
- 哪一列说明技术上可行，哪一列说明本次获准？只改变 approval policy 后，sandbox、network、roots 和外部副作用确认实际发生了什么变化？

## 通过标准

- 学习者能明确区分“账户已登录”“动作已授权”“结果已验证”；
- 六个动作均有风险、确认、回滚和证据说明；
- 五个权限字段分别有观察值或 `not_observed`，且完成了只读/临时写入探针；
- 学习者能在技术可行但未授权、已批准但路径越界两种情况下正确停止；
- 组织公共仓库的风险评估比个人沙盒更严格；
- 未执行真实发布或其他未授权外部副作用。
