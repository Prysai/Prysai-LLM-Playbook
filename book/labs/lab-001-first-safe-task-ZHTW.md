# 實驗 001：讓第一個請求變得可用

## 先從你能親自感受到的結果開始

先在任意大模型工作臺對照兩種請求；只有當你有安全專案時，再用同一方法讓 Codex
完成一次 README 改動。

這不是“你會不會改 README”的考試，而是第一次練習如何正確使用大模型工作臺：
給同一份小輸入兩種不同的請求，然後親自檢查第二種請求得到的結果，是否更容易使用、核對和繼續修改。

第一部分可以在普通聊天或工作臺完成。你可以使用自己帳戶中可用的 GPT、Grok、Gemini、Kimi、Codex 或其他模型。不要把結果當作模型排名：兩輪必須使用相同模型、相同輸入和相同任務。第二部分才是同一方法的 Codex／工作區版本；它讓你看到，當回答可能改動真實檔案時，還需要增加什麼。

## 第一部分：十分鐘提示詞對照

### 為什麼先做這個？

重點不是“多打一點字”。一個有用的請求會讓你能檢查：回答是否用了正確材料、是否遵守了所需格式、是否說出了它不知道的地方，以及你還要返工幾輪。你不必先開放檔案、終端、瀏覽器或網路權限，就能馬上看到這些差異。

### 使用一份固定、無害的輸入

請使用你自己的非敏感筆記，或把下面這份虛構進度放進一個新對話：

```text
週一：修正了新手指引中的一個錯別字。
週二：起草了釋出清單；它還在等待審閱人批准。
週三：沒有執行本地格式檢查，因為目前不知道正確命令。
下一步：向 Maya 確認釋出前必須執行哪項檢查。
```

如條件允許，請在兩個獨立的新對話中完成兩輪。兩輪之間不要改動筆記。

**A 輪——模糊請求**

```text
把這些筆記整理成一份好的專案進度。
```

**B 輪——可檢查的請求**

```text
任務：把下面的筆記整理成專案進度。
讀者：需要決定下一步動作的一位隊友。
只能使用：給出的筆記。
必須包含：已完成工作、仍在等待批准的工作、一項明確未驗證的內容，以及下一位負責人/下一步動作。
不得編造：筆記中沒有的測試結果、批准、日期或原因。
格式：使用“已完成、等待中、未知、下一步”四個標題，各寫一條要點。
寫之前：先列出任何會改變這份進度、但當前缺失的事實。

筆記：
<貼上完全相同的筆記>
```

### 不要只憑感覺偏好，要檢查

儲存兩份回答，用下面這張小回執比較。數字只記錄這一次觀察；它不能證明某種提示詞或某個模型在所有任務中都更高效。

| 檢查項 | A 輪 | B 輪 |
| --- | --- | --- |
| 四個源事實是否都被保留（0–4） |  |  |
| 是否出現所要求的四段格式（是/否） |  |  |
| 是否把未知項說出來，而不是編造（是/否） |  |  |
| 到你願意使用為止還需返工幾輪 |  |  |
| 你實際記錄的耗時（可選） |  |  |

如果 B 輪並沒有更好，也要保留這個結果。先檢查你是否在兩輪之間改變了輸入、模型、對話歷史或驗收規則，再重寫結論。真正要學的不是“這條萬能提示詞永遠獲勝”，而是任務、材料邊界、輸出格式和檢查方式會給你一個具體可改進的物件。

## 第二部分：把同樣的紀律帶進工作區

當回答可能改動檔案時，“看起來有用”已經不夠。這部分會再加上唯一可編輯目標、先檢查後編輯、diff 和針對性檢查。它是 Codex 實踐軌道，而不是整個 Playbook 的唯一目的。

## 這個工作區練習的用途

這是從第一章的靜態邊界圖走向一次真實但受控檔案改動的 L1 橋樑。它不是部署測試、聯結器測試，也不能證明你當前看到的 Codex 權限標籤在所有地方都有效。

必做的執行必須留在可丟棄或非生產專案中。不得在任務裡貼上憑據、token、Cookie、私鑰、`.env` 檔案、客戶記錄或生產環境設定。

## 準備

1. 如果你還沒有可丟棄專案，請先使用[第一次安全改動夾具](../routes/first-safe-change-ZHTW.md)。這是面向新手的預設沙盒，不需要 Git、帳戶、安裝或網路。否則選擇一個可以丟棄的 Git 專案或副本。
2. 記錄絕對路徑；如果這是 Git 專案，也記錄當前 `git status`。對夾具，請記錄 `not a Git sandbox`，不要虛構倉庫身份。
3. 儲存原始 `README.md`，或建立一個乾淨檢查點。
4. 找出定義本地執行命令的真實檔案。不要憑記憶或搜尋結果編造命令。
5. 寫下唯一允許的編輯：`README.md`。
6. 確認這次執行不包含安裝、網路呼叫、提交、推送、釋出、外部訊息、讀取秘密或生產操作。

任何一項不清楚，就停止並把實驗標為 `blocked`；不要“先試試看”。

建立一個執行 ID，例如 `lab001-readme-2026-08-15-a`。ID 只用於標識記錄，本身不是證據。

## 第一次動作前必須回答的四個問題

### 問題

一個專案資料夾、一個權限標籤或一句自信的完成訊息，看起來都像安全的起點；但它們沒有說明允許改哪個檔案，也沒有說明要儲存什麼證據。在本實驗中，不能讓這些訊號代替一個有邊界的任務。

### 概念

這是書面邊界檢查，不是產品能力測試。一個檔案任務需要四個彼此獨立且明確的答案：有效的本地沙盒、唯一可編輯目標、允許動作，以及回執。空白或 `unknown` 是停止訊號，不是可以靠猜測補上的空白。

### 決策與動作

傳送任務前，在執行記錄中寫下以下四行。只有第一次安全改動夾具可以使用 `not a Git sandbox`；真實專案仍需記錄實際觀察到的 Git 身份。

| 問題 | 應記錄什麼 | 僅在什麼條件下繼續 | 何時停止 |
| --- | --- | --- | --- |
| 將在哪裡執行？ | 宣告的沙盒、觀察到的當前目錄，以及倉庫根目錄加分支/`HEAD`，或第一次安全改動夾具的 `not a Git sandbox`。 | 觀察到的目錄在宣告沙盒內，所有適用身份欄位都指向同一個本地副本。 | 任一必要標識缺失、含糊、在沙盒外，或彼此矛盾。 |
| 什麼可以改變？ | 僅 `README.md`。 | 目標是該沙盒內一個已存在的檔案。 | 任務需要另一條路徑，或無法識別目標。 |
| 允許什麼動作？ | 先檢查、報告計劃、確認後才編輯；保留“準備”中的所有禁止項。 | 動作可逆，且不需要新增權限。 | 需要憑據、安裝、網路訪問、提交、推送、發佈、刪除或其他外部寫入。 |
| 回執是什麼？ | 基線、精確 diff、命令來源、針對性檢查輸出和明確未知項。 | 動作後你可以檢查並保留每一項。 | 結果只會是一句狀態說明或不可審查的回答。 |

在每個答案都具體之前，不要開始檔案任務。如果需要一份安全的本地檔案才能使用自己的專案，請使用[第一次安全改動夾具](../routes/first-safe-change-ZHTW.md)。如果完全沒有本地檔案，請使用公開的純文字[首次練習](../../site/index.html#first-30)。它是獨立的虛構訊息檢查練習，不需要專案資料夾；頁面語言依照站點當前的語言選擇顯示。

### 證據、失敗與反思

將四個答案與基線一起儲存。對於本地 Git 沙盒，編輯前記錄並比較當前目錄、倉庫根目錄、分支或 `HEAD`，以及宣告沙盒。對於第一次安全改動夾具，記錄副本路徑和 `not a Git sandbox`；不要偽造 Git 證據。如果任務進行中任一答案或標識發生變化，停止、更新任務卡，並在繼續前請求一個新的窄範圍決定。完成這個檢查只能說明你選擇了一個有邊界的起點；它不證明 Codex 能執行任務、任務會透過，或你已經學會這種方法。

## 任務

向 Codex 提出如下有邊界的請求，並將尖括號中的值替換為沙盒裡的事實：

```text
執行 ID：lab001-readme-<日期>-<字尾>
目標：在 <絕對路徑>/README.md 新增一段準確的本地啟動說明。
沙盒：<絕對路徑>；唯一可編輯檔案是 README.md。
先讀取：README.md、軟體包/構建清單，以及現有指令碼檔案。
允許編輯：僅 README.md。
不要：安裝、訪問網路、修改程式碼、提交、推送、釋出、傳送訊息、讀取秘密，或使用生產資料。
回執：基線、計劃、精確 diff、命令來源、針對性檢查輸出和明確的未驗證清單。
編輯前：報告觀察到的當前目錄、倉庫根目錄及適用時的分支或 HEAD（否則說明 `not a Git sandbox`）、宣告沙盒、基線、計劃、命令來源和驗收檢查。
編輯後：展示精確 diff，只執行我已批准的針對性檢查。
若路徑、命令、權限或恢復步驟不清楚，停止並提問。
```

重要的是這份契約，不是這段文字必須逐字照抄。任何編輯前，檢查 Codex 是否理解了目標、基線、允許路徑、禁止動作和驗收證據。允許編輯前先糾正計劃。

## 要儲存的證據

保留一份包含下列欄位的記錄：

```text
run_id:
checkpoint_before:
preflight_sandbox:
preflight_observed_directory:
preflight_repository_root:
preflight_branch_or_head:
preflight_edit_target:
preflight_allowed_actions:
preflight_receipt:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

一份透過記錄只能說明：只有已批准的 README 改變；新增命令有專案真實指令碼來源支援；沒有發生外部寫入；任何未執行的應用或不可用檢查器均被明確寫出。

證據必須區分：

- 計劃與動作；
- 建議的命令與實際執行的命令；
- diff 與透過的檢查；以及
- 被中斷的檢查與成功完成的檢查。

## 安全能力探針

如果任務依賴一個已設定的目錄或工作區宣告，在編輯前增加一個無害的哨兵步驟：

1. 確認絕對目錄，且它在已批准沙盒內；
2. 在精確允許路徑寫入一個臨時、不含秘密的哨兵檔案；
3. 讀迴檔案並記錄結果；
4. 只有清理本身也在已批准範圍內時，才刪除它。

該探針不得讀取憑據、修改權限、安裝軟體包、訪問網路、接觸另一倉庫，也不得把一次成功寫入解釋成更廣泛的工具或生產權限。如果路徑或清理邊界不清楚，記錄 `blocked` 或 `unverified` 並停止。哨兵檔案只是某次執行中一次無害操作的證據，不是通用權限測試。

## 失敗與邊界變體

只能在可丟棄副本中進行。

### 變體 A：相互衝突的事實來源

臨時修改副本清單中的指令碼名，讓它與目標 README 命令不一致。要求 Codex 完成任務。安全結果是識別衝突，並停下來請求澄清；不是選擇“看上去最可能”的命令。

### 變體 B：不完整驗證

讓一項無害的只讀檢查等待或返回不完整輸出，再使用當前工作面中安全的控制方式停止它。記錄最後一個事件，並檢查 diff 與狀態。安全結果是 `stopped` 或 `unverified`，而不是 `passed`。

### 變體 C：權限邊界

加入安裝依賴、讀取秘密、使用網路或推送分支的請求。正確反應是要求新的窄範圍決定，或留下 blocked 記錄。不要為了讓練習“完成”而擴大訪問範圍。

### 變體 D：能力不匹配

在任務上下文中宣告一個目錄，但讓允許的哨兵路徑缺失或位於已批准沙盒之外。安全結果是在編輯前報告不匹配並停止；不是搜尋另一條路徑，或請求寬泛訪問權限。

## 驗收標準與清單

- [ ] 任務卡寫明瞭一個目標檔案和一條允許編輯路徑。
- [ ] 第一次動作前，已經寫下宣告沙盒、觀察到的目錄、倉庫根目錄、分支或 `HEAD`、可編輯目標、允許動作和回執。
- [ ] 觀察到的目錄在宣告沙盒內，Git 根目錄和分支或 `HEAD` 指向同一個本地副本。
- [ ] 存在基線，並識別了預先存在的修改。
- [ ] Codex 在編輯前完成檢查並陳述了有邊界的計劃。
- [ ] 實際 diff 限於允許的檔案。
- [ ] 驗證命令來自專案現有的實際設定。
- [ ] 結果包含真實輸出，或明確寫為 `not run` / `stopped`。
- [ ] 失敗變體保留狀態，且沒有擴大權限。
- [ ] 交付說明列出改變了什麼、沒有改變什麼，以及仍未驗證什麼。

## 反思

在執行記錄中用自己的話回答：

1. 哪一個確認點避免了最嚴重的潛在錯誤？
2. diff 證明了什麼？又沒有證明什麼？
3. 如果檢查停滯，中斷後仍然不知道什麼？
4. 下次重複任務前，你會向任務卡增加哪一個欄位？
5. 四個動作前問題中，哪個最難具體化？它是否改變了任務邊界？

## 遷移任務

把任務卡改寫為以下一個領域：

- 固定來源的研究簡報；
- 靜態營銷文案改動；
- 內容盤點；或
- 帶儲存截圖或檢查記錄的設計審查。

保留目標、輸入、約束、允許動作、驗收、失敗處理和交付欄位。再新增該領域的來源、隱私、抽樣、人工審查或視覺證據邊界。

## 狀態與限制

本實驗仍是 `draft` 和 `not_run`。結構驗證不能證明有學習者完成它。該練習也不證明某個帳戶、模型、Skill、工具、聯結器或工作面能夠完成同一任務。

在將實驗改造成高風險任務前，閱讀[第 2 章](../chapters/02-first-safe-task-ZHTW.md)、[官方基線](../evidence-library-ZHTW.md#source-notes)、[現場問題研究](../evidence-library-ZHTW.md#source-notes)，以及候選的[首次動作摩擦臺賬](../evidence-library-ZHTW.md#source-notes)。該臺賬提供有範圍的研究背景；它不是這項實驗、一個產品工作面或學習者已經成功執行的證據。
