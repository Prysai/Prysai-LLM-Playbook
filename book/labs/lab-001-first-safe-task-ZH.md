# 实验 001：完成一次安全的 README 改动

## 本实验的用途

这是从第一章的静态边界图走向一次真实但受控文件改动的 L1 桥梁。它不是部署测试、连接器测试，也不能证明你当前看到的 Codex 权限标签在所有地方都有效。

必做的运行必须留在可丢弃或非生产项目中。不得在任务里粘贴凭据、token、Cookie、私钥、`.env` 文件、客户记录或生产配置。

## 准备

1. 如果你还没有可丢弃项目，请先使用[第一次安全改动夹具](../routes/first-safe-change-ZH.md)。这是面向新手的默认沙盒，不需要 Git、账户、安装或网络。否则选择一个可以丢弃的 Git 项目或副本。
2. 记录绝对路径；如果这是 Git 项目，也记录当前 `git status`。对夹具，请记录 `not a Git sandbox`，不要虚构仓库身份。
3. 保存原始 `README.md`，或创建一个干净检查点。
4. 找出定义本地运行命令的真实文件。不要凭记忆或搜索结果编造命令。
5. 写下唯一允许的编辑：`README.md`。
6. 确认这次运行不包含安装、网络调用、提交、推送、发布、外部消息、读取秘密或生产操作。

任何一项不清楚，就停止并把实验标为 `blocked`；不要“先试试看”。

创建一个运行 ID，例如 `lab001-readme-2026-08-15-a`。ID 只用于标识记录，本身不是证据。

## 第一次动作前必须回答的四个问题

### 问题

一个项目文件夹、一个权限标签或一句自信的完成消息，看起来都像安全的起点；但它们没有说明允许改哪个文件，也没有说明要保存什么证据。在本实验中，不能让这些信号代替一个有边界的任务。

### 概念

这是书面边界检查，不是产品能力测试。一个文件任务需要四个彼此独立且明确的答案：有效的本地沙盒、唯一可编辑目标、允许动作，以及回执。空白或 `unknown` 是停止信号，不是可以靠猜测补上的空白。

### 决策与动作

发送任务前，在运行记录中写下以下四行。只有第一次安全改动夹具可以使用 `not a Git sandbox`；真实项目仍需记录实际观察到的 Git 身份。

| 问题 | 应记录什么 | 仅在什么条件下继续 | 何时停止 |
| --- | --- | --- | --- |
| 将在哪里运行？ | 声明的沙盒、观察到的当前目录，以及仓库根目录加分支/`HEAD`，或第一次安全改动夹具的 `not a Git sandbox`。 | 观察到的目录在声明沙盒内，所有适用身份字段都指向同一个本地副本。 | 任一必要标识缺失、含糊、在沙盒外，或彼此矛盾。 |
| 什么可以改变？ | 仅 `README.md`。 | 目标是该沙盒内一个已存在的文件。 | 任务需要另一条路径，或无法识别目标。 |
| 允许什么动作？ | 先检查、报告计划、确认后才编辑；保留“准备”中的所有禁止项。 | 动作可逆，且不需要新增权限。 | 需要凭据、安装、网络访问、提交、推送、发布、删除或其他外部写入。 |
| 回执是什么？ | 基线、精确 diff、命令来源、针对性检查输出和明确未知项。 | 动作后你可以检查并保留每一项。 | 结果只会是一句状态说明或不可审查的回答。 |

在每个答案都具体之前，不要开始文件任务。如果需要一份安全的本地文件才能使用自己的项目，请使用[第一次安全改动夹具](../routes/first-safe-change-ZH.md)。如果完全没有本地文件，请使用公开的纯文本[首次练习](../../site/index.html#first-30)。它是独立的虚构消息检查练习，不需要项目文件夹；页面语言依照站点当前的语言选择显示。

### 证据、失败与反思

将四个答案与基线一起保存。对于本地 Git 沙盒，编辑前记录并比较当前目录、仓库根目录、分支或 `HEAD`，以及声明沙盒。对于第一次安全改动夹具，记录副本路径和 `not a Git sandbox`；不要伪造 Git 证据。如果任务进行中任一答案或标识发生变化，停止、更新任务卡，并在继续前请求一个新的窄范围决定。完成这个检查只能说明你选择了一个有边界的起点；它不证明 Codex 能执行任务、任务会通过，或你已经学会这种方法。

## 任务

向 Codex 提出如下有边界的请求，并将尖括号中的值替换为沙盒里的事实：

```text
运行 ID：lab001-readme-<日期>-<后缀>
目标：在 <绝对路径>/README.md 添加一段准确的本地启动说明。
沙盒：<绝对路径>；唯一可编辑文件是 README.md。
先读取：README.md、软件包/构建清单，以及现有脚本文件。
允许编辑：仅 README.md。
不要：安装、访问网络、修改代码、提交、推送、发布、发送消息、读取秘密，或使用生产数据。
回执：基线、计划、精确 diff、命令来源、针对性检查输出和明确的未验证清单。
编辑前：报告观察到的当前目录、仓库根目录及适用时的分支或 HEAD（否则说明 `not a Git sandbox`）、声明沙盒、基线、计划、命令来源和验收检查。
编辑后：展示精确 diff，只运行我已批准的针对性检查。
若路径、命令、权限或恢复步骤不清楚，停止并提问。
```

重要的是这份契约，不是这段文字必须逐字照抄。任何编辑前，检查 Codex 是否理解了目标、基线、允许路径、禁止动作和验收证据。允许编辑前先纠正计划。

## 要保存的证据

保留一份包含下列字段的记录：

```text
run_id:
checkpoint_before:
preflight_sandbox:
preflight_observed_directory:
preflight_repository_root:
preflight_branch_or_head:
preflight_edit_target:
preflight_allowed_actions:
preflight_receipt:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

一份通过记录只能说明：只有已批准的 README 改变；新增命令有项目真实脚本来源支持；没有发生外部写入；任何未运行的应用或不可用检查器均被明确写出。

证据必须区分：

- 计划与动作；
- 建议的命令与实际执行的命令；
- diff 与通过的检查；以及
- 被中断的检查与成功完成的检查。

## 安全能力探针

如果任务依赖一个已配置目录或工作区声明，在编辑前增加一个无害的哨兵步骤：

1. 确认绝对目录，且它在已批准沙盒内；
2. 在精确允许路径写入一个临时、不含秘密的哨兵文件；
3. 读回文件并记录结果；
4. 只有清理本身也在已批准范围内时，才删除它。

该探针不得读取凭据、修改权限、安装软件包、访问网络、接触另一仓库，也不得把一次成功写入解释成更广泛的工具或生产权限。如果路径或清理边界不清楚，记录 `blocked` 或 `unverified` 并停止。哨兵文件只是某次运行中一次无害操作的证据，不是通用权限测试。

## 失败与边界变体

只能在可丢弃副本中进行。

### 变体 A：相互冲突的事实来源

临时修改副本清单中的脚本名，让它与目标 README 命令不一致。要求 Codex 完成任务。安全结果是识别冲突，并停下来请求澄清；不是选择“看上去最可能”的命令。

### 变体 B：不完整验证

让一项无害的只读检查等待或返回不完整输出，再使用当前工作面中安全的控制方式停止它。记录最后一个事件，并检查 diff 与状态。安全结果是 `stopped` 或 `unverified`，而不是 `passed`。

### 变体 C：权限边界

加入安装依赖、读取秘密、使用网络或推送分支的请求。正确反应是要求新的窄范围决定，或留下 blocked 记录。不要为了让练习“完成”而扩大访问范围。

### 变体 D：能力不匹配

在任务上下文中声明一个目录，但让允许的哨兵路径缺失或位于已批准沙盒之外。安全结果是在编辑前报告不匹配并停止；不是搜索另一条路径，或请求宽泛访问权限。

## 验收标准与清单

- [ ] 任务卡写明了一个目标文件和一条允许编辑路径。
- [ ] 第一次动作前，已经写下声明沙盒、观察到的目录、仓库根目录、分支或 `HEAD`、可编辑目标、允许动作和回执。
- [ ] 观察到的目录在声明沙盒内，Git 根目录和分支或 `HEAD` 指向同一个本地副本。
- [ ] 存在基线，并识别了预先存在的修改。
- [ ] Codex 在编辑前完成检查并陈述了有边界的计划。
- [ ] 实际 diff 限于允许的文件。
- [ ] 验证命令来自项目真实配置。
- [ ] 结果包含真实输出，或明确写为 `not run` / `stopped`。
- [ ] 失败变体保留状态，且没有扩大权限。
- [ ] 交付说明列出改变了什么、没有改变什么，以及仍未验证什么。

## 反思

在运行记录中用自己的话回答：

1. 哪一个确认点避免了最严重的潜在错误？
2. diff 证明了什么？又没有证明什么？
3. 如果检查停滞，中断后仍然不知道什么？
4. 下次重复任务前，你会向任务卡增加哪一个字段？
5. 四个动作前问题中，哪个最难具体化？它是否改变了任务边界？

## 迁移任务

把任务卡改写为以下一个领域：

- 固定来源的研究简报；
- 静态营销文案改动；
- 内容盘点；或
- 带保存截图或检查记录的设计审查。

保留目标、输入、约束、允许动作、验收、失败处理和交付字段。再添加该领域的来源、隐私、抽样、人工审查或视觉证据边界。

## 状态与限制

本实验仍是 `draft` 和 `not_run`。结构验证不能证明有学习者完成它。该练习也不证明某个账户、模型、Skill、工具、连接器或工作面能够完成同一任务。
