# 第十六章：工程轨——从想法到可靠软件

## 本章要解决的问题

工程任务最容易让 Agent 直接进入代码，跳过需求边界、架构取舍、测试设计、运行时观察和回滚准备。一个补丁能编译，甚至所有单元测试都通过，也不代表用户路径正确、错误处理可用、依赖版本一致、部署安全或生产可以回滚。

本章把工程 Skill 定义为一条有证据的生命周期：每个阶段都有进入条件、最小切片、失败路径和退出证据；当验证卡住或失败时，先诊断而不是盲目增加代码或扩大权限。

## 学习目标

完成本章后，你应能：

1. 为工程任务写出范围、进入条件、退出条件、风险和停止条件。
2. 把官方文档验证、增量实现、测试、调试、运行时检查、审查、发布和回滚纳入同一流程。
3. 区分编译成功、单元测试通过、集成测试通过、运行时正确、用户验收和生产可用。
4. 识别长时间运行、半成品串接、未授权环境替换、秘密泄露和不可回滚变更，并保留恢复证据。

## 现实问题入口：代码改了不等于工作完成

- **FP-09**：模型容量错误可能中断任务，排队请求还可能接在半完成状态上。它要求在重试前检查工作树、差异、测试和完成点，避免把新的指令接到未知状态。
- **FP-10**：Windows CLI 的格式化/验证命令可能长时间停在 Working，且没有清晰错误。它要求给命令设置输出边界或超时，并把“命令启动”与“验证通过”分开。
- **FP-11**：Agent 被报告把源码验证扩大为持久环境 force reinstall。它要求把安装、发布、部署、重启和在线验证拆成不同授权状态。

这些是现场研究中的用户报告或分析，不是本地复现，也不是对所有版本的根因确认。工程流程应以当前仓库和当前运行时证据为准。

## 核心概念与决策

### 1. 工程生命周期

```text
问题定义 → 规格与验收 → 计划与切片 → 增量实现
        → 静态检查/测试 → 运行时验证 → 审查/简化
        → 发布/回滚 → 维护与回归
```

每一段写清楚：

| 阶段 | 进入条件 | 最小退出证据 |
|---|---|---|
| 定义 | 有用户/系统问题和范围 | 一段可复述的问题陈述 |
| 规格 | 边界、输入、输出和错误已知 | 验收条件和非目标 |
| 计划 | 依赖和风险已识别 | 可独立验证的切片列表 |
| 实现 | 当前切片与基线已确认 | 小范围差异和更新记录 |
| 测试 | 行为和失败路径可执行 | 测试命令、结果和失败解释 |
| 运行验证 | 可启动环境和代表性数据可用 | 日志、截图/响应、版本和环境 |
| 发布 | 变更已审查，回滚可用 | 发布记录、监控和回滚演练 |

### 2. 规格先于实现

一个好的工程任务至少说明：用户动作、输入约束、成功输出、错误输出、边界行为、非目标、性能/安全约束、可观察信号和验收方式。若用户只说“加一个导出功能”，先问导出格式、数据范围、权限、失败时是否产生部分文件、覆盖规则和最终验收；不要让 Skill 用默认值替代决策。

### 3. 来源驱动、怀疑驱动、增量驱动

- **来源驱动**：框架、API、库和版本行为以官方文档、类型定义、当前代码或可复现运行结果为准；博客和模型记忆只是线索。
- **怀疑驱动**：对类型系统和单元测试无法证明的断言做反向检查，例如真实网络、数据库、浏览器、权限、并发、时区和部署配置。
- **增量驱动**：每次只改变一个可解释切片，保存差异和回滚点，避免在未知失败状态上叠加修复。

### 4. 运行时证据有自己的层级

编译证据只能说明代码可构建；测试证据说明指定用例的断言通过；运行时证据还要包括启动方式、依赖版本、环境变量是否为测试值、真实输入、响应/界面、日志和错误路径。生产可用还需要安全、性能、迁移、监控、回滚和用户验收证据。四者不能互相冒充。

### 5. 停止条件和权限边界

命令无输出超时、测试依赖未安装、工作树出现未知改动、需要访问真实凭据、需要修改持久环境、需要发布/部署/重启，都是停下来核对范围的信号。若验证需要安装包或替换运行时，应先获得明确授权，记录 artifact、目标路径、影响范围和回滚方法；没有授权就用隔离环境、测试账号或静态检查替代。

## 可观察小实验：对照“直接实现”和完整生命周期

### Setup

选择一个低风险小功能，例如对本地文本列表增加去重并输出 JSON。准备一份基线项目、五条正常数据、空输入、重复数据、非法编码或缺少字段的数据。固定运行时版本，确保没有真实密钥和外部写入。设定一个短命令超时和输出目录。

### Task

1. **直接实现轮次**：只给目标描述，要求 Agent 实现；记录它是否澄清规格、改了哪些文件、运行了哪些命令、是否覆盖失败输入。
2. **生命周期轮次**：先要求问题陈述、验收条件、非目标、切片计划和测试矩阵；再逐步实现，每步查看差异。
3. 两轮都执行静态检查、单元测试、真实运行、空输入和非法输入测试；记录每个阶段发现的问题。
4. 让 Agent 模拟一次中断或容量错误：先停止，检查工作树、最近差异、日志和测试状态，再决定继续、回滚或开新 checkpoint。
5. 不允许 force reinstall、生产写入、部署或重启；若 Agent 提出这些动作，只记录为超出授权的建议。

### Evidence

保留两轮的任务协议、变更差异、测试矩阵、命令与退出状态、运行输入/输出、错误日志、发现问题的阶段、回滚点和最终验收记录。至少标出四种状态：构建成功、测试通过、运行正确、用户/发布验收。证据应能回答“哪个版本在什么环境、用什么输入、得到什么结果”。

### Failure variant

让格式化命令进入长时间无输出状态，或让测试依赖一个不存在的服务。正确行为是按停止条件中断并恢复控制权，检查工作树和进程状态，标记“验证未完成”，而不是等待后宣称通过或扩大为重装环境。再让前一个切片处于半成品状态，追加一个无关请求；正确行为是先建立 checkpoint，不把后续请求直接施加到未知状态。

### Reflection

回答：

- 完整生命周期多留下了哪些证据，哪些问题更早被发现？
- 哪一条运行时证据无法由单元测试替代？
- 你何时会选择回滚，何时会继续诊断？
- 若需要持久安装才能验证，新的授权、影响和回滚记录是什么？

## 失败与边界案例

- **只看绿色测试**：测试可能没有启动真实服务、加载真实构建产物或覆盖权限/浏览器/移动端路径；补充集成、端到端或人工运行证据。
- **构建成功但运行失败**：检查启动入口、环境变量、依赖版本、静态资源、路由、数据库迁移和日志；不要把编译结果写成运行时验证。
- **命令卡住**：参照 FP-10，设置超时、输出边界和可中断机制；中断后重新检查工作树、残留进程和验证状态。
- **模型容量/会话中断**：参照 FP-09，先审查差异和完成点，再从干净 checkpoint 继续；不要默认排队任务知道当前状态。
- **验证扩大为环境替换**：参照 FP-11，区分 source modified、validated、installed、published、deployed、restarted、live verified，并逐项授权。
- **外部依赖无法访问**：记录未验证项，使用测试替身或沙盒，不能用“命令已执行”代替外部系统证据。
- **回滚不可用**：没有可恢复 artifact、数据库备份、迁移逆操作或配置快照时，生产发布应停在 candidate。

## 迁移练习

选择一个已有工程任务，改写为一页工程任务协议：问题、范围、验收、非目标、权限、风险、切片、测试矩阵、运行验证和回滚。然后：

1. 为正常、空、非法、超时、权限不足各写一个测试或检查。
2. 让 Agent 只实现第一个切片，保留差异和命令证据。
3. 在本地或沙盒中进行一次真实启动检查，记录版本、输入、日志和结果。
4. 让同事只看证据判断当前是 draft、candidate、verified 还是 production-ready，并修正过度声明。

## 验收清单

- [ ] 我为工程任务写了范围、非目标、进入条件、退出条件和停止条件。
- [ ] 我把任务拆成可独立运行和回滚的增量切片。
- [ ] 我能区分编译成功、测试通过、运行正确、用户验收和生产可用。
- [ ] 我使用官方文档或当前代码验证了关键框架/API 断言。
- [ ] 我覆盖了正常、边界、失败、权限和超时路径。
- [ ] 我保留了差异、命令、退出状态、日志、运行环境和最终输出证据。
- [ ] 我能针对 FP-09、FP-10 或 FP-11 说明恢复与权限边界。
- [ ] 我没有在未授权情况下安装、force reinstall、发布、部署或重启。
