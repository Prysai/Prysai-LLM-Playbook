# 第 20 章：建立個人 Codex 工作系統

> `content_status: candidate`
> `experiment_status: draft / not_run`
> 本章介紹一種可遷移的方法，不把某個產品的記憶、自動載入或入口行為當作永久前提。

## 本章要解決的問題

很多人每次重新開啟 Codex，都要從頭再解釋一遍專案、目標、術語、約束和驗收標準。結果就是脈絡不一致、決策無法追溯、過時指令被反覆使用，而有用的經驗無法帶進下一項任務。更嚴重的風險是：把個人隨手紀錄當作記憶庫，把 token、密碼、Cookie、客戶文字或未經確認的結論放進去。

## 真實問題入口

FP-10（驗證或格式化指令可能看起來卡住）和 FP-11（驗證被描述為擴大成未經授權的持久環境變更）是公開使用者問題研究中的報告條目。它們不是本機重現，也不是普遍的根因結論。本章藉此追問：個人工作系統是否會暴露過時指令、記錄停止點，並阻止範圍在未獲授權的情況下擴大。

## 學習目標

學完本章，你應該能夠：

- 區分專案規則、任務脈絡、目前狀態、可重複使用的範本和反思紀錄；
- 為重複性工作建立一個小巧、可清理、可追溯的個人工作包；
- 使用固定輸入、雜湊、執行日誌和證據完整度，比較系統輔助路徑與基線路徑；
- 判斷何時保留任務協議、建立 Skill 候選、繼續觀察或阻塞工作；
- 發現過時脈絡，並在不儲存秘密的前提下把有用的做法移交給其他人。

## 概念：五種資產，五種不同的職責

| 資產 | 它回答的問題 | 生命週期 | 不放什麼 |
|---|---|---|---|
| 專案規則 | 這個專案必須始終遵守什麼？ | 有版本管理、有意變更、定期複核 | 臨時猜測和個人秘密 |
| 任務脈絡 | 這次必須完成什麼？ | 為任務而建，任務結束後歸檔 | 無關的歷史 |
| 目前狀態 | 已讀、已改、已驗證或被阻塞了什麼？ | 在每個檢查點更新 | 把計畫當作結果 |
| 範本 | 相似任務應如何開始和交付？ | 反覆實踐後提煉 | 未經驗證的永久結論 |
| 反思紀錄 | 什麼有效、什麼失敗、下次應改變什麼？ | 只保留可移交的經驗 | token、密碼、Cookie、客戶文字或不必要的個人資料 |

脈絡並非越多越好。相關性、可信度、敏感性和時效性比長度更重要。

## 決策：建立 Skill 還是保留任務協議？

在建立可複用資產之前，先完成這張決策卡。僅憑重複是不夠的。

| 觀察到的情況 | 決策 | 所需證據 |
|---|---|---|
| 請求是一次性的，或輸入與輸出仍在變化 | 保留任務協議 | 一次任務的輸入、約束、決策和交付記錄 |
| 輸入、決策點和輸出穩定，並且同時有正例和失敗例 | 建立 Skill 候選 | 至少三次執行、一個失敗集合和一項遷移任務 |
| 方法有用，但觸發邊界或副作用不清楚 | 繼續觀察或阻塞 | 缺口記錄、風險說明和待驗證項 |
| 涉及秘密、外部寫入或生產發佈，且授權或回滾不清楚 | 阻塞 | 權限矩陣、人工批准點和回滾計畫 |

至少要記錄 `decision_id`、重複任務、候選資產、穩定輸入、失敗類型、證據位置、負責人、`next_review` 和 `decision_action`。一次偶然的成功絕不能成為建立 Skill 的理由。

## 行動：組裝最小的個人工作包

從五種紀錄開始：專案地圖、任務協議、狀態日誌、證據索引和反思紀錄。啟動時檢查規則、分支、目前狀態和權限；執行中只攜帶必要的脈絡；交付時把確實已驗證的工作與仍未完成的工作分開；反思時提煉出另一個人能夠理解並檢驗的規則。

一份有用的交付記錄包括：

- 已完成的事項和變更過的檔案；
- 實際執行過的命令、測試或檢查，以及相應的結果和退出碼（適用時）；
- 未驗證、被阻塞或超出授權範圍的事項；
- 風險以及具體的復原方法；
- 下一次複核或決策的負責人。

產品會記住什麼、會載入哪些檔案、入口如何表現，都是易變的產品事實。請查閱目前的第一方文件和實際獲授權的介面；不要把個人習慣變成對產品的保證。

## 實驗：建立個人工作系統

這是在可丟棄副本中進行的離線對比。它不得連線生產環境、傳送訊息、發佈內容、讀取真實秘密或產生外部寫入。

### 準備

建立一個臨時副本和基線，命名為 `personal-system-triage-v1`。使用下面這份固定的、已脫敏的輸入：

```text
待分類專案：
1. 「按鈕在窄螢幕上溢位。」已有截圖；尚未做任何修復。
2. 「建置通過。」只有指令退出碼；沒有使用者驗收。
3. 「驗證失敗。」缺少版本、入口和錯誤日誌。
4. 「文案需要更新。」缺少受眾和來源。
```

使用下面這份固定的任務文字：

> 把四個專案分別分類為「需要更多輸入」「可以執行」或「需要人工確認」。不要虛構缺失的版本、權限或使用者驗收。對每個專案，寫出下一步和所需證據。

在任一路徑執行之前，先儲存輸入雜湊和乾淨臨時副本的雜湊。建立空白紀錄，命名為 `project-map`、`task-protocol`、`state-log`、`evidence-index` 和 `reflection`。不要把 token、密碼、Cookie、客戶文字或不必要的個人資料放進去。

### 任務

1. **基線 A：**只提供固定的任務和輸入，不使用個人工作系統的五種記錄。
2. **候選 B：**使用五種紀錄，把工作包標記為 `personal-system-v1`，並記錄讀取、變更、驗證、未驗證和被阻塞的內容。
3. 每條路徑各執行兩次。每次執行前都復原相同的輸入和臨時副本基線。使用 `run-id` 值 `20-personal-system-triage-v1-A-01`、`A-02`、`B-01` 和 `B-02`。
4. 不得連線、寫入、發佈或讀取秘密。如果任務需要其中任何一項動作，就把這次執行標記為 `blocked`；不要從模擬中推斷可用性。

### 證據門

每次執行儲存一條記錄：

```yaml
run_id: "20-personal-system-triage-v1-B-01"
task_id: "personal-system-triage-v1"
system_version: "none | personal-system-v1"
input_hash: "sha256:..."
baseline_hash: "sha256:...; 已恢復的臨時副本基線"
context_files: ["project-map", "task-protocol", "state-log", "evidence-index", "reflection"]
clarification_rounds: 0
actual_changes: "無變更或檔案/diff 摘要"
validation: "檢查、結果和退出碼；未執行則為 not_run"
evidence_items: ["輸入", "分類", "缺輸入的理由", "下一步", "驗證", "未驗證說明"]
evidence_completeness: "0/6"
rework_count: 0
log_location: "evals/results/；沒有執行則為 not_run"
reviewer: "獨立複核角色；沒有則為 not_assigned"
unverified_items: ["實際入口行為", "帳號層級權限", "執行期間結果"]
status: "pass | fail | not_comparable | blocked | not_run"
```

對比表必須包含重複解釋次數、澄清輪數、發現缺少輸入所用的時間、返工次數、證據完整度、分類錯誤和實際耗時。證據完整度是可核對的六項必需材料所占的比例。如果基線或輸入雜湊不一致，就使用 `not_comparable`；不要把這種差異稱為改進。

只有當四份日誌全部完整、沒有發生秘密或外部副作用，並且分類與停止理由符合驗收清單時，候選路徑才有資格獲得實驗通過。即便如此，結果也不會讓該 Skill 變成 `verified`。

### 失敗案例與邊界

把一條故意過時的指令和一個舊目錄作為靜態 fixture 資料加入專案地圖。正確的行為是檢查目前狀態、把相關紀錄標記為過時、停止重複使用舊指令，並在狀態日誌中記錄這個缺口。如果學習者複製了過時紀錄、虛構驗證細節、擴大權限，或把計畫當作驗證，實驗即告失敗，並保留失敗日誌。

### 反思

在 `reflection` 記錄中回答以下問題：

- 哪一項脈絡真正改變了決策？
- 哪條記錄已經過時？
- 還有哪些證據仍然缺失？
- 什麼解釋了基線與候選路徑之間的差異？
- 下次應該刪除、保留或更新什麼？
- 這條經驗能遷移到另一個領域嗎？它的限度在哪裡？

回答之後更新決策卡。「記得要小心」不是一條可移交的規則。

## 邊界與常見錯誤

- 不斷膨脹的脈絡會把舊事實與新目標混在一起。
- 個人紀錄不是秘密儲存，也不能替代權限複核。
- 「指令啟動了」不等於驗證完成；「這個帳號以前用過」也不能證明目前的入口和範圍正確。
- 對一次性請求，任務協議通常比新建一個 Skill 更輕。
- 沒有獨立重現、失敗集合和移交證據，Skill 就仍然只是 `candidate`。
- 一個已設定的產品功能、一段被記住的對話或一次成功的建置，本身都不能證明目前的執行期間行為、團隊影響、部署或使用者驗收。

## 遷移任務

把一個穩定的個人工作流程交給另一位成員。第二個人只能使用專案地圖、任務協議和證據索引，並且必須在可丟棄副本中工作，不能有任何口頭補充。儲存輸入雜湊、執行日誌、diff、驗收結果和缺少證據清單。記錄哪些隱性知識沒有被寫下來，然後決定要修訂哪份資產。

## 驗收清單

- [ ] 我能區分規則、任務脈絡、狀態、範本和反思。
- [ ] 我的記錄裡沒有 token、密碼、Cookie、客戶文字或不必要的個人資料。
- [ ] 我能在相同的輸入和基線下比較兩條路徑。
- [ ] 每次執行都有 `run-id`、日誌、證據完整性數值和未驗證項清單。
- [ ] 我能區分建立 Skill、保留協議、繼續觀察和阻塞。
- [ ] 我能識別過時指令並描述一種復原方法。
- [ ] 另一個人可以在沒有口頭補充的情況下復現關鍵判斷。

## 來源與維護邊界

脈絡、證據和反思方法屬於專案方法論。產品入口、Skill 的呼叫與分發、自動載入、權限模式和產品功能是會變化的事實。以下紀錄界定了來源邊界；它們不能證明每個帳號或每個執行期間的行為。

```yaml
- claim: "Skill 的呼叫與分發必須對照目前官方的 Skills 與 Plugins 文件以及獲授權的入口進行核查"
  source: "https://learn.chatgpt.com/docs/skills-and-plugins.md"
  checked_at: "2026-08-09"
  applies_to: "官方文件所宣告的產品入口、帳號範圍和組織範圍"
  owner: "課程維護者"
  next_review: "2026-11-09"
  claim_status: "current"
- claim: "權限與批准邊界取決於操作介面、sandbox 和批准設定；不能從單次會話推斷"
  source: "https://learn.chatgpt.com/docs/permission-modes.md"
  checked_at: "2026-08-09"
  applies_to: "官方文件所宣告的操作介面和配置範圍"
  owner: "安全與課程維護者"
  next_review: "2026-11-09"
  claim_status: "current"
```

本章刻意不聲稱存在記憶功能、會自動儲存某一類內容，或對特定帳號可用。如果日後要加入這樣的說法，它需要直接的來源、範圍、查閱日期、負責人和複核紀錄。本章狀態保持 `candidate`；實驗保持 `draft / not_run`。
