# 第7章：Skill、Plugin、MCP、ツールはどう仕事を分担するか

**状態：** `candidate`。**比較：** `not_run`。この章のケースは方法を学ぶためのもので、
外部Skillがこのリポジトリで実行されたことや、チームで採用できることを証明するものではありません。

**ここから始める：** まずタスクに何が足りないのかを言葉にします。そのうえで、
不足を埋める最小限の能力を選びます。名前や件数から選び始めないでください。

## この章が解決する問題

「Skillが必要だ」と考えても、それが正しいとは限りません。Skill、Plugin、MCPサーバー、
コネクター、スクリプト、テンプレート、ドキュメントは、それぞれ別の問題を解決します。これらを
同じ種類の「機能」として扱うと、不要な能力までインストールし、依存関係が見えないまま、
外部への影響範囲を広げてしまいます。

役に立つ問いは「どのディレクトリに Skill が多いか」ではありません。

> このタスクに何が足りないのか。権限、ライセンス、依存関係、証拠を管理できる範囲で、
> その不足を埋める最小限の能力は何か。

## 学習目標

- 方法・接続・実行・配布という四つの層を説明できる。
- ディレクトリではなくタスクを起点に、最小限の有用な組み合わせを導ける。
- Skill、Plugin、コネクターを採用する前に、起動条件、依存関係、ライセンス、権限、
  副作用、証拠を確認できる。
- ファイルの存在、発見、読み込み、採用、動作の検証を区別できる。

## 実際に起きる問題：タスクを始める前に発見でつまずく

[Codexの現場調査](../evidence-library-JA.md#source-notes)には公開報告があります。
ただし、これは症状の記録であって、公式な原因説明でもローカルでの再現でもありません。ここで大切なのは、
「パスにある」「見えている」「読み込まれた」「使えた」を別々に記録することです。

| 公開症状 | 報告者が観測したこと | **証明しないこと** | 最初の安全な対応 |
|---|---|---|---|
| Skill は通常のファイルなら動くが、シンボリックリンクにすると発見されない | ファイルの形を変えると、発見結果も変わった | すべてのスキャナー、OS、リリースで同じ問題が起きること | 正確なファイル形式と作業面を残し、隔離試験で通常ファイルとリンクを比較する |
| 明示的な Skill の利用が、暗黙の利用可能リストに依存する | 明示した要求を、現在の作業面に表示されたリストから切り離して扱えない | これが一般的な振り分け規則や公式保証であること | 表示されたリスト、正確な要求、セッション、読み込み済みリソースを分けて保存する |

リポジトリにパスがあるだけでは、現在のホストがそのSkillを発見したとは言えません。表示された
名前も、セッションが読み込んだ証拠にはなりません。読み込めたとしても、外部の依存関係や権限が
機能した証拠にはなりません。各段階を一つずつ観測し、観測できないものは `not_observed` と記録します。

## 1. 四つの層で能力を整理する

選ぶ前に、何が不足しているのかを四つの層のどれに当たるかで整理します。

```text
方法の層        Skill            ある種類のタスクを繰り返す方法
接続の層        MCP/connector    外部のデータ、コンテキスト、操作への接続
実行の層        tool             読む、編集する、実行する、閲覧する、呼び出す
配布の層        Plugin           複数の能力を配布・組み合わせるパッケージ
```

実際の製品では層が重なることもありますが、設計上の問いは別々です。まず「何が不足しているか」を
この四層のどれかに置き、最初から複数の層を追加しないでください。

| 層 | 与えるもの | それだけでは与えないもの |
|---|---|---|
| Skill | 繰り返すタスクやワークフローの指示と支援リソース | 権限、外部アクセス、この環境で方法が有効だという証明 |
| MCP サーバー / コネクター | 外部ツール、リソース、コンテキスト、操作への橋渡し | 認証、各操作の承認、安全なデータ境界 |
| ツール | ファイルの読み取り、コマンド実行、API 呼び出しなど、観測可能な操作 | 使う理由、使用許可、結果の正しさ |
| Plugin | 複数の能力の配布と組み合わせ | 自動的な認可、すべての構成要素が使える保証 |

毎回同じように実行する決まった処理には、スクリプトが向いています。出力の形をそろえたいなら
テンプレート、必要な場面で背景を確認したいならドキュメントが向いています。方法を繰り返し使いながら、
その都度コンテキストに応じた判断も必要なら、Skillに価値があります。決定的な処理を毎回Skillで生成し直す必要はありません。

## 2. 範囲を広げない順番で選ぶ

1. タスクに明確な手順があるかを確認し、なければ先にタスクを明確にする。
2. 同じ方法を繰り返し使い、手順を抜かしやすいなら Skill を検討する。
3. 外部データや操作が本当に必要なときだけ、コネクターや MCP サーバーが必要かを検討する。
4. 変換が決定的なら、スクリプトを優先する。
5. 複数の能力をまとめて配布する必要があるときは、Plugin を配布層として検討する。
6. それから初めて、インストール、認証、追加の権限を決める。

この順序は意図的に保守的です。大きなディレクトリは能力が増えたように見える一方で、依存関係と
権限の実際のつながりを読みづらくします。インストールや認証は、最後に判断する別の副作用です。

## 3. Skill の名前ではなく、タスクの不足から考える

候補を採用する前に、次の問いに文章で答えます。答えられない項目があれば、採用はいったん止めます。

- **task gap：** 足りないのは安定した方法、決定的なスクリプト、外部接続、それともタスク定義そのものか。
- **trigger / non-trigger：** どの入力で起動するか。似た依頼のうち、どれは起動せず別のSkillが扱うのか。共通語だけでは不十分です。
- **source / revision：** 別のレビュアーがURL、固定コミット、バージョン、アーカイブのハッシュ、棚卸し日を確認できるか。
- **license / dependency：** リポジトリのライセンスは対象ファイルをカバーしているか。NOTICE、入れ子のアセット、実行時の依存関係を棚卸ししたか。
- **permission / side effect：** 何を読み書きするか。ネットワークやアカウントが必要か。送信、公開、削除、変更など、外部に影響を与えられるか。
- **verification / maintenance：** 隔離試験で正常系、境界、失敗、移行を扱えるか。承認、保守、バックアップ、更新、ロールバックのリハーサルを誰が担当するか。

外部ディレクトリの件数は品質指標ではありません。自動化パッケージにも、アカウント、ネットワーク、第三者
サービスに関するリスクがあります。候補ごとに、確認できた証拠に基づいてレビューしてください。件数や星の数を、ライセンスや動作確認の代わりにしてはいけません。

### Plugin に含まれるものと、サポートの範囲

公式の [Plugins](https://learn.chatgpt.com/docs/plugins.md) は、Pluginをインストール可能な能力パッケージ
と説明し、Skills、Connectors、またはその両方を含められるとしています。ConnectorはMCPサーバーを介して、
外部システムのツール、共有情報、操作を提供することがあります。Pluginは配布と組み合わせの仕組みであり、
認可そのものではありません。インストールできることと、その操作を実行してよいことも別です。

2026-08-09に確認したサポート範囲には、ChatGPT Chat/WorkのWeb、デスクトップ、モバイル、ChatGPTデスクトップ
アプリのCodex、Codex CLIのPlugin browserが挙げられています。IDE拡張のPluginサポートは挙げられて
いません。モバイルでChat/Workを使えることは、デスクトップと同じディレクトリ閲覧・インストールの作業面を
持つことを意味しません。これは確認日の製品説明であり、現在のアカウントでの動作を示す証拠ではありません。

製品と接続を、一つひとつ根拠が必要な鎖として扱います。

```text
product support → account / organization authorization → Plugin install
→ connector authentication → 新しい session → Skill/tool が見える
→ 実際の invocation → 外部結果の verification
```

各矢印は独立した主張です。`Sign in with ChatGPT` だけでPluginのデータアクセスが自動的に付与されたり、操作が
承認されたりするわけではありません。[fact impact registry](../../docs/governance/fact-impact-registry.yaml) の `OF-015`、
`OF-016`、`UF-001`、`UF-003`、`LB-002` を、影響する内容を変える前に確認してください。

2026-08-10に確認した公式のSkills/Plugins資料は、自動マッチと明示的な選択を別の入口として
説明しています。ChatGPTは `@`、Codexは `$` を使い、インストール後の新しいチャットまたはCLIセッションも
流れの一部です。これらは変わり得る製品上の事実であり、Skillに自動で付く権限ではありません。
ローカルで確認するなら、作業面、セッション、正確な呼び出し、読み込んだリソース、動作の出力、結果の
検証を記録する必要があります。このリポジトリにはその実行時記録がないため、状態は
`not_observed` のままです。

## 4. 採用前に作るレビュー記録

インストール前に `skill-adoption-decision.md` を作ります。「ライセンスを確認した」と一行書くだけでは不十分です。別の人が同じ判断をたどれる程度の記録を残してください。

```text
task_gap:
trigger_conditions:
non_trigger_conditions:
source_url / revision / inventory_date:
license / NOTICE / nested_assets:
dependencies:
target_install_scope:
permissions:
external_side_effects:
isolated_trial:
backup_and_restore_target:
rollback_steps_and_success_check:
approval_points:
behavior_tests: positive | boundary | failure | migration
owner / next_review:
decision: recommendation-only | blocked | approved-to-install | installed-candidate
evidence / unverified:
```

| 決定 | 意味 | ここまで言える | ここからは言えない |
|---|---|---|---|
| `recommendation-only` | タスクには合いそうで、読み取り専用のレビューまたは隔離試験を続ける | 「さらにレビューする価値がある」 | 「インストールを承認した」「使える」 |
| `blocked` | ライセンス、NOTICE、リビジョン、依存関係、権限、ロールバックの根拠が欠ける | 「まだ採用しない。解除条件はこれ」 | 「先にインストールして後で記録する」 |
| `approved-to-install` | リビジョン、範囲、バックアップ、ロールバック、承認地点が明確で受理された | 「この範囲ではインストールできる」 | 「インストール済み」「検証済み」 |
| `installed-candidate` | 対象パスとインストール記録は観測できるが、動作レビューは未完了 | 「隔離されたインストール候補がある」 | 「チームが採用した」「production-ready」 |

プロジェクトの `draft`、`candidate`、`verified`、`production-ready` は、この採用決定とは別です。GitHub
ページが見えるだけではライセンスは明らかにならず、マニフェストが存在してもツール呼び出しの成功は証明できません。採用判断を、プロジェクトの公開状態と混同しないでください。

### 混同しやすい五つの状態

| 状態 | 最低限の根拠 | 証明しないこと |
|---|---|---|
| ファイルが存在する | 固定リビジョンのパス、マニフェスト、棚卸し、ハッシュ | 現在の作業面で発見できること |
| 発見された | 現在の作業面に見える一覧または名前解決 | このセッションが読み込んだこと |
| 読み込まれた | 新しいセッションのリソースまたは指示 | チームが採用したこと |
| 採用された | 宣言した範囲の所有者と承認記録 | 動作が検証済みであること |
| 検証済み | 宣言した環境での正常系・境界・失敗・移行の証拠 | 別のアカウント、入口、バージョンでも同じに動くこと |

インストールも観測できる操作です。対象パスとインストールログは `installed-candidate` の根拠になりますが、
発見、読み込み、採用、動作検証を飛ばすことはできません。インストールできたことだけで成功と判断しないでください。

### 二つの採用決定例

- **推薦：** S05の `code-review-and-quality` は、基準状態を固定した差分レビューに対する
  `recommendation-only` の候補です。根拠は `https://github.com/addyosmani/agent-skills` のローカルアーカイブ、
  SHA-256 `6EEDBE7D2EA3A82417781D879785BD501FBDE21275627F557DE4B76560BA1250`、および
  リポジトリ単位で MIT と読める兆候です。入れ子の依存関係、全アセット、実効権限、ロールバックは未レビュー
  なので、次に行うのは読み取り専用のレビューまたはオフラインの隔離試験であり、インストールではありません。
- **blocked の例：** S06の `webapp-testing` は `blocked` のままにします。出典は
  `https://github.com/composio-community/awesome-codex-skills` のローカルアーカイブ、SHA-256 は
  `D3DA83ED9D474690E7FF235351376114972840C78BC319CBCB8F89CBD704608E` です。ルートに Apache-2.0 の
  兆候があっても、入れ子になった各Skill、スクリプト、アセットまで一貫してライセンス / NOTICE の対象となる根拠は
  ありません。アセットごとのレビューと実行可能なロールバックがない限り、`SKILL.md` があるだけでは不十分です。ダウンロードやインストールを先にせず、まず不足している証拠を列挙します。

## 5. 能力は組み合わせ、積み重ねすぎない

```text
task protocol → domain method → tool または connection → evidence review
```

低リスクのマーケティング実験なら、タスクの手順が目的と境界を定め、製品コンテキストの方法が対象読者と
位置付けを整理し、分析ツールが必要なデータを記録し、Evidence Reviewがイベントが実際に起きたかを確認します。
重なる十個のSkillを開くより、一つの方法と明確な手順の方が、振り分けとコンテキストを理解しやすいことが多いでしょう。

## 6. 組み合わせる前に引き継ぐ

能力から別の能力へ仕事を渡すときは、同じ項目を使います。

```text
status | owner | scope | inputs | assumptions | actions_done
actions_not_done | evidence | unverified | blocked_on | next_check
permission_boundary | next_review
```

ドメインSkillは方法を、タスクの手順は実行の境界を、Evidence Reviewは既存の主張のレビューを、
Workflow Orchestratorは段階とチェックポイントを担当します。呼び出されたSkillが別のSkillの権限を取得することはなく、
完全なオーケストレーションを再帰的に始めるべきでもありません。引き継ぎ時には、どの能力が何を担当するかを明記します。

## 7. 実験：三つの能力の組み合わせを比べる

### 準備

ローカルで低リスクかつ元に戻せるタスクを選びます。タスクの手順、固定リビジョンのSkill候補を二つ、外部接続を
要求するシミュレーションの選択肢を用意します。一つは隔離レビューを続けられるもの、もう一つはライセンス、NOTICE、
ロールバックが不明なため拒否すべきものにします。実データのアップロード、メッセージ送信、第三者への書き込み、
外部アカウントの認証は行いません。各組み合わせに `run-id` を付け、タスク文と受け入れ基準を固定します。

### タスク

同じタスクに対して、(1) 明確な手順だけ、(2) 手順とドメインSkill、(3) 手順、ドメインSkill、外部接続の三つを
設計します。各候補の採用前レビューを先に終えます。実験は読み取り専用です。インストール、認証、チーム単位の設定は
有効にしません。出力の品質、時間、権限の範囲、検証コスト、副作用を比べ、追加の能力が本当に利益を生む場合と、
複雑さだけを増やす場合を説明します。

### 証拠と振り返り

三つの経路、各 `run-id`、二つの `skill-adoption-decision.md`、依存関係・権限の表、ライセンスの所見、
シミュレーションまたは実際の出力、検証結果、明示した「実行しなかった外部操作」の一覧を保存します。有効な記録では、
出典とリビジョンを調べられ、ライセンスの結論が実ファイルを指し、インストール、バックアップ、ロールバックの対象、
所有者、承認地点を名指しし、正常系・境界・失敗・移行をカバーし、追加接続のない基準状態を残します。
シミュレーションの呼び出しは、必ずシミュレーションと明記します。実行時の成功と取り違えないでください。

`recommendation-only` または `blocked` を次の状態へ進めるために必要な証拠を説明します。各観測が
存在、発見、読み込み、採用、検証のどれを示すかを記し、早い段階の状態を後の状態の代わりにしません。

## 意図的な失敗と境界ケース

三つのSkillを提示します。互いに重なり、そのうち一つは、タスクがローカルの整理だけで足りるのに外部へのアップロードを
要求します。さらに、リポジトリは開けて `SKILL.md` もあるものの、ライセンスまたはロールバックが不明な候補を加えます。
重複を見つけ、不要な権限を拒否し、不明な候補を `blocked` とし、手順だけまたは一つのSkillの基準状態を残せれば合格です。

## 移行タスク

四層モデルを調査ワークフローと製品レポートのワークフローに適用します。それぞれで、方法、接続、そしてスクリプトに
すべき決定的な変換を特定します。

## 出典と保守の境界

| 事実または境界 | 出典 | 確認日 | 適用範囲 |
|---|---|---:|---|
| Skill のタスク / ワークフロー指示とリソース、明示的な選択 | [Skills and Plugins](https://learn.chatgpt.com/docs/skills-and-plugins.md) | 2026-08-09 | 当日の公式説明。ここで読み込まれた証明ではない |
| Plugin の組み合わせ、作業面、インストール、コネクター認証、承認 | [Plugins](https://learn.chatgpt.com/docs/plugins.md) | 2026-08-09 | アカウントや組織によりアクセスは変わる |
| MCP サーバー、ツール / リソース / プロンプト、許可・拒否の設定 | [MCP](https://learn.chatgpt.com/docs/extend/mcp.md) | 2026-08-09 | 認証、ツール、ポリシーは別にレビューが必要 |
| コネクター / MCP 操作の承認境界 | [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security.md) | 2026-08-09 | このリポジトリの実行時設定ではない |
| シンボリックリンクと明示的な呼び出しで起きる発見の症状 | [Codex field research](../evidence-library-JA.md#source-notes) | 2026-08-09 | 公開報告。再現または公式な根本原因はない |
| 候補アーカイブの棚卸しとライセンスの兆候 | [Skill candidate catalog](../evidence-library-JA.md#source-notes) | 2026-08-09 | プロジェクトの棚卸し。外部 Skill のインストール承認ではない |

Skill、Plugin、コネクター、MCP、マニフェスト、認証、呼び出しの詳細は変わります。まず
一次資料の記録を更新し、その後で fact impact registry、本章、Lab、Skill、フィクスチャ、サイトの経路を
レビューしてください。公式の説明、コミュニティの症状、ローカル実行時の証拠を一つの文に混ぜないでください。

- [ ] タスクの不足、起動条件、対象外条件、出典リビジョン、ライセンス、依存関係、権限、副作用、所有者、ロールバックを説明できる。
- [ ] 候補を `recommendation-only` に保ち、ライセンスまたはロールバックが不明なら `blocked` にできる。
- [ ] 存在、発見、読み込み、採用、検証済みの動作を区別できる。
- [ ] 固定した入力、受け入れ条件、証拠の境界で、手順だけの場合と能力を組み合わせた場合を比較できる。
- [ ] 実行しなかった外部操作や実行時の成功を言う前に、必要な証拠を説明できる。
- [ ] 本章は `candidate`、比較は `not_run` のままだと報告できる。
