# 第 7 章：Skill、Plugin、MCP、ツールは仕事をどう分けるか

**状態：** `candidate`。**比較：** `not_run`。この章のケースは方法を学ぶためのものであり、
外部 Skill がこのリポジトリで動いたことを証明するものではありません。

**ここから始める：** まずタスクの不足を言葉にし、その不足を埋める最小限の能力を選びます。

## この章が解決する問題

「Skill が必要だ」という判断が、いつも正しいとは限りません。Skill、Plugin、MCP サーバー、
コネクター、スクリプト、テンプレート、ドキュメントは、それぞれ別の問題を解きます。互いに交換できる名前のように扱うと、
タスクに不要な能力をインストールし、依存関係を見えにくくしたまま、外部への影響を知らずに範囲を広げてしまいます。

役に立つ問いは「どのディレクトリに Skill が多いか」ではありません。

> このタスクに何が足りないのか。権限、ライセンス、依存関係、証拠を管理できる状態を保ちながら、
> その不足を埋める最小限の能力は何か。

## 学習目標

- 方法、接続、実行、配布という四つの層を説明する。
- ディレクトリではなくタスクから、最小限の有用な組み合わせを導く。
- Skill、Plugin、コネクターを採用する前に、起動条件、依存関係、ライセンス、権限、
  副作用、証拠を確認する。
- ファイルの存在、発見、読み込み、採用、動作の検証を区別する。

## 現実の問題：発見はタスク開始前に失敗し得る

[Codex の現場調査](../evidence-library-JA.md#source-notes)には公開報告があります。
これらは症状の記録であり、公式な原因説明でもローカルでの再現でもありません。

| 公開症状 | 報告者が観測したこと | **証明しないこと** | 最初の安全な対応 |
|---|---|---|---|
| Skill は通常のファイルなら動くが、シンボリックリンクにすると発見されない | ファイルの表現によって発見結果が変わった | すべてのスキャナー、OS、リリースに同じ欠陥があること | 正確なファイル表現と作業面を残し、隔離試験で通常ファイルとリンクを比べる |
| 明示的な Skill の利用が、暗黙の利用可能リストに依存する | 明示した要求を、現在の作業面のリストから独立した操作として扱えない | 一般的な振り分け規則や公式保証 | 見えるリスト、正確な要求、セッション、読み込み済みリソースを分けて保存する |

リポジトリにパスがあることは、現在のホストがその Skill を発見したことを意味しません。見えている
名前はセッションが読み込んだ証拠ではなく、読み込みは外部の依存関係や権限が働いた証拠でも
ありません。

## 1. 四つの層で能力を捉える

選ぶ前に、何が不足しているのかを層に分けて言葉にします。

```text
方法層          Skill            ある種類のタスクを繰り返す方法
接続層          MCP/connector    外部のデータ、コンテキスト、操作への接続
実行層          tool             読む、編集する、実行する、閲覧する、呼び出す
配布層          Plugin           複数の能力を配布・組み合わせるパッケージ
```

現実の製品では重なることがありますが、設計上の問いは違います。

| 層 | 与えるもの | それだけでは与えないもの |
|---|---|---|
| Skill | 繰り返すタスクやワークフローの指示と支援リソース | 権限、外部アクセス、この環境で方法が有効だという証明 |
| MCP サーバー / コネクター | 外部ツール、リソース、コンテキスト、操作への橋渡し | 認証、各操作の承認、安全なデータ境界 |
| ツール | ファイルの読み取り、コマンド実行、API 呼び出しなど、観測可能な操作 | 使う理由、使用許可、結果の正しさ |
| Plugin | 複数の能力の配布と組み合わせ | 自動的な認可、すべての構成要素が使える保証 |

毎回同じように実行すべき決まった処理にはスクリプトが向きます。出力の形を安定させたいなら
テンプレート、特定の場面だけ読む背景知識にはドキュメントが向きます。方法を繰り返し使いながら、
なお文脈ごとの判断が必要なら、Skill に価値があります。

## 2. 範囲を広げない順番で選ぶ

1. タスクに明確な手順があるかを判断し、なければ先に明確にする。
2. 同じ方法を繰り返し使い、人が手順を抜かしやすいなら Skill を考える。
3. 外部データや操作が必要なときだけ、コネクターや MCP サーバーが必要かを問う。
4. 変換が決定的なら、スクリプトを優先する。
5. 複数の能力をまとめて配布する必要があるとき、Plugin を配布層として考える。
6. その後で初めて、インストール、認証、追加の権限を決める。

この順序は意図的に保守的です。大きなディレクトリは能力が増えたように見せる一方で、依存関係と
権限の実際のつながりを読みにくくします。

## 3. Skill の名前ではなく、タスクの不足から始める

候補を採用する前に、次を文章で答えます。

- **task gap：** 安定した方法、決定的なスクリプト、外部接続、それともタスク定義自体のどれが不足しているか。
- **trigger / non-trigger：** どの入力で起動するか。似た依頼のどれは起動せず、別の Skill が扱うか。共通語だけでは足りない。
- **source / revision：** 別のレビュー担当者が URL、固定コミット、バージョン、アーカイブのハッシュ、棚卸し日を調べられるか。
- **license / dependency：** リポジトリのライセンスは対象ファイルをカバーするか。NOTICE、入れ子のアセット、実行時の依存関係を棚卸ししたか。
- **permission / side effect：** 何を読み書きするか。ネットワークやアカウントが必要か。送信、公開、削除、変更など外部を変えられるか。
- **verification / maintenance：** 隔離試験で正常系、境界、失敗、移行を扱えるか。誰が承認、保守、バックアップ、更新、ロールバックのリハーサルを担当するか。

外部ディレクトリの件数は品質指標ではありません。自動化パッケージにも、アカウント、ネットワーク、第三者
サービスに関するリスクがあります。候補ごとに、自分で確認した証拠に基づくレビューが必要です。

### Plugin に含まれるものと、サポートの範囲

公式の [Plugins](https://learn.chatgpt.com/docs/plugins.md) は、Plugin をインストールできる能力パッケージ
と説明し、Skills、Connectors、またはその両方を含められるとしています。Connector は MCP サーバーに
支えられ、外部システムのツール、共有情報、操作を提供することがあります。Plugin は配布と組み合わせの仕組みであり、
認可そのものではありません。

2026-08-09 に確認したサポート範囲には、ChatGPT Chat/Work の Web、デスクトップ、モバイル、ChatGPT デスクトップ
アプリの Codex、Codex CLI の Plugin browser が挙げられています。IDE 拡張の Plugin サポートは挙げられて
いません。モバイルで Chat/Work が使えることは、デスクトップと同じディレクトリ閲覧・インストールの作業面を
持つことを意味しません。

製品と接続を、一つひとつ根拠が必要な鎖として扱います。

```text
product support → account / organization authorization → Plugin install
→ connector authentication → 新しい session → Skill/tool が見える
→ 実際の invocation → 外部結果の verification
```

各矢印は独立した主張です。`Sign in with ChatGPT` は Plugin のデータアクセスを自動的に与えず、操作を
承認もしません。[fact impact registry](../../docs/governance/fact-impact-registry.yaml) の `OF-015`、
`OF-016`、`UF-001`、`UF-003`、`LB-002` を、影響する内容を変える前に確認してください。

2026-08-10 に確認した公式の Skills/Plugins 資料は、自動マッチと明示的な選択を別の入口として
説明しています。ChatGPT は `@`、Codex は `$` を使い、インストール後の新しいチャットまたは CLI セッションも
流れの一部です。これらは変わり得る製品上の事実であり、Skill に自動で付く権限ではありません。
ローカルの確認では、作業面、セッション、正確な呼び出し、読み込んだリソース、動作の出力、結果の
検証を残す必要があります。このリポジトリにはその実行時記録がないため、状態は
`not_observed` のままです。

## 4. 採用前のレビュー・パッケージ

インストール前に `skill-adoption-decision.md` を作ります。「ライセンスを確認した」だけでは足りません。

```text
task_gap:
trigger_conditions:
non_trigger_conditions:
source_url / revision / inventory_date:
license / NOTICE / nested_assets:
dependencies:
target_install_scope:
permissions:
external_side_effects:
isolated_trial:
backup_and_restore_target:
rollback_steps_and_success_check:
approval_points:
behavior_tests: positive | boundary | failure | migration
owner / next_review:
decision: recommendation-only | blocked | approved-to-install | installed-candidate
evidence / unverified:
```

| 決定 | 意味 | 言えること | 言えないこと |
|---|---|---|---|
| `recommendation-only` | タスクには合いそうで、読み取り専用のレビューまたは隔離試験を続ける | 「さらにレビューする価値がある」 | 「インストールを承認した」 |
| `blocked` | ライセンス、NOTICE、リビジョン、依存関係、権限、ロールバックの根拠が欠ける | 「まだ採用しない」 | 「先にインストールして後で記録する」 |
| `approved-to-install` | リビジョン、範囲、バックアップ、ロールバック、承認地点が明確で受理された | 「この範囲ではインストールできる」 | 「インストール済み」または「検証済み」 |
| `installed-candidate` | 対象パスとインストール記録は観測できるが、動作レビューは未完了 | 「隔離されたインストール候補がある」 | 「チームが採用した」または「production-ready」 |

プロジェクトの `draft`、`candidate`、`verified`、`production-ready` は、この採用決定とは別です。GitHub
ページが見えることはライセンスを明らかにせず、マニフェストの存在はツール呼び出しの成功を証明しません。

### 混同しやすい五つの状態

| 状態 | 最低限の根拠 | 証明しないこと |
|---|---|---|
| ファイルが存在する | 固定リビジョンのパス、マニフェスト、棚卸し、ハッシュ | 現在の作業面で発見できること |
| 発見された | 現在の作業面に見える一覧または名前解決 | このセッションが読み込んだこと |
| 読み込まれた | 新しいセッションのリソースまたは指示 | チームが採用したこと |
| 採用された | 宣言した範囲の所有者と承認記録 | 動作が検証済みであること |
| 検証済み | 宣言した環境での正常系・境界・失敗・移行の証拠 | 別のアカウント、入口、バージョンでも同じに動くこと |

インストールも観測できる操作です。対象パスとインストールログは `installed-candidate` を支えられますが、
発見、読み込み、採用、動作検証を飛ばすことはできません。

### 二つの採用決定例

- **推薦：** S05 の `code-review-and-quality` は、定義済みの基準状態を持つ差分レビューに
  `recommendation-only` の候補になります。`https://github.com/addyosmani/agent-skills` のローカルアーカイブ、
  SHA-256 `6EEDBE7D2EA3A82417781D879785BD501FBDE21275627F557DE4B76560BA1250`、リポジトリ単位で MIT と読める
  兆候が根拠です。入れ子の依存関係、完全なアセット一式、実効権限、ロールバックは未レビュー
  なので、次は読み取り専用のレビューまたはオフラインの隔離試験であり、インストールではありません。
- **blocked の例：** S06 の `webapp-testing` は `blocked` のままにします。出典は
  `https://github.com/composio-community/awesome-codex-skills` のローカルアーカイブ、SHA-256 は
  `D3DA83ED9D474690E7FF235351376114972840C78BC319CBCB8F89CBD704608E` です。ルートに Apache-2.0 の
  兆候があっても、各入れ子の Skill、スクリプト、アセットに一貫したライセンス / NOTICE の適用範囲がある根拠は
  ありません。アセットごとのレビューと実行できるロールバックがない限り、`SKILL.md` があるだけでは不十分です。

## 5. 能力は組み合わせ、積み重ねすぎない

```text
task protocol → domain method → tool または connection → evidence review
```

低リスクのマーケティング実験なら、タスクの手順が目的と境界を定義し、製品コンテキストの方法が対象読者と
位置付けを渡し、分析ツールが必要なデータを記録し、Evidence Review がイベントが実際に起きたかを調べます。
重なる十個の Skill を開くより、一つの方法と明確な手順の方が、振り分けと文脈を理解しやすいことが多いです。

## 6. 組み合わせる前に引き継ぐ

能力から別の能力へ仕事を渡すときは、同じ項目を使います。

```text
status | owner | scope | inputs | assumptions | actions_done
actions_not_done | evidence | unverified | blocked_on | next_check
permission_boundary | next_review
```

ドメイン Skill は自分の方法を、タスクの手順は実行の境界を、Evidence Review は既存の主張のレビューを、
Workflow Orchestrator は段階とチェックポイントを担当します。呼び出された Skill は別の Skill の権限を取得せず、
完全なオーケストレーションを再帰的に始めるべきでもありません。

## 7. 実験：三つの能力の組み合わせを比べる

### 準備

ローカルで低リスク、元に戻せるタスクを選びます。タスクの手順、固定リビジョンの Skill 候補を二つ、外部接続を
要求するシミュレーションの選択肢を用意します。一つは隔離レビューを続けられ、もう一つはライセンス、NOTICE、
ロールバックが不明なため拒否されるべきものにします。実データのアップロード、メッセージ送信、第三者への書き込み、
外部アカウントの認証はしません。各組み合わせに `run-id` を付け、タスク文と受け入れ基準を固定します。

### タスク

同じタスクに対して、(1) 明確な手順だけ、(2) 手順とドメイン Skill、(3) 手順、ドメイン Skill、外部接続の三つを
設計します。各候補の採用前レビューを先に終えます。実験は読み取り専用です。インストール、認証、チーム単位の設定は
有効にしません。出力の品質、時間、権限の範囲、検証コスト、副作用を比べ、追加の能力が純粋な利益になる場合と、
複雑さだけを増やす場合を説明します。

### 証拠と振り返り

三つの経路、各 `run-id`、二つの `skill-adoption-decision.md`、依存関係・権限の表、ライセンスの所見、
シミュレーションまたは実際の出力、検証結果、明示した「実行しなかった外部操作」の一覧を保存します。有効な行では、
出典とリビジョンを調べられ、ライセンスの結論が実ファイルを指し、インストール、バックアップ、ロールバックの対象、
所有者、承認地点を名指しし、正常系・境界・失敗・移行をカバーし、追加接続のない基準状態を残します。
シミュレーションの呼び出しはシミュレーションと明記します。

`recommendation-only` または `blocked` を次の状態へ動かすために必要な証拠を説明します。各観測が
存在、発見、読み込み、採用、検証のどれを示すかを記し、早い状態で後の状態を置き換えません。

## 意図的な失敗と境界ケース

一つは外部へのアップロードを要求するが、タスクはローカルの整理だけで足りる、重なった三つの Skill を
提示します。さらに、リポジトリは開けて `SKILL.md` もあるものの、ライセンスまたはロールバックが不明な候補を
加えます。重複を見つけ、不要な権限を拒否し、不明な候補を `blocked` とし、手順だけまたは一つの Skill の
基準状態を残せれば合格です。

## 移行タスク

四層モデルを調査ワークフローと製品レポートのワークフローに適用します。それぞれで、方法、接続、スクリプトに
すべき決定的な変換を特定します。

## 出典と保守の境界

| 事実または境界 | 出典 | 確認日 | 適用範囲 |
|---|---|---:|---|
| Skill のタスク / ワークフロー指示とリソース、明示的な選択 | [Skills and Plugins](https://learn.chatgpt.com/docs/skills-and-plugins.md) | 2026-08-09 | 当日の公式説明。ここで読み込まれた証明ではない |
| Plugin の組み合わせ、作業面、インストール、コネクター認証、承認 | [Plugins](https://learn.chatgpt.com/docs/plugins.md) | 2026-08-09 | アカウントや組織によりアクセスは変わる |
| MCP サーバー、ツール / リソース / プロンプト、許可・拒否の設定 | [MCP](https://learn.chatgpt.com/docs/extend/mcp.md) | 2026-08-09 | 認証、ツール、ポリシーは別にレビューが必要 |
| コネクター / MCP 操作の承認境界 | [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security.md) | 2026-08-09 | このリポジトリの実行時設定ではない |
| シンボリックリンクと明示的な呼び出しで起きる発見の症状 | [Codex field research](../evidence-library-JA.md#source-notes) | 2026-08-09 | 公開報告。再現または公式な根本原因はない |
| 候補アーカイブの棚卸しとライセンスの兆候 | [Skill candidate catalog](../evidence-library-JA.md#source-notes) | 2026-08-09 | プロジェクトの棚卸し。外部 Skill のインストール承認ではない |

Skill、Plugin、コネクター、MCP、マニフェスト、認証、呼び出しの詳細は変わります。まず
一次資料の記録を更新し、それから fact impact registry、本章、Lab、Skill、フィクスチャ、サイトの経路を
レビューしてください。公式の説明、コミュニティの症状、ローカル実行時の証拠を一文に混ぜません。

## 受け入れチェックリスト

- [ ] Skill、Plugin、MCP サーバー、コネクター、ツール、スクリプト、テンプレート、ドキュメントを区別できる。
- [ ] タスクの不足、起動条件、対象外条件、出典リビジョン、ライセンス、依存関係、権限、副作用、所有者、ロールバックを説明できる。
- [ ] 候補を `recommendation-only` に保ち、ライセンスまたはロールバックが不明なら `blocked` にできる。
- [ ] 存在、発見、読み込み、採用、検証済みの動作を区別できる。
- [ ] 固定した入力、受け入れ条件、証拠の境界で、手順だけの場合と能力を組み合わせた場合を比較できる。
- [ ] 実行しなかった外部操作や実行時の成功を言う前に、必要な証拠を説明できる。
- [ ] 本章は `candidate`、比較は `not_run` のままだと報告できる。
