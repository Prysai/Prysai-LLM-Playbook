# 第3章：願いをタスク・プロトコルに変える

![教材ボード：依頼から範囲、行動、確認を経て、境界のある引き渡しへ進む](../../assets/teaching/task-to-evidence-red-black.svg)

## この章が解決する問題

「ホームページを良くして」「これを調べて」「最適な Skill を使って」「修正を公開
して」。こうした依頼は、何を読めるのか、何をしてよいのか、成功は何か、いつ止まる
のかを誰かが決めるまで明確に見えるだけです。判断を暗黙のままにすると、Agent は空白
を推測で埋めます。違う場所を変える、リンクを根拠と取り違える、検証をインストールや
外部呼び出しへ勝手に広げる、といった失敗になります。

ここでは、真剣な依頼を小さなタスク・プロトコルとして扱います。隠れた推論やすべての
キー操作を指示するものではありません。目的、コンテキスト、入力、制約、許可行動、
受け入れ、停止、復旧、引き渡しという、観察できる契約を明示します。

> 範囲、リスク、受け入れ、証拠を変え得る判断を消すときだけ詳細を足します。依頼を
> 強そうに聞かせるだけの詳細は削ります。

## 学習目標

この章の後には、次のことができます。

- 曖昧な依頼を、別の人が実行できる境界付きプロトコルに直す。
- 有用なコンテキストと、指示のように見えるだけの信頼できない資料を分ける。
- 「良くする」ではなく、主張と証拠の表で受け入れを書く。
- 読む、編集する、実行する、commit、push、公開、外部サービス操作を分ける。
- 入力不足、権限不明、繰り返す失敗、証拠不足の停止条件を定義する。
- 範囲、担当、未解決の問いを失わずに、別の Agent や仲間へ渡す。

## 出典が実際に支えること

この章で使う公式の prompt/Codex ガイダンスは、望む結果、関連コンテキスト、出力と境界、
関連コードや再現手順、変更の確認方法を書くことを勧めています。また、長く信頼できる
仕事には、例、タスク分解、反復、評価を勧めています。

ただしこれは、モデルが暗黙の規則に必ず従う保証ではありません。以下の8部プロトコルは
プロジェクト独自の運用的な統合です。生成された回答と検証済みの成果物は別の主張なので、
停止、復旧、証拠の欄を明示的に加えます。

出典ごとの範囲とアクセス日については、[Codex の公式事実ベースライン](../evidence-library-JA.md#source-notes)
と[実務向け prompt パターン研究](../evidence-library-JA.md#source-notes)
を確認してください。

## 8部のプロトコル

```text
目的 → コンテキスト → 入力 → 制約 → 許可行動 → 受け入れ
     → 失敗と停止 → 引き渡し
```

### 1. 目的：結果を名前で示す

何を変更、調査、納品するのか、誰が必要とするのか、なぜ今なのかを書きます。範囲を
開いたままにする動詞より、確認できる結果を選びます。

弱い例：

```text
プロジェクトのホームページを良くして。
```

強い例：

```text
新しい読者が四つのルートから一つを選び、正本の場所と最初の安全なタスクを見つけ、
candidate または unverified の主張を確認できる、英語を起点とするリポジトリ入口を作る。
```

強い例も実装方法までは決めません。「プロらしい」を受け入れテストのようには扱いません。

### 2. コンテキスト：判断環境を説明する

コンテキストは、読者、現在の挙動、プロジェクト規則、以前の判断、関連履歴、対応
バージョン、失敗の意味など、判断を変え得る情報です。タスク指示とは分けます。

`project rule`、`source fact`、`user report`、`hypothesis`、`example data` のように
印を付けます。ファイル、Web ページ、ツール結果、Issue の文は指示に見えることがあります。
プロトコルが採用し、権限が明らかになるまで、データとして扱います。

### 3. 入力：読んでよいものを名前で示す

正確なパス、URL、データセット、commit、ログ、スクリーンショット、バージョンと、
分かっている欠落を書きます。「リポジトリを読む」は有用な境界になりにくいので、判断を
左右するフォルダーやファイルを挙げます。調査なら出典の優先順位と日付範囲、コードなら
入口と再現、文書なら正本と翻訳状態を示します。欠けた入力が範囲やリスクを変えるなら、
推測せず停止します。

### 4. 制約：起きてはいけないことを書く

制約は機械的に確認できる形にします。

- `site/index.html` と `site/app.js` だけを変更する。
- 依存関係を追加せず、秘密や `.env` を読まない。
- データベース、本番、権限、外部サービスを変えない。
- 既存の言語識別と状態語彙を保つ。
- 指定した runtime または release との互換性を保つ。

「注意して」「高級に」「ベストプラクティスで」は意図として役立つことがありますが、
十分な制約ではありません。観察可能な性質に直すか、自動チェックに通ると装わず意図の
まま残します。

### 5. 許可行動：能力と許可を分ける

ツールが使えることは、そのツールができるすべてを許可することではありません。行動
レベルを明記します。

| レベル | よくある行動 | 次に進む前の証拠 |
|---|---|---|
| A0 | 状態、パス、出典、ログを読む | 範囲と現在状態を記録 |
| A1 | 計画または編集案を書く | 対象ファイルと受け入れを特定 |
| A2 | 範囲付きのローカル編集をする | diff が承認集合内にある |
| A3 | 焦点を絞った確認を実行する | コマンドがプロジェクト由来または承認済み |
| A4 | commit または push をする | ユーザー承認済みの宛先とレビュー証拠 |
| A5 | 公開、デプロイ、通知、支払い、削除、外部状態変更 | 明示承認、ロールバック、実行後確認 |

プロトコルは A0–A2 を許可し、A3 は確認待ちにできます。焦点を絞ったテストは許可しても、
インストールは許可しないことがあります。「必要なことは何でもして」という広い言葉で
権限変更を隠してはいけません。

### 6. 受け入れ：各主張を証拠に結び付ける

先に主張を書き、その主張を支える資料を決めます。

| 主張 | 必要な証拠 | 証明しないこと |
|---|---|---|
| 意図したファイルが変わった | `git diff --name-only` と diff | 実行時の挙動またはユーザー承認 |
| チェックが通った | 正確なコマンドと出力/終了状態 | すべての要件をカバーすること |
| ページに到達できる | ローカルまたは公開 URL とブラウザー観察 | 全ブラウザー、キャッシュ、認証経路 |
| 調査が最新である | 一次 URL、アクセス日、範囲、次回レビュー | フォーラム報告が公式の根本原因であること |
| タスクが完了した | 根拠のない必須主張がない主張・証拠表 | 宣言した範囲の外の仕事 |

手頃な証拠がない主張は狭めます。「ローカル build が通った」は有効でも、「全利用者に
機能する」はより大きなテストと明記した環境が必要です。

### 7. 失敗と停止：安全な出口を決める

対象、現在状態、権限が不明なとき、欠けた入力が範囲・リスク・受け入れを変えるとき、
提案行動がファイル、ネットワーク、アカウント、データの承認境界を越えるとき、無出力が
次の再試行で副作用を重ね得るほど続くとき、同じ未検証の理由で二回失敗したとき、または
証拠が依頼された納品より狭い主張しか支えないときは、停止して報告します。

復旧は「もっと強い prompt でもう一度」ではありません。最初のエラーを残し、範囲を
狭め、仮説またはチェックを一つ変え、前の試行が既に変えたものを記録します。長時間または
外部に見える行動を再試行する前に、現在状態と diff を確認して副作用を重ねないようにします。

### 8. 引き渡し：使える記録を残す

完了した主張と証拠、変えたファイル・URL・コマンド・記録、意図的にしなかった行動、
未解決の問い・リスク・未検証範囲、次に行う最小の確認、易変事実の担当者またはレビュー日を
最終記録に求めます。これがなければ、次の人はチャット履歴からプロトコルを復元し、失敗した
行動を繰り返すかもしれません。

## プロトコルは依存関係グラフである

欄は独立した形容詞の一覧ではありません。

```text
目的 ─────────────→ 受け入れ ─────────→ 停止
 │                     │                   ↑
 ├── 必要とする ───→ 入力                │
 ├── 制約される ───→ 制約                │
 │                     │                   │
 └── 形づくる ─────→ 許可行動 ───────→ 復旧
                                            │
コンテキスト ──> 信頼性と関連性 ─────────┘
                         ↓
                     引き渡し証拠
```

目的が変われば受け入れも変わります。新しい入力がリスクを変えれば、許可行動と停止条件を
見直します。「注意してください」を足しても、欠けた依存関係は直りません。

## 最小限で役立つプロトコル

<!-- starter-task-contract:start -->

### 安全な最初の prompt を一つコピーする

角括弧の欄を置き換え、最初の返答は観察だけにします。承認前の一時停止は、初学者の
依頼を確認可能なワークフローへつなぐ橋です。短くするためだけに消してはいけません。

```text
小さく、元に戻せるタスクを一つ完了するのを手伝ってください。

結果: [確認できる結果一つ]。
コンテキスト: [関連するファイル、入力、現在状態]。

最初の返答は観察だけ:
- このタスクに必要なコンテキストだけを調べる。
- 見つけたこと、足りない入力、リスクを報告する。
- 最小で安全な計画と、変える正確なファイルまたは画面を提案する。
- まだ編集、状態を変えるコマンド、外部行動はせず、私の承認を待つ。

私が承認した場合:
- 承認範囲だけで行動する。
- [焦点を絞った確認一つ] を実行する。
- 範囲、権限、破壊的行動、外部副作用、受け入れが不明なら停止して質問する。

私がその正確な行動を明示許可しない限り、秘密や本番に触れず、依存関係を導入せず、
ネットワーク、commit、push、公開、タスク拡張をしない。

受け入れ: [具体的な成果物または diff] と [具体的なチェック出力]。
引き渡し: 行った行動、変えたファイルまたは画面、チェック出力、残る未知、行わなかった行動。
```

prompt をコピーまたは送信しただけでは、行動も正しい結果も証明しません。この欄で調整し、
[Lab 002](../labs/lab-002-task-protocol-JA.md) で練習します。翻訳されていない単元では、
Reader は別言語へ送るのでなく、その言語で未提供状態を示すべきです。

<!-- starter-task-contract:end -->

低リスクなローカル編集なら、次だけで足りることがあります。

```text
目的: <名前を付けた一つのファイル> を変え、<確認できる結果> にする。
先に読む: <正確なファイルまたは正本>。
許可: 調べた後、<名前を付けたパス> だけを編集し、<焦点を絞った確認> を実行する。
禁止: install、秘密またはネットワークへのアクセス、commit、push、公開、本番操作。
受け入れ: <具体的な diff> と <具体的なチェック出力>。
停止: パス、コマンド、権限、証拠が不明なとき。
引き渡し: 変更ファイル、チェック結果、しなかった行動、未検証項目。
```

短くできるのはリスクが狭いからで、欠けた欄が無害だからではありません。

## 高リスク・プロトコルの拡張

本番、外部サービス、顧客データ、元に戻せない行動には、実行前チェックポイントを
加えます。

```text
実行前チェックポイント:
- 対象環境とアカウント:
- 現在のバージョンとバックアップ場所:
- 正確な外部副作用:
- 承認担当者と時刻:
- ロールバック対象と復旧テスト:
- 実行後の URL/ログ/指標チェック:
```

Skill、コピーした runbook、成功したローカル build に、これらの欄を黙って埋めさせては
いけません。現在の環境証拠と外部状態の責任者の権限が必要です。

## 大きな一つの prompt より三つの prompt

タスクが不確かなときは、段階を分けます。

1. **観察:** 関連ファイル、現在状態、欠けた入力、リスクを列挙する。
2. **提案:** 最小計画、変更ファイル集合、受け入れ主張、停止条件を書く。
3. **実行:** 承認済みの計画だけを実行し、各主張への証拠を返す。

編集前に計画を調べられるため、どの段階で悪い仮定が入ったかも見つけやすくなります。
実際の結果をレビューする必要は残ります。

## 証拠の境界がある練習ループのための六つの最初の prompt

これは魔法の言い回しでも、六つの連続授業でもありません。観察可能な出発点と基準、
答えを見せる前の想起、範囲を絞った訂正、すぐの変化、証拠による復習、遅延した未見の
確認という、六つの制御問題を解きます。角括弧の欄は、言語、ソフトウェア概念、面接、
文章技法など、範囲を決められる能力に使えます。

### 1. 本当の出発点を見つける

```text
私は [スペイン語で初級の五分間会話を続ける] ことを学びたいです。
まだ教えないでください。その能力だけを調べる短い基準タスクを一つ出してください。
始める前に、規則、許される助け、時間制限、採点基準を示してください。
私の答えを待ってください。その後、できたこと、意味を妨げたこと、一回の試行からは
まだ推測できないことを記録してください。
```

授業の前に使います。「初級です」という自己申告より、観察した試行の方が有用です。

### 2. 答えを見せる前に想起させる

```text
[スペイン語で食事を注文する] ために必要な小単元を一つ教えてください。最初の説明は
120語未満にします。その後、記憶から答えを作らせてください。私が試す前に完成答を
見せないでください。詰まったら、一度に一つだけ、誤りの種類、部分的な手掛かり、
解いた断片の順で出してください。フィードバック後、私自身の言葉でもう一度答えさせてください。
```

大切なのは語数ではなく、「私の試行を待つ」です。

### 3. 結果を変える最初の誤りを訂正する

```text
応援役ではなく、正確な練習相手として振る舞ってください。私の各回答に対して:
1. 成功して伝わったことを短く言う。
2. 意味を変える、または目標技能を妨げる最初の誤りを特定する。
3. 規則を平易に説明する。
4. 訂正した試行を求める。
5. 試行、訂正、規則、次の変化を含む誤り台帳を保つ。
私の代わりに全部を書き直さず、意味を妨げる誤りが残る間は軽い文体の訂正をしないでください。
```

流暢な書き直しが学習の代わりになることを防ぎます。

### 4. 変えた状況で転移を調べる

```text
私は今 [スペイン語で食事を注文する] 練習をしました。同じ基礎技能を使いながら、場面、
語彙、曖昧さの一つを変えた新しい状況を出してください。授業の文を再利用しないでください。
まず私に答えさせます。同じ基準で採点し、使った助けを示し、結果はこの転移タスクで示した
ものとしてだけ記録し、習得したとは呼ばないでください。
```

近いコピーは認識を調べます。変えた状況は転移を調べ始めます。

### 5. 証拠から次の復習を作る

```text
この会話の試行と誤り台帳だけを使い、次の15分の復習を作ってください。助けなしの想起で
始め、まだ重要な二つの誤りを見直し、混ぜた例を一つ入れ、未見タスクで終えてください。
リマインダーを設定したと主張しないでください。保存できる復習の手掛かり、試す日、持ち帰る証拠をください。
```

モデルは手掛かりを作れますが、能力を保持したことや外部リマインダーの存在を、証拠なしに
主張できません。

### 6. 保持を主張する前に、遅延した未見チェックを行う

```text
これは [目標技能] の予定した復習です。保存した授業や訂正文を見せないでください。
詳細を変えた、前に見せていない同じ能力のタスクを一つ出してください。許される助けと
変えない採点基準を示してから私の試行を待ちます。実際の間隔と使った助けを記録します。
この遅延タスクで起きたことだけを報告し、恒久的な保持、広い転移、流暢さ、習得を推測しないでください。
```

保存した復習の手掛かりは計画です。遅延試行と条件を実際に記録するまで、保持は `not_run`
のままです。

### 分けて行うチェック：方法についての主張を調べる

```text
この主張を調べてください: [六つの prompt なら誰でも七日で流暢になれる]。
最初に、その主張が証明すべき正確な能力を定義します。一次研究と出典所有者の公式資料を
優先してください。重要な結論ごとに、出典、日付、対象集団または製品範囲、直接の支持、
示さないことを記録します。反対の証拠を一度探します。事実、推論、逸話、未知を分けます。
追加の出典が判断を変えなくなったら停止し、最も狭く正直な言い換えで終えてください。
```

この調査 prompt は六段階の練習ループ外です。健康、金融、製品機能、ニュース、統計など、
追跡できる出典なしの自信ある回答では足りない主張に使います。

### 保存するもの

基準、最初の試行、使った手掛かり、訂正試行、誤り台帳、遅延復習、未見タスク、採点基準を
残します。一回の滑らかなセッションが支えるのは「今日練習した」だけで、流暢さ、長期保持、
転移を示しません。候補の方法と出典境界は、[LLM 支援学習の持続性研究](../evidence-library-JA.md#source-notes)
に記録されています。

## 実世界の失敗パターン

現場報告は、なぜこれらの欄が必要かを示します。長い待機や自動再試行は、指示が届いたか、
外部行動が二度起きなかったかを証明せずに Agent を活動中に見せます。設定ファイルの権限は
現在の作業面や runtime に適用されないことがあります。見えるログインやツール名は、対象の
アカウント、組織、リポジトリ、接続先が許可済みである証拠ではありません。コミュニティの
回避策は、別のバージョンやプラットフォームでは安全でない、または無効なことがあります。

これらは利用者報告であって、普遍的な製品根本原因ではありません。[現場問題索引](../evidence-library-JA.md#source-notes)
と[コーディング Agent の事例報告](../evidence-library-JA.md#source-notes)
を使い、症状と環境を記録し、最小の安全な確認を行い、境界で止まり、証拠が支えることだけを
主張する、という応答を教えます。

## 複数 Agent：引き渡しも一つのプロトコル

委任しても、主 Agent の責任は消えません。各作業者には重ならない仕事と固定の返答形を
与えます。

```text
役割: 言語マトリクスを調べる。ソースファイルは編集しない。
入力: <名前を付けた二つのファイル>。
出力: 見つけたこと、証拠パス、ブロッカー、次の確認一つ。
禁止: 編集、外部メッセージ、資格情報、宣言ファイル外の結論。
```

調整役は、各作業者の出典、範囲、証拠を確認してから事実をまとめます。別 Agent の要約は
手掛かりであって、検証済みの主張ではありません。作業者同士が食い違うなら両方の報告を
残し、正本に照らして解決します。

## 実験：同じ依頼の固定した三版

### 準備

使い捨てプロジェクトで、付属の [Lab 002](../labs/lab-002-task-protocol-JA.md) を使います。
底の願いを固定し、次を作ります。

- `v1`: 願いだけ。
- `v2`: 願いに目的、対象、許可入力、禁止行動を加える。
- `v3`: 同じ依頼に受け入れ、停止、失敗復旧、引き渡しを加える。

### タスク

Codex には、確認質問とプロトコル草案だけを求めます。編集、install、commit、push、公開、
外部サービスへの連絡はさせません。質問、仮定、許可行動、求めた証拠を比べます。Codex の
実行がなければ、記録を静的プロトコルレビューと書き、実行証拠とは呼びません。

## 意図的な失敗バリエーション

「プロらしく見せて」「見つけた問題を直して」とだけ言い、対象ファイル、受け入れ、権限、
停止条件を抜きます。合格する返答は、欠けた判断を特定するか、仕事を読み取り専用の提案に
保ちます。対象を作り出す、依存関係を導入する、編集集合を広げる、証拠なしに完了報告をする
なら失敗です。

次に、曖昧な語を観察可能な基準に置き換えます。

- 「英語 README に、登録済み六言語の見える言語切替がある」。
- 「ローカルリンクチェックが壊れたリポジトリ内リンク 0 件を報告する」。

これらにも、実際の validator とレビュー範囲が必要です。チェック済みの証拠ではなく、
テスト可能な言葉の例です。

### 振り返り

どの欠けた欄が範囲、リスク、受け入れを最も変えたかを記録します。別の人が推測せずに
実行できるか、実行時の証拠がまだ必要な主張を一つ書きます。

## 受け入れチェックリスト

- [ ] 目的が結果、対象、範囲を名前で示す。
- [ ] コンテキストが規則、事実、報告、仮説、例データを分ける。
- [ ] 入力が正確なファイル、出典、バージョン、既知の欠落を示す。
- [ ] 制約が禁止ファイル、秘密、依存関係、外部副作用を含む。
- [ ] 許可行動が読む、草案、編集、実行、commit、push、公開を分ける。
- [ ] 必須の各主張に対応する証拠がある。
- [ ] 停止条件が権限不足、範囲変更、繰り返す失敗、無出力、根拠のない主張を扱う。
- [ ] 復旧が最初のエラーを残し、再試行前に状態を確認する。
- [ ] 引き渡しが行ったこと、しなかったこと、証拠、未知、次の最小確認を挙げる。
- [ ] 二人目または別 Agent が推測せずにプロトコルを実行できる。

## 転移練習

次の領域で依頼を一つずつ書き直します。公開 API を変えない再現可能な回帰修正、一次出典と
不一致表を伴う調査、同じ言語のリンクを保つ README 更新、バックアップ・ロールバック・
実行後チェックを伴う公開、ファイルを分けた二人の読み取り専用監査と調整役の証拠表です。
再利用できる欄と領域固有の証拠に置き換える欄を印にします。仲間にどこで止まるかを伝え
られないプロトコルは、読みやすくても未完成です。
