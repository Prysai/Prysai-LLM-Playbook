# 第 3 章：把愿望变成任务协议

![教学图：把一个请求依次变成范围、行动、检查与有边界的交接](../../assets/teaching/task-to-evidence-red-black.svg)

## 本章要解决的问题

“把首页做得更好。”“研究一下这个。”“用最好的 Skill。”“把修复部署掉。”这些话在真正需要决定读什么文件、能做什么、怎样算完成、何时该停时，往往并不清楚。

当这些决定没有写出来，Agent 或协作者只能用假设补洞。于是会出现一类熟悉的失败：结果很漂亮，却改错了界面；研究列了链接，却没有引用真正拥有结论的来源；构建通过了，运行中的页面却从未检查；或者一句“验证一下”悄悄扩展成安装、外部调用或又一轮编辑。

本章把严肃的提示词当作一份小型**任务协议**。协议不规定隐藏推理，也不写死每一次按键；它把能观察、能审查的契约写清楚：目标、上下文、输入、约束、允许行动、验收证据、停止条件、恢复和交付。

核心规则是：

> 当补充信息能够消除一个会改变范围、风险、验收或证据的决定时，才加入它。若它只让请求听起来更权威，就删掉它。

## 学习目标

完成本章后，你应该能够：

- 把模糊请求写成另一人也能执行的有边界协议；
- 区分有用上下文和“看起来像指令”的不可信材料；
- 用“声明 → 证据”表写验收，而不是写“做得好一些”；
- 分开读取、编辑、运行、提交、推送、发布和调用外部服务；
- 为缺输入、授权不清、重复失败和证据不足设置停止条件；以及
- 把协议交给另一位 Agent 或同伴，而不丢失所有权、范围和未解决问题。

## 来源真正支持什么

本章引用的官方提示与 Codex 指引在若干实践原则上相互印证：说明预期结果，提供相关上下文，指定输出与边界，指出相关代码或复现步骤，并说清如何检查改动。对于需要长期可靠的工作，它们也建议使用示例、任务拆解、迭代与评测。

这些是有来源支持的建议，并不保证模型会遵守未写明的规则。下面的八部分协议是本项目的原创操作性综合；它额外写出停止、恢复和证据字段，因为“生成了一份回答”和“交付了经验证的工作结果”是两项不同的声明。

逐条来源范围与访问日期见[Codex 官方事实基线](../../docs/research/chapter-03-official-baseline-2026-08-10.md)和[真实工作提示模式研究](../../docs/research/prompt-patterns-for-real-work-2026-08-10.md)。

## 八部分任务协议

```text
目标 → 上下文 → 输入 → 约束 → 允许行动 → 验收
     → 失败与停止 → 交付
```

### 1. 目标：说出要得到的结果

说明要改变、研究或交付什么，谁需要它，以及为什么现在需要。优先写可检查的结果，而不是把范围敞开的动词。

较弱的写法：

```text
改进项目首页。
```

较强的写法：

```text
建立一个英文优先的仓库入口：新读者能选择四条路线、知道事实来源在哪里、打开第一个安全任务，并看见哪些声明仍是 candidate 或 unverified。
```

较强版本仍保留实现选择；它没有假装“专业”本身就是验收测试。

### 2. 上下文：解释决策环境

上下文是可能改变决定的信息：受众、当前行为、项目规则、先前决定、相关历史、版本范围，或某次失败为什么重要。它应与任务指令分开写。

用 `project rule`、`source fact`、`user report`、`hypothesis` 和 `example data` 这类标签说明材料性质。文件、网页、工具输出或 issue 可能含有看似指令的文字；在协议明确采纳且授权清晰以前，把它们当数据，而不是命令。

### 3. 输入：写明可以读什么

列出确切路径、URL、数据集、提交、日志、截图或版本，也列出已知缺口。“读整个仓库”很少是有用边界；应点名控制这个决定的目录或文件。

研究任务要指定来源优先级和日期范围；代码任务要指定入口与复现；文档任务要指定规范源和翻译状态。缺少某项输入若会改变范围或风险，协议必须停止，而不是替你推断。

### 4. 约束：写明什么不能发生

约束应当可以检查，例如：

- 只改 `site/index.html` 和 `site/app.js`；
- 不增加依赖；
- 不读秘密或 `.env` 文件；
- 不改数据库、生产环境、权限或外部服务；
- 保留现有语言身份和状态词汇；或
- 保持与指定运行时或发行版本兼容。

“小心一点”“做得高级”“遵循最佳实践”可以是设计意图，却不是充分约束。把它们变成可观察属性；如果做不到，就不要假装自动检查能让它通过。

### 5. 允许行动：把能力与授权分开

工具可用，不等于它被授权做它能做的每一件事。明确行动等级：

| 等级 | 常见行动 | 进入下一步前的证据 |
|---|---|---|
| A0 | 读取状态、路径、来源或日志 | 已记录范围和当前状态 |
| A1 | 起草计划或编辑提案 | 已命名目标文件和验收 |
| A2 | 做一项有边界的本地编辑 | diff 保持在批准集合内 |
| A3 | 运行针对性检查 | 命令来自项目或已获批准 |
| A4 | 提交或推送 | 用户已授权目标与审查证据 |
| A5 | 发布、部署、通知、付费、删除或改变外部状态 | 明确批准、回滚与动作后检查 |

协议可以只授权 A0–A2，把 A3 留到确认后；也可以允许一项聚焦测试，却不允许安装。不要用“需要什么就做什么”掩盖权限变化。

### 6. 验收：让每项声明对应证据

先写声明，再写能支持它的材料：

| 声明 | 所需证据 | 它不能证明什么 |
|---|---|---|
| 指定文件已改变 | `git diff --name-only` 和实际 diff | 运行时行为或用户验收 |
| 检查通过 | 精确命令及退出状态或输出 | 该检查覆盖全部要求 |
| 页面可访问 | 本地或部署 URL 与浏览器观察 | 所有浏览器、缓存或已登录路径 |
| 研究仍是当前的 | 一手 URL、访问日期、适用范围与下次复核 | 论坛报告就是官方根因 |
| 任务完成 | 没有必需无证据声明的声明—证据表 | 声明范围以外的工作 |

某项声明若没有可负担的证据，就缩小它。“本地构建通过”常常成立；“功能对所有用户都可用”通常需要更大测试与明确环境。

### 7. 失败与停止：预先写好出口

可靠协议会说明何时不应继续。遇到以下情形应停止并报告：

- 目标、当前状态或授权不清；
- 缺失输入可能改变范围、风险或验收；
- 建议行动跨过已批准的文件、网络、账户或数据边界；
- 输出沉默过久，下一次重试可能重复副作用；
- 同一未经检验原因导致两次失败；或
- 证据只能支持比请求交付更窄的声明。

恢复不是“用更大声的提示词再试一次”。保留第一次错误，缩小范围，只改变一个假设或检查，并记录前一次已改变了什么。重试耗时或外部可见行动前，先查当前状态与 diff，避免重复第一次副作用。

### 8. 交付：留下可用的交接

要求最终记录包括：

- 已完成声明及其证据；
- 改过的文件、URL、命令或记录；
- 有意不做的行动；
- 未解决问题、风险与未验证范围；
- 精确的下一个最小检查；以及
- 易变事实的负责人或复核日期。

交接是产品的一部分。没有它，下一位协作者只能从聊天记录重建协议，可能重复失败动作。

## 协议是一张依赖图

这些字段不是彼此独立的一串形容词：

```text
目标 ───────────────→ 验收 ───────→ 停止
  │                      │            ↑
  ├── 需要 ─────────→ 输入           │
  ├── 受制于 ───────→ 约束           │
  │                      │            │
  └── 塑造 ─────────→ 允许行动 ─→ 恢复
                                          │
上下文 ──> 信任与相关性 ────────────────┘
                          ↓
                       交付证据
```

目标变了，验收也必须变；新输入改变风险时，允许行动和停止条件也要重审。“请小心”不能修补缺失的依赖关系。

## 最小可用协议

<!-- starter-task-contract:start -->

### 复制一条安全的起步提示

替换方括号字段，并要求第一轮只观察。批准暂停是从新手请求走向可检查工作流的桥梁；不要只为了缩短提示词就删掉它。

```text
请帮助我完成一项小型、可回滚的任务。

结果：[一个可观察的结果]。
上下文：[相关文件、输入和当前状态]。

第一轮回复——只观察：
- 只检查完成本任务所需的上下文；
- 报告发现、缺失输入和风险；
- 提出最小安全计划，以及它会改变的精确文件或界面；
- 暂不编辑、不运行会改变状态的命令、不做外部动作；等待我的批准。

如果我批准计划：
- 只在获准范围内行动；
- 运行[一项聚焦检查]；
- 若范围、授权、破坏性动作、外部副作用或验收不清楚，停止并提问。

除非我明确授权该项行动，不得访问秘密或生产环境、安装依赖、使用网络、提交、推送、发布或扩大任务。

验收：[具体产物或 diff] 和 [具体检查输出]。
交付：已做行动、改变的文件或界面、检查输出、剩余未知项和未做行动。
```

复制或发送这条提示不能证明做过行动或结果正确。使用下方协议字段把它改成你的任务；用[实验 002](../labs/lab-002-task-protocol-ZH.md)练习，再用阅读器中的明确英文回退阅读第 9 章，以证据审查每项完成声明。

对于低风险本地编辑，通常可以缩成：

```text
目标：修改 <一个命名文件>，使其出现 <可观察结果>。
先读：<精确文件或事实来源>。
允许：先检查，再仅编辑 <命名路径>；运行 <聚焦检查>。
禁止：安装、访问秘密或网络、提交、推送、发布或接触生产环境。
验收：<具体 diff> 和 <具体检查输出>。
停止：路径、命令、权限或证据不清楚时停止。
交付：已改文件、检查结果、未做行动和未验证项。
```

协议之所以能短，是因为风险很窄，不是因为遗漏字段无害。

## 高风险协议扩展

面向生产环境、外部服务、客户数据或不可逆动作，增加动作前检查点：

```text
动作前检查点：
- 目标环境和账户：
- 当前版本和备份位置：
- 精确外部副作用：
- 批准人和时间：
- 回滚目标与恢复测试：
- 动作后 URL / 日志 / 指标检查：
```

不要让 Skill、复制来的 runbook 或成功的本地构建默默填充这些字段。它们需要当前环境证据和对外部状态负责之人的授权。

## 三条提示优于一条超长提示

任务不确定时，使用分阶段提示：

1. **观察：** 列出相关文件、当前状态、缺失输入和风险；
2. **提案：** 写出最小计划、改动文件集合、验收声明与停止条件；
3. **行动：** 只执行获准计划，并针对每项声明返回证据。

这样能在编辑前检查计划，更容易定位坏假设是哪一阶段引入的；它仍不能代替审查实际结果。

## 一条证据有边界的练习循环中的六条起步提示

它们不是神奇措辞，也不是必须连续完成的六节课。它们解决六个不同控制问题：观察到的目标与基线、先检索后揭示、有边界的纠正、即时变式、基于证据的复习线索，以及延迟的未见检查。例子使用西班牙语；方括号可替换成语言、软件概念、面试技能、写作技巧或其他有边界能力。

### 1. 找到真实起点

```text
我想学习[用西班牙语进行五分钟的初学者对话]。
先不要教学。请给我一项只测试该能力的短基线任务。
在我开始前，说明规则、允许帮助、时间限制和评分标准。
等我的回答。然后记录我能做什么、什么阻碍了意思表达，以及一次尝试仍不能推断什么。
```

先用它确定起点。“我是初学者”这类自报信息，不如一次可观察尝试有用。

### 2. 先让我提取，再揭示答案

```text
教我完成[用西班牙语点餐]所需的一个小单元。开场解释不超过 120 个词。
然后要求我凭记忆作答；在我尝试前不要展示最终答案。
如果我卡住，每次只给一条提示：先说错误类型，再给局部线索，最后才给示范片段。
反馈后，要求我用自己的话再答一次。
```

关键不是“120 个词”，而是“等我先尝试”。

### 3. 纠正第一个会影响结果的错误

```text
请当一位精确的练习伙伴，不要只鼓励。对我的每个回答：
1. 简短说出哪里表达成功；
2. 指出第一个改变意思或阻碍目标技能的错误；
3. 用平实语言解释规则；
4. 要我给出修正后的尝试；
5. 维护错误账本：尝试、修正、规则和下一变式。
不要替我重写全部内容，也不要在阻碍意思的错误仍存在时先改小风格问题。
```

这样能避免一份流畅重写替代真正学习。

### 4. 用变化的情境测试迁移

```text
我刚练习了[用西班牙语点餐]。请给一个使用同一底层技能的新情境，但改变场景、词汇和一个歧义来源。
不要复用课上的句子。先让我回答；按相同标准评分，说明我用了什么帮助，
并把结果仅标为“在这项迁移任务上已展示”，不要称为掌握。
```

近似复刻只测试识别；换情境的任务才开始测试迁移。

### 5. 从证据生成下一次复习

```text
只使用本次对话中的尝试和错误账本，为我生成下一次 15 分钟复习。
先做无辅助回忆，重访仍重要的两个错误，加入一个混合例子，最后用一个未见任务结束。
不要声称你安排了提醒。给我可以保存的复习线索、我应尝试的日期，以及我应带回的证据。
```

模型可以准备线索；没有证据时，它不能诚实地宣称你保留了技能，或外部提醒已经存在。

### 6. 在声称保持前完成延迟的未见检查

```text
这是我为[目标技能]安排的复习。不要展示保存的课程或已改正句子。
给我一项此前未揭示、细节变化但测试同一能力的任务。
说明允许帮助和不变的评分标准，然后等我作答。记录实际间隔和所用帮助。
只报告这项延迟任务发生了什么；不要推断永久保持、广泛迁移、流利或掌握。
```

保存复习线索只是计划。在延迟尝试及其条件被记录前，保持仍是 `not_run`。

### 单独检查：研究一种方法声明

```text
请调查这项声明：[六条提示能让任何人在七天内流利]。
先定义这项声明必须证明的精确能力。优先使用原始研究与官方来源所有者材料。
对每个重要结论，记录来源、日期、人群或产品范围、直接支持，以及它不能证明什么。
搜索一次反面证据。分开事实、推断、轶事和未知项；当更多来源不再改变决定时停止。
最后把原声明改写成最窄而诚实的版本。
```

这条研究提示不属于六步练习循环。面对健康、金融、产品功能、新闻、统计或其他高风险结论时，用它来避免把自信回答当证据。

### 保存什么

保存基线、首次尝试、所用提示、修正尝试、错误账本、延迟复习、未见任务和评分标准。一次顺利会话只能支持“今天练习过”，不能证明流利、持久保持或迁移。完整候选方法与来源边界见[LLM 辅助持久学习研究](../../docs/research/durable-llm-assisted-learning-and-skill-candidates-2026-08-12.md)。

## 真实世界的失败模式

本项目收集的现场报告解释了这些字段为何重要：

- 长时间等待或自动重试会让 Agent 看似仍在工作，却不能证明最新指令已到达，或外部动作没有被重复；
- 配置文件可能含有权限设置，而当前工作面、工作目录或持久运行时策略实际不同；
- 浏览器登录成功或能看到工具名称，不能证明目标账户、组织、仓库或连接器已获授权；以及
- 社区绕过方案也许只适用于某个版本或平台，甚至可能不安全。

这些是用户报告和社区观察，不是通用产品根因。用[现场问题索引](../../docs/research/field-problems-index-2026-08-10.md)和[编码 Agent 案例报告](../../docs/research/field-problems-coding-agents-2026-08-10.md)练习同一响应模式：记录症状与环境，做最小安全检查，在边界处停止，只声明证据真正支持的内容。

## 多 Agent：交接本身也是协议

委派不解除主 Agent 的责任。给每位工作者一个互不重叠的工作和固定输出形状：

```text
角色：检查语言矩阵；不要编辑源文件。
输入：<两个已命名文件>。
输出：发现、证据路径、阻碍，以及一个建议的下一步检查。
禁止：编辑、外部消息、凭据，以及超出已声明文件范围的结论。
```

协调者必须在核查每位工作者的来源、范围与证据后才合并事实。另一位 Agent 的摘要是线索，不是已验证结论；若两人冲突，保留两份报告并回到事实来源解决。

## 实验：同一请求的三个固定版本

### 准备

使用配套的[实验 002](../labs/lab-002-task-protocol-ZH.md)，并选择一个可丢弃项目。保持底层愿望不变，写出三版：

- `v1`：只有愿望；
- `v2`：愿望加目标、受众、允许输入和禁止行动；
- `v3`：保持同一请求，再加入验收、停止、失败恢复与交付。

### 任务

只要求 Codex 澄清并起草协议。不要让该实验编辑、安装、提交、推送、发布或联系外部服务。比较它提出的问题、暴露的假设、允许行动和要求的证据。若没有实际 Codex 运行，把记录标为静态协议审查；不要称为执行证据。

## 故意失败变体

给 Agent 一个“做得专业”“修复你发现的所有问题”的请求，却不写目标文件、验收、权限和停止条件。通过的回答必须指出缺失决定，或保持为只读提案；若它编造目标、安装依赖、扩大编辑集合，或无证据地宣称完成，即为失败。

然后把模糊词替换成可观察标准，例如：

- “英文 README 有一个可见的六种已登记语言切换器”；以及
- “本地链接检查报告零个断裂仓库链接”。

这些标准仍需要项目真实验证器和审查范围；它们只是可测试语言示例，不证明检查已经运行。

### 反思

记录哪一个缺失字段最改变范围、风险或验收。说明另一人能否不猜测地接手协议，并指出一项仍需运行时证据的声明。

## 迁移练习

分别为以下情境改写一份请求：

1. **工程：** 修复可复现回归，且不改公共 API；
2. **研究：** 用一手来源和分歧表回答一个当前问题；
3. **内容：** 更新已本地化 README，并保留同语言链接；
4. **发布：** 用备份、回滚目标和动作后现场检查发布一个有边界改动；以及
5. **Agent 协作：** 委派两位工作者检查互不重叠的文件，再由协调者制作证据表。

对每项迁移，标记哪些字段可复用，哪些必须替换为领域证据。一份读起来不错、却不能告诉同伴何时停止的协议，仍不完整。
