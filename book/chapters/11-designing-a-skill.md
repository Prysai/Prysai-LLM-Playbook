# 第十一章：设计一个真正有用的 Skill

## 本章要解决的问题

Skill 的价值不在于长度、术语或目录数量，而在于它能否在一类真实任务中减少遗漏、提高一致性、保护边界并留下更好的证据。

## 1. 先写触发边界

一个好的 description 要说明做什么、什么时候使用、什么时候不使用。过于宽泛的 skill 会到处触发，过于狭窄的 skill 会让用户无法发现。触发边界是产品设计，不是最后补的元数据。

## 2. 只放 Codex 不知道的东西

Codex 已经知道通用写作、编程和分析能力。Skill 应该补充不显然的领域知识、项目规则、脆弱流程、工具映射、输出契约和失败处理。把通用常识堆成长文只会消耗上下文。

## 3. 渐进披露

用三层组织：

```text
元数据：什么时候触发
SKILL.md：核心流程和选择规则
references/scripts/assets：仅在需要时加载或执行
```

不要在入口文件重复所有细节；不要把无关领域的参考材料都放进一次任务的上下文。

## 4. 写出完整流程

至少包含：输入检查、步骤顺序、决策点、外部内容信任边界、权限与秘密处理、失败和停止条件、输出格式和验证方式。理想路径之外的内容决定了 skill 是否真的可靠。

## 5. 以任务集评测

每个新 skill 至少需要：

- 一个正例：它应该触发并完成；
- 一个边界例：它应该拒绝或缩小范围；
- 一个失败例：输入缺失、错误、恶意或外部依赖不可用；
- 一个迁移例：换表达、领域或文件后仍能使用方法。

## 实验：把一次成功沉淀为 Skill

从实验 001 或实验 002 中选择一个反复出现的流程。先写成一次性任务协议，再判断哪些步骤在多次任务中稳定复用，最后创建一个最小 skill。比较：

- skill 是否减少了每次重复说明；
- 是否增加了不必要的上下文；
- 是否更早发现了输入缺失；
- 是否更容易验证结果；
- 不使用 skill 的简单任务是否会被误触发。

## 本章验收

学习者能创建一个符合 frontmatter、触发边界、核心流程、失败处理和输出证据要求的 skill；能解释哪些内容应该进入 reference 或 script；能用正例、边界例、失败例和迁移例证明它的价值。
