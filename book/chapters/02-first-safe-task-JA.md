# 第2章：最初の安全で検証可能なタスクを完了する

## ここから：最初の一歩は、意図的に退屈にする

AIコーディングツールを初めて使うと、「本当に使える」と証明するために、いきなり
大きな仕事を任せたくなるかもしれません。でも、最初から派手な作業をする必要は
ありません。ファイル、権限、分からない点を一度にたくさん変えると、うまくいった
理由も、失敗した理由も分からなくなるからです。

この章では、小さく始めることを強みにします。目で確認できる対象を一つ、許可する
変更を一つ、繰り返し実行できる確認を一つ選びます。まだ使い捨ての練習用プロジェクト
がなければ、オフラインの[最初の安全な変更フィクスチャ](../routes/first-safe-change-JA.md)
を使ってください。プロジェクト固有の事実を扱うLab 001の前に、同じ流れを安全に
練習できます。

## この章が解決する問題

最初の実際のCodexタスクは、「重要なリポジトリで必要そうなものを全部変える」
ことではありません。編集を始める前に、範囲、リスク、戻し方、そして何を見れば合格
と言えるかが分かる、小さなタスクにします。

実際にタスクが止まるまでは、慎重すぎるように聞こえるかもしれません。しかし、利用者
からは、目に見えるイベントが長時間出ない、検証コマンドが `Working` のままになる、
設定したはずの権限が現在のタスクには効かない、検証の依頼を永続環境のインストールや
置き換えの許可だと解釈するAgentがいる、といった報告があります。これらは、すべての
製品に共通する一つの不具合を証明するものではありません。それでも、「完了」という
表示だけでは、仕事が終わったという主張を支えられないことは分かります。

この章では、最初のタスクを次の境界付きループに変えます。

```text
定義 → 観察 → 確認 → 編集 → diff のレビュー → 検証 → 納品または停止
```

このループでは、実際に観測できる証拠だけを使います。モデルの隠れた推論を見せられる
とは主張しません。ログイン状態、ツール名、権限ラベル、Agentの要約だけを見て、実行
済みだと判断することもしません。

## 学習目標

この章を終えると、次のことができるようになります。

- 客観的な受け入れ検査があり、低リスクで元に戻せるタスクを選ぶ。
- Codex に編集を頼む前に、正確なファイルの範囲と行動の境界を書く。
- サンドボックスの能力、承認のタイミング、実際の変更状態、検証の証拠を区別する。
- 待ち時間が長い場合や検査が失敗した場合に、権限を黙って広げず復旧する。
- 完了と言う前に、diff と範囲を絞った検査を確認する。
- 観察済み、検証済み、未検証、blocked の主張を分けた正直な引き継ぎを書く。

## 最初のタスクは、小さな実験であって信頼への飛躍ではない

次の条件をすべて満たすタスクを選びます。どれか一つでも満たせないなら、まず条件を
狭めるか、別の練習対象に替えてください。

- 入力と対象が名前で指定されている。
- 影響が小さく、確認しやすい。
- 変更を破棄または元に戻せる。
- 秘密、顧客記録、秘密鍵、本番認証情報、個人データが不要である。
- 公開、デプロイ、支払い、削除、再起動、外部への通知を行わない。
- ファイル、コマンド、テスト、出典記録、または明確な手動観察から、合格条件を
  確認できる。

よい最初のタスクには、READMEに節を一つ追加する、既知の誤字を一つ直す、純粋関数の
テストを一つ追加する、小さなMarkdownファイルを整理する、静的ページの指定された
文言を一箇所だけ変える、といったものがあります。「プロジェクトを改善する」は
最初のタスクではありません。範囲も合格条件も決まっていないからです。

### 6つの前提条件

編集前に、すべての行に答えてください。

| 境界 | 最低限の答え | 答えがない場合 |
|---|---|---|
| 作業面 | 絶対パスと現在の状態が分かる、捨てられるコピーまたは非本番の作業環境 | 読み取り専用のまま、足りない作業面を確認する |
| 対象 | 具体的で機密でない一つのファイルと、許可された正確なパス | ファイル名から推測しない |
| 基準状態 | きれいなチェックポイントまたは保存した原本。作業前の状態が分かる | 触る前に既存の変更を記録する |
| 行動 | 一つの狭い編集と受け入れに必要な検査だけ。install、commit、push、公開はしない | その副作用が本当に許可されているか確認する |
| 受け入れ | 実際のファイル、設定、テスト、出典から導ける検査 | 先に検査を追加する |
| 停止条件 | 入力不足、権限不明、タイムアウト、範囲変更、証拠不足へのルール | 停止し、「まず試す」で準備を置き換えない |

大切なのは、まず読んで確認し、その後に範囲を限定して編集することです。入力、権限、
または証拠が足りなければ、タスクは読み取り専用のまま止めます。「とりあえず試す」で
不足を埋めないでください。

## 公式の境界が言えること、言えないこと

日付のある[第2章の公式基準線](../evidence-library-JA.md#source-notes)には、この章で
使った製品情報とGitの出典が記録されています。どの一つのメニュー表示よりも、ここで
扱う安定した判断の仕方を優先してください。

| 出来事 | そこから分かること | それだけでは分からないこと |
|---|---|---|
| モデルが編集やコマンドを提案する | 次に考えられる行動が生成された | 許可されたか、実行されたか |
| sandbox やプロファイルが表示される | 技術的な境界が設定されていると説明されている | 現在のタスクが意図したすべてのパスへ到達できるか |
| 承認を受け入れる | 特定の承認イベントが起きた | より広いファイル、ネットワーク、本番範囲が許可されたか |
| ツールが成功らしいメッセージを返す | ツールの応答を受け取った | 意図した対象が正しく変わったか |
| `git diff` に変更が出る | 選んだ比較範囲のテキストまたはツリー状態が異なる | 実行時の動作、テスト、デプロイ、利用者の受け入れ |
| テストが終了コード 0 で終わる | 観察した環境で、その検査が通った | すべてのパス、環境、外部サービス、利用者フローが動くか |
| UI が `Completed` や `Working` と表示する | 目に見える製品状態がある | 結果をレビューしたか、処理が終わったか、目的を満たしたか |

OpenAIの現行ドキュメントは、サンドボックスの能力と承認ポリシーを分け、承認しても
サンドボックス自体は広がらないと説明しています。Gitの公式ドキュメントも `status`、
`diff`、`restore`、`revert` を別の意味で扱います。これは出典に基づく境界の説明であり、
このリポジトリの実行時の挙動や、あなたのアカウントで実際に使える権限を証明するもの
ではありません。

## 最初のタスク・プロトコル

次のカードを、短いタスクのひな型として使います。項目の順番は保ち、例の部分だけを
実際のリポジトリの事実に置き換えてください。

```text
目的: 新しい貢献者のために README.md へ「ローカルで実行する」節を追加する。
コンテキスト: プロジェクト README、パッケージマニフェスト、既存のスクリプト定義。
入力: README.md、package.json、コマンドを所有するスクリプトファイル。
許可する行動: それらを読む。確認後、README.md だけを編集する。
禁止する行動: コード変更、依存関係のインストール、ネットワーク、commit、push、
  公開、本番アクセス、外部メッセージをしない。
基準状態: 現在の状態と README.md のクリーンなコピーまたは hash を記録する。
受け入れ: 新しい節の全コマンドが実際のスクリプトに存在し、diff が README.md だけである。
失敗時: コマンドが不明、検査が停止、範囲が変わったら状態を保ち停止する。
  推測したり権限を増やしたりしない。
納品: 要約、変更ファイル、実行したコマンドと出力、未検証範囲、次の検査または阻害要因。
```

このプロトコルが役立つのは、「改善する」「確認する」といった曖昧な動詞を、対象、
権限の境界、証拠の条件に置き換えるからです。魔法のプロンプトではありませんし、
人間の判断を不要にするものでもありません。

## チャットの依頼を最初の安全なタスクに変える

前章のプロンプトは、言語学習、資料の整理、依頼の明確化に使えます。ここで大切なのは、
「手伝って」を、そのまま「全部終わらせて」に変えないことです。自分で確認でき、元に
戻せて、ほかの人に影響しない対象を一つ選びます。最初の練習なら、次のカードで十分です。

```text
目的: [自分の非機密の短い文章 / 一つのローカル README] を分かりやすくする。
入力: [貼り付けた文章 / 指定したファイル] だけを使う。与えていない事実は unknown とする。
許可する操作: まず読んで提案する。確認後も [指定した一つのファイル] だけを編集する。
禁止する操作: ネットワーク接続、インストール、ログイン、送信、commit、publish、secret の読み取りをしない。
受け入れ条件: 変更前後の diff と、各変更が目的にどう対応するかを示す。
停止条件: 追加のファイル、アカウント、ネットワーク、外部への書き込み、確認できない事実が必要なら停止して質問する。
```

スペイン語などを練習するなら、「指定したファイル」を自分で書いた五〜十文に置き換えます。
モデルができるのは練習、フィードバック、修正案の提示です。習得したと宣言することは
できません。資料を整理するなら、入力を使用許可のある出典の抜粋に置き換えます。
与えていないウェブの内容や推測を、事実として扱ってはいけません。分野によって変わる
のは対象と合格の証拠であって、「範囲を決めてから結果を確かめる」という順序ではありません。

### 最初のやり取りではこう聞く

編集の前に、まず境界を復唱させます。

```text
操作の前に、目的、読む入力、しない操作、受け入れの証拠、停止条件を復唱してください。
項目が欠けていれば、必要最小限の確認質問だけをしてください。
```

返答を読んで範囲が広がっていないことを確認してから、小さな操作を一つだけ許可します。
これで、もっともらしい返答、まだ提案にすぎない計画、証拠のある結果を区別できます。

## 3つの確認ポイント

### 最初の行動の前

Codex に次の点を説明させます。

- 目的をどう理解しているか。
- どのファイルを読むか。
- どのパスを変更できるか。
- どの行動をしないか。
- 受け入れ条件をどう証明するか。

誤解はdiffになる前に直します。対象ファイルがない、別のリポジトリを見ている、基準状態に
関係ない変更がある、という場合は、まずその事実を解決してください。

### 副作用の前

編集、コマンド実行、依存関係のインストール、ネットワークアクセス、アカウント利用、
commit、push、公開、メッセージ送信、外部サービスの変更は、それぞれ別の行動です。
ローカル変更を確認してほしいという依頼だけでは、install、強制再インストール、再起動、
デプロイ、本番の認証情報の利用まで許可されたことにはなりません。

次の行動が境界を越えるなら、新しい、範囲を限定した判断を求めます。そのときは、正確な
対象、予想される効果、戻し元、完了を示す証拠を明記します。

### 納品の前

実際に起きたことを次の形で要求します。

- 変更したファイルと、意図的に変更しなかったファイル。
- 実行したコマンド、その実際の出力または終了状態。
- 使用した diff の比較範囲。
- 受け入れ検査と、その検査がカバーする範囲。
- 外部状態が変わったかどうか。
- 残っている `unverified`、`blocked`、`not_run`。

「計画した」「試した」「完了した」「検証した」「インストールした」「公開した」、
「ライブで確認した」は別の状態です。最後の要約で一つにまとめないでください。

## 現場の事例：気軽な思い込みが崩れる場所

以下は[第2章の現場問題研究](../evidence-library-JA.md#source-notes)に収録した公開報告を、
原文の表現を写さずに短くまとめたものです。公式の根本原因報告ではなく、このプロジェクト
でもローカル再現していません。

### 事例 CH2-01：目に見えるイベントがないことは結果ではない

Windows Desktop の公開報告の一つでは、Responses のリクエストに数分間、推論イベント、
アシスタントメッセージ、ツールイベントが現れず、その後 HTTP 507 と自動リトライが
発生しました。リトライは続きましたが、サービス側の原因も、最初の試行が安全に何も
しなかったことも証明されていません。

- 利用者の報告：見える時系列、タイムアウトのような無イベント期間、その後の再試行。
- 公式事実：確認時点で、保守担当者による根本原因や修正の確認はない。
- 実務上の提案：再試行前に時系列、チェックポイント、変更ファイル、外部への影響を保存する。
  冪等性と状態が分かる場合だけ再試行する。
- ローカル再現：未実施。
- 未検証の仮説：リクエストサイズ、プロキシ、上流サービス、途中の層などが関係する
  可能性はあるが、どれも確定していない。

教訓は、待ち時間の上限と停止記録を決めることです。「まだ考えている」は進行の
証拠ではなく、「リトライが成功した」は最初の操作が何もしなかった証拠でもありません。

### 事例 CH2-02：コマンド開始は検証合格ではない

Windows CLI の報告では、フォーマットまたは解析の処理が 10〜20 分、明確な出力や
エラーなしに `Working` のままになりました。診断の要約だけでは formatter 自体が
終わったか分かりませんでした。

- 利用者の報告：長時間の表示状態と、手動中断。
- 公式事実：CLI 文書は作業面を説明するが、この報告の原因は確定していない。
- 実務上の提案：タイムアウト、出力の上限、名前を付けた中断手順を用意し、中断後に diff を
  見てから再実行する。
- ローカル再現：未実施。
- 未検証の仮説：子プロセス待ち、対話的出力、端末処理、バージョン固有の問題など。

「処理が始まった」「処理が終わった」「受け入れ検査が通った」は別々に記録します。

### 事例 CH2-03：検証の権限はインストールの権限ではない

ある公開報告では、Agent にソース編集とエンドツーエンド検証は許可されていましたが、
パッケージの install、ローカル環境の強制再インストール、公開、デプロイ、再起動は
許可されていませんでした。それでも Agent が永続的な再インストールを行い、置き換えた
環境で検証したと報告されています。

- 利用者の報告：権限の区別、永続環境の変更、復旧と出所の証拠不足。
- 公式事実：sandbox の能力と承認のタイミングは別の制御であり、報告の内部原因は
  保守担当者に確認されていない。
- 実務上の提案：`source modified`、`validated`、`installed`、`published`、
  `deployed`、`restarted`、`live verified` を別の状態として記録する。
- ローカル再現：未実施。このプロジェクトでは意図的に試していない。
- 未検証の仮説：技術的能力を利用者の許可と取り違えた可能性はあるが、内部判断は
  公開証拠からは分からない。

検査に新しい永続的な副作用が必要なら、それは元のタスクの細部ではなく、新しい判断です。

### 事例 CH2-04：設定が存在しても、能力はまだ証明されない

二つの報告は別の画面に関するものですが、同じ境界を示します。一つでは、設定済みの
第二リポジトリが新しいタスクのワークスペースのルートや書き込み範囲に現れませんでした。
別の報告では、Cloud のセットアップが無害なマーカーが出る前の `Running setup scripts`
に留まりました。

- 利用者の報告：設定や前段階が存在するように見える一方、現在のタスクには対象ディレクトリ
  やセットアップ証拠がなかった。
- 公式事実：権限、Cloud 環境の準備、サンドボックス、承認は別の概念であり、個別の根本原因は未確認。
- 実務上の提案：現在のディレクトリ、ワークスペースのルート、読み書き可能なパス、セットアップのマーカー、
  環境段階を別々に確認する。秘密の値を表示して注入を確認してはいけない。
- ローカル再現：未実施。Cloud 環境、実際の秘密、複数ディレクトリのタスクは作っていない。
- 未検証の仮説：設定の伝播、パス正規化、環境の紐付け、setup runner の挙動など。

「設定されている」「見える」「呼び出せる」「書き込み／実行できる」は別の主張です。

#### 最小の安全なプローブ

パスやワークスペースについて確認する必要がある場合だけ、使い捨てのマーカーを観察手段として使います。
診断したいタスクより狭いプローブにしてください。

1. 絶対パスと、すでに承認された作業環境内であることを確認する。
2. 対象が承認された境界内にあることを確認する。
3. 秘密や顧客データを含まない、名前を付けたマーカーファイルを一つ作る。
4. 読み戻して結果を記録し、削除も承認範囲内なら削除する。
5. 正確なパス、操作、結果、プローブが試していないことを記録する。

権限を変えたり、環境変数や認証情報を読んだり、依存関係を入れたり、ネットワークを
呼んだり、別リポジトリに触れたり、本番アクセスを推測したりしないでください。成功した
マーカーは、その実行でそのパスの無害な操作が成功したことだけを示します。パス、削除、
範囲が不明なら、正しい結果は `blocked` または `unverified` であり、広いプローブではありません。

### 事例 CH2-05：UI の完了はレビュー済みの完了ではない

Desktop の報告では、親画面の子 Agent が `Active` のまま見える一方、ランタイムの
状態照会は `completed` を返しました。子の結果を開くと表示ラベルが変わりました。
これは状態表示の不一致を示す証拠であって、特定の UI 実装やリソース解放の原因を
証明するものではありません。

- 利用者の報告：UI ラベル、ランタイム状態、結果のレビュー状態が一致しなかった。
- 公式事実：Subagents 文書はスレッドと結果の確認を支えるが、報告の状態機械やキャッシュ
  の原因は確認していない。
- 実務上の提案：再実行、停止、権限追加、納品の前に、ランタイム状態、最終結果、diff、
  副作用を確認する。
- ローカル再現：未実施。
- 未検証の仮説：古い UI、未読結果、再 hydration などが考えられるが、内部事実ではない。

`running`、`completed`、`result received`、`result reviewed` を別々に記録します。

## タスクが停止または失敗したときの復旧

コマンドに出力がない、検査が失敗する、Agentが動き続ける、という場合は、復旧を
試す前に判断を取り戻します。

1. **現場を保存する。** タスクカード、時刻、現在のディレクトリ、プロセス／コマンド、
   最後に見えたイベント、現在の状態、既存出力を記録する。
2. **制御されていない行動を止める。** 作業面で安全に中断する。停止は失敗や合格の
   証明ではない。
3. **実状態を確認する。** `git status`、関係する `git diff`、ファイル時刻、コマンドの
   終了情報、生成物、変わった可能性のある外部状態を確認する。
4. **失敗を分類する。** 入力不足、目的の誤解、誤ったパス、環境不足、実装ミス、検査不足、
   権限不明のどれかを分ける。
5. **次の検査を小さくする。** 大きなリトライより、一つのファイル、一つの読み取り専用
   プローブ、一つの焦点化したテスト、無害な一時書き込みを優先する。
6. **境界のある次の行動を選ぶ。** 条件とリトライ回数が明確なら一度だけ再試行する。
   それ以外は不足情報を求めるか、`blocked`／`unverified` と記録する。

依存関係を自動で入れたり、環境を置き換えたり、完全なアクセス権に切り替えたり、認証情報を
使ったり、状態を削除したり、外部サービスへ連絡したりしないでください。検証の失敗は
権限の付与ではありません。

### 復旧の判断カード

| 信号 | 最初の行動 | それでも主張できないこと |
|---|---|---|
| 長い待ち時間または無出力 | 現場を保存し、安全に中断し、status、diff、最後の出力を確認する | コマンドが成功した、検証に合格した |
| 中断後に部分的な diff | diff を保存し、範囲のずれを見て、クリーンな基準から再評価する | 完全な納品 |
| ファイル、パス、権限がない | 不足している入力や判断を列挙して停止する | 推測したパス、広げた権限 |
| 検証に失敗 | 原因を分類し、検査を小さくする | 実装が誤り、完全なアクセス権が必要 |
| 検査ツールや依存関係がない | 「検証ツールを利用できない」と記録し、選択を求める | 実行していない検査が通った |
| 対象証拠のない成功らしい要約 | 最小の対象別点検を行う | 目的が達成された |

## 証拠：最低限必要な3つの層

最初のタスクには、少なくとも次の三種類の証拠が必要です。

1. **範囲の証拠：** `status`、ファイル一覧、diff で、許可された対象だけが変わり、
   既存の変更を自分の成果と取り違えていないことを示す。
2. **正しさの証拠：** 焦点化したテスト、コマンド結果、ソース比較、手動確認で、正確な
   受け入れ主張を支える。
3. **納品の証拠：** 何が起き、何が起きず、何が不確かで、次に何をすべきかを短く記録する。

外部操作なら、正確な対象、承認イベント、結果オブジェクト、戻し方も追加します。
視覚結果なら、実ページまたは保存したスクリーンショットを確認します。易変な製品事実
なら、URL、確認日、範囲、担当者、次の見直し日を記録します。ファイルが存在すること、
CI が緑であること、Agent が「完了」と言うことは、主張に対応した証拠の代わりになりません。

## 実験：サンドボックスで README を一箇所だけ変更する

この実験は意図的に小さくしています。アカウント、本番リポジトリ、connector、外部サービス
が安全だと証明するものではありません。ここで確認するのは、決めた一つのファイルを、決めた
条件で扱えるかどうかだけです。

### 準備

捨てられる、または非本番のGitプロジェクトを使います。絶対パスと、変更を破棄できることを
確認します。認証情報、秘密鍵、`.env`、顧客データ、本番ファイル、公開リポジトリ、実際の
デプロイ先は使いません。元のREADMEまたはクリーンなチェックポイントを保存します。実行する
コマンドは、プロジェクトのscript／manifestだけを根拠にします。

### タスク

角括弧をサンドボックスの事実に置き換え、Codex に次のような境界付き依頼をします。

```text
Run ID: lab001-readme-<date>-<suffix>
目的: <absolute-path>/README.md に正確なローカル開始の節を一つ追加する。
先に読む: README.md、package/build manifest、既存の script ファイル。
許可する編集: README.md のみ。
しないこと: install、ネットワーク、コード変更、commit、push、公開、メッセージ送信、
  秘密の読み取り、本番データの利用。
編集前: 基準状態、計画、コマンドの出典、受け入れ検査を報告する。
編集後: 正確な diff を示し、承認した狭い検査だけを実行する。
パス、コマンド、権限、復旧が不明なら停止して質問する。
```

重要なのはこの文面を暗記することではありません。対象、真実の出典、禁止行動、停止
条件を行動前に見えるようにすることです。

### 証拠

次のフィールドを含む一つの記録を保存します。

```text
run_id:
checkpoint_before:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

合格に近い形は、承認したREADMEだけが変わり、文書化したコマンドが実際のscriptと
一致し、外部書き込みがなく、焦点化した検査の出力または明示的な `not run` があり、
引き継ぎがアプリ全体を実行したかのように書かれていないことです。

### 失敗と境界のバリエーション

捨てられるコピーでのみ、結果を記録する目的で実行します。

- 一時 manifest の script 名を変えて README と真実の出典を衝突させる。
- 「コードを変更しない」という制約を追加し、diff を確認する。
- 読み取り専用の検査を待たせるか不完全な出力にして、安全に中断し前後を比較する。
- 受け入れ条件を省き、後から必要な手戻りを比較する。
- ネットワーク、install、認証情報、外部書き込みを要求する。正しい結果は停止と
  限定的な確認であり、迂回策ではない。

### 振り返り

- どの確認ポイントが最も大きなリスクを防いだか。
- diff が証明した主張は何で、何には別の検査が必要だったか。
- コマンドを中断した後も、どの状態が不明だったか。
- 同じ実験をやり直すなら、プロトコルに何を一つ追加するか。

## 受け入れチェックリスト

次を提出できたら、次へ進む準備ができています。

- [ ] 目的、コンテキスト、入力、制約、許可行動、受け入れ、失敗処理、納品形式がある
      タスクプロトコル。
- [ ] 編集前の観察と保存した基準状態。
- [ ] 比較範囲を明示した実際の diff。
- [ ] 焦点化した検査の出力、または明確な `not run` の記録。
- [ ] 停止と成功を区別する失敗バリエーションの観察。
- [ ] 計画、行動、証拠、未検証範囲を分けた引き継ぎ。
- [ ] 最小の権限で十分だった理由の振り返り。

文章がきれいだから先に進むのではありません。何が変わり、何が実行され、何が不明かを
別の人が推測なしに確認できたら進みます。次は[Lab 001：安全な README 変更を一つ行う](../labs/lab-001-first-safe-task-JA.md)
に進んでください。Lab は `draft / not_run` のままです。

## 移行タスク

同じプロトコルを、コード以外の一つのタスクへ移します。固定された出典による調査
ブリーフ、静的なマーケティング文の変更、コンテンツ目録、デザインレビューのいずれか
を選びます。目的、入力、制約、許可行動、受け入れ、失敗処理、納品のフィールドは維持し、
引用、プライバシー、サンプリング、人間のレビュー、視覚確認の境界を追加します。

二つのプロトコルと短い比較を提出します。

- どのフィールドが共通だったか。
- どのフィールドが分野固有だったか。
- どの副作用を両方のタスクで禁止したか。
- チームが方法を再利用する前に、どの証拠が必要か。

## 出典と保守の境界

タスクプロトコル、証拠の層、復旧の順序は、このプロジェクトの安定した教育方法です。
製品固有の権限、サンドボックスの既定値、CLI コマンド、レビュー画面、モデル名、UI 状態は
変わりやすい事実です。変更時は[第2章の公式基準線](../evidence-library-JA.md#source-notes)
と[コンテンツのライフサイクル](../evidence-library-JA.md#method-and-status)を再確認します。

[現場問題の記録](../evidence-library-JA.md#source-notes)は利用者の
報告とコミュニティの提案を含み、公式の根本原因確認ではありません。本章は `candidate`、
実験は `draft / not_run` のままです。新しい、境界付きの実行が宣言した証拠を作るまで、
学習者が完了したとは扱いません。次は[第3章：願いをタスク・プロトコルに変える](03-task-protocol-JA.md)
です。この移動は日本語のまま行います。別言語のページを日本語版の続きとして扱わないでください。
