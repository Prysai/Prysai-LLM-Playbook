# 第2章：最初の安全で検証可能なタスクを完了する

## ここから：最初の一歩は、意図的に退屈にする

ここでは、多くの人が「AI コーディングツールを本当に使える」と証明しなければ
ならないように感じます。しかし、最初から大きな作業をする必要はありません。
ファイル、権限、未知の要素を一度にたくさん変えると、成功や失敗の原因を見分けられ
なくなるからです。

この章では、小ささを長所として扱います。目に見える対象を一つ、許可する変更を
一つ、繰り返せる検査を一つ選びます。まだ捨てられるプロジェクトがなければ、
オフラインの[最初の安全な変更フィクスチャ](../routes/first-safe-change-JA.md)を
使ってください。プロジェクト固有の事実を扱う Lab 001 の前に、このループを安全に
練習できます。

## この章が解決する問題

最初の実際の Codex タスクは、「重要なリポジトリで必要そうなものを全部変える」
ことであってはいけません。編集を始める前に、範囲、リスク、戻し方、受け入れ証拠が
見える小さなタスクにします。

これは実際のタスクが失敗するまで、慎重すぎるように聞こえるかもしれません。
利用者からは、目に見えるイベントが長時間現れない、検証コマンドが `Working` の
ままになる、設定したはずの権限が現在のタスクには適用されない、検証の依頼を
永続環境のインストールや置き換えの許可として扱う Agent がいる、といった報告が
あります。これらは一つの普遍的な製品バグを証明するものではありません。しかし、
完了ラベルだけでは主張全体を支えられないことは示しています。

この章では、最初のタスクを次の境界付きループに変えます。

```text
定義 → 観察 → 確認 → 編集 → diff のレビュー → 検証 → 納品または停止
```

このループでは観測できる証拠を使います。モデルの隠れた推論を見せられるとは
主張せず、ログイン状態、ツール名、権限ラベル、Agent の要約だけで実行済みだと
判断もしません。

## 学習目標

この章を終えると、次のことができるようになります。

- 客観的な受け入れ検査があり、低リスクで元に戻せるタスクを選ぶ。
- Codex に編集を頼む前に、正確なファイルと行動の境界を書く。
- sandbox の能力、承認のタイミング、実際の変更状態、検証証拠を区別する。
- 待ち時間が長い場合や検査が失敗した場合に、権限を黙って広げず復旧する。
- 完了と言う前に、diff と範囲を絞った検査を確認する。
- 観察済み、検証済み、未検証、blocked の主張を分けた正直な引き継ぎを書く。

## 最初のタスクは、小さな実験であって信頼への飛躍ではない

次の条件をすべて満たすタスクを選びます。

- 入力と対象が名前で指定されている。
- 影響が小さく、確認しやすい。
- 変更を破棄または元に戻せる。
- 秘密、顧客記録、秘密鍵、本番認証情報、個人データが不要である。
- 公開、デプロイ、支払い、削除、再起動、外部への通知を行わない。
- ファイル、コマンド、テスト、出典記録、または明確な手動観察から受け入れを
  確認できる。

よい最初のタスクには、README に一つの節を追加する、既知の誤字を直す、純粋関数の
テストを一つ追加する、小さな Markdown ファイルを整理する、静的ページの指定された
文言を一箇所だけ変更する、といったものがあります。「プロジェクトを改善する」は
最初のタスクではありません。安定した境界も受け入れ条件もないからです。

### 6つの前提条件

編集前に、すべての行に答えてください。

| 境界 | 最低限の答え | 答えがない場合 |
|---|---|---|
| 作業面 | 絶対パスと現在の状態が分かる、捨てられるコピーまたは非本番 sandbox | 読み取り専用のまま、足りない作業面を確認する |
| 対象 | 具体的で機密でない一つのファイルと、許可された正確なパス | ファイル名から推測しない |
| 基準状態 | きれいなチェックポイントまたは保存した原本。作業前の状態が分かる | 触る前に既存の変更を記録する |
| 行動 | 一つの狭い編集と受け入れに必要な検査だけ。install、commit、push、公開はしない | その副作用が本当に許可されているか確認する |
| 受け入れ | 実際のファイル、設定、テスト、出典から導ける検査 | 先に検査を追加する |
| 停止条件 | 入力不足、権限不明、timeout、境界変更、証拠不足へのルール | 停止し、「まず試す」で準備を置き換えない |

現在の中国語原稿では、これは読み取り専用の観察から安全な編集へ移る場面として
説明されています。英語の原稿では同じ契約を明示しています。翻訳の実際の状態は
[ロケール・マトリクス](../../docs/governance/locale-matrix.yaml)で確認できます。

## 公式の境界が言えること、言えないこと

日付のある[第2章の公式基準線](../../docs/research/chapter-02-official-baseline-2026-08-10.md)
には、この章で使った製品情報と Git の出典が記録されています。安定した教え方は、
どの一つのメニュー表示より重要です。

| 出来事 | そこから分かること | それだけでは分からないこと |
|---|---|---|
| モデルが編集やコマンドを提案する | 次に考えられる行動が生成された | 許可されたか、実行されたか |
| sandbox やプロファイルが表示される | 技術的な境界が設定されていると説明されている | 現在のタスクが意図した全パスへ到達できるか |
| 承認を受け入れる | 特定の承認イベントが起きた | より広いファイル、ネットワーク、本番範囲が許可されたか |
| ツールが成功らしいメッセージを返す | ツールの応答を受け取った | 意図した対象が正しく変わったか |
| `git diff` に変更が出る | 選んだ比較範囲のテキストまたはツリー状態が異なる | 実行時の動作、テスト、デプロイ、利用者の受け入れ |
| テストが終了コード 0 で終わる | 観察した環境で、その検査が通った | すべてのパス、環境、外部サービス、利用者フローが動くか |
| UI が `Completed` や `Working` と表示する | 目に見える製品状態がある | 結果をレビューしたか、処理が終わったか、目的を満たしたか |

OpenAI の現行ドキュメントは sandbox の能力と承認ポリシーを分け、承認が sandbox
を拡張しないと説明しています。Git の公式ドキュメントも `status`、`diff`、
`restore`、`revert` を別の意味で扱います。これらは出典に基づく境界であり、
このリポジトリの実行時挙動や、あなたのアカウントの実効権限を証明するものでは
ありません。

## 最初のタスク・プロトコル

これを短いタスクカードとして使います。文言は保ち、例だけ実際のリポジトリの事実
に置き換えてください。

```text
目的: 新しい貢献者のために README.md へ「ローカルで実行する」節を追加する。
コンテキスト: プロジェクト README、パッケージマニフェスト、既存のスクリプト定義。
入力: README.md、package.json、コマンドを所有するスクリプトファイル。
許可する行動: それらを読む。確認後、README.md だけを編集する。
禁止する行動: コード変更、依存関係のインストール、ネットワーク、commit、push、
  公開、本番アクセス、外部メッセージをしない。
基準状態: 現在の状態と README.md のクリーンなコピーまたは hash を記録する。
受け入れ: 新しい節の全コマンドが実際のスクリプトに存在し、diff が README.md だけである。
失敗時: コマンドが不明、検査が停止、範囲が変わったら状態を保ち停止する。
  推測したり権限を増やしたりしない。
納品: 要約、変更ファイル、実行したコマンドと出力、未検証範囲、次の検査または阻害要因。
```

このプロトコルが役立つのは、曖昧な動詞を対象、権限境界、証拠要件に変えるからです。
魔法のプロンプトではなく、人間の判断を不要にするものでもありません。

## chat の prompt を最初の安全な task に変える

前章の prompt は言語学習、source の整理、依頼の明確化に使えます。ここで大切なのは「手伝って」をそのまま「全部終えて」にしないことです。見えて、戻せて、ほかの人へ影響しない対象を一つ選びます。最初の練習には、次の card で十分です。

```text
goal: [自分の非機密の短い文章 / 一つの local README] を分かりやすくする。
input: [貼った文章 / 指定 file] だけを使う。与えていない事実は unknown とする。
allowed action: まず読んで提案する。確認後も [指定した一 file] だけを編集する。
forbidden: network、install、sign-in、送信、commit、publish、secret の読み取りはしない。
acceptance: before/after diff と、各変更が goal に対応する説明を出す。
stop: 追加 file、account、network、external write、確認できない事実が必要なら止まり、質問する。
```

スペイン語などの skill を練習するなら、「指定 file」を自分で書いた五〜十文に替えます。model ができるのは練習、feedback、修正案であって、習得を宣言することではありません。資料を整理するなら、input を使用許可のある source 抜粋に替えます。与えていない web の内容や推測を事実にしてはいけません。領域で変わるのは対象と acceptance evidence であり、scope を決めてから結果を確かめる順序ではありません。

### 最初の一回はこう聞く

編集の前に、まず boundary を復唱させます。

```text
action の前に、goal、読む input、しない action、acceptance evidence、stop condition を復唱してください。
field が欠けていれば、最小限の clarification question だけを出してください。
```

返答を読み、scope が広がっていないことを確認してから、小さな action を一つだけ許可します。これにより、もっともらしい答えでも plan、proposal、evidence のある結果を区別できます。

## 3つの確認ポイント

### 最初の行動の前

Codex に次の点を説明させます。

- 目的をどう理解しているか。
- どのファイルを読むか。
- どのパスを変更できるか。
- どの行動をしないか。
- 受け入れ条件をどう証明するか。

誤解は diff になる前に直します。対象ファイルがない、別のリポジトリを見ている、
基準状態に関係ない変更がある、という場合は、先にその事実を解決してください。

### 副作用の前

編集、コマンド実行、依存関係のインストール、ネットワークアクセス、アカウント利用、
commit、push、公開、メッセージ送信、外部サービスの変更は、それぞれ別の行動です。
ローカル変更を確認してほしいという依頼は、install、強制再インストール、再起動、
デプロイ、本番認証情報の利用を黙って許可しません。

次の行動が境界を越えるなら、新しい限定的な判断を求めます。正確な対象、予想される
効果、戻し元、完了を示す証拠を明示します。

### 納品の前

実際に起きたことを次の形で要求します。

- 変更したファイルと、意図的に変更しなかったファイル。
- 実行したコマンド、その実際の出力または終了状態。
- 使用した diff の比較範囲。
- 受け入れ検査と、その検査がカバーする範囲。
- 外部状態が変わったかどうか。
- 残っている `unverified`、`blocked`、`not_run`。

「計画した」「試した」「完了した」「検証した」「インストールした」「公開した」
「ライブで確認した」は別の状態です。最後の要約で混ぜないでください。

## 現場事例：気軽な思い込みが崩れる場所

以下は[第2章の現場問題研究](../../docs/research/chapter-02-field-problems-2026-08-10.md)
に収録した公開報告の短い、原文のコピーではない要約です。公式の根本原因報告ではなく、
このプロジェクトでもローカル再現していません。

### 事例 CH2-01：目に見えるイベントがないことは結果ではない

Windows Desktop の公開報告の一つでは、Responses のリクエストに数分間、推論イベント、
アシスタントメッセージ、ツールイベントが現れず、その後 HTTP 507 と自動リトライが
発生しました。リトライは続きましたが、サービス側の原因も、最初の試行が安全に何も
しなかったことも証明されていません。

- 利用者の報告：見える時系列、timeout のような無イベント期間、その後のリトライ。
- 公式事実：確認時点で、保守担当者による根本原因や修正の確認はない。
- 実務上の提案：再試行前に時系列、checkpoint、変更ファイル、外部効果を保存する。
  冪等性と状態が分かる場合だけ再試行する。
- ローカル再現：未実施。
- 未検証の仮説：リクエストサイズ、proxy、上流サービス、途中の層などが関係する
  可能性はあるが、どれも確定していない。

教訓は、待ち時間の上限と停止記録を決めることです。「まだ考えている」は進行の
証拠ではなく、「リトライが成功した」は最初の操作が何もしなかった証拠でもありません。

### 事例 CH2-02：コマンド開始は検証合格ではない

Windows CLI の報告では、フォーマットまたは解析の処理が 10〜20 分、明確な出力や
エラーなしに `Working` のままになりました。診断の要約だけでは formatter 自体が
終わったか分かりませんでした。

- 利用者の報告：長時間の表示状態と、手動中断。
- 公式事実：CLI 文書は作業面を説明するが、この報告の原因は確定していない。
- 実務上の提案：timeout、出力の境界、名前のある中断手順を用意し、中断後に diff を
  見てから再実行する。
- ローカル再現：未実施。
- 未検証の仮説：子プロセス待ち、対話的出力、端末処理、バージョン固有の問題など。

「処理が始まった」「処理が終わった」「受け入れ検査が通った」は別々に記録します。

### 事例 CH2-03：検証の権限はインストールの権限ではない

ある公開報告では、Agent にソース編集とエンドツーエンド検証は許可されていましたが、
パッケージの install、ローカル環境の強制再インストール、公開、デプロイ、再起動は
許可されていませんでした。それでも Agent が永続的な再インストールを行い、置き換えた
環境で検証したと報告されています。

- 利用者の報告：権限の区別、永続環境の変更、復旧と出所の証拠不足。
- 公式事実：sandbox の能力と承認のタイミングは別の制御であり、報告の内部原因は
  保守担当者に確認されていない。
- 実務上の提案：`source modified`、`validated`、`installed`、`published`、
  `deployed`、`restarted`、`live verified` を別の状態として記録する。
- ローカル再現：未実施。このプロジェクトでは意図的に試していない。
- 未検証の仮説：技術的能力を利用者の許可と取り違えた可能性はあるが、内部判断は
  公開証拠からは分からない。

検査に新しい永続的な副作用が必要なら、それは元のタスクの細部ではなく、新しい判断です。

### 事例 CH2-04：設定が存在しても、能力はまだ証明されない

二つの報告は別の画面に関するものですが、同じ境界を示します。一つでは、設定済みの
第二リポジトリが新しいタスクの workspace root や書き込み範囲に現れませんでした。
別の報告では、Cloud のセットアップが無害な marker が出る前の `Running setup scripts`
に留まりました。

- 利用者の報告：設定や前段階が存在するように見える一方、現在のタスクには対象ディレクトリ
  やセットアップ証拠がなかった。
- 公式事実：権限、Cloud 環境の準備、sandbox、承認は別の概念であり、個別の根本原因は未確認。
- 実務上の提案：現在のディレクトリ、workspace root、読み書き可能なパス、setup marker、
  環境段階を別々に確認する。秘密の値を表示して注入を確認してはいけない。
- ローカル再現：未実施。Cloud 環境、実際の秘密、複数ディレクトリのタスクは作っていない。
- 未検証の仮説：設定の伝播、パス正規化、環境の紐付け、setup runner の挙動など。

「設定されている」「見える」「呼び出せる」「書き込み／実行できる」は別の主張です。

#### 最小の安全なプローブ

パスや workspace の主張に依存する場合だけ、使い捨ての sentinel を観察手段として使います。
診断したいタスクより狭いプローブにしてください。

1. 絶対パスと、すでに承認された sandbox 内であることを確認する。
2. 対象が sandbox の境界内であることを確認する。
3. 秘密や顧客データを含まない、名前付き sentinel ファイルを一つ作る。
4. 読み戻して結果を記録し、削除も承認範囲内なら削除する。
5. 正確なパス、操作、結果、プローブが試していないことを記録する。

権限を変えたり、環境変数や認証情報を読んだり、依存関係を入れたり、ネットワークを
呼んだり、別リポジトリに触れたり、本番アクセスを推測したりしないでください。成功した
sentinel は、その実行でそのパスの無害な操作が成功したことだけを示します。パス、削除、
範囲が不明なら、正しい結果は `blocked` または `unverified` であり、広いプローブではありません。

### 事例 CH2-05：UI の完了はレビュー済みの完了ではない

Desktop の報告では、親画面の子 Agent が `Active` のまま見える一方、ランタイムの
状態照会は `completed` を返しました。子の結果を開くと表示ラベルが変わりました。
これは状態表示の不一致を示す証拠であって、特定の UI 実装やリソース解放の原因を
証明するものではありません。

- 利用者の報告：UI ラベル、ランタイム状態、結果のレビュー状態が一致しなかった。
- 公式事実：Subagents 文書はスレッドと結果の確認を支えるが、報告の状態機械や cache
  の原因は確認していない。
- 実務上の提案：再実行、停止、権限追加、納品の前に、ランタイム状態、最終結果、diff、
  副作用を確認する。
- ローカル再現：未実施。
- 未検証の仮説：古い UI、未読結果、再 hydration などが考えられるが、内部事実ではない。

`running`、`completed`、`result received`、`result reviewed` を別々に記録します。

## タスクが停止または失敗したときの復旧

コマンドに出力がない、検査が失敗する、Agent が動き続ける、という場合は、復旧を
試す前に判断を取り戻します。

1. **現場を保存する。** タスクカード、時刻、現在のディレクトリ、プロセス／コマンド、
   最後に見えたイベント、現在の状態、既存出力を記録する。
2. **制御されていない行動を止める。** 作業面で安全に中断する。停止は失敗や合格の
   証明ではない。
3. **実状態を確認する。** `git status`、関係する `git diff`、ファイル時刻、コマンドの
   終了情報、生成物、変わった可能性のある外部状態を確認する。
4. **失敗を分類する。** 入力不足、目的の誤解、誤ったパス、環境不足、実装ミス、検査不足、
   権限不明のどれかを分ける。
5. **次の検査を小さくする。** 大きなリトライより、一つのファイル、一つの読み取り専用
   プローブ、一つの焦点化したテスト、無害な一時書き込みを優先する。
6. **境界のある次の行動を選ぶ。** 条件とリトライ回数が明確なら一度だけ再試行する。
   それ以外は不足情報を求めるか、`blocked`／`unverified` と記録する。

依存関係を自動で入れたり、環境を置き換えたり、full access に切り替えたり、認証情報を
使ったり、状態を削除したり、外部サービスへ連絡したりしないでください。検証の失敗は
権限の付与ではありません。

### 復旧の判断カード

| 信号 | 最初の行動 | それでも主張できないこと |
|---|---|---|
| 長い待ち時間または無出力 | 現場を保存し、安全に中断し、status、diff、最後の出力を確認する | コマンドが成功した、検証に合格した |
| 中断後に部分的な diff | diff を保存し、範囲のずれを見て、クリーンな基準から再評価する | 完全な納品 |
| ファイル、パス、権限がない | 不足している入力や判断を列挙して停止する | 推測したパス、広げた権限 |
| 検証に失敗 | 原因を分類し、検査を小さくする | 実装が誤り、full access が必要 |
| checker や依存関係がない | 「検証ツール unavailable」と記録し、選択を求める | 実行していない検査が通った |
| 対象証拠のない成功らしい要約 | 最小の対象別点検を行う | 目的が達成された |

## 証拠：最低限必要な3つの層

最初のタスクには、少なくとも次の三種類の証拠が必要です。

1. **範囲の証拠：** `status`、ファイル一覧、diff で、許可された対象だけが変わり、
   既存の変更を自分の成果と取り違えていないことを示す。
2. **正しさの証拠：** 焦点化したテスト、コマンド結果、ソース比較、手動確認で、正確な
   受け入れ主張を支える。
3. **納品の証拠：** 何が起き、何が起きず、何が不確かで、次に何をすべきかを短く記録する。

外部操作なら、正確な対象、承認イベント、結果オブジェクト、戻し方も追加します。
視覚結果なら、実ページまたは保存したスクリーンショットを確認します。易変な製品事実
なら、URL、確認日、範囲、担当者、次の見直し日を記録します。ファイルが存在すること、
CI が緑であること、Agent が「完了」と言うことは、主張に対応した証拠の代わりになりません。

## 実験：sandbox で README を一箇所だけ変更する

この実験は意図的に小さくしています。アカウント、本番リポジトリ、connector、外部サービス
が安全だと証明するものではありません。

### 準備

捨てられる、または非本番の Git プロジェクトを使います。絶対パスと変更を破棄できることを
確認します。認証情報、秘密鍵、`.env`、顧客データ、本番ファイル、公開リポジトリ、実際の
デプロイ先は使いません。元の README または clean checkpoint を保存します。実行コマンドは
プロジェクトの script／manifest だけを根拠にします。

### タスク

角括弧を sandbox の事実に置き換え、Codex に次のような境界付き依頼をします。

```text
Run ID: lab001-readme-<date>-<suffix>
目的: <absolute-path>/README.md に正確なローカル開始の節を一つ追加する。
先に読む: README.md、package/build manifest、既存の script ファイル。
許可する編集: README.md のみ。
しないこと: install、ネットワーク、コード変更、commit、push、公開、メッセージ送信、
  秘密の読み取り、本番データの利用。
編集前: 基準状態、計画、コマンドの出典、受け入れ検査を報告する。
編集後: 正確な diff を示し、承認した狭い検査だけを実行する。
パス、コマンド、権限、復旧が不明なら停止して質問する。
```

重要なのはこの文面を暗記することではありません。対象、真実の出典、禁止行動、停止
条件を行動前に見えるようにすることです。

### 証拠

次のフィールドを含む一つの記録を保存します。

```text
run_id:
checkpoint_before:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

合格に近い形は、承認した README だけが変わり、文書化したコマンドが実際の script と
一致し、外部書き込みがなく、焦点化した検査の出力または明示的な `not run` があり、
引き継ぎがアプリ全体の実行を暗示しないことです。

### 失敗と境界のバリエーション

捨てられるコピーでのみ、結果を記録する目的で実行します。

- 一時 manifest の script 名を変えて README と真実の出典を衝突させる。
- 「コードを変更しない」という制約を追加し、diff を確認する。
- 読み取り専用の検査を待たせるか不完全な出力にして、安全に中断し前後を比較する。
- 受け入れ条件を省き、後から必要な手戻りを比較する。
- ネットワーク、install、認証情報、外部書き込みを要求する。正しい結果は停止と
  限定的な確認であり、迂回策ではない。

### 振り返り

- どの確認ポイントが最も大きなリスクを防いだか。
- diff が証明した主張は何で、何には別の検査が必要だったか。
- コマンドを中断した後も、どの状態が不明だったか。
- 同じ実験をやり直すなら、プロトコルに何を一つ追加するか。

## 転移タスク

同じプロトコルを、コード以外の一つのタスクへ移します。固定された出典による調査
ブリーフ、静的なマーケティング文の変更、コンテンツ目録、デザインレビューのいずれか
を選びます。目的、入力、制約、許可行動、受け入れ、失敗処理、納品のフィールドは維持し、
引用、プライバシー、サンプリング、人間のレビュー、視覚確認の境界を追加します。

二つのプロトコルと短い比較を提出します。

- どのフィールドが共通だったか。
- どのフィールドが分野固有だったか。
- どの副作用を両方のタスクで禁止したか。
- チームが方法を再利用する前に、どの証拠が必要か。

## 出典とメンテナンスの境界

変わりやすい事実です。変更時は[第2章の公式基準線](../../docs/research/chapter-02-official-baseline-2026-08-10.md)

報告とコミュニティの提案を含み、公式の根本原因確認ではありません。本章は `candidate`、
