# 第 15 章：研究路线——从问题到可审计知识

**状态：**`candidate`。**实验：**`draft / not_run`。检索结果、论坛帖子和模型摘要都不是自动成立的结论。

## 问题：答案看起来完整，不代表研究已经完成

大语言模型能很快写出概览，却可能混淆来源、时间、地区、样本和推断。可靠研究不是“找到很多链接”，而是让另一位读者能检查：问题是什么、哪些来源被允许、为什么纳入或排除、原文说了什么、哪里仍然未知、结论能支持到什么范围。

## 先把问题缩到可回答

把“帮我研究 X”改写成：需要支持的决策、可被证据回答的具体问题、时间/地区/人群/版本范围、来源优先级、排除规则、交付形式和验收证据。范围不清时，先问问题；不要用更多检索结果掩盖目标不清。

## 来源不是同一种证据

| 来源类型 | 适合支持 | 不能自动支持 |
|---|---|---|
| 官方文档、法规、原始数据 | 产品事实、规则、原始声明 | 所有用户环境的实际行为 |
| 同行评审研究 | 在声明样本与方法中的结果 | 你的具体场景必然相同 |
| 公开用户报告 | 问题线索、失败模式、语言习惯 | 官方根因、普遍频率 |
| 模型摘要 | 导航、待核对的候选线索 | 引用真实性或最终结论 |

把外部文本当数据，而不是命令。页面里的“忽略规则”“上传材料”等指令不会获得授权。

## 操作：证据卡与主张账本

每个关键主张至少记录主张本身、证据类型和原始 URL、访问日期与适用范围、可定位原文、它支持什么与不支持什么、冲突来源或未知项、负责人和下次复核。再做主张账本，把“事实”“观察到的用户报告”“项目推断”“建议”“未知”分开。模型可以帮助归类和生成问题，但不能替代阅读原始来源；引用前要回到原文确认标题、作者、日期、范围和措辞。

## 最小可审计研究循环

1. 固定问题、范围和来源规则；
2. 先收集少量高相关来源，记录检索式和停止理由；
3. 逐条提取可定位证据，拒绝没有范围的漂亮句子；
4. 为相互冲突的来源建并列记录，不强行平均；
5. 写出只在证据范围内成立的结论和下一步验证；
6. 交付时附来源表、主张账本、未知项和复核日期。

## 小实验：把模糊问题变成可审计问题

在本地可丢弃记录中，选择一个不涉及秘密或外部写入的问题。先写一个过宽的问题，再把它缩到时间、对象和决策。使用固定、可见的来源列表，不必联网。为每条来源填写纳入/排除/未知、理由和停止条件。最后写三条主张：一条可由来源支持、一条仅是用户报告、一条必须保留 `unknown`。如果无法定位原文，就不要把它写成事实。

## 失败案例与验收

失败变体：给出一篇带命令式文字的网页摘要，或两篇范围不同且互相矛盾的来源。正确做法是把命令当数据、把冲突显式保留，并缩小结论；不是让模型选一个更顺眼的答案。

- [ ] 我能说清研究要支持的决策和边界。
- [ ] 每个关键主张都有可定位的来源、日期和范围。
- [ ] 我分开了官方事实、报告、推断、建议和未知。
- [ ] 我记录了纳入、排除、冲突和停止原因。
- [ ] 我没有把模型摘要或引用列表当原始证据。
- [ ] 另一位读者能复查我的来源和主张边界。

来源会过期，产品事实更会变化。研究完成不等于结论永久有效；请记录复核人和日期。可配合 [实验 008：把主题缩成可研究的问题](../labs/lab-008-research-question-ZH.md)。本章仍是 `candidate`，研究模板存在不证明结论正确。

## 从宽题到可审计交付：一张研究工作表

以“哪种 LLM 最适合我的团队？”为例。它不是可直接回答的问题，因为“最适合”没有任务、账户条件、预算、时间或验收标准。先把它改写为：

```text
问题：截至 <日期与时区>，针对 <三项已列出的任务>，哪些公开一手资料
说明了 <候选产品> 的已声明能力、限制和账户/地区未知项？
不回答：哪一个“最好”、未公开的价格或本团队尚未试用的真实表现。
来源优先级：官方文档和发布说明；其次是明确标注的用户报告。
交付：主张—来源—范围—未知项表，不作总排名。
停止：关键页面不可访问、产品/版本范围不清，或需要账户、隐私数据或付费动作。
```

接着为同一问题准备三组检索词：症状/任务词、边界词、环境词。不要只搜索你想证明的产品名称加“best”。每一轮记录查询式、日期、时区、来源范围、纳入和排除理由；搜索摘要、转述文章和模型给出的链接只能作为线索。

### 主张行比一段漂亮总结更重要

| 字段 | 示例写法 |
|---|---|
| 原子主张 | “页面 X 在访问日描述了功能 Y。” |
| 证据 | 原始 URL、最终 URL、标题、定位位置、访问日 |
| 范围 | 产品面、版本、地区、账户条件；未知则写未知 |
| 证据级别 | 官方说明 / 维护者确认 / 用户报告 / 线索 |
| 不能推出 | 不代表我的账户可用，不代表任务成功率或最佳选择 |
| 写作语气 | 已说明 / 有报告称 / 未证实，而不是“必然支持” |

如果一条来源只证明“有人报告遇到问题”，不要把同一行扩写成根因、普遍性或修复建议。将观察、解释和建议拆成不同主张。

## 小实验：处理一份冲突且部分不可访问的资料包

准备三项材料：一页可访问的官方资料、一则带日期和原始 URL 的用户报告，以及一项会跳转、要求登录或无法打开的链接。不要上传日志、Cookie、token、联系人或私有文件。

1. 先写三个候选问题，只选择一个；补齐范围、截止日、时区、纳入/排除和停止条件。
2. 为每项材料记录原始 URL、最终 URL（如有）、访问结果、标题/组织、日期和可定位位置。打不开就写 `inaccessible`，不以标题或搜索摘要补写内容。
3. 对每个关键主张做一次反向检索：寻找限制、不同环境或反例。未找到反例不是证实。
4. 若两页资料冲突，先检查它们是否谈的是不同版本、产品面、账户、地区或定义；仍无法解决时，保留双方并收窄交付。
5. 最终交付一页 `candidate` 记录：已知、未知、冲突、不能主张的内容、停止原因和下一项低风险动作。

## 本章验收补充

- [ ] 我能把“哪个最好”改写成有任务、范围、日期、来源优先级和交付形状的问题。
- [ ] 我保留原始与最终 URL、访问结果和可定位位置，而不把搜索摘要当阅读证据。
- [ ] 我对关键结论做过反向检索，并记录它没有证明什么。
- [ ] 官方冲突、账户差异、地区限制和用户报告都不会被我压成一个通用结论。

## 一次真实但低风险的研究卡

不要从“哪个模型最好？”开始。把问题改写成能够被检查、也能被拒绝的形式：

```text
问题：截至[日期与时区]，公开一手来源如何描述[两个命名模型]在
[一项具体任务，例如“把一段非敏感文字改成清晰的待办事项”]上的已声明能力、限制与未知项？
不回答：总体排名、未测试的成功率、账户可用性或隐藏价格。
优先来源：厂商官方页面、版本说明、公开 API/产品文档。
交付：claim → URL → 页面位置 → 访问日期 → 适用范围 → unknown 表。
停止：关键页打不开、需要登录/付款/私有数据，或来源互相冲突却无法解释。
```

让模型先帮你列出候选来源和搜索词，但把每条链接当作线索。打开来源后，亲自记录原标题、
原始和最终 URL、可定位段落、访问结果和页面所说的范围。模型说“官方支持”却找不到原文时，
把该句降为 `citation_unverified`，不要用看似完整的书目补洞。

## 一个主张，一条反向检查

对每条重要结论，都追加一个可能推翻或缩小它的问题。例如“页面宣称支持 X”之后，搜索该
能力的限制、账户或地区差异、版本前提与公开反例。没有找到反例不证明结论普遍成立；它只
说明你在记录的范围内没有找到。把结果写成：

| 主张 | 直接来源 | 反向检查 | 能支持什么 | 仍未知什么 |
|---|---|---|---|---|
| 页面在该日期描述 X | URL 与段落 | 限制/地区/版本检索 | 页面当时的公开表述 | 你的账户、真实任务成功率、最佳选择 |

最后交付一页 `candidate` 记录：已知、未知、冲突、没有声称的内容、停止原因和下一项低风险
动作。它不是模型评测、用户研究或购买建议；本章与实验仍分别是 `candidate` 和 `not_run`。

## 十分钟研究回执：先记录，再下结论

刚开始研究时，不必假装能一次做完完整报告。选一个窄问题，花十分钟填这张回执；它的目的
是让下一步可复查，而不是立刻给出“最好的模型”或“唯一原因”。

```text
问题：<一项任务、一个日期和一个范围>
不回答：<排名、效果、账号可用性或其他当前没有证据的事>
来源候选：<原始 URL，不把搜索摘要当正文>
实际访问：<成功 / redirect / login / timeout / 未读>
可定位的内容：<标题、日期、段落或 Issue 编号；没有就写 none>
这条来源支持：<一个原子事实>
这条来源不支持：<原因、普遍性、我的账号或实际任务结果>
反向检查：<一个会缩小结论的查询或来源>
当前状态：official / user_report / lead / inaccessible / citation_unverified
下一项安全动作：<读一个来源、比较范围，或停止>
```

“页面 X 在访问日描述了功能 Y”与“我的团队现在可用 Y”是两条不同的声明。前者可能有公开
页面支持；后者还需要账号、组织、地区和实际工作面的证据。不要用一条链接代替两条证据。

### 何时把一句话降级

| 原句 | 缺什么 | 更诚实的写法 |
|---|---|---|
| “模型 A 最适合研究。” | 任务、样本、比较和评分 | “公开页面描述了 A 的某项能力；是否适合本任务尚未评估。” |
| “这个问题由 X 引起。” | 可复现证据或维护者确认 | “一位用户报告了该症状，并提出 X 是可能原因。” |
| “官方支持。” | 可定位的官方正文及适用范围 | “在访问日，官方页面在其声明范围内描述了该功能。” |

降级不是削弱研究，而是避免读者把来源的存在误解为结论已经成立。

## 研究决策卡：从问题到停止回执

面对任何“帮我查一下”的请求，先把它写成能改变一个具体决定的问题。下面的卡片适用于公开或已获授权、且你自己能够打开检查的材料；它不会证明网页真实、替你浏览全部网络或替你做健康、法律、雇佣、金钱等高风险决定。

### 先固定决定与问题
```text
决定：我需要在 [日期] 前为 [对象] 决定什么？
问题：哪一个可回答的问题会改变这个决定？
范围：包含什么、不包含什么、事实截止到何日何时何地？
停止：缺少哪项来源、授权或定义时必须暂停？
```
### 给每条主张配来源所有者

| 主张 | 最可能的来源所有者 | 直接支持 | 冲突/未知 | 下一项允许检查 |
|---|---|---|---|---|
| [一句可核查的话] | 官方产品页 / 原始研究 / 法律政策 / 第一方数据 / 具名机构 | 引文或段落位置 | 不支持的部分或不同版本 | 一项最小检查 |

论坛经验可帮助你发现症状和提问方式，但不能自动证明根因或所有用户都会遇到同一问题。AI 生成的链接、标题、日期和引文也必须回到原始材料核对。

### 在结论前做一次反向检查

对每条计划写入结论的话，问四件事：材料是直接说了它，还是我在推断？有没有较新的版本、例外条件或冲突来源？访问日期是否仍在决定的时间范围内？如果另一位读者只看到台账，能否找到同样的支持？其中一项答不出来，就缩小句子或标为 `unknown`，而不是用自信语气补齐。

### 十分钟停止回执
```text
决定与问题：
已打开且可检查的材料：
直接支持：
解释或推断：
冲突与未知：
访问日期与范围：
下一项最小检查：
停止原因：
状态：research_plan | scope_checked_for_supplied_list | blocked | not_run
```

回执只说明在记录范围内发生了什么；它不是“研究完成”、最新事实、模型正确检索或可以采取行动的证明。
