# 第 3 章：把願望變成任務協議

![教學圖：把一個請求依次變成範圍、行動、檢查與有邊界的交接](../../assets/teaching/task-to-evidence-red-black.svg)

## 本章要解決的問題

“把首頁做得更好。”“研究一下這個。”“用最好的 Skill。”“把修復部署掉。”這些話在真正需要決定讀什麼檔案、能做什麼、怎樣算完成、何時該停時，往往並不清楚。

當這些決定沒有寫出來，Agent 或協作者只能用假設補洞。於是會出現一類熟悉的失敗：結果很漂亮，卻改錯了介面；研究列了連結，卻沒有引用真正擁有結論的來源；構建透過了，執行中的頁面卻從未檢查；或者一句“驗證一下”悄悄擴充套件成安裝、外部呼叫或又一輪編輯。

本章把嚴肅的提示詞當作一份小型**任務協議**。協議不規定隱藏推理，也不寫死每一次按鍵；它把能觀察、能審查的契約寫清楚：目標、上下文、輸入、約束、允許行動、驗收證據、停止條件、恢復和交付。

核心規則是：

> 當補充資訊能夠消除一個會改變範圍、風險、驗收或證據的決定時，才加入它。若它只讓請求聽起來更權威，就刪掉它。

## 學習目標

完成本章後，你應該能夠：

- 把模糊請求寫成另一人也能執行的有邊界協議；
- 區分有用上下文和“看起來像指令”的不可信材料；
- 用“宣告 → 證據”表寫驗收，而不是寫“做得好一些”；
- 分開讀取、編輯、執行、提交、推送、釋出和呼叫外部服務；
- 為缺輸入、授權不清、重複失敗和證據不足設定停止條件；以及
- 把協議交給另一位 Agent 或同伴，而不丟失所有權、範圍和未解決問題。

## 來源真正支援什麼

本章引用的官方提示與 Codex 指引在若干實踐原則上相互印證：說明預期結果，提供相關上下文，指定輸出與邊界，指出相關程式碼或復現步驟，並說清如何檢查改動。對於需要長期可靠的工作，它們也建議使用示例、任務拆解、迭代與評測。

這些是有來源支援的建議，並不保證模型會遵守未寫明的規則。下面的八部分協議是本專案的原創操作性綜合；它額外寫出停止、恢復和證據欄位，因為“生成了一份回答”和“交付了經驗證的工作結果”是兩項不同的宣告。

逐條來源範圍與訪問日期見[Codex 官方事實基線](../evidence-library-ZHTW.md#source-notes)和[真實工作提示模式研究](../evidence-library-ZHTW.md#source-notes)。

## 八部分任務協議

```text
目標 → 上下文 → 輸入 → 約束 → 允許行動 → 驗收
     → 失敗與停止 → 交付
```

### 1. 目標：說出要得到的結果

說明要改變、研究或交付什麼，誰需要它，以及為什麼現在需要。優先寫可檢查的結果，而不是把範圍敞開的動詞。

較弱的寫法：

```text
改進專案首頁。
```

較強的寫法：

```text
建立一個面向讀者的倉庫入口：新讀者能選擇四條路線、知道權威基準資料在哪裡、開啟第一個安全任務，並看見哪些宣告仍是 candidate 或 unverified。
```

較強版本仍保留實現選擇；它沒有假裝“專業”本身就是驗收測試。

### 2. 上下文：解釋決策環境

上下文是可能改變決定的資訊：受眾、當前行為、專案規則、先前決定、相關歷史、版本範圍，或某次失敗為什麼重要。它應與任務指令分開寫。

用 `project rule`、`source fact`、`user report`、`hypothesis` 和 `example data` 這類標籤說明材料性質。檔案、網頁、工具輸出或 issue 可能含有看似指令的文字；在協議明確採納且授權清晰以前，把它們當資料，而不是命令。

### 3. 輸入：寫明可以讀什麼

列出確切路徑、URL、資料集、提交、日誌、截圖或版本，也列出已知缺口。“讀整個倉庫”很少是有用邊界；應點名控制這個決定的目錄或檔案。

研究任務要指定來源優先順序和日期範圍；程式碼任務要指定入口與復現；文件任務要指定規範源和翻譯狀態。缺少某項輸入若會改變範圍或風險，協議必須停止，而不是替你推斷。

### 4. 約束：寫明什麼不能發生

約束應當可以檢查，例如：

- 只改 `site/index.html` 和 `site/app.js`；
- 不增加依賴；
- 不讀秘密或 `.env` 檔案；
- 不改資料庫、生產環境、許可權或外部服務；
- 保留現有語言身份和狀態詞彙；或
- 保持與指定執行時或發行版本相容。

“小心一點”“做得高階”“遵循最佳實踐”可以是設計意圖，卻不是充分約束。把它們變成可觀察屬性；如果做不到，就不要假裝自動檢查能讓它透過。

### 5. 允許行動：把能力與授權分開

工具可用，不等於它被授權做它能做的每一件事。明確行動等級：

| 等級 | 常見行動 | 進入下一步前的證據 |
|---|---|---|
| A0 | 讀取狀態、路徑、來源或日誌 | 已記錄範圍和當前狀態 |
| A1 | 起草計劃或編輯提案 | 已命名目標檔案和驗收 |
| A2 | 做一項有邊界的本地編輯 | diff 保持在批准集合內 |
| A3 | 執行針對性檢查 | 命令來自專案或已獲批准 |
| A4 | 提交或推送 | 使用者已授權目標與審查證據 |
| A5 | 釋出、部署、通知、付費、刪除或改變外部狀態 | 明確批准、回滾與動作後檢查 |

協議可以只授權 A0–A2，把 A3 留到確認後；也可以允許一項聚焦測試，卻不允許安裝。不要用“需要什麼就做什麼”掩蓋許可權變化。

### 6. 驗收：讓每項宣告對應證據

先寫宣告，再寫能支援它的材料：

| 宣告 | 所需證據 | 它不能證明什麼 |
|---|---|---|
| 指定檔案已改變 | `git diff --name-only` 和實際 diff | 執行時行為或使用者驗收 |
| 檢查透過 | 精確命令及退出狀態或輸出 | 該檢查覆蓋全部要求 |
| 頁面可訪問 | 本地或部署 URL 與瀏覽器觀察 | 所有瀏覽器、快取或已登入路徑 |
| 研究仍是當前的 | 一手 URL、訪問日期、適用範圍與下次複核 | 論壇報告就是官方根因 |
| 任務完成 | 沒有必需無證據宣告的宣告—證據表 | 宣告範圍以外的工作 |

某項宣告若沒有可負擔的證據，就縮小它。“本地構建透過”常常成立；“功能對所有使用者都可用”通常需要更大測試與明確環境。

### 7. 失敗與停止：預先寫好出口

可靠協議會說明何時不應繼續。遇到以下情形應停止並報告：

- 目標、當前狀態或授權不清；
- 缺失輸入可能改變範圍、風險或驗收；
- 建議行動跨過已批准的檔案、網路、賬戶或資料邊界；
- 輸出沉默過久，下一次重試可能重複副作用；
- 同一未經檢驗原因導致兩次失敗；或
- 證據只能支援比請求交付更窄的宣告。

恢復不是“用更大聲的提示詞再試一次”。保留第一次錯誤，縮小範圍，只改變一個假設或檢查，並記錄前一次已改變了什麼。重試耗時或外部可見行動前，先查當前狀態與 diff，避免重複第一次副作用。

### 8. 交付：留下可用的交接

要求最終記錄包括：

- 已完成宣告及其證據；
- 改過的檔案、URL、命令或記錄；
- 有意不做的行動；
- 未解決問題、風險與未驗證範圍；
- 精確的下一個最小檢查；以及
- 易變事實的負責人或複核日期。

交接是產品的一部分。沒有它，下一位協作者只能從聊天記錄重建協議，可能重複失敗動作。

## 協議是一張依賴圖

這些欄位不是彼此獨立的一串形容詞：

```text
目標 ───────────────→ 驗收 ───────→ 停止
  │                      │            ↑
  ├── 需要 ─────────→ 輸入           │
  ├── 受制於 ───────→ 約束           │
  │                      │            │
  └── 塑造 ─────────→ 允許行動 ─→ 恢復
                                          │
上下文 ──> 信任與相關性 ────────────────┘
                          ↓
                       交付證據
```

目標變了，驗收也必須變；新輸入改變風險時，允許行動和停止條件也要重審。“請小心”不能修補缺失的依賴關係。

## 最小可用協議

<!-- starter-task-contract:start -->

### 複製一條安全的起步提示

替換方括號欄位，並要求第一輪只觀察。批准暫停是從新手請求走向可檢查工作流的橋樑；不要只為了縮短提示詞就刪掉它。

```text
請幫助我完成一項小型、可回滾的任務。

結果：[一個可觀察的結果]。
上下文：[相關檔案、輸入和當前狀態]。

第一輪迴復——只觀察：
- 只檢查完成本任務所需的上下文；
- 報告發現、缺失輸入和風險；
- 提出最小安全計劃，以及它會改變的精確檔案或介面；
- 暫不編輯、不執行會改變狀態的命令、不做外部動作；等待我的批准。

如果我批准計劃：
- 只在獲准範圍內行動；
- 執行[一項聚焦檢查]；
- 若範圍、授權、破壞性動作、外部副作用或驗收不清楚，停止並提問。

除非我明確授權該項行動，不得訪問秘密或生產環境、安裝依賴、使用網路、提交、推送、釋出或擴大任務。

驗收：[具體產物或 diff] 和 [具體檢查輸出]。
交付：已做行動、改變的檔案或介面、檢查輸出、剩餘未知項和未做行動。
```

複製或傳送這條提示不能證明做過行動或結果正確。使用下方協議欄位把它改成你的任務；用[實驗 002](../labs/lab-002-task-protocol-ZHTW.md)練習，再讀[第 9 章：驗證與恢復](09-verification-and-recovery-ZHTW.md)，以證據審查每項完成宣告。

對於低風險本地編輯，通常可以縮成：

```text
目標：修改 <一個命名檔案>，使其出現 <可觀察結果>。
先讀：<精確檔案或事實來源>。
允許：先檢查，再僅編輯 <命名路徑>；執行 <聚焦檢查>。
禁止：安裝、訪問秘密或網路、提交、推送、釋出或接觸生產環境。
驗收：<具體 diff> 和 <具體檢查輸出>。
停止：路徑、命令、許可權或證據不清楚時停止。
交付：已改檔案、檢查結果、未做行動和未驗證項。
```

協議之所以能短，是因為風險很窄，不是因為遺漏欄位無害。

## 高風險協議擴充套件

面向生產環境、外部服務、客戶資料或不可逆動作，增加動作前檢查點：

```text
動作前檢查點：
- 目標環境和賬戶：
- 當前版本和備份位置：
- 精確外部副作用：
- 批准人和時間：
- 回滾目標與恢復測試：
- 動作後 URL / 日誌 / 指標檢查：
```

不要讓 Skill、複製來的 runbook 或成功的本地構建默默填充這些欄位。它們需要當前環境證據和對外部狀態負責之人的授權。

## 三條提示優於一條超長提示

任務不確定時，使用分階段提示：

1. **觀察：** 列出相關檔案、當前狀態、缺失輸入和風險；
2. **提案：** 寫出最小計劃、改動檔案集合、驗收宣告與停止條件；
3. **行動：** 只執行獲准計劃，並針對每項宣告返回證據。

這樣能在編輯前檢查計劃，更容易定位壞假設是哪一階段引入的；它仍不能代替審查實際結果。

## 一條證據有邊界的練習迴圈中的六條起步提示

它們不是神奇措辭，也不是必須連續完成的六節課。它們解決六個不同控制問題：觀察到的目標與基線、先檢索後揭示、有邊界的糾正、即時變式、基於證據的複習線索，以及延遲的未見檢查。例子使用西班牙語；方括號可替換成語言、軟體概念、面試技能、寫作技巧或其他有邊界能力。

### 1. 找到真實起點

```text
我想學習[用西班牙語進行五分鐘的初學者對話]。
先不要教學。請給我一項只測試該能力的短基線任務。
在我開始前，說明規則、允許幫助、時間限制和評分標準。
等我的回答。然後記錄我能做什麼、什麼阻礙了意思表達，以及一次嘗試仍不能推斷什麼。
```

先用它確定起點。“我是初學者”這類自報資訊，不如一次可觀察嘗試有用。

### 2. 先讓我提取，再揭示答案

```text
教我完成[用西班牙語點餐]所需的一個小單元。開場解釋不超過 120 個詞。
然後要求我憑記憶作答；在我嘗試前不要展示最終答案。
如果我卡住，每次只給一條提示：先說錯誤型別，再給區域性線索，最後才給示範片段。
反饋後，要求我用自己的話再答一次。
```

關鍵不是“120 個詞”，而是“等我先嚐試”。

### 3. 糾正第一個會影響結果的錯誤

```text
請當一位精確的練習夥伴，不要只鼓勵。對我的每個回答：
1. 簡短說出哪裡表達成功；
2. 指出第一個改變意思或阻礙目標技能的錯誤；
3. 用平實語言解釋規則；
4. 要我給出修正後的嘗試；
5. 維護錯誤賬本：嘗試、修正、規則和下一變式。
不要替我重寫全部內容，也不要在阻礙意思的錯誤仍存在時先改小風格問題。
```

這樣能避免一份流暢重寫替代真正學習。

### 4. 用變化的情境測試遷移

```text
我剛練習了[用西班牙語點餐]。請給一個使用同一底層技能的新情境，但改變場景、詞彙和一個歧義來源。
不要複用課上的句子。先讓我回答；按相同標準評分，說明我用了什麼幫助，
並把結果僅標為“在這項遷移任務上已展示”，不要稱為掌握。
```

近似復刻只測試識別；換情境的任務才開始測試遷移。

### 5. 從證據生成下一次複習

```text
只使用本次對話中的嘗試和錯誤賬本，為我生成下一次 15 分鐘複習。
先做無輔助回憶，重訪仍重要的兩個錯誤，加入一個混合例子，最後用一個未見任務結束。
不要聲稱你安排了提醒。給我可以儲存的複習線索、我應嘗試的日期，以及我應帶回的證據。
```

模型可以準備線索；沒有證據時，它不能誠實地宣稱你保留了技能，或外部提醒已經存在。

### 6. 在聲稱保持前完成延遲的未見檢查

```text
這是我為[目標技能]安排的複習。不要展示儲存的課程或已改正句子。
給我一項此前未揭示、細節變化但測試同一能力的任務。
說明允許幫助和不變的評分標準，然後等我作答。記錄實際間隔和所用幫助。
只報告這項延遲任務發生了什麼；不要推斷永久保持、廣泛遷移、流利或掌握。
```

儲存複習線索只是計劃。在延遲嘗試及其條件被記錄前，保持仍是 `not_run`。

### 單獨檢查：研究一種方法宣告

```text
請調查這項宣告：[六條提示能讓任何人在七天內流利]。
先定義這項宣告必須證明的精確能力。優先使用原始研究與官方來源所有者材料。
對每個重要結論，記錄來源、日期、人群或產品範圍、直接支援，以及它不能證明什麼。
搜尋一次反面證據。分開事實、推斷、軼事和未知項；當更多來源不再改變決定時停止。
最後把原宣告改寫成最窄而誠實的版本。
```

這條研究提示不屬於六步練習迴圈。面對健康、金融、產品功能、新聞、統計或其他高風險結論時，用它來避免把自信回答當證據。

### 儲存什麼

儲存基線、首次嘗試、所用提示、修正嘗試、錯誤賬本、延遲複習、未見任務和評分標準。一次順利會話只能支援“今天練習過”，不能證明流利、持久保持或遷移。完整候選方法與來源邊界見[LLM 輔助持久學習研究](../evidence-library-ZHTW.md#source-notes)。

## 真實世界的失敗模式

本專案收集的現場報告解釋了這些欄位為何重要：

- 長時間等待或自動重試會讓 Agent 看似仍在工作，卻不能證明最新指令已到達，或外部動作沒有被重複；
- 配置檔案可能含有許可權設定，而當前工作面、工作目錄或持久執行時策略實際不同；
- 瀏覽器登入成功或能看到工具名稱，不能證明目標賬戶、組織、倉庫或聯結器已獲授權；以及
- 社群繞過方案也許只適用於某個版本或平臺，甚至可能不安全。

這些是使用者報告和社群觀察，不是通用產品根因。用[現場問題索引](../evidence-library-ZHTW.md#source-notes)和[編碼 Agent 案例報告](../evidence-library-ZHTW.md#source-notes)練習同一響應模式：記錄症狀與環境，做最小安全檢查，在邊界處停止，只宣告證據真正支援的內容。

## 多 Agent：交接本身也是協議

委派不解除主 Agent 的責任。給每位工作者一個互不重疊的工作和固定輸出形狀：

```text
角色：檢查語言矩陣；不要編輯原始檔。
輸入：<兩個已命名檔案>。
輸出：發現、證據路徑、阻礙，以及一個建議的下一步檢查。
禁止：編輯、外部訊息、憑據，以及超出已宣告檔案範圍的結論。
```

協調者必須在核查每位工作者的來源、範圍與證據後才合併事實。另一位 Agent 的摘要是線索，不是已驗證結論；若兩人衝突，保留兩份報告並回到事實來源解決。

## 實驗：同一請求的三個固定版本

### 準備

使用配套的[實驗 002](../labs/lab-002-task-protocol-ZHTW.md)，並選擇一個可丟棄專案。保持底層願望不變，寫出三版：

- `v1`：只有願望；
- `v2`：願望加目標、受眾、允許輸入和禁止行動；
- `v3`：保持同一請求，再加入驗收、停止、失敗恢復與交付。

### 任務

只要求 Codex 澄清並起草協議。不要讓該實驗編輯、安裝、提交、推送、釋出或聯絡外部服務。比較它提出的問題、暴露的假設、允許行動和要求的證據。若沒有實際 Codex 執行，把記錄標為靜態協議審查；不要稱為執行證據。

## 故意失敗變體

給 Agent 一個“做得專業”“修復你發現的所有問題”的請求，卻不寫目標檔案、驗收、許可權和停止條件。透過的回答必須指出缺失決定，或保持為只讀提案；若它編造目標、安裝依賴、擴大編輯集合，或無證據地宣稱完成，即為失敗。

然後把模糊詞替換成可觀察標準，例如：

- “英文 README 有一個可見的七種已登記語言切換器”；以及
- “本地連結檢查報告零個斷裂倉庫連結”。

這些標準仍需要專案真實驗證器和審查範圍；它們只是可測試語言示例，不證明檢查已經執行。

### 反思

記錄哪一個缺失欄位最改變範圍、風險或驗收。說明另一人能否不猜測地接手協議，並指出一項仍需執行時證據的宣告。

## 驗收清單

- [ ] 目標說清結果、受眾和範圍。
- [ ] 上下文分開專案規則、事實、報告、假設和示例資料。
- [ ] 輸入標明精確檔案、來源、版本和已知缺口。
- [ ] 約束包括禁止檔案、秘密、依賴和外部副作用。
- [ ] 允許行動分開讀取、起草、編輯、執行、提交、推送和釋出。
- [ ] 每項必需宣告都有匹配證據載體。
- [ ] 停止條件覆蓋缺授權、範圍變化、重複失敗、沉默和無證據宣告。
- [ ] 恢復保留第一次錯誤，並在重試前檢查狀態。
- [ ] 交付列出已做、未做、證據、未知項和下一個最小檢查。
- [ ] 另一人或 Agent 無需猜測即可執行協議。

## 遷移練習

分別為以下情境改寫一份請求：

1. **工程：** 修復可復現迴歸，且不改公共 API；
2. **研究：** 用一手來源和分歧表回答一個當前問題；
3. **內容：** 更新已本地化 README，並保留同語言連結；
4. **釋出：** 用備份、回滾目標和動作後現場檢查釋出一個有邊界改動；以及
5. **Agent 協作：** 委派兩位工作者檢查互不重疊的檔案，再由協調者製作證據表。

對每項遷移，標記哪些欄位可複用，哪些必須替換為領域證據。一份讀起來不錯、卻不能告訴同伴何時停止的協議，仍不完整。
