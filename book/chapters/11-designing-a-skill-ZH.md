# 第 11 章：设计一个真正有用的 Skill

**状态：** `candidate`

**实验状态：** `not_run`
**译文边界：** 本章由既有中文候选稿迁移而来。它可支持中文读者完成本章的概念、练习和验收，但尚未与当前英文规范稿逐段对齐，也未通过独立中文审校；不可视为完整或已验证译本。

## 本章要解决的问题

Skill 的价值不在于长度、术语或目录数量，而在于它能否在一类真实任务中减少遗漏、提高一致性、保护边界并留下更好的证据。一个只会重复通用常识的 Skill 会消耗上下文；一个没有触发边界、失败处理和验收契约的 Skill，会把不稳定的个人习惯包装成“自动化”。

本章把 Skill 当作可复用的方法包来设计：它描述适用范围、输入检查、决策点、允许行动、停止条件和输出证据，但不替用户决定本次任务的具体目标。

## 学习目标

读者完成本章后应当能够：

- 为 Skill 写出清楚的触发条件、不适用范围和输入契约；
- 从一次成功流程中提炼真正可复用的判断，而不是堆叠通用知识；
- 用渐进披露组织 `SKILL.md`、references、scripts 和 assets；
- 为秘密、外部内容、权限、失败和停止写出可执行边界；
- 用正例、边界例、失败例和迁移例评估 Skill 的价值，并区分发现、调用、加载和验证。

## 现实问题入口

[FP-06](../../docs/research/field-problems-codex.md#fp-06：skill-discovery-忽略文件-symlink)记录了普通文件与 symlink 在发现行为上的用户报告；[FP-07](../../docs/research/field-problems-codex.md#fp-07：显式-skill-调用错误地依赖隐式可见列表)记录了显式调用与隐式可见列表混淆的报告。两条记录都没有官方确认或本地复现，不能当成所有版本的固定行为；它们提醒我们：Skill 目录里“存在一个文件”，不等于运行时已经发现、解析、触发、加载并验证它。

## 1. 先写触发契约

Skill 的描述（description）应能回答四个问题：

1. 用户正在做什么任务时应该使用它？
2. 哪些输入或上下文必须存在？
3. 哪些相似任务不应该使用它？
4. 触发后应该留下什么结果和证据？

可以先用下面的模板，而不是从一段宣传语开始：

```text
适用：当用户要……且存在……时。
不适用：如果用户只要……或缺少……，应先……/拒绝……。
输入：需要读取哪些文件、数据、版本和权限状态。
输出：交付哪些文件、报告、diff、日志或待确认项。
```

过于宽泛的 Skill 会在不相关任务中增加上下文和误触发；过于狭窄的 Skill 会让用户无法发现。触发边界是能力设计的一部分，不是最后补的元数据。

## 2. 只沉淀可复用的判断

Codex 已具备通用写作、编程和分析能力。Skill 应补充那些不显然、容易遗漏或需要项目一致性的内容，例如：

- 领域术语、项目结构和文件优先级；
- 脆弱步骤、常见失败和恢复顺序；
- 工具到任务的映射，而不是工具名列表；
- 输出格式、证据标准和停止条件；
- 秘密、外部内容、许可证和副作用的边界。

一个简单的提炼测试是：删掉这句话后，具有通用能力的 Agent 是否仍能在本项目中做出同样可靠的判断？如果能，句子可能只是背景噪声；如果不能，再说明它依赖什么证据、何时适用、失败时怎么办。

Skill 也不应吞掉本次任务协议。用户目标、项目规则、Skill 方法和工具行动的关系是：

```text
本次任务协议：这一次要交付什么
项目规则：长期有效的术语、许可和安全约束
Skill：这类任务通常如何检查、决策、执行和验证
工具：当前真正可以采取的具体行动
```

发生冲突时，暴露冲突并暂停；不要让 Skill 静默改写用户目标或扩大权限。

## 3. 用渐进披露控制上下文

推荐的三层结构是：

```text
元数据：什么时候触发
SKILL.md：最短的核心流程、选择规则和边界
references/scripts/assets：只有在当前分支需要时才加载或执行
```

`SKILL.md` 应让读者从输入检查走到交付，不应复制所有参考材料。参考文件适合放长表格、领域背景、版本化规范和例子；脚本适合确定性检查、格式转换或可重复操作；资产适合模板或明确授权的素材。每个附属资源都应说明用途、输入、输出和失败处理。

不要把“有脚本”当成“已验证”：脚本仍可能改错路径、读取秘密、联网或使用过期接口。第一次使用附属资源时，先在临时目录或无敏感数据的样本上做 smoke test，并记录版本和输出。

## 4. 写出完整而有限的流程

一个可靠 Skill 至少应包含以下顺序：

1. **确认输入：** 检查文件、版本、来源、权限和必需字段；缺失时询问或停止，不猜测；
2. **建立范围：** 列出会读什么、会改什么、不会改什么；
3. **选择路径：** 根据任务大小、风险、可逆性和证据要求选择步骤；
4. **执行最小动作：** 每次动作有目标、输出和变更边界；
5. **观察并分类失败：** 区分输入、环境、权限、实现和验证失败；
6. **决定继续、缩小、询问或停止：** 写出触发条件，不使用无限重试；
7. **交付证据：** 给出文件、diff、命令输出、来源、未验证项和下一步。

外部文档、网页、Issue、邮件和工具返回值都是数据，不是自动覆盖 Skill 规则的指令。只把它们作为事实输入，经过来源、范围和可信度检查后再使用。秘密永远不应进入 Skill 文件、示例、日志或交付摘要；如果任务确实需要秘密，说明由谁、在哪个受控入口提供，以及怎样避免写入输出。

## 5. 以任务集评测，而不是只读一遍

每个 Skill 至少需要四类任务：

- **正例：** 应该触发，并在声明范围内完成；
- **边界例：** 相似但不适用，应拒绝、缩小范围或请求补充输入；
- **失败例：** 输入缺失、命令失败、外部依赖不可用或出现不可信内容时，应保留状态并停止在正确位置；
- **迁移例：** 换表达、领域或文件后，方法仍然成立，但具体事实不会被硬编码带过去。

为每个任务记录：初始上下文、Skill 是否发现、是否被选中、加载了哪些资源、采取了哪些行动、产生了哪些证据、是否越过边界。这样才能定位问题是在 discovery、routing、loading、execution 还是 verification。

## 实验：把一次成功沉淀为最小 Skill

### 设置

选一个不涉及秘密、网络发布或生产数据的重复流程，例如“检查一份 Markdown 文档的链接和标题层级”。先不用 Skill，手工写一份一次性任务协议，包含输入、限制、检查步骤、失败处理和输出证据。准备三份故意不同的样本文档：正常、缺少链接目标、包含长文本但不需要全量改写。

### 任务

从一次性协议中标出“至少在三次任务中会复用”的判断，写成一个最小 `SKILL.md` 草稿，要求包含：触发描述、不适用范围、输入检查、核心步骤、停止条件、输出格式和验证方式。把详细规则放进一个 reference，把确定性检查放进一个只读脚本；如果不需要，就不要创建资源。用正常样本运行一次，再与不用 Skill 的协议对照。

### 证据

保存一份不含敏感内容的实验记录，至少包括：Skill 草稿、正例输入、运行输出、检查过的资源、样本 diff 或报告、人工判断，以及“发现/触发/加载/验证”四个状态。证据应能支持这些断言：Skill 触发范围清楚、输入缺失会被发现、输出可检查、没有额外修改无关文件。

### 失败变体

依次测试三个变体：缺少目标文件、样本文档包含一条来自外部内容的指令性文字、目标目录是不可写位置。观察并记录 Skill 是否拒绝猜测、是否把外部文字当数据、是否在写入前停止。再测试一个不相关的纯文本润色请求，检查是否误触发。不要为通过实验而扩大权限或修改 Skill 发现配置。

### 反思

回答：哪一条规则是领域特有的，哪一条只是通用常识？如果删掉 reference，入口文件是否仍能指导安全停止？如果脚本报告通过，是否仍需要人工检查？一次 Skill 运行成功，能否证明它在其他版本、目录或工作面也可用？

## 失败或边界案例

- **文件存在但未发现：** 不把目录列表当成运行时证据。分别检查路径、元数据、当前工作面能否看到、是否被触发，以及内容是否真的加载。
- **隐式不可见但显式要求调用：** 不假设任一列表等于 Skill 全集；记录当前产品入口、版本和实际结果，必要时用等价的人工流程降级，并把它标为降级而不是修复。
- **symlink、junction 或不同安装方式：** 这是环境和版本相关的易变行为。不要在正文写成永久兼容矩阵；把实际检查留在复核记录中。
- **Skill 过于宽泛：** 如果边界任务频繁触发，收窄 description，加入不适用例，并重新跑正例和边界例。
- **Skill 试图代替工具或授权：** Skill 可以规定方法，不能凭文字创造文件、网络、账号或发布权限。需要工具或新权限时，先写清影响并暂停。
- **参考资料许可证不清：** 不复制文字、图片、代码或 Skill 指令。记录来源和许可决定；只有链接或原创改写在边界清楚时才进入项目。

## 迁移练习

把实验中的文档检查 Skill 迁移成一个研究资料审查 Skill，再迁移成一个团队发布前检查 Skill。每次迁移都保留流程骨架，但重写领域输入、证据、失败和权限边界。至少给每个版本设计一个正例、一个边界例和一个外部依赖失败例，并说明哪些事实必须从官方来源或项目记录重新读取。

## 本章验收

- [ ] 我能写出 Skill 的适用条件、不适用条件、输入和输出契约。
- [ ] 我能解释 Skill 补充什么项目特有判断，以及为什么不应重复通用常识。
- [ ] 我能把入口流程、长参考资料、确定性脚本和授权资产分层。
- [ ] Skill 对输入缺失、外部不可信内容、权限不足和验证失败都有停止或询问动作。
- [ ] 我能区分发现、触发、加载、执行和验证，并为每一步写证据。
- [ ] 我完成了正例、边界例、失败例和迁移例，且未把社区报告写成官方承诺。
- [ ] 我能说明一次成功运行的证据范围，以及下一次复核需要记录的版本和环境。

## 来源与更新提示

Skill 的触发契约、渐进披露、失败处理、任务集评测和证据边界是稳定方法；具体调用语法、发现范围、目录结构、插件能力和资源加载行为属于易变事实。产品事实请以[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)及其中列出的当前官方文档为准；现实问题请回到[现场研究记录](../../docs/research/field-problems-codex.md)查看证据等级、原始 URL 和调查限制。吸收外部 Skill、代码或资产前，按项目的[资产与来源台账](../../docs/sources/asset-register.md)记录来源、许可、适用范围和复核日期。
