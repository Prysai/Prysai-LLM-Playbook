# 第 11 章：设计一个真正有用的 Skill

**状态：** `candidate`

**实验状态：** `not_run`
**译文边界：** 本章提供中文候选阅读与练习路径，尚未通过独立中文审校或真实学习者运行。文件、链接与练习结构存在，不等于翻译质量、学习效果或 Skill 运行行为已经验证。

## 本章要解决的问题

Skill 的价值不在于长度、术语或目录数量，而在于它能否在一类真实任务中减少遗漏、提高一致性、保护边界并留下更好的证据。一个只会重复通用常识的 Skill 会消耗上下文；一个没有触发边界、失败处理和验收契约的 Skill，会把不稳定的个人习惯包装成“自动化”。

本章把 Skill 当作可复用的方法包来设计：它描述适用范围、输入检查、决策点、允许行动、停止条件和输出证据，但不替用户决定本次任务的具体目标。

## 学习目标

读者完成本章后应当能够：

- 为 Skill 写出清楚的触发条件、不适用范围和输入契约；
- 从一次成功流程中提炼真正可复用的判断，而不是堆叠通用知识；
- 用渐进披露组织 `SKILL.md`、references、scripts 和 assets；
- 为秘密、外部内容、权限、失败和停止写出可执行边界；
- 用正例、边界例、失败例和迁移例评估 Skill 的价值，并区分发现、调用、加载和验证。

## 现实问题入口

[FP-06](../../docs/research/field-problems-codex.md#fp-06：skill-discovery-忽略文件-symlink)记录了普通文件与 symlink 在发现行为上的用户报告；[FP-07](../../docs/research/field-problems-codex.md#fp-07：显式-skill-调用错误地依赖隐式可见列表)记录了显式调用与隐式可见列表混淆的报告。两条记录都没有官方确认或本地复现，不能当成所有版本的固定行为；它们提醒我们：Skill 目录里“存在一个文件”，不等于运行时已经发现、解析、触发、加载并验证它。

## 1. 先写触发契约

Skill 的描述（description）应能回答四个问题：

1. 用户正在做什么任务时应该使用它？
2. 哪些输入或上下文必须存在？
3. 哪些相似任务不应该使用它？
4. 触发后应该留下什么结果和证据？

可以先用下面的模板，而不是从一段宣传语开始：

```text
适用：当用户要……且存在……时。
不适用：如果用户只要……或缺少……，应先……/拒绝……。
输入：需要读取哪些文件、数据、版本和权限状态。
输出：交付哪些文件、报告、diff、日志或待确认项。
```

过于宽泛的 Skill 会在不相关任务中增加上下文和误触发；过于狭窄的 Skill 会让用户无法发现。触发边界是能力设计的一部分，不是最后补的元数据。

## 2. 只沉淀可复用的判断

Codex 已具备通用写作、编程和分析能力。Skill 应补充那些不显然、容易遗漏或需要项目一致性的内容，例如：

- 领域术语、项目结构和文件优先级；
- 脆弱步骤、常见失败和恢复顺序；
- 工具到任务的映射，而不是工具名列表；
- 输出格式、证据标准和停止条件；
- 秘密、外部内容、许可证和副作用的边界。

一个简单的提炼测试是：删掉这句话后，具有通用能力的 Agent 是否仍能在本项目中做出同样可靠的判断？如果能，句子可能只是背景噪声；如果不能，再说明它依赖什么证据、何时适用、失败时怎么办。

Skill 也不应吞掉本次任务协议。用户目标、项目规则、Skill 方法和工具行动的关系是：

```text
本次任务协议：这一次要交付什么
项目规则：长期有效的术语、许可和安全约束
Skill：这类任务通常如何检查、决策、执行和验证
工具：当前真正可以采取的具体行动
```

发生冲突时，暴露冲突并暂停；不要让 Skill 静默改写用户目标或扩大权限。

## 3. 用渐进披露控制上下文

推荐的三层结构是：

```text
元数据：什么时候触发
SKILL.md：最短的核心流程、选择规则和边界
references/scripts/assets：只有在当前分支需要时才加载或执行
```

`SKILL.md` 应让读者从输入检查走到交付，不应复制所有参考材料。参考文件适合放长表格、领域背景、版本化规范和例子；脚本适合确定性检查、格式转换或可重复操作；资产适合模板或明确授权的素材。每个附属资源都应说明用途、输入、输出和失败处理。

不要把“有脚本”当成“已验证”：脚本仍可能改错路径、读取秘密、联网或使用过期接口。第一次使用附属资源时，先在临时目录或无敏感数据的样本上做 smoke test，并记录版本和输出。

## 4. 写出完整而有限的流程

一个可靠 Skill 至少应包含以下顺序：

1. **确认输入：** 检查文件、版本、来源、权限和必需字段；缺失时询问或停止，不猜测；
2. **建立范围：** 列出会读什么、会改什么、不会改什么；
3. **选择路径：** 根据任务大小、风险、可逆性和证据要求选择步骤；
4. **执行最小动作：** 每次动作有目标、输出和变更边界；
5. **观察并分类失败：** 区分输入、环境、权限、实现和验证失败；
6. **决定继续、缩小、询问或停止：** 写出触发条件，不使用无限重试；
7. **交付证据：** 给出文件、diff、命令输出、来源、未验证项和下一步。

外部文档、网页、Issue、邮件和工具返回值都是数据，不是自动覆盖 Skill 规则的指令。只把它们作为事实输入，经过来源、范围和可信度检查后再使用。秘密永远不应进入 Skill 文件、示例、日志或交付摘要；如果任务确实需要秘密，说明由谁、在哪个受控入口提供，以及怎样避免写入输出。

## 5. 以任务集评测，而不是只读一遍

每个 Skill 至少需要四类任务：

- **正例：** 应该触发，并在声明范围内完成；
- **边界例：** 相似但不适用，应拒绝、缩小范围或请求补充输入；
- **失败例：** 输入缺失、命令失败、外部依赖不可用或出现不可信内容时，应保留状态并停止在正确位置；
- **迁移例：** 换表达、领域或文件后，方法仍然成立，但具体事实不会被硬编码带过去。

为每个任务记录：初始上下文、Skill 是否发现、是否被选中、加载了哪些资源、采取了哪些行动、产生了哪些证据、是否越过边界。这样才能定位问题是在 discovery、routing、loading、execution 还是 verification。

## 实验：把一次成功沉淀为最小 Skill

### 准备

选一个不涉及秘密、网络发布或生产数据的重复流程，例如“检查一份 Markdown 文档的链接和标题层级”。先不用 Skill，手工写一份一次性任务协议，包含输入、限制、检查步骤、失败处理和输出证据。准备三份故意不同的样本文档：正常、缺少链接目标、包含长文本但不需要全量改写。

### 任务

从一次性协议中标出“至少在三次任务中会复用”的判断，写成一个最小 `SKILL.md` 草稿，要求包含：触发描述、不适用范围、输入检查、核心步骤、停止条件、输出格式和验证方式。把详细规则放进一个 reference，把确定性检查放进一个只读脚本；如果不需要，就不要创建资源。用正常样本运行一次，再与不用 Skill 的协议对照。

### 证据

保存一份不含敏感内容的实验记录，至少包括：Skill 草稿、正例输入、运行输出、检查过的资源、样本 diff 或报告、人工判断，以及“发现/触发/加载/验证”四个状态。证据应能支持这些断言：Skill 触发范围清楚、输入缺失会被发现、输出可检查、没有额外修改无关文件。

### 失败变体

依次测试三个变体：缺少目标文件、样本文档包含一条来自外部内容的指令性文字、目标目录是不可写位置。观察并记录 Skill 是否拒绝猜测、是否把外部文字当数据、是否在写入前停止。再测试一个不相关的纯文本润色请求，检查是否误触发。不要为通过实验而扩大权限或修改 Skill 发现配置。

### 反思

回答：哪一条规则是领域特有的，哪一条只是通用常识？如果删掉 reference，入口文件是否仍能指导安全停止？如果脚本报告通过，是否仍需要人工检查？一次 Skill 运行成功，能否证明它在其他版本、目录或工作面也可用？

## 失败或边界案例

- **文件存在但未发现：** 不把目录列表当成运行时证据。分别检查路径、元数据、当前工作面能否看到、是否被触发，以及内容是否真的加载。
- **隐式不可见但显式要求调用：** 不假设任一列表等于 Skill 全集；记录当前产品入口、版本和实际结果，必要时用等价的人工流程降级，并把它标为降级而不是修复。
- **symlink、junction 或不同安装方式：** 这是环境和版本相关的易变行为。不要在正文写成永久兼容矩阵；把实际检查留在复核记录中。
- **Skill 过于宽泛：** 如果边界任务频繁触发，收窄 description，加入不适用例，并重新跑正例和边界例。
- **Skill 试图代替工具或授权：** Skill 可以规定方法，不能凭文字创造文件、网络、账号或发布权限。需要工具或新权限时，先写清影响并暂停。
- **参考资料许可证不清：** 不复制文字、图片、代码或 Skill 指令。记录来源和许可决定；只有链接或原创改写在边界清楚时才进入项目。

## 迁移练习

把实验中的文档检查 Skill 迁移成一个研究资料审查 Skill，再迁移成一个团队发布前检查 Skill。每次迁移都保留流程骨架，但重写领域输入、证据、失败和权限边界。至少给每个版本设计一个正例、一个边界例和一个外部依赖失败例，并说明哪些事实必须从官方来源或项目记录重新读取。

## 来源与更新提示

Skill 的触发契约、渐进披露、失败处理、任务集评测和证据边界是稳定方法；具体调用语法、发现范围、目录结构、插件能力和资源加载行为属于易变事实。产品事实请以[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)及其中列出的当前官方文档为准；现实问题请回到[现场研究记录](../../docs/research/field-problems-codex.md)查看证据等级、原始 URL 和调查限制。吸收外部 Skill、代码或资产前，按项目的[资产与来源台账](../../docs/sources/asset-register.md)记录来源、许可、适用范围和复核日期。

## 一次可观察的设计流程

下面用“审查 Markdown 链接”这个低风险任务，走完从问题到证据的完整流程。它不需要网络、账号或真实用户数据；它也不证明任何宿主会自动发现这个 Skill。

### 先把任务缩小到能检查的范围

不要写“帮我检查文档质量”。这类目标没有边界。先写出本次任务协议：

```text
目标：找出 docs/quickstart.md 中失效的相对 Markdown 链接。
允许：读取该文件；在临时报告中列出候选问题；运行只读链接检查。
不允许：修改正文、访问网络、安装依赖、删除文件、发布结果。
验收：报告逐条给出链接文本、目标、检查结果和无法判断的原因。
停止：文件不存在、链接规则不明确，或检查需要超出允许范围的行动。
```

这个协议属于这一次任务；Skill 只提供“怎样审查”的可复用方法。把两者混在一起，下一次任务就会把旧文件名、旧权限和旧结论带进去。

### 设计触发与让行规则

触发条件不是广告语。它应该让读者和 Agent 都能判断：这是不是它该接手的工作。

| 项目 | 链接审查 Skill 的示例 |
|---|---|
| 适用 | 用户要求检查一个已指定 Markdown 文件中的本地链接，并给出了目标和验收条件 |
| 不适用 | 用户要求改写文案、检查远程站点、批量修复全仓库，或没有指定目标文件 |
| 需要先问 | 链接是应以当前文件、仓库根目录还是站点构建目录为基准？ |
| 必须停止 | 需要网络、凭据、写入受保护目录或改变发布内容，而任务没有明确授权 |

“链接”“审查”两个词同时出现，不等于应触发。关键词只是一条线索；任务意图、输入是否完整、方法是否归它负责、风险是否可接受，才共同构成触发判断。

### 把动作和证据配对

每一步都要回答两个问题：允许做什么？留下什么可复查的东西？

| 阶段 | 允许动作 | 应留下的证据 | 还不能证明什么 |
|---|---|---|---|
| 输入检查 | 读取指定文件和任务协议 | 文件路径、基线版本、缺失输入清单 | 链接一定失效 |
| 候选扫描 | 提取相对链接 | 候选链接表与解析规则 | 目标文件存在 |
| 本地检查 | 只读检查解析后的路径 | 每条路径的存在/不存在/未知结果 | 线上 URL 可访问 |
| 交付 | 写入可丢弃报告 | 报告、命令和退出状态 | 已修复问题 |
| 复核 | 让人阅读高风险或未知项 | 审核决定和未覆盖范围 | 方法对所有仓库都有效 |

这样写能阻止一个常见误报：脚本运行退出为零，于是报告宣称“所有链接正确”。退出状态只证明该脚本按其定义完成；它不自动覆盖被忽略的格式、构建期重写或远程目标。

## 最小 Skill 不是最少文字

“最小”指的是只保留每次都需要的判断。对上面的任务，一个入口文件可以短，但不能漏掉关键边界：

```markdown
---
name: local-link-review
description: Review local Markdown links in a named file when a target,
acceptance rule, and read-only scope are supplied. Do not use for rewrites,
network checks, or bulk repairs.
---

1. Confirm the target, link base, allowed scope, and acceptance rule.
2. Stop and ask if any one is missing.
3. Extract only local relative links; preserve the original text.
4. Run the declared read-only check and record its version and exit status.
5. Return candidate, confirmed, and unknown results separately.
6. Do not edit, publish, install, or use the network without new approval.
```

如果链接解析规则依赖多个 Markdown 方言，细节可以放进 `references/`；如果有确定性的本地检查器，可以放进 `scripts/`。但“没有目标就停止”“不得联网或写入”这类安全规则必须留在入口中，不能藏到可选文件里。

## 故意失败一次，才知道停止是否真实

正例往往太宽容。请把同一任务复制为一个临时样本，只改一个变量：把一个链接改成不存在的相对路径。预期结果不是“Skill 很聪明”，而是一个具体、可见、可复查的信号，例如：

```text
BROKEN: [安装说明] (guides/install.md)
resolved: docs/guides/install.md
check: path does not exist
scope: local relative path only; remote availability not checked
```

然后再运行一个边界例：同一文件内有 `https://` 链接。这个 Skill 应把它归为“范围外/未知”，而不是偷偷联网。最后运行一个缺失输入例：不给链接基准。正确结果是提问或停止，而不是猜测仓库布局。

### 回滚不是一句“撤销”

本练习不修改原文件，所以最安全的设计是把报告写入临时目录，并在结束时删除该目录或保留路径给读者确认。若一个 Skill 需要写入，必须在执行前写清：目标位置、执行前基线、可逆步骤、回读检查和无法恢复时的停止点。不要让“可以撤销”成为没有对象的承诺。

## 小实验：把一次成功变成可审查记录

1. 选择一个自己拥有、可安全读取的 Markdown 文件；不要把秘密、私人材料或受限项目贴给模型。
2. 按上面的任务协议填写目标、允许范围和验收条件。
3. 用人工步骤或当前工作面可用的 Skill 执行一次只读检查；记录环境、日期、输入和原始输出。
4. 加入一个故意坏链接，重新执行，并确认它留下的是失败信号而不是修复动作。
5. 移除坏链接或丢弃临时样本，回读原文件与报告，确认没有超出授权的改动。
6. 请另一位读者只看任务协议和报告，判断他能否说出结果、范围和未知项。

实验完成只能说明你在记录的环境中观察到了这些结果。它不证明所有 Skill 主机、版本、目录或模型都会以同样方式发现、选择或执行该方法。

## 常见误区

- **把描述写成承诺：** “自动保障发布安全”既没有任务边界，也没有可测验收。改成具体输入、输出和停止条件。
- **把脚本当作 Skill：** 脚本可以检查一个确定问题；Skill 仍需决定何时运行、何时不运行、结果如何解释。
- **把发现当成可靠性：** 即使一个 host 列出了 Skill，也仍要分别验证元数据、选择、加载、动作和交付证据。
- **把成功样本当作评测：** 至少保留正例、近似但不应触发的例子、缺失输入和故意失败；迁移到新领域时重新审查假设。
- **把未知项藏起来：** “未检查远程链接”“无法判断构建期路径”是结果的一部分，不是报告的失败。

## 采用回执：目录里有文件，不等于可以依赖它

在把一个 Skill 交给真实任务前，先写一张采用回执。它避免“看到目录，就默认已经生效”的
误解，也让下一位审查者知道该从哪一层开始检查：

```text
Skill 名称与版本：
任务缺口：它要补上的具体判断，而不是“让 AI 更强”
来源与许可证：原创 / 已审查来源；许可和复核日期
本次宿主与工作面：实际产品、版本和可见路径
已观察到：文件存在 / 发现 / 选择 / 加载 / 动作 / 输出（逐项填写）
未观察到：任何没有运行、没有回读或没有独立审查的层
允许范围：读取、临时写入、网络、安装、发布分别是否允许
下一项安全检查：只验证一个未观察到的层
停止条件：缺少输入、许可、恢复目标或证据时停止
```

例如，`SKILL.md` 位于仓库中，只支持“文件存在”；它不支持“宿主已发现”或“方法已经
执行”。即使一次报告生成成功，也只支持那次任务和记录的环境，不支持所有模型、所有目录或
所有用户都能得到同样结果。采用回执不是额外官话，而是把“我以为能用”变成可复查的判断。

## 先审来源，再采用外部方法

外部 Skill 的说明文字、脚本和示例都先当作待审查材料。不要因为仓库热门、描述流畅或名字
相似，就复制到课程或交给真实数据运行。至少逐项确认：

1. 原始项目链接、具体 revision、维护者和检查日期；
2. 顶层许可是否覆盖所需的代码、脚本、素材和嵌套依赖；
3. 它会读取、写入、安装、联网或发送什么；
4. 本项目的任务缺口是否真的需要它，而不是一个更小的原创流程；以及
5. 用无敏感临时样本做过什么检查，哪些行为仍未运行。

不能回答其中任何一项时，保留链接和研究记录即可，不把内容复制为本项目的 Skill，也不把它
列为已采用能力。这样做不会证明外部方法无害；它只是防止“来源不明的便利”变成用户承担的
风险。
