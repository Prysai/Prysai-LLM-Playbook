# 第八章：从定义到交付的完整生命周期

## 本章要解决的问题

只会让 Codex“开始写”无法保证项目完成。稳定结果来自一条有检查点的生命周期：定义、计划、构建、验证、审查、交付和维护。

## 学习目标

读者完成本章后应当能够：

- 为一个真实任务写出定义、计划、构建、验证、审查和交付检查点；
- 用竖向切片尽早产生可运行或可审查证据；
- 在容量、命令卡住或权限变化时从明确 checkpoint 恢复。

## 现实问题入口

FP-09 的容量中断、FP-10 的 Working 卡住和 FP-01 的 OAuth 版本回归，都说明生命周期不能只写“开始—完成”。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)。

## 1. 六个阶段

```text
定义 → 计划 → 构建 → 验证 → 审查 → 交付/维护
```

### 定义

明确用户、问题、范围、非目标和成功标准。必要时先访谈或提问，不要用实现速度掩盖目标不清。

### 计划

把工作切成依赖清楚、可单独验证的切片。高风险未知要早暴露，任务太大就继续拆。

### 构建

让 Agent 按最小切片行动。每个切片都保留可观察的变更，避免一次覆盖大量不相关文件。

### 验证

根据任务选择测试、构建、运行、浏览器、视觉、来源、性能或安全检查。不要把“构建通过”当成所有维度都通过。

### 审查

检查目标是否满足、范围是否越界、证据是否足够、是否引入了维护负担或隐性风险。必要时使用新鲜上下文进行反向审查。

### 交付与维护

交付变更、证据、限制和下一步；把长期规则、来源和已知问题沉淀回项目上下文。发布后继续观察，不把一次通过当作永远正确。

## 2. 竖向切片

不要先把所有数据库做完、再做所有 API、最后做所有 UI。每个切片应该从输入到可观察结果走通一小段。例如“用户可以创建任务”应同时包含最小数据、接口、界面和验证，而不是留下多个无法运行的半成品层。

## 3. 检查点

在每两个或三个小任务后停下来检查：

- 是否仍然符合目标；
- 测试和运行是否通过；
- 变更范围是否扩大；
- 是否出现新的假设或冲突；
- 下一步是否仍然值得继续。

检查点不是降低效率，而是把错误发现从项目末尾提前到返工还便宜的地方。

## 一份完整的贯穿案例：审查一份 Markdown 章节

> **案例类型：** 填写示例，不是已经运行的日志。它用来展示如何把第 7、10、12、13、14 章的字段接成一条可执行路径；学习者运行时必须替换成自己的真实路径和命令。

### 目标与非目标

假设任务是：审查一份 Markdown 章节，修正已经确认的文档问题，检查本地链接，保留可审查的 diff，并完成本地提交前审查。

```text
owner: content-maintainer
target: docs/guide.md
goal: 让章节中的步骤、链接和验收描述彼此一致
allowed_scope: 只修改 docs/guide.md；只在本地读取和检查
non_goals: 不改代码；不安装依赖；不提交；不推送；不发布；不发送外部消息
```

输入只包括目标文件、项目规则文件、链接检查器（如果项目已经提供）和本次任务明确给出的缺陷清单。不读取秘密文件、客户资料或无关目录。若缺陷清单涉及一个易变的产品事实，先转到事实来源记录；不能把搜索结果直接写成正文。

### 能力选择与不选择

| 能力 | 本案例的决定 | 原因与边界 |
|---|---|---|
| Task Protocol | 使用 | 固定目标、范围、确认点和交付格式；不授予额外权限 |
| Workflow Orchestrator | 使用 | 管理阶段、依赖和 checkpoint；每阶段仍受本任务范围约束 |
| Evidence Review | 使用 | 把“链接检查通过”“只改了一个文件”等声明对回实际证据 |
| Research | 不使用 | 当前缺陷不需要新增外部事实；若出现事实争议，再单独建立来源记录 |
| 浏览器、connector、GitHub 写操作 | 不使用 | 本任务只需本地 Markdown 和本地检查；不应为了“顺手”增加外部副作用 |

选择原则是先选最小有效组合，再决定是否需要工具。Skill 被选中不等于它可以改变范围，也不等于任务已经完成。

### 阶段、依赖与退出证据

```text
定义 → 计划 → 构建 → 验证 → 审查 → 交付
  └──────每一步的退出证据成为下一步的输入──────┘
```

| 阶段 | 允许动作 | 主要风险 | 退出证据 |
|---|---|---|---|
| 定义 | 读取规则、目标文件和缺陷清单，确认目标与非目标 | 目标文件或缺陷范围不清 | 任务卡、读取清单、允许范围 |
| 计划 | 把缺陷分成可独立检查的两三个局部改动，列出依赖 | 顺手改到其他文件或引入新事实 | 计划、依赖顺序、待确认假设 |
| 构建 | 只编辑 `docs/guide.md`，每完成一小段就查看 diff | 文档改动扩大、破坏原有结构 | 实际 diff、checkpoint、改动文件清单 |
| 验证 | 执行已存在的链接检查和 Markdown/差异检查 | 把命令中断或静态检查当成完整正确性 | 命令、退出码、输出、未验证项 |
| 审查 | 用新鲜上下文阅读 diff，逐条对照目标和边界 | 只看摘要，漏掉越界或无来源断言 | 审查记录、问题清单或明确的通过理由 |
| 交付 | 输出摘要、证据、限制和下一步 | 把本地完成说成已提交或已发布 | 交付摘要；明确未 commit、未 push、未发布 |

依赖关系是：定义完成才能计划，计划确认后才能编辑，编辑产生 diff 后才能验证，验证结果进入审查，审查通过才适合交付。任一阶段缺少退出证据，就把状态保持为 `blocked` 或 `unverified`，不要继续堆叠下一阶段。

### Checkpoint、回滚与命令卡

开始前使用一个干净的临时副本，并记录 `git status --short`、目标文件的原始副本或内容 hash。注意：hash 只能证明文件是否变化，不能单独还原文件；需要回滚时还必须有原始副本、干净提交或其他明确恢复来源。

```text
CP0: 目标文件原始副本 + 工作树状态
CP1: 计划确认；此时不应有文件 diff
CP2: 局部编辑完成；保存 git diff -- docs/guide.md
CP3: 检查完成；保存退出码、输出和未验证项
```

本案例的命令卡如下。命令只适用于项目中确实存在对应脚本的情况；找不到脚本时停止并记录缺口，不要猜一个命令或自动安装工具。

```text
命令/动作：git status --short
工作目录：仓库根目录的临时副本
可能修改：无
联网/安装/外部写入：否
退出条件：确认目标文件和工作树状态

命令/动作：git diff --check；git diff -- docs/guide.md
可能修改：无
联网/安装/外部写入：否
退出条件：差异格式可读，且只包含允许文件

命令/动作：项目已提供的本地链接检查器
可能修改：无；不接受安装依赖作为前置动作
联网/安装/外部写入：以项目文档为准，默认不联网
退出条件：命令退出并保存输出；中断不算通过
```

回滚决策是：如果 CP2 的 diff 越界，先保存 diff，再回到 CP0 的副本重新开始；如果只是某个段落有问题，只撤销该段落并重新验证；不要在没有检查 diff 和恢复来源前执行覆盖式恢复命令。

### 进入实验 013 前：带走阶段与检查点

进入[实验 013：L3 贯穿式可审计运行](../labs/lab-013-l3-vertical-slice.md)前，把本节的生命周期压缩成一张阶段卡：

```text
current_stage: 当前阶段
stage_exit_evidence: 离开本阶段必须留下的证据
checkpoint_before: 本阶段开始时的状态/副本/hash
checkpoint_after: 本阶段结束时的 diff、日志或输出
stop_condition: 什么情况必须暂停
recovery_path: 暂停后从哪个 checkpoint 恢复或回滚
```

决策规则很简单：没有 `stage_exit_evidence` 就不能进入下一阶段；只有“Agent 说完成了”时，状态保持 `unverified`，并记录缺失证据。

### 交接摘要

贯穿案例结束时，交接记录至少写成这样：

```text
status: ready_for_local_review
owner: content-maintainer
scope: docs/guide.md only
inputs: docs/guide.md; project rules; existing link checker; defect list
assumptions: defect list is authoritative for this run; no new product fact is needed
actions_done: inspected; planned; edited one file; ran diff and link checks
actions_not_done: commit; push; publish; browser review; external fact refresh
evidence: CP0/CP2 records; git diff; command outputs; review notes
unverified: reader usefulness; rendered page appearance; facts outside the defect list
blocked_on: human review before any local commit
next_check: reviewer checks target file and evidence paths
permission_boundary: local reversible edit and read-only checks only
next_review: after the next source or chapter-structure change
```

### 三种结果与正确交付

- **正例：** diff 只有 `docs/guide.md`，链接检查和 `git diff --check` 都有退出码为 0 的输出，审查者能逐条找到目标与证据。此时可以说“本地审查准备完成”，不能说已提交或已发布。
- **失败例：** 链接检查指出一个目标不存在。保留失败输出，判断是目标写错、文件缺失还是检查器范围限制；只在原因明确时做最小修正，否则交付为 `blocked`，不靠猜测改链接。
- **边界例：** 检查器不存在、需要安装依赖、目标文件包含未经登记的产品事实，或临时副本不是干净状态。停止在对应确认点，记录缺什么证据；不要用安装、联网、扩大读取范围或推送来“完成”任务。

一个诚实的最终摘要应该是：

```text
已完成：审查并修改 docs/guide.md；实际 diff 已保存。
已验证：允许范围、diff 格式、本地链接检查（逐项列出命令和退出码）。
未验证：浏览器渲染、读者理解度、缺陷清单之外的外部事实。
未执行：commit、push、发布和任何外部写入。
下一步：人工审查证据后，再单独决定是否创建本地提交。
```

## 故意失败/边界实验

在构建完成但未运行验证时直接写“已完成”，再模拟一次命令卡住或模型容量错误。通过标准是交付中保留 checkpoint、未验证项和恢复路径，而不是继续堆叠修改。

## 迁移练习

把生命周期应用到一项非代码工作，例如研究报告或营销页面。为每个阶段写出进入条件、退出证据和不可越过的副作用边界。

## 来源与更新提示

具体入口、模型、工具和认证事实需要随产品更新复核；生命周期方法本身是稳定原则。当前产品事实以[官方 Codex 基线](../../docs/research/openai-codex-baseline.md)为准。

## 实验：同一需求的两种拆法

### Setup

选择一个低风险小功能或文档交付，准备脱敏输入、明确验收标准和临时分支/副本。禁止直接发布、推送、删除或修改生产环境；记录开始状态和允许变更范围。

### Task

选一个小功能，先写一份水平拆分计划，再写一份竖向切片计划。对比哪份计划更早产生可运行证据，哪份计划更容易定位失败。

### Evidence

保存两份计划、依赖图、每个切片的进入/退出条件、实际 diff、验证输出和 checkpoint 记录。通过条件是至少一个切片能独立产生可审查证据，并能指出未完成的阶段。

### Reflection

说明哪一个未知最早暴露、哪一个切片仍然过大，以及如果命令卡住或容量不足，应该从哪个 checkpoint 恢复。记录下一轮只会改变的一个拆分条件。

## 本章验收

学习者能为一个真实任务写出阶段、切片、依赖、验收和检查点；能解释为什么计划不是实现的替代品，为什么每个切片都必须保持可验证状态；能在执行中暂停并重新评估而不是盲目完成原计划。
