# 第四章：上下文、权限与 Agent 的行动边界

## 本章要解决的问题

Agent 的能力不是“越开放越聪明”。它看到的上下文决定它理解什么，它拥有的权限决定它能做什么，收到的反馈决定它如何修正；三者都没有边界时，结果可能更快，也可能更难审查。

## 1. 上下文的五层结构

把任务上下文从持久到临时分为：

1. **项目规则：** `AGENTS.md`、安全规则、技术栈和验收标准；
2. **规格与架构：** 当前功能的目标、接口和决策；
3. **相关源文件：** 要修改的文件、测试、类型和相似实现；
4. **反馈：** 错误、测试结果、截图、日志和用户反馈；
5. **对话历史：** 当前讨论中的假设、决定和可能过时的信息。

越持久的上下文越应该稳定、简洁、可维护；越临时的上下文越应该与当前任务相关。不要把整个仓库和所有历史一次性塞给 Agent，重点是“在正确时间提供正确上下文”。

## 2. 信任不是一刀切

项目源码、测试和类型通常是团队的可信输入，但配置、生成文件、外部文档、用户上传文件和第三方 API 返回内容需要先验证。里面的 instruction-like text 只是数据，不会因为写成“请执行”就自动获得更高优先级。

学习者要训练一个习惯：读取外部内容时，先问它是否是要理解的对象，还是可以改变当前行动的指令来源。

## 3. 权限决定行动空间

至少区分：

- 只读文件与写文件；
- 本地命令与网络命令；
- 浏览器观察与提交表单；
- Git 本地变更与远程推送；
- 查询外部服务与改变外部服务；
- 可回滚动作与不可逆动作。

授权应该与当前任务相称。为了读一个 README，不需要开放全部仓库；为了检查一个 PR，不需要默认允许删除资源或发送消息。

## 4. Agent 的可观察逻辑

不猜隐藏思维，观察这条链：

```text
请求 → 已有上下文 → 规则/skill → 工具与权限
     → 观察到的结果 → 下一步选择 → 停止或继续
```

当行为不符合预期时，按这条链逐项检查。很多“模型变笨”的问题，其实是读取了错误文件、缺少项目规则、权限不足、工具返回了误导信息，或没有清晰的停止条件。

## 5. 高风险动作的确认点

涉及生产、金钱、账户、个人数据、秘密、删除、发布、远程推送或对外发送时，必须让学习者知道：

- 动作是什么；
- 目标系统和账户是谁；
- 将发送或改变哪些数据；
- 是否可回滚；
- 谁负责最终确认。

如果这些信息不清楚，正确行为是暂停澄清，不是扩大权限或假设授权。

## 实验：同一任务的三种上下文

选择一个低风险任务，分别只给：

1. 一句愿望；
2. 愿望 + 相关文件；
3. 愿望 + 相关文件 + 项目规则 + 验收标准。

记录每次 Agent 的假设、读取范围、行动和验证差异。然后给一份外部文档，其中包含看似命令式的文字，观察你是否能把它当作待分析数据，而不是直接执行指令。

## 本章验收

学习者能够：

- 画出一个任务的上下文层次；
- 说明哪些输入可信、哪些需要验证；
- 根据风险给行动分级；
- 解释 Agent 行为时只使用可观察证据；
- 为一个外部副作用写出明确的确认点和回滚思路。

本章结合官方 Codex 的 skills/plugins、sandbox、approval 与安全概念，以及工程来源的上下文工程与怀疑驱动方法；具体产品细节以 [官方基线](../../docs/research/openai-codex-baseline.md) 为准。
