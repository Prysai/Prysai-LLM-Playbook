# 第 9 章：驗證、懷疑與復原

**狀態：** candidate。**實驗狀態：** not_run。本章說明如何讓完成宣告與證據對得上，
以及工作流程變得不確定時如何復原。公開報告和範例只是教學材料，不是本機重現、
官方根因分析、客戶工作成果或正式環境證據。

## 本章要解決的問題

Agent 可能會為錯誤、超出範圍、從未執行，或在錯誤環境中檢查的結果寫出看似可信的
完成摘要。可靠的做法不是盲信，也不是永遠懷疑；而是把摘要拆成一條條宣告，並為每條宣告
分配在其範圍內足以支撐它的最小證據。

![教學卡：在第一份缺失證據處停止，並用一項安全檢查復原](../../assets/teaching/evidence-recovery-ladder.svg)

> 這是專案自有的教學卡。它解釋一種審查方法；不證明某個 Skill、Agent、工具或外部服務
> 曾執行任何動作。

## 學習目標

完成本章後，你應該能夠：

- 把完成摘要拆成獨立宣告，並為每條選擇足夠且最小的證據；
- 區分 error、unverified、unknown、partial、not_observed 和 verified；
- 找到能力鏈中最後確認的階段與第一處無證據階段；
- 當一次執行失敗時保留狀態、縮小範圍、增加一項有用檢查，或清楚停下來；以及
- 寫出不誇大的交付說明，列出已完成工作、剩餘缺口和下一項安全檢查。

## 現實入口：重新取得控制，不等於證明結果正確

專案的 [Codex 現場研究](../evidence-library-ZHTW.md#source-notes) 記錄了容量中斷、
命令持續停在 Working，以及驗證擴大為持久重灌的報告。後續
[跟進研究](../evidence-library-ZHTW.md#source-notes)還記錄了工作階段可用
但目標工具未註冊，以及長請求最終報錯並重試的情形。

這些報告有用，是因為它們暴露了工作流程中可以觀察到的斷點；但它們不能證明普遍的服務原因、
適用於所有帳戶的修復方式，也不構成本機重現。用它們練習一個關鍵區分：重新取得一次執行的控制權，
不等於證明預期結果正確。

| 報告症狀 | 報告支持什麼 | 它不能證明什麼 | 第一個安全回應 |
|---|---|---|---|
| 所選模型不可用，任務停止 | 有報告者觀察到容量錯誤和任務中斷 | 佇列如何處理、伺服器端原因，或所有帳戶／版本的行為 | 暫停後續提示；重試前檢查 diff、日誌和最後接受的檢查點 |
| 格式化或驗證持續 Working | 該次執行沒有收到完成訊號 | 普遍死鎖、確切子程序或根因 | 設定有上限的等待時間，儲存輸出和程序狀態，只按復原規則中斷 |
| 工作階段可用但預期工具缺失 | 工作階段中的工具清單與任務預期不一致 | 每個提供商／版本都會暴露相同工具集 | 記錄實際工具清單；在操作檔案、瀏覽器或外部服務前停下 |
| 驗證變成強制重新安裝 | 「檢查結果」可能被誤解為允許改動持久環境 | 重新安裝永遠錯誤，或報告適用於所有 Agent | 分開記錄原始碼、測試、安裝、重啟、部署和線上驗證 |

下一步應由證據和授權來決定，而不是由等待了多久或狀態標籤看起來多麼「自信」來決定。

## 三份 Windows 報告：訊號不是證據

下列案例來自 2026-08-12 查閱的公開 GitHub 報告。它們是教學材料，
不是本機重現、官方診斷或普遍的 Windows 行為。

| 公開症狀 | 它可教什麼 | 第一個有界檢查 | 停在何處之前 |
|---|---|---|---|
| CLI 輸出超出終端視窗尺寸後無法從捲動緩衝區找回（[#35335](https://github.com/openai/codex/issues/35335)） | 視窗只是顯示結果，不是持久證據 | 將回應儲存或重新產生到具名檔案；記錄 CLI、終端和提示範圍 | 不要把視窗中看不到內容直接宣告為 Agent 或儲存庫資料遺失 |
| 非 BMP 字元貼上到 TUI 編輯框後消失（[#37578](https://github.com/openai/codex/issues/37578)） | 編輯框回顯不等於輸入完整 | 在傳送有後果的請求前，用無害測試字串比較預期與實際收到的字串 | 不要編輯、提交或傳送未被保留的輸入 |
| 很長的檢查點引用讓 Windows Git 報 bad ref 或 Filename too long（[#37559](https://github.com/openai/codex/issues/37559)） | Agent 內部狀態不等於一般專案狀態 | 在獲批的診斷範圍內記錄 git status、git show-ref、git fsck --full、git worktree list 和準確的 ref 路徑 | 未備份、未授權就刪除 .git 材料、修改 Git 設定、抓取或修復引用 |

詳見[Windows 輸入與證據現場問題](../evidence-library-ZHTW.md#source-notes)。
實用規則是：**重試前先保存最小的可持久化產物**——輸出檔案、收到的輸入對比、diff、雜湊、
命令日誌或去識別化的交接。社群變通方法可以幫助分診，卻不是官方修復，也不授權持久環境改動。

### 現場案例：命令完成，宣告仍可能不可審查

邊界案例 [FC-EVIDENCE-01](../evidence-library-ZHTW.md#source-notes)
使用 issue #34951 區分執行與審計證據。該 issue 仍公開、沒有維護者診斷，也未在此復現。
如果必要的輸出被隱藏或缺失，只保留已獲授權的退出碼、事件、diff、產物、雜湊或回讀證據；
把審計宣告標為 unverified，並寫明缺失的通道。不要只為找回顯示內容而重跑有後果的動作、
削弱安全控制，或把成功形狀的狀態推斷為真實結果。

## 1. 讓宣告和證據對得上

先寫出你想說的那句話，再問：另一位審閱者需要檢查什麼，才能在已宣告的範圍內接受它？

| 宣告 | 支撐該範圍的最低證據 | 仍在宣告之外的內容 |
|---|---|---|
| 檔案發生變更 | diff、具名路徑或雜湊 | 改動是否正確或完整 |
| 檢查通過 | 精確命令、工作目錄、退出碼和相關輸出 | 另一環境也會有相同行為 |
| 應用可以執行 | 實際啟動，並觀察一條明確命名的關鍵路徑 | 視覺品質、安全、使用者價值或正式環境就緒 |
| 頁面看起來正確 | 在指定視窗尺寸下進行瀏覽器或截圖審查 | 無障礙、所有斷點、後端行為或轉換 |
| 事實來自官方來源 | 權威 URL、查閱日期、範圍和複核負責人 | 目前帳戶或執行時具有相同能力 |
| 沒有暴露秘密 | 針對本次改動的掃描、環境檢查與邊界說明 | 未知外部系統從未收到秘密 |
| 結果幫助使用者 | 已定義樣本、任務和使用者驗收記錄 | 普遍市場成功或未來結果 |
| 結果已達到正式環境就緒 | 品質、安全、維護、發布和回滾門禁 | 未測試的環境或無人負責的未來改動 |

### 在 Lab 013 之前：寫一張宣告—證據對照表

在進入 [Lab 013：可審計的垂直切片](../labs/lab-013-l3-vertical-slice-ZHTW.md) 前，
將「完成」拆成可檢查的行。每行只可由其宣告範圍內的證據支持：

~~~text
assertion: 我到底在宣告什麼？
scope: 該宣告覆蓋的檔案、命令、執行、版本或環境
evidence: 路徑、命令輸出、日誌、截圖、來源或審查記錄
status: verified / partial / unverified / blocked / not_run
gap_or_next_check: 缺什麼，以及增加證據的最小方式
~~~

不要用一次 diff 去證明測試通過，也不要用登入頁面去證明權杖交換或外部動作成功。證據缺失時，
按情況標為 unverified、blocked 或 not_run，保留缺口並進入復原流程。

## 2. 用懷疑來選擇下一項檢查

對一個重要決策，寫出一條短宣告，然後暫時把它從自己的推理中拿掉：

- 哪個前提沒有證據？
- 哪個邊界條件沒有覆蓋？
- 結果會不會來自 mock、快取、過期檔案或錯誤環境？
- 若宣告為假，最先會在哪裡可見？
- 哪一項最小額外檢查可能改變決策？

目標不是無止境地懷疑，而是在交付前儘早發現代價高昂的錯誤。一項好的檢查只改變一個相關
條件，產生可觀察結果，並帶有停止規則。

### 狀態標籤不是完成檢查

| 宣告 | 最低證據 |
|---|---|
| 「原始碼改了。」 | 指定路徑的 diff 或檔案比較 |
| 「檢查跑過了。」 | 精確命令、工作目錄、退出碼和輸出 |
| 「應用能用。」 | 指定環境和輸入下的執行時觀察 |
| 「頁面看起來正確。」 | 指定視窗尺寸的渲染檢查與視覺標準 |
| 「功能已交付。」 | 儲存庫或部署狀態、發布記錄和交付後檢查 |

最後一句比前四句都強。建置通過當然有價值，但不會自動成為執行時、視覺、安全或使用者驗收
證據。

## 3. 按有邊界的順序復原

當事情失敗或變得不清楚時，按此順序：

1. 保留精確錯誤和目前狀態；
2. 分類可能邊界：輸入、理解、環境、實作、能力、權限或驗證；
3. 縮小範圍並復現最小可觀察斷點；
4. 做一次最小修復，或增加一項定向檢查；
5. 重跑受影響路徑並記錄新證據；
6. 失敗仍不清楚時，停止並交付精確阻塞說明；
7. 只有證據支持時，才擴大權限、範圍或重試預算。

不要用「再跑一次」、「多給權限」或「讓模型再想一遍」來代替診斷。

### 能力鏈：每個階段成功都需要獨立證據

公開報告反覆出現一種容易誤導的順序：工具名稱出現在清單裡、網頁可以讀取、提供商接受設定，
而真實發現呼叫、點選或更高層能力依然失敗。可見工具名只證明名字可見；不證明註冊、
可發現、執行或副作用成功。

~~~text
工具或 Skill 可見
  → 一次只讀發現呼叫可執行
  → 可讀取目標狀態
  → 目標動作返回成功
  → 確認預期外部狀態變化
~~~

每一步都需要獨立證據。讀 DOM 不證明點選成功；解析設定不證明後端能力可用；一次成功啟動
不證明下一個視窗、版本或帳戶有相同能力。誠實交接可以寫「唯讀檢查已驗證；提交未驗證」，
這比「工具能用」更有價值。

### 斷點卡：在第一層沒有證據處停止

不要先猜根因。找出最後通過的宣告，以及第一條失敗或未觀察到的宣告。為單次執行儲存：

~~~yaml
run_id: "唯一執行標識"
surface: "實際工作面及版本"
expected_capability: "本次執行所需的最小能力"
chain:
  - stage: "入口／工作階段可用"
    observation: "可觀察事件或錯誤"
    status: "passed | failed | not_observed"
  - stage: "工具已註冊且可發現"
    observation: "工具列表或只讀發現結果"
    status: "passed | failed | not_observed"
  - stage: "目標狀態可讀取"
     observation: "唯讀目標、帳戶、路徑或視窗證據"
    status: "passed | failed | not_observed"
  - stage: "目標動作返回"
    observation: "結果、退出碼或錯誤類別"
    status: "passed | failed | not_observed"
  - stage: "預期副作用已確認"
    observation: "目標狀態、diff 或回讀結果"
    status: "passed | failed | not_observed"
last_confirmed_stage: "最後通過階段"
first_breakpoint: "第一處 failed 或 not_observed 階段"
safe_next_check: "只改變一個條件的最小檢查"
stop_condition: "何時不擴大權限或副作用而停止"
~~~

工具名稱可見而唯讀發現失敗，斷點就是「工具已註冊且可發現」；動作回傳成功而目標狀態沒有變化，
斷點就是「預期副作用已確認」。不要越過斷點去做更高風險的動作，也不要事後拿後面的偶然成功
去補早期證據。

### 長時間等待卻沒有事件：先記錄時間線

「介面仍顯示 Working」是一項觀察，不是根因。長請求至少記錄：

~~~text
request_started_at
first_event_at
each tool or network event
last_event_at
interrupt or error time
automatic retry start time
final state
~~~

到達預先同意的無事件閾值時：

1. 標為 no_event_observed；不要把它改寫成根因或「任務運作正常」；
2. 用已獲授權的方式重新取得控制，再檢查程序、工作樹、目標狀態和最後檢查點；
3. 第一次請求可能已有副作用時，按 unverified 或 blocked 停止；
4. 只有在動作具冪等性、狀態已經複查，且重試規則在執行前已宣告或某個條件已明確改變時，
   才允許一次有限重試；
5. 將客戶端自動重試記錄為獨立事件。第二次成功只證明第二次，不能把第一次無事件
    改寫為初次通過。

HTTP 狀態、長上下文、網路等待、模型推理或上游服務故障可以是待測假設；沒有官方確認
或本機重現時，它們不是已建立的根因。

## 4. 把復原狀態和完成狀態分開

使用描述真實證據的狀態詞：

- practice：學習執行；不得複用為生產證據；
- candidate：結構或輸出有希望，但評估或來源審查未完成；
- verified：在宣告範圍、版本和任務集內有證據；
- production-ready：品質、安全、回滾、維護和發布門禁均通過。

觀察狀態不同於完成狀態。not_observed 表示沒有看到預期事件，不是根因診斷；not_run
表示計劃實驗尚未執行，不是通過或失敗；partial、unverified 與 blocked 描述目前能支持
的最窄證據缺口。

復原可以重新取得控制，卻不會自動升級完成狀態。例如，中斷一個掛起程序並儲存 diff，可能形成有用
的 candidate 交接，但所需的執行時結果仍然是 unverified。

### Codex 現場差異：工作面可見，但能力不可用

公開報告描述了可見的 Computer Use 和 node_repl 工作面；在這些工作面上，只讀的 list_apps() 或
list_windows() 呼叫會出現 spawn EPERM；瀏覽器彈窗與 DOM 可讀，但點選超時；以及
自訂提供商可接受設定，卻未必暴露預期的多 Agent 能力。這些是 2026-08-10 使用者報告，
不是本機重現，也不是官方根因分析。參見[網頁現場研究](../evidence-library-ZHTW.md#source-notes)
中的 WF-08—WF-11。這個帶有產品名稱的例子不屬於上面定義的通用範圍。

## 實驗：審計一條完成宣告

**實驗狀態：** not_run。

### 準備

準備經過去識別化的完成摘要、diff、測試輸出、來源連結和一項刻意缺失的證據。不要連線正式環境服務
或改動外部系統。把每句完成宣告拆為獨立主張，並在審查前決定允許的狀態詞。

### 任務

使用 [Lab 003](../labs/lab-003-evidence-review-ZHTW.md) 把摘要變成宣告表。為每一行寫清楚範圍、
證據、狀態與下一步；隨後刻意加入「全部測試通過」這類沒有證據的句子，觀察審查是否拒絕它，
而不是接受摘要的語氣。

### 證據與覆盤

儲存宣告表、每項宣告的證據路徑、缺口類別、審查決定和復原或補充計劃。至少包括一條
事實宣告、一條執行時宣告和一條使用者效果宣告，說明為什麼一份弱證據不能代替三者。
記錄最容易藏在漂亮摘要裡的宣告、最小卻最能降低風險的檢查，以及為什麼 unverified
不等於 wrong；再把下次交付說明的一句話改寫成與證據相稱的狀態。

## 刻意失敗與邊界案例

在可丟棄副本中開始一項小而可逆的改動。在執行檢查前，先寫一份聲稱「完成」且「全部測試通過」的
交接；然後揭示測試輸出從未產生，或擬議復原需要安裝、重啟、網路呼叫，或寫入原範圍外。

只有學習者做到以下各項，練習才算通過：

- 把無證據宣告標為 unverified 或 not_run；
- 保留部分 diff、錯誤、範圍和最後檢查點；
- 拒絕從 diff 推斷執行時或使用者驗收；以及
- 選擇一項安全檢查或清楚停下來，而不是堆疊編輯或靜默擴大權限。

## 遷移練習

把宣告表用於研究結論或行銷實驗報告。至少寫一條事實宣告、一條執行宣告和一條使用者效果
宣告；解釋為什麼三者不能共用一份薄弱證據，並為最缺乏支持的宣告命名最小後續檢查。

## 來源與維護邊界

證據紀律和狀態詞彙是穩定方法；命令、入口、模型行為、提供商行為和公開 issue 狀態是
易變事實。具體操作應對照[評測框架](../evidence-library-ZHTW.md#method-and-status)、
[官方基線](../evidence-library-ZHTW.md#source-notes)和
[網頁現場研究](../evidence-library-ZHTW.md#source-notes)。

## 驗收清單

- [ ] 我能為來源、測試、執行時、視覺、安全和使用者效果宣告選擇不同證據。
- [ ] 我能區分錯誤、無證據結果與僅僅未知的結果。
- [ ] 我能定位能力鏈的最後確認階段和第一處斷點。

- [ ] 我能寫出包含已完成、未完成、未知、風險、證據路徑和下一項安全檢查的交付說明。
