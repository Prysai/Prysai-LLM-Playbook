# 第 20 章：构建个人 Codex 工作系统

> `content_status: candidate`
> `experiment_status: draft / not_run`
> 本章介绍一种可迁移的方法，不把某个产品的记忆、自动加载或入口行为当作永久前提。

## 本章要解决的问题

很多人每次重新打开 Codex，都要从头再解释一遍项目、目标、术语、约束和验收标准。结果就是上下文不一致、决策无法追溯、过时命令被反复复用，而有用的经验无法带进下一项任务。更严重的风险是：把个人随手记录当作记忆库，把 token、密码、Cookie、客户文本或未经确认的结论放进去。

## 真实问题入口

FP-10（验证或格式化命令可能看起来会卡住）和 FP-11（验证被描述为扩展成未经授权的持久环境变更）是公开用户问题研究中的报告条目。它们不是本地复现，也不是普遍的根因结论。本章借助它们来追问：个人工作系统是否会暴露过时命令、记录停止点，并阻止范围在未获授权的情况下扩大。

## 学习目标

学完本章，你应该能够：

- 区分项目规则、任务上下文、当前状态、可复用模板和反思记录；
- 为重复性工作构建一个小巧、可清理、可追溯的个人工作包；
- 使用固定输入、哈希、运行日志和证据完整性，比较系统辅助路径与基线路径；
- 判断何时保留任务协议、创建 Skill 候选、继续观察或阻塞工作；
- 发现过时上下文，并在不存储秘密的前提下把有用的做法迁移给其他人。

## 概念：五种资产，五种不同的职责

| 资产 | 它回答的问题 | 生命周期 | 不放什么 |
|---|---|---|---|
| 项目规则 | 这个项目必须始终遵守什么？ | 有版本管理、有意变更、定期复核 | 临时猜测和个人秘密 |
| 任务上下文 | 这次必须完成什么？ | 为任务而建，任务结束后归档 | 无关的历史 |
| 当前状态 | 已读、已改、已验证或被阻塞了什么？ | 在每个检查点更新 | 把计划当作结果 |
| 模板 | 相似任务应如何开始和交付？ | 反复实践后提炼 | 未经验证的永久结论 |
| 反思记录 | 什么有效、什么失败、下次应改变什么？ | 只保留可迁移的经验 | token、密码、Cookie、客户文本或不必要的个人数据 |

上下文并非越多越好。相关性、可信度、敏感性和时效性比长度更重要。

## 决策：创建 Skill 还是保留任务协议？

在创建可复用资产之前，先完成这张决策卡。仅凭重复是不够的。

| 观察到的情况 | 决策 | 所需证据 |
|---|---|---|
| 请求是一次性的，或输入与输出仍在变化 | 保留任务协议 | 一次任务的输入、约束、决策和交付记录 |
| 输入、决策点和输出稳定，并且同时有正例和失败例 | 创建 Skill 候选 | 至少三次运行、一个失败集合和一项迁移任务 |
| 方法有用，但触发边界或副作用不清楚 | 继续观察或阻塞 | 缺口记录、风险说明和待验证项 |
| 涉及秘密、外部写入或生产发布，且授权或回滚不清楚 | 阻塞 | 权限矩阵、人工批准点和回滚计划 |

至少要记录 `decision_id`、重复任务、候选资产、稳定输入、失败类型、证据位置、负责人、`next_review` 和 `decision_action`。一次偶然的成功绝不能成为创建 Skill 的理由。

## 行动：组装最小的个人工作包

从五种记录开始：项目地图、任务协议、状态日志、证据索引和反思记录。启动时检查规则、分支、当前状态和权限；执行中只携带必要的上下文；交付时把确实已验证的工作与仍然未完成的工作分开；反思时提炼出另一个人能够理解并检验的规则。

一份有用的交付记录包括：

- 已完成的事项和变更过的文件；
- 实际运行过的命令、测试或检查，以及相应的结果和退出码（适用时）；
- 未验证、被阻塞或超出授权范围的事项；
- 风险以及具体的恢复方法；
- 下一次复核或决策的负责人。

产品会不会记住什么、会加载哪些文件、入口如何表现，都是易变的产品事实。请查阅当前的第一方文档和实际获授权的界面；不要把个人习惯变成对产品的保证。

## 实验：建立个人工作系统

这是在可丢弃副本中进行的离线对比。它不得连接生产环境、发送消息、发布内容、读取真实秘密或产生外部写入。

### 准备

创建一个临时副本和基线，命名为 `personal-system-triage-v1`。使用下面这份固定的、已脱敏的输入：

```text
待分类项目：
1. “按钮在窄屏上溢出。”已有截图；尚未做任何修复。
2. “构建通过。”只有命令退出码；没有用户验收。
3. “认证失败。”缺少版本、入口和错误日志。
4. “文案需要更新。”缺少受众和来源。
```

使用下面这份固定的任务文本：

> 把四个项目分别分类为“需要更多输入”“可以执行”或“需要人工确认”。不要虚构缺失的版本、权限或用户验收。对每个项目，写出下一步和所需证据。

在任一路径运行之前，先保存输入哈希和干净临时副本的哈希。创建空白记录，命名为 `project-map`、`task-protocol`、`state-log`、`evidence-index` 和 `reflection`。不要把 token、密码、Cookie、客户文本或不必要的个人数据放进去。

### 任务

1. **基线 A：**只提供固定的任务和输入，不使用个人工作系统的五种记录。
2. **候选 B：**使用五种记录，把工作包标记为 `personal-system-v1`，并记录读取、变更、验证、未验证和被阻塞的内容。
3. 每条路径各运行两次。每次运行前都恢复相同的输入和临时副本基线。使用 `run-id` 值 `20-personal-system-triage-v1-A-01`、`A-02`、`B-01` 和 `B-02`。
4. 不得连接、写入、发布或读取秘密。如果任务需要其中任何一项动作，就把这次运行标记为 `blocked`；不要从模拟中推断可用性。

### 证据门

每次运行保存一条记录：

```yaml
run_id: "20-personal-system-triage-v1-B-01"
task_id: "personal-system-triage-v1"
system_version: "none | personal-system-v1"
input_hash: "sha256:..."
baseline_hash: "sha256:...; 已恢复的临时副本基线"
context_files: ["project-map", "task-protocol", "state-log", "evidence-index", "reflection"]
clarification_rounds: 0
actual_changes: "无变更或文件/diff 摘要"
validation: "检查、结果和退出码；未执行则为 not_run"
evidence_items: ["输入", "分类", "缺输入的理由", "下一步", "验证", "未验证说明"]
evidence_completeness: "0/6"
rework_count: 0
log_location: "evals/results/；没有运行则为 not_run"
reviewer: "独立复核角色；没有则为 not_assigned"
unverified_items: ["实际入口行为", "账户级权限", "运行时结果"]
status: "pass | fail | not_comparable | blocked | not_run"
```

对比表必须包含重复解释次数、澄清轮数、发现缺失输入所用的时间、返工次数、证据完整性、分类错误和实际耗时。证据完整性是可以核对的六项必需材料所占的比例。如果基线或输入哈希不一致，就使用 `not_comparable`；不要把这种差异称为改进。

只有当四份日志全部完整、没有发生秘密或外部副作用，并且分类与停止理由符合验收清单时，候选路径才有资格获得实验通过。即便如此，结果也不会让该 Skill 变成 `verified`。

### 失败案例与边界

把一条故意过时的命令和一个旧目录作为静态 fixture 数据加入项目地图。正确的行为是检查当前状态、把相关记录标记为过时、停止复用旧命令，并在状态日志中记录这个缺口。如果学习者复制了过时记录、虚构认证细节、扩大权限，或把计划当作验证，实验即告失败，并保留失败日志。

### 反思

在 `reflection` 记录中回答以下问题：

- 哪一项上下文真正改变了决策？
- 哪条记录已经过时？
- 还有哪些证据仍然缺失？
- 什么解释了基线与候选路径之间的差异？
- 下次应该删除、保留或更新什么？
- 这条经验能迁移到另一个领域吗？它的限度在哪里？

回答之后更新决策卡。“记住要小心”不是一条可迁移的规则。

## 边界与常见错误

- 不断膨胀的上下文会把旧事实与新目标混在一起。
- 个人记录不是秘密存储，也不能替代权限复核。
- “命令启动了”不等于验证完成；“这个账户以前用过”也不能证明当前的入口和范围正确。
- 对一次性请求，任务协议通常比新建一个 Skill 更轻。
- 没有独立复现、失败集合和迁移证据，Skill 就仍然只是 `candidate`。
- 一个已配置的产品功能、一段被记住的对话或一次成功的构建，本身都不能证明当前的运行时行为、团队影响、部署或用户验收。

## 迁移任务

把一个稳定的个人工作流交给另一位成员。第二个人只能使用项目地图、任务协议和证据索引，并且必须在可丢弃副本中工作，不能有任何口头补充。保存输入哈希、运行日志、diff、验收结果和缺失证据清单。记录哪些隐性知识没有被写下来，然后决定修订哪份资产。

## 验收清单

- [ ] 我能区分规则、任务上下文、状态、模板和反思。
- [ ] 我的记录里没有 token、密码、Cookie、客户文本或不必要的个人数据。
- [ ] 我能在相同的输入和基线下比较两条路径。
- [ ] 每次运行都有 `run-id`、日志、证据完整性数值和未验证项清单。
- [ ] 我能区分创建 Skill、保留协议、继续观察和阻塞。
- [ ] 我能识别过时命令并描述一种恢复方法。
- [ ] 另一个人可以在没有口头补充的情况下复现关键判断。

## 来源与维护边界

上下文、证据和反思方法属于项目方法论。产品入口、Skill 的调用与分发、自动加载、权限模式和产品功能是会变化的事实。以下记录界定了来源边界；它们不能证明每个账户或每个运行时的行为。

```yaml
- claim: "Skill 的调用与分发必须对照当前官方的 Skills 与 Plugins 文档以及获授权的入口进行核查"
  source: "https://learn.chatgpt.com/docs/skills-and-plugins.md"
  checked_at: "2026-08-09"
  applies_to: "官方文档所声明的产品入口、账户范围和组织范围"
  owner: "课程维护者"
  next_review: "2026-11-09"
  claim_status: "current"
- claim: "权限与批准边界取决于操作界面、sandbox 和批准配置；不能从单次会话推断"
  source: "https://learn.chatgpt.com/docs/permission-modes.md"
  checked_at: "2026-08-09"
  applies_to: "官方文档所声明的操作界面和配置范围"
  owner: "安全与课程维护者"
  next_review: "2026-11-09"
  claim_status: "current"
```

本章刻意不声称存在记忆功能、会自动保存某一类内容，或对特定账户可用。如果日后要加入这样的说法，它需要直接的来源、范围、访问日期、负责人和复核记录。本章状态保持 `candidate`；实验保持 `draft / not_run`。
