# 第 10 章：計画と垂直スライス

**状態：** `candidate`。計画と例は教材用です。Agent が実際に作業を実行したことや、どのリポジトリでもこの分割方法が機能することを証明するものではありません。

## この章が解決する問題

詳しく見える計画でも、最後まで誰も結果を確認できないことがあります。データ、API、UIを順番にすべて仕上げる横割りの計画では、前提の間違いに気づくのが遅れます。垂直スライス（vertical slice）は、入力から確認できる根拠までを一つにつなげた、小さな成果を作ります。

```text
one input → smallest change → observable action → focused check → evidence
```

これは一度に全部を変える口実ではありません。レビューと切り戻しができる範囲に収めながら、最も高くつくリスクを早く見つける方法です。

![教案例：lifecycle checkpoint が大きな目標を証拠のある出口へ分ける](../../assets/teaching/locales/ja/lifecycle-checkpoints.svg)

> これはプロジェクトが作成した教材カードです。計画方法を説明するものであり、Agent、
> Skill、コマンド、外部サービスが実行された証拠ではありません。

## 学習目標

大きなプロジェクトを、小さく観察できるスライスに分けます。編集前に依存関係と停止点を記録し、失敗した試行も、次の人が範囲や権限を推測せずに続けられる形で引き継ぎます。この練習だけで、一般的な作業速度、モデルの品質、長期的な学習効果を測ることはできません。

## 現実の問題：詳しい計画でも確認できる結果が出ない

計画にたくさんのファイル、段階、ツールを並べても、誰かが確認できる最初の状態が示されていないことがあります。リスクは、長く連なった仮定の中に隠れます。存在しないファイル、不明な権限、曖昧な受け入れ条件が、確認できない作業を積み重ねた後で初めて現れるのです。垂直スライスでは、次に見える一歩を止める依存関係を先に確かめます。

長時間の Agent 作業に関する公開報告では、容量エラーのあとに何が完了したのか分からなくなったり、
formatter や validation が `Working` のまま完了通知を返さなかったりする例が出ています。
コミュニティの議論からは、会話の中だけでなく TODO、計画、状態を外に記録しておく必要も見えてきます。
これらは製品全体の原因を断定する材料ではありません。計画を観察可能にするための入力として扱います。

| 報告された症状 | evidence が支えること | 証明しないこと | 計画上の対応 |
|---|---|---|---|
| 長いタスクの途中でモデルが使えなくなった | 作業が中断され、途中の状態が不確かなまま残ったという観測 | サービス側の原因、キューの挙動、すべてのアカウントでの再現 | 新しい指示を止め、作業ツリー、最後の出力、チェックポイントを確認してから、スライスを一つだけ再試行する |
| formatter または validation が `Working` のまま | その実行では役に立つ完了通知が得られなかった | 常に起きるデッドロック、正確な子プロセス、根本原因 | 「進展なし」とみなす時間を決め、標準出力・標準エラー・終了コード・変更ファイルを保存する |
| 複雑なタスクでは TODO と計画を見える場所に置きたい | 外部に状態を残すと長い作業を追いやすいという利用者の報告 | すべてのモデルやタスクで、見える計画が改善をもたらすこと | 判断の要約、差分、チェック結果、次の行動を必須にし、スピナー表示を納品の根拠にしない |

計画は Agent が最後まで終える約束ではありません。人が一時停止し、状態を確認し、次の判断を下すための
操作面です。

## 編集前にスライスを設計する

| 項目 | 答える問い |
|---|---|
| 結果（outcome） | 最後に、誰が何を確認できるか |
| 入力（input） | どのファイル、データ、判断を固定するか |
| 境界（boundary） | どのファイル、権限、副作用を許可するか |
| 最小の変更 | 結果を生む最小の変更は何か |
| 確認（check） | どのコマンド、検査、読み戻しで不合格と判断できるか |
| 根拠（evidence） | どの差分、出力、スクリーンショット、レビューを残すか |
| 未証明（not proven） | 何が範囲外に残るか |
| 復旧（recovery） | 最後に受け入れた状態へどう戻すか |

良いスライスは、判断できる問いに答えます。「ナビゲーションを全部移行する」では、何をもって成功とするか分かりません。「一人の読者が日本語の目次からローカルの章を開き、練習を見つけ、記録した経路で戻れるか」なら確認できます。

### 1. 作業名より先に結果を決める

利用者、レビュー担当者、後続システムのいずれかが確認できる一文から始めます。

> 新しい貢献者が1ページを読み、ネットワークなしでローカルチェックを1つ実行し、
> 合格か不合格かを確認できる。

「ドキュメントのパイプラインを作る」と書くより、この結果カードに直した方が、計画で守るべきものがはっきりします。

```text
Outcome: いま、誰が何を実行または確認できるか
Inputs: ファイル、データ、仮定、前提条件
Allowed actions: 許可する対象と変更の種類
Non-goals: 今回は意図的に後回しにする作業
Evidence: 差分、コマンド出力、テスト、スクリーンショット、レビュー記録
Risk: 秘密情報、外部呼び出し、永続化、削除、取り消せない変更
```

将来の機能をすべてそろえないと観測できないなら、結果をさらに小さくします。

### 2. 依存関係を wish list ではなく事実として描く

依存関係とは、「次の行動で意味のある結果を出す前に、これが成立していなければならない」という意味です。
各項目について、次を答えます。

1. **Depends on:** 先に存在していなければならない正確な状態や根拠は何か。
2. **Provides to:** 次のスライスに渡すファイル、項目、コマンド結果、判断は何か。
3. **Blocked by:** 安全に推測できない、足りない入力は何か。
4. **Dependency check:** 読み取り専用で最も低コストに確認する方法は何か。

たとえば `database → API → UI → deployment` という流れを、次のような根拠の鎖に置き換えます。

```text
Slice A: fixed sample record を local に読める
  provides: sample data shape と passing read check
Slice B: read-only endpoint がその record を返す
  depends_on: A; provides: observable API response
Slice C: 一つの screen が endpoint response を render する
  depends_on: B; provides: user-visible path
Slice D: disposable build で path を確認する
  depends_on: C; provides: build output と reviewable diff
```

矢印が表すのは、Agentの隠れた記憶ではなく、根拠と受け渡しの接点です。確認していない依存関係は、
黙って成立したことにせず、`assumed` と明記します。

### 3. 計画の形を選ぶ

| 形 | 得意なこと | よくある失敗 | 使う場面 |
|---|---|---|---|
| 横割り | 技術層、担当者、リリース前提を一覧にする | 最初の利用者向け結果が、多くの層の後ろに隠れる | 能力マップや担当範囲をレビューするとき |
| ファイル／順序ベース | 編集箇所を特定し、小さな差分を保ちやすい | リポジトリの順番が、利用者価値の順番になってしまう | 変更内容が理解済みで、本当に局所的なとき |
| 垂直 | 入力から確認できる結果までの細い経路を証明する | 最初のスライスが「機能全体」になってしまう | 早いフィードバック、可逆な実験、引き継ぎが必要なとき |

垂直スライスは「バックエンドの小さな一部」ではありません。1つの結果を示すために必要な境界だけを
横断し、余分な磨き込み、将来の抽象化、本番データは持ち込みません。

まだ答えるべき問いが決まっていないなら、探査（probe）を使います。依存関係の有無を読む、サンプルを1つ表示する、
無害なツール呼び出しが目的の対象に届くか確かめる、といった読み取り専用または可逆な調査です。
探査の成果は「続行・範囲を狭める・停止」の判断であって、機能の完成ではありません。

### 4. タスクの山ではなくスライスカードを使う

```text
slice_id: S-01
outcome: 一つの observable user/team result
depends_on: 先に必要な exact state、file、evidence
provides_to: 次の slice に渡す input または decision
inputs: named files、fixtures、versions、assumptions
allowed_actions: この slice で許可する path と action class
non_goals: change、install、publish、infer しないもの
change_budget: expected files、commands、external effects
acceptance_evidence: passed と呼ぶための exact proof
failure_signal: failed または stalled run の見え方
stop_condition: state を保存して decision を求める条件
recovery: 最小の安全な retry または rollback
handoff: status、evidence path、remaining risk、next action
```

この項目は、「人がXできる」という結果を「AgentがYとZを編集した」という話にすり替えないためにあります。
ファイルは実装の根拠であって、自動的に納品の根拠になるわけではありません。

### 5. 変更予算とチェックポイントを決める

実行前に、意図的に狭い変更予算を決めます。

- 変更してよいファイル。
- 実行してよいコマンド。
- 再試行の最大回数、または「進展なし」とみなす時間。
- ネットワーク、認証情報、インストール、永続状態を使ってよいか。
- 取り消せない操作の前に必要な人の確認。
- スライスが止まったときに保存する成果物。

これはトークン数の予測ではなく、副作用の境界です。予算外のファイル、新しい依存関係、本番用の認証情報、
別のリポジトリが必要になったら、そこで止めて計画を更新します。

各チェックポイントには、少なくとも次を残します。

```text
goal and current slice:
completed actions and evidence:
worktree / branch / target path:
files changed and baseline comparison:
last command, output, and exit status:
permission and external-effect state:
open assumptions or blockers:
next single action:
```

チェックポイントはAgentの短期的な会話の外に保存します。小さなMarkdown、Issueメモ、承認済みのタスク記録で十分です。
秘密情報、Cookie、トークン、非公開の認証情報は入れません。

### 6. スライスが本当に小さいか判断する

タイトルに独立した利用者向けの結果が複数含まれている、実装と移行・リリースが混ざっている、
受け入れを判断する人が複数必要、最初の切り分け地点がない――このどれかなら大きすぎます。最初の
役に立つ根拠が最後まで出てこないなら、分割します。

逆に、読めない、実行できない、レビューできない孤立したファイルだけを作るなら小さすぎます。
最も近い、観察できるスライスと合わせます。ただし、リファクタリング自体を探査として試す場合は例外です。

> 会話に参加していなかったレビュー担当者が成果物を見て、「何が変わり、どう確認し、何が未証明で、次に何を安全にできるか」を答えられるか。

答えられなければ、スライスにもっと良い受け渡し口を作るか、結果をさらに小さくする必要があります。

## 依存関係を起点に計画する

1. ツールを選ぶ前に、結果と受け入れ条件を書く。
2. 入力、依存関係、権限、まだ分からない事実を列挙する。
3. 結果を止める可能性がある不明点を最初に置く。
4. 失敗しても根拠が残るスライスを選ぶ。
5. 確認の順序と停止条件を決めておく。
6. 各スライスの後に、差分、範囲、根拠、次の判断をレビューする。

タスクリストを約束だと思わないでください。タスクを実行しても、望んだ結果が出るとは限りません。計画では前提を見えるようにし、安心させる言葉の陰に隠さないことが大切です。

## 小実験：安全なスライス一つで三つの計画を比べる

この実験では、ネットワーク、インストール、認証情報、コミット、プッシュ、デプロイ、本番データを
使いません。他の人の変更が入った作業ツリーではなく、一時ディレクトリを使います。

### 準備

リモート接続、秘密情報、外部アカウントを使わない、ローカルの使い捨てコピーを用意します。短い原文、既知の変更、固定した受け入れ確認の問いを選び、基準リビジョンを保存します。始める前に停止規則を決め、インストール、公開、送信はしません。

一時ディレクトリに、次のような README.md を作ります。

```markdown
## Slice Lab

Starting point. The page does not yet explain what changed or how to check it.
```

受け入れ条件は小さく固定します。読者が `What changed` と `How to verify` の2つの見出しを見つけられることです。
PowerShellで行う読み取り専用のチェックは、次のとおりです。

```powershell
$text = Get-Content -Raw README.md
$required = '# Slice Lab', '## What changed', '## How to verify'
$missing = $required | Where-Object { $text -notmatch [regex]::Escape($_) }
if ($missing) { $missing | ForEach-Object { "MISSING: $_" }; exit 1 }
'PASS: required headings found'; exit 0
```

### やること

同じ目標に対して、7項目以内の計画を3種類書きます。

1. 執筆、ツール、レビュー、リリースに分ける横割りの計画。
2. 触るファイルの順番で並べるファイル順の計画。
3. 最小限の「読めて確認できるページ」を先に作る垂直計画。

各項目に結果、依存関係、根拠、停止条件を付け、垂直計画の最初の項目だけを実行します。2つの見出しと、その下の正直な一文を追加し、スタイル、リンク、ビルドシステム、将来のセクションは追加しません。
編集前後の対象パスと差分を保存し、ローカルチェックを1回実行します。初めて見るレビュー担当者でも、基準状態、
最初に確認できた結果、変更ファイル、正確なコマンドと終了ステータス、範囲外の内容を答えられる状態にします。

1つのタスクから、一般的な速さや品質を測ろうとはしません。観測していない時間、コスト、結果は `unavailable`、`unknown`、`not_run` と記録します。

### 証拠

2つの計画、固定した入力、選んだスライス、依存関係と権限に関する前提、差分、確認結果、停止点、引き継ぎカードを保存します。実行していない試行は `not_run` のままです。もっともらしい計画は、結果の代わりにはなりません。

残す成果物は、一時ディレクトリ内の `slice-record.md`（または同等の承認済みメモ）です。

```text
baseline: edit 前の README.md
chosen_plan: vertical
changed_files: README.md only
check: 実際に実行した exact command
result: exact output と exit status
acceptance: passed / failed / not_observed
not_proven: styling、build、deployment、user acceptance
next_slice: 一つの bounded next action
```

- [ ] 結果、入力、範囲、受け入れ条件を観測できる。
- [ ] スライスに確認方法と復旧元がある。
- [ ] 失敗した試行もレビューできる証拠が残る。
- [ ] 明示的な権限がない外部への副作用は、範囲外である。
- [ ] 引き継ぎで、変更済み、確認済み、ブロック、未確認を分けている。

## 三つの計画を比べる：最初の根拠が出るものを選ぶ

同じ依頼について、エディターを開く前に3つの案を書きます。3つとも実行する必要はありません。どの案が最初の役に立つ結果を隠してしまうかを比べるためです。

| 形 | よくある最初の手順 | 最初の役立つ証拠 | 続けない合図 |
|---|---|---|---|
| 横割り | 「まずデータを全部、次にUIを全部用意する」 | 多くの層を終えてから、やっと出てくる | 今日レビューできる人、入力、確認方法がない |
| ファイル順 | 「このファイルをこの順番で編集する」 | ローカルでレビューできる差分 | ファイルの順番が、誰に何が見えるかを説明していない |
| 垂直 | 「固定した入力から1つの結果を見せ、確認する」 | 小さな経路、確認結果、記録 | 最初の経路だけで公開、インストール、複数システムの変更が必要 |

次の手順に進む価値があるかを早く知りたいときは、垂直計画を選びます。依存関係、権限、ファイルの存在さえ分からないなら、読み取り専用の探査（probe）を選びます。探査が答えるのは「続けられるか」であって、機能が完成したかではありません。

## 再利用できる計画プロンプト

次を出発点にして、自分のタスクに合わせて値を置き換えます。本番のタスクにそのまま貼り付けず、
対象と境界を先に埋めてください。

```text
Goal
Deliver one vertical slice: [named user/reviewer が観測できる result]

Context and inputs
- Repository/workspace: [absolute path or approved surface]
- Relevant files and fixtures: [exact paths]
- Baseline: [branch/commit/hash/status or saved copy]
- Known assumptions: [まだ未確認の facts]

Scope contract
- Allowed actions: [exact paths と read/edit/run/check]
- Change budget: [files、commands、retry/time limit]
- Non-goals: [feature、install、network、deploy、cleanup の除外]
- Human confirmation required before: [irreversible/external action]

Slice design
- depends_on: [precondition と cheap check]
- provides_to: [next slice の exact input]
- acceptance_evidence: [diff、output、test、render、review record]
- failure_signal: [error、missing output、timeout、scope drift]

Execution rules
1. baseline と既存変更を read-only で確認してから edit する。
2. first mutation の前に slice card と checkpoint を保存する。
3. stated evidence を出す最小の action だけを行う。
4. 各 action の後に changed state を報告し、spinner や自分の summary から成功を推測しない。
5. dependency、target path、useful event、budget に問題があれば stop して checkpoint を保存する。
   install、publish、delete、permission の拡大はしない。
6. recovery では target を読み戻し、baseline と diff を比較し、変数一つで idempotent action を一回だけ retry する。

Delivery
status (passed / blocked / unverified)、changed files、exact evidence、failed attempts、
remaining unknowns、rollback/recovery、next single action を返す。acceptance evidence がなければ complete と呼ばない。
```

このプロンプトだけでAgentの信頼性が上がるわけではありません。会話の依頼を、別の人が監査できる
契約に変えるところに価値があります。

## 停止・引き継ぎカード

中断されても計画は消えません。ただし、それだけで続行してよいことにはなりません。セッションを閉じる前、
または助けを求める前に、その会話を知らない人でも読めるカードを残します。

```text
slice: 一つの観測可能な結果の名前
baseline: 比較したブランチ、リビジョン、またはコピー
done with evidence: 実際に行った変更と証拠
blocker or unknown: 最初に欠けた依存関係または確認
target state: no change / partial / unknown
not yet: 権限、インストール、公開、または除外したファイル
one next action: 読み取り専用の探索、または同じ結果を壊さずに再試行できる操作
```

次に行う操作を1つ、具体的な名前で言えないなら、スライスはまだ大きすぎます。「続けて」と頼む前に、
問いを分けてください。

## まず、完結するスライスを一つ作る

「コース全体を改善する」ことから始めません。初めて読む人向けに、120語以内のローカル文章を1つ選びます。
このスライスで目指す結果は控えめです。**何を変えたか** と **どう確認するか** の2つの見出しを見えるようにし、
公開、インストール、他のファイルの編集はしません。

最初にモデルへ「まだ編集しない」と伝え、次のカードを渡します。

```text
outcome: 読者が変更内容と確認方法を読める
fixed input: 120語以内のローカルファイル一つ
allowed: 文章の提案。確認後はそのファイルだけを編集
forbidden: 公開、インストール、リンク変更、他ファイルの変更
acceptance: 二つの見出しがあり、人が見つけられる
stop if: ファイルがない、別ファイルが必要、依頼が曖昧になる
```

その後は、定義 → 3段階の計画を依頼 → 編集前に範囲を確認 → 小さく編集 → 前後を比較 → 2つの見出しを読む →
正直に引き継ぐ、の順で進めます。モデルが作業を広げようとしたら、カードに戻ります。新しい判断なしに範囲を広げても、
「より役に立つ」ことにはなりません。

## 数字を作らずに、二つの頼み方を比べる

直接の依頼（「分かりやすくして」）と、このカードを使う依頼を1回ずつ試せます。文章、モデル、ツール、使える時間、
読者に確認してもらう方法を固定します。両方のプロンプト、バージョン、読者の質問、エラーを保存します。変数が変わったら
`not_comparable` と記録します。返答が速く見えることや、文章がきれいなことだけで、一般的な生産性やモデルの優劣は証明できません。
この練習で観測するのは、編集前に何が足りなかったか、結果をレビューできるかです。

## 安全に失敗し、境界を守る

**どう確認するか** をわざと消すか、存在しないファイルを指定します。最初の失敗から、内容が足りないのか、
入力が間違っているのかを見分けます。失敗を隠すために依存関係や権限を増やしません。観測したこと、まだ証明できないこと、
安全な次の操作を1つ書きます。

| シグナル | 分類 | 最初の復旧 |
|---|---|---|
| 必須の見出しがない | 内容の受け入れ失敗 | 欠けた見出しだけを戻し、同じチェックを再実行する |
| チェックが間違ったファイルを見ている | テスト／入力の失敗 | 対象パスを読み直し、契約で許されている場合だけチェックを直す |
| 決めた時間内に出力がない | 実行状態が不明 | 待つのをやめ、コマンド、時間、プロセス状態、差分を保存する |
| インストール、ネットワーク、広すぎるパスが必要 | 範囲／権限の失敗 | 新しい判断を求め、環境を黙って修理しない |

復旧後は、何が変わったかと、失敗が何を証明**しなかった**かを書きます。失敗したチェックが証明するのは、
その入力に対するそのチェックが通らなかったことだけです。リポジトリ全体やAgent全体が壊れた、または大規模な書き直しが
必要だとは言えません。

## 実際の作業で復旧・停止するとき

長いタスクが中断されたとき、無条件に「続けて」と指示しません。

1. 新しい書き込み、外部リクエスト、インストール、削除、デプロイを止める。
2. チェックポイント、`git status`、関連する差分、最後のコマンド出力、実際の対象パスを読む。
3. 断点を「入力不足」「範囲のずれ」「検証失敗」「基盤／タイムアウト」「権限」「不明」に分類する。
4. 読み取り専用の探査か、最小スライスへの冪等な再試行のどちらか1つを選び、変える変数は1つにする。
5. 新しい根拠と、次のスライスがまだ有効かどうかをチェックポイントに追記する。
6. 原因が分からない、再試行の予算を使い切った、対象が変わった――このいずれかなら、編集を積み重ねず、
   ブロックされた状態として引き継ぐ。

途中までの成果物が安全で役に立つなら残し、`partial` または `unverified` と明記します。切り戻しが必要なら、
失敗の根拠を先に保存し、既存の利用者の変更を消さない範囲だけ戻します。

> 新しい根拠、新しい権限、または安定した対象がなければ、自動的に続けない。

## 期待する成果物：別の人が実行できる引き継ぎ

1つのスライスは、途中でブロックされても、次の成果物を残します。

1. **スライスカード：** 結果、依存関係、範囲、根拠、予算、停止条件。
2. **チェックポイント：** 最後に確認した状態、対象の同一性、変更ファイル、コマンド結果、次の行動。
3. **実装差分または変更なしの記録：** 実際に動いたもの。
4. **検証記録：** 正確なコマンド、環境、終了ステータス、出力、確認範囲。
5. **失敗記録：** 失敗した入力、観測できたシグナル、復旧方法、再試行が安全かどうか。
6. **引き継ぎメモ：**

```text
status: passed / partial / blocked / unverified
done: evidence が支える claim
changed: exact paths または none
evidence: artifact path または link
not_proven: runtime、external、visual、security、user claim
risks: 残った side effect または assumption
next: 一つの bounded action
owner: person または team
```

引き継ぎは後から付ける事務作業ではなく、スライスの一部です。これがなければ、次の人は長い
会話の記録から状態を作り直し、すでに行った操作を繰り返すかもしれません。

## 振り返る

横割りの計画なら最後まで見つからなかった依存関係は何ですか。垂直スライスを確認可能にした根拠は何ですか。
確認後も範囲外に残った主張は何ですか。

いま取り組んでいるタスクから、まだ別の人に渡せないほど大きいものを1つ書き出します。どの最初のスライスなら、
意味のある根拠を最初に出せますか。どの行動、入力、判断を明確に範囲外にしますか。そこで中断されたら、
推測せずに再開するためにどの記録が必要ですか。

## 依存関係を、確認しやすい順に並べる

計画の順序は、ファイル名やチームの担当順ではなく、最初に大きなリスクを減らせる順に決めます。各依存関係について、
「これがなければ何ができないか」「読み取り専用で確かめられるか」を書きます。

| 依存関係 | 先に確認する理由 | 最小の確認 | 未確認ならどうするか |
| --- | --- | --- | --- |
| 対象ファイルの同一性 | 別のコピーを編集すると結果が無意味になる | 絶対パスと基準状態を読む | 停止して正しいルートを尋ねる |
| 受け入れ規則 | 「良くする」だけではレビューできない | 読者が見える規則を一文にする | 結果をさらに小さくする |
| 必要な入力 | 入力がなければ提案を比べられない | 名前を指定したファイル／出典のリビジョンを読む | `blocked_input` にする |
| 権限 | 書き込みや外部操作はタスクの意味を変える | 許可されたパス／操作をタスクカードと照合 | 承認を尋ねる。範囲を広げない |
| 検証の出典 | 確認方法がなければ引き渡しの主張を作れない | コマンド、手動規則、読み戻しを特定 | `unverified` のまま引き継ぐ |

依存関係の図は、完璧でなくて構いません。大切なのは、不明点を後ろへ隠さず、最初の垂直スライスで安全に表に出すことです。

## 実例：読者の経路を1つ直す

例として、ローカルの章の冒頭120語に「何をするか」と「どう確認するか」が書かれていないとします。目標を「コース全体を改善する」から、次のように小さくします。

```text
Outcome: 初めて読む人が二つの見出しを見つけ、最初の操作を一つ言える。
Fixed input: 使い捨てコピーにある、名前を指定した章ファイル一つ。
Allowed change: そのファイルのローカル文章だけ。編集前は提案にとどめる。
Acceptance: 「What changed」と「How to check」があり、どちらも120語以内の節にある。
Evidence: 基準状態、正確な差分、手動の読み戻し、未確認事項の一覧。
Stop: 別ファイル、リンク、公開、インストール、または読者データが必要になる。
```

このスライスの価値は、コースを完成させることではありません。タスクの契約が十分か、対象が正しいか、確認方法が読者に見える規則を直接見ているかを、低いコストで確かめることです。受け入れ条件を満たしても、理解、登録、定着、全般的な品質は `not proven` のままです。

## 計画レビュー：開始前と変更後に確認すること

エディターを開く前と、1つのスライスが終わった後に、同じ5つを確認します。

1. この結果を1文で言えますか。誰が何を確認しますか。
2. 最初の確認は、作った成果物ではなく受け入れ条件を見ていますか。
3. どの前提が間違っていたら、この計画はすぐに止まりますか。
4. 失敗しても、次の人が基準状態と試した範囲をレビューできますか。
5. 次のスライスは新しい根拠を求めていますか。それとも同じ約束を大きくしているだけですか。

はい／いいえだけで答えられないなら、その計画はまだ実行手順ではなく希望です。読み取り専用の探査、質問、またはより小さい結果に戻します。

## 失敗を根拠に変える

| 失敗 | 安全な結果 |
| --- | --- |
| 対象ファイルがない | 対象を作らず `blocked_input` と記録 |
| 受け入れ条件が「もっと良く」のまま | 読者に見える規則を尋ね、編集しない |
| 最初のスライスが三つのシステムを変える | ローカルの成果物一つに戻す |
| 確認にインストール／ネットワークが必要 | 新しい権限を尋ねるか、`unverified` で停止 |
| 差分が許可したファイルを越える | 追加変更をレビューし、ロールバックや判断なしに続けない |

失敗は計画そのものの失敗ではなく、最初に高くつく前提が見えた記録です。最初に根拠がなくなった主張、実際の差分、
最後に受け入れた状態、安全な次の操作を1つ、引き継ぎに残します。

## 別の分野へ移す

同じスライスの考え方を、調査、言語練習、内容レビューにも使います。結果、固定した入力、許可する操作と禁止する操作、
確認、復旧は保ちます。言語練習では、受け入れ条件に、AIが流暢に返答することだけでなく、後から初見の内容を助けなしに
思い出せるかどうかも入れます。その練習で証明できないことも書きます。

分野ごとに3〜7枚のスライスカードを作ります。

- **エンジニアリング：** 固定フィクスチャを返す読み取り専用エンドポイントと、それを表示する1つの画面。認証、分析、デプロイは最初のスライスから外す。
- **調査：** 出典表、不確実性の列、範囲を限定した結論を持つ1つの質問。出典を確認するまで、検索結果を事実と呼ばない。
- **マーケティング：** 承認済みの製品コンテキストから、対象読者向けの草稿とレビュー可能な実験を1つ。公開とリアルタイムの読者データは外す。
- **Skill設計：** トリガー、入力スキーマ、許可する操作、出力、失敗経路、レビュー日を1つずつ定める。未レビューの外部Skillはインストールも呼び出しもしない。

別の人、または新しいAgentのコンテキストに口頭説明なしでカードを読んでもらい、隠れた仮定を1つと、
足りない受け入れシグナルを1つ見つけてもらいます。直すのはレビュー担当者の記憶ではなく、カードそのものです。

## 受け入れチェックリスト

- [ ] 結果、入力、範囲、受け入れ条件を確認できる。
- [ ] スライスに確認方法、停止規則、復旧元がある。
- [ ] 失敗した試行もレビューできる証拠を残す。
- [ ] 明示的な権限がない外部への副作用は、範囲外である。
- [ ] 引き継ぎで、変更済み、確認済み、ブロック、未確認を分ける。

## 出典と保守の境界

垂直スライス、依存関係の順序、停止点は、このプロジェクトの安定した教え方です。一方、製品機能、権限、
モデルの利用可能性、コミュニティで報告された症状は変わります。現在の主張は、[公式ファクトカード](../evidence-library-JA.md#source-notes)と
[フィールド問題索引](../evidence-library-JA.md#source-notes)で確認してください。これらは、ローカルでの実行や独立した学習者の観察の代わりにはなりません。

| topic | source | Accessed | evidence boundary | Owner / next review |
|---|---|---:|---|---|
| task protocol に goal、context、constraints、acceptance、stop、recovery、delivery を含める | [Prompt patterns for real work](../evidence-library-JA.md#source-notes) | 2026-08-11 | project research synthesis。vendor が定めた prompt format ではない | `curriculum-maintainer` / 2026-09-11 |
| capacity interruption と long-running verification で state が不明になることがある | [Field problems and prompt patterns P2](../evidence-library-JA.md#source-notes)、[field-problems deep dive](../evidence-library-JA.md#source-notes) | 2026-08-11 | public user reports。universal cause、repair、local reproduction は主張しない | `curriculum-maintainer` / 2026-09-11 |
| external checkpoint、vertical slice、complete handoff を curriculum に加える | [Content value upgrade plan P2](../evidence-library-JA.md#source-notes) | 2026-08-11 | project planning recommendation。experiment は `not_run` | `curriculum-maintainer` / 2026-09-11 |
| current Codex entry points、permission、model、command flag、UI state | [OpenAI Codex baseline](../evidence-library-JA.md#source-notes)、[official Codex documentation](https://developers.openai.com/codex/) | 2026-08-11 | volatile product facts。command や label は first-party source で再確認する | `curriculum-maintainer` / 2026-09-11 |

同じテンプレートを、調査メモ、マーケティング文、デザインレビューにも使えます。ただし、受け入れ条件は分野に合わせて変えます。
調査なら出典の範囲と引用、文案なら提供された事実と読者の条件、デザインレビューならビューポートと観察が必要です。
プラットフォーム固有のコマンド、モデルの動作、速さ、コストは、現在の出典と実際の実行がない限り主張しません。

- [ ] 結果が小さく、観察する人に分かる。
- [ ] 最初に大きなリスクを持つ依存関係に、読み取り専用の確認または停止規則がある。
- [ ] 一つのスライスが、一つのレビュー可能な成果物と証拠を残す。
- [ ] 失敗と不明点を引き渡しから消していない。
- [ ] 次のスライスが、範囲の拡大ではなく新しい判断になっている。
