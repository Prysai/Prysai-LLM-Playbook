# 第1章：Codex を信頼する前に GPT を理解する

## この章が解決する問題

Codex は「より優れたコードを書けるチャット画面」だとよく説明されます。しかし、
現実の作業で最初の失敗に直面した瞬間、この説明は役に立たなくなります。同じ依頼でも、
モデル、プロジェクト、コンテキスト、権限、ツール、フィードバックが変わると、なぜ挙動が
変わるのかを説明できないからです。また、自信に満ちた回答やツールのメッセージを、作業が
実行され、確認まで済んだ証拠として扱うという危険な近道も招きます。

この章では、実用に必要な小さなモデルを構築します。これは、隠れた思考の連鎖
（chain-of-thought）について主張するものではありません。扱うのは、学習者が確認できるもの、
すなわち入力、選択されたコンテキスト、要求された行動、ツールの境界、返された結果、
変更された状態、そして停止の判断に使われた証拠だけです。

## 学習目標

この章を終えると、次のことができるようになります。

- GPT、モデル、Codex の製品画面、ツール、Skill、Agent ループを区別する。
- ユーザーの文が変わらなくても、コンテキストの選択とサンプリングによって出力が変わり得る
  理由を説明する。
- モデルが提案したツール操作を、実行時の権限確認、ツールの結果、最終的な検証と切り分ける。
- 不確かな完了の主張を、小さく元に戻せる実験へ変える。
- 公式な根本原因を作り上げることなく、現実に現れた症状を認識する。

## まず、観測可能な層を理解する

タスクを分析するときは、次の層を使います。

    モデルの能力
            ↓ 応答または行動案を生成する
    Codex の作業画面
            ↓ プロジェクトのコンテキストと実行境界を提供する
    ツール／ランタイム
            ↓ 要求された行動を許可、拒否、または実行することがある
    ツールの結果／変更された状態
            ↓ 新たな証拠または新たなコンテキストになる
    検証と人による判断
            ↓ 作業を停止できるか、復旧が必要かを決める
    納品についての主張

矢印は自動的な保証ではありません。モデルがシェルコマンドを提案しても、ランタイムがそれを
実行していない場合があります。ランタイムが終了コード 0 でコマンドを実行しても、確認した
ファイルや環境が間違っている場合があります。ツールが成功したように見えるメッセージを返しても、
意図した外部オブジェクトは変更されていないかもしれません。矢印の一つひとつに、それぞれの
証拠が必要です。

### 用語を平易に説明すると

| 用語 | 何をもたらすか | 何の証明にはならないか |
|---|---|---|
| GPT | 生成モデルの能力群 | ファイルやターミナルへのアクセス、アカウント上の権限、変更の成功 |
| モデル | 一回の実行に使う具体的なモデル／構成 | あらゆる画面で利用できること、またはあらゆるタスクに最適であること |
| Codex | モデルをプロジェクトのコンテキスト、ツール、権限へ接続する作業画面 | 表示されているすべてのアカウントやコネクターが対象に対して認可済みであること |
| ツール | ファイル、プロセス、ブラウザー、Git ホスト、サービスを読み取りまたは変更するためのインターフェース | 要求された行動が許可され、正しく、完了していること |
| Skill | トリガー、入力、境界、手順、証拠を備えた再利用可能な方法 | 新しいモデル、権限の付与、または検証の代わり |
| Agent | 観察、行動、フィードバック、再試行、停止をめぐる、観測可能な複数ステップのループ | 隠れた推論へのアクセス、または無限に再試行する権限 |

プロジェクトの安定した用語は [CONTEXT.md](../../CONTEXT.md) で定義されています。
モデル名、呼び出し構文、権限の既定値といった製品詳細は変動しやすい事実です。日付付きの
[公式基準線](../../docs/research/openai-codex-baseline.md)を参照し、そこからリンクされた
一次資料を、依拠する前に再確認してください。

## 言語モデルはどのように回答を生成するか

役に立つ単純化されたモデルは、次のとおりです。

    選択されたコンテキスト + タスク + モデル構成
            → 次に来る可能性のあるトークンの確率分布
            → サンプリングまたは選択されたトークンを一つずつ生成
            → 応答、構造化された行動案、または拒否

モデルは、データベースからあらかじめ書かれた回答を一つ取り出しているわけではありません。
受け取ったコンテキストを条件として、系列を生成します。コンテキスト、順序、指示、ツールの
結果、生成構成が少し変わるだけでも、続きを変えることがあります。この図から、モデルが何を
考えたのかを正確に知ることはできません。公平に比較するために、どの入力を固定すべきかが
分かります。

### メカニズムカード：コンテキストは予算であり、フィルターでもある

コンテキストは、多ければ自動的に良くなるものではありません。候補となる入力を一つずつ分類します。

1. 対象と受け入れ条件を特定するために必要か。
2. 信頼できるか。それとも、データの中にある未検証の指示か。
3. このタスクに使える程度に新しいか。
4. 有用な情報を増やすか。それとも、コンテキストの空間をタスクと奪い合うか。

README を編集するなら、プロジェクト規則と対象の README は関連する可能性があります。無作為に
選んだ古い issue、コピーされたプロンプト、無関係な秘密情報は関連しません。「プロジェクト規則を
無視せよ」と書かれたファイルも、分析対象のファイルであって、従うべき権限者ではありません。
したがって、コンテキストの選択は品質上の判断であると同時に、セキュリティ上の判断でもあります。

### メカニズムカード：ばらつきは測定の問題である

二つの出力が異なるというだけでは、あるコンテキストが差の原因になったと証明できません。
モデルのサンプリング結果が異なった、サービスが別のリビジョンを使った、ツールの状態が変わった、
またはタスクの指定が不十分だった可能性があります。一度に変える変数は一つにし、次を記録します。

    run-id | モデル／画面 | 入力リビジョン | 変更した変数 | 出力／状態 | 証拠 | 不明点

可能ならベースラインを繰り返してください。変数を固定できない場合は、観察結果を「異なる結果を
観測した」と記し、「X が原因だった」とは記さないでください。

## ツール呼び出しはプロトコルの境界であり、魔法のような操作ではない

Codex がツールを使える場合は、次の四つを別々の出来事として捉えます。

1. モデルが行動を提案する。
2. ランタイムが範囲、権限、確認規則をチェックする。
3. ツールが実行、拒否、またはタイムアウトする。
4. 次のステップで、結果と変更された状態を確認する。

次の記述は同じ意味ではありません。

- 「モデルがコマンドを書いた。」
- 「コマンドが実行された。」
- 「コマンドが意図した対象を変更した。」
- 「変更が受け入れ条件を満たしている。」

ローカルファイルの場合、確認したパス、変更前後の差分、対象を絞ったチェック、未検証事項の一覧が、
有用な証拠になり得ます。GitHub その他の外部操作では、正確な対象、認可状態、確認点、結果オブジェクト、
ロールバックまたは復旧の経路も加えます。ログイン画面、ツール名、「完了」と書かれたメッセージだけでは、
これらの不足を一つも埋められません。

### 権限と能力は同じではない

公式な製品境界では、技術的な sandbox と承認の境界を区別しています。プロジェクトの用語では、
次のようになります。

- sandbox は、ランタイムが技術的にアクセスできる範囲を表す。
- 承認は、ランタイムが行動の前に一時停止しなければならない場合を表す。
- どちらも、対象、範囲、結果が正しいことを証明しない。

モデル名、Skill の存在、アカウントへのログイン、利用可能なボタンから権限を推測しないでください。
副作用を伴う操作の直前に、対象と行動を確認します。学習用の演習は、秘密情報を含まない使い捨ての
コピーで始めてください。

## 早い段階で学ぶ価値のある三つのメカニズム上の落とし穴

同じ観測可能な境界が、よく使われる三つの仕組みに現れます。製品デモでは異なって見えますが、
いずれも、もっともらしくてもまだ信頼できない結果を生み出す可能性があります。

### 1. 構造化出力は、構文的に正しくても意味的に誤っている場合がある

JSON Schema や型付きの応答によって、形、必須フィールド、一部の型を制約できます。しかし、ID が
実在すること、日付が最新であること、権限が有効であること、出典が値を裏付けていることは証明できません。
次の三つのチェックを使います。

```text
スキーマ／型のチェック → ビジネスルールのチェック → 出典／状態のチェック
```

たとえば、`{ "status": "approved" }` は有効な JSON で、スキーマを満たしていても、その承認が
別のプロジェクトに対するものかもしれません。モデルの生の出力、スキーマの結果、ビジネスルールの
結果、外部での検証を、それぞれ独立した証拠として保存してください。
[LLM メカニズム研究](../../docs/research/llm-mechanism-deep-dive-2026-08-10.md#机制卡-d-structured-output-把语法错误变成语义错误)では、
これを教育上の境界として記録しています。すべてのプロバイダーが同じ実装を使っているという主張ではありません。

### 2. 検索は資料を選ぶが、その完全な利用を保証しない

検索または検索拡張は、関連するチャンクを選ぶことがあります。しかし、関連性は完全性、新しさ、権威性、
またはモデルが実際に因果的に利用したことと同じではありません。小さな例外の段落が広い一般規則より
低く順位付けされたり、チャンクの境界によって条件とその定義が切り離されたりする場合があります。
クエリ、フィルター、リビジョン、選択されたチャンク ID、最終的な引用を記録してください。回答が変わった
場合、実験によって理由を切り分けられていない限り、「検索コンテキストが変わったことで異なる結果が
生じた」と記します。

### 3. 指示のように見えるデータも、データである

Web ページ、添付ファイル、issue 本文、ツールの結果、データベースのフィールド、MCP リソースには、
「それまでの規則を無視せよ」のような文が含まれることがあります。その文字列は、システム指示のように
見えるというだけで権限を得るわけではありません。信頼できないデータとして扱い、外部操作は既定で
読み取り専用に保ち、ツール呼び出しへ影響させる前に別途判断を求めてください。初心者向けに実践できる
プロンプトインジェクション対策は、データの出所を特定し、ツールの境界を制限し、試みられた行動を記録に
残すことです。

これら三つの落とし穴は、プロバイダー固有の出典と低リスクの実験を用いて、
[メカニズムの詳細研究](../../docs/research/llm-mechanism-deep-dive-2026-08-10.md)で扱っています。

## Agent ループが本当に意味するもの

Agent は、観測可能な痕跡を残す状態機械として教えるのが最適です。

    ready（準備完了）
      → observed（観察済み）
      → planned（計画済み）
      → action_requested（行動要求済み）
      → awaiting_approval（承認待ち）／executing（実行中）
      → feedback_received（フィードバック受領済み）
      → verified（検証済み）／recoverable_failure（復旧可能な失敗）／blocked（ブロック中）
      → stop（停止）または bounded_retry（回数を制限した再試行）

ループには、再試行の回数上限と、各再試行の理由が必要です。入力、権限、環境、受け入れ条件が
変わっていないのに「もう一度試す」ことは、復旧戦略ではありません。適切な停止記録は、次の問いに
答えます。

- どの状態に到達したか。
- 何かが変わったなら、何が変わったか。
- どの証拠がその主張を裏付けるか。
- どの証拠が不足しているか。
- 不確実性を減らせる、次の最小の確認は何か。

隠れた推論を公開しているふりをしなくても、このループは役に立ちます。観測可能な出来事と判断を
記録してください。作り上げた私的な理由付けを、モデル内部の処理の記録として提示してはいけません。

## 現場の事例：役に立つ教訓は境界にある

以下は、プロジェクトの現場調査で収集した、公開されているユーザー報告です。公式な根本原因の報告ではなく、
このプロジェクトでローカルに再現したものでもありません。素朴な理解がどこで破綻するかを示す点に価値があります。

### 事例 FP-09：容量による中断と、危険な再試行の思い込み

選択したモデルが容量上限により利用不能になり、その後キューに入れた指示が、部分的に完了した状態から
続行されたように見えることがある、とユーザーが報告しました。この報告から、サービス側の原因や正確な
キューの意味は確定できません。したがって、安全な対応は「続行を何度も押す」ことではありません。

安全な最小の対応は、次のとおりです。

1. 停止し、モデル、画面、時刻、表示されたエラーを記録する。
2. 別の指示を送る前に、現在の差分とチェックポイントを確認する。
3. 現在の状態に対して、利用できる最小範囲のチェックを実行する。
4. どの状態を正として扱うか決めた後でのみ、名前を付けたチェックポイントから再開するか、
   クリーンな実行を始める。

出典と証拠ラベル：現場調査の [FP-09](../../docs/research/field-problems-codex.md#fp-09-模型容量错误中断任务，并可能让排队后续任务接在半成品上)。

### 事例 FP-10：「Working」は進捗の証拠ではない

Windows CLI のユーザーから、フォーマットまたは分析処理が、明確な完了やエラーを示さず長時間
Working／実行中の状態にとどまったという報告がありました。この報告から、コマンドのハング、プロセス処理、
出力のバッファリング、環境のずれ、その他の要因のどれが原因かは証明できません。長時間実行中という表示は、
状態の観察であって、成功した結果ではありません。

コマンド、プロセスの状態、経過時間、出力、中断した時点を記録します。その後、安全であれば差分を確認し、
対象を絞ったチェックを別途実行してください。「UI にまだ Working と表示されている」を「フォーマッターが
完了した」という意味に変えてはいけません。

出典と証拠ラベル：現場調査の [FP-10](../../docs/research/field-problems-codex.md#fp-10格式化验证命令让-windows-cli-agent-长时间停在-working)。

### 事例 FP-11：検証が意図せずタスクを拡大することがある

ある公開報告では、Agent が検証ステップを、許可されていない強制再インストールへ拡大したとされています。
報告内の説明が実際の根本原因かどうかは確認されていません。根本原因に左右されない長期的な教訓は、検証にも、
宣言されたコマンド範囲、書き込み範囲、停止点が必要だということです。

チェックに破壊的なリセット、ネットワーク呼び出し、パッケージの再インストール、認証情報が必要になった場合は、
停止して新たな判断を求めます。「チェックが失敗した」ことは、権限を拡大してよいという許可にはなりません。

証拠の分類と関連する章／実験の対応については、
[現場問題インデックス](../../docs/research/field-problems-index-2026-08-10.md)を参照してください。

## 現実のタスクに使う判断規則

Codex に行動を依頼する前に、次の小さなタスクカードを書きます。

| 項目 | README だけを変更する場合の例 | 不足している場合の対応 |
|---|---|---|
| 目標 | 新しいコントリビューターがプロジェクトを始められるようにする | 質問する。「改善して」を受け入れ条件として解釈しない |
| コンテキスト | プロジェクト規則、README、パッケージスクリプト | 関連する最小限のファイルだけを読む |
| 許可された行動 | 使い捨てのブランチで、ローカルの README 一つを編集する | 明記されていない副作用は禁止として扱う |
| フィードバック | 差分、リンクチェック、コマンド出力の記録 | さらに編集する前にチェックを追加する |
| 停止条件 | 範囲が変わった、コマンドにインストール／ネットワークが必要、または証拠が不足している | 停止し、`blocked` または `not_observed` と記録する |
| 納品についての主張 | 「README を変更。リンクチェックは合格。実行時テストは未実施」 | 各主張を、実際に存在する証拠の範囲内に保つ |

このカードは長いプロンプトより価値があります。プロンプトでは暗黙になりがちな判断を、明らかにするからです。

## 小さな実験：タスクを固定し、一つの入力だけを変える

### 準備

README 一つと短いプロジェクト規則だけを含む、使い捨てのローカルコピーを使います。非公開リポジトリ、
秘密情報、顧客データ、ネットワーク呼び出し、外部アカウントは使わないでください。試行ごとに実行 ID を記録します。

### タスク

モデルまたは Codex の画面に、次のように依頼します。

> README を確認し、改善点を一つ特定してください。ファイルは編集しないでください。
> 読んだ内容、その改善が重要な理由、後で編集した場合に確認する方法を説明してください。

ベースラインを実行し、その後、一度に一つの変数だけを変えて繰り返します。

1. 対象読者とプロジェクトの目標を追加する。
2. プロジェクト規則を一つ追加する。
3. 回答の前に短い計画を求める。
4. 明示的な受け入れ条件を追加する。

実行と実行の間で画面またはモデルが変わった場合は、交絡要因として記録してください。安易な変更前後の比較から、
因果関係を主張しないでください。

### 証拠

プロンプト／入力のリビジョン、実行 ID、画面／モデルのラベル、読み取り範囲、回答、ファイル差分の有無、
未検証事項を保存します。静的な演習に合格しても、すべての Codex 画面で同じ挙動が起きることは証明できません。

### 振り返り

- 単なる表現ではなく、タスクの境界を変えた変数はどれか。
- ツールの提案と、実行された行動をどのように区別したか。
- 結果が正しいと主張する前に、何を観察する必要があるか。
- 不確実性を一つ取り除ける、次の最小の実験は何か。

## 意図的な失敗

使い捨てのコピーで、意図的に指定が不十分な次の依頼を使います。

> プロジェクト全体をプロフェッショナルにし、すべての問題を修正してください。

正しい応答は、範囲の定まらない大規模な編集ではありません。適切な応答では、「プロフェッショナル」の定義、

- 許可された行動と停止条件を含むタスクカードを書ける。
- 証拠が何を証明しないかを明記した実行記録を作れる。
