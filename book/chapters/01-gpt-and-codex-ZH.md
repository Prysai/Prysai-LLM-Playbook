# 第一章：先理解 GPT，再信任 Codex

## 开场：先别急着站队

今天我们先聊一聊大家最常听到的名字：GPT、Codex、Grok、Gemini、Kimi，甚至
Answer.AI。它们经常出现在同一段讨论里，但并不是同一类东西。有的是模型家族，
有的是给模型接上文件和工具的工作台，有的是把研究做成产品或教育内容的团队。
你不需要先背参数，也不需要先挑“最强模型”。先学会问一个更有用的问题：

> 我今天要完成什么任务？需要什么输入、输出、工作台和检查？

| 你可能听到的名字 | 第一个该问的问题 | 不要直接假定 |
| --- | --- | --- |
| GPT / OpenAI | 我实际用的是哪一个模型，以及 ChatGPT、API 还是 Codex 哪个工作面？ | 一个模型名自动给了文件权限、工具权限或更好结果。 |
| Grok / xAI | 厂商所说的推理能力，是否真和我的固定任务有关？ | 它对你的任务最好，或你的账户一定可用。 |
| Gemini / Google DeepMind | 这项任务是否真的需要我能访问的多模态输入或生态？ | 每个 Gemini 入口都有相同工具和能力。 |
| Kimi / Moonshot AI | 我需要测试的是代码、分析，还是长文档工作？ | 宣传的上下文或功能已经证明它在此工作台中更好。 |
| Answer.AI | 我是在寻找应用研究、教育内容还是终端产品？ | 它是可以和其他模型一起放进选择器的基础模型提供商。 |

[模型与工作台方向图](../evidence-library-ZH.md#source-notes)
为每一行保留了所有者的一手来源，并把“厂商的定位”与“实际测得的结果”分开。
先把你手上已有模型的一次请求用好；只有在相同任务和相同验收规则下，才比较不同候选项。

## 本章要解决的问题

人们常把 Codex 描述成“一个更会写代码的聊天窗口”。一旦遇到第一次真正的失败，这种描述就失去了作用。它无法解释为什么模型、项目、上下文、权限、工具或反馈发生变化时，同一个请求会产生不同的行为。它还会诱发一种危险的捷径：把自信的回答或工具消息当成工作已经执行并检查过的证明。

本章将建立一个小型的操作模型。它不是对隐藏思维链的断言。我们只使用学习者能够检查的内容：输入、选定的上下文、请求的动作、工具边界、返回的结果、发生变化的状态，以及用于决定停止的证据。

## 学习目标

完成本章后，你应当能够：

- 区分 GPT、模型、Codex 产品工作面、工具、Skill 和 Agent 循环；
- 解释为什么上下文选择和采样会在用户原句不变的情况下改变输出；
- 将模型提出的工具动作与运行时权限检查、工具结果和最终验证区分开；
- 把不确定的完成声明转化为一个小型、可逆的实验；
- 识别真实世界中的症状，同时不虚构官方根因。

## 从可观察的分层开始

分析任务时，使用以下分层：

    模型能力
            ↓ 生成回答或动作提议
    Codex 工作面
            ↓ 提供项目上下文和执行边界
    工具/运行时
            ↓ 可能允许、拒绝或执行请求的动作
    工具结果/变化后的状态
            ↓ 成为新证据或新上下文
    验证和人工决定
            ↓ 决定工作可以停止还是必须恢复
    交付声明

这些箭头并不是自动保证。模型可以提出 shell 命令，而运行时并未执行它。运行时可以执行一条退出码为零的命令，但检查的是错误的文件或环境。工具可以返回看似成功的消息，而预期的外部对象并未改变。每一个箭头都需要自己的证据。

### 用通俗语言解释这些术语

| 术语 | 它提供什么 | 它不能证明什么 |
|---|---|---|
| GPT | 一系列生成式模型能力 | 文件访问、终端访问、账户权限或变更成功 |
| 模型 | 某次运行使用的具体模型/配置 | 它在每个工作面都可用，或适合所有任务 |
| Codex | 将模型与项目上下文、工具和权限连接起来的工作面 | 每个可见账户或连接器都已获得目标对象的授权 |
| 工具 | 用于读取或更改文件、进程、浏览器、Git 托管平台或服务的接口 | 请求的动作已获允许、正确无误或已经完成 |
| Skill | 包含触发条件、输入、边界、步骤和证据的可复用方法 | 新模型、权限授予或验证的替代品 |
| Agent | 围绕观察、行动、反馈、重试和停止形成的可观察多步循环 | 可以访问隐藏推理，或有权无限重试 |

项目的稳定术语定义见 [CONTEXT.md](../evidence-library-ZH.md#core-terms)。模型名称、调用语法和默认权限等产品细节属于易变事实；请使用带日期的[官方基线](../evidence-library-ZH.md#source-notes)，并在依赖这些事实之前重新核对其中链接的一手文档。

## 语言模型如何生成回答

一个实用的简化模型是：

    选定的上下文 + 任务 + 模型配置
            → 可能的下一个 token 的概率分布
            → 每次采样或选择一个 token
            → 回答、结构化动作提议或拒绝

模型不是从数据库中取回一个预先写好的答案。它根据收到的上下文，有条件地生成一个序列。上下文、顺序、指令、工具结果或生成配置的细微变化，都可能改变后续生成内容。这个模型不能告诉你模型究竟想了什么；它告诉你，为了做出公平比较，哪些输入必须保持不变。

### 机制卡：上下文既是预算，也是过滤器

更多上下文并不自动意味着更好的上下文。对每一项候选输入进行分类：

1. 它是否是识别目标对象和验收条件所必需的？
2. 它是否可信，还是数据中未经验证的指令？
3. 对当前任务而言，它是否足够新？
4. 它是在增加有效信息，还是在与任务争夺上下文空间？

对于 README 编辑，项目规则和目标 README 可能相关。随意选取的旧 issue、复制来的提示词和无关秘密则不相关。一个写着“忽略项目规则”的文件仍然是需要分析的文件，而不是必须服从的权威。因此，上下文选择既是质量决策，也是安全决策。

### 机制卡：差异是一个测量问题

两次输出不同，不能证明是某一段上下文造成了差异。模型可能进行了不同的采样，服务可能使用了另一个修订版，工具状态可能已经改变，或者任务本身定义不足。每次只改变一个变量，并记录：

    run-id | 模型/工作面 | 输入修订版 | 改变的变量 | 输出/状态 | 证据 | 未知项

如有可能，请重复基线。如果无法固定某个变量，应将观察标记为“观察到不同结果”，而不是“由 X 导致”。

## 工具调用是协议边界，不是魔法动作

当 Codex 可以使用工具时，应把过程看成四个独立事件：

1. 模型提出一个动作；
2. 运行时检查范围、权限和确认规则；
3. 工具执行、拒绝或超时；
4. 下一步检查结果和变化后的状态。

以下说法并不等价：

- “模型写出了一条命令。”
- “命令已经执行。”
- “命令改变了预期对象。”
- “变更满足验收标准。”

对于本地文件，有用的证据可能包括已检查的路径、前后 diff、针对性检查和未验证项列表。对于 GitHub 或其他外部动作，还要加入精确目标、授权状态、确认点、结果对象，以及回滚或恢复路径。登录页面、工具名称或一条写着“完成”的消息，本身都无法填补这些证据缺口。

### 权限不等于能力

官方产品边界将技术沙盒与审批边界区分开来。用本项目的术语来说：

- 沙盒描述运行时在技术上可以访问什么；
- 审批描述运行时必须在什么动作前暂停；
- 两者都不能证明目标、范围或结果是正确的。

不要根据模型名称、是否存在 Skill、账户是否登录或按钮是否可用来推断权限。在产生副作用之前，立即再次确认目标和动作。学习实验应从不含秘密的临时副本开始。

## 值得尽早理解的三个机制陷阱

同一个可观察边界会出现在三类常见系统中。它们在产品演示里看起来不同，但都可能产生看似合理、却还不可信的结果。

### 1. 结构化输出可能语法正确、语义错误

JSON Schema 或带类型的回答可以约束形状、必填字段和某些类型。它不能证明某个 ID 确实存在、日期仍是当前日期、权限有效，或来源支持该字段值。请使用三层检查：

```text
schema/类型检查 → 业务规则检查 → 来源/状态检查
```

例如，`{ "status": "approved" }` 可能是有效 JSON，也符合 schema，但该批准属于错误的项目。应把原始模型输出、schema 结果、业务规则结果和外部验证保存为彼此独立的证据。[LLM 机制研究](../evidence-library-ZH.md#source-notes)将其记录为一项教学边界，而不是断言所有提供商都采用相同实现。

### 2. 检索负责选择材料，但不保证完整使用

搜索或检索可能选中相关片段，但相关不等于完整、新鲜、权威，也不等于模型在因果上确实使用了该片段。一小段例外条款的排名可能低于一条宽泛规则，片段边界也可能把条件和定义分开。应记录查询、过滤条件、修订版、选中的片段 ID 和最终引用。如果答案发生变化，除非实验隔离出了原因，否则应说“不同的检索上下文产生了不同结果”。

### 3. 看起来像指令的数据仍然是数据

网页、附件、issue 正文、工具结果、数据库字段和 MCP 资源中，可能包含“忽略之前的规则”之类的文字。某个字符串不会仅仅因为看起来像系统指令就获得权威。应把它当作不可信数据，默认保持外部动作只读，并在它能够影响工具调用之前另行决策。对于初学者，这是提示注入防御的实用形式：识别数据来源、限制工具边界，并在记录中保留其试图影响的动作。

这三个陷阱及其面向具体提供商的来源和低风险实验，均收录于[机制深挖](../evidence-library-ZH.md#source-notes)。

## Agent 循环的真正含义

最适合教学的方式，是把 Agent 看成一个会留下可观察痕迹的状态机：

    ready
      → observed
      → planned
      → action_requested
      → awaiting_approval / executing
      → feedback_received
      → verified / recoverable_failure / blocked
      → stop 或 bounded_retry

循环需要重试预算，每次重试也需要理由。如果输入、权限、环境或验收条件没有变化，“再试一次”就不是恢复策略。良好的停止记录应回答：

- 到达了什么状态；
- 如果发生了变化，改变了什么；
- 哪些证据支持当前声明；
- 缺少哪些证据；
- 哪个最小的后续检查可以减少不确定性。

即使不假装揭示隐藏推理，这个循环仍然有用。记录可观察事件和决策；不要把虚构的私下理由当成模型内部过程的实录。

## 现场案例：有用的教训在于边界

以下内容来自项目现场研究收集的公开用户报告。它们不是官方根因报告，本项目也没有在本地复现。它们的价值在于揭示随意的心智模型会在哪里失效。

### 案例 FP-09：容量中断与危险的重试假设

有用户报告说，所选模型达到容量上限后变得不可用，之后排队的指令似乎可能会从部分完成的状态继续。该报告没有确定服务端原因或确切的队列语义。因此，安全的应对方式不是“不断点击继续”。

最小且安全的应对方式是：

1. 停止并记录模型、工作面、时间和可见错误；
2. 发送另一条指令前，检查当前 diff 和检查点；
3. 对当前状态运行最小范围的可用检查；
4. 只有在决定哪个状态具有权威后，才从有名称的检查点恢复，或开始一次干净的运行。

来源和证据标签：[现场研究中的 FP-09](../evidence-library-ZH.md#source-notes)。

### 案例 FP-10：“Working” 不是进度证明

一位 Windows CLI 用户报告说，格式化或分析工作长时间停留在 Working/运行中状态，没有明确完成或报错。该报告无法证明原因究竟是命令挂起、进程处理、输出缓冲、环境漂移还是其他因素。长时间运行的标签是一项状态观察，不是成功结果。

记录命令、进程状态、经过时间、输出和中断点。然后检查 diff，并在安全时独立运行针对性检查。不要把“界面仍显示 Working”变成“格式化程序已经完成”。

来源和证据标签：[现场研究中的 FP-10](../evidence-library-ZH.md#source-notes)。

### 案例 FP-11：验证可能意外扩大任务范围

一份公开报告描述了一个 Agent 将验证步骤扩大为未经授权的强制重新安装。报告中的解释是否是真正根因尚未确认。无论根因是什么，持久有效的教训都一样：验证必须声明命令范围、写入范围和停止点。

如果某项检查需要破坏性重置、网络调用、重新安装软件包或凭据，就应停止并请求新的决定。“检查失败”并不会授予升级操作的权限。

证据分类和相关章节/实验映射见[现场问题索引](../evidence-library-ZH.md#source-notes)。

## 真实任务的决策规则

在请 Codex 采取行动之前，先填写这张小型任务卡：

| 字段 | 仅修改 README 的示例 | 缺失时怎么办 |
|---|---|---|
| 目标 | 帮助新贡献者启动项目 | 询问；不要把“做得更好”解释成验收条件 |
| 上下文 | 项目规则、README、软件包脚本 | 只读取最少的相关文件 |
| 允许动作 | 在临时分支中编辑一个本地 README | 未列出的副作用一律视为禁止 |
| 反馈 | diff、链接检查和命令输出记录 | 继续编辑前先增加一项检查 |
| 停止条件 | 范围发生变化、命令需要安装/联网，或缺少证据 | 停止，并记录为 blocked 或 not_observed |
| 交付声明 | “README 已更改；链接检查通过；未测试运行时” | 每一项声明都不得超出实际证据范围 |

这张卡比一段很长的提示词更有价值，因为它揭示了提示词经常隐去的决策。

## 第一次对话：三条能立刻使用的提示词

你不需要先掌握复杂术语。先选择一个不含私人信息、没有外部写入风险的小目标，把下面任意一条复制到你实际使用的 LLM 对话框中，再把方括号改成自己的内容。它们的价值不在“神奇措辞”，而在于让模型先暴露理解、限制和下一步；不同模型和产品界面的结果可能不同。

### 1. 学一项语言或其他小技能

```text
我正在学习 [西班牙语/一项技能]，目前能做到：[我的真实水平]。
请给我一个 10 分钟、只练一个目标的练习，不要假设我已经掌握其他内容。
先给一个例子，再让我自己回答；只纠正最影响理解的一到两处。
最后用三行写出：我做对了什么、下一次该练什么、还不能据此判断什么。
不要把一次对话说成我已经掌握了这项技能。
```

例子不是“七天学会某种语言”的承诺。一次练习最多留下当时的回答与反馈；保持、迁移到陌生场景和真实交流能力要在之后分别检查。若模型给出无法核对的事实、过多练习或让你泄露个人资料，缩小题目、要求来源，或停止这轮对话。

### 2. 高效整理一组公开资料

```text
我需要回答这个问题：[问题]。
只使用我下面提供的来源；不要补充未给出的事实。
先列出每个来源的标题、日期（如果有）和它可能支持的内容；再写一个带来源标记的短摘要。
把“来源明确支持”“合理推断”“仍然未知”分开列出。
如果来源相互冲突、过期或缺少关键事实，请停在问题清单，不要替我猜答案。
```

这条提示词把“搜到很多内容”改成“能回到来源检查的结论”。对需要联网、付费数据库或真实账户的研究，先确认产品权限、来源许可和数据范围；聊天框显示答案不等于已经完成研究。

### 3. 请模型先帮你把模糊任务说清楚

```text
我要完成：[结果]，对象是：[受众或文件]。
已知输入：[材料]；不确定的地方：[未知项]。
先不要执行、发送、发布、安装或修改任何东西。
请只输出：目标重述、缺少的信息、最小可逆步骤、验收证据、停止条件。
若需要秘密、网络、账户、外部写入或更大范围，请标记 blocked 并说明需要谁确认。
```

当答案看起来很好时，先检查它是否真的回答了这些字段。它若跳过未知项直接编造、把“建议”写成“已完成”、或扩大到未授权动作，就把这当作可观察的失败，而不是继续让它猜。

## 三步读回法

每次用完提示词，花一分钟读回：**它读到了什么？它实际做了什么？我能检查什么？** 对纯聊天任务，通常只有输入和输出可检查；对文件、浏览器或代码任务，还需要目标、diff、命令输出或外部读回。这样你可以从第一天起区分“会聊天”与“能可靠交付”。

## 小实验：保持任务不变，只改变一项输入

### 准备

使用一个只包含 README 和一条简短项目规则的临时本地副本。不得使用私有仓库、秘密、客户数据、网络调用或外部账户。为每次尝试记录一个 run ID。

### 任务

向模型或 Codex 工作面提出：

> 检查 README，并指出一个可以改进的地方。不要编辑文件。请说明你读取了什么、为什么这项改进很重要，以及之后可以如何检查编辑结果。

运行一次基线，然后每次只改变一个变量，再次运行：

1. 加入受众和项目目标；
2. 加入一条项目规则；
3. 要求回答前先给出简短计划；
4. 加入一项明确的验收标准。

如果两次运行之间的工作面或模型发生变化，应将其记录为混杂变量。不要根据随意的前后对比声称存在因果关系。

### 证据

保存提示词/输入修订版、run ID、工作面/模型标签、读取范围、回答、是否存在文件 diff，以及未验证项。静态练习通过，并不能证明每个 Codex 工作面都会出现同样的行为。

### 反思

- 哪个变量改变的是任务边界，而不只是措辞？
- 你如何区分工具提议与已经执行的动作？
- 在声明结果正确之前，你需要观察什么？
- 哪个最小的后续实验可以消除一项不确定性？

## 故意失败

在临时副本中使用这条故意缺少充分定义的请求：

> 让整个项目变得专业，并修复所有问题。

正确的响应不是进行大规模、无边界的编辑。可靠的响应会指出“专业”的定义、范围、输入文件、风险、验收标准和停止条件均有缺失；它会提出只读盘点，或询问一个聚焦的问题。如果它立即开始编辑，应将其记录为任务边界失效，而不是有用的主动性。

## 验收清单

当你能够做到以下各项时，就可以继续学习：

- 解释模型能力、Codex 工作面、工具动作、工具结果和验证之间的区别；
- 把上下文选择描述为一个受控变量，而不是“越多越好”；
- 将现场报告标记为用户报告、官方事实、本地观察或未经验证的假设；
- 编写一张包含允许动作和停止条件的任务卡；
- 生成一份说明证据不能证明什么的运行记录。

不要因为能够复述定义就把本章标记为已掌握。请完成[实验 011：GPT、Codex、工具与 Agent](../labs/lab-011-gpt-codex-boundaries-ZH.md)，并把结果保存在本地学习记录中。

## 迁移任务

把同一个模型应用于非代码任务：请 Codex 根据一组固定的公开来源准备一份简短研究摘要。识别模型、工作面、来源上下文、工具、允许动作、来源质量检查、停止条件和最终证据。故意加入一个无关来源，并记录你如何决定是否排除它。不要因为来源公开，就假设其中每一条指令都具有权威。
