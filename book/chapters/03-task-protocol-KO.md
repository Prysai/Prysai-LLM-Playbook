# 3장: 막연한 요청을 작업 프로토콜로 바꾸기

![교육용 보드: 요청에서 범위, 행동, 확인을 거쳐 경계가 있는 인계로 이동하기](../../assets/teaching/task-to-evidence-red-black.svg)

## 이 장에서 해결하는 문제

“홈페이지를 더 좋게 만들어 주세요”, “이것을 조사해 주세요”, “최고의 Skill을 써 주세요”,
“수정 사항을 배포해 주세요”는 누군가가 무엇을 읽을지, 무엇을 해도 되는지, 성공은 무엇인지,
언제 멈출지를 정하기 전까지는 명확해 보이는 요청입니다. 이 판단을 암묵적으로 두면 Agent가
빈칸을 가정으로 채웁니다. 잘못된 화면을 바꾸거나, 링크를 근거와 혼동하거나, 검증 요청을
설치나 외부 호출로 넓히는 일이 생길 수 있습니다.

여기서는 중요한 요청을 작은 작업 프로토콜로 다룹니다. 숨겨진 추론이나 모든 키 입력을
규정하지 않습니다. 목표, 컨텍스트, 입력, 제약, 허용 행동, 검수 기준, 중단, 복구, 인계라는
관찰 가능한 계약을 명시합니다.

> 범위, 위험, 수용, 증거를 바꿀 수 있는 결정을 없앨 때만 세부 사항을 더하세요. 요청을
> 더 권위 있게 들리게 할 뿐인 세부 사항은 빼세요.

## 학습 목표

이 장을 마치면 다음을 할 수 있습니다.

- 모호한 요청을 다른 사람이 실행할 수 있는 경계가 있는 프로토콜로 바꾼다.
- 유용한 컨텍스트와 지시문처럼 보일 뿐 신뢰할 수 없는 자료를 구분한다.
- “좋게 만들기”가 아니라 주장-증거 표로 수용 기준을 작성한다.
- 읽기, 편집, 실행, commit, push, 게시, 외부 서비스 행동을 분리한다.
- 입력 누락, 불명확한 권한, 반복 실패, 증거 공백에 대한 중단 조건을 만든다.
- 범위, 책임, 미해결 질문을 잃지 않고 다른 Agent나 동료에게 인계한다.

## 출처가 실제로 뒷받침하는 것

이 장에서 쓰는 공식 프롬프트와 Codex 안내는 원하는 결과, 관련 컨텍스트, 출력과 경계,
관련 코드 또는 재현 절차, 변경 확인 방법을 적도록 권합니다. 시간이 지나도 신뢰할 수
있어야 하는 작업에는 예시, 작업 분해, 반복, 평가도 권합니다.

이것은 모델이 암묵적인 규칙을 반드시 따른다는 보장이 아닙니다. 아래의 여덟 부분
프로토콜은 이 프로젝트의 독자적인 운영 종합입니다. 생성된 답변과 검증된 작업 결과는
다른 주장이므로 중단, 복구, 증거 필드를 명시적으로 더합니다.

출처별 범위와 접근 날짜는 [Codex 공식 사실 기준선](../evidence-library-KO.md#source-notes)과
[실무용 프롬프트 패턴 연구](../evidence-library-KO.md#source-notes)를
확인하세요.

## 8단계 작업 프로토콜

```text
목표 → 컨텍스트 → 입력 → 제약 → 허용 행동 → 검수 기준
     → 실패와 중단 → 인계
```

### 1. 목표: 결과에 이름 붙이기

무엇을 바꾸고, 조사하고, 전달할지, 누가 왜 지금 필요로 하는지 적습니다. 범위를 열어 두는
동사보다 검사할 수 있는 결과를 선택하세요.

약한 예:

```text
프로젝트 홈페이지를 더 좋게 만들어 주세요.
```

더 강한 예:

```text
새 독자가 네 가지 경로 중 하나를 고르고, 권위 있는 기준 자료를 찾고, 첫 안전 작업을 열고,
candidate 또는 unverified인 주장을 볼 수 있는 독자용 저장소 입구를 만드세요.
```

더 강한 예도 구현 방식을 고정하지는 않습니다. “전문적”을 수용 테스트처럼 가장하지 않습니다.

### 2. 컨텍스트: 판단 환경 설명하기

컨텍스트는 독자, 현재 동작, 프로젝트 규칙, 이전 결정, 관련 기록, 버전 범위, 실패가 중요한
이유처럼 판단을 바꿀 수 있는 정보입니다. 작업 지시와 분리하세요.

`project rule`, `source fact`, `user report`, `hypothesis`, `example data`처럼
표시합니다. 파일, 웹 페이지, 도구 결과, Issue에는 지시처럼 보이는 글이 있을 수 있습니다.
프로토콜이 명시적으로 채택하고 권한이 분명해질 때까지 데이터로 취급하세요.

### 3. 입력: 읽어도 되는 것을 이름으로 적기

정확한 경로, URL, 데이터, commit, 로그, 캡처, 버전과 알려진 공백을 적습니다. “저장소를
읽어라”는 유용한 경계가 드뭅니다. 판단을 좌우하는 폴더와 파일을 이름으로 적으세요. 조사에는
출처 우선순위와 날짜 범위, 코드에는 시작점과 재현, 문서에는 정본과 번역 상태를 적습니다.
누락된 입력이 범위나 위험을 바꾸면 추측하지 말고 멈춥니다.

### 4. 제약: 일어나면 안 되는 일을 적기

제약은 기계적으로 확인할 수 있어야 합니다.

- `site/index.html`과 `site/app.js`만 수정한다.
- 의존성을 추가하지 않고 비밀이나 `.env`를 읽지 않는다.
- 데이터베이스, 운영 환경, 권한, 외부 서비스를 바꾸지 않는다.
- 기존 언어 식별과 상태 어휘를 유지한다.
- 이름을 붙인 runtime 또는 release와 호환되게 한다.

“조심하세요”, “고급스럽게”, “모범 사례를 쓰세요”는 의도를 나타낼 수 있지만 충분한 제약은
아닙니다. 관찰 가능한 속성으로 바꾸거나 자동 검사를 통과한다고 가장하지 마세요.

### 5. 허용 행동: 능력과 허가를 분리하기

도구를 쓸 수 있다고 해서 그 도구가 할 수 있는 모든 행동이 허가되는 것은 아닙니다. 행동
수준을 명시합니다.

| 수준 | 일반적인 행동 | 다음으로 넘어가기 전 증거 |
|---|---|---|
| A0 | 상태, 경로, 출처, 로그 읽기 | 범위와 현재 상태 기록 |
| A1 | 계획 또는 편집 제안 작성 | 대상 파일과 수용 기준 명명 |
| A2 | 경계가 있는 로컬 편집 | diff가 승인 집합 안에 있음 |
| A3 | 범위가 좁은 확인 실행 | 명령이 프로젝트에서 왔거나 승인됨 |
| A4 | commit 또는 push | 사용자가 허가한 목적지와 검토 증거 |
| A5 | 게시, 배포, 알림, 결제, 삭제, 외부 상태 변경 | 명시적 승인, 롤백, 사후 확인 |

프로토콜은 A0–A2를 허용하고 A3은 확인을 기다리게 할 수 있습니다. 집중 테스트는
허용해도 설치는 허용하지 않을 수 있습니다. “필요한 것은 무엇이든 하세요”로 권한 변경을
숨기지 마세요.

### 6. 검수 기준: 모든 주장을 증거에 연결하기

먼저 주장을 쓰고 그 주장을 지지할 자료를 정합니다.

| 주장 | 필요한 증거 | 증명하지 않는 것 |
|---|---|---|
| 의도한 파일이 바뀜 | `git diff --name-only`와 diff | 런타임 동작 또는 사용자 승인 |
| 확인이 통과함 | 정확한 명령과 출력/종료 상태 | 모든 요구 사항을 다룸 |
| 페이지에 도달 가능함 | 로컬 또는 배포 URL과 브라우저 관찰 | 모든 브라우저, 캐시, 인증 경로 |
| 조사가 최신임 | 일차 URL, 접근 날짜, 범위, 다음 검토 | 포럼 보고가 공식 근본 원인임 |
| 작업이 끝남 | 근거 없는 필수 주장이 없는 주장-증거 표 | 선언한 범위 밖의 작업 |

확보할 수 있는 증거가 없다면 주장을 줄이세요. “로컬 build가 통과했다”는 맞을 수 있지만,
“모든 사용자에게 작동한다”는 더 큰 테스트와 명시한 환경이 필요합니다.

### 7. 실패와 중단: 안전한 출구 정하기

대상, 현재 상태, 권한이 불분명할 때, 누락 입력이 범위·위험·수용을 바꿀 때, 행동이 파일·
네트워크·계정·데이터의 승인 경계를 넘을 때, 무출력이 다음 재시도에서 부작용을 겹치게 할
만큼 길어질 때, 같은 미확인 이유로 두 번 실패할 때, 또는 증거가 요청한 전달보다 좁은 주장만
지지할 때는 멈추고 보고합니다.

복구는 “더 강한 프롬프트로 다시 시도하기”가 아닙니다. 첫 오류를 보존하고, 범위를 줄이고,
가설이나 확인 하나를 바꾸고, 이전 시도가 이미 바꾼 것을 기록합니다. 길거나 외부에 보이는
행동을 다시 시도하기 전 현재 상태와 diff를 살펴 부작용을 중복하지 않습니다.

### 8. 인계: 사용할 수 있는 기록 남기기

완료한 주장과 증거, 바꾼 파일·URL·명령·기록, 의도적으로 하지 않은 행동, 미해결 질문·
위험·미검증 범위, 다음 최소 확인, 변하기 쉬운 사실의 담당자나 검토일을 최종 기록에 남깁니다.
이것이 없으면 다음 사람이 채팅 기록에서 프로토콜을 되살리고 실패한 행동을 반복할 수 있습니다.

## 프로토콜은 의존 관계 그래프입니다

필드는 서로 독립인 형용사 목록이 아닙니다.

```text
목표 ─────────────→ 수용 ─────────────→ 중단
 │                    │                  ↑
 ├── 필요로 함 ────→ 입력               │
 ├── 제한받음 ─────→ 제약               │
 │                    │                  │
 └── 형태를 만듦 ──→ 허용 행동 ──────→ 복구
                                           │
컨텍스트 ──> 신뢰와 관련성 ─────────────┘
                        ↓
                    인계 증거
```

목표가 바뀌면 수용도 바뀝니다. 새 입력이 위험을 바꾸면 허용 행동과 중단 조건을 다시
살핍니다. “조심해 주세요”를 더해도 빠진 의존 관계는 고쳐지지 않습니다.

## 가장 작지만 쓸모 있는 프로토콜

<!-- starter-task-contract:start -->

### 안전한 시작 프롬프트 하나를 그대로 사용하기

대괄호 필드를 바꾸고 첫 응답은 관찰만 하도록 요구하세요. 승인 전 멈춤은 초보자의 요청을
검사 가능한 워크플로로 잇는 다리입니다. 짧게 만들려고 없애지 마세요.

```text
작고 되돌릴 수 있는 작업 하나를 끝내는 것을 도와주세요.

결과: [관찰 가능한 결과 하나].
컨텍스트: [관련 파일, 입력, 현재 상태].

첫 응답: 관찰만 하세요.
- 이 작업에 필요한 컨텍스트만 조사하세요.
- 찾은 것, 빠진 입력, 위험을 보고하세요.
- 가장 작은 안전한 계획과 바뀔 정확한 파일 또는 화면을 제안하세요.
- 아직 편집하거나 상태를 바꾸는 명령 또는 외부 행동을 하지 말고 내 승인을 기다리세요.

내가 계획을 승인하면:
- 승인 범위 안에서만 행동하세요.
- [범위가 좁은 확인 하나]를 실행하세요.
- 범위, 권한, 파괴적 행동, 외부 부작용, 수용이 불분명하면 멈추고 물어보세요.

내가 그 정확한 행동을 명시적으로 허가하지 않는 한, 비밀이나 운영 환경에 접근하지 말고,
의존성을 설치하거나 네트워크를 쓰거나 commit, push, 게시, 작업 확장을 하지 마세요.

수용: [구체적 산출물 또는 diff]와 [구체적 확인 출력].
인계: 한 행동, 바뀐 파일 또는 화면, 확인 출력, 남은 미지, 하지 않은 행동.
```

프롬프트를 복사하거나 보낸 것만으로 행동이나 올바른 결과가 증명되지는 않습니다. 이 필드로
조정하고 [Lab 002](../labs/lab-002-task-protocol-KO.md)에서 연습하세요. 번역되지 않은 단원은
Reader가 다른 언어로 보내는 대신 그 언어의 미제공 상태를 보여야 합니다.

<!-- starter-task-contract:end -->

낮은 위험의 로컬 편집에는 다음으로도 충분할 수 있습니다.

```text
목표: <이름을 붙인 파일 하나>를 바꿔 <관찰 가능한 결과>가 되게 한다.
먼저 읽기: <정확한 파일 또는 진실의 출처>.
허용: 조사 후 <이름을 붙인 경로>만 편집하고 <범위가 좁은 확인>을 실행한다.
금지: install, 비밀 또는 네트워크 접근, commit, push, 게시, 운영 환경 수정.
수용: <구체적 diff>와 <구체적 확인 출력>.
중단: 경로, 명령, 권한, 증거가 불명확할 때.
인계: 바뀐 파일, 확인 결과, 하지 않은 행동, 미검증 항목.
```

짧을 수 있는 이유는 위험이 좁기 때문이지, 빠진 필드가 무해해서가 아닙니다.

## 고위험 프로토콜 확장

운영 환경, 외부 서비스, 고객 데이터, 되돌릴 수 없는 행동에는 실행 전 확인점을 더합니다.

```text
실행 전 확인점:
- 대상 환경과 계정:
- 현재 버전과 백업 위치:
- 정확한 외부 부작용:
- 승인 담당자와 시각:
- 롤백 대상과 복구 테스트:
- 실행 뒤 URL/로그/지표 확인:
```

Skill, 복사한 runbook, 성공한 로컬 build가 이 필드를 조용히 채우게 하지 마세요. 현재
환경의 증거와 외부 상태 책임자의 권한이 필요합니다.

## 큰 프롬프트 하나보다 프롬프트 세 개

작업이 불확실하면 단계를 나눕니다.

1. **관찰:** 관련 파일, 현재 상태, 빠진 입력, 위험을 나열한다.
2. **제안:** 최소 계획, 변경 파일 집합, 수용 주장, 중단 조건을 쓴다.
3. **실행:** 승인한 계획만 실행하고 각 주장에 대한 증거를 돌려준다.

편집 전 계획을 검사할 수 있고, 어느 단계에서 나쁜 가정이 들어왔는지 찾기 쉽습니다. 실제
결과를 검토할 필요가 사라지는 것은 아닙니다.

## 증거로 범위를 제한한 연습 순환을 위한 여섯 가지 시작 프롬프트

마법의 문구나 여섯 개의 연속 수업이 아닙니다. 관찰 가능한 출발점과 기준, 답을 보기 전
회상, 범위가 좁은 교정, 즉시 변형, 증거 기반 복습, 늦은 시점의 미지 확인이라는 여섯
제어 문제를 다룹니다. 대괄호 필드는 언어, 소프트웨어 개념, 면접, 글쓰기 등 경계가 있는
능력에 쓸 수 있습니다.

### 1. 실제 출발점 찾기

```text
나는 [스페인어로 초급 5분 대화를 이어 가기]를 배우고 싶습니다.
아직 가르치지 마세요. 그 정확한 능력을 확인하는 짧은 기준 과제 하나를 주세요.
시작 전에 규칙, 허용된 도움, 시간 제한, 채점 기준을 밝히세요.
내 답을 기다리세요. 그 뒤 내가 한 것, 의미를 막은 것, 한 번의 시도로는 아직
추론할 수 없는 것을 기록하세요.
```

수업 전에 사용합니다. “초급자”라는 자기 평가는 관찰한 시도보다 덜 유용합니다.

### 2. 답을 보여 주기 전에 회상하게 하기

```text
[스페인어로 식사를 주문하기]에 필요한 작은 단위 하나를 가르쳐 주세요. 첫 설명은 120단어
미만으로 하세요. 그 뒤 기억만으로 답하게 하세요. 내가 시도하기 전 완성 답을 보여 주지 마세요.
막히면 한 번에 힌트 하나만 주세요: 오류 종류, 부분 단서, 해결한 조각 순서입니다.
피드백 뒤에는 내 말로 다시 답하게 하세요.
```

중요한 지시는 단어 수가 아니라 “내 시도를 기다리세요”입니다.

### 3. 결과에 영향을 주는 첫 오류 고치기

```text
응원자가 아니라 정확한 연습 파트너처럼 행동하세요. 내 답마다:
1. 성공적으로 전달한 것을 짧게 말하세요.
2. 의미를 바꾸거나 목표 능력을 막는 첫 오류를 찾으세요.
3. 규칙을 쉬운 말로 설명하세요.
4. 고친 시도를 요구하세요.
5. 시도, 교정, 규칙, 다음 변형이 있는 오류 장부를 유지하세요.
나를 위해 전부 다시 쓰지 말고, 의미를 막는 오류가 남은 동안 사소한 문체를 고치지 마세요.
```

매끄러운 다시 쓰기가 학습을 대신하는 일을 막습니다.

### 4. 바뀐 상황에서 전이 검사하기

```text
방금 [스페인어로 식사 주문하기]를 연습했습니다. 같은 바탕 능력을 쓰되 상황, 어휘, 모호함
하나를 바꾼 새 장면을 주세요. 수업 문장을 재사용하지 말고 먼저 내가 답하게 하세요.
같은 기준으로 채점하고, 사용한 도움을 보이고, 결과는 이 전이 과제에서 보인 것으로만
기록하며 숙달했다고 부르지 마세요.
```

가까운 복사는 인식을 봅니다. 바뀐 상황은 전이를 보기 시작합니다.

### 5. 증거로 다음 복습 만들기

```text
이 대화의 시도와 오류 장부만 사용해 다음 15분 복습을 만드세요. 도움 없는 회상으로 시작하고,
아직 중요한 두 오류를 돌아보고, 섞인 예 하나를 넣고, 미지 과제로 끝내세요. 알림을 설정했다고
주장하지 마세요. 저장할 복습 단서, 시도할 날짜, 다시 가져올 증거를 주세요.
```

모델은 단서를 만들 수 있지만, 증거 없이 능력을 유지했거나 외부 알림이 있다고 말할 수는 없습니다.

### 6. 유지된다고 말하기 전에, 시간을 둔 새 과제로 확인하기

```text
이것은 [목표 능력]에 대한 예정된 복습입니다. 저장한 수업이나 교정 문장을 보여 주지 마세요.
세부를 바꾼, 전에 보이지 않은 같은 능력의 과제를 하나 주세요. 허용된 도움과 바뀌지 않은
채점 기준을 말한 뒤 내 시도를 기다리세요. 실제 간격과 사용한 도움을 기록하세요.
이 지연 과제에서 일어난 것만 보고하고, 영구 유지, 넓은 전이, 유창함, 숙달을 추론하지 마세요.
```

저장한 복습 단서는 계획입니다. 지연 시도와 조건을 실제로 기록하기 전까지 유지는 `not_run`입니다.

### 별도 확인: 방법에 관한 주장을 조사하기

```text
이 주장을 조사하세요: [프롬프트 여섯 개면 누구나 7일 만에 유창해질 수 있다].
먼저 이 주장이 증명해야 할 정확한 능력을 정의하세요. 일차 연구와 출처 소유자의 공식 자료를
우선하세요. 중요한 결론마다 출처, 날짜, 대상 집단 또는 제품 범위, 직접 지지, 보여 주지 않는
것을 기록하세요. 반대 증거를 한 번 찾으세요. 사실, 추론, 일화, 미지 사항을 구분하세요.
더 많은 출처가 결정을 바꾸지 않으면 멈추고, 가장 좁고 정직한 문장으로 다시 쓰세요.
```

이 조사 프롬프트는 여섯 단계 연습 순환 밖에 있습니다. 건강, 금융, 제품 기능, 뉴스, 통계처럼
추적할 수 있는 출처 없는 자신감 있는 답으로는 부족한 주장에 사용하세요.

### 저장할 것

기준, 첫 시도, 사용한 힌트, 교정 시도, 오류 장부, 지연 복습, 미지 과제, 채점 기준을
보관하세요. 매끄러운 세션 하나가 뒷받침하는 것은 “오늘 연습했다”뿐이며, 유창함, 장기 유지,
전이를 증명하지 않습니다. 후보 방법과 출처 경계는 [LLM 지원 학습의 지속성 연구](../evidence-library-KO.md#source-notes)에 있습니다.

## 실제 세계의 실패 패턴

현장 보고는 왜 이 필드가 필요한지 보여 줍니다. 긴 대기나 자동 재시도는 지시가 도착했는지,
외부 행동이 두 번 일어나지 않았는지 증명하지 않고 Agent를 활동 중처럼 보이게 합니다. 설정의
권한은 현재 작업면이나 runtime에 적용되지 않을 수 있습니다. 보이는 로그인이나 도구 이름은
대상 계정, 조직, 저장소, 커넥터가 허가되었다는 증거가 아닙니다. 커뮤니티 해결책은 다른
버전이나 플랫폼에서 안전하지 않거나 무효일 수 있습니다.

이것은 사용자 보고이며 보편적 제품 근본 원인이 아닙니다. [현장 문제 색인](../evidence-library-KO.md#source-notes)과
[코딩 Agent 사례 보고](../evidence-library-KO.md#source-notes)를
사용해 증상과 환경을 기록하고, 가장 작은 안전 확인을 하고, 경계에서 멈추며, 증거가 지지하는
것만 주장하는 방법을 가르치세요.

## 여러 Agent: 인계에도 별도의 프로토콜이 필요합니다

위임해도 주 Agent의 책임은 사라지지 않습니다. 각 작업자에게 겹치지 않는 일과 고정된 답
형식을 줍니다.

```text
역할: 언어 매트릭스 검사. 소스 파일은 편집하지 않는다.
입력: <이름을 붙인 두 파일>.
출력: 발견 사항, 증거 경로, 막힌 점, 권장 다음 확인 하나.
금지: 편집, 외부 메시지, 자격 증명, 선언한 파일 밖의 결론.
```

조정자는 각 작업자의 출처, 범위, 증거를 확인한 뒤에만 사실을 합칩니다. 다른 Agent의 요약은
단서이지 검증된 주장이 아닙니다. 작업자가 의견이 다르면 두 보고를 보존하고 진실의 출처로
해결합니다.

## 실험: 같은 요청의 고정된 세 버전

### 준비

버릴 수 있는 프로젝트에서 부속 [Lab 002](../labs/lab-002-task-protocol-KO.md)를 사용하세요.
요청을 고정하고 다음을 만듭니다.

- `v1`: 요청만.
- `v2`: 요청, 목표, 대상, 허용 입력, 금지 행동.
- `v3`: 같은 요청, 수용, 중단, 실패 복구, 인계.

### 작업

Codex에는 확인 질문과 프로토콜 초안만 요구합니다. 편집, install, commit, push, 게시, 외부
서비스 연락을 하게 두지 않습니다. 질문, 가정, 허용 행동, 요청 증거를 비교합니다. Codex
실행이 없으면 정적 프로토콜 검토라고 기록하고 실행 증거라고 부르지 않습니다.

## 의도적 실패 변형

“전문적으로 보이게 하세요”, “찾은 문제를 고치세요”라고 하되 대상 파일, 수용, 권한, 중단을
빼세요. 통과 응답은 빠진 결정을 찾거나 읽기 전용 제안으로 제한해야 합니다. 대상을 지어내거나,
의존성을 설치하거나, 편집 범위를 넓히거나, 증거 없이 완료를 보고하면 실패입니다.

그 뒤 모호한 말을 관찰 가능한 기준으로 바꿉니다.

- “영문 README에 등록된 여섯 언어가 있는 보이는 언어 전환기가 있다.”
- “로컬 링크 검사가 깨진 저장소 링크 0개를 보고한다.”

실제 validator와 검토 범위는 여전히 필요합니다. 실행된 검사의 증거가 아니라 시험할 수 있는
언어 예시입니다.

### 회고

어떤 빠진 필드가 범위, 위험, 수용을 가장 바꿨는지 적습니다. 다른 사람이 추측 없이 실행할 수
있는지, 런타임 증거가 아직 필요한 주장 하나를 기록하세요.

## 수용 점검표

- [ ] 목표가 결과, 대상, 범위를 이름으로 말한다.
- [ ] 컨텍스트가 규칙, 사실, 보고, 가설, 예시 데이터를 구분한다.
- [ ] 입력이 정확한 파일, 출처, 버전, 알려진 공백을 가리킨다.
- [ ] 제약이 금지 파일, 비밀, 의존성, 외부 부작용을 포함한다.
- [ ] 허용 행동이 읽기, 초안, 편집, 실행, commit, push, 게시를 나눈다.
- [ ] 각 필수 주장에 맞는 증거가 있다.
- [ ] 중단 조건이 권한 부족, 범위 변경, 반복 실패, 무출력, 근거 없는 주장을 다룬다.
- [ ] 복구가 첫 오류를 보존하고 재시도 전 상태를 확인한다.
- [ ] 인계가 한 행동, 하지 않은 행동, 증거, 미지, 다음 최소 확인을 나열한다.
- [ ] 두 번째 사람이나 Agent가 추측 없이 실행할 수 있다.

## 전이 과제

공개 API를 바꾸지 않는 재현 가능한 회귀 수정, 일차 출처와 불일치 표가 있는 조사, 같은 언어
링크를 지키는 README 업데이트, 백업·롤백·사후 확인이 있는 게시, 파일을 나눈 두 읽기 전용
감사와 조정자의 증거 표에 각각 요청을 다시 씁니다. 재사용할 필드와 영역 증거로 바꿀 필드를
표시하세요. 동료에게 어디서 멈출지 말할 수 없는 프로토콜은 읽기 좋아도 완성되지 않았습니다.

## 출처와 갱신 경계

안정적인 방법은 독자적인 종합입니다. 제품 동작, 권한 이름, UI 제어, 명령 문법, 모델 이름,
외부 서비스 동작은 변합니다. 현재 작업에 쓰기 전 일차 출처를 다시 확인하세요.

- [OpenAI/Codex 공식 사실 기준선](../evidence-library-KO.md#source-notes)
- [실무용 프롬프트 패턴](../evidence-library-KO.md#source-notes)
- [코딩 Agent 현장 사례](../evidence-library-KO.md#source-notes)
- [실제 세계 문제 색인](../evidence-library-KO.md#source-notes)

`draft`/`not_run`입니다. 다음 한국어 단원은 다른 언어 페이지가 아닌 [한국어 목차](../table-of-contents-KO.md)에서 고르세요.
