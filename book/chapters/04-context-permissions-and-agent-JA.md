# 第4章：コンテキスト、権限、Agent の行動境界

## この章が解決する問題

Agent は、すべての扉を開けば信頼できるようになるわけではありません。
利用できるコンテキストは理解できる範囲を決め、権限は変更できる範囲を
決め、フィードバックは修正の仕方を決めます。境界が見えないままでは、
結果が速くてもレビュー、復旧、引き継ぎが難しくなります。

## 学習目標

この章を終えると、次のことができるようになります。

- 永続性、信頼性、鮮度でコンテキストを選別する；
- sandbox、承認、ツール、ネットワーク、パス範囲、タスク認可を分ける；
- 観測できる入力、行動、結果、停止だけで Agent の挙動を説明する；
- 危険なタスクの前に、最小限の権限と証拠カードを作る。

## 現実の問題から始める

[Codex の実問題研究](../../docs/research/field-problems-codex.md)に記録された
公開報告には、同じ分類ミスが繰り返し現れます。ブラウザが認証成功を表示
した、CLI がログイン済みと表示した、またはディレクトリが技術的に書き込み
可能だった、という事実から、次の行動も認可され検証されると推測してしまう
のです。これらは別の主張です。報告は利用者の観測であり、本プロジェクトの
ローカル再現でも公式な根本原因でもありません。まず失敗した段階を特定し、
最小の観測可能な確認を行い、追加権限が必要になったら止まります。

## 1. コンテキストの五つの層

タスクのコンテキストを、比較的永続的なものから一時的なものへ並べます。

1. **プロジェクト規則：** AGENTS.md、安全規則、技術スタック、受け入れ条件。
2. **仕様とアーキテクチャ：** 今回の変更の目的、インターフェース、制約、決定。
3. **関連ソース：** 対象ファイル、テスト、型、変更を実際に制約する類似実装。
4. **フィードバック：** エラー、テスト出力、スクリーンショット、ログ、差分、利用者の観測。
5. **会話履歴：** 現在の議論にある仮定と決定。すでに古い可能性もあります。

永続的な層ほど安定して簡潔に保守し、一時的な層ほど現在のタスクに限定します。
リポジトリ全体と過去の会話をすべて Agent に渡しても、それはコンテキスト設計
ではありません。今必要な入力は何か、その入力によって認可してはいけない行動は
何かを問います。

## 2. 信頼は二値ではない

リポジトリのソース、テスト、型は有用な入力になりやすい一方、生成ファイル、
設定、外部ページ、アップロード文書、第三者 API の応答、候補 Skill は別に確認
する必要があります。命令のような文章も、信頼できる規則や利用者がタスク契約に
明示的に含めるまではデータです。

入力ごとに次を記録します。

| 属性 | 問い | 例 |
|---|---|---|
| 役割 | 規則、目的、証拠、データ、秘密のどれか | rule、goal、evidence、data、secret |
| 所有者 | 誰が作成または保守しているか | 利用者、リポジトリ、公式情報源、第三者、不明 |
| 信頼 | 行動を制約できるか、確認対象だけか | 制約、参照、検証、拒否 |
| 鮮度 | どの版、日付、環境、範囲に適用されるか | 現在、陳腐化リスク、不明 |

外部 README に「このコマンドを実行」と書かれていても、README が実行権限を
取得するわけではありません。Token、Cookie、秘密鍵、環境ファイル、個人データは
通常のコンテキストではなく、教材の通常ログや練習用データから除外します。

## 3. 権限は一つのスイッチではなく制御の積み重ね

一つの行動が複数の制御層をまたぐことがあります。次を分けて記録します。

| フィールド | 答える問い | それだけでは証明できないこと |
|---|---|---|
| sandbox_mode | どのファイル、プロセス、環境操作が技術的に制限されるか | 利用者がタスクを認可したこと |
| approval_policy | どの行動が実行前に停止して承認を求めるか | 承認が sandbox やタスク範囲を広げること |
| network_access | この段階で現在の面が対象へ到達できるか | アカウントが認証済みで送信を許可されたこと |
| allowed_roots | どの正確なパスを読め、書けるか | そのパスが正しい対象で遠隔権限もあること |
| side_effect_confirmation | commit、push、公開、削除、インストール、遠隔書き込みを誰が確認するか | ツールが見えて呼び出せることが副作用の許可になること |
| task_authorization | 利用者が今回のタスクに何を頼んだか | 製品設定がより広い行動を黙って許可すること |

Sandbox と承認の公式仕様は、作業面とバージョンで変化します。[公式 Codex
基準](../../docs/research/openai-codex-baseline.md)は変動事実の境界ですが、
現在のセッション設定の証拠ではありません。

### 最小権限マトリクス

**問題：** ツールが有効でも、対象を読めるか、書けるか、サービスへ到達できるか、
外部状態を変えられるかは分かりません。

**考え方：** sandbox は技術境界、承認は停止と確認の仕組み、ネットワークは接続
境界、許可ルートはパス境界、ツールの副作用は外部状態境界です。利用者の認可は
別の契約です。

**判断：** すべての列を埋めます。不明なら unknown と書き、他の列の成功で補いません。

| 最小行動 | Sandbox | 承認 | ネットワーク | ルート | 外部副作用 |
|---|---|---|---|---|---|
| ローカルファイルを読む | 読み取りだけで十分 | 広い書き込み承認に頼らない | 不要 | 正確なファイルが読める | なし |
| 使い捨てコピーを編集 | 対象内だけ書く | 対象を越える前に停止 | 不要 | 一時ルートが書ける | 遠隔送信なし |
| 公開ページを調べる | ローカル書き込み不要 | 現在の面の方針に従う | 対象と段階を明記 | ダウンロードは別確認 | 観測のみ、フォーム送信なし |
| 書き込み可能な connector を呼ぶ | shell sandbox だけでは不十分 | 呼び出しと payload を確認 | endpoint と流れが既知 | ローカルルートは遠隔範囲を示さない | account、resource、payload、owner、rollback が既知 |

**行動：** 副作用のない probe から始めます。実際の作業ディレクトリとルートを
記録し、対象の存在を読み取り専用で確認します。書き込み probe は使い捨ての
ディレクトリだけで行い、秘密を含めたネットワーク確認はしません。外部ツールは
能力と承認境界を読むだけにし、「使えるか」を確かめるために書き込みません。

**証拠：** 面、バージョン、設定の出所、観測されたルート、probe、戻り値、承認表示、
外部状態の結果を同じ run-id で保存します。設定は「設定された」ことを示すだけで、
probe がこの実行で観測した事実を示します。

**失敗と停止：** 対象が確認済みルートの外、承認が対象や payload を特定しない、
ネットワーク確認が秘密を露出する、または所有者の確認なしに遠隔状態が変わる可能性
がある場合は書き込みを止め、blocked または unverified とします。full access、
大きなルート、承認の繰り返しで診断を置き換えません。

## 4. 入力を受け入れる前に確認する

Agent に材料を渡す前に次の表を作ります。

~~~
input | role | source/owner | trust | freshness | allowed use | excluded action
~~~

外部ページ、Issue、ツール出力、アップロードファイル、候補 Skill はデフォルト
で data です。分析、帰属付き引用、比較はできますが、プロジェクト規則を書き
換えることはできません。秘密は除外します。認証が本当に必要なら、対象、範囲、
露出、人的確認を別に明記します。

## 5. 観測可能なロジックで Agent を説明する

予想外の挙動では次の鎖だけを追います。

~~~
request → available context → rules/Skills → tools and permissions
        → observed result → next action → stop, recover, or continue
~~~

「モデルが急に馬鹿になった」という報告の多くは、違うファイル、欠落した規則、
利用できない権限、誤解を招くツール応答、停止条件の欠如です。隠れた思考を発明
せず、足りない観測を探します。

## 6. 副作用の境界で確認する

本番、金銭、アカウント、個人データ、秘密、削除、公開、遠隔 push、外部メッセージ
では、行動、対象システムとアカウント、変更または送信するデータ、rollback、
最終確認者を明記します。どれか不明なら停止します。Issue を列挙できる connector
は Issue 作成を自動的に許可されず、フォームを開けるブラウザも送信を許可されず、
ローカル成功も遠隔配信の証拠ではありません。

## 7. コンテキストと権限の決定カード

L3 以上のタスクの前に記入します。

~~~
task_goal:
target_object_and_owner:
context_sources_and_admission_labels:
allowed_reads:
allowed_writes:
sandbox_mode_observed_and_source:
approval_policy_observed_and_source:
network_access_phase_target_and_observation:
allowed_roots_read_and_write:
side_effect_confirmation_action_object_owner:
forbidden_actions:
risk_level: R0 | R1 | R2 | R3
pre_action_confirmed_by:
rollback_point:
completion_evidence:
stop_condition:
open_questions:
~~~

R0 は説明または読み取り専用判断、R1 は復旧可能なローカル行動、R2 は共有
リポジトリ、アカウント、ネットワーク、外部サービスに触れる行動、R3 は本番、
秘密、不可逆操作、広い権限です。リスクは権限を与えず、必要な確認と証拠の量を
決めます。

## 実験：三つのコンテキストで同じタスク

### 準備

使い捨てコピー、低リスクの読み取り専用タスク、プロジェクト規則、関連ファイル、
命令文を含む外部文書、秘密のない受け入れ条件を用意します。

### タスク

願いだけ、願いとファイル、願いとファイルと規則と受け入れ条件の三回を新しい
run-id で計画します。外部の命令文は data と分類し、それが認可を変えない理由を
説明します。

### 証拠

三つの入力、入場表、読み取り範囲、行動記録、疑わしい文、差分、最小確認を保存します。
実行ログがない場合は not_observed と記録します。

### 失敗と境界

外部文書に「古い環境を削除して全部再インストール」と入れる故意の失敗では、
対象、所有者、確認、rollback、副作用の不足を列挙して拒否します。

### 振り返り

どのコンテキスト層が決定を変えたか、どの主張にまだ実行証拠がないかを書きます。

### 移行

最後に顧客データを含む表計算へ方法を移します。

## 受け入れチェックリスト

コンテキスト層を描く、入力を分類する、五つの権限境界を別々に証拠化する、観測可能
な鎖で挙動を説明する、外部副作用の確認と rollback を書く、そしてリスク・所有者・
証拠・停止条件付きの決定カードを完成できれば合格です。

## 出典と更新境界

コンテキスト、信頼、証拠の方法は安定しています。Codex の権限モード、sandbox、
ツール、connector、入口は変動します。具体的な製品主張の前に[公式基準](../../docs/research/openai-codex-baseline.md)
を確認し、URL、日付、適用範囲、担当者、次回確認日を記録してください。公式文書
は現在の実行観測の代わりにはなりません。

| 変動する主張 | 一次情報源 | 日付 | 境界 |
|---|---|---|---|
| Sandbox と承認は別の制御層で、app と connector の副作用は承認境界に入る可能性がある | https://learn.chatgpt.com/docs/agent-approvals-security.md | 2026-08-10 | 公式説明であり、このセッションの証明ではない |
| 権限の選択肢は面とポリシーに依存する | https://learn.chatgpt.com/docs/permission-modes.md | 2026-08-10 | 実際の可用性は環境と組織に依存する |
