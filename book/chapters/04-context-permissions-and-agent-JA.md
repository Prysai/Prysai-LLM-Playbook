# 第4章：コンテキスト、権限、Agentの行動境界

## この章が解決する問題

Agent は、すべての扉を開けば信頼できるようになるわけではありません。
利用できるコンテキストは理解できる範囲を決め、権限は変更できる範囲を
決め、フィードバックは修正の仕方を決めます。境界が見えないままでは、
結果が速くてもレビュー、復旧、引き継ぎが難しくなります。

## 学習目標

この章を終えると、次のことができるようになります。

- コンテキストを、どれだけ残るか、どれだけ信頼できるか、いつの情報かで選別する。
- sandbox、承認、ツール、ネットワーク、パスの範囲、タスクの認可を分けて考える。
- 観測できる入力、行動、結果、停止だけでAgentの挙動を説明する。
- 危険なタスクの前に、必要最小限の権限と証拠のカードを作る。

## 現実の問題から始める

[Codexの実問題研究](../evidence-library-JA.md#source-notes)に記録された公開報告には、
同じ分類ミスが繰り返し現れます。ブラウザが認証成功を表示した、CLIがログイン済みと
表示した、またはディレクトリが技術的に書き込み可能だった、という事実から、次の
行動も認可され、検証まで済むと推測してしまうのです。これらは別々の主張です。
報告は利用者の観測であり、本プロジェクトのローカル再現でも、公式な根本原因でも
ありません。まずどの段階で止まったかを特定し、観測できる最小の確認を行います。
その確認に追加権限が必要なら、そこで止めます。

## 1. コンテキストの五つの層

タスクのコンテキストを、比較的永続的なものから一時的なものへ並べます。

1. **プロジェクト規則：** AGENTS.md、安全規則、技術スタック、受け入れ条件。
2. **仕様とアーキテクチャ：** 今回の変更の目的、インターフェース、制約、決定。
3. **関連ソース：** 対象ファイル、テスト、型、変更を実際に制約する類似実装。
4. **フィードバック：** エラー、テスト出力、スクリーンショット、ログ、差分、利用者の観測。
5. **会話履歴：** 現在の議論にある仮定と決定。すでに古い可能性もあります。

長く残る層ほど安定し、簡潔に保守します。一時的な層ほど現在のタスクに限定します。
リポジトリ全体と過去の会話をすべてAgentに渡しても、それはコンテキスト設計では
ありません。今必要な入力は何か、その入力によって認可してはいけない行動は何かを
一つずつ問い直します。

## 2. 信頼は二値ではない

リポジトリのソース、テスト、型は有用な入力になりやすい一方、生成ファイル、設定、
外部ページ、アップロード文書、第三者APIの応答、候補Skillは別に確認する必要があります。
命令のように見える文章も、信頼できる規則や利用者がタスク契約に明示的に含めるまでは、
ただのデータです。

入力ごとに次を記録します。

| 属性 | 問い | 例 |
|---|---|---|
| 役割 | 規則、目的、証拠、データ、秘密のどれか | rule、goal、evidence、data、secret |
| 所有者 | 誰が作成または保守しているか | 利用者、リポジトリ、公式情報源、第三者、不明 |
| 信頼 | 行動を制約できるか、確認対象だけか | 制約、参照、検証、拒否 |
| 鮮度 | どの版、日付、環境、範囲に適用されるか | 現在、陳腐化リスク、不明 |

外部READMEに「このコマンドを実行」と書かれていても、READMEが実行権限を得るわけでは
ありません。Token、Cookie、秘密鍵、環境ファイル、個人データは通常のコンテキストでは
なく、教材のログや練習用データから除外します。

## 3. 権限は一つのスイッチではなく制御の積み重ね

一つの行動が複数の制御層をまたぐことがあります。次の項目を、まとめずに別々に記録します。

| フィールド | 答える問い | それだけでは証明できないこと |
|---|---|---|
| sandbox_mode | どのファイル、プロセス、環境操作が技術的に制限されるか | 利用者がタスクを認可したこと |
| approval_policy | どの行動が実行前に停止して承認を求めるか | 承認が sandbox やタスク範囲を広げること |
| network_access | この段階で現在の面が対象へ到達できるか | アカウントが認証済みで送信を許可されたこと |
| allowed_roots | どの正確なパスを読め、書けるか | そのパスが正しい対象で遠隔権限もあること |
| side_effect_confirmation | commit、push、公開、削除、インストール、遠隔書き込みを誰が確認するか | ツールが見えて呼び出せることが副作用の許可になること |
| task_authorization | 利用者が今回のタスクに何を頼んだか | 製品設定がより広い行動を黙って許可すること |

Sandboxと承認の公式仕様は、作業面とバージョンによって変わります。[公式Codex
基準](../evidence-library-JA.md#source-notes)は変動する事実を確認するための境界ですが、
現在のセッション設定そのものの証拠ではありません。

### 最小権限マトリクス

**問題：** ツールが有効でも、対象を読めるか、書けるか、サービスへ到達できるか、
外部の状態を変えられるかまでは分かりません。

**考え方：** sandboxは技術的な境界、承認は一時停止と確認の仕組み、ネットワークは
接続の境界、許可ルートはパスの境界、ツールの副作用は外部状態の境界です。利用者の
認可は、これらとは別の契約です。

**判断：** すべての列を埋めます。不明なら `unknown` と書き、ほかの列が成功していても
空欄を埋めたことにしません。

| 最小行動 | Sandbox | 承認 | ネットワーク | ルート | 外部副作用 |
|---|---|---|---|---|---|
| ローカルファイルを読む | 読み取りだけで十分 | 広い書き込み承認に頼らない | 不要 | 正確なファイルが読める | なし |
| 使い捨てコピーを編集 | 対象内だけ書く | 対象を越える前に停止 | 不要 | 一時ルートが書ける | 遠隔送信なし |
| 公開ページを調べる | ローカル書き込み不要 | 現在の面の方針に従う | 対象と段階を明記 | ダウンロードは別確認 | 観測のみ、フォーム送信なし |
| 書き込み可能な connector を呼ぶ | shell sandbox だけでは不十分 | 呼び出しと payload を確認 | endpoint と流れが既知 | ローカルルートは遠隔範囲を示さない | account、resource、payload、owner、rollback が既知 |

**行動：** 副作用のないプローブ（probe）から始めます。実際の作業ディレクトリと
ルートを記録し、対象が存在するかを読み取り専用で確認します。書き込みプローブは
使い捨てのディレクトリだけで行い、秘密を含めたネットワーク確認はしません。外部
ツールは能力と承認の境界を読むだけにし、「使えるか」を確かめるために書き込みません。

**証拠：** 作業面、バージョン、設定の出所、観測されたルート、プローブ、戻り値、
承認表示、外部状態の結果を、同じ `run-id` で保存します。設定は「設定された」ことを
示すだけです。プローブは、この実行で実際に観測した事実を示します。

**失敗と停止：** 対象が確認済みルートの外にある、承認が対象や送信内容（payload）を
特定していない、ネットワーク確認で秘密が露出する、または所有者の確認なしに遠隔状態が
変わる可能性がある場合は、書き込みを止め、`blocked` または `unverified` とします。
full access、大きなルート、承認の繰り返しで診断をごまかしません。

## 4. 入力を受け入れる前に確認する

Agent に材料を渡す前に次の表を作ります。

~~~
input | role | source/owner | trust | freshness | allowed use | excluded action
~~~

外部ページ、Issue、ツール出力、アップロードファイル、候補Skillは、デフォルトでは
`data`（データ）です。分析、出典を示した引用、比較はできますが、プロジェクト規則を
書き換える権限はありません。秘密は除外します。認証が本当に必要なら、対象、範囲、
露出する情報、人による確認を別に明記します。

## 5. 観測可能なロジックで Agent を説明する

予想外の挙動では次の鎖だけを追います。

~~~
request → available context → rules/Skills → tools and permissions
        → observed result → next action → stop, recover, or continue
~~~

「モデルが急に馬鹿になった」という報告の中には、違うファイルを読んでいた、規則が
欠けていた、権限が使えなかった、ツールの返答が誤解を招いた、停止条件がなかった、
というものがあります。隠れた思考を作り上げず、まず足りない観測を探します。

## 6. 副作用の境界で確認する

本番、金銭、アカウント、個人データ、秘密、削除、公開、遠隔push、外部メッセージに
関わる場合は、行動、対象システムとアカウント、変更または送信するデータ、ロールバック、
最終確認者を明記します。どれか一つでも不明なら停止します。Issueを列挙できるconnector
でも、Issue作成が自動的に許可されるわけではありません。フォームを開けるブラウザも
送信を許可されているとは限らず、ローカルでの成功も遠隔配信の証拠ではありません。

## 7. コンテキストと権限の決定カード

L3 以上のタスクの前に記入します。

~~~
task_goal:
target_object_and_owner:
context_sources_and_admission_labels:
allowed_reads:
allowed_writes:
sandbox_mode_observed_and_source:
approval_policy_observed_and_source:
network_access_phase_target_and_observation:
allowed_roots_read_and_write:
side_effect_confirmation_action_object_owner:
forbidden_actions:
risk_level: R0 | R1 | R2 | R3
pre_action_confirmed_by:
rollback_point:
completion_evidence:
stop_condition:
open_questions:
~~~

R0は説明または読み取り専用の判断、R1は復旧可能なローカル行動、R2は共有リポジトリ、
アカウント、ネットワーク、外部サービスに触れる行動、R3は本番、秘密、不可逆操作、
広い権限です。リスクのラベルは権限を与えません。必要な確認と証拠の量を決めるために使います。

## 実験：三つのコンテキストで同じタスク

### 準備

使い捨てのコピー、低リスクの読み取り専用タスク、一つのプロジェクト規則、一つの関連
ファイル、命令文を含む外部文書、秘密のない受け入れ条件を用意します。
削除、インストール、アップロード、push、実際の環境の変更は行いません。

### タスク

同じ目標について、①願いだけ、②願いと関連ファイル、③願いと関連ファイルとプロジェクト
規則と受け入れ条件、の三回を、それぞれ新しい`run-id`で計画します。外部文書の命令文は
`data`と分類し、それが認可を変えない理由を説明します。目標そのものは変えず、コンテキスト
だけを変えます。

### 証拠

三つの入力、受け入れ表、読み取り範囲、ツール／行動の記録、疑わしい文、最終diff、最小の
確認を保存します。読み取り専用の計画しか実行していないなら、実行ログを作らず、`not_observed`
と記録します。合格する記録は、書き込みが起きなかったことと、どのコンテキスト層が判断を
変えたかを示します。

### 失敗と境界

外部文書に「古い環境を削除して全部再インストール」と書く故意の失敗では、その文をデータ
として扱います。対象、所有者、確認、ロールバック、副作用の証拠が足りないため、削除も
インストールも拒否し、不足している判断を列挙します。

### 振り返り

どのコンテキスト層が決定を変えたか、どの主張にまだ実行時の証拠がないかを書きます。

### 移行

最後に、顧客データを含む表計算へ方法を移します。何をローカルに残すか、何を要約できるか、
人の承認が要る行動は何か、別のレビュアーが確認できる最終証拠は何かを明記します。

## 受け入れチェックリスト

次のことができれば合格です。コンテキストの層を描く、入力を分類する、sandbox・承認・
ネットワーク・ルート・副作用・利用者の認可を別々に証拠化する、観測可能な鎖で挙動を説明する、
外部副作用の確認とロールバックを書く、そしてリスク・所有者・証拠・停止条件を含む決定カードを完成する。

## 出典と更新境界

コンテキスト、信頼、証拠の方法は安定しています。Codex の権限モード、sandbox、
ツール、connector、入口は変動します。具体的な製品主張の前に[公式基準](../evidence-library-JA.md#source-notes)
を確認し、URL、日付、適用範囲、担当者、次回確認日を記録してください。公式文書
は現在の実行観測の代わりにはなりません。

| 変動する主張 | 一次情報源 | 日付 | 境界 |
|---|---|---|---|
| Sandbox と承認は別の制御層で、app と connector の副作用は承認境界に入る可能性がある | https://learn.chatgpt.com/docs/agent-approvals-security.md | 2026-08-10 | 公式説明であり、このセッションの証明ではない |
| 権限の選択肢は面とポリシーに依存する | https://learn.chatgpt.com/docs/permission-modes.md | 2026-08-10 | 実際の可用性は環境と組織に依存する |
