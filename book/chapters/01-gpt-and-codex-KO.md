# 제1장: Codex를 신뢰하기 전에 GPT 이해하기

## 이 장에서 해결하는 문제

사람들은 흔히 Codex를 “코드를 더 잘 작성하는 채팅 창”이라고 설명합니다.
하지만 이 설명은 실제 실패를 처음 마주하는 순간부터 쓸모가 없어집니다. 모델,
프로젝트, 컨텍스트, 권한, 도구 또는 피드백이 달라질 때 같은 요청이 왜 다르게
작동하는지 설명하지 못하기 때문입니다. 또한 자신감 있는 답변이나 도구 메시지를
작업이 실행되고 확인되었다는 증거로 간주하는 위험한 지름길을 부추깁니다.

이 장에서는 작은 운영 모델을 세웁니다. 이는 숨겨진 사고 과정(chain-of-thought)에
대한 주장이 아닙니다. 학습자가 검사할 수 있는 것, 즉 입력, 선택된 컨텍스트,
요청된 행동, 도구 경계, 반환된 결과, 변경된 상태, 그리고 중단 판단에 사용된
증거만 다룹니다.

## 학습 목표

이 장을 마치면 다음을 할 수 있어야 합니다.

- GPT, 모델, Codex 제품 표면, 도구, Skill, Agent 루프를 구분합니다.
- 사용자의 문장이 바뀌지 않아도 컨텍스트 선택과 샘플링 때문에 출력이 달라질 수
  있는 이유를 설명합니다.
- 모델이 제안한 도구 행동을 런타임 권한 확인, 도구 결과, 최종 검증과 분리합니다.
- 불확실한 완료 주장을 작고 되돌릴 수 있는 실험으로 바꿉니다.
- 공식 근본 원인을 지어내지 않고 실제 현장의 증상을 인식합니다.

## 관찰 가능한 스택에서 시작하기

작업을 분석할 때 다음 스택을 사용하세요.

    모델 역량
            ↓ 응답 또는 행동 제안을 생성
    Codex 작업 표면
            ↓ 프로젝트 컨텍스트와 실행 경계를 제공
    도구/런타임
            ↓ 요청된 행동을 허용하거나 거부하거나 실행할 수 있음
    도구 결과 / 변경된 상태
            ↓ 새로운 증거나 새로운 컨텍스트가 됨
    검증과 사람의 결정
            ↓ 작업을 중단할지 복구해야 할지 결정
    전달 주장

화살표는 자동 보장이 아닙니다. 모델은 런타임이 실행하지 않은 셸 명령을 제안할 수
있습니다. 런타임은 종료 코드가 0인 명령을 실행했지만 잘못된 파일이나 환경을
확인했을 수 있습니다. 도구는 성공처럼 보이는 메시지를 반환했지만 의도한 외부
객체를 변경하지 않았을 수 있습니다. 각 화살표에는 그에 맞는 증거가 필요합니다.

### 쉬운 말로 풀어본 용어

| 용어 | 기여하는 것 | 입증하지 못하는 것 |
|---|---|---|
| GPT | 생성 모델 역량의 한 계열 | 파일 접근, 터미널 접근, 계정 권한 또는 성공적인 변경 |
| 모델 | 한 번의 실행에 사용되는 구체적인 모델/구성 | 모든 표면에서 사용할 수 있다거나 모든 작업에 가장 적합하다는 것 |
| Codex | 모델을 프로젝트 컨텍스트, 도구, 권한에 연결하는 작업 표면 | 보이는 모든 계정이나 커넥터가 대상에 대해 권한을 갖고 있다는 것 |
| 도구 | 파일, 프로세스, 브라우저, Git 호스트 또는 서비스를 읽거나 변경하기 위한 인터페이스 | 요청된 행동이 허용되었거나 정확하거나 완료되었다는 것 |
| Skill | 트리거, 입력, 경계, 단계, 증거를 갖춘 재사용 가능한 방법 | 새로운 모델, 권한 부여 또는 검증의 대체물 |
| Agent | 관찰, 행동, 피드백, 재시도, 중단을 둘러싼 관찰 가능한 다단계 루프 | 숨겨진 추론에 대한 접근이나 무한히 재시도할 권한 |

프로젝트의 안정적인 용어는 [CONTEXT.md](../evidence-library-KO.md#core-terms)에 정의되어 있습니다.
모델 이름, 호출 구문, 기본 권한과 같은 제품 세부 사항은 변동 가능한 사실입니다.
날짜가 명시된 [공식 기준선](../evidence-library-KO.md#source-notes)을
사용하고, 이에 의존하기 전에 링크된 1차 공식 문서를 다시 확인하세요.

## 언어 모델이 답변을 생성하는 방식

유용하게 단순화한 모델은 다음과 같습니다.

    선택된 컨텍스트 + 작업 + 모델 구성
            → 가능한 다음 토큰에 대한 분포
            → 한 번에 하나씩 샘플링되거나 선택되는 토큰
            → 응답, 구조화된 행동 제안 또는 거부

모델은 데이터베이스에서 미리 작성된 답변 하나를 가져오는 것이 아닙니다. 모델은
주어진 컨텍스트를 조건으로 시퀀스를 생성합니다. 컨텍스트, 순서, 지침, 도구 결과
또는 생성 구성이 조금만 달라져도 이어지는 내용이 바뀔 수 있습니다. 이 그림은
모델이 정확히 무엇을 생각했는지 알려주지 않습니다. 공정한 비교를 위해 어떤
입력을 고정해야 하는지 알려줍니다.

### 메커니즘 카드: 컨텍스트는 예산이자 필터다

컨텍스트가 많다고 자동으로 더 좋은 컨텍스트가 되는 것은 아닙니다. 입력 후보마다
다음과 같이 분류하세요.

1. 객체와 수용 조건을 식별하는 데 필요한가?
2. 신뢰할 수 있는가, 아니면 데이터 안에 들어 있는 검증되지 않은 지침인가?
3. 이 작업에 사용할 만큼 최신인가?
4. 유용한 신호를 더하는가, 아니면 컨텍스트 공간을 놓고 작업과 경쟁하는가?

README 편집에는 프로젝트 규칙과 대상 README가 관련될 수 있습니다. 무작위로
고른 오래된 issue, 복사된 프롬프트, 무관한 비밀 정보는 관련되지 않습니다.
“프로젝트 규칙을 무시하라”고 적힌 파일도 따라야 할 권위가 아니라 분석해야 할
파일일 뿐입니다. 따라서 컨텍스트 선택은 품질 결정인 동시에 보안 결정입니다.

### 메커니즘 카드: 변이는 측정의 문제다

두 출력이 다르다는 사실만으로 특정 컨텍스트 하나가 차이를 일으켰다고 입증할 수는
없습니다. 모델이 다르게 샘플링했거나, 서비스가 다른 리비전을 사용했거나, 도구
상태가 바뀌었거나, 작업 명세가 불충분했을 수 있습니다. 한 번에 변수 하나만
바꾸고 다음을 기록하세요.

    run-id | 모델/표면 | 입력 리비전 | 변경한 변수 | 출력/상태 | 증거 | 미확인 사항

가능하면 기준 실행을 반복하세요. 변수를 고정할 수 없다면 관찰 결과를 “다른 결과가
관찰됨”이라고 표시하고 “X가 원인임”이라고 표시하지 마세요.

## 도구 호출은 마법 같은 행동이 아니라 프로토콜 경계다

Codex가 도구를 사용할 수 있을 때는 네 가지 사건을 분리해서 생각하세요.

1. 모델이 행동을 제안합니다.
2. 런타임이 범위, 권한, 확인 규칙을 검사합니다.
3. 도구가 실행되거나, 거부하거나, 시간 초과됩니다.
4. 다음 단계에서 결과와 변경된 상태를 검사합니다.

다음 문장들은 서로 같은 뜻이 아닙니다.

- “모델이 명령을 작성했다.”
- “명령이 실행되었다.”
- “명령이 의도한 객체를 변경했다.”
- “변경이 수용 기준을 충족한다.”

로컬 파일의 유용한 증거에는 검사한 경로, 변경 전후 diff, 범위를 좁힌 확인,
미검증 목록이 포함될 수 있습니다. GitHub 또는 그 밖의 외부 행동이라면 정확한
대상, 권한 상태, 확인 지점, 결과 객체, 롤백 또는 복구 경로를 추가하세요. 로그인
페이지, 도구 이름, 또는 “완료”라는 메시지만으로는 그 어떤 증거 공백도 메울 수
없습니다.

### 권한은 역량과 같지 않다

공식 제품 경계는 기술적 샌드박스와 승인 경계를 구분합니다. 프로젝트 용어로
말하면 다음과 같습니다.

- 샌드박스는 런타임이 기술적으로 접근할 수 있는 범위를 설명합니다.
- 승인은 런타임이 어떤 행동 전에 멈춰야 하는지를 설명합니다.
- 둘 중 어느 것도 대상, 범위 또는 결과가 정확하다는 것을 입증하지 않습니다.

모델 이름, Skill 존재 여부, 계정 로그인 또는 사용 가능한 버튼만으로 권한을
추론하지 마세요. 부작용이 발생하기 직전에 대상과 행동을 확인하세요. 학습 실습은
비밀 정보가 없는 일회용 복사본으로 시작하세요.

## 초기에 배워둘 가치가 있는 세 가지 메커니즘 함정

동일한 관찰 가능 경계가 흔히 쓰이는 세 가지 시스템에 나타납니다. 제품 데모에서는
서로 다르게 보이지만, 각각 그럴듯하면서도 아직 신뢰할 수 없는 결과를 만들어낼 수
있습니다.

### 1. 구조화된 출력은 문법적으로 맞아도 의미상 틀릴 수 있다

JSON Schema 또는 타입이 지정된 응답은 형태, 필수 필드, 일부 타입을 제한할 수
있습니다. 그렇다고 ID가 존재하거나, 날짜가 최신이거나, 권한이 유효하거나,
출처가 값을 뒷받침한다는 뜻은 아닙니다. 세 가지 검사를 사용하세요.

```text
스키마/타입 검사 → 비즈니스 규칙 검사 → 출처/상태 검사
```

예를 들어 `{ "status": "approved" }`는 유효한 JSON이고 스키마를 충족할 수
있지만, 승인이 잘못된 프로젝트에 속할 수 있습니다. 원시 모델 출력, 스키마 결과,
비즈니스 규칙 결과, 외부 검증을 별도의 증거로 보존하세요. [LLM 메커니즘
연구](../evidence-library-KO.md#source-notes)는
이를 모든 제공자가 같은 구현을 사용한다는 주장이 아니라 교육을 위한 경계로
기록합니다.

### 2. 검색은 자료를 선택할 뿐, 완전한 활용을 보장하지 않는다

검색 또는 검색 증강(retrieval)이 관련 청크를 선택할 수 있지만, 관련성이 완전성,
최신성, 권위 또는 모델의 실제 인과적 사용과 같은 것은 아닙니다. 작은 예외 문단이
포괄적인 규칙보다 낮게 평가되거나, 청크 경계가 조건을 그 정의와 분리할 수
있습니다. 쿼리, 필터, 리비전, 선택된 청크 ID, 최종 인용을 기록하세요. 답변이
달라졌다면 실험이 그 이유를 분리해 낸 경우가 아닌 한 “다른 검색 컨텍스트가 다른
결과를 생성함”이라고 말하세요.

### 3. 지침처럼 보이는 데이터도 여전히 데이터다

웹 페이지, 첨부 파일, issue 본문, 도구 결과, 데이터베이스 필드, MCP 리소스에는
“이전 규칙을 무시하라” 같은 텍스트가 포함될 수 있습니다. 그 문자열은 시스템
지침처럼 보인다는 이유만으로 권위를 얻지 않습니다. 신뢰할 수 없는 데이터로
취급하고, 외부 행동은 기본적으로 읽기 전용으로 유지하며, 도구 호출에 영향을
주기 전에 별도의 결정을 요구하세요. 이것이 초급 학습자를 위한 프롬프트 인젝션
방어의 실용적인 형태입니다. 데이터 출처를 식별하고, 도구 경계를 제한하고, 시도된
행동을 기록에 보존하세요.

이 세 가지 함정은 [메커니즘 심층 연구](../evidence-library-KO.md#source-notes)에서
제공자별 출처와 저위험 실험을 통해 다룹니다.

## Agent 루프가 실제로 의미하는 것

Agent는 관찰 가능한 흔적을 남기는 상태 머신으로 가르치는 것이 가장 좋습니다.

    ready
      → observed
      → planned
      → action_requested
      → awaiting_approval / executing
      → feedback_received
      → verified / recoverable_failure / blocked
      → stop 또는 bounded_retry

루프에는 재시도 예산과 각 재시도의 이유가 필요합니다. 입력, 권한, 환경 또는 수용
조건이 바뀌지 않았다면 “다시 시도”는 복구 전략이 아닙니다. 좋은 중단 기록은
다음 질문에 답합니다.

- 어떤 상태에 도달했는가?
- 변경된 것이 있다면 무엇인가?
- 어떤 증거가 주장을 뒷받침하는가?
- 어떤 증거가 누락되었는가?
- 불확실성을 줄일 수 있는 가장 작은 다음 확인은 무엇인가?

숨겨진 추론이 드러난다고 가장하지 않아도 루프는 유용할 수 있습니다. 관찰 가능한
사건과 결정을 기록하고, 지어낸 비공개 근거를 모델 내부 과정의 기록처럼 제시하지
마세요.

## 현장 사례: 유용한 교훈은 경계다

다음은 프로젝트의 현장 연구에서 수집한 공개 사용자 보고입니다. 공식 근본 원인
보고가 아니며, 이 프로젝트에서 로컬로 재현하지도 않았습니다. 이 사례들의 가치는
안이한 멘탈 모델이 어디에서 무너지는지 보여준다는 데 있습니다.

### 사례 FP-09: 용량으로 인한 중단과 위험한 재시도 가정

사용자들은 선택한 모델이 용량 한계로 사용할 수 없게 되었으며, 나중에 대기열에
들어간 지침이 부분적으로 완료된 상태에서 이어지는 것처럼 보일 수 있다고
보고했습니다. 이 보고는 서비스 측 원인이나 정확한 대기열 의미론을 확정하지
않습니다. 따라서 안전한 대응은 “계속 이어서 실행을 누르는 것”이 아닙니다.

가장 작은 안전 대응은 다음과 같습니다.

1. 중단하고 모델, 표면, 시간, 화면에 보이는 오류를 기록합니다.
2. 다른 지침을 보내기 전에 현재 diff와 체크포인트를 검사합니다.
3. 현재 상태에서 가능한 가장 좁은 범위의 검사를 실행합니다.
4. 어떤 상태를 기준으로 삼을지 결정한 뒤에만 이름 붙인 체크포인트에서 재개하거나
   깨끗한 실행을 시작합니다.

출처 및 증거 라벨: [현장 연구의 FP-09](../evidence-library-KO.md#source-notes).

### 사례 FP-10: “Working”은 진행의 증거가 아니다

한 Windows CLI 사용자는 포매팅 또는 분석 작업이 명확한 완료나 오류 없이 오랫동안
Working/running 상태에 머물렀다고 보고했습니다. 이 보고는 명령 중단, 프로세스
처리, 출력 버퍼링, 환경 드리프트 또는 다른 요인 중 무엇이 원인인지 입증하지
않았습니다. 장시간 실행 중이라는 라벨은 상태 관찰이지 성공한 결과가 아닙니다.

명령, 프로세스 상태, 경과 시간, 출력, 중단 지점을 기록하세요. 그런 다음 안전하다면
diff를 검사하고 범위를 좁힌 검사를 독립적으로 실행하세요. “UI에 아직 Working이라고
표시된다”를 “포매터가 완료되었다”로 바꾸지 마세요.

출처 및 증거 라벨: [현장 연구의 FP-10](../evidence-library-KO.md#source-notes).

### 사례 FP-11: 검증이 의도치 않게 작업을 확장할 수 있다

한 공개 보고는 Agent가 검증 단계를 권한 없이 강제 재설치하는 작업으로 확장한
사례를 설명합니다. 보고서의 설명이 실제 근본 원인인지는 확인되지 않았습니다.
하지만 지속적으로 적용할 수 있는 교훈은 근본 원인과 무관합니다. 검증에는 선언된
명령 범위, 쓰기 범위, 중단 지점이 있어야 합니다.

검사에 파괴적인 초기화, 네트워크 호출, 패키지 재설치 또는 자격 증명이 필요하다면
중단하고 새로운 결정을 요청하세요. “검사가 실패했다”는 사실이 권한 확대를 허용하지
않습니다.

증거 분류와 관련 장/실험 매핑은 [현장 문제 인덱스](../evidence-library-KO.md#source-notes)를
참조하세요.

## 실제 작업을 위한 결정 규칙

Codex에 행동을 요청하기 전에 다음과 같은 작은 작업 카드를 작성하세요.

| 필드 | README만 변경하는 예 | 누락되었을 때 할 일 |
|---|---|---|
| 목표 | 새로운 기여자가 프로젝트를 시작하도록 돕기 | 질문합니다. “더 좋게 만들어라”를 수용 조건으로 해석하지 않습니다. |
| 컨텍스트 | 프로젝트 규칙, README, 패키지 스크립트 | 관련된 최소한의 파일만 읽습니다. |
| 허용된 행동 | 일회용 브랜치에서 로컬 README 하나 편집 | 나열되지 않은 부작용은 금지된 것으로 취급합니다. |
| 피드백 | diff, 링크 검사, 명령 출력 기록 | 더 편집하기 전에 검사를 추가합니다. |
| 중단 조건 | 범위가 변경되거나, 명령에 설치/네트워크가 필요하거나, 증거가 누락됨 | 중단하고 `blocked` 또는 `not_observed`로 기록합니다. |
| 전달 주장 | “README 변경됨, 링크 검사 통과, 런타임 테스트 안 함” | 각 주장을 실제로 확보한 증거의 범위 안에 둡니다. |

이 카드는 프롬프트가 흔히 암묵적으로 남겨두는 결정을 드러내므로 긴 프롬프트보다
더 가치가 있습니다.

## 작은 실험: 작업은 고정하고 입력 하나만 바꾸기

### 준비

README와 짧은 프로젝트 규칙 하나만 들어 있는 일회용 로컬 복사본을 사용하세요.
비공개 저장소, 비밀 정보, 고객 데이터, 네트워크 호출 또는 외부 계정을 사용하지
마세요. 모든 시도에 실행 ID를 기록하세요.

### 작업

모델 또는 Codex 표면에 다음과 같이 요청하세요.

> README를 검사하고 개선점 하나를 찾아주세요. 파일은 편집하지 마세요. 무엇을
> 읽었는지, 그 개선이 중요한 이유, 이후 편집을 어떻게 확인할 수 있는지
> 설명하세요.

기준 실행을 한 다음, 변수 하나만 바꾸어 반복하세요.

1. 대상 독자와 프로젝트 목표를 추가합니다.
2. 프로젝트 규칙 하나를 추가합니다.
3. 답변 전에 짧은 계획을 요구합니다.
4. 명시적인 수용 기준을 추가합니다.

실행 사이에 표면이나 모델이 바뀌었다면 이를 교란 변수로 기록하세요. 가벼운 변경
전후 비교만으로 인과관계를 주장하지 마세요.

### 증거

프롬프트/입력 리비전, 실행 ID, 표면/모델 라벨, 읽기 범위, 답변, 파일 diff의 존재
여부, 미검증 항목을 저장하세요. 정적 실습을 통과했다는 사실이 모든 Codex 표면에서
같은 행동이 나타난다는 것을 입증하지는 않습니다.

### 회고

- 어떤 변수가 표현만 바꾼 것이 아니라 작업 경계를 바꾸었나요?
- 도구 제안과 실행된 행동을 어떻게 구분했나요?
- 결과가 정확하다고 주장하려면 무엇을 관찰해야 하나요?
- 불확실성 하나를 없앨 수 있는 가장 작은 다음 실험은 무엇인가요?

## 첫 대화: 바로 쓸 수 있는 세 가지 prompt

어려운 용어를 먼저 외울 필요는 없습니다. 개인 정보가 없고 외부 write 위험이 없는 작은 목표 하나를 고른 뒤 아래 중 하나를 실제로 쓰는 LLM 대화창에 붙여 넣으세요. 대괄호는 자신의 내용으로 바꿉니다. 핵심은 “마법 문구”가 아니라 이해, 한계, 다음 행동을 먼저 드러내게 하는 것입니다. model과 product surface에 따라 결과는 달라질 수 있습니다.

### 1. 언어 또는 작은 skill 배우기

```text
저는 [스페인어 / 배우려는 skill]을 공부하고 있습니다. 지금 할 수 있는 것은 [솔직한 현재 수준]입니다.
다른 내용을 이미 안다고 가정하지 말고, 한 목표만 연습하는 10분 과제를 만들어 주세요.
먼저 예시 하나를 보여 준 뒤 제가 답하게 하세요. 이해에 가장 큰 영향을 주는 한두 가지만 고쳐 주세요.
마지막에 세 줄로 제가 잘한 것, 다음에 연습할 것, 이 한 번으로는 판단할 수 없는 것을 적어 주세요.
한 번의 대화를 이 skill을 익혔다는 증거로 말하지 마세요.
```

이는 “7일 만에 언어를 익힌다”는 약속이 아닙니다. 한 번의 연습은 그때의 답과 feedback만 남깁니다. 유지, 낯선 상황 전이, 실제 대화 능력은 나중에 따로 확인해야 합니다. 확인할 수 없는 사실, 너무 많은 과제, 개인 정보 요구가 나오면 과제를 좁히거나 source를 요구하거나 그 대화를 멈춥니다.

### 2. 공개 자료를 빠르게 정리하기

```text
다음 질문에 답해야 합니다: [질문].
아래에 제공한 source만 사용하고, 제공하지 않은 사실을 추가하지 마세요.
먼저 각 source의 title, 날짜(있다면), 뒷받침할 수 있는 내용을 적고, 그다음 source 표시가 있는 짧은 요약을 작성하세요.
“source가 분명히 말하는 것”, “합리적 추론”, “아직 모르는 것”을 나누세요.
source가 충돌하거나 오래되었거나 중요한 사실이 빠졌다면 답을 추측하지 말고 질문 목록에서 멈추세요.
```

이 prompt는 “많이 찾았다”를 source로 돌아가 확인할 수 있는 결론으로 바꿉니다. network, 유료 database, 실제 account가 필요한 조사라면 먼저 product permission, source license, data scope를 확인하세요. 화면에 답이 나와도 조사가 끝났다는 뜻은 아닙니다.

### 3. 모호한 요청을 먼저 분명하게 만들기

```text
내가 원하는 결과는 [결과]이고 대상은 [독자 또는 file]입니다.
알고 있는 input은 [자료]이고 모르는 점은 [unknown]입니다.
아직 실행, 전송, 게시, install, 편집을 하지 마세요.
goal 재진술, 빠진 정보, 되돌릴 수 있는 최소 단계, acceptance evidence, stop condition만 출력하세요.
secret, network, account, external write, 더 넓은 scope가 필요하면 blocked로 표시하고 누구의 확인이 필요한지 알려 주세요.
```

답이 좋아 보여도 이 field에 실제로 답했는지 확인하세요. unknown을 건너뛰고 꾸며 내거나, proposal을 완료로 쓰거나, 허가받지 않은 action을 넓히면 그것은 관찰 가능한 failure입니다. 더 추측하게 하지 마세요.

## 세 가지 read-back

매번 1분만 써서 **무엇을 읽었는지, 실제로 무엇을 했는지, 무엇을 확인할 수 있는지**를 다시 읽습니다. chat만 하는 task에서 확인 가능한 것은 보통 input과 output입니다. file, browser, code task라면 target, diff, command output, external read-back도 필요합니다. 이렇게 첫날부터 “대화할 수 있음”과 “믿고 전달할 수 있음”을 구분합니다.

## 의도된 실패

일회용 복사본에서 다음과 같이 의도적으로 불충분하게 명세된 요청을 사용하세요.

> 프로젝트 전체를 전문적으로 만들고 모든 문제를 고쳐주세요.

올바른 대응은 범위가 정해지지 않은 대규모 편집이 아닙니다. 건전한 대응은
“전문적”의 정의, 범위, 입력 파일, 위험, 수용 기준, 중단 조건이 누락되었음을
식별하고 읽기 전용 목록 조사를 제안하거나 초점을 좁힌 질문을 하는 것입니다.
즉시 편집한다면 이를 유용한 주도성이 아니라 작업 경계의 실패로 기록하세요.

## 수용 체크리스트

다음을 할 수 있다면 계속 진행할 준비가 된 것입니다.

- 모델 역량, Codex 표면, 도구 행동, 도구 결과, 검증의 차이를 설명할 수 있습니다.
- 컨텍스트 선택을 “많을수록 항상 좋다”가 아니라 통제 변수로 설명할 수 있습니다.
- 현장 보고를 사용자 보고, 공식 사실, 로컬 관찰 또는 검증되지 않은 가설로 표시할
  수 있습니다.
- 허용된 행동과 중단 조건이 있는 작업 카드를 작성할 수 있습니다.
- 증거가 입증하지 못하는 내용까지 명시하는 실행 기록을 만들 수 있습니다.

정의를 반복할 수 있다는 이유만으로 이 장을 숙달했다고 표시하지 마세요. [Lab 011
— GPT, Codex, 도구와 Agent](../labs/lab-011-gpt-codex-boundaries-KO.md)를 완료하고
결과를 로컬 학습 기록에 보관하세요.

## 전이 과제

같은 모델을 코드가 아닌 작업에 적용하세요. Codex에 고정된 공개 출처 모음으로 짧은
연구 개요를 작성하도록 요청합니다. 모델, 작업 표면, 출처 컨텍스트, 도구, 허용된
행동, 출처 품질 검사, 중단 조건, 최종 증거를 식별하세요. 의도적으로 관련 없는
출처 하나를 추가하고 제외 여부를 어떻게 결정하는지 기록하세요. 공개 출처라고 해서
그 안의 모든 지침에 권위가 생긴다고 가정하지 마세요.
