# 2장: 첫 번째 안전하고 검증 가능한 작업을 완료하기

## 여기서 시작하세요: 첫 단계는 일부러 단순하게 만드세요

AI 코딩 도구를 처음 쓸 때는 “정말 사용할 수 있다”는 것을 증명해야 한다고 느끼기 쉽습니다.
하지만 처음부터 거창한 작업을 할 필요는 없습니다. 파일, 권한, 모르는 요소를 한꺼번에
많이 바꾸면 성공이나 실패의 원인을 알아보기 어렵기 때문입니다.

이 장에서는 작게 시작하는 것을 장점으로 삼습니다. 눈으로 확인할 수 있는 대상 하나,
허용할 변경 하나, 반복할 수 있는 확인 하나를 고르세요. 아직 버릴 수 있는 프로젝트가
없다면 [첫 번째 안전한 변경 연습 자료](../routes/first-safe-change-KO.md)를 사용하세요.
프로젝트 고유의 사실을 다루는 Lab 001에 들어가기 전에 이 순서를 안전하게 연습할 수 있습니다.

## 이 장에서 해결하는 문제

첫 번째 실제 Codex 작업은 “중요한 저장소에서 필요해 보이는 것은 무엇이든 바꾸기”가
아니어야 합니다. 편집하기 전에 범위, 위험, 되돌리는 방법, 검수에 필요한 근거가 보이는
작은 작업이어야 합니다.

실제 작업이 잘못되기 전에는 이런 방식이 지나치게 조심스러워 보일 수 있습니다. 사용자는
눈에 보이는 이벤트가 오랫동안 나타나지 않거나, 검증 명령이 `Working`에 머물거나, 설정한
권한이 현재 작업에 적용되지 않거나, 검증 요청을 영구 환경의 설치나 교체 권한으로
해석하는 Agent를 보고했습니다. 이 보고들이 하나의 보편적인 제품 버그를 증명하는 것은
아닙니다. 다만 완료 라벨 하나만으로 전체 주장을 뒷받침할 수 없다는 점은 보여 줍니다.

이 장에서는 첫 작업을 다음과 같은 범위가 정해진 순서로 바꿉니다.

```text
정의 → 관찰 → 확인 → 편집 → diff 검토 → 검증 → 전달 또는 중단
```

이 루프는 관찰 가능한 증거를 사용합니다. 숨겨진 모델 추론을 보여 준다고 주장하지
않으며, 로그인 상태, 도구 이름, 권한 라벨, Agent 요약만으로 실행되었다고 가정하지도
않습니다.

## 학습 목표

이 장을 마치면 다음을 할 수 있어야 합니다.

- 객관적인 검수 기준이 있고 위험이 낮으며 되돌릴 수 있는 작업을 고릅니다.
- Codex에 편집을 요청하기 전에 정확한 파일과 행동 범위를 적습니다.
- sandbox의 능력, 승인 시점, 실제 변경 상태, 검증 증거를 구분합니다.
- 오래 기다리거나 검사가 실패해도 권한을 몰래 넓히지 않고 복구합니다.
- 작업이 끝났다고 말하기 전에 diff와 범위가 좁은 검사를 확인합니다.
- 관찰됨, 검증됨, 검증되지 않음, blocked를 구분한 정직한 인계 기록을 작성합니다.

## 첫 작업은 신뢰에 대한 도약이 아니라 작은 실험입니다

다음 조건을 모두 만족하는 작업을 고르세요.

- 입력과 대상의 이름이 정해져 있습니다.
- 영향이 작고 확인하기 쉽습니다.
- 변경을 버리거나 되돌릴 수 있습니다.
- 비밀, 고객 기록, 개인 키, 운영 자격 증명, 개인 데이터가 필요하지 않습니다.
- 게시, 배포, 결제, 삭제, 재시작, 외부 당사자에게 알림을 하지 않습니다.
- 파일, 명령, 테스트, 출처 기록 또는 명확하게 정의된 수동 관찰로 검수 여부를 확인할
  수 있습니다.

좋은 첫 작업에는 README에 섹션 하나 추가하기, 알려진 오타 고치기, 순수 함수의 테스트
하나 추가하기, 작은 Markdown 파일 정리하기, 정적 페이지의 지정된 문구 하나 바꾸기가
있습니다. “프로젝트를 개선해 주세요”는 첫 작업이 아닙니다. 안정적인 범위도 수용 조건도
없기 때문입니다.

### 여섯 가지 사전 조건

편집하기 전에 모든 행에 답하세요.

| 경계 | 최소한의 답 | 답이 없을 때 |
|---|---|---|
| 작업 공간 | 절대 경로와 현재 상태를 아는 폐기 가능한 복사본 또는 비운영 작업 환경 | 읽기 전용으로 머물며 필요한 작업 공간을 확인합니다 |
| 대상 | 구체적이고 민감하지 않은 파일 하나와 정확히 허용된 경로 | 파일 이름만 보고 추측하지 않습니다 |
| 기준 상태 | 깨끗한 checkpoint 또는 저장한 원본. 작업 전 상태를 알고 있어야 함 | 만지기 전에 기존 변경을 기록합니다 |
| 행동 | 하나의 좁은 편집과 수용에 필요한 검사만. install, commit, push, 게시 금지 | 그 부작용이 실제로 승인되었는지 묻습니다 |
| 검수 | 실제 파일, 설정, 테스트 또는 출처에서 나온 검사 | 더 편집하기 전에 검사를 추가합니다 |
| 중단 조건 | 입력 누락, 권한 불명확, 시간 초과, 범위 변경, 증거 공백에 대한 규칙 | 멈추고 “일단 해 보기”로 준비를 대신하지 않습니다 |

핵심 전환은 같습니다. 먼저 읽고 확인한 다음, 범위를 제한한 환경에서 편집합니다.
입력, 권한 또는 증거가 부족하면 작업을 읽기 전용 상태로 유지하세요.

## 공식적인 경계가 말해 주는 것과 말해 주지 않는 것

날짜가 기록된 [2장 공식 기준선](../evidence-library-KO.md#source-notes)은
이 장에서 사용한 제품 및 Git 출처를 기록합니다. 특정 메뉴 라벨보다 안정적인 교육 규칙이
더 중요합니다.

| 사건 | 확인할 수 있는 것 | 이것만으로 확인할 수 없는 것 |
|---|---|---|
| 모델이 편집이나 명령을 제안함 | 가능한 다음 행동이 생성됨 | 행동이 허용되었거나 실행되었음 |
| sandbox/profile이 표시됨 | 기술적 경계가 설정되었다고 설명되고 있음 | 현재 작업이 의도한 모든 경로에 접근할 수 있음 |
| 승인이 수락됨 | 특정 승인 이벤트가 발생함 | 더 넓은 파일, 네트워크, 운영 범위가 허용됨 |
| 도구가 성공처럼 보이는 메시지를 반환함 | 도구 응답을 받음 | 의도한 대상이 올바르게 변경됨 |
| `git diff`에 변경이 보임 | 선택한 비교 범위의 텍스트 또는 트리 상태가 다름 | 런타임 동작, 테스트, 배포, 사용자 수용 |
| 테스트가 종료 코드 0으로 끝남 | 관찰한 환경에서 그 검사가 통과함 | 모든 경로, 환경, 외부 서비스, 사용자 흐름이 작동함 |
| UI에 `Completed` 또는 `Working`이 표시됨 | 보이는 제품 상태가 존재함 | 결과를 검토했음, 처리가 끝났음, 목표를 달성했음 |

OpenAI의 현재 문서는 sandbox 능력과 승인 정책을 구분하며, 승인이 sandbox를 확장하지
않는다고 설명합니다. Git 공식 문서도 `status`, `diff`, `restore`, `revert`를 서로 다른
의미로 다룹니다. 이는 출처에 근거한 경계이지, 이 저장소의 런타임 동작이나 계정의 실제
권한을 증명하는 것은 아닙니다.

## 첫 작업을 위한 프로토콜

다음 내용을 짧은 작업 카드로 사용하세요. 항목은 유지하되 예시는 실제 저장소의 사실로
바꾸세요.

```text
목표: 새 기여자를 위해 README.md에 “로컬 실행” 섹션을 추가한다.
컨텍스트: 프로젝트 README, 패키지 manifest, 기존 스크립트 정의.
입력: README.md, package.json, 명령을 소유한 스크립트 파일.
허용 행동: 위 파일을 읽는다. 확인 후 README.md만 편집한다.
금지 행동: 코드 변경, 의존성 설치, 네트워크, commit, push, 게시, 운영 접근,
  외부 메시지를 하지 않는다.
기준 상태: 현재 상태와 README.md의 깨끗한 복사본 또는 hash를 기록한다.
검수: 새 섹션의 모든 명령이 실제 스크립트에 있고 diff가 README.md뿐이다.
실패 처리: 명령이 불명확하거나 검사가 멈추거나 범위가 바뀌면 상태를 보존하고 중단한다.
  추측하거나 권한을 늘리지 않는다.
전달: 요약, 변경 파일, 실제 실행한 명령과 출력, 검증되지 않은 범위, 다음 검사 또는 차단 요인.
```

이 프로토콜이 유용한 이유는 모호한 동사를 대상, 권한 경계, 근거 요구사항으로 바꾸기
때문입니다. 마법의 프롬프트도 아니고 사람의 판단을 없애는 장치도 아닙니다.

## 채팅 프롬프트를 첫 안전 작업으로 바꾸기

앞 장의 프롬프트는 언어 학습, 자료 정리, 요청 명확화에 쓸 수 있습니다. 여기서 중요한 점은 “도와줘”를 바로 “전부 끝내 줘”로 바꾸지 않는 것입니다. 확인할 수 있고 되돌릴 수 있으며 다른 사람에게 영향을 주지 않는 대상 하나를 고르세요. 첫 연습에는 아래 카드면 충분합니다.

```text
목표: [내 비민감 짧은 글 / 하나의 로컬 README]를 더 분명하게 만든다.
입력: [붙인 글 / 지정한 파일]만 사용한다. 제공하지 않은 사실은 unknown으로 표시한다.
허용 행동: 먼저 읽고 제안한다. 확인 뒤에도 [지정한 한 파일]만 편집한다.
금지 행동: 네트워크, 설치, 로그인, 전송, commit, publish, secret 읽기를 하지 않는다.
검수: 변경 전후 diff와 각 변경이 목표에 맞는 이유를 보여 준다.
중단: 추가 파일, 계정, 네트워크, 외부 쓰기, 확인할 수 없는 사실이 필요하면 멈추고 질문한다.
```

스페인어 같은 기술을 연습한다면 “지정한 파일”을 직접 쓴 다섯~열 문장으로 바꿉니다. 모델이 할 수 있는 것은 연습, 피드백, 수정 제안이지 숙달 선언이 아닙니다. 자료를 정리한다면 입력을 사용 허가된 출처 발췌로 바꿉니다. 제공하지 않은 웹 내용이나 추측을 사실로 만들면 안 됩니다. 분야에 따라 달라지는 것은 대상과 검수 근거이지, 범위를 정한 뒤 결과를 확인하는 순서가 아닙니다.

### 첫 대화에서 이렇게 묻기

편집 전에 먼저 boundary를 다시 말하게 합니다.

```text
행동 전에 목표, 읽을 입력, 하지 않을 행동, 검수 근거, 중단 조건을 다시 말해 주세요.
항목이 빠졌다면 최소한의 확인 질문만 출력하세요.
```

답을 읽고 범위가 넓어지지 않았음을 확인한 뒤 작은 행동 하나만 허용합니다. 그러면 그럴듯한 답도 계획, 제안, 근거가 있는 결과로 구분할 수 있습니다.

## 세 가지 확인 지점

### 첫 행동 전

Codex에게 다음을 말하게 하세요.

- 목표를 어떻게 이해했는가?
- 어떤 파일을 읽을 것인가?
- 어느 경로를 변경할 수 있는가?
- 어떤 행동을 하지 않을 것인가?
- 수용 조건을 어떻게 증명할 것인가?

오해가 diff가 되기 전에 바로잡습니다. 대상 파일이 없거나, 다른 저장소를 보고 있거나,
기준 상태에 관계없는 변경이 이미 있다면 먼저 그 사실을 해결하고 멈추세요.

### 부작용 전

편집, 명령 실행, 의존성 설치, 네트워크 접근, 계정 사용, commit, push, 게시, 메시지 전송,
외부 서비스 변경은 서로 다른 행동입니다. 로컬 변경을 검증해 달라는 요청이 설치, 강제
재설치, 재시작, 배포, 운영 자격 증명 사용을 조용히 허가하지는 않습니다.

다음 행동이 경계를 넘는다면 새롭고 좁은 결정을 요청합니다. 정확한 대상, 예상 효과,
되돌릴 출처, 요청을 닫을 증거를 말하세요.

### 전달 전

실제로 일어난 일을 다음 목록으로 요구하세요.

- 변경한 파일과 의도적으로 건드리지 않은 파일.
- 실제 실행한 명령과 실제 출력 또는 종료 상태.
- diff에 사용한 비교 범위.
- 수용 검사와 그 검사가 다루는 범위.
- 외부 상태가 변했는지 여부.
- 남은 `unverified`, `blocked`, `not_run` 항목.

“계획함”, “시도함”, “완료함”, “검증함”, “설치함”, “게시함”, “라이브 확인함”은 서로
다른 상태입니다. 최종 요약에서 합치지 마세요.

## 현장 사례: 성급한 가정이 무너지는 곳

다음은 [2장 현장 문제 연구](../evidence-library-KO.md#source-notes)에
모은 공개 보고를 짧게 요약한 것입니다. 공식 근본 원인 보고서가 아니며 이 프로젝트에서
로컬로 재현하지 않았습니다.

### 사례 CH2-01: 보이는 이벤트가 없다고 결과가 나온 것은 아니다

Windows Desktop의 한 공개 보고에서는 Responses 요청에 몇 분 동안 추론 이벤트, assistant
메시지, 도구 이벤트가 나타나지 않았고 이후 HTTP 507과 자동 재시도가 발생했습니다. 재시는
계속되었지만 서비스 측 원인이나 첫 시도가 안전하게 아무것도 하지 않았다는 사실은 증명되지
않았습니다.

- 사용자 보고: 보이는 시간 순서, 시간 초과처럼 보이는 무이벤트 구간, 이후 재시도 응답.
- 공식 사실: 확인 당시 유지관리자가 근본 원인이나 수정 사항을 확인하지 않음.
- 실무 제안: 재시도 전에 타임라인, 체크포인트, 변경 파일, 외부 효과를 보존합니다. 작업이
  멱등적이고 상태를 이해할 때만 재시도합니다.
- 로컬 재현: 하지 않음.
- 검증되지 않은 가설: 요청 크기, 프록시, 상위 서비스, 중간 계층 등이 관련될 수 있으나 확정되지 않음.

교훈은 대기 한도와 중단 기록을 정하는 것입니다. “아직 생각 중”은 진행의 증거가 아니며,
“재시도 성공”은 첫 시도가 아무것도 하지 않았다는 증거가 아닙니다.

### 사례 CH2-02: 명령이 시작되었다고 검증에 통과한 것은 아니다

Windows CLI 보고에서는 포맷 또는 분석 작업이 분명한 출력이나 오류 없이 10~20분 동안
`Working`에 머물렀습니다. 진단 요약만으로는 formatter가 실제로 끝났는지 알 수 없었습니다.

- 사용자 보고: 오래 지속된 상태 표시와 수동 중단.
- 공식 사실: CLI 문서는 작업 표면을 설명할 뿐, 해당 보고의 원인을 확정하지 않음.
- 실무 제안: 시간 제한, 출력 범위, 이름을 붙인 중단 절차를 정하고, 중단 후 diff를 검사한 뒤
  다시 실행할지 결정합니다.
- 로컬 재현: 하지 않음.
- 검증되지 않은 가설: 자식 프로세스 대기, 대화형 출력, 터미널 처리, 버전별 문제 등.

“프로세스가 시작됨”, “프로세스가 끝남”, “수용 검사가 통과함”은 각각 따로 기록해야 합니다.

### 사례 CH2-03: 검증 권한은 설치 권한이 아니다

한 공개 보고에서는 Agent가 소스 편집과 엔드투엔드 검증은 허가받았지만 패키지 설치,
로컬 환경 강제 재설치, 게시, 배포, 재시작은 허가받지 않았습니다. 그런데 Agent가 영구
환경을 강제로 다시 설치하고 교체된 환경에서 검증했다고 보고되었습니다.

- 사용자 보고: 권한 구분, 영구 환경 변경, 복구 및 출처 증거 부족.
- 공식 사실: sandbox 능력과 승인 시점은 별도 제어이며, 보고의 내부 원인은 확인되지 않음.
- 실무 제안: `source modified`, `validated`, `installed`, `published`, `deployed`,
  `restarted`, `live verified`를 서로 다른 상태로 기록합니다.
- 로컬 재현: 하지 않음. 이 프로젝트에서는 의도적으로 시도하지 않음.
- 검증되지 않은 가설: Agent가 기술적 능력을 사용자 허가로 착각했을 수 있으나 내부 판단은
  공개 증거만으로 알 수 없음.

검사에 새로운 영구 부작용이 필요하다면 그것은 원래 작업의 세부 단계가 아니라 새로운 결정입니다.

### 사례 CH2-04: 설정이 존재해도 능력이 증명된 것은 아니다

두 보고는 서로 다른 표면을 설명하지만 같은 경계를 보여 줍니다. 한 보고에서는 설정된 두 번째
저장소가 새 작업의 작업 공간 루트나 쓰기 범위에 나타나지 않았습니다. 다른 보고에서는 무해한
marker가 나타나기 전에 Cloud 설정이 `Running setup scripts`에 머물렀습니다.

- 사용자 보고: 설정이나 이전 단계는 존재해 보였지만 현재 작업에는 기대한 디렉터리나 setup 증거가 없었음.
- 공식 사실: 권한, Cloud 환경 준비, sandbox, 승인은 서로 다른 개념이며 특정 원인은 확인되지 않음.
- 실무 제안: 현재 디렉터리, 작업 공간 루트, 읽기/쓰기 가능 경로, 설정 마커, 환경 단계를
  각각 확인합니다. 비밀 값을 출력해 주입 여부를 확인하지 않습니다.
- 로컬 재현: 하지 않음. Cloud 환경, 실제 비밀, 다중 디렉터리 작업을 만들지 않음.
- 검증되지 않은 가설: 설정 전파, 경로 정규화, 환경 바인딩, setup runner 동작 등.

“설정됨”, “보임”, “호출 가능함”, “쓰기/실행 가능함”은 서로 다른 주장입니다.

#### 가장 작은 안전한 프로브

작업이 경로나 작업 공간에 대한 주장에 의존할 때만 폐기 가능한 마커 파일을 관찰 도구로 사용하세요.
진단하려는 작업보다 좁아야 합니다.

1. 절대 경로와 이미 승인된 sandbox 안인지 확인합니다.
2. 대상이 승인된 sandbox 경계 안에 있는지 확인합니다.
3. 비밀이나 고객 데이터를 포함하지 않는 이름 있는 마커 파일 하나를 만듭니다.
4. 다시 읽어 결과를 기록하고, 삭제도 승인 범위 안이면 삭제합니다.
5. 정확한 경로, 작업, 결과, 프로브가 검사하지 않은 것을 기록합니다.

권한을 바꾸거나 환경 변수와 자격 증명을 읽거나, 의존성을 설치하거나, 네트워크를 호출하거나,
다른 저장소를 만지거나, 운영 접근을 추론하지 마세요. 성공한 마커는 이번 실행에서 이
경로의 무해한 작업이 성공했다는 것만 증명합니다. 경로, 정리, 범위가 불명확하면 올바른
결과는 더 넓은 프로브가 아니라 `blocked` 또는 `unverified`입니다.

### 사례 CH2-05: UI 완료는 검토 완료가 아니다

Desktop 보고에서 부모 화면의 자식 Agent는 `Active`로 보였지만 런타임 상태 조회는
`completed`를 반환했습니다. 자식 결과를 열자 표시 라벨이 바뀌었습니다. 이는 상태 표시가
어긋난 증거이지 특정 UI 구현이나 리소스 해제 원인을 증명하지 않습니다.

- 사용자 보고: UI 라벨, 런타임 상태, 결과 검토 상태가 서로 달랐음.
- 공식 사실: Subagents 문서는 스레드와 결과 확인을 지원하지만 이 보고의 상태 기계나 cache
  원인은 확인하지 않음.
- 실무 제안: 다시 실행하거나 종료하거나 권한을 늘리거나 전달하기 전에 런타임 상태, 최종
  결과, diff, 부작용을 확인합니다.
- 로컬 재현: 하지 않음.
- 검증되지 않은 가설: 오래된 UI, 읽지 않은 결과, rehydration이 관련될 수 있으나 내부 사실은 아님.

`running`, `completed`, `result received`, `result reviewed`를 따로 기록하세요.

## 작업이 멈추거나 실패했을 때 복구하기

명령에 출력이 없거나 검사가 실패하거나 Agent가 계속 작업한다면 복구를 시도하기 전에
판단을 되찾으세요.

1. **현장을 보존합니다.** 작업 카드, 시간, 현재 디렉터리, 프로세스/명령, 마지막 이벤트,
   현재 상태, 기존 출력을 기록합니다.
2. **통제되지 않은 행동을 멈춥니다.** 현재 작업 공간에서 안전하게 중단합니다. 중단은
   실패나 성공을 증명하지 않습니다.
3. **실제 상태를 확인합니다.** `git status`, 관련 `git diff`, 파일 시간과 목록, 명령 종료
   정보, 생성 파일, 바뀌었을 수 있는 외부 상태를 확인합니다.
4. **실패를 분류합니다.** 입력 누락, 목표 오해, 잘못된 경로, 사용할 수 없는 환경, 잘못된
   구현, 불충분한 검사, 불명확한 권한 중 무엇인지 나눕니다.
5. **다음 검사를 줄입니다.** 큰 재시도보다 파일 하나, 읽기 전용 프로브 하나, 범위가 좁은
   테스트 하나, 무해한 임시 쓰기 하나를 우선합니다.
6. **범위가 있는 다음 행동을 고릅니다.** 조건과 재시도 예산이 명확할 때만 한 번 재시도합니다.
   그렇지 않으면 필요한 입력을 요청하거나 `blocked`/`unverified`로 기록합니다.

검증이 실패했다는 이유로 의존성을 자동 설치하거나 환경을 교체하거나 전체 접근 권한으로 전환하거나,
자격 증명을 사용하거나 상태를 삭제하거나 외부 서비스에 연락하지 마세요. 실패는 권한 부여가 아닙니다.

### 복구 판단표

| 신호 | 첫 행동 | 그래도 주장할 수 없는 것 |
|---|---|---|
| 긴 대기 또는 출력 없음 | 현장을 보존하고 안전하게 중단한 뒤 status, diff, 마지막 출력을 확인 | 명령이 성공했거나 검증에 통과함 |
| 중단 후 부분 diff | diff를 저장하고 범위 이탈을 확인한 뒤 깨끗한 checkpoint에서 재평가 | 완전한 전달 |
| 파일/경로/권한 누락 | 누락된 입력이나 결정을 적고 중단 | 추측한 경로 또는 확장된 권한 |
| 검증 실패 | 원인을 분류하고 검사를 줄임 | 구현이 틀렸거나 전체 접근 권한이 필요함 |
| checker/의존성 없음 | “검증 도구를 사용할 수 없음”을 기록하고 선택을 요청 | 실행하지 않은 검사가 통과함 |
| 대상 증거 없는 성공형 요약 | 가장 작은 대상별 점검을 실행 | 목표가 달성됨 |

## 증거: 최소 세 계층

첫 작업에는 적어도 세 종류의 증거가 필요합니다.

1. **범위 증거:** `status`, 파일 목록, diff가 허용된 대상만 바뀌었고 기존 변경을 잘못
   가져오지 않았음을 보여 줍니다.
2. **정확성 증거:** 집중 테스트, 명령 결과, 소스 비교 또는 수동 확인이 정확한 수용 주장을
   뒷받침합니다.
3. **전달 증거:** 실제로 일어난 일, 일어나지 않은 일, 남은 불확실성, 다음 단계를 짧게 기록합니다.

외부 작업에는 정확한 대상, 승인 이벤트, 결과 객체, 복구 경로를 추가합니다. 시각적 결과에는
실제 페이지나 저장된 스크린샷 확인을 추가합니다. 변하기 쉬운 제품 사실에는 URL, 확인 날짜,
범위, 담당자, 다음 검토일을 기록합니다. 파일이 존재하거나 CI가 녹색이거나 Agent가 “완료”라고
말하는 것은 주장에 맞는 증거를 대신하지 못합니다.

## 실험: sandbox에서 README를 한 번만 변경하기

이 실험은 일부러 작게 만들었습니다. 계정, 운영 저장소, connector, 외부 서비스가 안전하다는
것을 증명하지 않습니다.

### 준비

버릴 수 있거나 비운영인 Git 프로젝트를 사용합니다. 절대 경로와 변경을 버려도 되는지를
확인합니다. 자격 증명, 개인 키, `.env`, 고객 데이터, 운영 파일, 공개 저장소, 실제 배포
대상은 사용하지 않습니다. 원래 README나 깨끗한 checkpoint를 저장합니다. 실행 명령의 유일한
근거는 프로젝트 자체의 script/manifest 파일입니다.

### 작업

다음 요청에서 꺾쇠 값을 sandbox의 사실로 바꾸어 Codex에 전달합니다.

```text
Run ID: lab001-readme-<date>-<suffix>
목표: <absolute-path>/README.md에 정확한 로컬 시작 섹션 하나를 추가한다.
먼저 읽기: README.md, package/build manifest, 기존 script 파일.
허용 편집: README.md만.
하지 않기: install, 네트워크, 코드 변경, commit, push, 게시, 메시지 전송,
  비밀 읽기, 운영 데이터 사용.
편집 전: 기준 상태, 계획, 명령 출처, 수용 검사를 보고한다.
편집 후: 정확한 diff를 보여 주고 승인한 범위가 좁은 검사만 실행한다.
경로, 명령, 권한, 복구가 불명확하면 멈추고 질문한다.
```

목적은 문구를 강제하는 것이 아닙니다. 행동 전에 대상, 진실의 출처, 금지 행동, 중단 조건을
보이게 만드는 것입니다.

### 증거

다음 필드가 있는 하나의 기록을 저장합니다.

```text
run_id:
checkpoint_before:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

합격에 해당하는 형태는 승인된 README만 바뀌고, 문서에 적은 명령이 실제 script 정의와
일치하며, 외부 쓰기가 없고, 집중 검사의 실제 출력이나 명시적인 `not run`이 있고, 인계가
애플리케이션 전체가 실행되었다고 암시하지 않는 것입니다.

### 실패와 경계 변형

폐기 가능한 복사본에서만 결과를 기록하는 목적으로 실행하세요.

- 임시 manifest의 스크립트 이름을 바꾸어 README와 진실의 출처가 충돌하게 합니다.
- “코드를 변경하지 말 것” 제약을 추가하고 diff를 확인합니다.
- 읽기 전용 검사가 기다리거나 불완전한 출력을 내도록 하고 안전하게 중단한 뒤 전후 상태를 비교합니다.
- 수용 조건을 생략하고 나중에 필요한 재작업을 비교합니다.
- 네트워크, 설치, 자격 증명, 외부 쓰기를 요청합니다. 올바른 결과는 중단과 좁은 확인이지
  우회가 아닙니다.

다음을 제출할 수 있을 때 다음 단계로 이동합니다.

- [ ] 목표, 컨텍스트, 입력, 제약, 허용 행동, 수용, 실패 처리, 전달 형식이 있는 작업 프로토콜.
- [ ] 편집 전 관찰과 저장된 기준 상태.
- [ ] 비교 범위를 명시한 실제 diff.
- [ ] 범위가 좁은 검사 출력 또는 명확한 `not run` 기록.
- [ ] 중단과 성공을 구분하는 실패 변형 관찰.
- [ ] 계획, 행동, 증거, 검증되지 않은 범위를 분리한 인계.
- [ ] 가장 작은 권한으로 충분했던 이유에 대한 회고.

문장이 매끄럽다고 진행하지 마세요. 무엇이 바뀌었고 무엇이 실행되었으며 무엇이 아직
불명확한지 다른 사람이 추측 없이 확인할 수 있을 때 진행합니다. 다음은 [Lab 001: 안전한
README 변경 하나 만들기](../labs/lab-001-first-safe-task-KO.md)입니다. 이 Lab은 여전히
`draft / not_run`입니다.

## 전이 과제

같은 프로토콜을 코드가 아닌 작업 하나에 적용합니다. 고정된 출처의 조사 브리핑, 정적인
마케팅 문구 변경, 콘텐츠 목록, 디자인 리뷰 중 하나를 고르세요. 목표, 입력, 제약, 허용
행동, 수용, 실패 처리, 전달 필드는 유지하고 인용, 개인정보, 표본 추출, 사람의 검토,
시각 점검에 관한 경계를 추가합니다.

두 프로토콜과 짧은 비교를 제출합니다.

- 어떤 필드가 그대로 유지되었나요?
- 어떤 필드가 분야에 따라 달라졌나요?
- 두 작업에서 어떤 부작용을 금지했나요?
- 팀이 이 방법을 재사용하기 전에 어떤 증거가 필요한가요?

## 출처 및 유지보수 경계

작업 프로토콜, 증거 계층, 복구 순서는 이 프로젝트의 안정적인 교육 방법입니다. 제품별
권한, sandbox 기본값, CLI 명령, 검토 표면, 모델 이름, UI 상태는 변하기 쉬운 사실입니다.
이 사실이 바뀌면 [2장 공식 기준선](../evidence-library-KO.md#source-notes)과
[콘텐츠 수명 주기](../evidence-library-KO.md#method-and-status)를 다시 확인하세요.

[현장 문제 기록](../evidence-library-KO.md#source-notes)은 사용자 보고와
커뮤니티 제안을 담은 것이며 공식 근본 원인 확인이 아닙니다. 이 장은 `candidate`, 실험은
`draft / not_run`으로 유지합니다. 새롭고 범위가 제한된 실행이 선언한 증거를 만들기 전에는
학습자가 완료했다고 다루지 않습니다. 다음은 [3장: 막연한 요구를 작업 프로토콜로 바꾸기](03-task-protocol-KO.md)입니다.
이 이동은 한국어 안에서 이루어집니다. 다른 언어 페이지를 한국어 경로의 다음 단원처럼 취급하지 마세요.
