# 第一章：先理解 GPT，再理解 Codex

## 本章要解决的问题

很多人第一次使用 Codex，会把它当成一个“更会写代码的聊天窗口”。这个理解既不完全错误，也不够用。它解释不了为什么同一个请求在不同项目、不同权限、不同上下文和不同模型下会得到完全不同的结果。

本章建立一个最小但够用的心智模型：GPT 是生成与判断能力的基础，Codex 是把这种能力放进项目、工具和交付流程中的工作面。

## 学习目标

读者完成本章后应当能够：

- 用自己的话区分 GPT、模型、产品和 Codex；
- 为一个任务列出目标、上下文、行动空间、反馈和停止条件；
- 判断一个问题需要任务协议、Skill 还是额外工具。

## 现实问题入口

现场研究中的 FP-09（模型容量中断任务）和 FP-10（验证命令长时间停在 Working）说明：同一句请求的结果还取决于模型、反馈和停止条件。报告来自用户 issue，不是官方根因结论；阅读时要保留这个证据边界。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)。

## 1. GPT、模型和产品不是同一个东西

可以先这样区分：

```text
模型：提供生成、理解、转换和判断能力的引擎
产品：把模型放进某种用户体验、账号体系和工作入口
Codex：让模型在项目和工具边界内参与真实工作的一组工作面
```

模型回答的是“我能生成什么”；产品决定“用户从哪里使用”；Codex 进一步决定“我能看到哪些上下文、可以采取哪些行动、如何留下交付证据”。

这也是为什么“换一个模型”与“换一个工作方式”不是一回事。模型可能影响速度、质量、成本和稳定性；Codex 工作面则影响文件、终端、浏览器、Git、skills、权限和验证方式。

## 2. Codex 的基本闭环

一个可观察的 Codex 任务通常可以拆成：

```text
理解目标 → 读取上下文 → 形成计划 → 采取行动
       → 观察结果 → 修正或停止 → 验证并交付
```

这不是隐藏的“魔法思考”描述，而是学习者应该能够观察和审查的工作闭环。你不需要假装知道模型内部每一步隐含推理，但必须知道它看到了什么、使用了什么工具、改变了什么、依据什么停止，以及如何证明结果正确。

## 3. 五个决定结果的变量

同一个请求的结果至少受到五类变量影响：

### 目标

“帮我优化一下”没有说明优化什么、为谁优化、什么叫成功。目标越模糊，Agent 越可能用自己的假设填空。

### 上下文

项目结构、现有代码、设计规范、数据、历史决策和限制条件决定了任务的真实边界。给得太少会让 Agent 猜，给得太多会让它失去重点，给错则会让它沿着错误前提行动。

### 行动空间

一个只能回复文本的模型，和可以读取文件、运行命令、操作浏览器、调用 GitHub 的 Codex，行动空间不同。行动空间越大，收益和副作用都会增加。

### 反馈

测试失败、浏览器截图、编译错误、用户反馈、来源对照和运行日志，都是 Agent 修正行为的反馈。没有反馈，就只能凭表面感觉继续行动。

### 停止条件

如果没有明确的完成标准，Agent 可能在“看起来差不多”时停止，也可能不停地修改。可靠任务必须写清楚什么时候完成、什么时候暂停、什么时候需要人确认。

## 4. 把五个变量写成任务卡

理解这五个变量还不够；开始任务前要把它们写下来。任务卡不需要长，但必须让别人看出 Codex 能看到什么、能做什么，以及什么时候不能继续。

| 字段 | 写什么 | 空缺时怎么处理 |
|---|---|---|
| 目标 | 可交付结果和受益者 | 先澄清，不把“优化”“做好”当目标 |
| 上下文 | 必要文件、版本、规则和已知事实 | 只读检查允许范围内的输入；超出范围就询问 |
| 行动空间 | 允许读取、编辑、运行、提交或外部调用的动作 | 未明确授权的副作用默认不做 |
| 反馈 | 测试、diff、截图、来源、日志或人工检查 | 先补一个能观察结果的检查，不凭摘要判断 |
| 停止条件 | 完成、暂停、失败和需人工确认的条件 | 到达条件就停，不能用“再试一次”代替判断 |

例如“只补 README 的本地运行说明”可以写成：目标是让首次贡献者能启动项目；输入是 `README.md` 和项目脚本；允许动作是读取并编辑 `README.md`；反馈是脚本对照和 diff；如果脚本冲突、需要安装依赖或需要推送，就停止。这里最重要的不是措辞，而是把“不允许做什么”也变成可检查记录。

## 5. Skill 放在哪里

Skill 不是一个更长的提示词，也不是一个可以替你承担判断的“万能开关”。它更像一份可复用的工作协议：

- 什么时候应该触发；
- 需要哪些输入；
- 先检查什么；
- 按什么顺序行动；
- 什么情况下停止或询问；
- 最终输出和证据是什么；
- 失败时如何恢复。

如果一个任务只需要清楚的目标和几条约束，增加 skill 可能反而增加上下文负担。只有当方法会反复使用、过程容易漏步骤、质量标准需要统一，或领域知识确实重要时，skill 才真正值得沉淀。

## 6. 一个帮助记忆的比喻

把一次 Codex 任务想成一个小型工作室：

| 工作室元素 | Codex 对应物 |
|---|---|
| 项目委托 | 用户目标 |
| 资料室 | 文件、代码、文档和历史上下文 |
| 工具台 | 终端、编辑器、浏览器、Git 和连接器 |
| 操作手册 | Skill、AGENTS.md、项目规则 |
| 安全门 | Sandbox、权限和审批 |
| 质检台 | 测试、运行、来源、视觉和人工验收 |
| 出货单 | 变更说明、证据和交付格式 |

优秀的使用者不会只对工匠说“做得更好”，而会说明委托、材料、限制、工具、质检标准和交付要求。

## 最小实验：解释同一个请求为什么会有不同结果

### Setup

在临时副本或空白沙盒项目中进行。只允许读取 README，不允许编辑文件、运行安装/发布命令、访问外部服务或提交 Git。记录工作面、模型、日期和你实际提供的上下文；不要放入秘密、客户数据或私人仓库内容。

### Task

给 Codex 一个低风险任务，例如：

> 请查看当前项目的 README，指出其中一个可以改进的地方。先不要修改文件。请说明你读取了什么、为什么认为它值得改进，以及如何验证修改后的效果。

然后分别改变一个变量：

先运行一次不额外提供上下文的基线，再每次只增加一项变化：

1. 不提供项目背景；
2. 提供项目目标和受众；
3. 添加一条项目规则；
4. 要求它先给计划；
5. 给出明确的验收标准。

每次使用新的 `run-id`，记录实际输入、工作面、模型或入口、允许动作和是否产生 diff。记录每次回答的差异。不要比较“哪次文案更漂亮”，而要比较：它是否理解目标、是否使用了正确上下文、是否提出了可验证的建议、是否尊重了“不修改文件”的边界。

如果模型、工作面或项目副本在两次运行间发生变化，只能把结果记为“观察到的差异”，不能直接说是某一项上下文造成的。要排除随机性，至少重复一次基线或明确记录这个限制。

### Evidence

保存基线和五次变体的输入、`run-id`、Codex 的计划或回答、读取文件清单和一张比较表。比较表至少记录目标理解、上下文使用、允许行动、验收建议和不确定性；确认沙盒没有产生文件差异。若没有实际运行或工具日志，必须把对应证据标为“未观察”。

建议使用这一行格式记录每次运行：

```text
run-id | 只改变的变量 | 读取范围 | 产生的副作用 | 观察到的证据 | 未验证项
```

### Reflection

回答：哪一个变量改变了行为？你如何排除“回答只是随机不同”的解释？哪一条上下文是必要的、哪一条只是噪声？下一轮只改变哪个变量？

## 故意失败实验

把请求写成：

> 把这个项目整体优化到最好。

观察 Codex 是否会：

- 追问“最好”具体指什么；
- 先检查项目状态；
- 给出计划和风险；
- 直接开始大范围修改；
- 生成一份听起来正确但无法验证的总结。

失败实验的价值不在于嘲笑模型，而在于看见任务协议缺失会如何放大不确定性。

## 本章验收

学习者能够用自己的话回答：

- GPT、模型、产品和 Codex 的区别是什么？
- 为什么上下文和工具会改变结果？
- 为什么权限越大，验证要求也应该越高？
- Skill 在什么情况下比一次性提示更有价值？
- 一个任务至少需要哪些完成和停止条件？

如果只能复述定义，还没有掌握。请提交最小实验的记录，并指出你改变的变量和观察到的证据。

## 迁移练习

把本章的最小模型迁移到一个不涉及代码的任务，例如整理一份研究资料或制作一张产品报告。分别写出模型、Codex 工作面、上下文、工具、允许行动、停止条件和验收证据。然后删掉一个上下文来源，预测结果会出现什么变化，并用低风险试验验证预测。
