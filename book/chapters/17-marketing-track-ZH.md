# 第 17 章：营销路线——从产品理解到增长实验

## 本章要解决的问题

当请求缺少产品、受众、定位、证据与期望行动时，营销工作就会变得含糊不清。若团队在决定数据应当改变什么之前，就先去收集大量事件流或做出漂亮的仪表盘，也会带来风险。更严重的失误是：让一个营销 Skill 把个人数据、客户名单、组织权限或发布权限带进一个并不需要它们的实验。

本章把营销当作一个可复核的决策系统：建立带版本管理的产品上下文，陈述假设，定义最小有用的测量计划，然后在尊重隐私、样本限制与归因不确定性的前提下制作内容或采取行动。

## 学习目标

学完本章后，你应该能够：

1. 创建覆盖产品、受众、问题、替代方案、差异化、异议、客户语言、语气、证据与期望行动的产品上下文。
2. 从决定出发倒推，得出最小有用的事件、指标、分母、样本、时间窗、命名方案与停止规则。
3. 识别营销结论中的抽样偏差、过度归因、选择性报告、隐私风险与不确定性。
4. 用营销 Skill 设计一个增长实验，而不暴露个人数据、绕过平台权限或自动发布。

## 现实世界的切入点：身份、组织与数据都需要上下文

- **FP-03**：据报道，一名仅限企业（Enterprise）的用户在 `github.com` 上被探查，尽管相关入口是一个 Enterprise 主机。这说明默认主机或默认受众不能被当作用户事实。
- **FP-04**：据报道，同一用户可访问两家组织，而某个连接器被复用于其中第一家组织。这说明账号访问权限并不等于获授权将某家特定组织的数据用于某个特定实验。

这些是实地研究的用户报告，不是官方确认，也不是本地复现。本章用它们来训练区分身份、组织、安装范围与允许的数据使用。它们不是关于连接器行为的普遍结论。

## 核心概念与决策

### 1. 产品上下文是共享的、带版本管理的资产

产品上下文比一次性 prompt 更有用，因为它让假设可见、可复核。至少应记录：

```text
产品与版本；明确的非目标：
目标受众与被排除的受众：
核心问题与使用情境：
替代方案与转换成本：
差异化主张与可用证据：
常见异议与匿名化的客户语言：
品牌语气、禁用表述与合规边界：
期望行动与该行动的前提条件：
渠道、地区、语言与时间范围：
版本、变更原因、负责人与复核日期：
```

### 合成产品上下文：训练用 fixture，不是客户记录

本章的练习使用一个**合成产品上下文**。它是为练习而虚构的。它不描述任何真实的公司、客户、库存状况、受众规模、价格、转化率、客户证言或活动结果。

```yaml
context_id: synthetic-product-context-v1
product: "面向小型项目团队的本地规划工作区"
audience: "通过共享任务清单协调小型项目的人"
non_goals: ["不宣称市场份额", "不宣称客户成果"]
problem: "团队在会议与任务更新之间丢失了决策的脉络"
alternative: "共享文档加上手动提醒"
proof: "没有提供客户证据；产品主张仍属假设"
objections: ["配置成本", "数据访问", "又要多维护一个工具"]
desired_action: "查看本地样例工作区"
data_boundary: "仅合成记录；不含姓名、邮箱、IP 地址或外部 ID"
status: candidate
```

这个 fixture 的意义在于演示上下文字段与证据边界。它并不是允许编造证据。没有证据的主张必须保持为假设、被弱化，或被删除。

### 2. 为决策而测量

先写出决定，再选择数据：

```text
要做的决定：
关键假设：
必须回答的最小问题：
指标定义与事件名称：
分母、样本、时间窗与分群：
去重、缺失数据与延迟处理：
同意、隐私、保留期与访问控制：
停止规则与下一步行动：
```

“变体 B 的点击率更高”这句话，在没有说明曝光条件、分母、去重规则、人群、时间窗与下一步行动之前，是不可复核的。不要把完整的邮箱地址、完整的 IP 地址、聊天记录或跨站标识符设为默认输入。应优先使用汇总、去标识化、短保留期的测试数据。

### 3. Agent 辅助判断，但不拥有归因

Agent 可以整理产品上下文、起草变体、检查事件名称、计算描述性统计并建议下一个实验。但它不能从文案差异中推断因果，不能在图表中掩盖样本偏差，也不能在没有单独授权、可复核的动作之下发布到广告平台、CRM、邮件系统或社交渠道。外部写入需要测试账号或 sandbox、人工批准、批次标识以及回滚或撤回路径。

### 4. 用能力分组代替工具目录

按候选 Skill 所支持的决定分组：

| 能力分组 | 典型输出 | 需记录的边界 |
|---|---|---|
| 产品上下文 | 带版本管理的上下文与主张台账 | 事实、假设、负责人、复核日期 |
| 内容与定位 | 绑定受众与异议的变体 | 证据、语气、禁用主张 |
| 转化实验 | 假设、曝光规则与停止规则 | 样本、分母、同意、时间窗 |
| 分发与增长 | 草稿或 sandbox 批次 | 渠道范围、批准、回滚 |
| 测量与归因 | 汇总报告与局限性 | 事件结构、数据质量、因果边界 |

## 具体证据表

| 证据项 | 具体产物 | 支持什么 | 不支持什么 |
|---|---|---|---|
| 产品上下文 | 带变更原因与负责人的 `synthetic-product-context-v1` | 练习使用了哪些主张与受众 | 产品有真实客户或成果 |
| 主张台账 | 标记为 `fact`、`hypothesis`、`unverified` 或 `not applicable` 的行 | 某句话是否有明确的证据状态 | 对标记为 `unverified` 的主张的证明 |
| 测量计划 | 指标定义、分母、时间窗、样本规则、停止规则 | 拟议的测量是否可复现 | 仅凭自身即为统计显著性或因果 |
| 数据字典 | 汇总字段、保留期、访问范围、缺失数据规则 | 哪些数据进入了分析 | 收集更多个人数据的许可 |
| 变体记录 | 输入、输出文本、审阅者与版本 | 实际比较了什么 | 某个变体导致了某个结果 |
| 分发记录 | sandbox 或草稿状态、批次 ID、批准、回滚路径 | 是否准备了受控动作 | 有任何内容被公开发送 |

## 可观察的小实验：针对同一合成产品的两次请求

### 准备

使用上面的合成产品上下文。准备一份脱敏的产品描述、三个合成的异议、没有客户证言、没有库存、没有业绩数字。创建一个只含计数的本地汇总表。表中不能包含姓名、邮箱地址、完整的 IP 地址、设备标识符或跨平台 ID。选择一个短时间窗和两个内容变体，但不要宣称其中任何一个变体已经被运行过。

### 任务

1. 向 Agent 发出请求 A：“为这个产品写一段精炼的介绍。”保存输出。
2. 向 Agent 发出请求 B，附上带版本管理的上下文、受众、异议、缺失的证据、期望行动与测量计划。要求给出两个变体、假设、主要指标、分母、样本限制与下一个决定。
3. 从具体性、受众契合度、证据状态与可行动性几个方面比较 A 和 B。标出每一个没有证据支持的主张。
4. 请 Agent 检查事件名称、去重、缺失值、时间窗与隐私边界。不要上传数据，也不要调用真实渠道。
5. 如果使用汇总样本数据，只能将其报告为描述性 fixture。当样本不足时，不要把差异说成因果，也不要宣布赢家。

### 证据

保留两个请求、上下文版本、生成的变体、假设表、指标定义、分母与样本说明、去标识化的数据字典、隐私决定、数据质量检查与下一决定记录。每一句话都应能识别为产品事实、营销假设或未验证的主张。

### 失败变体

提供一个模拟渠道，其默认主机是 `github.com`，尽管练习只授权了 Enterprise 主机。然后提供来自两家组织的汇总数据，却只授权其中一家。检查 Agent 是否把默认主机或现有账号访问当作充分条件。正确的行为是暂停，确认主机、组织与授权范围，并使用最小被允许的数据或合成数据。接着，提供一份很小但表面差异很大的样本，检查 Agent 是否说明了样本限制与结果的观察性质。

### 反思

- 哪些字段让请求 B 比请求 A 更具体？
- 哪个指标会真正改变下一个决定？
- 哪些字段可以在不丢失答案的前提下被汇总或删除？
- FP-03 和 FP-04 如何改变你对主机、组织、受众与数据访问的假设？

## 失败与边界情形

- **编造证据或客户语言：**没有依据的客户证言、客户数字或“市场领导者”式的主张，必须变成假设或被删除。
- **把小样本宣布为赢家：**记录样本量、分母、时间窗、分群与缺失数据。如果证据不足以支撑稳定的判断，就报告方向性信号或继续收集。
- **把相关性写成因果：**如果标题、渠道、价格与受众同时改变，不要把结果归因于某一个变量。隔离变量，或把结果描述为观察性的。
- **平台权限不匹配：**把主机、组织、安装范围与实验授权做成预检。缓存的连接器或默认账号并不等于当前的批准。
- **隐私越界：**不要把个人信息、敏感属性、私人对话、未同意联系人或跨情境标识符设为默认。使用最小化、汇总、访问控制与保留期限制。
- **没有恢复路径的发布：**邮件发送、广告修改、CRM 写入、社交发布与追踪变更，都需要草稿或 sandbox 检查、人工批准、批次 ID 以及撤回或回滚方法。
- **漂亮的图表掩盖薄弱数据：**检查重复事件、时区、延迟、机器人、分母漂移、缺失值与渠道选择。图表本身不是证据。

## 迁移练习

选择一个真实的营销决定，但只使用脱敏或汇总的数据：

1. 写一页产品上下文，并标出事实、假设与需要证据的主张。
2. 选择一个可能改变的决定，设计最小的测量计划与停止规则。
3. 对每个字段，记录其隐私理由、访问范围、保留期限与删除方法。
4. 设计一个 sandbox 实验与一个失败变体，用来测试主机、组织与发布授权。

## 验收清单

- [ ] 我有一个带版本管理的产品上下文，包含负责人、变更原因与复核日期。
- [ ] 我能区分产品事实、营销假设、客户证据与未验证的主张。
- [ ] 我能从一个决定推导出最小有用的指标、分母、样本、时间窗与停止规则。
- [ ] 我在相关处检查了重复、缺失数据、延迟、时区、机器人流量与选择偏差。
- [ ] 我没有把相关性变成因果，也没有从小样本宣布稳定的赢家。
- [ ] 我使用了最小化与去标识化或汇总、访问控制与保留期限制。
- [ ] 针对 FP-03 或 FP-04，我能解释主机、组织、连接器与实验授权之间的区别。
- [ ] 没有批准、sandbox 证据与恢复路径，我不会向外部平台发布或写入。
- [ ] 我能为练习中的每一条实质性主张指出具体的证据产物。

## 来源与维护边界

- **实地报告：**[`docs/research/field-problems-codex.md`](../evidence-library-ZH.md#source-notes) 中的 FP-03 与 FP-04。该记录状态为 `candidate`；它由 Prysai LLM Playbook 维护组于 2026-08-09 访问并整理。它不是本地复现。
- **营销方法参考：**[`docs/sources/asset-register.md`](../evidence-library-ZH.md#source-notes) 中的 S04。本章是对决策与证据实践的原创综合；它不复制任何外部营销 Skill 的文本。
- **易变的平台与隐私事实：**使用适用平台的官方开发者文档与隐私文档、组织政策与当前配置。在实验记录中记下 URL、访问日期、地区、数据负责人与保留政策。
- **维护负责人：**营销路线维护者。当定位、渠道、权限、隐私政策、事件结构或归因方法发生变化时进行复核，且最迟不晚于 2026-11-09。

本章状态为 `candidate`。只有当相关的数据质量、隐私与人工复核证据都存在时，营销结论才可以被称为 `verified`。本章不提供任何客户、库存、转化率或活动结果。
