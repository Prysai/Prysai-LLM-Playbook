# 第 16 章：工程路线——从想法到可靠软件

**状态：**`candidate`。**实验：**`draft / not_run`。能生成代码、通过构建或看到页面，都不等于真实用户需要、运行可靠或已经发布。

## 问题：把“写代码”误当成“交付结果”

AI 可以快速生成补丁，却也能在错误的仓库、错误的范围或未经授权的环境中生成看似合理的修改。可靠工程不是让模型一次写完，而是把需求、现状、最小切片、行动边界、验证、失败恢复和交接串成闭环。

## 从一个可验收的竖向切片开始

不要从“做完整产品”开始。先定义一个可以在可丢弃副本中验收的最小变化：用户可见结果、允许修改的路径、禁止动作、输入基线、验收命令、人工检查、回滚目标和未覆盖风险。

| 阶段 | 关键问题 | 最低证据 |
|---|---|---|
| 定义 | 用户到底要什么？范围和权限是什么？ | 任务协议、输入、基线 |
| 计划 | 最小切片和依赖是什么？ | 方案、风险、回滚 |
| 修改 | 实际改了什么？ | diff、路径、行动日志 |
| 验证 | 哪些声明被检查？ | 命令、原始输出、退出码、人工检查 |
| 交接 | 完成与未知分别是什么？ | 证据表、下一步、恢复方法 |

## 操作：给 Agent 一个工程合同

合同至少要说清：目标用户和可观察结果；允许读取/修改的目录；明确禁止的生产、网络、凭据、安装、发布和删除；现有命令与超时；验收标准；遇到失败的停止条件；以及谁确认外部副作用。不要把“自己判断并修好所有问题”当作合同，它没有范围也没有回滚。

每次修改前记录工作目录、仓库根目录、分支、输入版本、`git status` 和基线测试。每次修改后记录变更路径、diff、命令、退出码、原始输出、未运行检查和人工观察。一个绿色测试只能支持它覆盖的断言，不能支持部署、用户理解、性能、安全或发布成功。

## 小实验：一条 Markdown 竖向切片

在可丢弃副本中，仅允许修改一个指定 Markdown 文件。先写发布说明的输入事实和验收规则，再完成：CP0 定义、CP1 计划、CP2 修改、CP3 验证、CP4 交接。至少做一个失败分支：缺少输入时编辑前停止；检查失败时保存输出；或在新会话中仅根据检查点和仓库状态恢复。不要安装依赖、改 PATH、登录、push、发布或重启服务。

## 失败恢复不是重复同一条命令

失败后先问：当前状态是什么？已有副作用是什么？下一次尝试改变了什么诊断条件？若答案不清楚，应停止并保存检查点。重复同一命令并不能叫恢复。若工具建议强制重装、上传日志、使用凭据或扩大权限，把建议记为数据，等待明确授权。

## 我真的学会了吗？

- [ ] 我能把模糊需求切成可验收的竖向切片。
- [ ] 我在编辑前固定了范围、基线、权限和回滚。
- [ ] 我能把实际 diff、命令、退出码和人工观察对应到不同主张。
- [ ] 我在失败后先检查状态，而不是盲目重试或重装。
- [ ] 我能区分本地完成、远端发布、生产运行和用户验收。
- [ ] 我没有把构建通过写成产品成功。

框架、依赖、命令和部署规则都是易变事实，应以当前项目的官方文档和本地环境为准。配合 [实验 009：工程生命周期](../labs/lab-009-engineering-lifecycle-ZH.md) 与 [实验 013：可审计竖向切片](../labs/lab-013-l3-vertical-slice-ZH.md)。本章为 `candidate`，不证明任何具体系统已经生产可用。

## 把需求变成工程任务卡

“给我加导出功能”还不能开始编码。先把它写成一张可复核的卡；未知项保留为问题，而不是由模型自行决定：

```text
用户动作：在 <页面/命令> 请求导出 <明确数据范围>。
成功：生成 <格式>，包含 <字段>；用户能看到 <可观察结果>。
失败：无权限、空数据、无效输入、写入失败时分别返回什么？
非目标：不迁移历史数据、不发布、不改变权限、不接入外部服务。
允许范围：可读/可写路径、允许命令、网络和秘密边界。
验收：哪些测试、一次本地运行、哪项人工检查；各自覆盖什么？
恢复：原始状态、可删的临时产物、回读检查和停止条件。
```

只有当这张卡能让另一位开发者复述目标和非目标时，才选择第一个切片。若导出格式、覆盖策略或权限仍未知，最小切片可以只是读取输入并生成预览，而不是悄悄写文件。

### 四个绿灯，四种不同结论

| 证据 | 可以说什么 | 不能说什么 |
|---|---|---|
| 构建成功 | 指定配置能编译/打包 | 用户流程可用或已部署 |
| 测试通过 | 该测试断言在该环境成立 | 未覆盖的错误、浏览器、权限或真实输入正确 |
| 本地运行正确 | 指定版本和输入得到观察到的结果 | 生产环境、所有账户或性能已验证 |
| 发布状态可读回 | 指定远端出现该 revision 或记录 | 用户已接受、监控正常或能安全回滚 |

不要把四个绿灯合成“产品已经完成”。每个结论都需要自己的命令、输入、环境、输出和范围。

## 小实验：一个 JSON 竖向切片

在可丢弃目录做一个功能：读取 `input.json` 中的字符串列表，去除重复项并写入 `output.json`。只允许该目录内读写，不允许网络、安装、登录、提交、推送或发布。

1. 写任务卡和基线：正常列表、空列表、重复列表、缺字段或无效 JSON。
2. 先实现一个切片：只处理正常与重复输入；保存 diff 和命令输出。
3. 增加空输入和无效输入处理。每次只改变一个可解释点，并在改动后运行已声明检查。
4. 用独立本地命令读取 `output.json`，确认内容、错误信息和原输入的状态；记录运行版本、输入、退出码和原始输出。
5. 模拟中断：在一个半完成状态停止，先读 `git status`、diff、日志和输出，再决定继续、恢复或新建检查点。不要直接添加无关需求。

若命令无输出、依赖缺失、工作区未知，或建议改 PATH、重装运行时、上传日志、部署或重启，停止并说明缺失的授权和恢复材料。绿色结果不值得用扩大权限来换取。

## 本章验收补充

- [ ] 我能写出用户动作、成功/失败、非目标、范围、验收和恢复，而不是只写功能名。
- [ ] 我按切片保存 diff、命令、退出码、输入/输出和未知项。
- [ ] 我不会把构建、测试、本地运行、远端发布或用户接受混成一条结论。
- [ ] 我在中断或长时间无输出后先检查状态，再决定是否重试。

## 工程任务卡：一次可验收的最小改动

这张卡适用于你拥有或获授权的可丢弃项目副本。它先约束问题，再让任何 LLM 协助阅读、计划或编辑；它不授权安装、联网、提交、推送、发布或接触生产数据。

```text
目标：用户完成 [一个具体动作] 后应看到什么可检查结果？
范围：允许读取 [路径]；确认后仅改 [路径]；明确不改 [路径]。
基线：当前分支/提交、已有改动、相关测试或命令的原始结果。
真实来源：哪个规格、现有行为、测试、接口或设计文件拥有此事实？
最小切片：本次只改变哪一项可观察行为？
验收：文件范围、定向检查、运行时观察和人工阅读各验证什么？
禁止动作：安装、网络、删除、提交、推送、发布、外部消息、秘密读取。
停止：路径、规格、授权、恢复方法或验收规则不清楚时暂停。
交付：diff、实际命令与输出、通过/失败/未运行、未知项和最小下一步。
```

### 四个绿灯是四种不同结论

| 信号 | 最多说明什么 | 仍不能说明什么 |
|---|---|---|
| diff 很小 | 比较范围内文本变化有限 | 需求已满足或运行正确 |
| 静态检查通过 | 该检查在记录环境中通过 | 所有路径与用户场景正常 |
| 本地运行通过 | 一个明确运行场景可观察 | 部署、性能、安全或外部集成正确 |
| 人工验收通过 | 指定读者按指定规则看到了结果 | 长期维护、迁移或普遍采用 |

当任一绿灯缺失时，交付中保留 `not_run`、`blocked` 或 `unknown`。不要为了获得“全绿”而临时扩大权限、替换环境或改写规格。
