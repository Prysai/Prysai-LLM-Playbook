# 第 16 章：工程路线——从想法到可靠软件

**状态：**`candidate`。**实验：**`draft / not_run`。能生成代码、通过构建或看到页面，都不等于真实用户需要、运行可靠或已经发布。

## 问题：把“写代码”误当成“交付结果”

AI 可以快速生成补丁，却也能在错误的仓库、错误的范围或未经授权的环境中生成看似合理的修改。可靠工程不是让模型一次写完，而是把需求、现状、最小切片、行动边界、验证、失败恢复和交接串成闭环。

## 从一个可验收的竖向切片开始

不要从“做完整产品”开始。先定义一个可以在可丢弃副本中验收的最小变化：用户可见结果、允许修改的路径、禁止动作、输入基线、验收命令、人工检查、回滚目标和未覆盖风险。

| 阶段 | 关键问题 | 最低证据 |
|---|---|---|
| 定义 | 用户到底要什么？范围和权限是什么？ | 任务协议、输入、基线 |
| 计划 | 最小切片和依赖是什么？ | 方案、风险、回滚 |
| 修改 | 实际改了什么？ | diff、路径、行动日志 |
| 验证 | 哪些声明被检查？ | 命令、原始输出、退出码、人工检查 |
| 交接 | 完成与未知分别是什么？ | 证据表、下一步、恢复方法 |

## 操作：给 Agent 一个工程合同

合同至少要说清：目标用户和可观察结果；允许读取/修改的目录；明确禁止的生产、网络、凭据、安装、发布和删除；现有命令与超时；验收标准；遇到失败的停止条件；以及谁确认外部副作用。不要把“自己判断并修好所有问题”当作合同，它没有范围也没有回滚。

每次修改前记录工作目录、仓库根目录、分支、输入版本、`git status` 和基线测试。每次修改后记录变更路径、diff、命令、退出码、原始输出、未运行检查和人工观察。一个绿色测试只能支持它覆盖的断言，不能支持部署、用户理解、性能、安全或发布成功。

## 小实验：一条 Markdown 竖向切片

在可丢弃副本中，仅允许修改一个指定 Markdown 文件。先写发布说明的输入事实和验收规则，再完成：CP0 定义、CP1 计划、CP2 修改、CP3 验证、CP4 交接。至少做一个失败分支：缺少输入时编辑前停止；检查失败时保存输出；或在新会话中仅根据检查点和仓库状态恢复。不要安装依赖、改 PATH、登录、push、发布或重启服务。

## 失败恢复不是重复同一条命令

失败后先问：当前状态是什么？已有副作用是什么？下一次尝试改变了什么诊断条件？若答案不清楚，应停止并保存检查点。重复同一命令并不能叫恢复。若工具建议强制重装、上传日志、使用凭据或扩大权限，把建议记为数据，等待明确授权。

## 我真的学会了吗？

- [ ] 我能把模糊需求切成可验收的竖向切片。
- [ ] 我在编辑前固定了范围、基线、权限和回滚。
- [ ] 我能把实际 diff、命令、退出码和人工观察对应到不同主张。
- [ ] 我在失败后先检查状态，而不是盲目重试或重装。
- [ ] 我能区分本地完成、远端发布、生产运行和用户验收。
- [ ] 我没有把构建通过写成产品成功。

框架、依赖、命令和部署规则都是易变事实，应以当前项目的官方文档和本地环境为准。配合 [实验 009：工程生命周期](../labs/lab-009-engineering-lifecycle-ZH.md) 与 [实验 013：可审计竖向切片](../labs/lab-013-l3-vertical-slice-ZH.md)。本章为 `candidate`，不证明任何具体系统已经生产可用。
