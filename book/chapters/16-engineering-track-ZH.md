# 第 16 章：工程路线——从想法到可靠的软件

**状态：**`candidate`。**实验：**`draft / not_run`。能生成代码、通过构建或看到页面，都不等于真实用户需要、运行可靠或已经发布。

## 问题：把“写代码”误当成“交付结果”

AI 可以快速生成补丁，却也可能在错误的仓库、错误的范围或未经授权的环境中写出看似合理的修改。可靠的工程流程不是让模型一次写完，而是把需求、现状、最小切片、行动边界、验证、失败恢复和交接串成一个闭环。

## 学习目标

你能把需求拆成可验证的小切片，并把构建、测试、本地运行、发布和用户验收看作不同的证据主张。

## 真实问题入口：绿色测试不等于用户任务完成

补丁可以编译成功，却仍忽略空输入、错误路径或恢复方法。关键不是有多少绿灯，而是检查是否覆盖具体用户动作及其失败情形。

公开问题记录里有三类很适合工程练习的信号：

- **FP-09：** 有报告称，模型容量错误中断任务后，排队的请求可能接着使用半完成状态。重试前应先检查工作树、diff、测试和最后一个完成点，不能把未知状态当成干净起点。
- **FP-10：** 有 Windows CLI 的格式化或验证命令长时间停在 `Working`，却没有清晰错误。命令需要输出上限、超时和中断路径；“命令启动了”不等于“验证通过了”。
- **FP-11：** 有报告称，源代码验证被扩大成持久环境的强制重装。安装、发布、部署、重启和线上验证都是不同的授权状态，不能由“跑一下测试”自动推出。

这些是用户报告或分析，不是本项目对所有版本的本地复现或根因确认。真正做工程决策时，仍要回到当前仓库、当前运行时和当前证据。

## 工程生命周期：每一步都要有进入条件和退出证据

```text
定义问题 → 写规格与验收 → 计划和切片
        → 增量实现 → 静态检查/测试
        → 运行时验证 → 复核与简化
        → 发布/回滚 → 维护与回归
```

| 阶段 | 进入条件 | 最低出口证据 |
|---|---|---|
| 定义 | 已知用户或系统问题与范围 | 别人能复述的问题陈述 |
| 规格 | 输入、输出、错误和边界已写明 | 验收条件与非目标 |
| 计划 | 依赖和风险已列出 | 可独立验证的切片 |
| 实现 | 当前切片与基线已确认 | 小而可解释的 diff 和更新记录 |
| 测试 | 正常与失败路径可运行 | 命令、结果和失败解释 |
| 运行时验证 | 有可启动环境与代表性输入 | 版本、日志、响应/截图和环境 |
| 发布 | 变更已复核且可恢复 | 发布记录、监控和回滚演练 |

构建、测试、本地运行、用户接受和生产就绪是五个不同的结论；不要用其中一个替代另一个。

## 从一个能验收的最小纵向切片开始

不要从“做完整产品”开始。先定义一个可以在可丢弃副本中验收的最小变化：用户能看到的结果、允许修改的路径、禁止动作、输入基线、验收命令、人工检查、回滚目标和未覆盖风险。

| 阶段 | 关键问题 | 最低证据 |
|---|---|---|
| 定义 | 用户到底要什么？范围和权限是什么？ | 任务协议、输入、基线 |
| 计划 | 最小切片和依赖是什么？ | 方案、风险、回滚 |
| 修改 | 实际改了什么？ | diff、路径、行动日志 |
| 验证 | 哪些声明被检查？ | 命令、原始输出、退出码、人工检查 |
| 交接 | 完成与未知分别是什么？ | 证据表、下一步、恢复方法 |

## 做法：给 Agent 一份工程约定

这份约定至少要说清：目标用户和可观察结果；允许读取/修改的目录；明确禁止的生产、网络、凭据、安装、发布和删除；现有命令与超时；验收标准；遇到失败的停止条件；以及谁确认外部副作用。不要把“自己判断并修好所有问题”当作约定，它没有范围也没有回滚。

每次修改前记录工作目录、仓库根目录、分支、输入版本、`git status` 和基线测试。每次修改后记录变更路径、diff、命令、退出码、原始输出、未运行检查和人工观察。一个绿色测试只能支持它覆盖的断言，不能支持部署、用户理解、性能、安全或发布成功。

### 先查真实来源，再逐个切片改动

框架、API、库版本和命令的事实，优先从官方文档、类型定义、当前代码或可复现结果确认；博客和模型记忆只能作为线索。测试不能证明真实网络、数据库、浏览器、权限、并发、时区和部署行为时，要单独设计运行时检查。每次只改一个能解释的切片，并保存 diff 和恢复点；不要在未知失败上继续叠加修复。

### 运行时证据要单独记录

运行时检查至少记录启动命令、依赖版本、测试用环境变量、实际输入、响应或页面、日志、错误路径和环境。生产就绪还需要安全、性能、迁移、监控、回滚和用户验收证据。缺少输出、测试依赖、基线或工作树状态时，先停止并缩小检查；不要为了“让验证通过”替换运行时或强制重装环境。

## Web coding：把一个可见结果带到真实浏览器里

“做一个完整网站”隐藏了受众、页面状态、源文件、运行时、浏览器验收和发布
回滚等多个任务。先在可丢弃副本中完成一个静态页面的单一可见改动：读取
`examples/skill-sandbox/product-context-real-estate` 的 README 和 `index.html`，
只改 `index.html` 中的一句话，不加框架、图片、表单、API 或网络请求。Python 3
已经可用时，按沙盒文档在复制目录运行 `python -m http.server 4182`，打开
`http://127.0.0.1:4182/`，检查标题、改动句子、标题保留、链接、控制台和 390px
视口。

记录至少保留：复制目录、允许的文件、URL、检查到的可见状态、diff，以及部署、
无障碍、其他浏览器和用户验收等未验证项。源文件的 diff 不能证明 CSS 加载、相对
路径、移动端裁切或运行时错误；本地渲染通过也不等于网站已部署。

浏览器检查不是“看起来差不多”就结束。应逐项确认标题、主标题、状态文案、链接目标、控制台错误、键盘顺序，以及需要时的窄视口。视觉反馈可以补充目标区域和状态，但不能替代文字规格：写清要改哪一处、必须保留什么、用什么观察判定通过。

## 用 LLM 学编程：按证据逐级增加难度

不要承诺几天就“学会编程”。每一级都要有当前任务的可观察证据，再进入下一级：

| 等级 | 练习 | 进入下一级前的最低证据 |
|---|---|---|
| 1. 阅读 | 让模型解释一个已有函数或页面 | 能用自己的话说出输入、输出和一个边界 |
| 2. 修改 | 在可丢弃项目中做一个可见改动 | diff 只有允许文件，浏览器或检查器能看到变化 |
| 3. 测试 | 添加或运行一个聚焦检查，并包含失败例 | 能说清检查证明什么、没覆盖什么 |
| 4. 切片 | 从合同到运行时交付一个垂直功能 | 正常路径与空/无效路径都有记录 |
| 5. 恢复 | 从中断或失败检查点继续 | 继续前先看基线，保留失败证据 |
| 6. 协作 | 使用规则、隔离环境、复核和交接 | 另一个人能根据记录重现决策 |

每次让模型先读后改，先列范围和假设；缺少输入会改变风险或验收时就停止。模型的解释能帮助学习，但不等于你已经能独立诊断、实现或维护。

## 小实验：一条 Markdown 垂直切片

### 准备

使用包含 `input.json` 的可丢弃本地目录；不得联网、使用凭据、配置远端或安装依赖。记录原始文件与允许写入的路径。

### 任务

在可丢弃副本中，仅允许修改一个指定 Markdown 文件。先写发布说明的输入事实和验收规则，再完成：CP0 定义、CP1 计划、CP2 修改、CP3 验证、CP4 交接。至少做一个失败分支：缺少输入时编辑前停止；检查失败时保存输出；或在新会话中仅根据检查点和仓库状态恢复。不要安装依赖、改 PATH、登录、push、发布或重启服务。

### 证据

保存任务卡、diff、实际命令、退出码、输入、独立重新查看的输出和未执行动作。没有这些记录的测试不能证明发布或用户验收。

### 复盘

每个检查实际支持哪条主张？哪条失败路径仍未知，下一步最小检查是什么？

## 可观察实验：直接实现与完整生命周期的对照

在可丢弃目录中选择低风险功能，例如读取文本列表、去重后写入 JSON。准备正常输入、空输入、重复项、缺字段和无效编码；固定运行时版本、超时和输出目录，不使用真实秘密或外部写入。

1. **直接实现轮：** 只给出目标，记录模型是否澄清规格、改了哪些文件、执行了哪些命令，以及是否处理无效输入。
2. **生命周期轮：** 先要求问题陈述、验收、非目标、切片计划和测试矩阵，再逐片实现，并在每步后检查 diff。
3. 两轮都运行静态检查、单元测试、本地运行、空输入和无效输入；记录每个问题在哪一层被发现。
4. 模拟中断或容量错误：先停止，检查工作树、最近 diff、日志和测试状态，再决定继续、恢复或建立新检查点。
5. 不要强制重装、写入生产、部署或重启；这些建议应记为超出当前授权。

证据至少包括两个任务合同、diff、测试矩阵、命令与退出码、运行时输入/输出、错误日志、回滚点和最终验收。分别标记“构建成功、测试通过、运行时正确、用户/发布验收”，不要合并成一个完成标签。

## 迁移练习

把任务卡用于修改一个学习示例，但不改变链接、导航或发布状态。写清用户影响、文件、检查和恢复方法。

## 来源与维护边界

工程生命周期和证据分层是稳定方法。框架、命令、运行时和部署规则是易变事实，必须在具体项目、当前版本和实际环境中重新核验。

## 失败恢复不是重复同一条命令

失败后先问：当前状态是什么？已有副作用是什么？下一次尝试改变了什么诊断条件？若答案不清楚，应停止并保存检查点。重复同一命令并不能叫恢复。若工具建议强制重装、上传日志、使用凭据或扩大权限，把建议记为数据，等待明确授权。

## 我真的学会了吗？

- [ ] 我能把模糊需求切成可验收的垂直切片。
- [ ] 我在编辑前固定了范围、基线、权限和回滚。
- [ ] 我能把实际 diff、命令、退出码和人工观察对应到不同主张。
- [ ] 我在失败后先检查状态，而不是盲目重试或重装。
- [ ] 我能区分本地完成、远端发布、生产运行和用户验收。
- [ ] 我没有把构建通过写成产品成功。

框架、依赖、命令和部署规则都是易变事实，应以当前项目的官方文档和本地环境为准。配合 [实验 009：工程生命周期](../labs/lab-009-engineering-lifecycle-ZH.md) 与 [实验 013：可审计垂直切片](../labs/lab-013-l3-vertical-slice-ZH.md)。本章为 `candidate`，不证明任何具体系统已经生产可用。

## 把需求变成工程任务卡

“给我加导出功能”还不能开始编码。先把它写成一张可复核的卡；未知项保留为问题，而不是由模型自行决定：

```text
用户动作：在 <页面/命令> 请求导出 <明确数据范围>。
成功：生成 <格式>，包含 <字段>；用户能看到 <可观察结果>。
失败：无权限、空数据、无效输入、写入失败时分别返回什么？
非目标：不迁移历史数据、不发布、不改变权限、不接入外部服务。
允许范围：可读/可写路径、允许命令、网络和秘密边界。
验收：哪些测试、一次本地运行、哪项人工检查；各自覆盖什么？
恢复：原始状态、可删的临时产物、回读检查和停止条件。
```

只有当这张卡能让另一位开发者复述目标和非目标时，才选择第一个切片。若导出格式、覆盖策略或权限仍未知，最小切片可以只是读取输入并生成预览，而不是悄悄写文件。

### 四个绿灯，四种不同结论

| 证据 | 可以说什么 | 不能说什么 |
|---|---|---|
| 构建成功 | 指定配置能编译/打包 | 用户流程可用或已部署 |
| 测试通过 | 该测试断言在该环境成立 | 未覆盖的错误、浏览器、权限或真实输入正确 |
| 本地运行正确 | 指定版本和输入得到观察到的结果 | 生产环境、所有账户或性能已验证 |
| 发布状态可读回 | 指定远端出现该 revision 或记录 | 用户已接受、监控正常或能安全回滚 |

不要把四个绿灯合成“产品已经完成”。每个结论都需要自己的命令、输入、环境、输出和范围。

## 小实验：一个 JSON 垂直切片

在可丢弃目录做一个功能：读取 `input.json` 中的字符串列表，去除重复项并写入 `output.json`。只允许该目录内读写，不允许网络、安装、登录、提交、推送或发布。

1. 写任务卡和基线：正常列表、空列表、重复列表、缺字段或无效 JSON。
2. 先实现一个切片：只处理正常与重复输入；保存 diff 和命令输出。
3. 增加空输入和无效输入处理。每次只改变一个可解释点，并在改动后运行已声明检查。
4. 用独立本地命令读取 `output.json`，确认内容、错误信息和原输入的状态；记录运行版本、输入、退出码和原始输出。
5. 模拟中断：在一个半完成状态停止，先读 `git status`、diff、日志和输出，再决定继续、恢复或新建检查点。不要直接添加无关需求。

若命令无输出、依赖缺失、工作区未知，或建议改 PATH、重装运行时、上传日志、部署或重启，停止并说明缺失的授权和恢复材料。绿色结果不值得用扩大权限来换取。

## 本章验收补充

- [ ] 我能写出用户动作、成功/失败、非目标、范围、验收和恢复，而不是只写功能名。
- [ ] 我按切片保存 diff、命令、退出码、输入/输出和未知项。
- [ ] 我不会把构建、测试、本地运行、远端发布或用户接受混成一条结论。
- [ ] 我在中断或长时间无输出后先检查状态，再决定是否重试。

## 工程任务卡：一次可验收的最小改动

这张卡适用于你拥有或获授权的可丢弃项目副本。它先约束问题，再让任何 LLM 协助阅读、计划或编辑；它不授权安装、联网、提交、推送、发布或接触生产数据。

```text
目标：用户完成 [一个具体动作] 后应看到什么可检查结果？
范围：允许读取 [路径]；确认后仅改 [路径]；明确不改 [路径]。
基线：当前分支/提交、已有改动、相关测试或命令的原始结果。
真实来源：哪个规格、现有行为、测试、接口或设计文件拥有此事实？
最小切片：本次只改变哪一项可观察行为？
验收：文件范围、定向检查、运行时观察和人工阅读各验证什么？
禁止动作：安装、网络、删除、提交、推送、发布、外部消息、秘密读取。
停止：路径、规格、授权、恢复方法或验收规则不清楚时暂停。
交付：diff、实际命令与输出、通过/失败/未运行、未知项和最小下一步。
```

### 四个绿灯是四种不同结论

| 信号 | 最多说明什么 | 仍不能说明什么 |
|---|---|---|
| diff 很小 | 比较范围内文本变化有限 | 需求已满足或运行正确 |
| 静态检查通过 | 该检查在记录环境中通过 | 所有路径与用户场景正常 |
| 本地运行通过 | 一个明确运行场景可观察 | 部署、性能、安全或外部集成正确 |
| 人工验收通过 | 指定读者按指定规则看到了结果 | 长期维护、迁移或普遍采用 |

当任一绿灯缺失时，交付中保留 `not_run`、`blocked` 或 `unknown`。不要为了获得“全绿”而临时扩大权限、替换环境或改写规格。
