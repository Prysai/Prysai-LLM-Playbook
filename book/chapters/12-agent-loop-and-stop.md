# 第十二章：Agent 的循环、状态和停止条件

## 本章要解决的问题

用户常说“让 Agent 自主完成”，却没有说明它如何观察、如何决定下一步、什么时候重试、什么时候询问人、什么时候停止。没有这些约束，自主性很容易变成不可审查的连续动作：命令失败后重复执行，验证卡住后继续等待，或者在原任务已经失去边界时仍然修改文件。

本章把 Agent 视为一个可观察的工作循环。我们不猜测模型的隐藏推理，而是记录输入、可用上下文、计划、工具动作、结果、状态变化、风险和停止理由。

## 学习目标

读者完成本章后应当能够：

- 画出一个包含观察、计划、行动、反馈、状态更新和停止分支的 Agent 循环；
- 用状态记录区分目标、假设、已读、已改、已验证、未验证、阻塞和待确认；
- 判断失败属于可恢复、需补充输入、需人类判断还是应立即停止；
- 为重试写出变化点、预算和新证据，而不是允许无限循环；
- 在验证卡住、权限越界或工作树处于半成品状态时恢复控制权并诚实交付。

## 现实问题入口

[FP-10](../../docs/research/field-problems-codex.md#fp-10：格式化验证命令让-windows-cli-agent-长时间停在-working)记录了验证或格式化命令长时间没有完成的用户报告；[FP-11](../../docs/research/field-problems-codex.md#fp-11：agent-将源代码验证扩大为未授权的持久环境替换)记录了把“完成验证”扩大为安装、替换环境等未授权动作的事件报告。[FUP-01 与 FUP-05](../../docs/research/field-problems-follow-up-2026-08-10.md)还分别记录了子 Agent 已创建但任务消息未被观察到，以及长时间无事件后报错并自动重试的用户报告。这些报告均没有被本项目本地复现，也没有提供可由本项目确认的官方根因；它们的教学价值在于区分“状态存在”“能力链已贯通”“恢复控制权”“完成验证”和“获得新授权”。

## 1. 一个可观察的循环

```text
读取目标、上下文与授权
        ↓
形成当前计划、假设与下一可观察结果
        ↓
选择一个允许的工具动作
        ↓
记录输入、输出、错误和副作用
        ↓
更新状态、风险、证据和预算
        ├─ 验收已满足       → 交付
        ├─ 缺少输入/权限    → 暂停询问
        ├─ 可恢复失败        → 改变条件后小范围重试
        ├─ 目标或范围冲突    → 停止并报告冲突
        └─ 风险/重复失败     → 停止并交付阻塞说明
```

每次循环都应能回答：“我刚刚观察到什么？它证明了什么？下一步会改变哪个未知？如果这一步失败，在哪里停？”如果只能说“Agent 觉得应该继续”，就缺少可审查的状态。

## 2. 把状态写出来

复杂任务至少维护以下字段；可以放在任务记录、检查点或最终交付摘要中：

| 字段 | 要写的内容 | 不能替代的证据 |
|---|---|---|
| 目标 | 本次要交付的用户结果和非目标 | 不能用愿望代替验收 |
| 假设 | 当前认为成立、但尚未证明的前提 | 不能用计划代替事实 |
| 已读取 | 文件、版本、来源、工具返回和范围 | 不能证明已经正确理解 |
| 已改变 | 路径、diff、外部状态和时间 | 不能证明行为可用 |
| 已验证 | 实际命令、运行路径、截图、来源或人工检查 | 只覆盖声明的范围 |
| 未验证 | 尚未运行、无法访问或证据不足的断言 | 不能写成通过 |
| 阻塞/待确认 | 缺什么输入、权限、选择或人类判断 | 不应靠猜测清除 |
| 下一步 | 动作、预期观察、停止点和预算 | 不等于已经执行 |

状态更新应尽量是事件而不是形容词，例如“在临时目录运行检查，退出码 1，未改动文件”比“检查失败”更有用。对于会改变工作树的步骤，先保留 checkpoint 或 diff；对于外部动作，记录目标账户、组织、仓库、环境和授权范围。

## 3. 重试必须改变一个条件

重试前先分类失败：输入缺失、理解错误、工具或环境错误、实现错误、权限错误，还是验证选择错误。然后写出变化点：

```text
第一次失败：
失败类别：
保留的状态/证据：
本次只改变：
预期获得的新证据：
最多重试次数：
若仍失败则：
```

相同输入、相同工具、相同权限和相同假设的重复尝试，通常不会产生可靠的新证据。更好的下一步可能是补充文件、缩小范围、换一个只读验证方式、回到干净 checkpoint，或请求人类选择。重试预算要和风险匹配：无副作用的本地检查可以有小预算，高权限、联网、数据写入和发布动作不应靠自动重试推进。

### 自动重试仍然是一次新尝试

客户端或编排器发起自动重试时，也要遵守人工重试的证据规则。至少为每次尝试记录 `run_id`、`attempt_id`、`parent_attempt_id`、触发原因、开始时间、首个事件时间、最后事件时间、工具/外部副作用、结束状态和错误类别。自动重试不得覆盖原尝试的日志，也不得把后一次成功回填为 `first_pass: true`。

只有同时满足以下条件，自动重试才可继续：动作是只读或已证明幂等；第一次尝试的工作树与外部状态已经复核；没有未决审批；仍在预先声明的时间、调用和成本预算内；重试会改变一个明确条件或遵循预先声明且可审查的瞬时错误策略。写入、发布、发送消息、付费调用或状态不明的动作默认停止自动重试，转为人工确认。

### 用事件时间线识别长等待，而不是猜测原因

长任务开始前声明 `no_event_threshold` 和 `hard_stop_threshold`。时间线至少包含：请求开始、首个可见事件、每次工具调用、最后事件、达到无事件阈值、已授权中断、错误、自动重试和完成。达到无事件阈值只说明“在该观察窗口内没有事件”，不证明死锁、网络故障、模型仍在推理或服务端根因。

```text
request_started → first_event? → tool_or_output_events → completed
        │               │
        │ 无事件阈值     └─ 事件再次中断超过阈值
        ↓
pause_and_inspect → side_effect_unknown? → stop blocked/unverified
        │
        └─ 状态清楚、动作幂等、预算允许 → 最多一次受控重试
```

如果连首个事件都没有，先检查可观察的能力链：会话创建、任务消息到达、目标工具注册、工具调用开始、目标状态读取。停在第一个没有证据的层级；例如“子 Agent 已创建”不能证明任务正文到达，“请求被自动重试”不能证明第一次请求没有执行过动作。

## 4. 停止条件是交付协议的一部分

至少预先写出以下停止条件：

- 验收已经满足，且证据覆盖声明范围；
- 必需输入、目标选择或人类决策缺失；
- 当前权限与要做的动作不匹配；
- 下一步会产生未授权副作用；
- 发生重复失败且没有新的诊断信息；
- 目标、项目规则或新信息互相冲突；
- 达到时间、调用、变更或风险预算；
- 达到无事件阈值后仍无法确认进程、工作树或外部副作用状态；
- 自动重试将覆盖原始证据、重复非幂等动作或超出预先声明的重试预算；
- 工作树状态不明，无法判断下一步会作用于哪一份结果。

停止后不能只写“失败”。至少交付：已完成和未完成、最后一个可确认状态、错误或阻塞证据、未验证项、未执行的动作、恢复入口，以及需要谁做什么决定。停止是保护证据和边界的能力，不是自动任务的反面。

## 实验：缺失输入与重复失败

### Setup

在临时目录建立一个无秘密的小任务，例如“读取 `input.txt`，把每行非空内容按字母顺序写入 `output.txt`”。准备任务协议和验收条件：输出存在、行数与输入非空行数一致、原输入不变。不要使用网络、生产目录或持久环境安装。

### Task

第一轮故意不提供 `input.txt`。观察 Agent 是否说明缺失并暂停，而不是猜测内容或创建替代输入。第二轮提供一个包含重复行和空行的样本，要求它先读后改，并保留 diff 和运行结果。每一步都记录计划、实际动作、返回结果和状态。

### Evidence

提交状态表或日志，至少包含：任务协议、临时目录路径、输入存在性检查、实际修改、运行命令及输出、输出内容、原输入未改变的证据、停止或交付理由。证据应能区分“文件已生成”“转换规则正确”“验证命令成功”这三个断言。

### Failure variant

让验证命令连续失败两次，例如把验收条件临时改为一个不可能满足的行数要求。第一次失败后要求记录失败类别和变化点；第二次不能只重复同一命令，必须缩小范围、检查输入/假设或停止报告阻塞。若 Agent 提议安装新工具、修改持久环境或访问外部服务，实验直接停在授权检查处。

### Reflection

回答：缺失输入时，什么证据说明“暂停”是正确行为？第二次失败与第一次相比改变了什么？如果命令被中断，为什么不能写“验证通过”？哪一个状态字段最能防止后续动作误用半成品？

## 失败或边界案例

- **命令卡在 Working：** 保存请求开始、首个事件、最后事件和阈值时间；先用已授权的中断方式恢复控制权，不把等待时间当成成功证据。之后检查进程、工作树、输出、外部副作用和验证状态，再决定是否以更小范围重跑。
- **自动重试随后成功：** 原尝试保留为 `failed`、`interrupted` 或 `unverified`，后一次尝试单独记录；只有后一次满足验收，不得改写首次通过率。
- **验证失败但实现可能正确：** 不把“测试工具坏了”写成实现通过。分开记录实现状态和验证状态，尝试一个低风险、可解释的替代检查，仍不清楚就停止。
- **容量错误或会话切换：** 不把后续 prompt 自动接在半成品上。先检查 checkpoint、diff、最近输出和未完成切片，再选择继续、回滚或新任务。
- **为了验证而安装或替换环境：** 技术上可执行不等于获得授权。安装、force reinstall、改变持久环境、使用生产凭据、发布或重启都应成为新的确认点。
- **工具返回“成功”但没有目标证据：** 退出码、界面提示或 Agent 摘要只证明工具报告了某种状态；仍需检查目标文件、行为、外部状态或来源是否符合验收。
- **重复失败的诱惑：** 只在明确改变输入、工具、权限、范围或假设时重试，并设置上限；否则停止比继续堆叠修改更可靠。

## 迁移练习

把循环和停止卡分别应用于：

1. 一次研究资料收集：网页打不开、来源冲突或访问日期缺失时如何停；
2. 一次营销页面修改：浏览器渲染通过但用户效果尚未验证时如何区分状态；
3. 一次团队发布：本地检查通过但仓库、组织或发布权限不明确时如何请求确认。

每个场景写出至少两个可恢复失败、两个立即停止条件和一份交付摘要。要求把“下一步建议”与“已经执行的动作”分开。

## 本章验收

- [ ] 我能画出包含观察、行动、反馈、状态更新和四类分支的 Agent 循环；
- [ ] 我能为一项任务维护目标、假设、已读、已改、已验证、未验证、阻塞和下一步；
- [ ] 每次重试都有失败分类、变化点、新证据和上限；
- [ ] 长任务有无事件阈值、硬停止阈值和事件时间线，自动重试不会覆盖首次尝试；
- [ ] 我能说明命令卡住、容量中断和验证失败时如何先恢复证据，再决定继续；
- [ ] 我能区分恢复控制权、验证结果和获得新授权；
- [ ] 我能为缺失输入、权限不匹配、重复失败和未授权副作用写出停止交付；
- [ ] 我完成了实验，并能用日志或状态表证明 Agent 为什么继续、暂停或停止。

## 来源与更新提示

可观察循环、显式状态、有限重试和停止条件是稳定方法；具体 Agent 界面、Working 状态、模型容量、工具语义、审批流程和权限默认值属于易变事实。产品事实请以[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)及其中列出的当前官方文档为准；现场案例请以[研究记录](../../docs/research/field-problems-codex.md)的用户报告、独立复现、官方确认和本地复现标记为准。每次工具或产品更新后，重新执行本章的缺失输入和重复失败变体，记录入口、版本、环境、证据和复核日期；在没有运行证据前保持 `draft` 或 `candidate`，不要写成 `verified`。
