# 第六章：模型选择不是模型崇拜

## 本章要解决的问题

模型选择很容易被一句“这个模型最好”替代。真实工作需要的是：在特定任务、上下文、工具、时间和预算下，哪个模型足够好、更加稳定、返工更少。

## 学习目标

读者完成本章后应当能够：

- 先按任务类型和风险定义需求，再选择模型；
- 固定任务、上下文、工具、权限和评分标准进行比较；
- 把 GPT-5.6 Luna 当作待验证假设，而不是预先宣布的总体最佳模型。

## 现实问题入口

FP-08 记录了 model 与 custom provider 不一致的配置问题，FP-09 记录了容量错误和排队任务风险。它们说明模型选择还包括 provider、版本、容量和恢复策略。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)。

## 1. 用任务类型描述需求

先把任务分类，而不是先挑模型：

- **理解与提取：** 从材料中找出结构化信息；
- **转换与生成：** 按固定格式改写、归纳或生成；
- **规划与判断：** 处理多约束、权衡和不确定性；
- **代码与工具：** 读取项目、编辑、运行和修复；
- **研究与审查：** 找来源、核对证据、暴露缺口；
- **创作与设计：** 需要风格、审美和多轮反馈。

不同任务对速度、上下文、工具调用、长程一致性、视觉能力、成本和人工复核的权重不同。

## 2. 建立选择函数

```text
可接受质量
+ 任务稳定性
+ 工具/上下文适配
+ 可验证性
- 成本
- 延迟
- 返工
- 风险
```

这不是要计算出一个神奇分数，而是强迫团队把“最好”拆开。某模型在结构化摘要中便宜稳定，不代表它在复杂重构或高风险审查中就是最佳选择。

## 3. 先写模型卡，再做比较

每个候选模型至少记录：

```text
model_id / provider：
工作面与账户范围：
推理强度或配置：
任务集版本：
上下文、工具和权限：
成本口径：
通过标准：
已知容量/网络异常：
结论状态：观察 / candidate / verified / disputed
```

如果模型 ID、provider、上下文、权限、任务版本或成本口径不同，结果不能直接进入同一比较表；先标记 `not_comparable`，不要用平均数掩盖条件变化。

### 指标先定义再记录

- **首次通过：** 第一次运行就满足全部验收条件；不是“输出看起来不错”；
- **返工次数：** 从第一次失败到满足验收的额外尝试数；中断或条件改变要单独标记；
- **成本：** 记录实际可用的计费口径或明确写“未观察”，不把 token 数直接冒充货币成本；
- **错误类型：** 至少区分事实、范围、工具、权限、验证和格式错误；
- **人工评分：** 固定评分表和评分人，不能运行后再改标准。

## 4. GPT-5.6 Luna 的正确学习方式

官方资料把 GPT-5.6 Luna 描述为面向成本敏感工作负载优化的模型，Codex 文档强调它适合清晰、重复性较强的工作。团队当前提出了“性价比高、适合扩大使用”的待验证假设。

Field Guide 会教用户验证这个假设，而不会把它写成永久结论。至少要固定：

- 同一批任务和输入；
- 同一套工具、权限和上下文；
- 同一验收标准；
- 每个任务的重复次数；
- 运行时间、成本、首次通过率、返工率和错误类型；
- 人工对正确性、完整性和可维护性的评分。

如果只比较一次 demo 的文案观感，不能推出“性价比最高”。

## 5. 先选择最低足够能力

对低风险、重复性任务，优先选择成本和延迟更合适的模型；对高不确定性、高风险或需要复杂工具编排的任务，提高验证强度，必要时换更强模型或增加人工检查。模型更强不等于可以取消边界和验收。

## 6. 实验：固定任务集比较

### Setup

从 `evals/task-set-v1.yaml` 选择低风险任务，冻结任务文本、上下文、工作面、工具、权限、重复次数和评分表。先做 3 个任务的 smoke 对照；只有两边条件稳定且没有明显阻塞，才扩展为 10 个任务。不要使用秘密、生产数据或不可回滚动作；记录模型 ID、日期和任何容量/网络异常。

### Task

在扩展阶段建立 10 个小任务，包含抽取、转换、规划、代码检查和证据审查。让两个候选模型在完全相同的条件下完成，记录：

| 任务 | 首次通过 | 返工次数 | 运行时间 | 成本 | 主要错误 | 人工评分 |
|---|---:|---:|---:|---:|---|---:|
| 任务 1 |  |  |  |  |  |  |

smoke 阶段只允许得出“是否值得扩展”的结论；扩展阶段才可以报告任务类别上的观察。无论哪一阶段，都要写出“适合什么任务”和“不能推出什么”，防止从小样本扩张到所有任务。

### Evidence

保存任务集版本、模型卡、每次运行的原始输出或日志、首次通过/返工、耗时、成本口径、错误分类和人工评分。若条件变化或运行中断，标记该行 `not_comparable`，不用空值伪造结果；记录运行中断不会自动变成失败或通过。

### Reflection

回答：哪个任务类型真正改变了选择？一个更便宜的结果在哪些条件下仍不可接受？哪些结论只是官方产品描述、哪些来自本次运行？下一次复核日期是什么？

## 故意失败/边界实验

只挑一个漂亮的演示任务，让一个模型运行一次就宣布“性价比最高”。然后用评测夹具加入失败、迁移和权限边界任务，检查原结论是否仍然成立。若数据不足，结论必须退回 `candidate`。

## 迁移练习

把比较协议迁移到文档转换、研究证据审查和低风险代码检查三个任务，说明同一模型在不同任务上的优势不能直接互相外推。

## 来源与更新提示

模型 ID、描述、价格、限额和容量会变化。官方模型说明见[官方 Codex 基线](../../docs/research/openai-codex-baseline.md)和[本轮事实刷新记录](../../docs/research/openai-codex-facts-refresh-2026-08-09.md)，可执行任务集见[评测夹具](../../evals/task-set-v1.yaml)；本章不把未运行的评测写成结论，也不把官方的“快速/低成本”定位改写成项目性价比结论。

## 本章验收

学习者能把“模型好不好”改写成一个有任务集、指标、约束和复核日期的比较问题；能填写模型卡并识别 `not_comparable` 条件；能区分产品官方描述、团队假设和实验证据；能说明何时降低模型能力、何时提高验证强度。
