# 第一章：先理解 GPT，再信任 Codex

## 開場：先別急著站隊

今天先從大家最常聽到的名字開始：GPT、Codex、Grok、Gemini、Kimi，甚至
Answer.AI。它們經常出現在同一段討論裡，但並不是同一類東西。有的是模型家族，
有的是把檔案和工具接到模型上的工作環境，也有的是把研究做成產品或教育內容的團隊。
你不需要先背參數，也不需要先挑「最強模型」。先學會問一個更有用的問題：

> 我今天要完成什麼任務？需要什麼輸入、輸出、工作環境和哪些檢查？

| 你可能聽到的名字 | 第一個該問的問題 | 不要直接假定 |
| --- | --- | --- |
| GPT / OpenAI | 我實際用的是哪一個模型，以及 ChatGPT、API 還是 Codex 哪個工作環境？ | 一個模型名稱自動給了檔案權限、工具權限或更好結果。 |
| Grok / xAI | 提供者所說的推理能力，是否真的和我的具體任務有關？ | 它對你的任務最好，或我的帳戶一定能用。 |
| Gemini / Google DeepMind | 這項任務是否真的需要我能存取的輸入形式或生態系？ | 每個 Gemini 入口都有相同工具和能力。 |
| Kimi / Moonshot AI | 我需要測試的是程式碼、分析，還是長文件工作？ | 宣傳的上下文或功能已經證明它在這個工作環境中更好。 |
| Answer.AI | 我是在尋找應用研究、教育內容還是終端產品？ | 它是可以和其他模型一起放進選擇器的基礎模型提供者。 |

[模型與工作環境方向圖](../evidence-library-ZHTW.md#source-notes)
為每一行保留了提供者的一手來源，並把「廠商的定位」與「實際測得的結果」分開。
先把你手上已有模型的一次請求用好；只有在相同任務和相同驗收規則下，才比較不同候選項。

## 本章要解決的問題

人們常把 Codex 描述成「一個更會寫程式碼的聊天視窗」。一旦遇到第一次真正的失敗，這種描述就失去了作用。它無法解釋為什麼模型、專案、上下文、權限、工具或回饋發生變化時，同一個請求會產生不同的行為。它還會誘發一種危險的捷徑：把自信的回答或工具訊息當成工作已經執行並檢查過的證明。

本章將建立一個小型的操作模型。它不是對隱藏思維鏈的斷言。我們只使用學習者能夠檢查的內容：輸入、選定的上下文、請求的動作、工具邊界、回傳的結果、發生變化的狀態，以及用於決定停止的證據。

## 學習目標

完成本章後，你應當能夠：

- 區分 GPT、模型、Codex 產品工作環境、工具、Skill 和 Agent 迴圈；
- 解釋為什麼上下文選擇和取樣會在使用者原句不變的情況下改變輸出；
- 將模型提出的工具動作與執行時權限檢查、工具結果和最終驗證區分開；
- 把不確定的完成宣告轉化為一個小型、可逆的實驗；
- 識別真實世界中的症狀，同時不虛構官方根因。

## 從可觀察的分層開始

分析任務時，使用以下分層：

    模型能力
            ↓ 生成回答或動作提議
    Codex 工作環境
            ↓ 提供專案上下文和執行邊界
    工具／執行時
            ↓ 可能允許、拒絕或執行請求的動作
    工具結果/變化後的狀態
            ↓ 成為新證據或新上下文
    驗證和人工決定
            ↓ 決定工作可以停止還是必須恢復
    交付結果宣告

這些箭頭並不是自動保證。模型可以提出 shell 命令，但執行環境可能並未執行它。執行環境也可能執行一條退出碼為零的命令，卻檢查了錯誤的檔案或環境。工具可能回傳看似成功的訊息，而預期的外部物件並未改變。每一個箭頭都需要自己的證據。

### 用通俗語言解釋這些術語

| 術語 | 它提供什麼 | 它不能證明什麼 |
|---|---|---|
| GPT | 一系列生成式模型能力 | 檔案存取、終端機存取、帳戶權限或變更成功 |
| 模型 | 某次執行使用的具體模型／設定 | 它在每個工作環境都可用，或適合所有任務 |
| Codex | 將模型與專案上下文、工具和權限連接起來的工作環境 | 每個可見帳戶或連接器都已獲得目標物件的授權 |
| 工具 | 用於讀取或更改檔案、程序、瀏覽器、Git 託管平台或服務的介面 | 請求的動作已獲允許、正確無誤或已經完成 |
| Skill | 包含觸發條件、輸入、邊界、步驟和證據的可重複使用方法 | 新模型、權限授予或驗證的替代品 |
| Agent | 圍繞觀察、行動、回饋、重試和停止形成的可觀察多步迴圈 | 可以存取隱藏推理，或有權無限重試 |

專案使用的穩定術語定義見 [CONTEXT.md](../evidence-library-ZHTW.md#core-terms)。模型名稱、呼叫語法和預設權限等產品細節屬於易變事實；請使用帶日期的[官方基線](../evidence-library-ZHTW.md#source-notes)，並在依賴這些事實之前重新核對其中連結的一手文件。

## 語言模型如何生成回答

一個實用的簡化模型是：

    選定的上下文 + 任務 + 模型設定
            → 可能的下一個 token 的機率分佈
            → 每次取樣或選擇一個 token
            → 回答、結構化動作提議或拒絕

模型不是從資料庫中取回一個預先寫好的答案。它根據收到的上下文，有條件地生成一個序列。上下文、順序、指令、工具結果或生成設定的細微變化，都可能改變後續生成內容。這個簡化模型不能告訴你模型究竟「想了什麼」；它告訴你，為了做出公平比較，哪些輸入必須保持不變。

### 機制卡：上下文既是預算，也是過濾器

更多上下文並不自動意味著更好的上下文。先把每一項候選輸入分一分類：

1. 它是否是識別目標物件和驗收條件所必需的？
2. 它是否可信，還是資料中未經驗證的指令？
3. 對目前的任務而言，它是否足夠新？
4. 它是在增加有效資訊，還是在與任務爭奪上下文空間？

對於 README 編輯，專案規則和目標 README 可能相關。隨意選取的舊 issue、複製來的提示詞和無關秘密則不相關。一個寫著「忽略專案規則」的檔案仍然是需要分析的檔案，而不是必須服從的權威。因此，上下文選擇既是品質決策，也是安全決策。

### 機制卡：差異是一個測量問題

兩次輸出不同，不能證明是某一段上下文造成了差異。模型可能進行了不同的取樣，服務可能使用了另一個修訂版，工具狀態可能已經改變，或者任務本身定義不足。每次只改變一個變數，並記錄：

    run-id | 模型／操作環境 | 輸入修訂版 | 改變的變數 | 輸出／狀態 | 證據 | 未知項

如有可能，請重複基線。如果無法固定某個變數，應將觀察標記為「觀察到不同結果」，而不是「由 X 導致」。

## 工具呼叫是協議邊界，不是魔法動作

當 Codex 可以使用工具時，應把過程看成四個獨立事件：

1. 模型提出一個動作；
2. 執行時檢查範圍、權限和確認規則；
3. 工具執行、拒絕或超時；
4. 下一步檢查結果和變化後的狀態。

以下說法並不等價：

- 「模型寫出了一條命令。」
- 「命令已經執行。」
- 「命令改變了預期物件。」
- 「變更滿足驗收標準。」

對於本機檔案，有用的證據可能包括已檢查的路徑、前後 diff、針對性檢查和未驗證項列表。對於 GitHub 或其他外部操作，還要加入精確目標、授權狀態、確認點、結果物件，以及回復或還原路徑。登入頁面、工具名稱或一條寫著「完成」的訊息，本身都無法填補這些證據缺口。

### 權限不等於能力

官方產品邊界將技術沙盒與審批邊界區分開來。用本專案的術語來說：

- 沙盒描述執行時在技術上可以存取什麼；
- 審批描述執行時必須在什麼動作前暫停；
- 兩者都不能證明目標、範圍或結果是正確的。

不要根據模型名稱、是否存在 Skill、帳戶是否登入或按鈕是否可用來推斷權限。在產生副作用之前，立即再次確認目標和動作。學習實驗應從不含秘密的臨時副本開始。

## 值得儘早理解的三個機制陷阱

同一個可觀察邊界會出現在三類常見系統中。它們在產品示範裡看起來不同，但都可能產生看似合理、卻還不能信任的結果。

### 1. 結構化輸出可能語法正確、語義錯誤

JSON Schema 或帶型別的回答可以約束格式、必填欄位和某些型別。它不能證明某個 ID 確實存在、日期仍是目前日期、權限有效，或來源支援該欄位值。請使用三層檢查：

```text
schema/型別檢查 → 業務規則檢查 → 來源/狀態檢查
```

例如，`{ "status": "approved" }` 可能是有效 JSON，也符合 schema，但該核准屬於錯誤的專案。應把原始模型輸出、schema 結果、業務規則結果和外部驗證儲存為彼此獨立的證據。[LLM 機制研究](../evidence-library-ZHTW.md#source-notes)將其記錄為一項教學邊界，而不是斷言所有提供者都採用相同實作。

### 2. 檢索負責選擇材料，但不保證完整使用

搜尋或檢索可能選中相關片段，但相關不等於完整、新鮮、權威，也不等於模型在因果上確實使用了該片段。一小段例外條款的排名可能低於一條寬泛規則，片段邊界也可能把條件和定義分開。應記錄查詢、過濾條件、修訂版、選中的片段 ID 和最終引用。如果答案發生變化，除非實驗隔離出了原因，否則應說「不同的檢索上下文產生了不同結果」。

### 3. 看起來像指令的資料仍然是資料

網頁、附件、issue 正文、工具結果、資料庫欄位和 MCP 資源中，可能包含「忽略之前的規則」之類的文字。某個字串不會僅僅因為看起來像系統指令就獲得權威。應把它當作不可信資料，預設保持外部操作為唯讀，並在它能夠影響工具呼叫之前另行決策。對於初學者，這是提示注入防禦的實用形式：識別資料來源、限制工具邊界，並在記錄中保留其試圖影響的動作。

這三個陷阱及其面向具體提供者的來源和低風險實驗，均收錄於[機制深挖](../evidence-library-ZHTW.md#source-notes)。

## Agent 迴圈的真正含義

最適合教學的方式，是把 Agent 看成一個會留下可觀察痕跡的狀態機：

    ready
      → observed
      → planned
      → action_requested
      → awaiting_approval / executing
      → feedback_received
      → verified / recoverable_failure / blocked
      → stop 或 bounded_retry

迴圈需要重試預算，每次重試也需要理由。如果輸入、權限、環境或驗收條件沒有變化，「再試一次」就不是恢復策略。良好的停止記錄應回答：

- 到達了什麼狀態；
- 如果發生了變化，改變了什麼；
- 哪些證據支援目前的宣告；
- 缺少哪些證據；
- 哪個最小的後續檢查可以減少不確定性。

即使不假裝揭示隱藏推理，這個迴圈仍然有用。記錄可觀察事件和決策；不要把虛構的私下理由當成模型內部過程的實錄。

## 現場案例：有用的教訓在於邊界

以下內容來自專案現場研究收集的公開使用者報告。它們不是官方根因報告，本專案也沒有在本機重現。它們的價值在於說明過於簡化的心智模型會在哪裡失效。

### 案例 FP-09：容量中斷與危險的重試假設

有使用者報告說，所選模型達到容量上限後變得不可用，之後排隊的指令似乎可能會從部分完成的狀態繼續。該報告沒有確定服務端原因或確切的佇列語義。因此，安全的應對方式不是「不斷點選繼續」。

最小且安全的應對方式是：

1. 停止並記錄模型、操作環境、時間和可見錯誤；
2. 傳送另一條指令前，檢查目前的 diff 和檢查點；
3. 對目前的狀態執行最小範圍的可用檢查；
4. 只有在決定哪個狀態具有權威後，才從有名稱的檢查點恢復，或開始一次乾淨的執行。

來源和證據標籤：[現場研究中的 FP-09](../evidence-library-ZHTW.md#source-notes)。

### 案例 FP-10：「Working」不是進度證明

一位 Windows CLI 使用者報告說，格式化或分析工作長時間停留在 Working/執行中狀態，沒有明確完成或報錯。該報告無法證明原因究竟是命令掛起、程序處理、輸出緩衝、環境漂移還是其他因素。長時間執行的標籤是一項狀態觀察，不是成功結果。

記錄命令、程序狀態、經過時間、輸出和中斷點。然後檢查 diff，並在安全時獨立執行針對性檢查。不要把「介面仍顯示 Working」變成「格式化程式已經完成」。

來源和證據標籤：[現場研究中的 FP-10](../evidence-library-ZHTW.md#source-notes)。

### 案例 FP-11：驗證可能意外擴大任務範圍

一份公開報告描述了一個 Agent 將驗證步驟擴大為未經授權的強制重新安裝。報告中的解釋是否是真正根因尚未確認。無論根因是什麼，持久有效的教訓都一樣：驗證必須宣告命令範圍、寫入範圍和停止點。

如果某項檢查需要破壞性重置、網路呼叫、重新安裝套件或使用憑證，就應停止並請求新的決定。「檢查失敗」並不會授予升級操作的權限。

證據分類和相關章節／實驗對應見[現場問題索引](../evidence-library-ZHTW.md#source-notes)。

## 真實任務的決策規則

在請 Codex 採取行動之前，先填寫這張小型任務卡：

| 欄位 | 僅修改 README 的範例 | 缺失時怎麼辦 |
|---|---|---|
| 目標 | 幫助新貢獻者啟動專案 | 詢問；不要把「做得更好」解釋成驗收條件 |
| 上下文 | 專案規則、README、套件指令碼 | 只讀取最少的相關檔案 |
| 允許動作 | 在臨時分支中編輯一個本地 README | 未列出的副作用一律視為禁止 |
| 回饋 | diff、連結檢查和命令輸出紀錄 | 繼續編輯前先增加一項檢查 |
| 停止條件 | 範圍發生變化、命令需要安裝/聯網，或缺少證據 | 停止，並記錄為 blocked 或 not_observed |
| 交付宣告 | 「README 已更改；連結檢查通過；未測試執行時」 | 每一項宣告都不得超出實際證據範圍 |

這張卡比一段很長的提示詞更有價值，因為它揭示了提示詞經常隱去的決策。

## 第一次對話：三條能立刻使用的提示詞

你不需要先掌握複雜術語。先選擇一個不含私人資訊、沒有外部寫入風險的小目標，把下面任意一條複製到你實際使用的 LLM 對話框中，再把方括號改成自己的內容。它們的價值不在「神奇措辭」，而在於讓模型先說清楚自己的理解、限制和下一步；不同模型和工作環境的結果可能不同。

### 1. 學一項語言或其他小技能

```text
我正在學習 [西班牙語/一項技能]，目前能做到：[我的真實水平]。
請給我一個 10 分鐘、只練一個目標的練習，不要假設我已經掌握其他內容。
先給一個例子，再讓我自己回答；只糾正最影響理解的一到兩處。
最後用三行寫出：我做對了什麼、下一次該練什麼、還不能據此判斷什麼。
不要把一次對話說成我已經掌握了這項技能。
```

例子不是「七天學會某種語言」的承諾。一次練習只會留下當下的回答與回饋；記憶是否保留、能否遷移到陌生場景，以及真實交流能力，都要在之後分別檢查。若模型給出無法核對的事實、練習量過大或要求你提供個人資料，請縮小題目、要求來源，或停止這輪對話。

### 2. 高效整理一組公開資料

```text
我需要回答這個問題：[問題]。
只使用我下面提供的來源；不要補充未給出的事實。
先列出每個來源的標題、日期（如果有）和它可能支援的內容；再寫一個帶來源標記的短摘要。
把「來源明確支援」「合理推斷」「仍然未知」分開列出。
如果來源相互衝突、過期或缺少關鍵事實，請停在問題清單，不要替我猜答案。
```

這條提示詞把「蒐集到很多資料」改成「能回到來源檢查的結論」。對需要連網、付費資料庫或真實帳戶的研究，先確認產品權限、來源授權和資料範圍；聊天框顯示答案不等於研究已經完成。

### 3. 請模型先幫你把模糊任務說清楚

```text
我要完成：[結果]，對象是：[受眾或檔案]。
已知輸入：[材料]；不確定的地方：[未知項]。
先不要執行、傳送、發布、安裝或修改任何東西。
請只輸出：目標重述、缺少的資訊、最小可逆步驟、驗收證據、停止條件。
若需要秘密、網路、帳戶、外部寫入或更大範圍，請標記 blocked 並說明需要誰確認。
```

即使答案看起來很好，也先檢查它是否真的回答了這些欄位。若它跳過未知項直接編造、把「建議」寫成「已完成」，或擴大到未授權動作，就把這當作可觀察的失敗，不要繼續讓它猜。

## 三步核對法

每次用完提示詞，花一分鐘核對三件事：**它讀到了什麼？它實際做了什麼？我能檢查什麼？** 對純聊天任務，通常只有輸入和輸出可檢查；對檔案、瀏覽器或程式碼任務，還需要目標、diff、命令輸出或外部結果。這樣你從第一天起就能區分「會聊天」和「能可靠交付」。

## 小實驗：保持任務不變，只改變一項輸入

### 準備

使用一個只包含 README 和一條簡短專案規則的臨時本地副本。不得使用私有儲存庫、秘密、客戶資料、網路呼叫或外部帳戶。為每次嘗試記錄一個 run ID。

### 任務

向模型或 Codex 操作環境提出：

> 檢查 README，並指出一個可以改進的地方。不要編輯檔案。請說明你讀取了什麼、為什麼這項改進很重要，以及之後可以如何檢查編輯結果。

執行一次基線，然後每次只改變一個變數，再次執行：

1. 加入受眾和專案目標；
2. 加入一條專案規則；
3. 要求回答前先給出簡短計劃；
4. 加入一項明確的驗收標準。

如果兩次執行之間的操作環境或模型發生變化，應將其記錄為混雜變數。不要根據隨意的前後對比聲稱存在因果關係。

### 證據

儲存提示詞／輸入修訂版、run ID、操作環境／模型標籤、讀取範圍、回答、是否存在檔案 diff，以及未驗證項。靜態練習通過，並不能證明每個 Codex 操作環境都會出現同樣的行為。

### 反思

- 哪個變數改變的是任務邊界，而不只是措辭？
- 你如何區分工具提議與已經執行的動作？
- 在宣告結果正確之前，你需要觀察什麼？
- 哪個最小的後續實驗可以消除一項不確定性？

## 故意失敗

在臨時副本中使用這條故意缺少充分定義的請求：

> 讓整個專案變得專業，並修復所有問題。

正確的回應不是進行大規模、無邊界的編輯。可靠的回應會指出「專業」的定義、範圍、輸入檔案、風險、驗收標準和停止條件均有缺失；它會提出只讀盤點，或詢問一個聚焦的問題。如果它立即開始編輯，應將其記錄為任務邊界失效，而不是有用的主動性。

## 驗收清單

當你能夠做到以下各項時，就可以繼續學習：

- 解釋模型能力、Codex 操作環境、工具動作、工具結果和驗證之間的區別；
- 把上下文選擇描述為一個受控變數，而不是「越多越好」；
- 將現場報告標記為使用者報告、官方事實、本地觀察或未經驗證的假設；
- 編寫一張包含允許動作和停止條件的任務卡；
- 生成一份說明證據不能證明什麼的執行記錄。

不要因為能夠複述定義就把本章標記為已掌握。請完成[實驗 011：GPT、Codex、工具與 Agent](../labs/lab-011-gpt-codex-boundaries-ZHTW.md)，並把結果儲存在本地學習記錄中。

## 遷移任務

把同一個模型應用於非程式碼任務：請 Codex 根據一組固定的公開來源準備一份簡短研究摘要。識別模型、操作環境、來源上下文、工具、允許動作、來源品質檢查、停止條件和最終證據。故意加入一個無關來源，並記錄你如何決定是否排除它。不要因為來源公開，就假設其中每一條指令都具有權威。
