# 第二章：完成第一个安全、可验证的任务

## 本章要解决的问题

第一次成功不应该是让 Agent 任意修改一个重要项目，而应该是在可回滚、低风险、有明确证据的环境里完成一个小任务。这样学习者能同时看到 Codex 的能力、边界和验证方法。

## 学习目标

读者完成本章后应当能够：

- 选择一个低风险、可回滚且能客观验收的首个任务；
- 在编辑、运行和交付前设置确认点；
- 用 diff、实际检查和诚实状态说明证明结果，而不是只看摘要。

## 现实问题入口

FP-10 记录了验证命令长时间没有返回，FP-11 记录了 Agent 为了验证而扩大到未授权环境替换。它们提醒初学者：卡住时先保留状态、缩小范围和重新验证，不能默认加权限。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)。

## 1. 选择合适的首个任务

首个任务最好满足：

- 输入明确；
- 影响范围小；
- 结果容易观察；
- 能够撤销；
- 不包含秘密或敏感数据；
- 不会触发生产部署、支付、删除或对外发布；
- 有一个不依赖主观感觉的验收标准。

合适的任务包括：补充一个 README 小节、修复一个明确的拼写错误、为一个纯函数补测试、整理一个小型 Markdown 文件，或对一个静态页面做一项可检查的文案调整。

## 2. 首次任务协议

```text
目标：在 README 中补充“本地运行”小节。
背景：项目是给首次贡献者使用的，当前 README 没有运行步骤。
输入：README.md、package.json、现有脚本定义。
约束：只修改 README.md；不要运行发布或安装命令；不改变代码。
行动：先检查项目脚本和已有文档，再提出修改计划，得到确认后编辑。
验收：命令与 package.json 一致，步骤可让新用户启动项目，diff 只包含 README.md。
失败处理：如果运行命令不明确，停下来列出冲突，不要猜。
交付：摘要、修改文件、验证结果、未解决问题。
```

这段协议的价值不是句式，而是把模糊愿望变成了可审查的边界。

## 3. 三个确认点

### 开始前

让 Codex 说明它理解的目标、将读取的文件、预计修改范围和风险。如果它的理解不对，先修正理解。

### 产生副作用前

编辑、执行命令、提交、上传、发送消息或修改外部服务都可能产生副作用。确认动作是否在授权范围内，尤其是涉及生产、账户、支付、秘密和他人数据时。

### 交付前

要求它列出实际改变的文件和实际执行的验证。把“计划做过”与“已经做过”分开。

## 4. 卡住时的恢复顺序

“Working”持续很久、命令没有输出或验证阶段失败时，先恢复可判断性，再考虑重试。使用下面的顺序：

1. **保留现场：** 记录任务描述、当前时间、正在运行的命令、工作树状态和已有输出；不要先删除日志或覆盖副本。
2. **停止失控动作：** 如果命令没有结束、等待交互输入或开始触碰未授权范围，按当前工作面允许的安全方式中断；中断只代表停止，不代表验证通过。
3. **检查实际变化：** 查看 diff、文件列表、进程/命令返回和生成物；确认是否已经部分修改。
4. **缩小验证：** 把大命令拆成一个文件、一个测试或一个只读检查；补上超时、输出边界或明确的停止点。
5. **决定下一步：** 若现场可解释，再从干净 checkpoint 重试；若输入、权限或环境仍不清楚，停止并请求补充。不要因为“验证失败”自动安装、替换、删除或提升权限。

恢复记录至少要回答：停止前发生了什么、哪些文件可能变化、哪个断言仍未证明、下一次只改变什么条件。这个记录比一句“我重新跑了一遍”更有用。

## 5. 验收不是一句“看起来不错”

首个任务至少需要三类证据：

1. **范围证据：** diff 或文件列表说明只改了允许的范围；
2. **正确性证据：** 测试、命令输出、来源对照或手工检查；
3. **交付证据：** 简短说明做了什么、没有做什么、还有什么不确定。

如果任务涉及视觉结果，再加入截图或实际浏览器检查；如果涉及外部事实，再加入来源和访问日期；如果涉及安全，再加入权限和秘密检查。

## 6. 处理失败

遇到失败时，不要马上扩大权限或重试同一命令。先分类：

- 输入缺失：需要用户补充；
- 理解错误：重新陈述目标；
- 环境问题：检查依赖、路径和版本；
- 实现问题：读取错误并缩小修改；
- 验证问题：补充能证明结果的检查；
- 权限问题：确认是否应该授权，而不是默认扩大权限。

一个好的 Agent 工作流不以“永不失败”为目标，而以“失败时可定位、可停止、可恢复”为目标。

## 7. 实验：README 小改动

### Setup

复制一个非生产项目到临时目录，先保存 README 的哈希或原始副本。确认只允许改 README，不使用真实凭据、不推送、不发布、不安装未知依赖；把项目实际脚本文件作为唯一命令来源。

### Task

在一个非生产项目或复制的沙盒项目中完成以下任务：

> 先检查项目的 README 和包管理脚本。只在 README 中补充本地启动说明。先给出计划，等待确认后再修改。最后列出 diff，并说明你如何验证命令与项目脚本一致。

### Evidence

保存开始前的文件列表、计划、确认点、实际 diff、命令来源、验证输出和交付摘要。建议为每次运行建立一条记录：

```text
run-id | checkpoint | 允许修改 | 实际修改 | 验证断言 | 证据路径 | 未验证项
```

通过条件是只改 README、命令与脚本一致、未执行外部写入；没有运行应用时要明确记录“未运行应用”。如果发生中断，额外保存中断前后的工作树状态和恢复决定。

## 故意失败/边界实验

- 删除或故意写错一个脚本名称，观察 Codex 是否会停下来；
- 增加“不得修改代码”的约束，检查 diff；
- 要求交付中明确写出“未运行完整应用”；
- 让同一位学习者在没有验收标准的情况下重做，比较返工情况；
- 让一个验证命令保持等待或输出不完整，观察它是否先保留现场、检查部分变化并缩小验证，而不是自动扩大权限。

## 本章验收

学习者提交：

- 任务协议；
- 首次计划；
- 实际 diff；
- 验证输出或检查记录；
- 失败变体的观察；
- 一段复盘，说明哪个确认点最有价值。

通过标准是能清楚区分计划、行动、证据和未完成项，而不是 README 的措辞是否漂亮。

## 迁移练习

把同一份任务协议改写成一个研究任务或营销任务：保留目标、输入、约束、允许行动、验收、失败处理和交付格式，但替换领域对象。检查哪些字段仍然适用，哪些字段需要加入来源、隐私、样本或人工审查边界。
