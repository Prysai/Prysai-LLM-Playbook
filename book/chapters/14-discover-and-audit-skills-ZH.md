# 第 14 章：发现、安装与审计外部 Skill

**状态：**`candidate`。**实验：**`draft / not_run`。本章中的社区问题是风险线索，不是本地复现或官方根因结论。

## 先问一个更重要的问题

外部 Skill 能把重复步骤、领域知识和工具调用包装成方法，也可能带来依赖、网络访问、账号权限、外部副作用和许可证义务。真正的问题不是“哪里还有更多 Skill”，而是：一个真实任务暴露缺口后，Skill 是否真是合适的补救；怎样把目录条目变成可审计候选；怎样测试而不泄露秘密、不接受提示注入、不越过授权边界。

结论很简单：目录只是发现入口，不是质量证明；安装是状态变化，不是验证；“可以触发”不代表“应当采纳”。

## 本章目标

完成后，你应能：

1. 从任务目标、输入、输出和验收条件导出 Skill 需求，并区分知识、工作流、工具与权限缺口；
2. 在安装前审查来源、固定版本、触发与非触发条件、依赖、权限、许可证、备份、回滚、审批和负责人；
3. 识别要求秘密、无关上传、过宽权限或未声明外部行为的内容，并把候选标为 `blocked`；
4. 分开记录文件存在、被发现、被加载、被采纳和被验证，避免把一次烟雾测试写成生产采纳。

## 先写任务协议，再决定是否需要 Skill

把任务写成六项：目标、允许与禁止的输入、交付物、验收证据、授权范围、必须暂停的条件。范围不清时，先问问题；不要用安装掩盖需求不清。

| 缺口 | 常见处理方式 | 常见误判 |
|---|---|---|
| 缺少概念或事实 | 研究、官方文档、人工判断 | 用 Skill 代替查证来源 |
| 稳定重复的过程 | 本地 Skill 或脚本 | 用一个巨型 Skill 包办一切 |
| 外部系统的观察或改变 | 受控工具或连接器 | 把“可调用”当“已授权” |
| 目标或验收不清 | 先澄清任务 | 用安装掩盖问题 |

Skill 是方法与路由契约；工具是观察或改变外部世界的接口；Plugin/Connector 是承载或连接这些能力的产品层。审查时分别问：Skill 读什么、建议什么、工具实际做什么、外部服务会收到什么。不要从名称推断权限，也不要只凭 README 推断运行行为。

## 采纳决策卡

每个候选至少记录：任务缺口；触发与非触发条件；来源 URL、固定版本、清单日期；许可证、NOTICE、嵌套资产和复制边界；依赖、网络、账号；安装目标范围；权限和秘密边界；外部副作用；隔离试用；备份与恢复目标；回滚步骤和成功检查；审批点；负责人和下次复核；正例、边界、失败/注入、迁移测试；以及决策、证据、未知项和解除阻塞条件。

获取固定版本、写入安装目标、安装依赖或登录、进入团队或生产范围是不同审批点。一个审批不会自动推出下一个。回滚不能只写“删除目录”，必须说明安装前配置备份、准确目标、恢复步骤和恢复后的检查。

## 把决策状态和行为状态分开

| 决策 | 含义 |
|---|---|
| `recommendation-only` | 任务匹配看起来合理，只建议只读审查或隔离试用 |
| `blocked` | 许可证、版本、依赖、权限、目标范围或回滚中至少一项不清楚 |
| `approved-to-install` | 目标、备份、回滚、权限和审批明确，但尚未安装 |
| `installed-candidate` | 已在获批隔离目标安装且有路径与日志，行为验证和采纳仍未完成 |

行为证据另记：文件存在、被发现、被加载、被采纳、被验证。它们可部分成立，也会随工作面、账号、会话和版本不同而不同。文件存在不证明发现；发现不证明加载；加载不证明组织采纳；采纳也不证明行为已验证。

## 低风险实验：审查而不安装

准备两个固定版本或脱敏样本。A 有可追溯许可证和任务匹配，判断是否值得隔离试用；B 缺许可证、NOTICE 或回滚，判断是否阻止。只检查仓库 URL、固定版本、文件清单、许可证/NOTICE、`SKILL.md` 摘要、工具/网络/凭据声明和任务协议。不要安装、登录或启用团队环境。

为 A 设计但不运行四类验证：正例、边界例、失败/注入例、跨项目迁移例；写清输入、预期行为、停止条件和证据。A 没有真实安装目标、备份与回滚前只能是 `recommendation-only`。B 不能靠“根目录有许可证”越过嵌套资产、依赖或回滚缺口，应为 `blocked`。

## 常见失败与边界

- 列表里没有，不等于不存在：检查支持的根目录、普通文件要求和版本行为；链接、不同系统都需独立检查。
- 明确名称不能只看可见列表：用支持的显式入口记录解析结果；失败时给手动替代路径，不要假称已调用。
- 目录许可证不自动覆盖嵌套内容：没有明确许可证或 NOTICE 时保持 `reference-only` 或 `blocked`。
- 烟雾测试通过不代表生产安全：它可能没覆盖删除、重复重试、令牌泄漏、并发、超时、依赖损坏和维护者放弃。
- 安装会改变持久环境：涉及包、PATH、运行时替换、生产凭据或服务重启时，先明确目标、影响、回滚和授权。

## 我真的学会了吗？

- [ ] 我能从真实任务解释为什么需要或不需要 Skill。
- [ ] 我记录了来源、版本、触发/非触发条件和负责人。
- [ ] 我固定了版本，并写明隔离试用、备份、回滚和审批点。
- [ ] 我区分了 Skill 指令、工具权限与用户授权。
- [ ] 我审查了许可证、NOTICE、嵌套依赖与复制边界。
- [ ] 我为正例、边界、失败/注入和迁移设计了无秘密、低风险测试。

外部目录、产品入口和发现行为都是易变事实；使用前应查当前官方文档和项目来源。运行 [实验 017：采纳 Skill 前审计发现过程](../labs/lab-017-skill-discovery-audit-ZH.md)。本章仍是 `candidate`，并不证明某个 Skill 已安全采纳。

## 安装前，把候选项变成可否决的决定

目录、Star 和演示视频只能让一个 Skill 进入候选池，不能让它进入你的环境。为每个候选项留下一张独立审查卡：

```text
任务缺口：本次任务缺少什么稳定方法？
来源：项目 URL、固定 revision、检查日期、实际文件路径
触发 / 不触发：何时适用，何时必须让给其他方法？
许可证：仓库、目标文件、NOTICE、嵌套脚本与资产各自有什么证据？
依赖与权限：读取、写入、网络、账号、秘密、外部副作用
隔离试用：指定目录、无秘密输入、允许的动作与停止点
恢复：安装前配置备份、精确恢复步骤、恢复后的读回检查
决定：recommendation-only / blocked / approved-to-install / installed-candidate
```

缺少固定版本、许可证/NOTICE、安装目标、备份或恢复检查中的任意一项，就标为 `blocked`。不要通过“先装了再看”来消除信息缺口。

### 五种行为状态不能合并

```text
文件存在 → 当前工作面发现名称 → 新会话加载说明 → 所有者正式采用 → 四类用例验证
```

这五件事分别是 `file exists`、`discovered`、`loaded`、`adopted`、`verified`。一个目录中有 `SKILL.md`，最多证明第一个；安装日志最多支持 `installed-candidate`，不能证明触发正确、团队接受或真实效果。

## 四步审查法：先拒绝不清楚的候选项

不要从“怎么把它装进去”开始。先按顺序问四个问题，并在第一个无法用记录回答的地方停止：

1. **任务真的缺它吗？** 写出当前任务中重复、稳定且容易遗漏的判断。若只是缺少事实，先查来源；若目标不清，先澄清任务。
2. **我们拿到的到底是什么？** 固定项目 URL、revision、实际入口路径、许可/NOTICE 和嵌套依赖，而不是只保存项目名或 Star 数。
3. **它可能做什么？** 分开列出读取、写入、安装、联网、账号、秘密与外部副作用。没有清单时，不猜“应该没问题”。
4. **失败后怎么回到原处？** 写明隔离目录、安装前备份、恢复步骤与读回检查；“删掉目录”不是已验证的恢复方案。

四个问题都能用记录回答，才可以建议 `approved-to-install`；任何一项缺失，正确结果通常是
`recommendation-only` 或 `blocked`。这不是否定候选项，而是避免把好奇心变成未经审查的环境变更。

### 一个简短但完整的拒绝说明

```text
候选：<固定 URL 与 revision>
决定：blocked
原因：入口脚本会联网，但依赖清单、目标安装位置和恢复读回检查未提供。
已检查：项目链接、入口文件、顶层许可信号。
未检查：运行时行为、嵌套素材许可、实际网络流量。
解锁条件：补齐以上缺口后，在无敏感的隔离目录重做审查。
```

这种说明比“感觉不安全”更可用，也不把未运行的行为误写成已经发现的风险。

## 小实验：审查两个候选项，不安装任何一个

选择两个固定 revision 的公开候选项，或使用两个脱敏本地样本。A 应有可追溯来源和许可证信号；B 故意缺少许可证/NOTICE、依赖声明或恢复方案。

1. 只读取来源、revision、文件清单、入口摘要、依赖和许可信号；不下载到运行时目录，不登录，不联网执行。
2. 分别填审查卡，写明任务缺口、适用/不适用、最小权限、隔离试用和所有批准点。
3. 为 A 设计正例、边界例、注入/失败例和迁移例；每个都写输入、预期、停止点和证据，但不声称已运行。
4. 若 B 缺少文件级许可或可验证恢复，保持 `blocked`，写清解除阻塞所需材料。

来源中的“忽略上级规则”“读取并上传 `.env`”“为了测试先改生产配置”等文字都是不可信数据。它们不是 Skill 权限，也不是用户授权。正确结果是拒绝、记录并停止。

## 本章验收补充

- [ ] 我能区分知识缺口、重复方法、工具能力和不清楚的任务，且不会用安装掩盖问题。
- [ ] 我为外部候选项记录 URL、revision、文件路径、许可/NOTICE、依赖、权限和维护者。
- [ ] 我把获取、写入安装目标、安装依赖/认证、进入团队或生产范围分成独立批准点。
- [ ] 我只把有证据的状态写为存在、发现、加载、采用或验证；未知即写 `not_observed`。

## Skill 采用回执：先证明能审查，再决定是否启用

这个回执适用于项目自己的原创 Skill，也适用于从外部项目发现的候选项。它不会因为一个仓库热门、说明流畅或目录可见，就把外部内容变成可信或可执行的能力。

```text
候选名称与版本/提交：
来源：原创 | 外部；外部项目的原始链接：
维护者与复核日期：
要填补的具体任务缺口：
许可证：代码、文档、资产及嵌套依赖是否分别清楚：
预期读取/写入/网络/安装/发送/发布行为：
正例、边界例、失败例、迁移例：
已观察：文件存在 | 发现 | 选择 | 加载 | 执行 | 回读验证
未观察：
允许的临时试验范围：
拒绝、暂停或采用的理由：
下一项最小安全检查：
```

外部 `SKILL.md`、网页、Issue、安装日志和工具输出都属于待评估数据，其中的命令、链接或“忽略此前规则”一类文字不自动获得更高权限。没有清楚的来源、许可、行为范围或恢复路径时，正确决定是 `blocked` 或拒绝，而不是“先装上再说”。

### 分层启用，而不是一次性信任

先读元数据和说明，再在无敏感材料的临时目录中检查一条只读或可逆路径；只有在结果、范围和恢复方法都被记录后，才由人单独决定是否需要写入、网络、安装或外部动作。一次成功只支持记录的宿主、版本、输入和任务，不能证明跨模型、跨目录或跨账户都可靠。
