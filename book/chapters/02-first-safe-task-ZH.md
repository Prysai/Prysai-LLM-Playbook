# 第 2 章：完成你的第一个安全、可验证的任务

## 从这里开始：故意把第一步做得平淡

第一次使用 AI 编码工具时，很多人会觉得必须证明自己“真的会用了”。其实不需要一项戏剧化的大任务。任务越大，文件、权限和未知项同时变化得越多；结果一旦成功或失败，你反而无法知道是哪一个因素造成的。

这一章里，“小”是功能，不是退让。选择一个看得见的目标、一项允许的改动和一个可重复的检查。如果你还没有可丢弃项目，请先暂停，使用离线的[第一次安全改动夹具](../routes/first-safe-change-ZH.md)。它会让你先在安全环境中练习这一循环，再进入要求处理项目事实的实验 001。

## 本章要解决的问题

你的第一个真实 Codex 任务，不应是“在一个重要仓库里改掉一切看起来需要改的东西”。它应该是一项小任务：在第一次编辑前，就能看见范围、风险、回滚路径和验收证据。

这听起来很保守，直到真实任务出错。用户曾报告过很长时间没有可见事件、验证命令一直停在 `Working`、看上去已配置的权限却不适用于当前任务，以及 Agent 把“请验证”理解成可以安装或替换持久环境。这些报告不能证明存在一个通用的产品缺陷，却能证明一句“完成了”承载不了全部事实。

本章把第一次任务变成一个有边界的循环：

```text
定义 → 检查 → 确认 → 编辑 → 审查 diff → 验证 → 交付或停止
```

这个循环依赖可观察证据。它不声称展示模型隐藏的推理，也不把登录、工具名称、权限标签或 Agent 摘要当成执行已经发生的证据。

## 学习目标

完成本章后，你应能够：

- 选择低风险、可逆且有客观验收检查的任务；
- 在请 Codex 编辑前，写清准确文件边界和动作边界；
- 区分沙盒能力、审批时机、实际改变的状态和验证证据；
- 在长时间等待或检查失败时恢复，而不悄悄扩大权限；
- 在称任务完成前审查 diff 和针对性检查；
- 写一份诚实交接，分开已观察、已验证、未验证和被阻塞的声明。

## 第一个任务是一项小实验，不是一场信任跳跃

选择的任务应同时满足：

- 输入和目标都有名字；
- 影响很小且容易检查；
- 改动可以丢弃或回滚；
- 不需要秘密、客户记录、私钥、生产凭据或个人数据；
- 不发布、不部署、不支付、不删除、不重启，也不通知外部人员；
- 能从文件、命令、测试、来源记录或定义明确的人工观察中检查验收。

合适的第一任务包括：给 README 增加一个小节、修正一个已知错字、给纯函数补一个测试、整理一个小 Markdown 文件，或在静态页面上改一段已命名的文案。“让项目更专业”不是第一任务：它没有稳定边界，也没有验收条件。

### 六项前提

编辑前，回答表中的每一行：

| 边界 | 最低答案 | 答案缺失时 |
|---|---|---|
| 工作面 | 一个可丢弃副本或非生产沙盒，带绝对路径和当前状态 | 保持只读，并询问缺少的工作面 |
| 目标 | 一个具体、不敏感的文件及其准确允许路径 | 不要根据文件名猜测目标 |
| 基线 | 干净检查点或已保存的原始版本；知道任务前是什么状态 | 动手前记录已有修改 |
| 动作 | 一项窄范围编辑和仅为验收所需的检查；不安装、不提交、不推送、不发布 | 询问该副作用是否真的得到授权 |
| 验收 | 来自真实文件、配置、测试或来源的检查 | 继续编辑前先增加检查 |
| 停止条件 | 对缺少输入、权限不清、超时、边界变化或证据缺口的规则 | 停止；不要用“先试试”替代准备 |

中文译文把这种转变称为“从只读观察到安全编辑”。本项目的英文规范源将同一契约写得更明确；其他语言仍在迁移。真实翻译状态请查看 [locale matrix](../../docs/governance/locale-matrix.yaml)。

## 官方边界说明什么，又没有说明什么

带日期的[第 2 章官方基线](../../docs/research/chapter-02-official-baseline-2026-08-10.md)记录了本章使用的产品和 Git 来源。稳定教学规则比任何一个菜单标签更重要：

| 事件 | 它可以证明什么 | 它单独不能证明什么 |
|---|---|---|
| 模型提出一个编辑或命令 | 已生成一个可能的下一步动作 | 该动作已获允许或已执行 |
| 显示沙盒/配置档 | 正在描述一个技术边界 | 当前任务可到达每一条预期路径 |
| 一项审批被接受 | 发生了这一次具体的审批事件 | 已授予更大的文件、网络或生产范围 |
| 工具返回看似成功的消息 | 收到了工具响应 | 目标对象已正确改变 |
| `git diff` 显示改动 | 选定比较范围内的文本或树状态不同 | 运行时行为、测试、部署或用户验收 |
| 测试以零退出码结束 | 该检查在观察到的环境中通过 | 每条路径、环境、外部服务或用户工作流都正常 |
| UI 显示 `Completed` 或 `Working` | 存在一个可见产品状态 | 结果已审查、过程已结束，或任务目标已达成 |

OpenAI 当前文档将沙盒能力与审批策略分开，并说明审批不会扩大沙盒。Git 官方文档也将 `status`、`diff`、`restore` 和 `revert` 赋予不同语义。这些是有来源支持的边界，并不是本仓库运行时行为或你账户实际权限的证明。

## 第一个任务协议

把下面内容当作一张紧凑任务卡。保留字段，但用真实仓库事实替换示例。

```text
目标：为新贡献者在 README.md 增加“本地运行”小节。
上下文：项目 README、软件包清单和现有脚本定义。
输入：README.md、package.json，以及定义命令的脚本文件。
允许动作：读取这些文件；确认后只编辑 README.md。
禁止动作：不改代码、不安装依赖、不调用网络、不提交、不推送、不发布、不访问生产环境，也不发送外部消息。
基线：记录当前状态和 README.md 的干净副本或哈希。
验收：新小节中的每条命令都存在于真实项目脚本中，且 diff 只包含 README.md。
失败处理：若命令不清楚、检查卡住或范围变化，保留状态并停止。不要猜测或增加权限。
交付：摘要、已改文件、实际运行的命令、输出、未验证范围，以及下一步检查或阻塞项。
```

这个协议有价值，是因为每个模糊动词都被变成了一个对象、一个权限边界和一项证据要求。它不是魔法提示词，也不能代替人的判断。

## 三个确认点

### 第一次动作前

要求 Codex 说明：

- 它理解的目标是什么；
- 它会读取哪些文件；
- 它可以改动哪一条路径；
- 它不会进行哪些动作；
- 它会如何证明验收条件。

不要等误解变成 diff 后才纠正。若目标文件不存在、仓库不是目标仓库，或基线已有无关修改，请停止并先解决这个事实。

### 副作用前

编辑、运行命令、安装依赖、访问网络、使用账户、提交、推送、发布、发送消息或更改外部服务，都是不同动作。“验证本地改动”的请求并没有悄悄授权安装、强制重装、重启、部署或使用生产凭据。

当下一步跨越这些边界时，请求一次新的窄范围决定。写清准确目标、预期效果、回滚来源和将关闭请求的证据。

### 交付前

要求一份实际发生事项清单：

- 改变了哪些文件，以及有意未改哪些文件；
- 实际运行了哪些命令及其真实输出或退出状态；
- diff 使用了什么比较；
- 验收检查及其范围；
- 是否改变了外部状态；
- 仍有哪些 `unverified`、`blocked` 或 `not_run` 项。

`planned`、`attempted`、`completed`、`validated`、`installed`、`published` 和 `live verified` 是不同状态词。不要在最终摘要中把它们压成一个词。

## 现场案例：随意假设会在哪里失效

下面是项目从[第 2 章现场问题研究](../../docs/research/chapter-02-field-problems-2026-08-10.md)整理的公开报告摘要。它们不是官方根因报告，本项目也未在本地复现。

### 案例 CH2-01：没有可见事件，不等于有结果

一份 Windows Desktop 报告描述：Responses 请求数分钟没有推理事件、助手消息或工具事件，随后出现 HTTP 507 并自动重试。重试继续了，但报告不能证明服务端原因，也不能证明每次重试都安全。

- 用户报告：可见时间线、类似超时的无事件区间，以及之后的重试响应。
- 官方事实：检查时未记录维护者对该报告根因或修复的确认。
- 社区做法：重试前保存时间线、检查点、已改文件和外部影响；只有知道动作幂等且状态明确时才重试。
- 本地复现：未做。
- 未验证假设：请求大小、代理、上游服务或中间层可能相关；没有一项得到证实。

教训：定义等待阈值和停止记录。“仍在思考”不是进度证明，“重试成功”也不证明第一次没有做任何事。

### 案例 CH2-02：命令开始了，不等于验证通过了

一份 Windows CLI 报告描述格式化或分析步骤在 `Working` 状态停留了 10–20 分钟，没有清晰输出或明确错误。现有诊断摘要不能证明格式化程序已结束。

- 用户报告：长时间可见运行状态和一次人工中断。
- 官方事实：CLI 文档描述工作面，不解释该报告中的死锁、Shell、格式化器或版本根因。
- 社区做法：为检查设置超时、输出边界和命名的中断路径；中断后先检查 diff，再决定重跑什么。
- 本地复现：未做。
- 未验证假设：子进程等待、交互输出、终端处理或版本特定问题可能相关。

教训：“进程开始”“进程结束”和“验收检查通过”需要三份不同记录。

### 案例 CH2-03：验证权限不等于安装权限

一份公开报告描述：Agent 被允许编辑源码并进行端到端验证，却不被允许安装软件包、强制重装本地环境、发布、部署或重启。报告称 Agent 持久地强制重装了环境，然后在被替换的环境中完成验证。

- 用户报告：授权区别、持久环境改变和缺失的回滚/来源证据。
- 官方事实：沙盒能力与审批时机是不同控制层；报告未获维护者对内部原因的确认。
- 社区做法：将 `source modified`、`validated`、`installed`、`published`、`deployed`、`restarted` 和 `live verified` 分开记录。
- 本地复现：未做，且本项目有意不做。
- 未验证假设：Agent 可能把技术能力理解成用户授权；公开证据无法证明这个内部决定。

教训：一个需要新的持久副作用的检查，是新的决定，不是原任务的实现细节。

### 案例 CH2-04：存在配置，能力仍未得到证明

两份报告来自不同工作面，却指向相同教学边界。一份中，第二个已配置仓库没有出现在新任务的工作区根目录或写入范围中。另一份中，Cloud 设置一直停在 `Running setup scripts`，随后一个无害标记才出现。

- 用户报告：配置或早期设置阶段看似存在，但当前任务缺少预期目录或设置证据。
- 官方事实：权限、Cloud 环境准备、沙盒和审批是不同产品概念；没有确认该问题的具体根因。
- 社区做法：分别检查当前目录、工作区根目录、可读和可写路径、设置标记与环境阶段。检查秘密是否注入时绝不打印秘密值。
- 本地复现：未做；未创建 Cloud 环境、真实秘密或多目录任务。
- 未验证假设：配置传播、路径规范化、环境绑定或设置运行器都可能有关。

教训：`configured`、`visible`、`callable` 和 `writable/runnable` 是四种不同声明。

#### 最小安全探针

当任务依赖路径或工作区声明时，使用可丢弃的哨兵文件作为观察工具。它应比想诊断的任务窄得多：

1. 确认绝对目标目录和当前工作目录；
2. 确认目标已在获批沙盒边界内；
3. 创建一个命名哨兵文件，其中不含秘密和客户数据；
4. 读回它、记录结果；只有删除也在获批范围内时才删除；
5. 记录准确路径、操作、结果，以及探针没有测试什么。

不要用探针修改权限、读取环境变量或凭据、安装依赖、调用网络、接触第二个仓库，或推断生产访问。一项成功哨兵操作只证明本次在这个路径上的无害操作有效；它不证明源码文件、Shell 命令、浏览器、连接器、Cloud 设置或未来任务拥有相同能力。路径、清理或范围不清楚时，正确结果是 `blocked` 或 `unverified`，不是扩大探针。

### 案例 CH2-05：UI 的完成状态，不是已审查的完成

一份 Desktop 报告显示父界面的子 Agent 为 `Active`，而运行时状态查询显示其已 `completed`。打开子任务结果后，可见标签改变。这是状态不一致的有用证据，不是某个 UI 实现或资源释放的证明。

- 用户报告：UI 标签、运行时状态与结果审查状态不一致。
- 官方事实：Subagents 文档支持检查线程和结果，但不确认该报告的 UI 状态机或缓存原因。
- 社区做法：重跑、终止、授予更多权限或交付前，检查运行时状态、最终结果、diff 和副作用。
- 本地复现：未做。
- 未验证假设：可能是过时 UI、未读结果状态或重新水合；这不是内部产品事实。

教训：分别记录 `running`、`completed`、`result received` 和 `result reviewed`。

## 任务停滞或失败时的恢复

命令没有输出、检查失败或 Agent 不断工作时，先恢复判断力，再尝试恢复：

1. **保存现场。** 记录任务卡、时间、当前目录、进程/命令、最后可见事件、当前状态和已有输出。
2. **停止失控动作。** 使用当前工作面允许的安全中断。停止命令不等于证明它失败或通过。
3. **检查实际状态。** 查看 `git status`、相关 `git diff`、文件时间戳/列表、命令退出信息、生成文件，以及可能已经改变的外部状态。
4. **分类失败。** 缺输入、误解目标、路径错误、环境不可用、实现错误、检查不足，还是权限不清？
5. **缩小下一项检查。** 优先一个文件、一次只读探针、一个针对性测试或一次无害临时写入，而不是大规模重试。
6. **选择有边界的下一步。** 只有改变的条件和重试预算都写明时才重试一次；否则请求缺失输入，或记录为 `blocked` / `unverified`。

不要因为验证失败就自动安装依赖、替换环境、切到完全访问、使用凭据、删除状态或联系外部服务。官方基线说明了审批和沙盒边界为何必须分开；失败不是权限授予。

### 恢复决策卡

| 信号 | 第一个动作 | 仍不能声明 |
|---|---|---|
| 长时间等待或无输出 | 保存现场，安全中断，检查状态/diff/最后输出 | 命令成功或验证通过 |
| 中断后出现部分 diff | 保存 diff，检查范围漂移，从干净检查点重新评估 | 完整交付 |
| 缺文件、路径或权限 | 停止并列出缺少的输入或决定 | 猜测出的路径或扩大权限 |
| 验证失败 | 分类并缩小检查 | 实现一定错误，或必须完全访问 |
| 缺检查器/依赖 | 记录“验证工具不可用”并请求选择 | 没有运行的检查通过了 |
| 有成功样式摘要却无目标证据 | 运行最小的目标专用检查 | 任务目标已达成 |

## 证据至少需要三层

第一次任务至少需要三种证据：

1. **范围证据：** `status`、文件列表或 diff 显示只有允许对象改变，也不会把已有工作误算成这次改动。
2. **正确性证据：** 针对性测试、命令结果、来源比对或人工检查支持准确的验收声明。
3. **交付证据：** 一份短记录说明发生了什么、没有发生什么、仍不确定什么，以及下一步应做什么。

对外部动作，额外记录准确目标、授权事件、结果对象和回滚/恢复路径。对视觉结果，增加真实页面或截图检查。对易变产品事实，增加来源 URL、访问日期、范围、负责人和下次复核。文件存在、CI 变绿或 Agent 说“做完了”，都不能代替与声明相对应的证据。

## 实验：在沙盒中改一份 README

这个实验故意很小。它教授边界与证据习惯；不证明你的账户、生产仓库、连接器或外部服务安全。

### 准备

使用可丢弃或非生产 Git 项目。确认绝对路径，且丢弃本次改动可以接受。不要使用凭据、私钥、`.env` 文件、客户数据、生产文件、公共仓库或真实部署目标。保存原始 README 或干净检查点。任何运行命令只以项目自己的脚本/清单文件为来源。

### 任务

把下面这个有边界的请求交给 Codex，并将尖括号的值替换为沙盒事实：

```text
运行 ID：lab001-readme-<日期>-<后缀>
目标：在 <绝对路径>/README.md 添加一段准确的本地启动说明。
先读取：README.md、软件包/构建清单和现有脚本文件。
允许编辑：仅 README.md。
不要：安装、访问网络、改代码、提交、推送、发布、发送消息、读取秘密，或使用生产数据。
编辑前：报告基线、计划、命令来源和验收检查。
编辑后：展示精确 diff，只运行我已批准的针对性检查。
若路径、命令、权限或恢复步骤不清楚，停止并提问。
```

目的不是强制这段措辞，而是让目标、事实来源、禁止动作和停止条件在动作前可见。

### 证据

保存一份包含下列内容的记录：

```text
run_id:
checkpoint_before:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

通过的形态应是：只有批准的 README 改变；文档中的命令与项目真实脚本定义一致；针对性检查有真实输出或明确 `not run`；没有外部写入；交接不暗示未运行的完整应用已经运行。

### 失败与边界变体

只在可丢弃副本中运行这些变体，记录结果；不要悄悄“救回”实验：

- 在临时清单中改变脚本名，使 README 与事实来源冲突；
- 加入“不要修改代码”约束，并检查 diff；
- 让只读检查等待或返回不完整输出，中断后比较前后状态；
- 省略验收条件，比较另一个学习者需要做的返工；
- 让任务请求网络调用、安装、凭据或外部写入；正确结果是停止并进行窄范围澄清，不是寻找绕过办法。

### 反思

用自己的话回答：

- 哪个确认点避免的风险最多？
- diff 证明了哪项声明，哪项声明需要另一项检查？
- 如果命令停滞，中断后什么状态仍然未知？
- 下次重复任务前，你会如何改进协议？

## 验收清单

只有能够提交以下材料时，才继续：

- [ ] 一张含目标、上下文、输入、约束、允许动作、验收、失败处理和交付格式的任务协议；
- [ ] 编辑前观察和已保存基线；
- [ ] 标明比较范围的真实 diff；
- [ ] 针对性检查输出，或明确的 `not run` 记录；
- [ ] 一份能区分停止与成功的失败变体观察；
- [ ] 一份将计划、动作、证据和未验证范围分开的交接；
- [ ] 一段说明为何最小权限足够的反思。

不要因为文字写得漂亮就前进。只有当另一人无需猜测改了什么、执行了什么、还缺什么时，才继续。

## 迁移任务

把同一协议迁移到一个非工程任务：固定来源研究简报、静态营销文案改动、内容盘点或设计审查。保留目标、输入、约束、允许动作、验收、失败处理和交付字段；再加入该领域的引用、隐私、抽样、人工审查或视觉检查边界。

提交两份协议和一份短比较：

- 哪些字段保持稳定；
- 哪些字段依赖领域；
- 两项任务都禁止哪些副作用；
- 团队复用该方法前需要哪些证据。

## 来源与维护边界

任务协议、证据层和恢复顺序是本项目稳定的教学方法。产品具体权限、沙盒默认值、CLI 命令、审查工作面、模型名称和 UI 状态属于易变事实。相关事实变化时，重新检查[第 2 章官方基线](../../docs/research/chapter-02-official-baseline-2026-08-10.md)和[内容生命周期](../../docs/governance/content-lifecycle.md)。

[现场问题记录](../../docs/research/chapter-02-field-problems-2026-08-10.md)包含用户报告和社区建议，不是官方根因确认。本章保持 `candidate`，实验保持 `draft / not_run`，直到新的、有边界的运行产生所声明的证据。下一章仍在当前迁移路径中；中文译文尚不可用时，请在阅读器中接受明确的英文回退提示，而不要把回退显示成中文完成。
