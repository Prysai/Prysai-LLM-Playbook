# 第三章：把愿望变成任务协议

## 本章要解决的问题

“帮我把这个项目做得更好”“研究一下”“写个网站”“用最好的 skill”都是愿望，不是可执行任务。Agent 必须在大量细节中自行猜测时，结果就会受到它的假设影响，返工也很难定位。

本章把命令 AI 解释成设计一份轻量的任务协议。协议不是为了把每一步都替 Agent 写死，而是为了明确目标、输入、边界、证据和停止条件。

## 学习目标

读者完成本章后应当能够：

- 将一句愿望改写成目标、背景、输入、约束、行动、验收、失败处理和交付格式；
- 指出哪些缺失信息会改变范围或风险；
- 让协议保留 Agent 的判断空间，同时不允许它越过授权边界。

## 现实问题入口

FP-11 展示了“为了验证”也可能越过任务边界；FP-10 展示了没有清楚的命令边界时，失败很难定位。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)。

## 1. 八个组成部分

```text
目标 + 背景 + 输入 + 约束 + 允许行动 + 验收标准
     + 失败处理 + 交付格式
```

### 目标

描述想要的结果，而不是只描述动作。例如“让首次贡献者能启动项目”比“改 README”更有用。

### 背景

说明谁会使用、当前痛点、已有决策和为什么现在做。背景帮助 Agent 判断取舍，但不要塞入与任务无关的历史。

### 输入

列出文件、数据、链接、约束、版本和可使用的工具。输入不足时，写明允许 Agent 先检查什么。

### 约束

说明不修改什么、不连接什么、不公开什么，以及时间、格式、兼容性和品牌要求。

### 允许行动

区分只读检查、编辑、执行命令、提交、上传、发送消息和外部服务调用。越过当前范围的行动必须暂停。

### 验收标准

写出别人能够检查的条件：文件、测试、行为、视觉、来源、性能或人工批准。

### 失败处理

提前规定输入缺失、冲突、测试失败、权限不足或无法验证时应该停下来、询问还是回滚。

### 交付格式

要求最终说明完成项、未完成项、变更文件、验证证据、风险和下一步，而不是只说“完成了”。

## 2. 好协议不等于长提示词

协议的目标是减少关键歧义，不是把模型能做的每件事都规定一遍。一个简单任务可能只需要三行：目标、限制、验收。复杂任务才需要完整八项。

判断是否写够的标准是：另一个没有参与讨论的人，能否根据协议判断工作边界和完成证据。

## 3. 可直接复制的最小协议

先用下面的版本开始，再根据风险和依赖补字段。方括号中的内容必须替换；不能用“适当”“尽量”“做好”这类无法检查的词代替。

```text
目标：在 [目标文件/产物] 中实现 [可观察结果]，供 [使用者] 使用。
背景：当前 [问题/缺口]；已知决策是 [相关规则或事实]。
输入：允许读取 [文件、数据、来源、版本]；缺少 [输入] 时先停下来。
约束：只允许 [范围]；不得 [明确禁止的文件、秘密、外部系统或动作]。
行动：先做 [只读检查]，再提出计划；只有确认后才做 [编辑/运行]。
验收：必须满足 [条件 1]、[条件 2]；证据是 [diff/测试/来源/截图/人工检查]。
失败处理：遇到 [冲突、权限、长时间无输出、验证失败] 时 [停下/询问/恢复]，不得猜测或扩大权限。
交付：说明完成项、变更文件、实际验证、未验证项、风险和下一步。
```

可以把它压缩，但不能删掉与风险直接相关的字段。例如只改一个拼写错误时，背景和交付可以很短；涉及 GitHub 上传、生产服务、客户数据或外部消息时，必须明确目标、授权、回滚和结果检查。

## 4. 任务协议与 skill 的关系

任务协议描述“这一次要做什么”；skill 描述“这类任务通常应该如何做”。Skill 不应吞掉项目特定目标，也不应覆盖用户明确的约束。正确的关系是：

```text
用户任务协议：本次目标和边界
项目规则：长期上下文和不可违反的约束
Skill：可复用的方法、检查点和输出标准
工具：可以采取的具体行动
```

当它们冲突时，先暴露冲突，不要让 skill 静默覆盖用户目标或项目规则。

## 实验：三次改写

### Setup

在临时 Markdown 文件中准备同一个模糊愿望，禁止修改真实项目或调用外部服务。准备一张八项协议表，并将三次版本分别保存，避免后一次改写覆盖前一次。

### Task

把下面的愿望分别改成三个版本：

> 帮我把这个项目的首页做好。

版本一只补充目标；版本二补充输入和限制；版本三补充验收、失败处理和交付格式。每个版本单独保存，并为每轮记录 `run-id`。比较三次之后，Codex 是否更容易先提问、先计划、限制修改范围并给出证据。

### Evidence

保存三份协议、每份协议的缺失字段、Codex 的澄清问题或计划，以及最终比较表。比较表至少说明：哪些歧义被消除、哪些行动仍未授权、哪些验收证据仍缺失；不要用“看起来更专业”作为唯一证据。若某轮没有真实运行，只记录为“协议审查”，不要写成 Codex 已经执行。

推荐的比较表字段：

```text
版本 | 只新增的字段 | 新增约束 | 仍然缺失 | 允许动作 | 停止点 | 所需证据
```

### Reflection

指出一个“写得更多但没有增加约束”的字段，并说明何时应该删掉它。记录一个仍然需要用户决定的开放问题，以及下一次会先补哪项信息。

## 故意失败实验

写一份看似完整但不包含验收标准的协议，例如要求“完成后看起来高级、专业、现代”。让 Codex 执行后，找出至少三项无法客观判断的地方，再把它们改写成可检查条件。

## 本章验收

学习者能够：

- 将一个模糊愿望改写成八项任务协议；
- 区分本次目标、项目规则、skill 方法和工具行动；
- 为高风险行动写出暂停和确认点；
- 为“完成”提供至少两种外部可检查证据；
- 说明信息不足时 Agent 应该如何停止，而不是如何猜测。

本章的方法吸收了工程来源中对任务拆解、上下文工程和显式验收的实践，但正文与实验为 Field Guide 的原创重写。

## 迁移练习

把同一份八项协议分别用于一个研究问题和一个营销实验。标出哪些字段可以复用，哪些字段必须换成该领域自己的来源、隐私和验收条件。

## 来源与更新提示

任务协议是稳定方法；项目规则、工具权限和具体命令属于易变事实。产品事实以[官方 Codex 基线](../../docs/research/openai-codex-baseline.md)为准，现场案例以[问题研究记录](../../docs/research/field-problems-codex.md)的证据等级为准。
