# 第 9 章：验证、怀疑与恢复

**状态：** candidate。**实验状态：** not_run。本章教授如何让完成声明匹配证据，
以及工作流变得不确定时如何恢复。公开报告和示例都是教学输入，不是本地复现、
官方根因、客户工作或生产证据。

## 本章要解决的问题

Agent 可以为错误、超出范围、从未执行，或在错误环境检查的结果写出极具说服力的
完成摘要。可靠的响应不是盲信，也不是永远怀疑；而是把摘要拆成声明，并为每条声明
分配在其声明范围内足以支持它的最小证据。

![教学卡：在第一份缺失证明处停止，并用一项安全检查恢复](../../assets/teaching/evidence-recovery-ladder.svg)

> 这是项目自有教学卡。它解释审查方法；不证明某个 Skill、Agent、工具或外部服务
> 曾执行任何动作。

## 学习目标

完成本章后，你应该能够：

- 把完成摘要拆为独立声明，并为每条选择最小充分证据；
- 区分 error、unverified、unknown、partial、not_observed 和 verified；
- 找到能力链中最后确认的阶段与第一处无证据阶段；
- 当一次运行失败时保留状态、缩小范围、增加一项有用检查，或清晰停止；以及
- 写出不夸大的交付说明，列出已完成工作、剩余缺口和下一项安全检查。

## 现实入口：重新取得控制，不等于证明结果正确

项目的 [Codex 现场研究](../evidence-library-ZH.md#source-notes) 记录了容量中断、
命令持续停在 Working，以及验证扩大为持久重装的报告。后续
[跟进研究](../evidence-library-ZH.md#source-notes)还记录了会话可用
但目标工具未注册，以及长请求最终报错并重试的情形。

这些报告有用，是因为它们暴露了工作流可观察的断点；但它们不建立普遍服务原因、
所有账户的修复方式或本地复现。用它们练习一个关键区分：恢复一次运行的控制权，
不等于证明预期结果正确。

| 报告症状 | 报告支持什么 | 它不能证明什么 | 第一个安全响应 |
|---|---|---|---|
| 所选模型不可用，任务停止 | 有报告者看到了容量错误和中断任务 | 队列语义、服务端原因，或每个账户/版本行为 | 冻结后续提示；重试前检查 diff、日志和最后接受的检查点 |
| 格式化或验证持续 Working | 该次运行没有完成信号 | 普遍死锁、确切子进程或根因 | 设定有界等待，保存输出和进程状态，只按恢复规则中断 |
| 会话可用但预期工具缺失 | 会话与工具库存不符合任务预期 | 每个提供商/版本暴露相同工具集 | 记录实际工具清单；在文件、浏览器或外部服务动作前停止 |
| 验证变成强制重装 | “检查结果”可能被理解成许可改动持久环境 | 重装永远错误，或报告覆盖所有 Agent | 分开记录源码、测试、安装、重启、部署和线上验证 |

下一步应由证据和授权决定，而不是由等待时间或状态标签的自信程度决定。

## 三份 Windows 报告：信号不是证据

下列案例来自 2026-08-12 访问的公开 GitHub 报告。它们是教学输入，
不是本地复现、官方诊断或普遍 Windows 行为。

| 公开症状 | 它可教什么 | 第一个有界检查 | 停在何处之前 |
|---|---|---|---|
| CLI 输出超出终端视口后无法从滚动缓冲区找回（[#35335](https://github.com/openai/codex/issues/35335)） | 视口是呈现，不是持久证据 | 将响应保存或重新生成到具名文件；记录 CLI、终端和提示范围 | 把缺失视口断言为 Agent 或仓库数据丢失 |
| 非 BMP 字符粘贴到 TUI 编辑框后消失（[#37578](https://github.com/openai/codex/issues/37578)） | 编辑框回显不等于输入完整性 | 在发送有后果的请求前，用无害夹具比较预期与实际接收字符串 | 编辑、提交或发送未被保留的输入 |
| 很长的检查点引用让 Windows Git 报 bad ref 或 Filename too long（[#37559](https://github.com/openai/codex/issues/37559)） | 内部 Agent 状态不等于普通项目状态 | 在获批诊断范围内记录 git status、git show-ref、git fsck --full、git worktree list 与精确 ref 路径 | 未备份、未授权就删除 .git 材料、改 Git 配置、抓取或修复引用 |

详见[Windows 输入与证据现场问题](../evidence-library-ZH.md#source-notes)。
实用规则是：**重试前先捕获最小持久产物**——输出文件、收到输入的比较、diff、哈希、
命令日志或脱敏交接。社区变通方法可以帮助分诊，却不是官方修复，也不授权持久环境改动。

### 现场案例：命令完成，声明仍可能不可审查

有界案例 [FC-EVIDENCE-01](../evidence-library-ZH.md#source-notes)
使用 issue #34951 区分执行与审计证据。该 issue 仍公开、没有维护者诊断，也未在此复现。
若必需输出隐藏或缺失，只保留已经授权的退出码、事件、diff、产物、哈希或回读证据；
把审计声明标为 unverified，并写明缺失通道。不要只为找回呈现输出而重跑有后果动作、
削弱安全控制，或把成功形状的状态推断为真实结果。

## 1. 让声明匹配证据

先写出你想说的那一句话，再问：第二个人要检查什么，才能在已声明的范围内接受它？

| 声明 | 支撑该范围的最低证据 | 仍在声明之外的内容 |
|---|---|---|
| 文件改了 | diff、具名路径或哈希 | 改动正确或完整 |
| 检查通过 | 精确命令、工作目录、退出码和相关输出 | 另一环境也会同样行为 |
| 应用运行 | 实际启动和一次具名关键路径观察 | 视觉质量、安全、用户价值或生产就绪 |
| 页面看起来正确 | 指定视口的浏览器或截图审查 | 无障碍、所有断点、后端行为或转化 |
| 事实来自官方来源 | 权威 URL、访问日期、范围和复核负责人 | 当前账户或运行时有同样能力 |
| 没有暴露秘密 | 限定改动扫描、环境检查与边界说明 | 未知外部系统从未收到秘密 |
| 结果帮助用户 | 已定义样本、任务和用户验收记录 | 普遍市场成功或未来结果 |
| 结果可用于生产 | 质量、安全、维护、发布和回滚门禁 | 未测试环境或无人负责的未来改动 |

### 在 Lab 013 之前：写声明—证据表

在进入 [Lab 013：可审计的竖向切片](../labs/lab-013-l3-vertical-slice-ZH.md) 前，
将“完成”拆成可检查的行。每行只可由其声明范围内的证据支撑：

~~~text
assertion: 我到底在声明什么？
scope: 该声明覆盖的文件、命令、运行、版本或环境
evidence: 路径、命令输出、日志、截图、来源或审查记录
status: verified / partial / unverified / blocked / not_run
gap_or_next_check: 缺什么，以及增加证据的最小方式
~~~

不要用一次 diff 证明测试通过，也不要用登录页面证明令牌交换或外部动作成功。证据缺失时，
按情况标为 unverified、blocked 或 not_run，保留缺口并进入恢复流程。

## 2. 用怀疑来选择下一项检查

对一个重要决策，写出一条短声明，然后暂时把它从自己的推理中拿掉：

- 哪个前提没有证据？
- 哪个边界条件没有覆盖？
- 结果会不会来自 mock、缓存、过期文件或错误环境？
- 若声明为假，最先会在哪里可见？
- 哪一项最小额外检查可能改变决策？

目标不是无穷怀疑，而是在交付前让昂贵错误变得便宜可见。一项好检查只改变一个相关
条件，产生可观察结果，并带有停止规则。

### 状态标签不是出口检查

| 声明 | 最低证据 |
|---|---|
| “源码改了。” | 指定路径的 diff 或文件比较 |
| “检查跑过了。” | 精确命令、工作目录、退出码和输出 |
| “应用能用。” | 指定环境和输入下的运行时观察 |
| “页面看起来正确。” | 指定视口的渲染检查与视觉标准 |
| “功能已交付。” | 仓库或部署状态、发布记录和交付后检查 |

最后一句严格强于前四句。构建通过有价值，但不会自动成为运行时、视觉、安全或用户验收
证据。

## 3. 按有界顺序恢复

当事情失败或变得不清楚时，按此顺序：

1. 保留精确错误和当前状态；
2. 分类可能边界：输入、理解、环境、实现、能力、权限或验证；
3. 缩小范围并复现最小可观察断点；
4. 做一次最小修复，或增加一项定向检查；
5. 重跑受影响路径并记录新证据；
6. 失败仍不清楚时，停止并交付精确阻塞说明；
7. 只有证据支持时，才扩大权限、范围或重试预算。

不要用“再跑一次”“多给权限”或“让模型更努力想”替代诊断。

### 能力链：每一层成功都需要自己的证明

公开报告反复出现一个误导顺序：工具名出现在列表、网页可读、提供商接受配置，
而真实发现调用、点击或更高层能力依然失败。可见工具名只证明名字可见；不证明注册、
可发现、执行或副作用成功。

~~~text
工具或 Skill 可见
  → 一次只读发现调用可运行
  → 可读取目标状态
  → 目标动作返回成功
  → 确认预期外部状态变化
~~~

每步需要独立证据。读 DOM 不证明点击成功；解析配置不证明后端能力可用；一次成功启动
不证明下一个窗口、版本或账户有同样能力。诚实交接可以写“只读检查已验证；提交未验证”，
这比“工具能用”更有价值。

### 断点卡：在第一层无证据处停止

不要先猜根因。找最后通过的断言，和第一条失败或未观察到的断言。为单次运行保存：

~~~yaml
run_id: "唯一运行标识"
surface: "实际工作面及版本"
expected_capability: "本次运行所需的最小能力"
chain:
  - stage: "入口/会话可用"
    observation: "可观察事件或错误"
    status: "passed | failed | not_observed"
  - stage: "工具已注册且可发现"
    observation: "工具列表或只读发现结果"
    status: "passed | failed | not_observed"
  - stage: "目标状态可读取"
    observation: "只读目标、账户、路径或窗口证据"
    status: "passed | failed | not_observed"
  - stage: "目标动作返回"
    observation: "结果、退出码或错误类别"
    status: "passed | failed | not_observed"
  - stage: "预期副作用已确认"
    observation: "目标状态、diff 或回读结果"
    status: "passed | failed | not_observed"
last_confirmed_stage: "最后通过阶段"
first_breakpoint: "第一处 failed 或 not_observed 阶段"
safe_next_check: "只改变一个条件的最小检查"
stop_condition: "何时不扩大权限或副作用而停止"
~~~

工具名可见而只读发现失败，断点就是“工具已注册且可发现”；动作返回成功而目标状态不变，
断点就是“预期副作用已确认”。不要越过断点做更高风险动作，也不要用后来的幸运成功
倒填早期证据。

### 长等待却没有事件：先记录时间线

“界面仍显示 Working”是一项观察，不是根因。长请求至少记录：

~~~text
request_started_at
first_event_at
each tool or network event
last_event_at
interrupt or error time
automatic retry start time
final state
~~~

到达预先同意的无事件阈值时：

1. 标为 no_event_observed；不要改写成根因或健康任务；
2. 用已授权方式恢复控制，再检查进程、工作树、目标状态和最后检查点；
3. 第一次请求可能已有副作用时，按 unverified 或 blocked 停止；
4. 只有动作幂等、状态已复查，且重试规则在运行前声明或某条件已明确改变时，
   才允许一次有限重试；
5. 将客户端自动重试记录为独立事件。第二次成功只证明第二次，不能把第一次无事件
   改写为初次通过。

HTTP 状态、长上下文、网络等待、模型推理或上游服务故障可以是待测假设；没有官方确认
或本地复现时，它们不是已建立根因。

## 4. 把恢复状态与完成状态分开

使用描述真实证据的状态词：

- practice：学习运行；不得复用为生产证据；
- candidate：结构或输出有希望，但评估或来源审查未完成；
- verified：在声明范围、版本和任务集内有证据；
- production-ready：质量、安全、回滚、维护和发布门禁均通过。

观察状态不同于完成状态。not_observed 表示没有看到预期事件，不是根因诊断；not_run
表示计划实验尚未执行，不是通过或失败；partial、unverified 与 blocked 描述当前能支持
的最窄证据缺口。

恢复可以取得控制，却不升级完成状态。例如，中断一个挂起进程并保存 diff，可能形成有用
的 candidate 交接，而所请求的运行时结果仍是 unverified。

### Codex 现场差异：可见工作面，没有可用能力

公开报告描述了可见的 Computer Use 和 node_repl 工作面，其只读 list_apps() 或
list_windows() 调用会出现 spawn EPERM；浏览器弹窗与 DOM 可读，但点击超时；以及
自定义提供商可接受配置，却未必暴露预期的多 Agent 能力。这些是 2026-08-10 用户报告，
不是本地复现或官方根因。参见[网页现场研究](../evidence-library-ZH.md#source-notes)

## 实验：审计一条完成声明

**实验状态：** not_run。

### 准备

准备脱敏完成摘要、diff、测试输出、来源链接和一项刻意缺失的证据。不要连接生产服务
或改动外部系统。把每句完成声明拆为独立主张，并在审查前决定允许的状态词。

### 任务

使用 [Lab 003](../labs/lab-003-evidence-review-ZH.md) 把摘要变成声明表。为每一行写范围、
证据、状态与下一步；随后刻意加入“全部测试通过”一类无证据句子，观察审查是否拒绝它，
而不是接受摘要的语气。

### 证据与复盘

保存声明表、每项声明的证据路径、缺口类别、审查决定和恢复或补充计划。至少包括一条
事实声明、一条运行时声明和一条用户效果声明，说明为什么一份弱证据不能代替三者。
记录最容易藏在漂亮摘要里的声明、最小却最能降低风险的检查，以及为什么 unverified
不等于 wrong；再把下次交付说明的一句话改写成与证据相称的状态。

## 刻意失败与边界案例

在可丢弃副本中开始一项小而可逆的改动。跑检查前写一份称“完成”且“全部测试通过”的
交接；然后揭示测试输出从未产生，或拟议恢复需要安装、重启、网络调用，或写入原范围外。

只有学习者做到以下各项，练习才通过：

- 把无证据声明标为 unverified 或 not_run；
- 保留部分 diff、错误、范围和最后检查点；
- 拒绝从 diff 推断运行时或用户验收；以及
- 选择一项安全检查或清晰停止，而不是堆叠编辑或静默扩大权限。

## 迁移练习

将声明表用于研究结论或营销实验报告。至少写一条事实声明、一条执行声明和一条用户效果
声明；解释为什么三者不能共享一份弱证据，并为最缺支持的声明命名最小后续检查。

[官方基线](../evidence-library-ZH.md#source-notes)和
