# 11장: 쓸모 있는 Skill 설계하기

**상태:** `candidate`. **실험:** `not_run`. 이 장에서는 설계 방법을 설명합니다. 특정 호스트가 Skill을 발견하고, 불러오고, 실행했다는 증거를 제공하는 것은 아닙니다.

## 이 장에서 해결하는 문제

한 번 잘 된 세션만으로 프롬프트를 Skill로 만들면 위험합니다. 기록하지 않은 사실에 의존하거나, 필요하지 않은 권한을 요구하거나, 자격 증명이 있다고 가정하거나, 유행어가 들어갔다는 이유만으로 실행될 수 있기 때문입니다. 쓸모 있는 Skill은 반복되는 작업 유형을 범위가 정해진 행동과 확인 가능한 증거에 연결하는 버전 관리형 방법 패키지입니다.

> Skill은 범위가 정해진 작업 유형을 제한된 행동과 확인 가능한 증거에 연결하는, 발견 가능하고 재사용할 수 있는 방법 패키지입니다.

Skill은 모델, 도구, 권한, 커넥터, 사람의 승인을 대신하지 않습니다.

## 학습 목표

반복 작업에 정말 Skill이 필요한지 판단하고, 시작 조건(trigger)과 대상 제외 조건(non-trigger)이 있는 계약(contract)을 작성할 수 있습니다. 또한 방법(method), 데이터(data), 실행(execution)을 나누고, 성공·경계·실패·전이 사례로 후보(candidate)를 검토할 수 있습니다. `SKILL.md`가 존재하거나 한 번 실행되었다는 사실만으로 모든 호스트, 모델, 사용자에서 신뢰성(reliability)이 입증되는 것은 아닙니다.

## 실제 문제: Skill은 실행되기 전에 실패할 수 있습니다

### 탐색(discovery)은 따로 확인해야 하는 단계입니다

Skill을 디렉터리에 넣었다는 것은 그 위치에 파일이 있다는 사실만 뜻합니다. 파일의 존재, 현재 작업 화면(surface)에서 보이는지, 작업(task)에서 선택되었는지, 입구 파일이 불러와졌는지, 단계가 실행되었는지, 결과물(artifact)이 수용 조건을 통과했는지는 각각 기록해야 합니다. 어느 단계든 관찰하지 못했다면 인계(handoff)에 “연결됨”이라고 뭉뚱그리지 말고 `unknown`으로 남기세요.

### “연결됨”과 “호출 가능함”은 다릅니다

커넥터, 플러그인, 워크스페이스 설정이 화면에 보인다고 해서 현재 작업에 파일, 네트워크, 계정, 게시 권한이 자동으로 생기지는 않습니다. 처음 도입(adoption)할 때는 민감하지 않은 성공 사례로 실행 환경(host), 버전, 경로, 입력, 실제 선택, 출력을 기록하고, 관찰하지 못한 단계는 채택 기록(receipt)에 적습니다. 설정 화면은 실행 시점의 증거(runtime evidence)를 대신할 수 없습니다.

### 시작 조건(trigger)과 대상 제외 조건(non-trigger)을 먼저 나누기

시작 조건에는 작업 의도, 필요한 입력의 완비, 방법의 담당 범위, 감당할 수 있는 위험이 모두 필요합니다. 키워드가 일치하는 것만으로는 충분하지 않습니다. 가까운 작업을 다른 방법에 넘기는 `non_trigger`도 사용자의 주의와 권한을 지키는 제품 설계의 일부입니다. 어떤 방법도 문안 전체 수정, 원격 확인, 대량 수리, 권한의 출처가 불분명한 작업을 조용히 맡아서는 안 됩니다.

### 입력(input)·권한(permission)·비밀(secret)의 경계

입력은 제공됨(provided), 읽을 수 있음(readable), 추정함(inferred), 알 수 없음(unknown)으로 나눕니다. 경로, 버전, 출처, 기준선, 수용 규칙, 복구 위치가 없으면 모델이 임의로 채워 넣어서는 안 됩니다. 읽기, 임시 쓰기, 영구 쓰기, 네트워크, 설치, 전송, 게시, 삭제도 각각 별도의 권한입니다. 비밀은 `SKILL.md`, 예제, 로그, 스크린샷, 채택 기록(receipt)에 넣지 말고, 필요할 때도 지정된 통제된 입구에서만 다룹니다.

### 리소스(resource)를 늘리기 전에 판단하기

`scripts/`는 결과를 재현할 수 있고 검사 가능한 반복 작업에만 씁니다. `references/`에는 특정 분기에서만 필요한 상세를 둡니다. `assets/`는 용도와 라이선스가 명시된 정적 리소스로 제한합니다. 모든 리소스에 입력, 출력, 실패 방식, 부작용을 적습니다. 처음 실행할 때는 임시 디렉터리나 민감하지 않은 샘플을 사용하고 버전과 원시 출력을 남기세요. 스크립트가 있다는 사실만으로 안전성, 정확성, 실행 완료가 증명되는 것은 아닙니다.

## 설명문보다 먼저 계약 쓰기

```yaml
skill_id: evidence-boundary-review
version: "0.1.0"
owner: named-person-or-team
review_date: "YYYY-MM-DD"
purpose: "제공한 산출물을 지정한 증거 경계로 검토한다."
trigger:
  - "증거 경계 검토를 요청한다."
  - "산출물, 목표, 수용 조건이 제공됐다."
non_trigger:
  - "제한 없는 다시 쓰기를 요청한다."
  - "중요한 주장에 출처가 없다."
  - "다른 이름 붙은 방법이 작업을 맡는다."
required_inputs:
  - 대상 경로 또는 붙여 넣은 산출물
  - 목표, 제외 사항, 수용 조건
  - 중요한 주장의 출처
allowed_actions: "대상 읽기; 폐기 가능한 출력 디렉터리에 보고서 쓰기; 이름을 지정한 되돌릴 수 있는 로컬 검사 실행"
forbidden_actions: "비밀 읽기/출력, 게시, 전송, 삭제, 설치, 무단 네트워크"
output: "주장 → 증거 → 검토하지 못한 범위 보고서"
stop_when: "입력, 권한, 출처, 복구 대상이 없다"
```

시작 조건에는 작업 의도, 필요한 입력, 방법의 담당 범위, 허용 가능한 위험이 있어야 합니다. 키워드가 일치하는 것만으로는 부족합니다. 대상 제외 조건은 가까운 작업을 가로채지 않게 합니다.

## 방법·데이터·실행을 나누기

- `SKILL.md`에는 항상 필요한 목적, 경계, 절차, 중단 규칙, 증거를 둡니다.
- `references/`에는 특정 갈래에서만 읽을 자료를 둡니다.
- `scripts/`에는 의존성, 네트워크, 쓰기 범위, 종료 동작을 선언한 결정적 검사만 둡니다.
- `assets/`에는 선언한 정적 자원만 둡니다.

중요한 안전 규칙을 선택적인 참고 자료에 숨기지 않습니다. 파일이 있다는 사실은 탐색을, 탐색은 로드를, 로드는 채택을, 채택은 동작을 증명하지 않습니다.

### 권한을 한 줄로 뭉뚱그리지 않습니다

`파일을 다룬다`는 충분한 권한 설명이 아닙니다. 계약에는 실제로 필요한 행동만 각각 적습니다.

| 행동 | 별도 승인 또는 기록이 필요한 이유 | 이 장의 링크 점검 예 |
|---|---|---|
| 읽기 | 대상과 범위를 확인해야 한다 | 지정한 Markdown 파일만 읽기 |
| 임시 쓰기 | 결과가 버릴 수 있는 위치에만 남아야 한다 | 임시 사본 안에 보고서 쓰기 |
| 기존 파일 쓰기 | 사용자의 원본과 기존 변경을 덮을 수 있다 | 허용하지 않음 |
| 네트워크 / 설치 | 데이터 유출, 비용, 의존성, 실행 범위가 달라진다 | 허용하지 않음 |
| 전송 / 게시 / 삭제 | 되돌리기 어려운 외부 또는 파괴적 효과가 있다 | 허용하지 않음 |

비밀, 개인 기록, 쿠키, 토큰, `.env` 파일이 보이면 내용을 예제나 로그로 옮기지 말고 멈춥니다. 경로가 맞는지, 누가 변경을 소유하는지, 복구할 기준선이 있는지도 쓰기 전에 확인합니다.

### resource의 역할과 로드 조건

| 위치 | 두는 내용 | 언제 읽거나 실행하는가 | 두면 안 되는 것 |
|---|---|---|---|
| `SKILL.md` | 목적, trigger, 금지 행동, 중단, 핵심 증거 | 매 실행 | 선택 자료에 숨긴 안전 규칙 |
| `references/` | 특정 형식이나 갈래의 해석 기준 | 그 갈래가 실제로 선택됐을 때 | 모든 실행에 강제하는 장문 설명 |
| `scripts/` | 결정적 검사와 명시된 입출력 | 계약과 경로가 맞을 때 | 권한을 넓히거나 결과를 대신 판단하는 자동화 |
| `assets/` | 출처와 라이선스가 기록된 정적 자원 | 산출물에 꼭 필요할 때 | 출처·용도·라이선스가 불명확한 자료 |

이 분리는 짧아 보이기 위한 장식이 아닙니다. 다음 독자가 무엇을 반드시 읽어야 하고, 무엇이 특정 갈래에서만 필요한지, 어떤 파일이 실행 효과를 낼 수 있는지 판단하게 합니다.

## 네 가지 사례로 평가하기

| 사례 | 일어나야 할 일 | 일어나면 안 될 일 |
|---|---|---|
| 긍정 | 방법이 실행되고 검토 가능한 산출물을 남긴다 | 증거 없는 성공 선언 |
| 경계 | 올바른 방법에 넘기거나 구체적으로 질문한다 | 비슷한 이름만으로 실행 |
| 실패 | 위험한 쓰기 전에 멈추고 첫 누락 지점을 남긴다 | 입력, 권한, 결과를 지어냄 |
| 전이 | 도메인 사실을 바꾸고 가정을 다시 검사한다 | 명사만 기계적으로 바꿈 |

변수 하나만 바꾸고 결과물에서 확인할 수 있는 신호를 남기는 의도적 실패를 넣습니다. 복구(rollback)에는 대상, 기준선, 단계, 복구 후 다시 읽어 확인하는 검사가 필요합니다. “되돌리기”라고만 쓰는 것은 충분하지 않습니다.

## 실험과 경계

### 준비

적어도 두 번 수행한 로컬의 비민감 작업을 고릅니다. 폐기 가능한 입력, 명확한 수용 조건, 읽기 전용 경계를 정합니다. 자격 증명, 설치, 네트워크, 라이선스가 불분명한 다른 사람의 Skill 내용은 사용하지 않습니다.

### 작업

Markdown 링크 검토, 조사 보고서 출처 확인, 릴리스 인계처럼 두 번 이상 한 저위험 방법을 고릅니다. 계약, 긍정 사례, 실행하면 안 되는 근접 사례, 빠진 입력, 보이는 실패, rollback 검사를 만들고, 산출물이 무엇을 증명하고 무엇이 unknown인지 표로 남깁니다.

선언한 환경에서 이 사례들을 기록하고 독립 검토를 받기 전까지 Skill은 `candidate`입니다. 발견, 로드, 실행, 사업 효과를 주장하지 않습니다.

### 증거

contract, version, 비민감 input, expected와 actual output, stop point, 로드한 resource, host/surface의 정확한 observation을 보존합니다. 관찰하지 않은 layer는 `not_observed`로 적고 directory만으로 execution record를 만들지 않습니다.

## 관찰 가능한 설계 흐름

여기서는 위험이 낮은 “Markdown 로컬 링크 점검”을 예로 듭니다. 네트워크, 계정, 실제 사용자 데이터가 필요하지 않습니다. 그렇다고 특정 host가 이 Skill을 자동으로 발견한다는 증거는 아닙니다.

### 작업을 확인 가능한 범위로 줄이기

“문서 품질을 검토해 주세요”는 경계가 없습니다. 방법을 쓰기 전에 이번 작업의 계약을 적습니다.

```text
목표: docs/quickstart.md 안의 깨진 상대 Markdown 링크를 찾는다.
허용: 그 파일 읽기; 임시 보고서에 후보 기록; 읽기 전용 로컬 검사 실행.
금지: 본문 수정, 네트워크, 의존성 설치, 삭제, 게시.
수용: 보고서가 링크 텍스트, 대상, 검사 결과, unknown 사유를 각각 보여 준다.
중단: 파일이 없거나 해석 기준이 불명확하거나 허가되지 않은 행동이 필요하다.
```

이 계약은 이번 작업에만 속합니다. Skill은 반복해서 쓸 방법만 보관합니다. 둘을 섞으면 다음 작업에 오래된 경로, 권한, 결론이 따라옵니다.

### trigger와 양보 규칙 설계하기

trigger는 홍보 문구가 아닙니다. 이 방법이 이 작업을 맡아도 되는지 판단할 수 있어야 합니다.

| 항목 | 링크 점검 Skill의 예 |
|---|---|
| 적용 | 이름이 지정된 Markdown 파일의 로컬 링크를 목표와 수용 조건과 함께 점검해 달라는 요청 |
| 비적용 | 다시 쓰기, 원격 사이트 점검, 저장소 전체 수리, 대상 파일이 없는 요청 |
| 먼저 묻기 | 링크 기준은 현재 파일, 저장소 루트, 사이트 출력 중 어느 것인가? |
| 중단 | 명시 승인 없이 네트워크, 자격 증명, 보호된 쓰기, 게시 변경이 필요함 |

“링크”와 “점검”이라는 단어만으로는 부족합니다. 의도, 입력, 방법의 소유권, 허용 위험을 함께 봐야 합니다.

### 행동과 증거를 짝지어 두기

| 단계 | 허용 행동 | 남겨야 할 증거 | 아직 증명하지 않는 것 |
|---|---|---|---|
| 입력 점검 | 파일과 계약 읽기 | 경로, 기준 버전, 빠진 입력 | 링크가 실제로 깨졌다는 것 |
| 후보 추출 | 상대 링크 추출 | 후보 표와 해석 규칙 | 대상 파일의 존재 |
| 검사 | 읽기 전용으로 경로 해석 | 존재/없음/unknown 결과 | 원격 URL의 접근 가능성 |
| 전달 | 버릴 수 있는 보고서 쓰기 | 보고서, 명령, 종료 상태 | 문제가 수정되었다는 것 |
| 검토 | 위험하거나 unknown인 항목 읽기 | 결정과 미포함 범위 | 모든 저장소에서 통한다는 것 |

종료 상태가 0이라는 것은 검사가 자신의 정의에 따라 끝났다는 뜻일 뿐입니다. 무시한 형식, 빌드 시 재작성, 원격 대상까지 옳다는 뜻은 아닙니다.

## 최소는 중요한 판단을 빼는 것이 아니다

입구의 `SKILL.md`는 짧을 수 있지만, 매번 필요한 경계는 남겨야 합니다.

```markdown
---
name: local-link-review
description: 목표, 수용 조건, 읽기 전용 범위가 주어진 이름 있는 Markdown
파일의 로컬 링크를 검토한다. 다시 쓰기, 네트워크, 대량 수리에는 쓰지 않는다.
---

1. 대상, 링크 기준, 허용 범위, 수용 조건을 확인한다.
2. 하나라도 없으면 멈추고 질문한다.
3. 로컬 상대 링크만 추출하고 원문은 보존한다.
4. 선언된 읽기 전용 검사를 실행하고 버전과 종료 상태를 기록한다.
5. 후보, 확인됨, unknown 결과를 분리한다.
6. 새 승인 없이 수정, 게시, 설치, 네트워크를 하지 않는다.
```

세부 해석 규칙은 `references/`, 결정적인 검사기는 `scripts/`에 둘 수 있습니다. 그러나 “대상이 없으면 중단”, “네트워크와 쓰기를 하지 않음”은 선택 파일에 숨기면 안 됩니다.

## 의도적 실패로 중단을 시험하기

임시 샘플을 만들고 한 가지만 바꿉니다. 링크가 존재하지 않는 경로를 가리키게 합니다. 기대하는 것은 막연한 영리함이 아니라 눈에 보이는 신호입니다.

```text
BROKEN: [설치 안내] (guides/install.md)
resolved: docs/guides/install.md
check: path does not exist
scope: local relative path only; remote availability not checked
```

그다음 `https://` 링크가 있는 경계 사례를 실행합니다. 네트워크에 나가지 않고 범위 밖 또는 unknown으로 남겨야 합니다. 링크 기준이 빠진 경우에도 구조를 추측하지 말고 질문하거나 멈추는 것이 맞습니다.

## 멈추고, 보존하고, 되돌리기

재시도는 중단 규칙이 아닙니다. 무엇이 안전한 상태인지와 무엇을 바꿨는지가 없기 때문입니다. 다음 신호에서는 다음 행동 전에 멈춥니다.

| 신호 | 필요한 응답 |
|---|---|
| 필수 입력 또는 링크 기준이 없음 | 하나의 구체적 질문을 하거나 `blocked`로 기록 |
| 두 출처가 중요한 주장에 대해 충돌 | 양쪽을 보존하고 결정 권한자를 찾은 뒤 중단 |
| 대상 경로 또는 worktree가 불명확 | 현재 경로와 변경 상태를 읽고 수정하지 않음 |
| 비밀 또는 개인 데이터가 나타남 | 기록을 최소화·가림 처리하고 복사하지 않음 |
| 계획에 없던 네트워크, 설치, 게시, 삭제가 필요함 | 새 범위와 명시 승인을 기다림 |
| 같은 실패가 첫 재시도 뒤에도 반복됨 | 출력과 checkpoint를 보존하고 정한 재시도 한도에서 인계 |

재시도나 rollback 전에 `run_id`, host와 버전, repository root, 기준 revision, 대상 경로, 마지막 성공 checkpoint, 변경 파일, 명령과 종료 상태, 외부 행동, 첫 실패 지점, 다음 안전 검사를 남깁니다. 대화 요약은 현재 diff와 대상을 다시 읽는 일을 대신하지 않습니다.

되돌리기는 소유권에 맞춰야 합니다. 임시 산출물은 기록한 baseline으로 복구하고 읽어 확인합니다. 기존 사용자 파일이나 관련 없는 변경은 임의로 되돌리지 않습니다. 설치한 의존성은 이름 있는 backup 또는 고정 버전에서만 복구합니다. 이메일·업로드·배포 같은 외부 행동은 local Git 명령으로 되돌렸다고 증명되지 않으므로 서비스의 복구 절차나 소유자 확인이 필요합니다. rollback 명령의 성공이 아니라, 중요한 상태를 다시 읽어 baseline과 비교한 결과가 성공 증거입니다.

## 작은 실험과 경계

1. 안전하게 읽을 수 있는 Markdown 파일을 고른다. 비밀이나 사적인 자료를 모델에 주지 않는다.
2. 목표, 범위, 수용 조건을 작업 계약에 채운다.
3. 읽기 전용 검사를 한 번 실행하고 환경, 날짜, 입력, 원시 출력을 남긴다.
4. 임시로 깨진 링크를 넣어 다시 실행하고, 수리 행동이 아니라 실패 신호가 남는지 확인한다.
5. 샘플을 버리거나 줄을 되돌린 뒤 원본 파일과 보고서를 다시 읽어 승인되지 않은 변경이 없는지 확인한다.
6. 다른 독자에게 계약과 보고서만 보여 주고 결과, 범위, unknown을 설명할 수 있는지 묻는다.

이 관찰은 기록한 환경에만 적용됩니다. 다른 host, 버전, 모델에서도 같은 발견, 선택, 로드, 실행이 일어난다는 증거는 아닙니다.

### 실험이 증명하는 것과 증명하지 않는 것

이 작은 실험은 임시 사본에서 필요한 경계가 보이는지, 하나를 제거했을 때 검토자가 실패를 식별하는지만 보일 수 있습니다. 다음은 증명하지 않습니다.

- host가 Skill을 자동으로 발견·로드·호출한다는 것;
- 모든 화면 크기나 모든 링크 해석에서 결과가 같다는 것;
- 사용자가 경계 설명을 이해했다는 것;
- 실제 업무 효과, 전환, 안전성 또는 다른 모델에서의 신뢰성.

실제 검토에는 정확한 Skill 경로와 revision, 민감 정보를 제거한 input 또는 hash, host와 권한 문맥, proposal과 tool trace, 결과물, 의도적 실패 diff, rollback 뒤의 read-back을 보관합니다. 각 항목을 `observed`, `inferred`, `unverified`, `not_run` 중 하나로 구분합니다.

## 자주 하는 실수

- description을 보증으로 쓰기: “게시 안전을 자동 보장”은 경계와 수용 조건이 없다.
- script와 Skill을 혼동하기: script는 정해진 검사를 하고, Skill은 언제 쓰고 언제 멈추며 결과를 어떻게 해석할지 정한다.
- 발견을 신뢰성과 혼동하기: 메타데이터, 선택, 로드, 행동, 증거를 따로 확인한다.
- unknown을 숨기기: “원격 링크는 확인하지 않음”도 보고서의 중요한 결과다.

## 채택 기록: 파일이 있다고 의존할 수 있는 것은 아닙니다

Skill을 실제 작업에 넘기기 전에 채택 기록을 남깁니다. “폴더에 보인다”와 “믿고 써도 된다”를
혼동하지 않게 하고, 다음 검토자가 어느 단계부터 확인할지 보여 줍니다.

```text
Skill 이름과 버전:
작업 공백: “AI를 더 똑똑하게”가 아니라 보완할 구체적인 판단
출처와 라이선스: 원본 / 검토한 출처, 라이선스와 검토 날짜
이번 host와 surface: 실제로 쓴 제품, 버전, 경로
관찰됨: 파일 / 발견 / 선택 / 로드 / 행동 / 출력
미관찰: 실행, 되읽기, 독립 검토가 없는 모든 단계
허용 범위: 읽기, 임시 쓰기, 네트워크, 설치, 공개를 각각 기록
다음 안전 검사: 미관찰 단계 하나만 확인
중단: 입력, 권한, 복구 대상, 증거가 없을 때
```

저장소에 `SKILL.md`가 있다는 것은 파일 존재만 뒷받침합니다. host가 발견했거나 방법이 실행됐다는
뜻은 아닙니다. 보고서가 한 번 나와도 기록한 작업과 환경에 대한 관찰일 뿐, 모든 모델, 폴더,
사용자에게 같은 결과가 난다는 증거는 아닙니다.

## 외부 방법은 출처를 검토한 뒤 채택합니다

외부 Skill의 지침, script, example은 검토할 material로 취급합니다. 저장소가 인기 있거나 설명이
매끄럽거나 이름이 비슷하다는 이유만으로 과정에 복사하거나 실제 데이터로 실행하지 않습니다.
최소한 다음을 확인합니다.

1. 원본 링크, 구체 revision, 유지 담당자, 검토 날짜;
2. 상위 license가 필요한 code, script, asset, nested dependency를 포괄하는지;
3. 무엇을 읽고, 쓰고, 설치하고, 연결하고, 전송할 수 있는지;
4. 더 작은 자체 방법 대신 그 작업 공백에 정말 필요한지; 그리고
5. 민감하지 않은 임시 fixture에서 무엇을 검사했고 무엇은 아직 실행하지 않았는지.

답할 수 없는 항목이 있으면 링크와 조사 기록만 남깁니다. 본 프로젝트의 Skill로 복사하거나
채택된 능력이라고 표시하지 않습니다.

## 따라 하기: 반복 가능한 검사를 Skill로 만들기

적어도 두 번 해 본 작은 작업을 고릅니다. Markdown 파일의 로컬 링크 검토, 보고서에 출처와
날짜가 있는지 확인, diff와 테스트 명령을 포함한 인계 준비가 예입니다. “더 좋게 만들기”는
고르지 않습니다. 다른 사람이 같은 결정을 반복할 수 없기 때문입니다.

먼저 Skill 없이 한 번 작업하고 목표, 입력 파일, 허용 행동, 결과, 증거, 중단 지점만 남깁니다.
다른 작업에서도 필요한 판단에 밑줄을 긋습니다. 파일명이나 보기 좋은 응답이 아니라 그 판단이
Skill 후보입니다.

```text
사용 시점: 지정된 Markdown 파일의 로컬 링크 검토를 요청했을 때
사용하지 않음: 문장 다듬기, 웹 링크, 게시, 대량 수정
필수 입력: 파일, 링크 기준, 읽기 전용 범위, 수용 조건
반환: 확인됨, 후보, 알 수 없음을 분리한 보고서
중지: 파일/기준이 없거나 네트워크, 설치, 쓰기가 필요해질 때
```

`SKILL.md`를 쓰기 전에 모델에게 이 계약을 비판하게 하세요. 무엇을 멋대로 채울지, 어떤 가까운
요청을 다른 방법에 넘겨야 하는지, 검토자가 무엇으로 결과를 확인할지를 묻습니다. “모두
자동화한다”는 답을 받지 않습니다. 쓸모 있는 규칙에는 결정, 경계, 검토 가능한 신호가 있어야
합니다.

## 회고

Skill 안에서 재사용 가능한 decision과 이 file 또는 host에만 속한 것은 무엇인가요? Skill이 명시적으로 맡지 말아야 할 request는 무엇인가요? permission이나 scope를 넓히지 않고 다음 미관찰 layer를 확인할 evidence는 무엇인가요?

## 전이 과제

contract를 learning 또는 research task에 옮깁니다. learning Skill은 practice cycle과 나중 recall task를 조직할 수 있지만 fluency나 mastery를 주장하지 않습니다. research Skill은 source와 uncertainty를 정리할 수 있지만 찾은 link를 확인된 fact로 만들지 않습니다. trigger, non-trigger, stop rule, evidence boundary는 유지합니다.

## 수용 체크리스트

- [ ] candidate는 “AI를 더 좋게”가 아니라 이름 붙은 반복 decision을 해결한다.
- [ ] trigger, non-trigger, input, allowed action, stop, reviewable output이 있다.
- [ ] method, project-specific data, deterministic execution을 나눈다.
- [ ] positive, boundary, failure, transfer에 expected result 또는 정직한 `not_run`이 있다.
- [ ] external material은 source, license, side effect를 review한 뒤에만 채택한다.
- [ ] 핵심 `SKILL.md`에 목적, trigger, non-trigger, 입력, 허용·금지 행동, 중단, 출력, owner, version, review date가 있다.
- [ ] 읽기, 임시 쓰기, 기존 파일 쓰기, 네트워크, 설치, 전송·게시·삭제를 구분했다.
- [ ] token, password, cookie, private key, `.env`, 원시 개인 데이터가 package, fixture, log, example에 없다.
- [ ] references, scripts, assets마다 존재 이유, 로드 조건, 입력·출력·실패 경계가 있다.
- [ ] 의도적 실패는 변수 하나를 바꾸고 산출물에서 확인 가능한 실패 신호를 남긴다.
- [ ] rollback 대상, baseline 또는 backup, read-back 성공 검사가 정확히 기록돼 있다.
- [ ] 발견하지 못했거나 실행하지 못한 층은 성공으로 바꾸지 않고 `unknown` 또는 `not_run`으로 남겼다.

## 출처 및 유지보수 경계

Skill decision method는 project-authored입니다. host behavior, discovery, Plugin, MCP, permission, external candidate는 변합니다. 현재 claim은 [공식 사실 카드](../evidence-library-KO.md#source-notes), [Skill candidate record](../evidence-library-KO.md#source-notes), 구체 license source에서 확인합니다. 어느 것도 기록한 host의 run을 대신하지 않습니다.

## 채택 전 네 가지 사례

자격 증명이나 네트워크 없이 최소 세트를 준비합니다.

| 사례 | 입력 | 올바른 결과 |
|---|---|---|
| 긍정 | 파일과 기준이 분명함 | 로컬 링크 보고서와 읽기 증거 |
| 경계 | 문장만 다듬어 달라는 요청 | 실행하지 않고 링크 검토가 아니라고 설명 |
| 실패 | 파일 또는 기준이 없음 | 질문 또는 `blocked`; 경로를 추측하지 않음 |
| 전이 | 구조가 다른 다른 로컬 보고서 | 방법은 유지하고 기준과 수용 조건을 다시 결정 |

Skill 버전, 비민감 입력, 불러온 리소스, 출력, 첫 중단 지점을 보관합니다. 폴더에 파일이 있다는
사실은 host에서 발견, 로드, 실행되었다는 증거가 아닙니다. 기록이 생기기 전까지 이 장은
`candidate`, 실험은 `not_run`입니다.
