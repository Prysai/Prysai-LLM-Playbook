# 11장: 쓸모 있는 Skill 설계하기

**상태:** `candidate`. **실험:** `not_run`. 이 장은 설계 방법을 정합니다. 특정 host가 Skill을 발견, 로드, 실행했다는 증거는 아닙니다.

## 문제

한 번 잘 된 세션만으로 프롬프트를 Skill로 만들면 위험합니다. 기록하지 않은 사실에 의존하거나, 필요 없는 권한을 요구하거나, 자격 증명을 가정하거나, 유행어만으로 실행될 수 있습니다. 쓸모 있는 Skill은 반복 가능한 작업 범주를 제한된 행동과 검사 가능한 증거에 연결하는 버전 관리 방법 패키지입니다.

> Skill은 제한된 작업 범주를 제한된 행동과 검사 가능한 증거에 연결하는, 발견 가능하고 재사용 가능한 방법 패키지입니다.

Skill은 모델, 도구, 권한, 연결기, 사람의 승인을 대신하지 않습니다.

## 현실의 출발점: Skill이 실행되기 전에 실패할 수 있습니다

### discovery는 독립된 단계입니다

Skill을 디렉터리에 넣었다는 것은 그 위치에 file이 있다는 사실만 뜻합니다. file 존재, 현재 surface에서의 가시성, task의 선택, 입구의 load, step 실행, artifact acceptance는 각각 기록해야 합니다. 어느 단계든 관찰하지 못했다면 handoff에 “연결됨”이라고 뭉뚱그리지 말고 `unknown`이라고 적으세요.

### “연결됨”은 “호출 가능함”이 아닙니다

connector, plugin, workspace setting이 화면에 보인다고 해서 현재 task에 file, network, account, publish permission이 생기지는 않습니다. 첫 adoption에서는 민감하지 않은 positive case로 host, version, path, input, 실제 선택, output을 남기고, 관찰하지 못한 layer를 receipt에 씁니다. 설정 화면은 runtime evidence를 대신할 수 없습니다.

### trigger와 non-trigger를 먼저 나누기

trigger에는 task intent, complete input, method ownership, acceptable risk가 모두 필요합니다. keyword 일치는 충분조건이 아닙니다. 가까운 task에 양보하는 `non_trigger`는 attention과 permission을 지키는 product의 일부입니다. 어떤 method도 copy rewrite, remote check, bulk repair, authority가 불명확한 task를 조용히 맡아서는 안 됩니다.

### input, permission, secret 경계

input은 provided, readable, inferred, unknown으로 나눕니다. path, version, source, baseline, acceptance rule, recovery location이 없으면 model이 채워 넣으면 안 됩니다. read, temporary write, persistent write, network, install, send, publish, delete도 각각 다른 permission입니다. secret은 `SKILL.md`, example, log, screenshot, receipt에 넣지 말고, 필요할 때도 지정된 통제 입구에서만 다룹니다.

### resource를 늘리기 전의 판단

`scripts/`는 결정적이고 검사 가능한 반복 action, `references/`는 일부 branch에서만 필요한 상세, `assets/`는 용도와 license가 명시된 static resource로 제한합니다. 모든 resource에는 input, output, failure mode, 부작용을 적습니다. 첫 실행은 temporary directory 또는 비민감 sample에서 하고 version과 raw output을 남기세요. script가 있다는 사실은 안전, 정확성, 실행 완료의 증거가 아닙니다.

## 문장보다 먼저 계약 쓰기

```yaml
skill_id: evidence-boundary-review
version: "0.1.0"
owner: named-person-or-team
review_date: "YYYY-MM-DD"
purpose: "제공한 산출물을 지정한 증거 경계로 검토한다."
trigger:
  - "증거 경계 검토를 요청한다."
  - "산출물, 목표, 수용 조건이 제공됐다."
non_trigger:
  - "제한 없는 다시 쓰기를 요청한다."
  - "중요한 주장에 출처가 없다."
  - "다른 이름 붙은 방법이 작업을 맡는다."
required_inputs:
  - 대상 경로 또는 붙여 넣은 산출물
  - 목표, 제외 사항, 수용 조건
  - 중요한 주장의 출처
allowed_actions: "대상 읽기; 버릴 수 있는 출력에 보고서 쓰기; 이름 붙은 가역 로컬 검사 실행"
forbidden_actions: "비밀 읽기/출력, 게시, 전송, 삭제, 설치, 무단 네트워크"
output: "주장 → 증거 → 덮이지 않은 범위 보고서"
stop_when: "입력, 권한, 출처, 복구 대상이 없다"
```

trigger에는 작업 의도, 필요한 입력, 방법의 소유권, 허용 가능한 위험이 있어야 합니다. 키워드 일치만으로는 부족합니다. non-trigger는 가까운 작업을 가로채지 않게 합니다.

## 방법, 데이터, 실행을 나누기

- `SKILL.md`에는 항상 필요한 목적, 경계, 절차, 중단 규칙, 증거를 둡니다.
- `references/`에는 특정 갈래에서만 읽을 자료를 둡니다.
- `scripts/`에는 의존성, 네트워크, 쓰기 범위, 종료 동작을 선언한 결정적 검사만 둡니다.
- `assets/`에는 선언한 정적 자원만 둡니다.

중요한 안전 규칙을 선택적 참고 자료에 숨기지 않습니다. 파일 존재는 발견을, 발견은 로드를, 로드는 채택을, 채택은 동작을 증명하지 않습니다.

## 네 가지 사례로 평가하기

| 사례 | 일어나야 할 일 | 일어나면 안 될 일 |
|---|---|---|
| 긍정 | 방법이 실행되고 검토 가능한 산출물을 남긴다 | 증거 없는 성공 선언 |
| 경계 | 올바른 방법에 넘기거나 구체적으로 질문한다 | 비슷한 이름만으로 실행 |
| 실패 | 위험한 쓰기 전에 멈추고 첫 누락 지점을 남긴다 | 입력, 권한, 결과를 지어냄 |
| 전이 | 도메인 사실을 바꾸고 가정을 다시 검사한다 | 명사만 기계적으로 바꿈 |

한 변수만 바꾸고 산출물에 보이는 신호를 남기는 의도적 실패를 넣습니다. rollback은 대상, 기준선, 단계, 읽어 본 성공 검사가 필요합니다. “되돌리기”만으로는 충분하지 않습니다.

## 연습과 한계

Markdown 링크 검토, 조사 보고서 출처 확인, 릴리스 인계처럼 두 번 이상 한 저위험 방법을 고릅니다. 계약, 긍정 사례, 실행하면 안 되는 근접 사례, 빠진 입력, 보이는 실패, rollback 검사를 만들고, 산출물이 무엇을 증명하고 무엇이 unknown인지 표로 남깁니다.

선언한 환경에서 이 사례들을 기록하고 독립 검토를 받기 전까지 Skill은 `candidate`입니다. 발견, 로드, 실행, 사업 효과를 주장하지 않습니다.

## 관찰 가능한 설계 흐름

여기서는 위험이 낮은 “Markdown 로컬 링크 점검”을 예로 듭니다. 네트워크, 계정, 실제 사용자 데이터가 필요하지 않습니다. 그렇다고 특정 host가 이 Skill을 자동으로 발견한다는 증거는 아닙니다.

### 작업을 확인 가능한 범위로 줄이기

“문서 품질을 검토해 주세요”는 경계가 없습니다. 방법을 쓰기 전에 이번 작업의 계약을 적습니다.

```text
목표: docs/quickstart.md 안의 깨진 상대 Markdown 링크를 찾는다.
허용: 그 파일 읽기; 임시 보고서에 후보 기록; 읽기 전용 로컬 검사 실행.
금지: 본문 수정, 네트워크, 의존성 설치, 삭제, 게시.
수용: 보고서가 링크 텍스트, 대상, 검사 결과, unknown 사유를 각각 보여 준다.
중단: 파일이 없거나 해석 기준이 불명확하거나 허가되지 않은 행동이 필요하다.
```

이 계약은 이번 작업에만 속합니다. Skill은 반복해서 쓸 방법만 보관합니다. 둘을 섞으면 다음 작업에 오래된 경로, 권한, 결론이 따라옵니다.

### trigger와 양보 규칙 설계하기

trigger는 홍보 문구가 아닙니다. 이 방법이 이 작업을 맡아도 되는지 판단할 수 있어야 합니다.

| 항목 | 링크 점검 Skill의 예 |
|---|---|
| 적용 | 이름이 지정된 Markdown 파일의 로컬 링크를 목표와 수용 조건과 함께 점검해 달라는 요청 |
| 비적용 | 다시 쓰기, 원격 사이트 점검, 저장소 전체 수리, 대상 파일이 없는 요청 |
| 먼저 묻기 | 링크 기준은 현재 파일, 저장소 루트, 사이트 출력 중 어느 것인가? |
| 중단 | 명시 승인 없이 네트워크, 자격 증명, 보호된 쓰기, 게시 변경이 필요함 |

“링크”와 “점검”이라는 단어만으로는 부족합니다. 의도, 입력, 방법의 소유권, 허용 위험을 함께 봐야 합니다.

### 행동과 증거를 짝지어 두기

| 단계 | 허용 행동 | 남겨야 할 증거 | 아직 증명하지 않는 것 |
|---|---|---|---|
| 입력 점검 | 파일과 계약 읽기 | 경로, 기준 버전, 빠진 입력 | 링크가 실제로 깨졌다는 것 |
| 후보 추출 | 상대 링크 추출 | 후보 표와 해석 규칙 | 대상 파일의 존재 |
| 검사 | 읽기 전용으로 경로 해석 | 존재/없음/unknown 결과 | 원격 URL의 접근 가능성 |
| 전달 | 버릴 수 있는 보고서 쓰기 | 보고서, 명령, 종료 상태 | 문제가 수정되었다는 것 |
| 검토 | 위험하거나 unknown인 항목 읽기 | 결정과 미포함 범위 | 모든 저장소에서 통한다는 것 |

종료 상태가 0이라는 것은 검사가 자신의 정의에 따라 끝났다는 뜻일 뿐입니다. 무시한 형식, 빌드 시 재작성, 원격 대상까지 옳다는 뜻은 아닙니다.

## 최소는 중요한 판단을 빼는 것이 아니다

입구의 `SKILL.md`는 짧을 수 있지만, 매번 필요한 경계는 남겨야 합니다.

```markdown
---
name: local-link-review
description: 목표, 수용 조건, 읽기 전용 범위가 주어진 이름 있는 Markdown
파일의 로컬 링크를 검토한다. 다시 쓰기, 네트워크, 대량 수리에는 쓰지 않는다.
---

1. 대상, 링크 기준, 허용 범위, 수용 조건을 확인한다.
2. 하나라도 없으면 멈추고 질문한다.
3. 로컬 상대 링크만 추출하고 원문은 보존한다.
4. 선언된 읽기 전용 검사를 실행하고 버전과 종료 상태를 기록한다.
5. 후보, 확인됨, unknown 결과를 분리한다.
6. 새 승인 없이 수정, 게시, 설치, 네트워크를 하지 않는다.
```

세부 해석 규칙은 `references/`, 결정적인 검사기는 `scripts/`에 둘 수 있습니다. 그러나 “대상이 없으면 중단”, “네트워크와 쓰기를 하지 않음”은 선택 파일에 숨기면 안 됩니다.

## 의도적 실패로 중단을 시험하기

임시 샘플을 만들고 한 가지만 바꿉니다. 링크가 존재하지 않는 경로를 가리키게 합니다. 기대하는 것은 막연한 영리함이 아니라 눈에 보이는 신호입니다.

```text
BROKEN: [설치 안내] (guides/install.md)
resolved: docs/guides/install.md
check: path does not exist
scope: local relative path only; remote availability not checked
```

그다음 `https://` 링크가 있는 경계 사례를 실행합니다. 네트워크에 나가지 않고 범위 밖 또는 unknown으로 남겨야 합니다. 링크 기준이 빠진 경우에도 구조를 추측하지 말고 질문하거나 멈추는 것이 맞습니다.

## 작은 실험과 되돌아보기

1. 안전하게 읽을 수 있는 Markdown 파일을 고른다. 비밀이나 사적인 자료를 모델에 주지 않는다.
2. 목표, 범위, 수용 조건을 작업 계약에 채운다.
3. 읽기 전용 검사를 한 번 실행하고 환경, 날짜, 입력, 원시 출력을 남긴다.
4. 임시로 깨진 링크를 넣어 다시 실행하고, 수리 행동이 아니라 실패 신호가 남는지 확인한다.
5. 샘플을 버리거나 줄을 되돌린 뒤 원본 파일과 보고서를 다시 읽어 승인되지 않은 변경이 없는지 확인한다.
6. 다른 독자에게 계약과 보고서만 보여 주고 결과, 범위, unknown을 설명할 수 있는지 묻는다.

이 관찰은 기록한 환경에만 적용됩니다. 다른 host, 버전, 모델에서도 같은 발견, 선택, 로드, 실행이 일어난다는 증거는 아닙니다.

## 자주 하는 실수

- description을 보증으로 쓰기: “게시 안전을 자동 보장”은 경계와 수용 조건이 없다.
- script와 Skill을 혼동하기: script는 정해진 검사를 하고, Skill은 언제 쓰고 언제 멈추며 결과를 어떻게 해석할지 정한다.
- 발견을 신뢰성과 혼동하기: 메타데이터, 선택, 로드, 행동, 증거를 따로 확인한다.
- unknown을 숨기기: “원격 링크는 확인하지 않음”도 보고서의 중요한 결과다.

## 채택 영수증: 파일이 있다고 의존할 수 있는 것은 아닙니다

Skill을 실제 작업에 넘기기 전에 채택 영수증을 남깁니다. “폴더에 보인다”와 “믿고 써도 된다”를
혼동하지 않게 하고, 다음 검토자가 어느 단계부터 확인할지 보여 줍니다.

```text
Skill 이름과 버전:
작업 공백: “AI를 더 똑똑하게”가 아니라 보완할 구체적인 판단
출처와 라이선스: 원본 / 검토한 출처, 라이선스와 검토 날짜
이번 host와 surface: 실제로 쓴 제품, 버전, 경로
관찰됨: 파일 / 발견 / 선택 / 로드 / 행동 / 출력
미관찰: 실행, 되읽기, 독립 검토가 없는 모든 단계
허용 범위: 읽기, 임시 쓰기, 네트워크, 설치, 공개를 각각 기록
다음 안전 검사: 미관찰 단계 하나만 확인
중단: 입력, 권한, 복구 대상, 증거가 없을 때
```

저장소에 `SKILL.md`가 있다는 것은 파일 존재만 뒷받침합니다. host가 발견했거나 방법이 실행됐다는
뜻은 아닙니다. 보고서가 한 번 나와도 기록한 작업과 환경에 대한 관찰일 뿐, 모든 모델, 폴더,
사용자에게 같은 결과가 난다는 증거는 아닙니다.

## 외부 방법은 출처를 검토한 뒤 채택합니다

외부 Skill의 지침, script, example은 검토할 material로 취급합니다. 저장소가 인기 있거나 설명이
매끄럽거나 이름이 비슷하다는 이유만으로 과정에 복사하거나 실제 데이터로 실행하지 않습니다.
최소한 다음을 확인합니다.

1. 원본 링크, 구체 revision, 유지 담당자, 검토 날짜;
2. 상위 license가 필요한 code, script, asset, nested dependency를 포괄하는지;
3. 무엇을 읽고, 쓰고, 설치하고, 연결하고, 전송할 수 있는지;
4. 더 작은 자체 방법 대신 그 작업 공백에 정말 필요한지; 그리고
5. 민감하지 않은 임시 fixture에서 무엇을 검사했고 무엇은 아직 실행하지 않았는지.

답할 수 없는 항목이 있으면 링크와 조사 기록만 남깁니다. 본 프로젝트의 Skill로 복사하거나
채택된 능력이라고 표시하지 않습니다.

## 따라 하기: 반복 가능한 검사를 Skill로 만들기

적어도 두 번 해 본 작은 작업을 고릅니다. Markdown 파일의 로컬 링크 검토, 보고서에 출처와
날짜가 있는지 확인, diff와 테스트 명령을 포함한 인계 준비가 예입니다. “더 좋게 만들기”는
고르지 않습니다. 다른 사람이 같은 결정을 반복할 수 없기 때문입니다.

먼저 Skill 없이 한 번 작업하고 목표, 입력 파일, 허용 행동, 결과, 증거, 중단 지점만 남깁니다.
다른 작업에서도 필요한 판단에 밑줄을 긋습니다. 파일명이나 보기 좋은 응답이 아니라 그 판단이
Skill 후보입니다.

```text
사용 시점: 지정된 Markdown 파일의 로컬 링크 검토를 요청했을 때
사용하지 않음: 문장 다듬기, 웹 링크, 게시, 대량 수정
필수 입력: 파일, 링크 기준, 읽기 전용 범위, 수용 조건
반환: 확인됨, 후보, 알 수 없음을 분리한 보고서
중지: 파일/기준이 없거나 네트워크, 설치, 쓰기가 필요해질 때
```

`SKILL.md`를 쓰기 전에 모델에게 이 계약을 비판하게 하세요. 무엇을 멋대로 채울지, 어떤 가까운
요청을 다른 방법에 넘겨야 하는지, 검토자가 무엇으로 결과를 확인할지를 묻습니다. “모두
자동화한다”는 답을 받지 않습니다. 쓸모 있는 규칙에는 결정, 경계, 검토 가능한 신호가 있어야
합니다.

## 채택 전 네 가지 사례

자격 증명이나 네트워크 없이 최소 세트를 준비합니다.

| 사례 | 입력 | 올바른 결과 |
|---|---|---|
| 긍정 | 파일과 기준이 분명함 | 로컬 링크 보고서와 읽기 증거 |
| 경계 | 문장만 다듬어 달라는 요청 | 실행하지 않고 링크 검토가 아니라고 설명 |
| 실패 | 파일 또는 기준이 없음 | 질문 또는 `blocked`; 경로를 추측하지 않음 |
| 전이 | 구조가 다른 다른 로컬 보고서 | 방법은 유지하고 기준과 수용 조건을 다시 결정 |

Skill 버전, 비민감 입력, 불러온 리소스, 출력, 첫 중단 지점을 보관합니다. 폴더에 파일이 있다는
사실은 host에서 발견, 로드, 실행되었다는 증거가 아닙니다. 기록이 생기기 전까지 이 장은
`candidate`, 실험은 `not_run`입니다.
