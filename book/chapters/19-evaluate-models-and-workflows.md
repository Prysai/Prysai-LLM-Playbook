# 第十九章：评估模型和工作流——从感觉到证据

## 本章要解决的问题

“这个模型感觉更聪明”“这个 Skill 好像更稳定”“这次任务很快就完成了”都可以作为观察，但都不能单独支撑选择。模型、提示、上下文、工具、权限、任务难度和人的审查方式会一起影响结果。如果不固定这些变量，比较出来的可能只是不同实验条件。

## 学习目标

读者完成本章后应当能够：

- 把“哪个模型更好”改写成一个明确的决策问题；
- 建立有版本、覆盖多个领域和失败类型的任务集；
- 区分首次通过、最终通过、返工、耗时、成本和证据完整度；
- 记录错误类型，并用数据而不是印象决定下一步；
- 说明一次评估结论的适用范围和未知部分。

## 1. 先定义要做的决策

评估不是为了产生一个漂亮的总分，而是为了支持行动。例如：

| 决策 | 需要回答的比较问题 |
|---|---|
| 选择默认模型 | 哪个模型在核心任务集上满足最低质量，同时成本和延迟可接受？ |
| 选择 Skill | 启用 Skill 后，遗漏率、验证完整度或返工率是否改善？ |
| 选择工作流 | 完整生命周期是否降低返工，增加的前置时间是否值得？ |
| 选择权限 | 额外工具是否带来可测量收益，还是只增加副作用和审查成本？ |

如果不能说清楚评估结果会改变什么决定，就先不要扩大任务集或增加指标。

## 2. 固定任务集，而不是挑演示

一个可复用的任务集至少包含：

1. 目标明确的常规任务；
2. 缺失输入、冲突约束和恶意外部文本等边界任务；
3. 需要迁移到不同领域或表达方式的任务；
4. 需要人工判断的高价值任务。

每项任务都要有稳定的 ID、版本、输入上下文、允许行动、预期证据、禁止行为和通过标准。评测中途不能因为某个模型表现不好就删除任务；若任务本身有问题，应新建任务集版本并记录原因。

Field Guide 的任务字段和分层规则见[评测框架/夹具规范](../../docs/quality/evaluation-framework.md)，Luna 的固定任务集要求见[模型评估实验](../../docs/model-evaluation-luna.md)。当前已有 `evals/task-set-v1.yaml`，包含 30 个固定任务；它通过结构校验，但尚无模型运行日志，因此本章仍只能标为草稿。

真实问题入口：[证据审查实验](../labs/lab-003-evidence-review.md)。研究档案入口：[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)。

## 3. 固定条件并记录变化

比较模型或工作流时，尽量固定：

- 任务文本和上下文版本；
- 模型 ID、推理强度和产品入口；
- 工具集合、网络条件和权限；
- 时间预算、重复次数和输出格式；
- 验收标准、人工评分表和复核人。

如果任何条件变化，评测日志必须记录变化。否则“模型变好了”可能只是因为给了更多文件、更多时间或更宽权限。

## 4. 用分层指标描述结果

不要用单一分数掩盖不同问题。

- **首次通过率：** 第一次运行就满足最低验收的任务比例；
- **最终通过率：** 允许规定次数的修正后满足验收的比例；
- **返工率：** 需要额外人工或 Agent 修复的任务比例；
- **证据完整度：** 必需证据中实际提供并可核查的比例；
- **停止正确率：** 输入不足、权限冲突或重复失败时，是否在正确边界停下；
- **耗时和成本：** 从开始到满足验收的时间与统一口径成本；
- **错误类型：** 目标、上下文、实现、事实、权限、验证、交付或维护错误。

先看安全和最低质量门槛，再看速度和成本。一个更便宜但经常越权或虚构证据的方案，不能因为平均耗时低就被判定为更好。

## 5. 人工评分要可复核

对于解释质量、取舍、可维护性和学习价值，自动指标不够。人工评分表应当写出：

- 每个分数的行为描述；
- 什么证据可以支持该分数；
- 哪些错误会直接不通过；
- 谁评分、何时评分、是否需要第二位复核人。

评分者不应只看最终答案，还要检查实际读取、工具调用、变更、验证和未完成声明。

## 6. 评估主流程

```text
明确决策
  → 冻结任务集和条件
  → 运行基线与候选方案
  → 记录结果和证据
  → 逐项评分与错误分类
  → 分析质量/成本/风险取舍
  → 写出适用范围和下一次复核
```

评估完成后必须留下可重跑的任务集版本、运行日志和结论，而不是只留一句“推荐模型 X”。

## 实验：比较两条工作流

选择一个低风险任务，例如把一份结构化笔记转换成 Markdown。运行两次：

1. 只给目标，让 Codex 直接完成；
2. 使用任务协议、最小上下文、明确验收和证据审查。

记录前置时间、变更范围、首次通过、返工、发现问题的阶段和交付证据。不要预先假设第二条一定更快；它可能增加前置时间，却减少返工。

### 故意失败变体

第二次运行中途改变验收标准，却不更新任务集版本。通过标准不是得到一个更好的答案，而是发现实验条件已经改变，并把这次运行标记为不可直接比较。

## 迁移练习

把同一评估结构迁移到研究问题、营销实验或团队 Skill 选择。说明哪些指标可以复用，哪些必须因领域风险而调整。

## “我真的学会了吗？”

- [ ] 我能把一个模型偏好写成可验证的决策问题；
- [ ] 任务集有版本、正例、边界例和迁移例；
- [ ] 我记录了模型、上下文、工具、权限和重复次数；
- [ ] 我区分首次通过、最终通过、返工和证据完整度；
- [ ] 我能指出结论不适用的任务或环境；
- [ ] 我没有用一次演示证明“性价比最高”。
