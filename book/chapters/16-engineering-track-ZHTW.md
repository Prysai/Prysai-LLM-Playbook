# 第 16 章：工程路線——從想法到可靠軟體

**狀態：**`candidate`。**實驗：**`draft / not_run`。能生成程式碼、通過建置或看到頁面，都不等於符合使用者需求、執行可靠或已經發布。

## 問題：把「寫程式碼」誤當成「交付結果」

AI 可以快速生成補丁，卻也可能在錯誤的儲存庫、錯誤的範圍或未經授權的環境中產生看似合理的修改。可靠的工程流程不是讓模型一次寫完，而是把需求、現況、最小切片、行動邊界、驗證、失敗復原和交接串成一個閉環。

## 學習目標

完成本章後，你可以把需求拆成可驗證的小切片，並把建置、測試、本機執行、發布和使用者驗收視為不同的證據主張。

## 真實問題入口：綠色測試不等於使用者任務完成

補丁可以編譯成功，卻仍忽略空輸入、錯誤路徑或復原方法。關鍵不是有多少綠燈，而是檢查是否涵蓋具體使用者動作及其失敗情境。

公開問題記錄裡有三種很適合拿來練習的訊號：

- **FP-09：** 有報告指出，模型容量錯誤可能中斷工作，而排隊中的請求接著使用半完成狀態。重試前先檢查工作樹、diff、測試和最後完成點；不要把未知狀態當成乾淨起點。
- **FP-10：** 有 Windows CLI 的格式化或驗證指令長時間停在 `Working`，卻沒有清楚錯誤。指令需要輸出上限、逾時和中斷路徑；「指令啟動了」不等於「驗證通過」。
- **FP-11：** 有報告指出，來源驗證被擴大成持久環境的強制重裝。安裝、發布、部署、重啟和線上驗證都是不同的授權狀態，不能由「跑一次測試」自動推出。

這些是使用者報告或分析，不是本專案對所有版本的本機重現，也沒有確認根因。真正作工程決策時，仍要回到目前的儲存庫、執行環境和現有證據。

## 工程生命週期：每一步都有入口與出口

```text
定義問題 → 撰寫規格與驗收 → 計畫和切片
        → 增量實作 → 靜態檢查／測試
        → 執行時驗證 → 複核與簡化
        → 發布／復原 → 維護與回歸
```

| 階段 | 進入條件 | 最低出口證據 |
|---|---|---|
| 定義 | 已知使用者或系統問題與範圍 | 其他人能複述的問題描述 |
| 規格 | 輸入、輸出、錯誤和邊界已寫明 | 驗收條件與非目標 |
| 計畫 | 相依套件和風險已列出 | 可獨立驗證的切片 |
| 實作 | 目前切片與基線已確認 | 小而可解釋的 diff 和更新紀錄 |
| 測試 | 正常與失敗路徑可執行 | 命令、結果和失敗解釋 |
| 執行時驗證 | 有可啟動環境與代表性輸入 | 版本、日誌、回應／截圖和環境 |
| 發布 | 變更已複核且可復原 | 發布紀錄、監控和回復演練 |

建置、測試、本機執行、使用者接受和生產就緒是五個不同結論；不要用其中一個替代另一個。

## 從一個可驗收的垂直切片開始

不要從「做完整產品」開始。先定義一個可以在可丟棄副本中驗收的最小變化：使用者可見結果、允許修改的路徑、禁止動作、輸入基線、驗收命令、人工檢查、回滾目標和未覆蓋風險。

| 階段 | 關鍵問題 | 最低證據 |
|---|---|---|
| 定義 | 使用者到底要什麼？範圍和權限是什麼？ | 任務協議、輸入、基線 |
| 計劃 | 最小切片和依賴是什麼？ | 方案、風險、回滾 |
| 修改 | 實際改了什麼？ | diff、路徑、行動日誌 |
| 驗證 | 哪些宣告被檢查？ | 命令、原始輸出、退出碼、人工檢查 |
| 交接 | 完成與未知分別是什麼？ | 證據表、下一步、復原方法 |

## 操作：給 Agent 一份工程契約

契約至少要說清：目標使用者和可觀察結果；允許讀取／修改的目錄；明確禁止的生產、網路、憑據、安裝、發布和刪除；現有指令與逾時；驗收標準；遇到失敗的停止條件；以及誰確認外部副作用。不要把「自己判斷並修好所有問題」當作契約，它沒有範圍也沒有回滾。

每次修改前記錄工作目錄、儲存庫根目錄、分支、輸入版本、`git status` 和基線測試。每次修改後記錄變更路徑、diff、指令、退出碼、原始輸出、未執行檢查和人工觀察。一個綠色測試只能支援它覆蓋的斷言，不能支援部署、使用者理解、效能、安全或發布成功。

### 先查真實來源，再逐片修改

框架、API、函式庫版本和指令的事實，優先用官方文件、型別定義、目前程式碼或可重現結果確認；部落格和模型記憶只能當線索。測試不能證明真實網路、資料庫、瀏覽器、權限、並行、時區或部署行為時，要另外設計執行期間的檢查。每次只改一個能解釋的切片，保存 diff 和復原點；不要在未知的失敗狀態上繼續疊加修正。

### 執行時證據需要獨立紀錄

執行期間的檢查至少記錄啟動指令、相依套件版本、測試用環境變數、實際輸入、回應或頁面、日誌、錯誤路徑和環境。生產就緒還需要安全、效能、遷移、監控、復原和使用者驗收證據。缺少輸出、測試相依套件、基線或工作樹狀態時，先停止並縮小檢查；不要為了「讓驗證通過」而替換執行環境或強制重灌。

## Web coding：把一個可見結果帶到真實瀏覽器

「做一個完整網站」隱藏了受眾、頁面狀態、原始檔、執行時、瀏覽器驗收和發布
回滾等多個任務。先在可丟棄副本中完成一個靜態頁面的單一可見改動：讀取
`examples/skill-sandbox/product-context-real-estate` 的 README 和 `index.html`，
只改 `index.html` 中的一句話，不加框架、圖片、表單、API 或網路請求。Python 3
已經可用時，按沙盒文件在複製目錄執行 `python -m http.server 4182`，開啟
`http://127.0.0.1:4182/`，檢查標題、改動句子、標題保留、連結、控制檯和 390px
視口。

記錄單至少保留：複製目錄、允許的檔案、URL、檢查到的可見狀態、diff，以及部署、
無障礙、其他瀏覽器和使用者驗收等未驗證項。原始檔的 diff 不能證明 CSS 載入、相對
路徑、移動端裁切或執行時錯誤；本地渲染透過也不等於網站已部署。

瀏覽器檢查不是「看起來差不多」就結束。逐項確認標題、主標題、狀態文字、連結目標、控制台錯誤、鍵盤順序，以及需要時的窄視口。視覺回饋可以補充目標區域和狀態，但不能代替文字規格：寫清楚要改哪裡、必須保留什麼，以及用什麼觀察判定通過。

## 用 LLM 學程式：依證據逐級增加難度

不要承諾幾天就「學會程式設計」。每一級都先留下目前任務的可觀察證據，再進入下一級：

| 等級 | 練習 | 進入下一級前的最低證據 |
|---|---|---|
| 1. 閱讀 | 請模型解釋一個現有函式或頁面 | 能用自己的話說出輸入、輸出和一個邊界 |
| 2. 修改 | 在可丟棄專案中做一個可見變更 | diff 只有允許檔案，瀏覽器或檢查器能看到變化 |
| 3. 測試 | 新增或執行一項聚焦檢查，包含失敗例 | 能說清檢查證明什麼、沒有涵蓋什麼 |
| 4. 切片 | 從合約到執行時交付一個垂直功能 | 正常路徑與空／無效路徑都有記錄 |
| 5. 復原 | 從中斷或失敗的檢查點繼續 | 繼續前先看基線，保留失敗證據 |
| 6. 協作 | 使用規則、隔離環境、複核和交接 | 另一個人能根據記錄單重現決策 |

每次讓模型先讀後改，先列出範圍和假設；缺少輸入會改變風險或驗收時就停止。模型的解釋能幫助學習，但不等於你已經能獨立診斷、實作或維護。

## 小實驗：一條 Markdown 垂直切片

### 準備

使用包含 `input.json` 的可丟棄本機目錄；不得聯網、使用憑據、設定遠端或安裝相依套件。記錄原始檔案與允許寫入的路徑。

### 任務

在可丟棄副本中，僅允許修改一個指定 Markdown 檔案。先寫發布說明的輸入事實和驗收規則，再完成：CP0 定義、CP1 計畫、CP2 修改、CP3 驗證、CP4 交接。至少做一個失敗分支：缺少輸入時在編輯前停止；檢查失敗時儲存輸出；或在新會話中僅根據檢查點和儲存庫狀態復原。不要安裝相依套件、改 PATH、登入、push、發布或重啟服務。

### 證據

儲存任務卡、diff、實際命令、退出碼、輸入、獨立讀回的輸出和未執行動作。沒有這些記錄的測試不能證明發布或使用者驗收。

### 覆盤

每個檢查實際支援哪條主張？哪條失敗路徑仍未知，下一步最小檢查是什麼？

## 可觀察實驗：直接實作與完整生命週期的對照

在可丟棄目錄選擇低風險功能，例如讀取文字清單、去重後寫入 JSON。準備正常輸入、空輸入、重複項、缺欄位和無效編碼；固定執行時版本、逾時和輸出目錄，不使用真實秘密或外部寫入。

1. **直接實作輪：** 只給目標，記錄模型是否澄清規格、修改哪些檔案、執行哪些命令，以及是否處理無效輸入。
2. **生命週期輪：** 先要求問題描述、驗收、非目標、切片計畫和測試矩陣，再逐片實作，每一步後檢查 diff。
3. 兩輪都執行靜態檢查、單元測試、本機執行、空輸入和無效輸入；記錄每個問題在哪一層被發現。
4. 模擬中斷或容量錯誤：先停止，檢查工作樹、最近 diff、日誌和測試狀態，再決定繼續、復原或建立新檢查點。
5. 不要強制重裝、寫入生產環境、部署或重啟；這些建議都屬於超出目前授權的行動。

證據至少包括兩份任務合約、diff、測試矩陣、命令與退出碼、執行時輸入／輸出、錯誤日誌、復原點和最終驗收。分別標記「建置成功、測試通過、執行時正確、使用者／發布驗收」，不要合併成一個完成標籤。

## 遷移練習

把任務卡用於修改一個學習示例，但不改變連結、導覽或發布狀態。寫清使用者影響、檔案、檢查和恢復方法。

## 來源與維護邊界

工程生命週期和證據分層是穩定方法。框架、指令、執行期間和部署規則是易變事實，必須在具體專案、目前版本和實際環境中重新核驗。

## 失敗復原不是重複同一條指令

失敗後先問：目前狀態是什麼？已有副作用是什麼？下一次嘗試改變了什麼診斷條件？若答案不清楚，應停止並儲存檢查點。重複同一指令並不能叫復原。若工具建議強制重灌、上傳日誌、使用憑據或擴大權限，把建議記為資料，等待明確授權。

## 我真的學會了嗎？

- [ ] 我能把模糊需求切成可驗收的垂直切片。
- [ ] 我在編輯前固定了範圍、基線、權限和回滾。
- [ ] 我能把實際 diff、命令、退出碼和人工觀察對應到不同主張。
- [ ] 我在失敗後先檢查狀態，而不是盲目重試或重灌。
- [ ] 我能區分本地完成、遠端發布、生產執行和使用者驗收。
- [ ] 我沒有把建置通過寫成產品成功。

框架、相依套件、指令和部署規則都是易變事實，應以目前專案的官方文件和本機環境為準。配合 [實驗 009：工程生命週期](../labs/lab-009-engineering-lifecycle-ZHTW.md) 與 [實驗 013：可稽核垂直切片](../labs/lab-013-l3-vertical-slice-ZHTW.md)。本章為 `candidate`，不證明任何具體系統已經生產可用。

## 把需求變成工程任務卡

「給我加匯出功能」還不能開始編碼。先把它寫成一張可複核的卡；未知項保留為問題，而不是由模型自行決定：

```text
使用者動作：在 <頁面／命令> 請求匯出 <明確資料範圍>。
成功：生成 <格式>，包含 <欄位>；使用者能看到 <可觀察結果>。
失敗：無權限、空資料、無效輸入、寫入失敗時分別返回什麼？
非目標：不遷移歷史資料、不發布、不改變權限、不接入外部服務。
允許範圍：可讀／可寫路徑、允許命令、網路和秘密邊界。
驗收：哪些測試、一次本地執行、哪項人工檢查；各自覆蓋什麼？
恢復：原始狀態、可刪除的臨時產物、讀回檢查和停止條件。
```

只有當這張卡能讓另一位開發者複述目標和非目標時，才選擇第一個切片。若匯出格式、覆蓋策略或權限仍未知，最小切片可以只是讀取輸入並產生預覽，而不是悄悄寫檔案。

### 四個綠燈，四種不同結論

| 證據 | 可以說什麼 | 不能說什麼 |
|---|---|---|
| 建置成功 | 指定設定能編譯／打包 | 使用者流程可用或已部署 |
| 測試通過 | 該測試斷言在該環境成立 | 未覆蓋的錯誤、瀏覽器、權限或真實輸入正確 |
| 本地執行正確 | 指定版本和輸入得到觀察到的結果 | 生產環境、所有帳戶或效能已驗證 |
| 發布狀態可讀回 | 指定遠端出現該 revision 或記錄 | 使用者已接受、監控正常或能安全回滾 |

不要把四個綠燈合成「產品已經完成」。每個結論都需要自己的命令、輸入、環境、輸出和範圍。

## 小實驗：一個 JSON 垂直切片

在可丟棄目錄做一個功能：讀取 `input.json` 中的字串列表，去除重複項並寫入 `output.json`。只允許該目錄內讀寫，不允許網路、安裝、登入、提交、推送或發布。

1. 寫任務卡和基線：正常列表、空列表、重複列表、缺欄位或無效 JSON。
2. 先實現一個切片：只處理正常與重複輸入；儲存 diff 和命令輸出。
3. 增加空輸入和無效輸入處理。每次只改變一個可解釋點，並在改動後執行已宣告檢查。
4. 用獨立本地命令讀取 `output.json`，確認內容、錯誤資訊和原輸入的狀態；記錄執行版本、輸入、退出碼和原始輸出。
5. 模擬中斷：在一個半完成狀態停止，先讀 `git status`、diff、日誌和輸出，再決定繼續、恢復或新建檢查點。不要直接新增無關需求。

若命令無輸出、依賴缺失、工作區未知，或建議改 PATH、重灌執行時、上傳日誌、部署或重啟，停止並說明缺失的授權和恢復材料。綠色結果不值得用擴大權限來換取。

## 工程任務卡：一次可驗收的最小改動

這張卡適用於你擁有或獲授權的可丟棄專案副本。它先約束問題，再讓任何 LLM 協助閱讀、計劃或編輯；它不授權安裝、聯網、提交、推送、發布或接觸生產資料。

```text
目標：使用者完成 [一個具體動作] 後應看到什麼可檢查結果？
範圍：允許讀取 [路徑]；確認後僅修改 [路徑]；明確不改 [路徑]。
基線：目前分支／提交、已有改動、相關測試或命令的原始結果。
真實來源：哪個規格、現有行為、測試、介面或設計檔案擁有此事實？
最小切片：本次只改變哪一項可觀察行為？
驗收：檔案範圍、定向檢查、執行時觀察和人工閱讀各驗證什麼？
禁止動作：安裝、網路、刪除、提交、推送、發布、外部訊息、秘密讀取。
停止：路徑、規格、授權、恢復方法或驗收規則不清楚時暫停。
交付：diff、實際命令與輸出、通過／失敗／未執行、未知項和最小下一步。
```

### 四個綠燈是四種不同結論

| 訊號 | 最多說明什麼 | 仍不能說明什麼 |
|---|---|---|
| diff 很小 | 比較範圍內文字變化有限 | 需求已滿足或執行正確 |
| 靜態檢查透過 | 該檢查在記錄環境中透過 | 所有路徑與使用者場景正常 |
| 本地執行透過 | 一個明確執行場景可觀察 | 部署、效能、安全或外部整合正確 |
| 人工驗收透過 | 指定讀者按指定規則看到了結果 | 長期維護、遷移或普遍採用 |

當任一綠燈缺失時，交付中保留 `not_run`、`blocked` 或 `unknown`。不要為了獲得「全綠」而臨時擴大權限、替換環境或改寫規格。
