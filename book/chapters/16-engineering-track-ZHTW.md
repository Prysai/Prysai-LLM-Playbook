# 第 16 章：工程路線——從想法到可靠軟體

**狀態：**`candidate`。**實驗：**`draft / not_run`。能生成程式碼、透過構建或看到頁面，都不等於真實使用者需要、執行可靠或已經發布。

## 問題：把“寫程式碼”誤當成“交付結果”

AI 可以快速生成補丁，卻也能在錯誤的倉庫、錯誤的範圍或未經授權的環境中生成看似合理的修改。可靠工程不是讓模型一次寫完，而是把需求、現狀、最小切片、行動邊界、驗證、失敗恢復和交接串成閉環。

## 學習目標

你能把需求拆成可驗證的小切片，並把構建、測試、本地執行、釋出和使用者驗收當作不同的證據主張。

## 真實問題入口：綠色測試不等於使用者任務完成

補丁可以編譯成功，卻仍忽略空輸入、錯誤路徑或恢復方法。關鍵不是有多少綠燈，而是檢查是否覆蓋具體使用者動作及其失敗情形。

## 從一個可驗收的豎向切片開始

不要從“做完整產品”開始。先定義一個可以在可丟棄副本中驗收的最小變化：使用者可見結果、允許修改的路徑、禁止動作、輸入基線、驗收命令、人工檢查、回滾目標和未覆蓋風險。

| 階段 | 關鍵問題 | 最低證據 |
|---|---|---|
| 定義 | 使用者到底要什麼？範圍和許可權是什麼？ | 任務協議、輸入、基線 |
| 計劃 | 最小切片和依賴是什麼？ | 方案、風險、回滾 |
| 修改 | 實際改了什麼？ | diff、路徑、行動日誌 |
| 驗證 | 哪些宣告被檢查？ | 命令、原始輸出、退出碼、人工檢查 |
| 交接 | 完成與未知分別是什麼？ | 證據表、下一步、恢復方法 |

## 操作：給 Agent 一個工程合同

合同至少要說清：目標使用者和可觀察結果；允許讀取/修改的目錄；明確禁止的生產、網路、憑據、安裝、釋出和刪除；現有命令與超時；驗收標準；遇到失敗的停止條件；以及誰確認外部副作用。不要把“自己判斷並修好所有問題”當作合同，它沒有範圍也沒有回滾。

每次修改前記錄工作目錄、倉庫根目錄、分支、輸入版本、`git status` 和基線測試。每次修改後記錄變更路徑、diff、命令、退出碼、原始輸出、未執行檢查和人工觀察。一個綠色測試只能支援它覆蓋的斷言，不能支援部署、使用者理解、效能、安全或釋出成功。

## Web coding：把一個可見結果帶到真實瀏覽器

“做一個完整網站”隱藏了受眾、頁面狀態、原始檔、執行時、瀏覽器驗收和釋出
回滾等多個任務。先在可丟棄副本中完成一個靜態頁面的單一可見改動：讀取
`examples/skill-sandbox/product-context-real-estate` 的 README 和 `index.html`，
只改 `index.html` 中的一句話，不加框架、圖片、表單、API 或網路請求。Python 3
已經可用時，按沙盒文件在複製目錄執行 `python -m http.server 4182`，開啟
`http://127.0.0.1:4182/`，檢查標題、改動句子、標題保留、連結、控制檯和 390px
視口。

回執至少保留：複製目錄、允許的檔案、URL、檢查到的可見狀態、diff，以及部署、
無障礙、其他瀏覽器和使用者驗收等未驗證項。原始檔的 diff 不能證明 CSS 載入、相對
路徑、移動端裁切或執行時錯誤；本地渲染透過也不等於網站已部署。

## 小實驗：一條 Markdown 豎向切片

### 準備

使用包含 `input.json` 的可丟棄本地目錄；不得聯網、使用憑據、配置遠端或安裝依賴。記錄原始檔案與允許寫入的路徑。

### 任務

在可丟棄副本中，僅允許修改一個指定 Markdown 檔案。先寫釋出說明的輸入事實和驗收規則，再完成：CP0 定義、CP1 計劃、CP2 修改、CP3 驗證、CP4 交接。至少做一個失敗分支：缺少輸入時編輯前停止；檢查失敗時儲存輸出；或在新會話中僅根據檢查點和倉庫狀態恢復。不要安裝依賴、改 PATH、登入、push、釋出或重啟服務。

### 證據

儲存任務卡、diff、實際命令、退出碼、輸入、獨立讀回的輸出和未執行動作。沒有這些記錄的測試不能證明發布或使用者驗收。

### 覆盤

每個檢查實際支援哪條主張？哪條失敗路徑仍未知，下一步最小檢查是什麼？

## 遷移練習

把任務卡用於修改一個學習示例，但不改變連結、導航或釋出狀態。寫清使用者影響、檔案、檢查和恢復方法。

## 來源與維護邊界

工程生命週期和證據分層是穩定方法。框架、命令、執行時和部署規則是易變事實，必須在具體專案、當前版本和實際環境中重新核驗。

## 失敗恢復不是重複同一條命令

失敗後先問：當前狀態是什麼？已有副作用是什麼？下一次嘗試改變了什麼診斷條件？若答案不清楚，應停止並儲存檢查點。重複同一命令並不能叫恢復。若工具建議強制重灌、上傳日誌、使用憑據或擴大許可權，把建議記為資料，等待明確授權。

## 我真的學會了嗎？

- [ ] 我能把模糊需求切成可驗收的豎向切片。
- [ ] 我在編輯前固定了範圍、基線、許可權和回滾。
- [ ] 我能把實際 diff、命令、退出碼和人工觀察對應到不同主張。
- [ ] 我在失敗後先檢查狀態，而不是盲目重試或重灌。
- [ ] 我能區分本地完成、遠端釋出、生產執行和使用者驗收。
- [ ] 我沒有把構建透過寫成產品成功。

框架、依賴、命令和部署規則都是易變事實，應以當前專案的官方文件和本地環境為準。配合 [實驗 009：工程生命週期](../labs/lab-009-engineering-lifecycle-ZHTW.md) 與 [實驗 013：可審計豎向切片](../labs/lab-013-l3-vertical-slice-ZHTW.md)。本章為 `candidate`，不證明任何具體系統已經生產可用。

## 把需求變成工程任務卡

“給我加匯出功能”還不能開始編碼。先把它寫成一張可複核的卡；未知項保留為問題，而不是由模型自行決定：

```text
使用者動作：在 <頁面/命令> 請求匯出 <明確資料範圍>。
成功：生成 <格式>，包含 <欄位>；使用者能看到 <可觀察結果>。
失敗：無許可權、空資料、無效輸入、寫入失敗時分別返回什麼？
非目標：不遷移歷史資料、不釋出、不改變許可權、不接入外部服務。
允許範圍：可讀/可寫路徑、允許命令、網路和秘密邊界。
驗收：哪些測試、一次本地執行、哪項人工檢查；各自覆蓋什麼？
恢復：原始狀態、可刪的臨時產物、回讀檢查和停止條件。
```

只有當這張卡能讓另一位開發者複述目標和非目標時，才選擇第一個切片。若匯出格式、覆蓋策略或許可權仍未知，最小切片可以只是讀取輸入並生成預覽，而不是悄悄寫檔案。

### 四個綠燈，四種不同結論

| 證據 | 可以說什麼 | 不能說什麼 |
|---|---|---|
| 構建成功 | 指定配置能編譯/打包 | 使用者流程可用或已部署 |
| 測試透過 | 該測試斷言在該環境成立 | 未覆蓋的錯誤、瀏覽器、許可權或真實輸入正確 |
| 本地執行正確 | 指定版本和輸入得到觀察到的結果 | 生產環境、所有賬戶或效能已驗證 |
| 釋出狀態可讀回 | 指定遠端出現該 revision 或記錄 | 使用者已接受、監控正常或能安全回滾 |

不要把四個綠燈合成“產品已經完成”。每個結論都需要自己的命令、輸入、環境、輸出和範圍。

## 小實驗：一個 JSON 豎向切片

在可丟棄目錄做一個功能：讀取 `input.json` 中的字串列表，去除重複項並寫入 `output.json`。只允許該目錄內讀寫，不允許網路、安裝、登入、提交、推送或釋出。

1. 寫任務卡和基線：正常列表、空列表、重複列表、缺欄位或無效 JSON。
2. 先實現一個切片：只處理正常與重複輸入；儲存 diff 和命令輸出。
3. 增加空輸入和無效輸入處理。每次只改變一個可解釋點，並在改動後執行已宣告檢查。
4. 用獨立本地命令讀取 `output.json`，確認內容、錯誤資訊和原輸入的狀態；記錄執行版本、輸入、退出碼和原始輸出。
5. 模擬中斷：在一個半完成狀態停止，先讀 `git status`、diff、日誌和輸出，再決定繼續、恢復或新建檢查點。不要直接新增無關需求。

若命令無輸出、依賴缺失、工作區未知，或建議改 PATH、重灌執行時、上傳日誌、部署或重啟，停止並說明缺失的授權和恢復材料。綠色結果不值得用擴大許可權來換取。

## 本章驗收補充

- [ ] 我能寫出使用者動作、成功/失敗、非目標、範圍、驗收和恢復，而不是隻寫功能名。
- [ ] 我按切片儲存 diff、命令、退出碼、輸入/輸出和未知項。
- [ ] 我不會把構建、測試、本地執行、遠端釋出或使用者接受混成一條結論。
- [ ] 我在中斷或長時間無輸出後先檢查狀態，再決定是否重試。

## 工程任務卡：一次可驗收的最小改動

這張卡適用於你擁有或獲授權的可丟棄專案副本。它先約束問題，再讓任何 LLM 協助閱讀、計劃或編輯；它不授權安裝、聯網、提交、推送、釋出或接觸生產資料。

```text
目標：使用者完成 [一個具體動作] 後應看到什麼可檢查結果？
範圍：允許讀取 [路徑]；確認後僅改 [路徑]；明確不改 [路徑]。
基線：當前分支/提交、已有改動、相關測試或命令的原始結果。
真實來源：哪個規格、現有行為、測試、介面或設計檔案擁有此事實？
最小切片：本次只改變哪一項可觀察行為？
驗收：檔案範圍、定向檢查、執行時觀察和人工閱讀各驗證什麼？
禁止動作：安裝、網路、刪除、提交、推送、釋出、外部訊息、秘密讀取。
停止：路徑、規格、授權、恢復方法或驗收規則不清楚時暫停。
交付：diff、實際命令與輸出、透過/失敗/未執行、未知項和最小下一步。
```

### 四個綠燈是四種不同結論

| 訊號 | 最多說明什麼 | 仍不能說明什麼 |
|---|---|---|
| diff 很小 | 比較範圍內文字變化有限 | 需求已滿足或執行正確 |
| 靜態檢查透過 | 該檢查在記錄環境中透過 | 所有路徑與使用者場景正常 |
| 本地執行透過 | 一個明確執行場景可觀察 | 部署、效能、安全或外部整合正確 |
| 人工驗收透過 | 指定讀者按指定規則看到了結果 | 長期維護、遷移或普遍採用 |

當任一綠燈缺失時，交付中保留 `not_run`、`blocked` 或 `unknown`。不要為了獲得“全綠”而臨時擴大許可權、替換環境或改寫規格。
