# 第九章：验证、怀疑与恢复

## 本章要解决的问题

Agent 可以生成一个合理的完成摘要，也可以生成一个事实错误、范围越界或未运行的结果。可靠使用的核心不是相信或不相信，而是针对每种断言安排恰当证据。

## 学习目标

读者完成本章后应当能够：

- 把完成摘要拆成断言，并为每条断言选择最小充分证据；
- 区分错误、未验证、未知、部分完成和已验证；
- 在失败时保留状态、缩小范围、补证或明确停止。

## 现实问题入口

FP-09、FP-10 和 FP-11 分别对应容量中断、命令卡住和越权验证；后续研究中的 FUP-02 和 FUP-05 分别记录了“会话可用但目标工具未注册”和“长时间无事件后报错并自动重试”。它们适合用来练习“恢复控制权”与“证明结果正确”不是同一件事。所有这些 Issue 都是用户对特定环境的报告，本项目没有本地复现，也没有据此确认官方根因；教材只能使用其中可观察的断点和排查动作。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)与[后续研究](../../docs/research/field-problems-follow-up-2026-08-10.md)。

## 1. 断言与证据匹配

| 断言 | 最小证据 |
|---|---|
| 文件已修改 | diff、文件路径或 hash |
| 测试通过 | 实际命令和输出 |
| 应用能运行 | 实际启动和关键路径检查 |
| 页面视觉正确 | 渲染后的浏览器/截图检查 |
| 事实来自官方来源 | 权威链接、访问日期和适用范围 |
| 没有泄露秘密 | 变更扫描、环境检查和范围说明 |
| 对用户有效 | 明确样本、任务和验收反馈 |
| 可以生产使用 | 所有必要门禁和回滚方案 |

### 进入实验 013 前：断言—证据表

进入[实验 013：L3 贯穿式可审计运行](../labs/lab-013-l3-vertical-slice.md)前，把“完成”拆成可核对的行；每行只允许由对应范围内的证据支撑：

```text
assertion: 我要声明什么
scope: 声明适用于哪个文件、命令、运行或环境
evidence: 证据路径、命令输出或人工复核记录
status: verified / partial / unverified / blocked
gap_or_next_check: 缺什么，下一步如何补证
```

不要用同一份 diff 证明测试通过，也不要用登录状态证明外部动作发生。找不到证据时，正确行动是标为 `unverified` 或 `blocked`，保留缺口并进入恢复流程。

## 2. 怀疑驱动检查

对重要决策先写一个短断言，然后把它从自己的推理中抽出来，单独问：

- 哪个前提没有证据？
- 哪个边界条件没有覆盖？
- 哪个结果可能来自 mock、缓存、过时文件或错误环境？
- 如果断言是错的，最先会在哪里暴露？
- 最小的补充检查是什么？

审查的目标不是制造无休止的怀疑，而是让高风险错误在交付前变得便宜。

## 3. 失败恢复顺序

遇到失败时按以下顺序处理：

1. 保留具体错误和当前状态；
2. 判断是输入、理解、环境、实现、权限还是验证问题；
3. 缩小范围并重现；
4. 做一个最小修复或补充检查；
5. 重新验证相关路径；
6. 如果失败仍不清楚，停止并交付清晰的阻塞说明；
7. 只有在证据支持时才扩大权限、范围或重试次数。

不要用“再跑一次”“给更多权限”“让模型再想想”替代诊断。

### 现实边界：每一层“成功”都要单独取证

公开 Issue 中反复出现一种容易误判的序列：工具出现在列表里，页面也能读到，但真正的发现调用、点击或后端能力仍然失败。比如，某 Windows 报告称 Computer Use 与 `node_repl` 可见，却在只读 `list_apps()` / `list_windows()` 启动辅助进程时遇到 `spawn EPERM`；另一份报告称浏览器弹窗和 DOM 可读，但点击因 CDP 超时失败；还有报告称自定义 Provider 接受配置，却不一定支持更高等级的多 Agent 能力。这些都是 2026-08-10 的公开用户报告，不是本项目的本地复现或官方根因结论，详见[网页田野研究](../../docs/research/web-field-problems-2026-08-10.md) WF-08—WF-11。

把能力拆成可观察的断言：

```text
工具/Skill 可见
  → 只读发现调用可执行
  → 目标状态可读
  → 目标动作返回成功
  → 外部状态发生预期变化
```

每向右走一步都要有自己的证据。读取 DOM 不能证明点击成功；配置被解析不能证明后端能力可用；一次启动成功不能证明下一次窗口、版本或账户仍有相同能力。正确恢复动作是记录版本、工作面、目标和错误类别，先做最小低风险对照；条件没有改变时不要重复同一动作。最终交付可以是“读取已验证、提交未验证”或“单 Agent 已验证、多 Agent 未验证”，这比笼统写“工具正常/流程完成”更准确。

### 能力链断点卡：停在最早没有证据的一层

真实排查不从猜根因开始，而从定位“最后一个已通过断言”和“第一个未通过断言”开始。为一次运行保存：

```yaml
run_id: "唯一运行标识"
surface: "实际工作面及版本"
expected_capability: "本次需要的最小能力"
chain:
  - stage: "入口/会话可用"
    observation: "可观察事件或错误"
    status: "passed | failed | not_observed"
  - stage: "工具已注册并可发现"
    observation: "工具列表或只读发现结果"
    status: "passed | failed | not_observed"
  - stage: "目标状态可读"
    observation: "目标、账户、路径或窗口的只读证据"
    status: "passed | failed | not_observed"
  - stage: "目标动作返回"
    observation: "调用结果、退出码或错误类别"
    status: "passed | failed | not_observed"
  - stage: "预期副作用已确认"
    observation: "目标端状态、diff 或回读结果"
    status: "passed | failed | not_observed"
last_confirmed_stage: "最后一个 passed"
first_breakpoint: "第一个 failed 或 not_observed"
safe_next_check: "只改变一个条件的最小检查"
stop_condition: "何时停止而不扩大权限或副作用"
```

如果工具名称可见但只读发现失败，断点就在“工具已注册并可发现”；如果动作返回成功但目标状态没有变化，断点在“预期副作用已确认”。不要跨过断点继续更高风险动作，也不要用后续偶然成功倒填前一层证据。

### 长等待无事件：先记录时间线，再决定恢复

“界面仍在 Working”只是一项状态观察。为长请求至少记录 `request_started_at`、`first_event_at`、每次工具/网络事件、`last_event_at`、中断或错误时间、自动重试开始时间和最终状态。达到运行前约定的无事件阈值时：

1. 把状态标为 `no_event_observed`，不要写成失败根因或任务仍健康；
2. 用已授权方式恢复控制权，并检查进程、工作树、目标端状态和最后 checkpoint；
3. 第一次请求是否产生副作用仍不清楚时，停止为 `unverified` 或 `blocked`；
4. 只有动作幂等、状态已复核，且重试策略在运行前已声明或本次明确改变了一个条件时，才允许一次有限重试；
5. 客户端自动重试也必须作为独立事件保留。重试成功只证明后一次尝试成功，不能把前一次无事件改写成首次通过。

HTTP 状态、长上下文、网络等待、模型推理或上游服务问题可以成为待检假设，但在没有官方确认或本地复现前都不能写成根因。

## 4. 完成状态词汇

- `practice`：用于学习，结果不应被复用为生产结论；
- `candidate`：有潜力，但缺少完整评测或来源审查；
- `verified`：在声明的范围、版本和任务集内有证据；
- `production-ready`：通过项目要求的质量、安全、回滚和维护门禁。

## 实验：完成声明审查

### Setup

准备一份脱敏的完成摘要、diff、测试输出、来源链接和一项故意缺失的证据；不得连接生产服务或修改外部系统。把每条完成声明拆成独立断言，并预先规定状态词汇。

### Task

使用 [实验 003](../labs/lab-003-evidence-review.md)，把一份完成摘要拆成断言表。每项都写清范围、证据、状态和下一步。再故意加入一句无证据的“全部测试通过”，观察审查流程是否拒绝直接采信。

### Evidence

保存断言表、每条断言对应的证据路径、缺口分类、审查决定和恢复/补证计划。至少包含一条事实断言、一条运行断言和一条用户效果断言，并证明它们没有被同一份弱证据覆盖。

### Reflection

说明哪条声明最容易被漂亮摘要掩盖，哪个最小检查能降低风险，以及为什么“未验证”不等于“错误”。写出下一次交付会如何改变状态措辞。

## 本章验收

学习者能为不同类型断言选择不同证据；能区分未验证与错误；能根据错误类型选择恢复动作；能写出一个包含已完成、未完成、未知和风险的诚实交付报告。

## 迁移练习

把断言表用于一份研究结论或营销实验报告。至少加入一条事实断言、一条运行断言和一条用户效果断言，并说明它们不能共享同一份证据。

## 来源与更新提示

完成状态词汇和证据原则是稳定方法；命令、入口和模型行为属于易变事实。使用[评测框架](../../docs/quality/evaluation-framework.md)、[官方基线](../../docs/research/openai-codex-baseline.md)和[网页田野研究](../../docs/research/web-field-problems-2026-08-10.md)复核具体操作。公开 Issue 的版本、页面状态和维护者回复会变化；教材只吸收可迁移的证据纪律，不把单个报告写成产品保证。
