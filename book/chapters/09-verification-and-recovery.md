# 第九章：验证、怀疑与恢复

## 本章要解决的问题

Agent 可以生成一个合理的完成摘要，也可以生成一个事实错误、范围越界或未运行的结果。可靠使用的核心不是相信或不相信，而是针对每种断言安排恰当证据。

## 学习目标

读者完成本章后应当能够：

- 把完成摘要拆成断言，并为每条断言选择最小充分证据；
- 区分错误、未验证、未知、部分完成和已验证；
- 在失败时保留状态、缩小范围、补证或明确停止。

## 现实问题入口

FP-09、FP-10 和 FP-11 分别对应容量中断、命令卡住和越权验证；它们适合用来练习“恢复控制权”与“证明结果正确”不是同一件事。入口：[Codex 真实用户问题现场研究](../../docs/research/field-problems-codex.md)。

## 1. 断言与证据匹配

| 断言 | 最小证据 |
|---|---|
| 文件已修改 | diff、文件路径或 hash |
| 测试通过 | 实际命令和输出 |
| 应用能运行 | 实际启动和关键路径检查 |
| 页面视觉正确 | 渲染后的浏览器/截图检查 |
| 事实来自官方来源 | 权威链接、访问日期和适用范围 |
| 没有泄露秘密 | 变更扫描、环境检查和范围说明 |
| 对用户有效 | 明确样本、任务和验收反馈 |
| 可以生产使用 | 所有必要门禁和回滚方案 |

## 2. 怀疑驱动检查

对重要决策先写一个短断言，然后把它从自己的推理中抽出来，单独问：

- 哪个前提没有证据？
- 哪个边界条件没有覆盖？
- 哪个结果可能来自 mock、缓存、过时文件或错误环境？
- 如果断言是错的，最先会在哪里暴露？
- 最小的补充检查是什么？

审查的目标不是制造无休止的怀疑，而是让高风险错误在交付前变得便宜。

## 3. 失败恢复顺序

遇到失败时按以下顺序处理：

1. 保留具体错误和当前状态；
2. 判断是输入、理解、环境、实现、权限还是验证问题；
3. 缩小范围并重现；
4. 做一个最小修复或补充检查；
5. 重新验证相关路径；
6. 如果失败仍不清楚，停止并交付清晰的阻塞说明；
7. 只有在证据支持时才扩大权限、范围或重试次数。

不要用“再跑一次”“给更多权限”“让模型再想想”替代诊断。

## 4. 完成状态词汇

- `practice`：用于学习，结果不应被复用为生产结论；
- `candidate`：有潜力，但缺少完整评测或来源审查；
- `verified`：在声明的范围、版本和任务集内有证据；
- `production-ready`：通过项目要求的质量、安全、回滚和维护门禁。

## 实验：完成声明审查

### Setup

准备一份脱敏的完成摘要、diff、测试输出、来源链接和一项故意缺失的证据；不得连接生产服务或修改外部系统。把每条完成声明拆成独立断言，并预先规定状态词汇。

### Task

使用 [实验 003](../labs/lab-003-evidence-review.md)，把一份完成摘要拆成断言表。每项都写清范围、证据、状态和下一步。再故意加入一句无证据的“全部测试通过”，观察审查流程是否拒绝直接采信。

### Evidence

保存断言表、每条断言对应的证据路径、缺口分类、审查决定和恢复/补证计划。至少包含一条事实断言、一条运行断言和一条用户效果断言，并证明它们没有被同一份弱证据覆盖。

### Reflection

说明哪条声明最容易被漂亮摘要掩盖，哪个最小检查能降低风险，以及为什么“未验证”不等于“错误”。写出下一次交付会如何改变状态措辞。

## 本章验收

学习者能为不同类型断言选择不同证据；能区分未验证与错误；能根据错误类型选择恢复动作；能写出一个包含已完成、未完成、未知和风险的诚实交付报告。

## 迁移练习

把断言表用于一份研究结论或营销实验报告。至少加入一条事实断言、一条运行断言和一条用户效果断言，并说明它们不能共享同一份证据。

## 来源与更新提示

完成状态词汇和证据原则是稳定方法；命令、入口和模型行为属于易变事实。使用[评测框架](../../docs/quality/evaluation-framework.md)与[官方基线](../../docs/research/openai-codex-baseline.md)复核具体操作。
