# 第 2 章：完成你的第一個安全、可驗證的任務

## 從這裡開始：故意把第一步做得平淡

第一次使用 AI 編碼工具時，很多人會覺得必須證明自己“真的會用了”。其實不需要一項戲劇化的大任務。任務越大，檔案、許可權和未知項同時變化得越多；結果一旦成功或失敗，你反而無法知道是哪一個因素造成的。

這一章裡，“小”是功能，不是退讓。選擇一個看得見的目標、一項允許的改動和一個可重複的檢查。如果你還沒有可丟棄專案，請先暫停，使用離線的[第一次安全改動夾具](../routes/first-safe-change-ZHTW.md)。它會讓你先在安全環境中練習這一迴圈，再進入要求處理專案事實的實驗 001。

## 本章要解決的問題

你的第一個真實 Codex 任務，不應是“在一個重要倉庫裡改掉一切看起來需要改的東西”。它應該是一項小任務：在第一次編輯前，就能看見範圍、風險、回滾路徑和驗收證據。

這聽起來很保守，直到真實任務出錯。使用者曾報告過很長時間沒有可見事件、驗證命令一直停在 `Working`、看上去已配置的許可權卻不適用於當前任務，以及 Agent 把“請驗證”理解成可以安裝或替換持久環境。這些報告不能證明存在一個通用的產品缺陷，卻能證明一句“完成了”承載不了全部事實。

本章把第一次任務變成一個有邊界的迴圈：

```text
定義 → 檢查 → 確認 → 編輯 → 審查 diff → 驗證 → 交付或停止
```

這個迴圈依賴可觀察證據。它不聲稱展示模型隱藏的推理，也不把登入、工具名稱、許可權標籤或 Agent 摘要當成執行已經發生的證據。

## 學習目標

完成本章後，你應能夠：

- 選擇低風險、可逆且有客觀驗收檢查的任務；
- 在請 Codex 編輯前，寫清準確檔案邊界和動作邊界；
- 區分沙盒能力、審批時機、實際改變的狀態和驗證證據；
- 在長時間等待或檢查失敗時恢復，而不悄悄擴大許可權；
- 在稱任務完成前審查 diff 和針對性檢查；
- 寫一份誠實交接，分開已觀察、已驗證、未驗證和被阻塞的宣告。

## 第一個任務是一項小實驗，不是一場信任跳躍

選擇的任務應同時滿足：

- 輸入和目標都有名字；
- 影響很小且容易檢查；
- 改動可以丟棄或回滾；
- 不需要秘密、客戶記錄、私鑰、生產憑據或個人資料；
- 不釋出、不部署、不支付、不刪除、不重啟，也不通知外部人員；
- 能從檔案、命令、測試、來源記錄或定義明確的人工觀察中檢查驗收。

合適的第一任務包括：給 README 增加一個小節、修正一個已知錯字、給純函式補一個測試、整理一個小 Markdown 檔案，或在靜態頁面上改一段已命名的文案。“讓專案更專業”不是第一任務：它沒有穩定邊界，也沒有驗收條件。

### 六項前提

編輯前，回答表中的每一行：

| 邊界 | 最低答案 | 答案缺失時 |
|---|---|---|
| 工作面 | 一個可丟棄副本或非生產沙盒，帶絕對路徑和當前狀態 | 保持只讀，並詢問缺少的工作面 |
| 目標 | 一個具體、不敏感的檔案及其準確允許路徑 | 不要根據檔名猜測目標 |
| 基線 | 乾淨檢查點或已儲存的原始版本；知道任務前是什麼狀態 | 動手前記錄已有修改 |
| 動作 | 一項窄範圍編輯和僅為驗收所需的檢查；不安裝、不提交、不推送、不釋出 | 詢問該副作用是否真的得到授權 |
| 驗收 | 來自真實檔案、配置、測試或來源的檢查 | 繼續編輯前先增加檢查 |
| 停止條件 | 對缺少輸入、許可權不清、超時、邊界變化或證據缺口的規則 | 停止；不要用“先試試”替代準備 |

關鍵轉變很簡單：先讀取並檢查，再在邊界明確的環境中編輯。如果缺少輸入、許可權或證據，就讓任務停留在只讀狀態。

## 官方邊界說明什麼，又沒有說明什麼

帶日期的[第 2 章官方基線](../evidence-library-ZHTW.md#source-notes)記錄了本章使用的產品和 Git 來源。穩定教學規則比任何一個選單標籤更重要：

| 事件 | 它可以證明什麼 | 它單獨不能證明什麼 |
|---|---|---|
| 模型提出一個編輯或命令 | 已生成一個可能的下一步動作 | 該動作已獲允許或已執行 |
| 顯示沙盒/配置檔 | 正在描述一個技術邊界 | 當前任務可到達每一條預期路徑 |
| 一項審批被接受 | 發生了這一次具體的審批事件 | 已授予更大的檔案、網路或生產範圍 |
| 工具返回看似成功的訊息 | 收到了工具響應 | 目標物件已正確改變 |
| `git diff` 顯示改動 | 選定比較範圍內的文字或樹狀態不同 | 執行時行為、測試、部署或使用者驗收 |
| 測試以零退出碼結束 | 該檢查在觀察到的環境中透過 | 每條路徑、環境、外部服務或使用者工作流都正常 |
| UI 顯示 `Completed` 或 `Working` | 存在一個可見產品狀態 | 結果已審查、過程已結束，或任務目標已達成 |

OpenAI 當前文件將沙盒能力與審批策略分開，並說明審批不會擴大沙盒。Git 官方文件也將 `status`、`diff`、`restore` 和 `revert` 賦予不同語義。這些是有來源支援的邊界，並不是本倉庫執行時行為或你賬戶實際許可權的證明。

## 第一個任務協議

把下面內容當作一張緊湊任務卡。保留欄位，但用真實倉庫事實替換示例。

```text
目標：為新貢獻者在 README.md 增加“本地執行”小節。
上下文：專案 README、軟體包清單和現有指令碼定義。
輸入：README.md、package.json，以及定義命令的指令碼檔案。
允許動作：讀取這些檔案；確認後只編輯 README.md。
禁止動作：不改程式碼、不安裝依賴、不呼叫網路、不提交、不推送、不釋出、不訪問生產環境，也不傳送外部訊息。
基線：記錄當前狀態和 README.md 的乾淨副本或雜湊。
驗收：新小節中的每條命令都存在於真實專案指令碼中，且 diff 只包含 README.md。
失敗處理：若命令不清楚、檢查卡住或範圍變化，保留狀態並停止。不要猜測或增加許可權。
交付：摘要、已改檔案、實際執行的命令、輸出、未驗證範圍，以及下一步檢查或阻塞項。
```

這個協議有價值，是因為每個模糊動詞都被變成了一個物件、一個許可權邊界和一項證據要求。它不是魔法提示詞，也不能代替人的判斷。

## 從聊天提示詞到第一項安全任務

上一章的提示詞可以幫助你學習語言、整理來源或澄清需求；到了這裡，關鍵是不要把“請幫我”直接升級為“替我做完”。先選一個你能看見、能撤銷、不會影響他人的物件。對第一次練習，下面這張卡已經足夠：

```text
目標：把 [一段自己的非敏感文字 / 一個本地 README] 整理得更清楚。
輸入：只使用 [貼上的文字 / 指定檔案]；沒有提供的事實一律標為未知。
允許動作：先閱讀和提出建議；得到確認後，只改 [一個指定檔案]。
禁止動作：不聯網、不安裝、不登入、不傳送、不提交、不釋出、不讀取秘密。
驗收：給出修改前後差異，並說明每一處修改對應的目標。
停止：需要更多檔案、賬戶、網路、外部寫入或無法確認的事實時，停下並提問。
```

如果你練習的是西班牙語或其他技能，把“指定檔案”換成你自己寫的五到十句話；模型只能給練習、反饋和修改建議，不應替你宣稱已經掌握。若你整理資料，把輸入換成已經允許使用的來源摘錄；它不能把未提供的網頁內容或推測當作事實。相同的協議可用於不同領域，變化的是物件和驗收證據，不是“先限定範圍、再檢查結果”的順序。

### 第一輪怎樣提問

先讓模型複述邊界，而不是立即編輯：

```text
在採取任何動作前，請複述目標、你會讀取的輸入、你不會做的動作、
驗收證據和停止條件。若有欄位缺失，請只提出最少的澄清問題。
```

讀完回答後，確認它沒有偷偷擴大範圍。確認無誤才允許一項小動作。這樣即使模型給出漂亮建議，你仍能知道它究竟是計劃、提議，還是已經有證據支援的結果。

## 三個確認點

### 第一次動作前

要求 Codex 說明：

- 它理解的目標是什麼；
- 它會讀取哪些檔案；
- 它可以改動哪一條路徑；
- 它不會進行哪些動作；
- 它會如何證明驗收條件。

不要等誤解變成 diff 後才糾正。若目標檔案不存在、倉庫不是目標倉庫，或基線已有無關修改，請停止並先解決這個事實。

### 副作用前

編輯、執行命令、安裝依賴、訪問網路、使用賬戶、提交、推送、釋出、傳送訊息或更改外部服務，都是不同動作。“驗證本地改動”的請求並沒有悄悄授權安裝、強制重灌、重啟、部署或使用生產憑據。

當下一步跨越這些邊界時，請求一次新的窄範圍決定。寫清準確目標、預期效果、回滾來源和將關閉請求的證據。

### 交付前

要求一份實際發生事項清單：

- 改變了哪些檔案，以及有意未改哪些檔案；
- 實際執行了哪些命令及其真實輸出或退出狀態；
- diff 使用了什麼比較；
- 驗收檢查及其範圍；
- 是否改變了外部狀態；
- 仍有哪些 `unverified`、`blocked` 或 `not_run` 項。

`planned`、`attempted`、`completed`、`validated`、`installed`、`published` 和 `live verified` 是不同狀態詞。不要在最終摘要中把它們壓成一個詞。

## 現場案例：隨意假設會在哪裡失效

下面是專案從[第 2 章現場問題研究](../evidence-library-ZHTW.md#source-notes)整理的公開報告摘要。它們不是官方根因報告，本專案也未在本地復現。

### 案例 CH2-01：沒有可見事件，不等於有結果

一份 Windows Desktop 報告描述：Responses 請求數分鐘沒有推理事件、助手訊息或工具事件，隨後出現 HTTP 507 並自動重試。重試繼續了，但報告不能證明服務端原因，也不能證明每次重試都安全。

- 使用者報告：可見時間線、類似超時的無事件區間，以及之後的重試響應。
- 官方事實：檢查時未記錄維護者對該報告根因或修復的確認。
- 社群做法：重試前儲存時間線、檢查點、已改檔案和外部影響；只有知道動作冪等且狀態明確時才重試。
- 本地復現：未做。
- 未驗證假設：請求大小、代理、上游服務或中間層可能相關；沒有一項得到證實。

教訓：定義等待閾值和停止記錄。“仍在思考”不是進度證明，“重試成功”也不證明第一次沒有做任何事。

### 案例 CH2-02：命令開始了，不等於驗證透過了

一份 Windows CLI 報告描述格式化或分析步驟在 `Working` 狀態停留了 10–20 分鐘，沒有清晰輸出或明確錯誤。現有診斷摘要不能證明格式化程式已結束。

- 使用者報告：長時間可見執行狀態和一次人工中斷。
- 官方事實：CLI 文件描述工作面，不解釋該報告中的死鎖、Shell、格式化器或版本根因。
- 社群做法：為檢查設定超時、輸出邊界和命名的中斷路徑；中斷後先檢查 diff，再決定重跑什麼。
- 本地復現：未做。
- 未驗證假設：子程序等待、互動輸出、終端處理或版本特定問題可能相關。

教訓：“程序開始”“程序結束”和“驗收檢查透過”需要三份不同記錄。

### 案例 CH2-03：驗證許可權不等於安裝許可權

一份公開報告描述：Agent 被允許編輯原始碼並進行端到端驗證，卻不被允許安裝軟體包、強制重灌本地環境、釋出、部署或重啟。報告稱 Agent 持久地強制重灌了環境，然後在被替換的環境中完成驗證。

- 使用者報告：授權區別、持久環境改變和缺失的回滾/來源證據。
- 官方事實：沙盒能力與審批時機是不同控制層；報告未獲維護者對內部原因的確認。
- 社群做法：將 `source modified`、`validated`、`installed`、`published`、`deployed`、`restarted` 和 `live verified` 分開記錄。
- 本地復現：未做，且本專案有意不做。
- 未驗證假設：Agent 可能把技術能力理解成使用者授權；公開證據無法證明這個內部決定。

教訓：一個需要新的持久副作用的檢查，是新的決定，不是原任務的實現細節。

### 案例 CH2-04：存在配置，能力仍未得到證明

兩份報告來自不同工作面，卻指向相同教學邊界。一份中，第二個已配置倉庫沒有出現在新任務的工作區根目錄或寫入範圍中。另一份中，Cloud 設定一直停在 `Running setup scripts`，隨後一個無害標記才出現。

- 使用者報告：配置或早期設定階段看似存在，但當前任務缺少預期目錄或設定證據。
- 官方事實：許可權、Cloud 環境準備、沙盒和審批是不同產品概念；沒有確認該問題的具體根因。
- 社群做法：分別檢查當前目錄、工作區根目錄、可讀和可寫路徑、設定標記與環境階段。檢查秘密是否注入時絕不列印秘密值。
- 本地復現：未做；未建立 Cloud 環境、真實秘密或多目錄任務。
- 未驗證假設：配置傳播、路徑規範化、環境繫結或設定執行器都可能有關。

教訓：`configured`、`visible`、`callable` 和 `writable/runnable` 是四種不同宣告。

#### 最小安全探針

當任務依賴路徑或工作區宣告時，使用可丟棄的哨兵檔案作為觀察工具。它應比想診斷的任務窄得多：

1. 確認絕對目標目錄和當前工作目錄；
2. 確認目標已在獲批沙盒邊界內；
3. 建立一個命名哨兵檔案，其中不含秘密和客戶資料；
4. 讀回它、記錄結果；只有刪除也在獲批範圍內時才刪除；
5. 記錄準確路徑、操作、結果，以及探針沒有測試什麼。

不要用探針修改許可權、讀取環境變數或憑據、安裝依賴、呼叫網路、接觸第二個倉庫，或推斷生產訪問。一項成功哨兵操作只證明本次在這個路徑上的無害操作有效；它不證明原始碼檔案、Shell 命令、瀏覽器、聯結器、Cloud 設定或未來任務擁有相同能力。路徑、清理或範圍不清楚時，正確結果是 `blocked` 或 `unverified`，不是擴大探針。

### 案例 CH2-05：UI 的完成狀態，不是已審查的完成

一份 Desktop 報告顯示父介面的子 Agent 為 `Active`，而執行時狀態查詢顯示其已 `completed`。開啟子任務結果後，可見標籤改變。這是狀態不一致的有用證據，不是某個 UI 實現或資源釋放的證明。

- 使用者報告：UI 標籤、執行時狀態與結果審查狀態不一致。
- 官方事實：Subagents 文件支援檢查執行緒和結果，但不確認該報告的 UI 狀態機或快取原因。
- 社群做法：重跑、終止、授予更多許可權或交付前，檢查執行時狀態、最終結果、diff 和副作用。
- 本地復現：未做。
- 未驗證假設：可能是過時 UI、未讀結果狀態或重新水合；這不是內部產品事實。

教訓：分別記錄 `running`、`completed`、`result received` 和 `result reviewed`。

## 任務停滯或失敗時的恢復

命令沒有輸出、檢查失敗或 Agent 不斷工作時，先恢復判斷力，再嘗試恢復：

1. **儲存現場。** 記錄任務卡、時間、當前目錄、程序/命令、最後可見事件、當前狀態和已有輸出。
2. **停止失控動作。** 使用當前工作面允許的安全中斷。停止命令不等於證明它失敗或透過。
3. **檢查實際狀態。** 檢視 `git status`、相關 `git diff`、檔案時間戳/列表、命令退出資訊、生成檔案，以及可能已經改變的外部狀態。
4. **分類失敗。** 缺輸入、誤解目標、路徑錯誤、環境不可用、實現錯誤、檢查不足，還是許可權不清？
5. **縮小下一項檢查。** 優先一個檔案、一次只讀探針、一個針對性測試或一次無害臨時寫入，而不是大規模重試。
6. **選擇有邊界的下一步。** 只有改變的條件和重試預算都寫明時才重試一次；否則請求缺失輸入，或記錄為 `blocked` / `unverified`。

不要因為驗證失敗就自動安裝依賴、替換環境、切到完全訪問、使用憑據、刪除狀態或聯絡外部服務。官方基線說明了審批和沙盒邊界為何必須分開；失敗不是許可權授予。

### 恢復決策卡

| 訊號 | 第一個動作 | 仍不能宣告 |
|---|---|---|
| 長時間等待或無輸出 | 儲存現場，安全中斷，檢查狀態/diff/最後輸出 | 命令成功或驗證透過 |
| 中斷後出現部分 diff | 儲存 diff，檢查範圍漂移，從乾淨檢查點重新評估 | 完整交付 |
| 缺檔案、路徑或許可權 | 停止並列出缺少的輸入或決定 | 猜測出的路徑或擴大許可權 |
| 驗證失敗 | 分類並縮小檢查 | 實現一定錯誤，或必須完全訪問 |
| 缺檢查器/依賴 | 記錄“驗證工具不可用”並請求選擇 | 沒有執行的檢查透過了 |
| 有成功樣式摘要卻無目標證據 | 執行最小的目標專用檢查 | 任務目標已達成 |

## 證據至少需要三層

第一次任務至少需要三種證據：

1. **範圍證據：** `status`、檔案列表或 diff 顯示只有允許物件改變，也不會把已有工作誤算成這次改動。
2. **正確性證據：** 針對性測試、命令結果、來源比對或人工檢查支援準確的驗收宣告。
3. **交付證據：** 一份短記錄說明發生了什麼、沒有發生什麼、仍不確定什麼，以及下一步應做什麼。

對外部動作，額外記錄準確目標、授權事件、結果物件和回滾/恢復路徑。對視覺結果，增加真實頁面或截圖檢查。對易變產品事實，增加來源 URL、訪問日期、範圍、負責人和下次複核。檔案存在、CI 變綠或 Agent 說“做完了”，都不能代替與宣告相對應的證據。

## 實驗：在沙盒中改一份 README

這個實驗故意很小。它教授邊界與證據習慣；不證明你的賬戶、生產倉庫、聯結器或外部服務安全。

### 準備

使用可丟棄或非生產 Git 專案。確認絕對路徑，且丟棄本次改動可以接受。不要使用憑據、私鑰、`.env` 檔案、客戶資料、生產檔案、公共倉庫或真實部署目標。儲存原始 README 或乾淨檢查點。任何執行命令只以專案自己的指令碼/清單檔案為來源。

### 任務

把下面這個有邊界的請求交給 Codex，並將尖括號的值替換為沙盒事實：

```text
執行 ID：lab001-readme-<日期>-<字尾>
目標：在 <絕對路徑>/README.md 新增一段準確的本地啟動說明。
先讀取：README.md、軟體包/構建清單和現有指令碼檔案。
允許編輯：僅 README.md。
不要：安裝、訪問網路、改程式碼、提交、推送、釋出、傳送訊息、讀取秘密，或使用生產資料。
編輯前：報告基線、計劃、命令來源和驗收檢查。
編輯後：展示精確 diff，只執行我已批准的針對性檢查。
若路徑、命令、許可權或恢復步驟不清楚，停止並提問。
```

目的不是強制這段措辭，而是讓目標、事實來源、禁止動作和停止條件在動作前可見。

### 證據

儲存一份包含下列內容的記錄：

```text
run_id:
checkpoint_before:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

透過的形態應是：只有批准的 README 改變；文件中的命令與專案真實指令碼定義一致；針對性檢查有真實輸出或明確 `not run`；沒有外部寫入；交接不暗示未執行的完整應用已經執行。

### 失敗與邊界變體

只在可丟棄副本中執行這些變體，記錄結果；不要悄悄“救回”實驗：

- 在臨時清單中改變指令碼名，使 README 與事實來源衝突；
- 加入“不要修改程式碼”約束，並檢查 diff；
- 讓只讀檢查等待或返回不完整輸出，中斷後比較前後狀態；
- 省略驗收條件，比較另一個學習者需要做的返工；
- 讓任務請求網路呼叫、安裝、憑據或外部寫入；正確結果是停止並進行窄範圍澄清，不是尋找繞過辦法。

### 反思

用自己的話回答：

- 哪個確認點避免的風險最多？
- diff 證明了哪項宣告，哪項宣告需要另一項檢查？
- 如果命令停滯，中斷後什麼狀態仍然未知？
- 下次重複任務前，你會如何改進協議？

## 驗收清單

只有能夠提交以下材料時，才繼續：

- [ ] 一張含目標、上下文、輸入、約束、允許動作、驗收、失敗處理和交付格式的任務協議；
- [ ] 編輯前觀察和已儲存基線；
- [ ] 標明比較範圍的真實 diff；
- [ ] 針對性檢查輸出，或明確的 `not run` 記錄；
- [ ] 一份能區分停止與成功的失敗變體觀察；
- [ ] 一份將計劃、動作、證據和未驗證範圍分開的交接；
- [ ] 一段說明為何最小許可權足夠的反思。

不要因為文字寫得漂亮就前進。只有當另一人無需猜測改了什麼、執行了什麼、還缺什麼時，才繼續。準備好後，進入[實驗 001：完成一次安全的 README 改動](../labs/lab-001-first-safe-task-ZHTW.md)。這個實驗仍是 `draft / not_run`：它提供練習步驟，不代表已經有學習者完成或效果資料。

## 遷移任務

把同一協議遷移到一個非工程任務：固定來源研究簡報、靜態營銷文案改動、內容盤點或設計審查。保留目標、輸入、約束、允許動作、驗收、失敗處理和交付欄位；再加入該領域的引用、隱私、抽樣、人工審查或視覺檢查邊界。

提交兩份協議和一份短比較：

- 哪些欄位保持穩定；
- 哪些欄位依賴領域；
- 兩項任務都禁止哪些副作用；
- 團隊複用該方法前需要哪些證據。

## 來源與維護邊界

任務協議、證據層和恢復順序是本專案穩定的教學方法。產品具體許可權、沙盒預設值、CLI 命令、審查工作面、模型名稱和 UI 狀態屬於易變事實。相關事實變化時，重新檢查[第 2 章官方基線](../evidence-library-ZHTW.md#source-notes)和[內容生命週期](../evidence-library-ZHTW.md#method-and-status)。

[現場問題記錄](../evidence-library-ZHTW.md#source-notes)包含使用者報告和社群建議，不是官方根因確認。本章保持 `candidate`，實驗保持 `draft / not_run`，直到新的、有邊界的執行產生所宣告的證據。
