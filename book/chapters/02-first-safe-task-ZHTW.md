# 第 2 章：完成你的第一個安全、可驗證的任務

## 從這裡開始：故意把第一步做得平淡

第一次使用 AI 編碼工具時，很多人會覺得得先完成一項大任務，才能證明自己「真的會用了」。其實不用一開始就挑戰大任務。任務越大，檔案、權限和未知因素同時變化得越多；結果一旦成功或失敗，你反而很難判斷究竟是哪一個因素造成的。

這一章裡，「小」是刻意的設計，不是退讓。選擇一個看得見的目標、一項獲准的變更和一個可重複的檢查。如果你還沒有可丟棄的專案，請先暫停，使用離線的[第一次安全改動夾具](../routes/first-safe-change-ZHTW.md)。它會讓你先在安全環境中練習這個循環，再進入要求處理專案事實的實驗 001。

## 本章要解決的問題

你的第一個真實 Codex 任務，不應是「在一個重要儲存庫裡，把所有看起來需要改的東西一次改完」。它應該是一項小任務：在第一次編輯前，就能看見範圍、風險、復原路徑和驗收證據。

這聽起來很保守，直到真實任務出了問題。使用者曾報告過很長時間沒有可見事件、驗證命令一直停在 `Working`、看似已設定的權限卻不適用於目前的任務，以及 Agent 把「請驗證」理解成可以安裝軟體或替換持久化環境。這些報告不能證明存在一個通用的產品缺陷，卻能說明一句「完成了」無法涵蓋全部事實。

本章把第一次任務變成一個有邊界的迴圈：

```text
定義 → 檢查 → 確認 → 編輯 → 審查 diff → 驗證 → 交付或停止
```

這個循環依賴可觀察的證據。它不聲稱展示模型隱藏的推理，也不把登入狀態、工具名稱、權限標籤或 Agent 摘要當成動作已經執行的證據。

## 學習目標

完成本章後，你應能夠：

- 選擇低風險、可逆且有客觀驗收檢查的任務；
- 在請 Codex 編輯前，寫清楚準確的檔案邊界和動作邊界；
- 區分沙盒能力、審批時機、實際改變的狀態和驗證證據；
- 在長時間等待或檢查失敗時恢復，而不悄悄擴大權限；
- 在稱任務完成前審查 diff 和針對性檢查；
- 寫一份誠實的交接，分開已觀察、已驗證、未驗證和受阻的宣告。

## 第一個任務是一項小實驗，不是一場信任跳躍

選擇的任務應同時滿足：

- 輸入和目標都有名字；
- 影響很小且容易檢查；
- 變更可以丟棄或復原；
- 不需要秘密、客戶記錄、私鑰、生產憑據或個人資料；
- 不釋出、不部署、不支付、不刪除、不重啟，也不通知外部人員；
- 能從檔案、命令、測試、來源記錄或定義明確的人工觀察中檢查是否達到驗收條件。

合適的第一項任務包括：在 README 新增一個小節、修正一個已知錯字、為純函式補上一項測試、整理一個小型 Markdown 檔案，或修改靜態頁面上一段已指定的文案。「讓專案更專業」不是第一項任務：它沒有穩定的範圍，也沒有驗收條件。

### 六項前提

編輯前，回答表中的每一行：

| 邊界 | 最低答案 | 答案缺失時 |
|---|---|---|
| 操作環境（實際工作的地方） | 一個可丟棄的副本或非生產沙盒，帶有絕對路徑和目前狀態 | 保持唯讀，並詢問缺少的操作環境資訊 |
| 目標 | 一個具體、不敏感的檔案及其準確允許路徑 | 不要根據檔名猜測目標 |
| 基線 | 乾淨檢查點或已儲存的原始版本；知道任務前是什麼狀態 | 動手前記錄已有修改 |
| 動作 | 一項窄範圍編輯，以及僅為驗收所需的檢查；不安裝、不提交、不推送、不釋出 | 詢問該副作用是否真的獲得授權 |
| 驗收 | 來自真實檔案、設定、測試或來源的檢查 | 繼續編輯前先增加檢查 |
| 停止條件 | 對缺少輸入、權限不清、超時、邊界變化或證據缺口的規則 | 停止；不要用「先試試」代替準備 |

關鍵轉變很簡單：先讀取並檢查，再在邊界明確的環境中編輯。如果缺少輸入、權限或證據，就讓任務停留在唯讀狀態。

## 官方邊界說明什麼，又沒有說明什麼

帶日期的[第 2 章官方基線](../evidence-library-ZHTW.md#source-notes)記錄了本章使用的產品和 Git 來源。穩定教學規則比任何一個選單標籤更重要：

| 事件 | 它可以證明什麼 | 它單獨不能證明什麼 |
|---|---|---|
| 模型提出一個編輯或命令 | 已生成一個可能的下一步動作 | 該動作已獲允許或已執行 |
| 顯示沙盒/設定檔 | 正在描述一個技術邊界 | 目前任務可到達每一條預期路徑 |
| 一項審批被接受 | 發生了這一次具體的審批事件 | 已授予更大的檔案、網路或生產範圍 |
| 工具回傳看似成功的訊息 | 收到了工具回應 | 目標物件已正確改變 |
| `git diff` 顯示改動 | 選定比較範圍內的文字或樹狀態不同 | 執行時行為、測試、部署或使用者驗收 |
| 測試以零退出碼結束 | 該檢查在觀察到的環境中通過 | 每條路徑、環境、外部服務或使用者流程都正常 |
| UI 顯示 `Completed` 或 `Working` | 存在一個可見產品狀態 | 結果已審查、過程已結束，或任務目標已達成 |

OpenAI 目前的文件將沙盒能力與審批策略分開，並說明審批不會擴大沙盒。Git 官方文件也賦予 `status`、`diff`、`restore` 和 `revert` 不同的語意。這些是有來源支援的邊界，並不是本儲存庫執行時行為或你帳戶實際權限的證明。

## 第一個任務協議

把下面內容當作一張緊湊任務卡。保留欄位，但用真實倉庫事實替換示例。

```text
目標：為新貢獻者在 README.md 新增「本機執行」小節。
上下文：專案 README、套件清單和現有指令碼定義。
輸入：README.md、package.json，以及定義命令的指令碼檔案。
允許動作：讀取這些檔案；確認後只編輯 README.md。
禁止動作：不改程式碼、不安裝相依套件、不呼叫網路、不提交、不推送、不釋出、不存取正式環境，也不傳送外部訊息。
基線：記錄目前狀態和 README.md 的乾淨副本或雜湊值。
驗收：新小節中的每條命令都存在於真實專案指令碼中，且 diff 只包含 README.md。
失敗處理：若命令不清楚、檢查卡住或範圍變化，保留狀態並停止。不要猜測或增加權限。
交付：摘要、已改檔案、實際執行的命令、輸出、未驗證範圍，以及下一步檢查或阻塞項。
```

這個協議有價值，是因為每個模糊動詞都被轉成一個物件、一個權限邊界和一項證據要求。它不是魔法提示詞，也不能代替人的判斷。

## 從聊天提示詞到第一項安全任務

上一章的提示詞可以幫助你學習語言、整理來源或釐清需求；到了這裡，關鍵是不要把「請幫我」直接升級成「替我做完」。先選一個你看得見、能復原、又不會影響他人的物件。對第一次練習，下面這張卡就夠了：

```text
目標：把 [一段自己的非敏感文字 / 一個本機 README] 整理得更清楚。
輸入：只使用 [貼上的文字 / 指定檔案]；沒有提供的事實一律標為未知。
允許動作：先閱讀和提出建議；得到確認後，只改 [一個指定檔案]。
禁止動作：不聯網、不安裝、不登入、不傳送、不提交、不釋出、不讀取秘密。
驗收：給出修改前後差異，並說明每一處修改對應的目標。
停止：需要更多檔案、帳戶、網路、外部寫入或無法確認的事實時，停下來提問。
```

如果你練習的是西班牙語或其他技能，把「指定檔案」換成你自己寫的五到十句話；模型只能提供練習、回饋和修改建議，不應替你宣稱已經掌握。若你整理資料，把輸入換成已獲准使用的來源摘錄；它不能把未提供的網頁內容或推測當成事實。相同的協議可用於不同領域，改變的是物件和驗收證據，不是「先限定範圍，再檢查結果」的順序。

### 第一輪怎樣提問

先讓模型複述邊界，而不是立即編輯：

```text
在採取任何動作前，請複述目標、你會讀取的輸入、你不會做的動作、
驗收證據和停止條件。若有欄位缺失，請只提出最少的澄清問題。
```

讀完回答後，確認它沒有偷偷擴大範圍。確認無誤才允許一項小動作。這樣即使模型給出漂亮建議，你仍能知道它究竟是計劃、提議，還是已經有證據支援的結果。

## 三個確認點

### 第一次動作前

要求 Codex 說明：

- 它理解的目標是什麼；
- 它會讀取哪些檔案；
- 它可以改動哪一條路徑；
- 它不會進行哪些動作；
- 它會如何證明驗收條件。

不要等誤解變成 diff 後才糾正。若目標檔案不存在、倉庫不是目標倉庫，或基線已有無關修改，請停止並先解決這個事實。

### 副作用前

編輯、執行命令、安裝相依套件、存取網路、使用帳戶、提交、推送、釋出、傳送訊息或變更外部服務，都是不同的動作。「驗證本機變更」的請求，並沒有悄悄授權安裝、強制重灌、重啟、部署或使用正式環境憑證。

當下一步跨越這些邊界時，請求一次新的窄範圍決定。寫清楚準確目標、預期效果、復原來源和結束請求所需的證據。

### 交付前

要求一份實際發生事項清單：

- 改變了哪些檔案，以及有意未改哪些檔案；
- 實際執行了哪些命令及其真實輸出或退出狀態；
- diff 使用了什麼比較；
- 驗收檢查及其範圍；
- 是否改變了外部狀態；
- 仍有哪些 `unverified`、`blocked` 或 `not_run` 項。

`planned`、`attempted`、`completed`、`validated`、`installed`、`published` 和 `live verified` 是不同狀態詞。不要在最終摘要中把它們壓成一個詞。

## 現場案例：隨意假設會在哪裡失效

下面是專案從[第 2 章現場問題研究](../evidence-library-ZHTW.md#source-notes)整理的公開報告摘要。它們不是官方根因報告，本專案也未在本機重現。

### 案例 CH2-01：沒有可見事件，不等於有結果

一份 Windows Desktop 報告描述：Responses 請求數分鐘沒有推理事件、助手訊息或工具事件，隨後出現 HTTP 507 並自動重試。重試繼續了，但報告不能證明服務端原因，也不能證明每次重試都安全。

- 使用者報告：可見時間線、類似逾時的無事件區間，以及之後的重試回應。
- 官方事實：檢查時未記錄維護者對該報告根因或修復的確認。
- 社群做法：重試前儲存時間線、檢查點、已改檔案和外部影響；只有知道動作冪等且狀態明確時才重試。
- 本機重現：未做。
- 未驗證假設：請求大小、代理、上游服務或中間層可能相關；沒有一項得到證實。

教訓：定義等待閾值並記錄停止點。「仍在思考」不是進度證明，「重試成功」也不代表第一次沒有做任何事。

### 案例 CH2-02：命令開始了，不等於驗證通過了

一份 Windows CLI 報告描述格式化或分析步驟在 `Working` 狀態停留了 10–20 分鐘，沒有清晰輸出或明確錯誤。現有診斷摘要不能證明格式化程式已結束。

- 使用者報告：長時間可見執行狀態和一次人工中斷。
- 官方事實：CLI 文件描述操作環境，不解釋該報告中的死鎖、Shell、格式化器或版本根因。
- 社群做法：為檢查設定超時、輸出邊界和命名的中斷路徑；中斷後先檢查 diff，再決定重跑什麼。
- 本機重現：未做。
- 未驗證假設：子程序等待、互動輸出、終端處理或版本特定問題可能相關。

教訓：「程序開始」「程序結束」和「驗收檢查通過」需要三份不同的記錄。

### 案例 CH2-03：驗證權限不等於安裝權限

一份公開報告描述：Agent 被允許編輯原始碼並進行端對端驗證，卻不被允許安裝套件、強制重灌本機環境、釋出、部署或重啟。報告稱 Agent 持久地強制重灌了環境，然後在被替換的環境中完成驗證。

- 使用者報告：授權區別、持久環境變更，以及缺少復原與來源證據。
- 官方事實：沙盒能力與審批時機是不同控制層；報告未獲維護者對內部原因的確認。
- 社群做法：將 `source modified`、`validated`、`installed`、`published`、`deployed`、`restarted` 和 `live verified` 分開記錄。
- 本機重現：未做，而且本專案有意不做。
- 未驗證假設：Agent 可能把技術能力理解成使用者授權；公開證據無法證明這個內部決定。

教訓：一個需要新的持久副作用的檢查，是新的決定，不是原任務的實現細節。

### 案例 CH2-04：已有設定，能力仍未得到證明

兩份報告來自不同操作環境，卻指向相同的教學邊界。一份中，第二個已設定的儲存庫沒有出現在新任務的工作區根目錄或寫入範圍中。另一份中，Cloud 設定一直停在 `Running setup scripts`，隨後一個無害標記才出現。

- 使用者報告：設定或早期設定階段看似存在，但目前任務缺少預期目錄或設定證據。
- 官方事實：權限、Cloud 環境準備、沙盒和審批是不同的產品概念；沒有確認該問題的具體根因。
- 社群做法：分別檢查目前目錄、工作區根目錄、可讀和可寫路徑、設定標記與環境階段。檢查是否注入秘密時，絕不列印秘密值。
- 本機重現：未做；未建立 Cloud 環境、真實秘密或多目錄任務。
- 未驗證假設：設定傳遞、路徑規範化、環境繫結或設定執行器都可能有關。

教訓：`configured`、`visible`、`callable` 和 `writable/runnable` 是四種不同宣告。

#### 最小安全探針

當任務依賴路徑或工作區聲明時，可以使用可丟棄的哨兵檔案作為觀察工具。它應比想診斷的任務窄得多：

1. 確認絕對目標目錄和目前工作目錄；
2. 確認目標已在獲批沙盒邊界內；
3. 建立一個命名哨兵檔案，其中不含秘密和客戶資料；
 4. 重新查看它並記錄結果；只有刪除也在獲批範圍內時才刪除；
5. 記錄準確路徑、操作、結果，以及探針沒有測試什麼。

不要用探針修改權限、讀取環境變數或憑證、安裝相依套件、呼叫網路、接觸第二個儲存庫，或推斷正式環境的存取權。一項成功的哨兵操作，只證明這次在這個路徑上的無害操作有效；它不證明原始碼檔案、Shell 命令、瀏覽器、連接器、Cloud 設定或未來任務擁有相同能力。路徑、清理或範圍不清楚時，正確結果是 `blocked` 或 `unverified`，不是擴大探針。

### 案例 CH2-05：UI 的完成狀態，不是已審查的完成

一份 Desktop 報告顯示父介面的子 Agent 為 `Active`，而執行時狀態查詢顯示其已 `completed`。開啟子任務結果後，可見標籤改變。這是狀態不一致的有用證據，不是某個 UI 實現或資源釋放的證明。

- 使用者報告：UI 標籤、執行時狀態與結果審查狀態不一致。
- 官方事實：Subagents 文件支援檢查執行緒和結果，但不確認該報告的 UI 狀態機或快取原因。
- 社群做法：重跑、終止、授予更多權限或交付前，檢查執行時狀態、最終結果、diff 和副作用。
- 本機重現：未做。
- 未驗證假設：可能是過時 UI、未讀結果狀態或重新水合；這不是內部產品事實。

教訓：分別記錄 `running`、`completed`、`result received` 和 `result reviewed`。

## 任務停滯或失敗時的恢復

命令沒有輸出、檢查失敗或 Agent 不斷工作時，先恢復判斷力，再嘗試恢復：

1. **儲存現場。** 記錄任務卡、時間、目前目錄、程序/命令、最後可見事件、目前狀態和已有輸出。
2. **停止失控動作。** 使用目前操作環境允許的安全中斷。停止命令不等於證明它失敗或通過。
3. **檢查實際狀態。** 檢視 `git status`、相關 `git diff`、檔案時間戳/列表、命令退出資訊、生成檔案，以及可能已經改變的外部狀態。
4. **分類失敗。** 缺輸入、誤解目標、路徑錯誤、環境不可用、實作錯誤、檢查不足，還是權限不清？
5. **縮小下一項檢查。** 優先一個檔案、一次唯讀探針、一個針對性測試或一次無害的臨時寫入，而不是大規模重試。
6. **選擇有邊界的下一步。** 只有改變的條件和重試預算都寫明時才重試一次；否則請求缺失輸入，或記錄為 `blocked` / `unverified`。

不要因為驗證失敗就自動安裝相依套件、替換環境、切換到完整存取權限、使用憑證、刪除狀態或聯絡外部服務。官方基線說明了審批和沙盒邊界為何必須分開；失敗不是權限授予。

### 恢復決策卡

| 訊號 | 第一個動作 | 仍不能宣告 |
|---|---|---|
| 長時間等待或無輸出 | 儲存現場，安全中斷，檢查狀態/diff/最後輸出 | 命令成功或驗證通過 |
| 中斷後出現部分 diff | 儲存 diff，檢查範圍漂移，從乾淨檢查點重新評估 | 完整交付 |
| 缺檔案、路徑或權限 | 停止並列出缺少的輸入或決定 | 猜測出的路徑或擴大權限 |
| 驗證失敗 | 分類並縮小檢查 | 實作一定錯誤，或必須完整存取 |
| 缺檢查器/相依套件 | 記錄「驗證工具不可用」並請求選擇 | 沒有執行的檢查通過了 |
| 有成功樣式摘要卻無目標證據 | 執行最小的目標專用檢查 | 任務目標已達成 |

## 證據至少需要三層

第一次任務至少需要三種證據：

1. **範圍證據：** `status`、檔案列表或 diff 顯示只有允許物件改變，也不會把已有工作誤算成這次改動。
2. **正確性證據：** 針對性測試、命令結果、來源比對或人工檢查支援準確的驗收宣告。
3. **交付證據：** 一份短記錄說明發生了什麼、沒有發生什麼、仍不確定什麼，以及下一步應做什麼。

對外部動作，額外記錄準確目標、授權事件、結果物件和復原路徑。對視覺結果，增加真實頁面或截圖檢查。對易變產品事實，增加來源 URL、存取日期、範圍、負責人和下次複核。檔案存在、CI 變綠或 Agent 說「做完了」，都不能代替與聲明相對應的證據。

## 實驗：在沙盒中改一份 README

這個實驗故意很小。它教你建立邊界與證據習慣；不證明你的帳戶、正式儲存庫、連接器或外部服務安全。

### 準備

使用可丟棄或非生產 Git 專案。確認絕對路徑，且可以接受丟棄本次變更。不要使用憑證、私鑰、`.env` 檔案、客戶資料、正式檔案、公開儲存庫或真實部署目標。儲存原始 README 或乾淨檢查點。任何執行命令都只能以專案自己的指令碼/清單檔案為來源。

### 任務

把下面這個有邊界的請求交給 Codex，並將尖括號的值替換為沙盒事實：

```text
執行 ID：lab001-readme-<日期>-<字尾>
目標：在 <絕對路徑>/README.md 新增一段準確的本機啟動說明。
先讀取：README.md、套件/建置清單和現有指令碼檔案。
允許編輯：僅 README.md。
不要：安裝、存取網路、改程式碼、提交、推送、釋出、傳送訊息、讀取秘密，或使用正式資料。
編輯前：報告基線、計劃、命令來源和驗收檢查。
編輯後：展示精確 diff，只執行我已批准的針對性檢查。
若路徑、命令、權限或復原步驟不清楚，停止並提問。
```

目的不是強制這段措辭，而是讓目標、事實來源、禁止動作和停止條件在動作前可見。

### 證據

儲存一份包含下列內容的記錄：

```text
run_id:
checkpoint_before:
scope:
inputs_read:
assumptions:
actions_done:
actions_not_done:
diff_scope:
verification_command:
verification_result:
unverified:
blocked_on:
next_check:
permission_boundary:
status: passed | failed | stopped
```

通過的形態應是：只有獲准的 README 變更；文件中的命令與專案真實指令碼定義一致；針對性檢查有真實輸出或明確的 `not run`；沒有外部寫入；交接不暗示未執行的完整應用已經執行。

### 失敗與邊界變體

只在可丟棄副本中執行這些變體，記錄結果；不要悄悄「救回」實驗：

- 在臨時清單中改變指令碼名，使 README 與事實來源衝突；
- 加入「不要修改程式碼」的約束，並檢查 diff；
- 讓唯讀檢查等待或回傳不完整輸出，中斷後比較前後狀態；
- 省略驗收條件，比較另一個學習者需要做的返工；
- 讓任務請求網路呼叫、安裝、憑據或外部寫入；正確結果是停止並進行窄範圍澄清，不是尋找繞過辦法。

### 反思

用自己的話回答：

- 哪個確認點避免的風險最多？
- diff 證明了哪項宣告，哪項宣告需要另一項檢查？
- 如果命令停滯，中斷後什麼狀態仍然未知？
- 下次重複任務前，你會如何改進協議？

## 驗收清單

只有能夠提交以下材料時，才繼續：

- [ ] 一張含目標、上下文、輸入、約束、允許動作、驗收、失敗處理和交付格式的任務協議；
- [ ] 編輯前觀察和已儲存基線；
- [ ] 標明比較範圍的真實 diff；
- [ ] 針對性檢查輸出，或明確的 `not run` 記錄；
- [ ] 一份能區分停止與成功的失敗變體觀察；
- [ ] 一份將計劃、動作、證據和未驗證範圍分開的交接；
- [ ] 一段說明為何最小權限足夠的反思。

不要因為文字寫得漂亮就前進。只有當另一人無需猜測改了什麼、執行了什麼、還缺什麼時，才繼續。準備好後，進入[實驗 001：完成一次安全的 README 改動](../labs/lab-001-first-safe-task-ZHTW.md)。這個實驗仍是 `draft / not_run`：它提供練習步驟，不代表已有學習者完成或具有效果資料。

## 遷移任務

把同一協議遷移到一個非工程任務：固定來源研究簡報、靜態營銷文案改動、內容盤點或設計審查。保留目標、輸入、約束、允許動作、驗收、失敗處理和交付欄位；再加入該領域的引用、隱私、抽樣、人工審查或視覺檢查邊界。

提交兩份協議和一份短比較：

- 哪些欄位保持穩定；
- 哪些欄位依賴領域；
- 兩項任務都禁止哪些副作用；
- 團隊複用該方法前需要哪些證據。

## 來源與維護邊界

任務協議、證據層和復原順序是本專案穩定的教學方法。產品具體權限、沙盒預設值、CLI 命令、審查操作環境、模型名稱和 UI 狀態屬於易變事實。相關事實變化時，重新檢查[第 2 章官方基線](../evidence-library-ZHTW.md#source-notes)和[內容生命週期](../evidence-library-ZHTW.md#method-and-status)。

[現場問題記錄](../evidence-library-ZHTW.md#source-notes)包含使用者報告和社群建議，不是官方根因確認。本章保持 `candidate`，實驗保持 `draft / not_run`，直到新的、有邊界的執行產生所宣告的證據。
