# 第 11 章：設計一個真正有用的 Skill

**狀態：** `candidate`

**實驗狀態：** `not_run`
**譯文邊界：** 本章提供繁體中文的候選閱讀與練習路徑，尚未經過獨立中文審校，也尚未由真實學習者實際使用。檔案、連結與練習結構存在，不等於翻譯品質、學習效果或 Skill 的執行行為已經驗證。

## 本章要解決的問題

Skill 的價值不在於篇幅、術語或目錄數量，而在於它能否在一類真實任務中減少遺漏、提高一致性、守住邊界，並留下更好的證據。只會重複通用常識的 Skill 會消耗上下文；沒有觸發邊界、失敗處理和驗收契約的 Skill，則會把不穩定的個人習慣包裝成「自動化」。

本章把 Skill 當作可重複使用的方法包來設計：它描述適用範圍、輸入檢查、決策點、允許的動作、停止條件和輸出證據，但不替使用者決定這次任務的具體目標。

## 學習目標

讀者完成本章後應當能夠：

- 為 Skill 寫出清楚的觸發條件、不適用範圍和輸入契約；
- 從一次成功流程中提煉真正可複用的判斷，而不是堆疊通用知識；
- 用漸進披露組織 `SKILL.md`、references、scripts 和 assets；
- 為秘密、外部內容、權限、失敗和停止寫出可執行的邊界；
- 用正例、邊界例、失敗例和遷移例評估 Skill 的價值，並區分發現、呼叫、載入和驗證。

## 現實問題入口

[FP-06](../evidence-library-ZHTW.md#source-notes)記錄了普通檔案與 symlink 在發現行為上的使用者報告；[FP-07](../evidence-library-ZHTW.md#source-notes)記錄了明確呼叫與隱式可見清單混淆的報告。兩筆記錄都沒有官方確認或本機重現，不能當成所有版本的固定行為；它們提醒我們：Skill 目錄裡「有一個檔案」，不等於執行期間已經發現、解析、觸發、載入並驗證它。

### 發現是獨立階段

`SKILL.md` 出現在目錄中，只能證明檔案位於那個位置。讀者應分別記錄：目前工作面是否看得到它、任務是否選取它、入口是否真的載入、步驟是否實際執行，以及產物是否通過驗收。任何一層缺少觀察，都應標為 `unknown`；不要用「已經接上」概括整個過程。

### 「已連線」不等於「可呼叫」

連接器、外掛程式或工作區設定可能讓某項能力出現在介面中，但不會自動提供這次任務所需的檔案、網路、帳號或發布權限。第一次採用 Skill 時，先用不含敏感資料的正例記錄宿主、版本、路徑、輸入、實際選擇和輸出；把尚未觀察到的層寫進回執，不要把設定截圖當成執行證據。

### 先寫契約，再寫說明文字

#### 最小契約

在寫長篇說明前，先讓第一次接觸它的讀者能回答：誰維護它、何時複核、填補什麼缺口、何時觸發、何時應該讓出處理權、需要哪些輸入、允許和禁止哪些動作、交付什麼、何時停止。若其中任何一項只能回答「看情況」，Skill 就還沒有可審查的邊界。

#### 欄位如何互相約束

`purpose` 說明一類明確判斷；`trigger` 必須同時依賴任務意圖和完整輸入；`non_trigger` 保護相鄰方法；`allowed_actions` 不得超出這次任務授予的權限；`output` 必須能按驗收規則檢查；`stop_when` 則把來源、權限、復原路徑或關鍵欄位的缺失變成明確的停止點。description 不是宣傳語，更不能把「提高效率」或「自動安全」寫成無法測量的承諾。

#### 任務協議不能被 Skill 吞掉

Skill 提供的是一類任務的方法；這次的任務協議決定具體物件、時間、受眾、授權和驗收方式。使用者的要求與 Skill 建議衝突時，應說明差異並請使用者決定。Skill 不能藉「最佳實務」默默擴大讀寫範圍、連線網路、安裝、提交或發布。

### 觸發與不觸發

#### 實用觸發測試

依序確認：這是否真是該方法負責的任務？目標、基線和驗收條件是否已給出？允許的動作是否足以完成最低限度的檢查？風險是否仍在目前授權範圍內？任何一個答案為否時，就提出一個澄清問題、交給更合適的方法，或停止。關鍵詞重疊從來不是充分條件。

#### 不觸發也是產品的一部分

「不處理什麼」同樣是產品設計的一部分，能保護使用者的注意力和權限。例如，本機連結審查不應接管文案改寫、遠端網站檢查、整個儲存庫的修復或未知目錄任務。清楚的不觸發規則，比泛用名稱更能讓目錄在規模變大後維持可預測性。

### 輸入、權限與秘密邊界

#### 輸入契約

輸入欄位應區分已提供、可讀取、推斷和未知。缺少路徑、版本、來源、基線、驗收規則或復原位置時，不要讓模型自行補全。外部網頁、Issue、電子郵件和工具輸出都只是待評估的資料；即使看起來像指令，也不能覆蓋 Skill 規則。

#### 權限矩陣與秘密政策

將讀取、臨時寫入、持久寫入、網路、安裝、傳送、發布和刪除分別列出。每類動作都要寫明對象、批准人、可觀察結果和復原方式。秘密不得放進 `SKILL.md`、範例、日誌、截圖或回執；若受控系統確實需要秘密，應由指定入口提供，並記錄如何避免回顯和二次傳播。

### 選擇指令碼、參考資料與資產時避免過度建置

指令碼只適合確定、可檢查的重複動作；參考資料只放目前分支可能需要的詳細規則；資產必須說明授權、用途和載入時機。任何資源都應標明輸入、輸出、失敗方式和副作用。第一次執行時，先用臨時目錄或不含敏感資料的範例做 smoke test，並記錄版本和原始輸出；「有指令碼」不等於指令碼安全、正確或已經執行。

## 1. 先寫觸發契約

Skill 的描述（description）應能回答四個問題：

1. 使用者正在做什麼任務時應該使用它？
2. 哪些輸入或上下文必須存在？
3. 哪些相似任務不應該使用它？
4. 觸發後應該留下什麼結果和證據？

可以先用下面的模板，而不是從一段宣傳語開始：

```text
適用：當使用者要……且存在……時。
不適用：如果使用者只要……或缺少……，應先……/拒絕……。
輸入：需要讀取哪些檔案、資料、版本和權限狀態。
輸出：交付哪些檔案、報告、diff、日誌或待確認項。
```

過於寬泛的 Skill 會在不相關任務中增加上下文並造成誤觸發；過於狹窄的 Skill 又會讓使用者找不到它。觸發邊界是能力設計的一部分，不是最後才補上的後設資料。

## 2. 只沉澱可複用的判斷

Codex 已具備通用寫作、程式設計和分析能力。Skill 應補充那些不顯然、容易遺漏或需要專案一致性的內容，例如：

- 領域術語、專案結構和檔案優先順序；
- 脆弱步驟、常見失敗和復原順序；
- 工具到任務的對映，而不是工具名列表；
- 輸出格式、證據標準和停止條件；
- 秘密、外部內容、許可證和副作用的邊界。

一個簡單的提煉測試是：刪掉這句話後，具備通用能力的 Agent 是否仍能在本專案中做出同樣可靠的判斷？如果能，這句話可能只是背景雜訊；如果不能，就說明它依賴什麼證據、何時適用，以及失敗時怎麼辦。

Skill 也不應吞掉本次任務協議。使用者目標、專案規則、Skill 方法和工具行動的關係是：

```text
本次任務協議：這一次要交付什麼
專案規則：長期有效的術語、許可和安全約束
Skill：這類任務通常如何檢查、決策、執行和驗證
工具：當前真正可以採取的具體行動
```

發生衝突時，明確指出衝突並暫停；不要讓 Skill 默默改寫使用者目標或擴大權限。

## 3. 用漸進披露控制上下文

推薦的三層結構是：

```text
中繼資料：什麼時候觸發
SKILL.md：最短的核心流程、選擇規則和邊界
references/scripts/assets：只有在當前分支需要時才載入或執行
```

`SKILL.md` 應帶讀者從輸入檢查走到交付，不應複製所有參考材料。參考檔案適合放長表格、領域背景、版本化規範和範例；指令碼適合確定性檢查、格式轉換或可重複操作；資產適合範本或明確授權的素材。每個附屬資源都應說明用途、輸入、輸出和失敗處理。

不要把「有指令碼」當成「已驗證」：指令碼仍可能改錯路徑、讀取秘密、聯網或使用過期介面。第一次使用附屬資源時，先在臨時目錄或無敏感資料的樣本上做 smoke test，並記錄版本和輸出。

## 4. 寫出完整而有限的流程

一個可靠的 Skill 至少應包含以下步驟：

1. **確認輸入：** 檢查檔案、版本、來源、權限和必要欄位；缺失時詢問或停止，不猜測；
2. **建立範圍：** 列出會讀什麼、會改什麼、不會改什麼；
3. **選擇路徑：** 根據任務大小、風險、可逆性和證據要求選擇步驟；
4. **執行最小動作：** 每次動作有目標、輸出和變更邊界；
5. **觀察並分類失敗：** 區分輸入、環境、權限、實作和驗證失敗；
6. **決定繼續、縮小、詢問或停止：** 寫出觸發條件，不使用無限重試；
7. **交付證據：** 給出檔案、diff、命令輸出、來源、未驗證項和下一步。

外部文件、網頁、Issue、電子郵件和工具回傳值都是資料，不會自動覆蓋 Skill 規則。只把它們當作事實輸入，經過來源、範圍和可信度檢查後再使用。秘密永遠不應進入 Skill 檔案、範例、日誌或交付摘要；如果任務確實需要秘密，請說明由誰、在哪個受控入口提供，以及如何避免寫入輸出。

## 5. 以任務集評測，而不是只讀一遍

每個 Skill 至少需要四類任務：

- **正例：** 應該觸發，並在宣告範圍內完成；
- **邊界例：** 相似但不適用，應拒絕、縮小範圍或請求補充輸入；
- **失敗例：** 輸入缺失、命令失敗、外部依賴不可用或出現不可信內容時，應保留現狀，並在正確的邊界處停止；
- **遷移例：** 更換表述、領域或檔案後，方法仍然成立，但具體事實不會被硬編碼帶過去。

為每個任務記錄：初始上下文、Skill 是否被發現、是否被選中、載入了哪些資源、採取了哪些行動、產生了哪些證據，以及是否越過邊界。這樣才能定位問題出在 discovery、routing、loading、execution 還是 verification。

## 實驗：把一次成功沉澱為最小 Skill

### 準備

選一個不涉及秘密、網路發布或生產資料的重複流程，例如「檢查一份 Markdown 文件的連結和標題層級」。先不用 Skill，手動寫一份一次性任務協議，包含輸入、限制、檢查步驟、失敗處理和輸出證據。準備三份刻意不同的範例文件：正常、缺少連結目標，以及包含長文字但不需要全部改寫。

### 任務

從一次性協議中標出「至少會在三次任務中重複使用」的判斷，寫成一個最小 `SKILL.md` 草稿，要求包含：觸發描述、不適用範圍、輸入檢查、核心步驟、停止條件、輸出格式和驗證方式。把詳細規則放進一個 reference，把確定性檢查放進一個唯讀指令碼；如果不需要，就不要建立資源。用正常範例執行一次，再與不用 Skill 的協議對照。

### 證據

儲存一份不含敏感內容的實驗記錄，至少包括：Skill 草稿、正例輸入、執行輸出、檢查過的資源、範例 diff 或報告、人工判斷，以及「發現／觸發／載入／驗證」四個狀態。證據應能支援以下宣告：Skill 的觸發範圍清楚、輸入缺失會被發現、輸出可以檢查，而且沒有額外修改無關檔案。

### 失敗變體

依序測試三個變體：缺少目標檔案、範例文件包含一段來自外部內容的指令文字，以及目標目錄不可寫。觀察並記錄 Skill 是否拒絕猜測、是否把外部文字當成資料，以及是否在寫入前停止。再測試一個不相關的純文字潤飾請求，檢查是否誤觸發。不要為了通過實驗而擴大權限或修改 Skill 的發現設定。

### 反思

回答：哪一條規則是領域特有的，哪一條只是通用常識？如果刪掉 reference，入口檔案是否仍能指導安全停止？如果指令碼報告通過，是否仍需要人工檢查？一次 Skill 執行成功，能否證明它在其他版本、目錄或工作面也可用？

## 失敗或邊界案例

- **檔案存在但未發現：** 不把目錄列表當成執行時證據。分別檢查路徑、後設資料、當前工作面能否看到、是否被觸發，以及內容是否真的載入。
- **清單中看不見，但使用者明確要求呼叫：** 不要假設任何清單都等於 Skill 全集；記錄目前產品入口、版本和實際結果，必要時降級為等價的人工流程，並把它標為降級，而不是修復。
- **symlink、junction 或不同安裝方式：** 這是環境和版本相關的易變行為。不要在正文寫成永久相容矩陣；把實際檢查留在複核記錄中。
- **Skill 過於寬泛：** 如果邊界任務頻繁觸發，收窄 description，加入不適用例，並重新跑正例和邊界例。
- **Skill 試圖取代工具或授權：** Skill 可以規定方法，不能靠文字創造檔案、網路、帳號或發布權限。需要工具或新權限時，先寫清楚影響並暫停。
- **參考資料許可證不清：** 不復制文字、圖片、程式碼或 Skill 指令。記錄來源和許可決定；只有連結或原創改寫在邊界清楚時才進入專案。

## 遷移練習

把實驗中的文件檢查 Skill 遷移成一個研究資料審查 Skill，再遷移成一個團隊發布前檢查 Skill。每次遷移都保留流程骨架，但重新設計領域輸入、證據、失敗和權限邊界。至少為每個版本設計一個正例、一個邊界例和一個外部依賴失敗例，並說明哪些事實必須從官方來源或專案記錄重新讀取。

## 本章驗收

- [ ] 我能寫出 Skill 的適用條件、不適用條件、輸入和輸出契約。
- [ ] 我能解釋 Skill 補充什麼專案特有判斷，以及為什麼不應重複通用常識。
- [ ] 我能把入口流程、長參考資料、確定性指令碼和授權資產分層。
- [ ] Skill 對輸入缺失、外部不可信內容、權限不足和驗證失敗都有停止或詢問動作。
- [ ] 我能區分發現、觸發、載入、執行和驗證，並為每一步寫證據。
- [ ] 我完成了正例、邊界例、失敗例和遷移例，且未把社群報告寫成官方承諾。
- [ ] 我能說明一次成功執行的證據範圍，以及下一次複核需要記錄的版本和環境。

## 來源與更新提示

Skill 的觸發契約、漸進揭露、失敗處理、任務集評測和證據邊界是穩定方法；具體呼叫語法、發現範圍、目錄結構、外掛能力和資源載入行為則屬於易變事實。產品事實請以[OpenAI Codex 官方基線](../evidence-library-ZHTW.md#source-notes)及其中列出的目前官方文件為準；現實問題請回到[現場研究記錄](../evidence-library-ZHTW.md#source-notes)檢視證據等級、原始 URL 和調查限制。吸收外部 Skill、程式碼或資產前，依專案的[資產與來源登錄表](../evidence-library-ZHTW.md#source-notes)記錄來源、授權、適用範圍和複核日期。

## 一次可觀察的設計流程

下面用「審查 Markdown 連結」這個低風險任務，走完從問題到證據的完整流程。它不需要網路、帳號或真實使用者資料；也不證明任何宿主會自動發現這個 Skill。

### 先把任務縮小到能檢查的範圍

不要寫「幫我檢查文件品質」。這類目標沒有邊界。先寫出這次的任務協議：

```text
目標：找出 docs/quickstart.md 中失效的相對 Markdown 連結。
允許：讀取該檔案；在臨時報告中列出候選問題；執行只讀連結檢查。
不允許：修改正文、存取網路、安裝相依套件、刪除檔案或發布結果。
驗收：報告逐條給出連結文字、目標、檢查結果和無法判斷的原因。
停止：檔案不存在、連結規則不明確，或檢查需要超出允許範圍的行動。
```

這份協議只屬於這次任務；Skill 只提供「如何審查」的可重複使用方法。把兩者混在一起，下一次任務就會把舊檔名、舊權限和舊結論帶進去。

### 設計觸發與讓出處理權的規則

觸發條件不是廣告語。它應該讓讀者和 Agent 都能判斷：這是不是它該接手的工作。

| 項目 | 連結審查 Skill 的範例 |
|---|---|
| 適用 | 使用者要求檢查一個已指定 Markdown 檔案中的本機連結，並給出了目標和驗收條件 |
| 不適用 | 使用者要求改寫文案、檢查遠端站點、批次修復整個儲存庫，或沒有指定目標檔案 |
| 需要先問 | 連結應以目前檔案、儲存庫根目錄，還是網站建置目錄為基準？ |
| 必須停止 | 需要網路、憑證、寫入受保護目錄或改變發布內容，而任務沒有明確授權 |

「連結」和「審查」同時出現，不等於應該觸發。關鍵詞只是一條線索；任務意圖、輸入是否完整、方法是否負責，以及風險是否可接受，才共同構成觸發判斷。

### 把動作和證據配對

每一步都要回答兩個問題：允許做什麼？留下什麼可複查的東西？

| 階段 | 允許動作 | 應留下的證據 | 還不能證明什麼 |
|---|---|---|---|
| 輸入檢查 | 讀取指定檔案和任務協議 | 檔案路徑、基線版本、缺失輸入清單 | 連結一定失效 |
| 候選掃描 | 提取相對連結 | 候選連結表與解析規則 | 目標檔案存在 |
| 本機檢查 | 只讀檢查解析後的路徑 | 每條路徑的存在/不存在/未知結果 | 線上 URL 可存取 |
| 交付 | 寫入可丟棄報告 | 報告、命令和退出狀態 | 已修復問題 |
| 複核 | 讓人閱讀高風險或未知項 | 稽核決定和未覆蓋範圍 | 方法對所有儲存庫都有效 |

這樣寫能阻止一個常見誤報：指令碼執行以零狀態結束，報告就宣稱「所有連結都正確」。退出狀態只證明指令碼依照自己的定義完成；它不會自動涵蓋被忽略的格式、建置時重寫或遠端目標。

## 最小 Skill 不是最少文字

「最小」指的是只保留每次都需要的判斷。對上面的任務，入口檔案可以短，但不能漏掉關鍵邊界：

```markdown
---
name: local-link-review
description: Review local Markdown links in a named file when a target,
acceptance rule, and read-only scope are supplied. Do not use for rewrites,
network checks, or bulk repairs.
---

1. Confirm the target, link base, allowed scope, and acceptance rule.
2. Stop and ask if any one is missing.
3. Extract only local relative links; preserve the original text.
4. Run the declared read-only check and record its version and exit status.
5. Return candidate, confirmed, and unknown results separately.
6. Do not edit, publish, install, or use the network without new approval.
```

如果連結解析規則依賴多個 Markdown 方言，細節可以放進 `references/`；如果有確定性的本機檢查器，可以放進 `scripts/`。但「沒有目標就停止」「不得連線網路或寫入」這類安全規則必須留在入口中，不能藏在可選檔案裡。

## 故意失敗一次，才知道停止是否真實

正例往往太寬容。請把同一任務複製成一個臨時範例，只改一個變數：把一個連結改成不存在的相對路徑。預期結果不是「Skill 很聰明」，而是一個具體、可見、可複查的訊號，例如：

```text
BROKEN: [安裝說明] (guides/install.md)
resolved: docs/guides/install.md
check: path does not exist
scope: local relative path only; remote availability not checked
```

然後再執行一個邊界例：同一檔案內有 `https://` 連結。這個 Skill 應把它歸為「超出範圍／未知」，而不是偷偷連線網路。最後執行一個缺少輸入的例子：不提供連結基準。正確結果是提問或停止，而不是猜測儲存庫的布局。

### 復原不是一句「撤銷」

本練習不修改原檔案，所以最安全的設計是把報告寫入臨時目錄，結束時刪除該目錄，或保留路徑讓讀者確認。若 Skill 需要寫入，必須在執行前寫清楚：目標位置、執行前基線、可逆步驟、回讀檢查，以及無法復原時的停止點。不要讓「可以撤銷」變成沒有對象的承諾。

## 小實驗：把一次成功變成可審查記錄

1. 選擇一個自己擁有、可安全讀取的 Markdown 檔案；不要把秘密、私人材料或受限專案貼給模型。
2. 按上面的任務協議填寫目標、允許範圍和驗收條件。
3. 用人工步驟或當前工作面可用的 Skill 執行一次只讀檢查；記錄環境、日期、輸入和原始輸出。
4. 加入一個故意壞連結，重新執行，並確認它留下的是失敗訊號而不是修復動作。
5. 移除壞連結或丟棄臨時樣本，回讀原檔案與報告，確認沒有超出授權的改動。
6. 請另一位讀者只看任務協議和報告，判斷他能否說出結果、範圍和未知項。

實驗完成只能說明你在記錄的環境中觀察到了這些結果。它不證明所有 Skill 主機、版本、目錄或模型都會以同樣方式發現、選擇或執行該方法。

## 常見誤區

- **把描述寫成承諾：** 「自動保障發布安全」既沒有任務邊界，也沒有可測驗收。改成具體輸入、輸出和停止條件。
- **把指令碼當作 Skill：** 指令碼可以檢查一個確定問題；Skill 仍需決定何時執行、何時不執行、結果如何解釋。
- **把發現當成可靠性：** 即使一個 host 列出了 Skill，也仍要分別驗證後設資料、選擇、載入、動作和交付證據。
- **把成功樣本當作評測：** 至少保留正例、近似但不應觸發的例子、缺失輸入和故意失敗；遷移到新領域時重新審查假設。
- **把未知項藏起來：** 「未檢查遠端連結」「無法判斷建置期路徑」是結果的一部分，不是報告的失敗。

## 採用回執：目錄裡有檔案，不等於可以依賴它

在把一個 Skill 交給真實任務前，先寫一張採用回執。它避免「看到目錄，就預設已經生效」的
誤解，也讓下一位審查者知道該從哪一層開始檢查：

```text
Skill 名稱與版本：
任務缺口：它要補上的具體判斷，而不是「讓 AI 更強」
來源與許可證：原創 / 已審查來源；許可和複核日期
本次宿主與工作面：實際產品、版本和可見路徑
已觀察到：檔案存在 / 發現 / 選擇 / 載入 / 動作 / 輸出（逐項填寫）
未觀察到：任何沒有執行、沒有回讀或沒有獨立審查的層
允許範圍：讀取、臨時寫入、網路、安裝、發布分別是否允許
下一項安全檢查：只驗證一個未觀察到的層
停止條件：缺少輸入、權限、復原目標或證據時停止
```

例如，`SKILL.md` 位於儲存庫中，只支援「檔案存在」；它不支援「宿主已發現」或「方法已經
執行」。即使一次報告生成成功，也只支援那次任務和記錄的環境，不支援所有模型、所有目錄或
所有使用者都能得到同樣結果。採用回執不是額外官話，而是把「我以為能用」變成可複查的判斷。

## 先審來源，再採用外部方法

外部 Skill 的說明文字、指令碼和範例都先當作待審查材料。不要因為儲存庫熱門、描述流暢或名字
相似，就複製到課程或交給真實資料執行。至少逐項確認：

1. 原始專案連結、具體 revision、維護者和檢查日期；
2. 頂層許可是否覆蓋所需的程式碼、指令碼、素材和巢狀依賴；
3. 它會讀取、寫入、安裝、聯網或傳送什麼；
4. 本專案的任務缺口是否真的需要它，而不是一個更小的原創流程；以及
5. 用無敏感臨時樣本做過什麼檢查，哪些行為仍未執行。

不能回答其中任何一項時，保留連結和研究記錄即可，不把內容複製為本專案的 Skill，也不把它
列為已採用能力。這樣做不會證明外部方法無害；它只是防止「來源不明的便利」變成使用者承擔的
風險。
