# 第十章：把大目标拆成可交付切片

## 本章要解决的问题

“做一个完整产品”“融合所有内容”“把网站做到高级”这类目标通常跨越多个系统和判断。一次性让 Agent 完成，最容易得到范围失控、半成品堆积和无法定位的失败。真正需要设计的不是一张很长的待办清单，而是一串能够独立产生证据、能够暂停、能够恢复的交付切片。

本章把“大目标”改写成一条小而完整的路径：每个切片都有结果、边界、依赖、验收、停止点和下一步接口。

## 学习目标

读者完成本章后应当能够：

- 将一个模糊目标拆成三至七个有依赖关系的竖向切片；
- 区分水平分层、竖向切片和“看似很小但不可验收”的任务；
- 为每个切片写出输入、允许行动、验收证据、失败处理和停止条件；
- 在模型容量、验证卡住或新信息改变目标时，从最近的检查点安全恢复；
- 解释为什么“修改了很多文件”不等于“交付了一个可用结果”。

## 现实问题入口

[FP-09](../../docs/research/field-problems-codex.md#fp-09：模型容量错误中断任务，并可能让排队后续任务接在半成品上)记录了任务中断和半成品状态混淆的用户报告；[FP-10](../../docs/research/field-problems-codex.md#fp-10：格式化验证命令让-windows-cli-agent-长时间停在-working)记录了验证命令长时间没有结果的报告。两条记录都不是官方故障结论，也没有被本地复现；它们适合作为计划设计的压力测试：如果中途停止，能否知道已经完成什么、还缺什么、下一步从哪里开始？

## 1. 先定义交付结果，再画依赖

先写一句可以被使用者观察到的结果，例如“贡献者能在临时目录中启动示例并看到成功页面”，而不是“完成前端、后端和部署”。然后列出这个结果所需的：

1. 输入：文件、数据、环境或明确的假设；
2. 行为：用户或系统必须完成的动作；
3. 接口：切片之间传递的文件、字段、命令或状态；
4. 证据：测试、运行结果、diff、截图、来源或人工确认；
5. 风险：秘密、外部服务、不可逆变更和未解决的未知。

依赖图回答“什么必须先存在”，但不自动决定任务顺序。优先选择能尽早让真实结果出现的路径；把高风险未知放在前面验证，把低风险的润色留到后面。

一个实用的切片卡如下：

```text
切片名称：
用户/团队结果：
输入与前置条件：
本次允许改动：
不做什么：
验收证据：
失败后先保留什么：
停止条件：
交给下一切片的接口：
```

## 2. 水平计划与竖向切片

水平计划是“先做所有数据，再做所有 API，最后做所有界面”。它便于按技术角色分工，却会把第一次可观察结果推迟到很后面。竖向切片是“让用户完成一个小动作”，同时包含最小数据、接口、界面和验证；它更早产生真实反馈，也更容易回滚。

例如目标是“读者可以提交一份学习实验”：

- 水平拆法：先建全部实验表，再写全部接口，再做全部页面，最后联调；
- 竖向拆法：先支持一份固定实验的填写、保存和重新打开，并用一个低风险样例验证闭环；
- 后续切片：再加入校验、列表、权限、导出和团队协作。

竖向不等于“把所有功能塞进一小块”。它只要求一条路径端到端可用；非必要的扩展仍然明确排除。

## 3. 判断一个切片是否足够小

一个好切片应当有：

- 一个清楚的用户或团队结果，而不是一组技术动作；
- 已满足或已记录的依赖；
- 尽量少的文件和系统边界；
- 能在一次专注会话中完成并检查的规模；
- 至少一种直接证据，而不是只看 Agent 的总结；
- 明确的失败后停止点和恢复入口；
- 与后续切片兼容的接口或交接记录。

以下信号说明还要继续拆：

- 标题中有两个以上互相独立的“和”；
- 验收标准同时涉及代码、视觉、生产数据和组织审批，却没有分阶段；
- 需要先安装、迁移或发布才能知道基本假设是否成立；
- 一次失败后无法指出是哪个子目标失败；
- 只有“全部完成后才有价值”，中间没有可观察结果。

反过来，切片也可能过小：如果它只能产生一个孤立文件，无法验证任何真实行为，或依赖很多未完成的后续工作，就应与能观察结果的相邻切片合并。

## 4. 检查点、变更预算与人工确认

每完成两个或三个切片，建立一个检查点。检查点至少记录：

```text
目标是否仍然相同：
已完成的切片与证据：
工作树/diff 的范围：
已验证与未验证：
新增假设或阻塞：
下一切片是否仍值得做：
```

为每个切片设一个变更预算，例如“只改两个章节文件”“不安装依赖”“不接触生产数据”。如果实现需要超出预算，先暂停并更新计划；不要把范围扩大隐藏在“顺手修一下”里。

涉及架构、数据迁移、生产环境、外部发布、高权限或不可逆操作时，确认点必须放在副作用发生前。确认不是让人审阅所有细节，而是让人知道目标、影响、证据和回滚方式，并明确批准哪一个动作。

## 实验：同一大目标的三种拆法

### Setup

在一个临时目录或本仓库的只读副本中，建立一个不含秘密的微型目标：

> 让新贡献者能够阅读一页说明，运行一个无网络的小检查，并知道成功或失败的下一步。

准备一份空白记录表，不修改本仓库文件。把“可运行”定义为：命令退出、输出可读、失败时不改变外部系统。

### Task

分别写三份计划，每份都限制为三至七项：

1. 水平计划：按文档、脚本、测试、发布分层；
2. 按文件或章节顺序的计划；
3. 按学习者能力闭环的竖向计划。

给每项补齐切片卡，并画出依赖箭头。然后选第三份计划的第一项，用一个临时说明文件和一个本地无副作用检查完成它。记录开始状态、改动、命令输出和结束状态。

### Evidence

提交一张对照表或 Markdown 记录，至少包含：三份计划、第一项的输入和边界、实际 diff、实际命令与输出、验收判断。证据必须能让没有参与实验的人回答：第一项完成了吗？若未完成，卡在哪里？下一步是否可以安全继续？

### Failure variant

在第二项开始前故意让检查命令返回非零，或把一项必需输入留空。不得直接添加依赖、修改外部服务或跳过检查。把状态标为“阻塞/未验证”，写出改变后的最小计划，并说明为什么不应继续堆叠切片。

### Reflection

回答以下问题：哪一种计划最早产生了真实证据？哪一种失败最容易定位？如果前一项只改了文件却没有可观察结果，它是否应算作交付？哪些依赖是事实，哪些只是当时的假设？

## 失败或边界案例

- **容量或会话中断：** 不从记忆中的“应该做完了”继续。先检查 diff、最近命令、测试输出和切片卡，再决定恢复、回滚还是重开任务。
- **验证命令卡住：** 中断命令只代表恢复了控制权，不代表验证通过。保留中断前输出，重新确认工作树，再换成有时间边界或更小范围的验证。
- **依赖未满足：** “顺便安装”可能改变持久环境。若依赖安装不在本次授权内，停下并报告需要的版本、来源、影响和回滚方案。
- **目标在执行中改变：** 新需求应成为新切片或新任务协议；不要把旧计划的未完成项伪装成新目标已经完成。
- **大切片无法再拆：** 先找一个最小风险假设做探针，例如只读检查或固定样例闭环；探针的结果决定是否继续，而不是直接进入全面实现。

## 迁移练习

把本章切片卡分别用于一个研究报告、一个营销页面和一个团队 Skill。每个场景写三至七个切片，并特别标出：

- 研究场景的来源、访问日期和证据等级；
- 营销场景的用户效果、隐私和发布确认；
- Skill 场景的触发、失败处理、验证和许可证边界。

再任选一项，把“已完成文件”改写成“用户可观察结果”，并补上一个可以在十分钟内执行的检查。

## 本章验收

- [ ] 我能把一个大目标拆成三至七个竖向切片，并画出依赖；
- [ ] 每个切片都有用户/团队结果、输入、范围、验收证据和停止条件；
- [ ] 我能指出一个水平计划为什么会延迟真实反馈，并给出竖向替代方案；
- [ ] 我能在命令卡住、容量中断或输入缺失后保留 checkpoint，而不是声称完成；
- [ ] 我能区分“修改了文件”“通过了某项检查”和“交付结果可用”；
- [ ] 我能为高风险切片写出副作用前的人工确认点和回滚思路；
- [ ] 我完成了实验记录，且记录中同时有操作证据、判断理由和失败变体复盘。

## 来源与更新提示

依赖图、竖向切片、检查点和变更预算是稳定的方法；具体工作面、模型、命令、容量、权限和界面属于易变事实。现场问题只作为用户报告和研究入口，不能升级成产品承诺。产品事实请以[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)及其中列出的当前官方文档为准；引用具体版本或行为前，记录访问日期、适用入口和复核责任人。每次产品或工具更新后，至少重跑本章实验的正例和失败变体，并把结果标为 `draft`、`candidate`、`verified` 或 `production-ready`，不要只凭文案更新状态。
