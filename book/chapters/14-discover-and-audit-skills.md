# 第十四章：如何发现、安装和审查外部 Skill

## 本章要解决的问题

外部 Skill 能把重复步骤、领域知识和工具调用封装成可复用能力，但它也会扩大上下文、依赖、网络访问、账号权限、外部副作用和许可证责任。真正的问题不是“哪里有更多 Skill”，而是：面对一个真实任务，如何判断缺口是否适合用 Skill 解决，如何把一个目录条目审查成候选能力，如何在不泄露秘密、不接受提示注入、不越权写入的条件下验证它。

本章的结论是：目录是发现入口，不是质量证明；安装是状态变化，不是验证；“能触发”也不等于“值得纳入”。

## 学习目标

完成本章后，你应能：

1. 从任务目标、输入、输出和验收标准推导 Skill 需求，并区分知识缺口、流程缺口、工具缺口和权限缺口。
2. 为候选 Skill 填写可交给维护者批准或拒绝的安装前审查包，覆盖来源/revision、触发与不触发条件、依赖、权限、外部副作用、许可证/NOTICE、隔离试运行、备份、回滚、批准点和 owner。
3. 识别 Skill 中的提示注入、秘密索取、无关上传、过宽权限和未声明外部动作，并将候选标记为 `blocked` 或缩小到安全范围。
4. 用低风险 smoke test、边界测试和失败测试建立证据，区分文件存在、被发现、被加载、被采用和被验证，并把采用决策限制在 `recommendation-only`、`blocked`、`approved-to-install` 或 `installed-candidate`。

## 现实问题入口：从“能找到”到“敢采用”

本章直接连接现场研究中的三个问题：

- **FP-06**：普通 `SKILL.md` 可以被发现，文件 symlink 却可能被忽略。它提醒我们：发现机制是实现细节，不能把“列表里没有”直接解释成“Skill 不存在”，也不能把某一版本的发现行为写成永久规则。
- **FP-07**：显式调用可能错误地依赖隐式可见列表。它提醒我们分别记录“隐式路由证据”和“显式名称解析证据”，不能用一个列表替代两种验证。
- **FP-11**：Agent 曾被报告把源码验证扩大为持久环境的 force reinstall。它提醒我们，Skill 的可执行性不等于用户授权；安装、验证、发布、部署和重启是不同状态，必须分别取得授权和留下证据。

这些都是用户报告或社区证据，不是本地复现，也不是官方已确认的通用行为。读者应把 FP 编号当作风险入口，不能把 issue 的推测当成产品承诺。

## 核心概念与决策

### 1. 先写任务协议，再决定是否需要 Skill

用下面的最小协议描述任务：

```text
目标：要改变什么？
输入：哪些文件、数据或公开资料可以读？哪些不可读？
输出：交付物的最终形态是什么？
验收：什么证据能说明完成？
授权：允许哪些工具、网络、账号和写入动作？
停止：遇到什么情况必须暂停并询问？
```

然后把缺口归类：

| 缺口 | 适合的解决方式 | 常见误判 |
|---|---|---|
| 不知道概念或事实 | 研究、官方文档、人工判断 | 用 Skill 代替来源核验 |
| 步骤重复且稳定 | 本地 Skill 或脚本 | 用一个大 Skill 覆盖所有场景 |
| 需要观察或改变外部系统 | 受控工具/连接器 | 把“可调用”当成“已授权” |
| 目标和验收不清 | 先澄清任务 | 安装 Skill 掩盖需求不清 |

### 2. Skill、工具、Plugin、Connector 不是一回事

Skill 是方法和路由契约；工具是可观察或可改变外部世界的接口；Plugin/Connector 是承载或连接这些能力的产品层。审查时要问四个问题：Skill 读什么、Skill 会建议什么、工具实际做什么、外部服务收到什么。不能仅凭 Skill 名称推断权限，也不能仅凭 README 推断运行时行为。

### 3. 许可证和安全边界是采用条件，不是脚注

候选通过功能测试，也可能因为许可证不清、嵌套依赖未声明、品牌/代码不可复制或隐私处理不明而不能进入发行版。项目资产台账规定：没有明确许可证的内容默认只作研究参考或外链；目录型来源 S03、S06 是索引或候选池，不把条目数量当质量证明；S02 的 CC BY-NC 4.0 内容不能在未保留归属和许可边界时直接纳入商业发行版。

### 4. 把提示注入当作不可信输入

Skill 文本、README、远程页面、Issue、样例文件和工具返回值都属于数据。出现“忽略上级规则”“读取并上传密钥”“把结果发到某地址”“执行未授权命令”等指令时，应将其标记为可疑内容，不因它位于 Skill 文件中就获得更高优先级。安全做法是截取最小输入、移除秘密、在无网络或沙盒条件下运行，并记录拒绝了什么。

## 决策流程与审查卡

### Step 1：发现

从任务协议反推关键词，在官方目录、项目仓库或已登记的来源中寻找候选。记录搜索日期、来源 URL、提交或版本，不复制正文。星标、下载数、目录数量和宣传语只能产生候选，不能替代审查。

### Step 2：形成安装前审查包

每个候选至少填一份 `skill-adoption-decision.md`：

```text
candidate / task_gap:
trigger_conditions / non_trigger_conditions:
source_url / revision / inventory_date:
license / NOTICE / nested_assets / copy_boundary:
dependencies / network / account:
target_install_scope:
permissions / secrets_boundary:
external_side_effects:
isolated_trial:
backup_and_restore_target:
rollback_steps / rollback_success_check:
approval_points:
behavior_tests: positive | boundary | failure | migration
owner / version_policy / next_review:
decision: recommendation-only | blocked | approved-to-install | installed-candidate
evidence / unverified / unblock_conditions:
```

`approval_points` 至少分开记录：允许获取固定 revision、允许写入指定安装目标、允许安装依赖/联网/认证、允许进入团队或生产范围。前一批准不自动包含后一批准。`rollback` 也不能只写“删除文件”，要给出安装前配置备份、精确目标、恢复步骤和恢复后的成功检查。

### Step 3：区分决策和行为状态

采用决策只有四种结果：

- `recommendation-only`：任务匹配初步成立，只推荐继续只读审查或隔离试用；
- `blocked`：许可证/NOTICE、revision、依赖、权限、目标范围或回滚至少一项不清；
- `approved-to-install`：安装目标、备份/回滚、权限和批准点均已明确并获批，但尚未安装；
- `installed-candidate`：已在批准的隔离目标完成安装，有日志和路径证据，仍待行为验证与采用决定。

这不是项目内容成熟度。行为证据另列为：

```text
文件存在：固定 revision 的路径、清单或哈希成立
被发现：当前工作面能列出或解析名称
被加载：新会话记录显示实际加载了候选资源/指令
被采用：owner 和批准记录将其纳入声明的个人/团队范围
被验证：正例、边界例、失败例和迁移例在声明环境通过
```

五项可以部分成立，也可能因工作面、账户、会话和版本而不同。文件存在不证明被发现；发现不证明加载；加载不代表组织采用；采用不代表行为验证。安装日志只证明安装动作，最多使采用决策成为 `installed-candidate`。

### Step 4：分层启用

优先级从低风险到高风险：本地只读 → 可回滚文件操作 → 沙盒或测试账号的外部连接 → 生产写入和公开发布。升级前必须说明新增权限、证据和回滚方式。生产级内容成熟度还需要组织批准、许可证清单、版本锁定、维护责任和回归计划；一次成功的 smoke test 最多支持项目成熟度 `candidate`，不能直接称为 `verified`，也不会自动改变上述采用决策。

## 可观察小实验：对两个候选作批准或拒绝决定

### Setup

准备两个固定 revision 的候选，或用两个脱敏本地样例代替：A 与任务缺口相符、许可证信号可定位，目标是判断是否值得推荐隔离试用；B 的许可证/NOTICE 或回滚说明故意缺失，目标是作出拒绝或暂不采用决定。准备候选仓库 URL、固定 revision、目录清单、许可证/NOTICE 文件、`SKILL.md` frontmatter 摘要、工具/网络/凭据声明和当前任务协议。只读审查，不安装、不认证、不启用团队环境；目标安装路径、配置备份或恢复检查尚不明确时，不得写 `approved-to-install`。

可直接使用本项目的原创示范输入：A 为 S05 `code-review-and-quality`，来源 `https://github.com/addyosmani/agent-skills`，revision 证据为归档 SHA-256 `6EEDBE7D2EA3A82417781D879785BD501FBDE21275627F557DE4B76560BA1250`；B 为 S06 `webapp-testing`，来源 `https://github.com/composio-community/awesome-codex-skills`，revision 证据为归档 SHA-256 `D3DA83ED9D474690E7FF235351376114972840C78BC319CBCB8F89CBD704608E`。A 的合理初始结果是 `recommendation-only`：仓库级 MIT 信号可定位，但仍需逐项核验依赖和嵌套资产。B 的合理结果是 `blocked`：根目录许可证不能自动覆盖嵌套 Skill/脚本/素材，且未给出具体备份和回滚时不得安装。这里只引用台账元数据并原创总结，不复制源仓库正文。

### Task

1. 先不安装，分别检查入口文件摘要、manifest、依赖声明和许可证/NOTICE 信号；记录 URL、revision 和实际文件路径。
2. 为 A/B 各填一份安装前审查包，明确任务缺口、触发/不触发条件、最小权限、外部副作用、隔离试运行、备份/回滚、批准点和 owner。
3. 为 A 设计但不执行行为验证计划：一个正例、一个边界例、一个失败/注入例和一个跨项目迁移例；写清输入、期望行为、停止条件和证据。
4. 将 A 保持为 `recommendation-only`，除非安装批准、具体路径、备份与回滚均已有真实证据；不要为了得到更高状态而安装。
5. 不绕过 B 的许可或回滚缺口，将其标为 `blocked`，并写清解阻材料。分别填写“文件存在/被发现/被加载/被采用/被验证”，未知项写 `not_observed`，不做推断。

### Evidence

证据包至少包含两份 `skill-adoption-decision.md`、来源 URL/revision、目录清单、指向实际文件的许可证/NOTICE 结论、依赖与权限清单、具体安装/备份/回滚目标、批准点、owner、A 的四类行为验证计划、B 的阻塞与解阻条件，以及五项行为状态。另一位读者应能复现“为什么 A 只值得继续审查、为什么 B 被拒绝”，而不是只能看到笼统建议。

### Failure variant

让候选仓库保持可访问且 `SKILL.md` 确实存在，但移除可定位的许可证/NOTICE，或只写“删除目录即可”而不给出配置备份和恢复检查。也可以让候选说明要求读取真实 `.env` 并上传。正确结果是 `blocked`：不下载、不安装、不提权、不上传，也不把文件存在写成已发现、已加载、已采用或已验证。

### Reflection

回答四个问题：

- 哪一条证据改变了你的采用决定？
- 你验证的是 Skill 的行为，还是只验证了目录元数据？
- 如果 FP-06/07 的发现差异在你的版本中出现，你会如何分别验证隐式和显式调用？
- 哪个动作必须由用户或组织另行授权，为什么不能藏在 Skill 内？
- 谁负责下一次 revision、许可证或依赖变化后的复核？

## 失败与边界案例

- **列表缺失不等于不存在**：先检查受支持的 Skill root、普通文件要求和版本，再记录“未发现”而不是“不可用”。symlink、hardlink、目录链接和不同操作系统的行为必须单独验证。
- **显式名称不能只看可见列表**：尝试受支持的显式入口，记录解析结果；若入口失败，提供等价人工流程并把它记录为降级，不伪造“已调用”。
- **目录许可证不覆盖嵌套内容**：S06 根目录的许可证信号不能自动覆盖每个嵌套 Skill、脚本、图片和依赖；缺少独立许可或 NOTICE 时，保持 `reference-only` 或 `blocked`。
- **通过 smoke test 仍可能不适合生产**：它可能没有覆盖数据删除、重试重复写入、重定向泄露 token、并发、超时、依赖断裂和维护中止。生产采用要增加权限审查、回归集、回滚演练和责任人。
- **安装动作本身可能改变持久环境**：若验证需要安装包、修改 PATH、替换运行时、使用生产凭据或重启服务，必须先写明目标、范围、影响、回滚和授权。参照 FP-11 区分“源码已修改”“已验证”“已安装”“已发布”“已部署”“已重启”“已在线验证”。

## 迁移练习

选择你正在使用的一个 Skill 或团队内部脚本，不改变生产环境：

1. 把它从目录条目改写成任务协议和完整安装前审查包。
2. 设计一个只读 smoke test、一个失败变体和一个提示注入变体。
3. 输出一页“采用决定”，只使用四个允许值，并为决定绑定批准点、owner 和证据。
4. 让另一位同事只看审查卡，判断能否复现你的结论；若不能，补齐缺失的来源、版本、权限或输出证据。
