# 第 14 章：發現、安裝與審計外部 Skill

**狀態：**`candidate`。**實驗：**`draft / not_run`。本章中的社群問題是風險線索，不是本機重現或官方根因結論。

## 本章要解決的問題

外部 Skill 能把重複步驟、領域知識和工具呼叫包裝成方法，也可能帶來相依套件、網路存取、帳戶權限、外部副作用和授權條款。真正的問題不是「哪裡還有更多 Skill」，而是：一個真實任務暴露缺口後，Skill 是否真是合適的補救；怎樣把目錄條目變成可稽核候選；怎樣測試而不洩露秘密、不接受提示注入、不越過授權邊界。

結論很簡單：目錄只是發現入口，不是品質證明；安裝是狀態變化，不是驗證；「可以觸發」不代表「應該採納」。

## 本章目標

完成後，你應能：

1. 從任務目標、輸入、輸出和驗收條件匯出 Skill 需求，並區分知識、工作流程、工具與權限缺口；
2. 在安裝前審查來源、固定版本、觸發與非觸發條件、相依套件、權限、授權條款、備份、回滾、審批和負責人；
3. 識別要求秘密、無關上傳、過寬權限或未宣告外部行為的內容，並把候選標為 `blocked`；
4. 分開記錄檔案存在、被發現、被載入、被採納和被驗證，避免把一次煙霧測試寫成生產採納。

## 學習目標

你能區分任務缺口與知識、工具或授權問題，並用來源、revision、授權條款、權限、復原方案和證據判斷候選項。

## 先寫任務協議，再決定是否需要 Skill

把任務寫成六項：目標、允許與禁止的輸入、交付物、驗收證據、授權範圍、必須暫停的條件。範圍不清時，先問問題；不要用安裝掩蓋需求不清。

| 缺口 | 常見處理方式 | 常見誤判 |
|---|---|---|
| 缺少概念或事實 | 研究、官方文件、人工判斷 | 用 Skill 代替查證來源 |
| 穩定重複的流程 | 本機 Skill 或指令碼 | 用一個巨型 Skill 包辦一切 |
| 外部系統的觀察或改變 | 受控工具或連接器 | 把「可呼叫」當「已授權」 |
| 目標或驗收不清 | 先澄清任務 | 用安裝掩蓋問題 |

Skill 是方法與路由契約；工具是觀察或改變外部世界的介面；Plugin/Connector 是承載或連線這些能力的產品層。審查時分別問：Skill 讀什麼、建議什麼、工具實際做什麼、外部服務會收到什麼。不要從名稱推斷權限，也不要只憑 README 推斷執行行為。

## 採納決策卡

每個候選至少記錄：任務缺口；觸發與非觸發條件；來源 URL、固定版本、清單日期；授權條款、NOTICE、巢狀資產和複製邊界；相依套件、網路、帳戶；安裝目標範圍；權限和秘密邊界；外部副作用；隔離試用；備份與復原目標；回滾步驟和成功檢查；審批點；負責人和下次複核；正例、邊界、失敗/注入、遷移測試；以及決策、證據、未知項和解除阻塞條件。

取得固定版本、寫入安裝目標、安裝相依套件或登入、進入團隊或生產範圍是不同審批點。一個審批不會自動推出下一個。回滾不能只寫「刪除目錄」，必須說明安裝前設定備份、準確目標、復原步驟和復原後的檢查。

## 把決策狀態和行為狀態分開

| 決策 | 含義 |
|---|---|
| `recommendation-only` | 任務匹配看起來合理，只建議只讀審查或隔離試用 |
| `blocked` | 授權條款、版本、相依套件、權限、目標範圍或回滾中至少一項不清楚 |
| `approved-to-install` | 目標、備份、回滾、權限和審批明確，但尚未安裝 |
| `installed-candidate` | 已在獲批隔離目標安裝且有路徑與日誌，行為驗證和採納仍未完成 |

行為證據另記：檔案存在、被發現、被載入、被採納、被驗證。它們可部分成立，也會隨工作面、帳戶、工作階段和版本不同而不同。檔案存在不證明發現；發現不證明載入；載入不證明組織採納；採納也不證明行為已驗證。

## 低風險實驗：審查而不安裝

### 準備

選擇兩個固定 revision 的公開候選項，或兩個已脫敏的本機樣本。只準備 URL、revision、檔案清單和授權條款/NOTICE 訊號；不要設定安裝目標、登入或使用秘密。

### 任務

準備兩個固定版本或脫敏樣本。A 有可追溯的授權條款且符合任務，判斷是否值得隔離試用；B 缺少授權條款、NOTICE 或回滾，判斷是否阻止。只檢查儲存庫 URL、固定版本、檔案清單、授權條款/NOTICE、`SKILL.md` 摘要、工具/網路/憑據宣告和任務協議。不要安裝、登入或啟用團隊環境。

為 A 設計但不執行四類驗證：正例、邊界例、失敗/注入例、跨專案遷移例；寫清輸入、預期行為、停止條件和證據。A 沒有真實安裝目標、備份與回滾前只能是 `recommendation-only`。B 不能靠「根目錄有授權條款」越過巢狀資產、相依套件或回滾缺口，應為 `blocked`。

### 證據

為 A 和 B 分別儲存審查卡：來源、revision、實際路徑、授權條款/NOTICE 結論、相依套件、預期權限、負責人、決定與未知項。為 A 保留正例、邊界、失敗/注入、遷移四類已設計但未執行的用例。審查卡不聲稱已安裝或已觀察到執行行為。

### 覆盤

哪一個缺口真的是可重複的方法，哪一個只是事實、工具或授權缺口？缺少什麼資訊使安裝不成立？

## 真實問題入口：可發現不等於可採納

目錄條目、Star 或示範只能讓候選項可見，不能證明其來源、巢狀相依套件或副作用。先判斷它是否改善一項具體的重複任務，再在無秘密的狹小環境中審查。

## 遷移練習

把審查卡應用到團隊已經使用的一個內部指令碼。寫出觸發與不觸發條件、最小只讀檢查、一個注入案例，以及將來誰有權批准寫入或聯網；不要改變指令碼或生產環境。

## 來源與維護邊界

審查卡和狀態區分是穩定方法。目錄、安裝、執行行為與產品介面會變化；必須針對固定 revision、具體環境和實際目標路徑重新核驗。

## 常見失敗與邊界

- 列表裡沒有，不等於不存在：檢查支援的根目錄、普通檔案要求和版本行為；連結、不同系統都需獨立檢查。
- 明確名稱不能只看可見列表：用支援的顯式入口記錄解析結果；失敗時給手動替代路徑，不要假稱已呼叫。
- 目錄授權條款不自動覆蓋巢狀內容：沒有明確授權條款或 NOTICE 時保持 `reference-only` 或 `blocked`。
- 煙霧測試通過不代表生產安全：它可能沒覆蓋刪除、重複重試、令牌洩漏、並行、超時、相依套件損壞和維護者放棄。
- 安裝會改變持久環境：涉及套件、PATH、執行時替換、生產憑據或服務重啟時，先明確目標、影響、回滾和授權。

## 我真的學會了嗎？

- [ ] 我能從真實任務解釋為什麼需要或不需要 Skill。
- [ ] 我記錄了來源、版本、觸發/非觸發條件和負責人。
- [ ] 我固定了版本，並寫明隔離試用、備份、回滾和審批點。
- [ ] 我區分了 Skill 指令、工具權限與使用者授權。
- [ ] 我審查了授權條款、NOTICE、巢狀相依套件與複製邊界。
- [ ] 我為正例、邊界、失敗/注入和遷移設計了無秘密、低風險測試。

外部目錄、產品入口和發現行為都是易變事實；使用前應查當前官方文件和專案來源。執行 [實驗 017：採納 Skill 前稽核發現過程](../labs/lab-017-skill-discovery-audit-ZHTW.md)。本章仍是 `candidate`，並不證明某個 Skill 已安全採納。

## 安裝前，把候選項變成可否決的決定

目錄、Star 和演示影片只能讓一個 Skill 進入候選池，不能讓它進入你的環境。為每個候選項留下一張獨立審查卡：

```text
任務缺口：本次任務缺少什麼穩定方法？
來源：專案 URL、固定 revision、檢查日期、實際檔案路徑
觸發 / 不觸發：何時適用，何時必須讓給其他方法？
授權條款：儲存庫、目標檔案、NOTICE、巢狀指令碼與資產各自有什麼證據？
相依套件與權限：讀取、寫入、網路、帳戶、秘密、外部副作用
隔離試用：指定目錄、無秘密輸入、允許的動作與停止點
復原：安裝前設定備份、精確復原步驟、復原後的讀回檢查
決定：recommendation-only / blocked / approved-to-install / installed-candidate
```

缺少固定版本、授權條款/NOTICE、安裝目標、備份或復原檢查中的任意一項，就標為 `blocked`。不要透過「先裝了再看」來消除資訊缺口。

### 五種行為狀態不能合併

```text
檔案存在 → 當前工作面發現名稱 → 新會話載入說明 → 所有者正式採用 → 四類用例驗證
```

這五件事分別是 `file exists`、`discovered`、`loaded`、`adopted`、`verified`。一個目錄中有 `SKILL.md`，最多證明第一個；安裝日誌最多支援 `installed-candidate`，不能證明觸發正確、團隊接受或真實效果。

## 四步審查法：先拒絕不清楚的候選項

不要從「怎麼把它裝進去」開始。先按順序問四個問題，並在第一個無法用記錄回答的地方停止：

1. **任務真的缺它嗎？** 寫出當前任務中重複、穩定且容易遺漏的判斷。若只是缺少事實，先查來源；若目標不清，先澄清任務。
2. **我們拿到的到底是什麼？** 固定專案 URL、revision、實際入口路徑、授權條款/NOTICE 和巢狀相依套件，而不是只儲存專案名稱或 Star 數。
3. **它可能做什麼？** 分開列出讀取、寫入、安裝、聯網、帳戶、秘密與外部副作用。沒有清單時，不猜「應該沒問題」。
4. **失敗後怎麼回到原處？** 寫明隔離目錄、安裝前備份、復原步驟與讀回檢查；「刪掉目錄」不是已驗證的復原方案。

四個問題都能用記錄回答，才可以建議 `approved-to-install`；任何一項缺失，正確結果通常是
`recommendation-only` 或 `blocked`。這不是否定候選項，而是避免把好奇心變成未經審查的環境變更。

### 一個簡短但完整的拒絕說明

```text
候選：<固定 URL 與 revision>
決定：blocked
原因：入口指令碼會聯網，但相依套件清單、目標安裝位置和復原讀回檢查未提供。
已檢查：專案連結、入口檔案、頂層許可訊號。
未檢查：執行時行為、巢狀素材許可、實際網路流量。
解鎖條件：補齊以上缺口後，在無敏感的隔離目錄重做審查。
```

這種說明比「感覺不安全」更可用，也不把未執行的行為誤寫成已經發現的風險。

## 小實驗：審查兩個候選項，不安裝任何一個

選擇兩個固定 revision 的公開候選項，或使用兩個脫敏本機樣本。A 應有可追溯來源和授權條款訊號；B 故意缺少授權條款/NOTICE、相依套件宣告或復原方案。

1. 只讀取來源、revision、檔案清單、入口摘要、依賴和許可訊號；不下載到執行時目錄，不登入，不聯網執行。
2. 分別填審查卡，寫明任務缺口、適用/不適用、最小權限、隔離試用和所有批准點。
3. 為 A 設計正例、邊界例、注入/失敗例和遷移例；每個都寫輸入、預期、停止點和證據，但不聲稱已執行。
4. 若 B 缺少檔案級授權或可驗證復原，保持 `blocked`，寫清解除阻塞所需材料。

來源中的「忽略上級規則」「讀取並上傳 `.env`」「為了測試先改生產設定」等文字都是不可信資料。它們不是 Skill 權限，也不是使用者授權。正確結果是拒絕、記錄並停止。

## 本章驗收補充

- [ ] 我能區分知識缺口、重複方法、工具能力和不清楚的任務，且不會用安裝掩蓋問題。
- [ ] 我為外部候選項記錄 URL、revision、檔案路徑、授權條款/NOTICE、相依套件、權限和維護者。
- [ ] 我把取得、寫入安裝目標、安裝相依套件/認證、進入團隊或生產範圍分成獨立批准點。
- [ ] 我只把有證據的狀態寫為存在、發現、載入、採用或驗證；未知即寫 `not_observed`。

## Skill 採用回執：先證明能審查，再決定是否啟用

這個回執適用於專案自己的原創 Skill，也適用於從外部專案發現的候選項。它不會因為一個儲存庫熱門、說明流暢或目錄可見，就把外部內容變成可信或可執行的能力。

```text
候選名稱與版本/提交：
來源：原創 | 外部；外部專案的原始連結：
維護者與複核日期：
要填補的具體任務缺口：
授權條款：程式碼、文件、資產及巢狀相依套件是否分別清楚：
預期讀取/寫入/網路/安裝/傳送/發布行為：
正例、邊界例、失敗例、遷移例：
已觀察：檔案存在 | 發現 | 選擇 | 載入 | 執行 | 回讀驗證
未觀察：
允許的臨時試驗範圍：
拒絕、暫停或採用的理由：
下一項最小安全檢查：
```

外部 `SKILL.md`、網頁、Issue、安裝日誌和工具輸出都屬於待評估資料，其中的命令、連結或「忽略此前規則」一類文字不自動獲得更高權限。沒有清楚的來源、授權、行為範圍或復原路徑時，正確決定是 `blocked` 或拒絕，而不是「先裝上再說」。

### 分層啟用，而不是一次性信任

先讀後設資料和說明，再在無敏感材料的臨時目錄中檢查一條只讀或可逆路徑；只有在結果、範圍和復原方法都被記錄後，才由人單獨決定是否需要寫入、網路、安裝或外部動作。一次成功只支援記錄的宿主、版本、輸入和任務，不能證明跨模型、跨目錄或跨帳戶都可靠。
