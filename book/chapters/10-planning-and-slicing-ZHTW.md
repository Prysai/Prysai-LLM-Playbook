# 第 10 章：規劃與豎向切片

**狀態：** candidate。**實驗狀態：** not_run。本章是與英文規範源對應的繁體中文候選譯文。
實驗是可在本地執行的低風險練習；本次內容編輯沒有替學習者執行它。

## 本章要解決的問題

“做完整個功能”“完成網站”或“讓工作流達到生產可用”聽起來像目標，卻還不是可執行的
計劃。它們把多種不確定性藏在一句話裡：

- 使用者最先應該觀察到什麼；
- 下一步有意義前，哪個假設必須成立；
- 哪些檔案、服務或人員在許可邊界內；
- 如何區分部分結果和可交付結果；以及
- 命令卡住、模型不可用或需求中途改變時，該做什麼。

Agent 可以寫出很長、很有條理的計劃，卻把第一項有意義的證據推到最後。它也可能完成
一個技術上很小的任務，卻留下無法使用的交接：檔案改了，但沒有人知道要跑什麼、還有什麼
沒被證明，或者重試會不會重複一次副作用。

因此，有用的工作單位不是待辦事項裡的一行，而是一條有邊界、可觀察的交付切片：一個小改動
產生結果，記錄證據，宣告限制，並給下一條切片留下安全介面。

![教學卡：生命週期檢查點把大目標變成攜帶證據的出口](../../assets/teaching/lifecycle-checkpoints.svg)

> 這是專案自有教學卡。它說明一種規劃方法；不證明 Agent、Skill、命令或外部服務
> 曾經執行。

## 學習目標

完成本章後，你應當能夠：

- 把模糊結果改寫為三到七條帶明確依賴的交付切片；
- 區分橫向技術計劃、豎向切片和低成本發現探針；
- 寫出含結果、輸入、允許動作、非目標、證據、變更預算、停止條件和交接介面的切片卡；
- 在不可逆動作前設定檢查點，並保留足以從中斷或上下文丟失中恢復的狀態；
- 設計一個狹窄、冪等的重試，而不是對半成品盲目繼續；以及
- 向他人誠實交接已完成、已受阻，以及現有證據仍不能證明的內容。

## 現實問題入口：計劃必須經得起中斷

專案的現場研究記錄了長時間、多步驟 Agent 工作的一些警訊：有公開 Codex 報告描述任務
遇到容量錯誤後，後續繼續操作面對未完成工作樹的不確定性；另一份報告描述格式化或驗證命令
長時間停在 Working，始終沒有完成訊號；Hacker News 的討論則反映，當複雜任務超過一段對話
的承載範圍時，外化計劃、待辦和狀態的實際需求。

這些是報告，不是普適的產品診斷。它們不能證明佇列語義、根因、每個賬戶的修復方法，或某個
釋出版本的保證。它們在這裡有價值，是因為即使原因未知，規劃問題依然成立：人在決定是否繼續
前，能否知道最後一次確認了什麼？

| 報告症狀 | 證據能支援什麼 | 它不能證明什麼 | 規劃響應 |
|---|---|---|---|
| 長任務中模型不可用 | 報告者觀察到執行中斷和不明確的部分狀態 | 服務端原因、佇列行為或所有賬戶的表現 | 凍結新指令；重試一個切片前檢查工作樹、最後輸出和檢查點 |
| 格式化或驗證持續停在 Working | 報告者在該次執行未看到有效完成訊號 | 普遍死鎖或準確的子程序根因 | 設定無進展閾值，儲存標準輸出、錯誤、退出碼和變更檔案 |
| 複雜任務需要可見待辦或計劃 | 社群討論認為外部狀態能讓長任務更容易追蹤 | 可見計劃一定改善每一種模型或任務 | 要求決策摘要、diff、檢查結果和下一項動作；不要把轉圈當作交付證據 |

這一區分很重要。計劃不是 Agent 必定完成的承諾；它是一個控制面，讓人能暫停、檢查並在不猜測
的情況下做下一次決定。

## 方法：從結果走向攜帶證據的切片

### 1. 先命名結果，再命名工作

先寫一句使用者、審查者或下游系統可以觀察到的話：

> 新貢獻者能閱讀一頁內容，在無需網路的情況下執行一項本地檢查，並看到明確的透過或失敗結果。

這句話比“搭建文件流水線”更強，因為它給計劃一個要保護的物件。再把它改寫成結果卡：

~~~text
結果：某人現在能做什麼或檢查什麼
輸入：檔案、資料、假設和前置條件
允許動作：準確的操作面與允許的變更型別
非目標：刻意推遲的、看似吸引人的工作
證據：檔案、diff、命令輸出、測試、截圖或審查記錄
風險：秘密、外部呼叫、持久化、刪除或不可逆改動
~~~

如果結果必須等全部未來功能完成後才可觀察，應先設計更小的結果。“API、介面、遷移、分析和
部署全部完成”是釋出里程碑，不是第一條切片。

### 2. 把依賴畫成事實，不是願望清單

依賴的含義是：“下一項動作能產生有意義結果之前，這件事必須為真。”它不只是
“這個專案在工單裡排得更靠前”。

對每個候選項都問四個問題：

1. **依賴於：** 哪個準確狀態或證據必須先存在？
2. **提供給：** 下一條切片會獲得哪個檔案、欄位、命令結果或決定？
3. **受阻於：** 哪個缺失輸入不能安全地猜測？
4. **依賴檢查：** 哪項最便宜的只讀檢查能證明前置條件存在？

這會把“資料庫 → API → 介面 → 部署”這類模糊序列改成可檢查的內容：

~~~text
切片 A：固定示例記錄可在本地讀取
  提供：示例資料形狀和一項透過的讀取檢查
切片 B：一個只讀端點返回該記錄
  依賴於：A；提供：可觀察的 API 響應
切片 C：一個介面渲染端點響應
  依賴於：B；提供：使用者可見路徑
切片 D：該路徑在可丟棄構建中被檢查
  依賴於：C；提供：構建輸出和可審查 diff
~~~

箭頭描述的是證據和介面，不是隱藏的 Agent 記憶。若某個依賴未被檢查，應標為
assumed，而不是悄悄當作已成立。

### 3. 選擇正確的計劃形狀

三種計劃形狀都有用，但回答的問題不同：

| 計劃形狀 | 擅長解決什麼 | 典型失敗 | 適用場景 |
|---|---|---|---|
| 橫向 | 展示全部技術層、責任歸屬或釋出前置項 | 第一個真實使用者結果被推遲到很多層完成後 | 需要能力地圖或責任審查 |
| 按檔案/順序 | 定位編輯，讓小改動易於審查 | 計劃跟著倉庫順序走，而非使用者價值 | 改動已理解且確實區域性 |
| 豎向 | 證明從輸入到可觀察結果的一條細路徑 | 第一條切片被做得太大，悄悄變成“整個功能” | 需要早期反饋、可逆實驗或交接 |

<mark class="highlight-text highlight-cyan">豎向切片不是“後端的一小塊”。</mark>
它只跨越展示一個結果所需的最少邊界。它可以同時觸及文件、指令碼和測試，但應排除無關潤色、
額外角色、生產資料和未來抽象。

當主要問題仍未知時，使用**探針**。探針是低成本、只讀或可逆的調查，例如檢查依賴是否存在、
渲染一個樣本，或確認一次無害工具呼叫能到達目標面。不要把探針偽裝成產品工作；它的產物應是
一個決定：繼續、收窄或停止。

### 4. 使用切片卡，而不是一堆任務

把這個簡明結構複製到任務記錄中：

~~~text
slice_id：S-01
outcome：一項使用者或團隊可觀察的結果
depends_on：先必須存在的準確狀態、檔案或證據
provides_to：下一條切片的準確輸入
inputs：具名檔案、夾具、版本和假設
allowed_actions：此切片允許的路徑和動作類別
non_goals：不會改動、安裝、釋出或推斷的內容
change_budget：預期檔案、命令和外部影響
acceptance_evidence：稱切片透過所需的準確證明
failure_signal：失敗或卡住會呈現什麼可觀察訊號
stop_condition：何時保留狀態並請求決定
recovery：一次最小且安全的重試或回滾路徑
handoff：狀態、證據路徑、剩餘風險和下一項動作
~~~

這些欄位防止一種常見替換：把“某人能夠做 X”替換成“Agent 編輯了 Y 和 Z 檔案”。
檔案是實現證據，不會自動成為交付證據。

### 5. 設定變更預算和檢查點

執行前，估計一個刻意狹窄的預算：

- 允許變動的檔案；
- 允許執行的命令；
- 最大重試次數或無進展等待時間；
- 是否允許網路、憑據、安裝或持久狀態；
- 不可逆動作前所需的人類確認；以及
- 切片停止時要保留的產物。

預算不是 token 用量預測，而是副作用邊界。若切片需要預算外檔案、新依賴、生產憑據或
另一個倉庫，應停止並更新計劃。“驗證時需要”不會靜默授予安裝或部署許可權。

每個檢查點至少記錄：

~~~text
目標與當前切片：
已完成動作與證據：
工作樹 / 分支 / 目標路徑：
變更檔案與基線比較：
最後命令、輸出和退出狀態：
許可權與外部副作用狀態：
開放假設或阻塞項：
下一項單一動作：
~~~

檢查點必須存在於 Agent 的短期對話狀態之外。一份小 Markdown 檔案、Issue 記錄或已批准的
任務記錄已經足夠。不要把秘密、Cookie、token 或私有憑據寫進去。

### 6. 判斷切片是否真的足夠小

當標題包含多個獨立使用者結果、混合實現/遷移/釋出、需要多種驗收權威，或能在多個層面失敗卻
沒有第一處斷點時，切片多半太大。若第一份有用證據只能在末尾出現，應拆分它。

當切片建立一個無法閱讀、執行、審查或接入可觀察行為的孤立檔案，或者只是後續切片所需的
私有重構時，它多半太小。除非該重構本身是刻意探針，否則應與最近的可觀察切片合併。

實用測試是：

> 一個沒有參與原對話的審查者，能否檢視產物並回答：“改了什麼、如何檢查、未證明什麼、
> 接下來可以安全做什麼？”

如果不能，切片需要更好的介面或更小的結果。

## 可複用的規劃提示詞

把下列內容作為起點。替換示例值；不要原封不動貼上到生產任務中。

~~~text
目標
交付一條豎向切片：[一名具名使用者或審查者可觀察的結果]。

上下文與輸入
- 倉庫/工作區：[絕對路徑或已批准的操作面]
- 相關檔案和夾具：[準確路徑]
- 基線：[分支/提交/雜湊/狀態或儲存的副本]
- 已知假設：[尚未確認的事實]

範圍契約
- 允許動作：[讀/編輯/執行/檢查，以及準確路徑]
- 變更預算：[檔案、命令、重試/時間上限]
- 非目標：[排除的功能、安裝、網路呼叫、部署或清理]
- 以下動作前需要人工確認：[不可逆或外部動作]

切片設計
- depends_on：[前置條件及其廉價檢查]
- provides_to：[下一條切片的準確輸入]
- acceptance_evidence：[diff、命令輸出、測試、渲染或審查記錄]
- failure_signal：[可觀察錯誤、缺失輸出、超時或範圍漂移]

執行規則
1. 編輯前檢查基線，並報告任何已有改動。
2. 第一次變更前寫切片卡和檢查點。
3. 做能產生既定證據的最小動作。
4. 每次動作後報告變更狀態；不要從轉圈、token 數或自己的完成摘要推斷成功。
5. 若依賴缺失、目標路徑不一致、命令在[時間上限]內沒有有效事件，或預算超出，停止並保留
   檢查點。不要安裝、釋出、刪除或擴大許可權。
6. 恢復時重讀目標，對比基線和 diff，並且只以一個改變的變數重試一次冪等動作。

交付
返回：狀態（passed / blocked / unverified）、變更檔案、準確證據、失敗嘗試、剩餘未知項、
回滾或恢復路徑，以及下一項單一動作。若缺少驗收證據，不要稱切片完成。
~~~

提示詞本身不會讓 Agent 可靠。它的價值在於把對話式請求變成另一個人可以審查的契約。

## 小實驗：三種計劃，一條安全切片

本實驗不使用網路、安裝、憑據、提交、推送、部署或生產資料。請使用臨時目錄，而非包含他人
修改的工作樹。

### 準備

建立一個臨時資料夾，其中的 README.md 只包含：

~~~markdown
## Slice Lab

起點：頁面還沒有說明改了什麼或如何檢查。
~~~

驗收目標刻意很小：讀者必須能看到“改了什麼”和“如何驗證”兩個小節。本地檢查為只讀搜尋。
在 PowerShell 中：

~~~powershell
$text = Get-Content -Raw README.md
$required = '# Slice Lab', '## What changed', '## How to verify'
$missing = $required | Where-Object { $text -notmatch [regex]::Escape($_) }
if ($missing) { $missing | ForEach-Object { "MISSING: $_" }; exit 1 }
'PASS: required headings found'; exit 0
~~~

在其他 Shell 中使用等效的無網路檢查：任一標題缺失時返回非零狀態。記錄你實際使用的命令。

### 任務

為同一個目標各寫一份不超過七項的計劃：

1. 按寫作、工具、審查和釋出分層的橫向計劃；
2. 按預計會觸及的檔案順序排列的計劃；
3. 先做最小可閱讀、可檢查頁面的豎向計劃。

每一項都必須有結果、依賴、證據和停止條件。隨後只執行豎向計劃的第一項：新增兩個標題，
並在每個標題下寫一句真實的話。不要新增樣式、連結、構建系統或未來部分。

編輯前後記錄目標路徑與 diff，並執行一次本地檢查。你的證據記錄應讓陌生人回答：

- 基線是什麼？
- 哪份計劃更早產出了第一個可觀察結果？
- 改了哪些檔案？
- 跑了哪條準確命令，它的退出狀態是什麼？
- 哪些內容被刻意排除在範圍外？

### 預期證據

在臨時目錄中儲存一個小型 slice-record.md（或等效且獲批的記錄）：

~~~text
baseline：編輯前的 README.md
chosen_plan：vertical
changed_files：僅 README.md
check：[準確命令]
result：[準確輸出和退出狀態]
acceptance：passed / failed / not_observed
not_proven：樣式、構建、部署、使用者驗收
next_slice：[一項有邊界的下一步]
~~~

預期產物不是“一份漂亮的 README”，而是一項小而可審查的變更，以及足以判斷下一條切片是否
安全的證據。

## 故意失敗：讓斷點可見

現在製造一次受控失敗：從 README.md 刪除 “## How to verify”，或讓檢查讀取一個不存在的
路徑。執行檢查一次並儲存非零輸出。不要為了讓錯誤消失而新增依賴、改變許可權，或重寫整頁。

可觀察訊號應是以下之一：

- MISSING: ## How to verify，且退出狀態非零；或
- 目標路徑錯誤時出現明確的找不到檔案錯誤。

恢復前先分類：

| 訊號 | 分類 | 第一項恢復動作 |
|---|---|---|
| 必需標題缺失 | 內容驗收失敗 | 只恢復缺失標題，然後重跑同一檢查 |
| 檢查指向錯誤檔案 | 測試/輸入失敗 | 重讀目標路徑；只有切片契約允許時才修正檢查 |
| 在所選閾值內沒有輸出 | 未知執行狀態 | 停止等待；儲存命令、時間、程序狀態和 diff |
| 修復需要安裝、網路呼叫或更寬路徑 | 範圍/授權失敗 | 停止並請求新決定；不要靜默“修復”環境 |

恢復後寫下改了什麼，以及失敗**沒有**證明什麼。一項失敗檢查只證明該檢查沒有對這個輸入透過；
它不證明整個倉庫損壞、Agent 損壞，或應當進行更大的重寫。

## 真實工作中的恢復與停止條件

長任務中斷後，不要傳送無條件的“繼續”。按以下順序：

1. **凍結新副作用。** 狀態未明時，不要排隊另一項寫入、外部請求、安裝、刪除或部署。
2. **檢查最後已知狀態。** 讀取檢查點、git status、相關 diff、最後命令輸出和真實目標路徑。
3. **分類斷點。** 標為缺失輸入、範圍漂移、驗證失敗、基礎設施/超時、許可權或未知。
4. **選擇一項有界動作。** 優先只讀探針，或對最小切片做冪等重試；一次只改變一個變數。
5. **更新檢查點。** 記錄新證據，以及下一條切片是否仍有效。
6. **停止或交接。** 若原因仍未知、重試預算耗盡或目標改變，交付受阻交接，而非繼續堆疊編輯。

只有部分狀態不安全、誤導性強或攜帶成本過高時才回滾。回滾前保留失敗證據；不要為了取得
看似乾淨的工作樹而丟棄使用者已有修改。若部分產物安全且有資訊價值，保留它並標為 partial 或
unverified。

停止規則可以寫得很直白：

> 沒有新證據、沒有新授權，或沒有穩定目標，就不自動繼續。

這條規則在上下文壓縮、模型容量錯誤、長時間命令、工作樹改變，或提示詞提出另一個結果時格外
重要。對話摘要可能保留意圖，卻不一定保留準確檔案狀態、程序狀態或外部副作用。

## 預期產物：另一個人能執行的交接

即使結果受阻，一條完整切片也留下這些產物：

1. **切片卡：** 結果、依賴、範圍、證據、預算和停止條件。
2. **檢查點：** 最後確認狀態、目標身份、變更檔案、命令結果和下一項動作。
3. **實現 diff 或明確的無變更記錄：** 實際移動了什麼。
4. **驗證記錄：** 準確命令、環境、退出狀態、輸出和檢查範圍。
5. **失敗記錄：** 失敗輸入、可觀察訊號、已嘗試恢復，以及為何另一輪重試安全或不安全。
6. **交接說明：**

~~~text
status：passed / partial / blocked / unverified
done：[有證據支援的宣告]
changed：[準確路徑或 none]
evidence：[連結或產物路徑]
not_proven：[未出現的執行時、外部、視覺、安全或使用者宣告]
risks：[剩餘副作用或假設]
next：[一項有邊界的動作]
owner：[個人或團隊]
~~~

交接是切片的一部分，不是“真正工作”結束後補的文書。沒有它，下一位必須從漫長聊天記錄重建
狀態，並可能重複已經發生的動作。

## 反思

離開本章前，寫下一項仍然大到無法交給另一人的當前任務。哪條第一切片能產生最早的有意義
證據？哪項動作、輸入或決定必須明確排除在範圍外？如果在該切片後中斷，什麼記錄能讓別人
不靠猜測繼續？

## 遷移任務

從另一個領域選擇一項真實但低風險的任務，並寫三到七張切片卡：

- **工程：** 新增一個只讀端點和一個渲染固定夾具的介面。第一條切片排除認證、分析和部署。
- **研究：** 用來源表、不確定性列和邊界清楚的結論回答一個窄問題。來源未核查前，不要把搜尋
  結果稱為已驗證事實。
- **營銷：** 把一份已批准的產品上下文改成一份面向特定受眾的草稿和一項可審查實驗。排除釋出和
  實時受眾資料。
- **Skill 設計：** 描述一個觸發條件、輸入結構、允許動作、預期輸出、失敗路徑和複核日期。規劃
  練習中不要安裝或呼叫未經審查的外部 Skill。

讓一名同事，或一個新鮮 Agent 上下文，在不聽口頭解釋的情況下審查這些卡。他們的工作是找出
一個隱藏假設和一個缺失驗收訊號。修改切片卡，不要依賴審查者的記憶。

## 驗收清單

- [ ] 我能用一句話說出第一項使用者或審查者可觀察的結果。
- [ ] 我能區分橫向計劃、檔案順序計劃、豎向切片和發現探針。
- [ ] 每條切片都有 depends_on、provides_to、依賴檢查和具名非目標。
- [ ] 每條切片都有強於“Agent 說它完成了”的證據規則。
- [ ] 我在任何不可逆動作前設定了檔案/動作/變更預算和檢查點。
- [ ] 我能識別計劃何時因推遲第一份有意義證據而太大。
- [ ] 我能識別計劃何時因沒有可觀察行為或可審查介面而太小。
- [ ] 我能在超時、範圍改變、缺少授權或目標未知時停止，而不自動堆疊編輯。
- [ ] 我能透過重讀狀態、一次只改變一個變數，從部分結果恢復。
- [ ] 我能在交接中分開 done、partial、blocked、unverified、not_proven 和 next。
- [ ] 我能說明本章實驗仍為 not_run，直到存在本地執行記錄和審查證據。
