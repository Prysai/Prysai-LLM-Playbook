# 第 10 章：規劃與垂直切片

**狀態：** candidate。**實驗狀態：** not_run。本章是英文規範來源的繁體中文候選譯文。
實驗是一項可以在本機完成的低風險練習；本次編輯沒有代替學習者執行它。

## 本章要解決的問題

「把整個功能做完」、「把網站做完」或「讓工作流程達到正式環境可用」聽起來像目標，卻還不能直接執行。
這些說法把好幾種不確定性都藏在一句話裡：

- 使用者首先應該看到什麼；
- 下一步要有意義，哪個假設必須先成立；
- 哪些檔案、服務或人員屬於允許的範圍；
- 如何區分「做到一半」和「可以交付」；以及
- 命令卡住、模型不可用，或需求做到一半發生變化時，該怎麼辦。

Agent 可以寫出很長、看起來很有條理的計劃，卻把第一份有意義的證據一直推到最後。它也可能完成
一個技術上很小的任務，卻留下無法接手的結果：檔案改了，但沒人知道該執行什麼、哪些事情還沒有
得到證明，也不知道重試會不會再次產生副作用。

所以，真正有用的工作單位不是待辦清單中的一行，而是一條有邊界、可以觀察的交付切片：用一次小改動
產生結果、留下證據、說明限制，並為下一條切片留下安全的銜接點。

![教學卡：生命週期檢查點把大目標拆成帶有證據的交付節點](../../assets/teaching/lifecycle-checkpoints.svg)

> 這是專案自有的教學卡。它說明一種規劃方法；不證明 Agent、Skill、命令或外部服務
> 曾經執行。

## 學習目標

完成本章後，你應該能夠：

- 把模糊結果改寫為三到七條、帶有明確依賴關係的交付切片；
- 區分橫向技術計劃、垂直切片和低成本的發現探針；
- 寫出含結果、輸入、允許動作、非目標、證據、變更預算、停止條件和交接介面的切片卡；
- 在不可逆動作前設定檢查點，並保留足以從中斷或上下文遺失中復原的狀態；
- 設計一個狹窄、冪等的重試，而不是對半成品盲目繼續；以及
- 向他人誠實交接已完成、已受阻，以及現有證據仍不能證明的內容。

## 現實問題入口：計劃必須經得起中斷

專案的現場研究記錄了長時間、多步驟 Agent 工作的一些警訊：公開的 Codex 報告描述任務
遇到容量錯誤後，接下來的操作面對未完成工作樹的不確定性；另一份報告描述格式化或驗證命令
長時間停在 Working，始終沒有完成訊號；Hacker News 的討論則反映，當複雜任務超過一段對話
能承載的範圍時，把計劃、待辦和狀態記錄在對話之外確實有需要。

這些是報告，不是普遍適用的產品診斷。它們不能證明佇列語意、根因、每個帳戶的修復方法，或某個
發布版本的保證。它們在這裡有價值，是因為即使原因未知，規劃問題仍然成立：人在決定是否繼續
之前，能不能知道最後一次確認了什麼？

| 報告症狀 | 證據能支持什麼 | 它不能證明什麼 | 規劃回應 |
|---|---|---|---|
| 長任務中模型不可用 | 報告者觀察到執行中斷，且部分狀態不明 | 伺服器端原因、佇列行為或所有帳戶的表現 | 凍結新指令；重試一個切片前，先檢查工作樹、最後輸出和檢查點 |
| 格式化或驗證持續停在 Working | 報告者在該次執行中沒有看到有效的完成訊號 | 普遍死鎖或準確的子程序根因 | 設定「沒有進展」的時間門檻，儲存標準輸出、錯誤、退出碼和變更檔案 |
| 複雜任務需要可見的待辦或計劃 | 社群討論指出，把狀態記在對話之外能讓長任務更容易追蹤 | 可見計劃一定會改善每一種模型或任務 | 要求決策摘要、diff、檢查結果和下一項動作；不要把轉圈畫面當成交付證據 |

這個區分很重要。計劃不是 Agent 一定會完成的承諾，而是一個控制面，讓人可以暫停、檢查，並在不靠猜測
的情況下做出下一步決定。

## 方法：從結果拆出帶有證據的切片

### 1. 先命名結果，再命名工作

先寫一句使用者、審查者或下游系統可以直接觀察到的話：

> 新貢獻者能閱讀一頁內容，在不連網的情況下執行一項本機檢查，並看到明確的通過或失敗結果。

這句話比「建立文件流水線」更有用，因為它清楚說明計劃要保護的結果。再把它改寫成一張結果卡：

~~~text
結果：現在有人能做什麼，或能檢查什麼
輸入：檔案、資料、假設和前置條件
允許動作：準確的操作範圍和允許的變更類型
非目標：這次刻意延後、雖然誘人但不在範圍內的工作
證據：檔案、diff、命令輸出、測試、截圖或審查記錄
風險：秘密資訊、外部呼叫、持久化、刪除或不可逆的修改
~~~

如果必須等未來所有功能都完成後才能看到結果，就先把結果拆小。「API、介面、遷移、分析和
部署全部完成」是發布里程碑，不是第一條切片。

### 2. 把依賴畫成事實，不是願望清單

依賴的意思是：「下一步動作要產生有意義的結果，這件事必須先成立。」它不只是
「這項工作在工單裡排在前面」。

對每個候選項都問四個問題：

1. **依賴於：** 哪個準確的狀態或證據必須先存在？
2. **提供給：** 下一條切片會拿到哪個檔案、欄位、命令結果或決定？
3. **受阻於：** 哪個缺少的輸入不能安全猜測？
4. **依賴檢查：** 哪項成本最低的唯讀檢查可以確認前置條件已經存在？

這會把「資料庫 → API → 介面 → 部署」這類模糊順序改成可以檢查的內容：

~~~text
切片 A：固定範例記錄可在本機讀取
  提供：範例資料形狀和一項通過的讀取檢查
切片 B：一個只讀端點返回該記錄
  依賴於：A；提供：可觀察的 API 響應
切片 C：一個介面渲染端點響應
  依賴於：B；提供：使用者可見路徑
切片 D：該路徑在可丟棄構建中被檢查
  依賴於：C；提供：構建輸出和可審查 diff
~~~

箭頭代表的是證據和交接介面，不是 Agent 隱藏的記憶。如果依賴還沒有檢查，就標為
assumed，不要默默把它當成已經成立。

### 3. 選擇合適的計劃形狀

三種計劃形狀都有用，但回答的問題不同：

| 計劃形狀 | 擅長解決什麼 | 典型失敗 | 適用場景 |
|---|---|---|---|
| 橫向 | 展示所有技術層、責任歸屬或發布前置項 | 第一個真實使用者結果被推遲到多個層次都完成之後 | 需要能力地圖或責任審查 |
| 按檔案／順序 | 定位編輯，讓小改動容易審查 | 計劃跟著儲存庫順序走，而不是跟著使用者價值走 | 改動已經理解，而且確實是局部變更 |
| 垂直 | 證明從輸入到可觀察結果的一條細路徑 | 第一條切片做得太大，悄悄變成「整個功能」 | 需要早期回饋、可逆實驗或交接 |

<mark class="highlight-text highlight-cyan">垂直切片不是「後端的一小塊」。</mark>
它只跨過展示一個結果所需的最少邊界。它可以同時涉及文件、指令碼和測試，但應排除無關潤色、
額外角色、生產資料和未來抽象層。

當主要問題還沒有答案時，使用**探針**。探針是低成本、唯讀或可逆的調查，例如檢查依賴是否存在、
渲染一個樣本，或確認一次無害的工具呼叫能到達目標範圍。不要把探針包裝成產品工作；它的產物應該是
一個決定：繼續、縮小範圍，還是停止。

### 4. 使用切片卡，不要堆一串任務

把這個簡明結構複製到任務記錄中：

~~~text
slice_id：S-01
outcome：一項使用者或團隊可觀察的結果
depends_on：先必須存在的準確狀態、檔案或證據
provides_to：下一條切片的準確輸入
inputs：具名檔案、夾具、版本和假設
allowed_actions：此切片允許的路徑和動作類別
non_goals：不會改動、安裝、發布或推斷的內容
change_budget：預期檔案、命令和外部影響
acceptance_evidence：宣告切片通過所需的準確證據
failure_signal：失敗或卡住會呈現什麼可觀察訊號
stop_condition：何時保留狀態並請求決定
recovery：一次最小且安全的重試或回滾路徑
handoff：狀態、證據路徑、剩餘風險和下一項動作
~~~

這些欄位可以防止一種常見的偷換：把「某人能夠完成 X」換成「Agent 編輯了 Y 和 Z 檔案」。
檔案是實作證據，但不會自動變成交付證據。

### 5. 設定變更預算和檢查點

執行前，先訂一個刻意收窄的預算：

- 允許修改的檔案；
- 允許執行的命令；
- 最大重試次數，或允許沒有進展多久；
- 是否允許使用網路、憑據、安裝或持久狀態；
- 不可逆動作前需要哪位人確認；以及
- 切片停止時要保留的產物。

預算不是 token 用量預測，而是副作用的邊界。如果切片需要預算外檔案、新依賴、生產憑據或
另一個儲存庫，就應該停下來更新計劃。「驗證需要」不會自動授予安裝或部署權限。

每個檢查點至少記錄：

~~~text
目標與目前切片：
已完成動作與證據：
工作樹 / 分支 / 目標路徑：
變更檔案與基線比較：
最後命令、輸出和退出狀態：
權限與外部副作用狀態：
開放假設或阻塞項：
下一項單一動作：
~~~

檢查點必須保存在 Agent 的短期對話狀態之外。一份小 Markdown 檔案、Issue 記錄或已批准的
任務記錄就足夠。不要把秘密資訊、Cookie、token 或私有憑據寫進去。

### 6. 判斷切片是否真的足夠小

如果標題包含多個獨立的使用者結果、把實作／遷移／發布混在一起、需要多種驗收權威，或者可能在多個層面失敗卻
沒有第一處斷點，切片多半太大。如果第一份有用證據只能到最後才出現，就應該拆開。

如果切片只建立了一個無法閱讀、執行、審查或連接到可觀察行為的孤立檔案，或者只是後續切片所需的
內部重構，它多半又太小。除非這個重構本身就是刻意設計的探針，否則應與最近的可觀察切片合併。

實用測試是：

> 一個沒有參與原對話的審查者，能不能檢視產物並回答：「改了什麼、如何檢查、還沒證明什麼，
> 接下來可以安全做什麼？」

如果不能，切片就需要更清楚的交接介面，或更小的結果。

## 可複用的規劃提示詞

把下面的內容當作起點，替換示例值；不要原封不動貼到正式任務中。

~~~text
目標
交付一條垂直切片：[一名具名使用者或審查者可觀察的結果]。

上下文與輸入
- 倉庫/工作區：[絕對路徑或已批准的操作面]
- 相關檔案和夾具：[準確路徑]
- 基線：[分支/提交/雜湊/狀態或儲存的副本]
- 已知假設：[尚未確認的事實]

範圍契約
- 允許動作：[讀/編輯/執行/檢查，以及準確路徑]
- 變更預算：[檔案、命令、重試/時間上限]
- 非目標：[排除的功能、安裝、網路呼叫、部署或清理]
- 以下動作前需要人工確認：[不可逆或外部動作]

切片設計
- depends_on：[前置條件及其廉價檢查]
- provides_to：[下一條切片的準確輸入]
- acceptance_evidence：[diff、命令輸出、測試、渲染或審查記錄]
- failure_signal：[可觀察錯誤、缺失輸出、超時或範圍漂移]

執行規則
1. 編輯前檢查基線，並報告任何已有改動。
2. 第一次變更前寫切片卡和檢查點。
3. 做能產生既定證據的最小動作。
4. 每次動作後報告變更狀態；不要從轉圈、token 數或自己的完成摘要推斷成功。
5. 若依賴缺失、目標路徑不一致、命令在[時間上限]內沒有有效事件，或預算超出，停止並保留
   檢查點。不要安裝、發布、刪除或擴大權限。
6. 復原時重讀目標，對比基線和 diff，並且只以一個改變的變數重試一次冪等動作。

交付
返回：狀態（passed / blocked / unverified）、變更檔案、準確證據、失敗嘗試、剩餘未知項、
回滾或復原路徑，以及下一項單一動作。若缺少驗收證據，不要稱切片完成。
~~~

提示詞本身不會讓 Agent 變得可靠。它的價值在於把對話式請求變成另一個人可以審查的契約。

## 小實驗：三種計劃，一條安全的切片

本實驗不使用網路、安裝、憑據、提交、推送、部署或生產資料。請使用臨時目錄，不要使用包含他人
修改的工作樹。

### 準備

建立一個臨時資料夾，裡面的 README.md 只包含：

~~~markdown
## Slice Lab

起點：頁面還沒有說明改了什麼或如何檢查。
~~~

驗收目標故意設得很小：讀者必須能看到「改了什麼」和「如何驗證」兩個小節。本機檢查是唯讀搜尋。
在 PowerShell 中：

~~~powershell
$text = Get-Content -Raw README.md
$required = '# Slice Lab', '## What changed', '## How to verify'
$missing = $required | Where-Object { $text -notmatch [regex]::Escape($_) }
if ($missing) { $missing | ForEach-Object { "MISSING: $_" }; exit 1 }
'PASS: required headings found'; exit 0
~~~

在其他 Shell 中使用等效的無網路檢查：任一標題缺失時返回非零狀態。記錄你實際執行的命令。

### 任務

圍繞同一個目標，各寫一份不超過七項的計劃：

1. 按寫作、工具、審查和發布分層的橫向計劃；
2. 按預計會觸及的檔案順序排列的計劃；
3. 先做最小可閱讀、可檢查頁面的垂直計劃。

每一項都必須有結果、依賴、證據和停止條件。接著只執行垂直計劃的第一項：新增兩個標題，
並在每個標題下寫一句真實的話。不要新增樣式、連結、建置系統或未來的章節。

編輯前後記錄目標路徑和 diff，並執行一次本機檢查。你的證據記錄應該讓一個陌生人回答：

- 基線是什麼？
- 哪份計劃更早產出了第一個可觀察結果？
- 改了哪些檔案？
- 跑了哪條準確命令，它的退出狀態是什麼？
- 哪些內容被刻意排除在範圍外？

### 預期證據

在臨時目錄中儲存一個小型 slice-record.md（或等效且獲批的記錄）：

~~~text
baseline：編輯前的 README.md
chosen_plan：vertical
changed_files：僅 README.md
check：[準確命令]
result：[準確輸出和退出狀態]
acceptance：passed / failed / not_observed
not_proven：樣式、構建、部署、使用者驗收
next_slice：[一項有邊界的下一步]
~~~

預期產物不是「一份漂亮的 README」，而是一項小而可審查的變更，以及足以判斷下一條切片是否安全的證據。

## 故意失敗：讓斷點可見

現在製造一次受控失敗：從 README.md 刪除「## How to verify」，或讓檢查讀取一個不存在的
路徑。執行檢查一次並儲存非零輸出。不要為了讓錯誤消失而新增依賴、改變權限或重寫整頁。

可觀察訊號應是以下之一：

- MISSING: ## How to verify，且退出狀態非零；或
- 目標路徑錯誤時出現明確的找不到檔案錯誤。

復原前先分類：

| 訊號 | 分類 | 第一項復原動作 |
|---|---|---|
| 必需標題缺失 | 內容驗收失敗 | 只復原缺失標題，然後重跑同一檢查 |
| 檢查指向錯誤檔案 | 測試/輸入失敗 | 重讀目標路徑；只有切片契約允許時才修正檢查 |
| 在所選閾值內沒有輸出 | 未知執行狀態 | 停止等待；儲存命令、時間、程序狀態和 diff |
| 修復需要安裝、網路呼叫或更寬路徑 | 範圍／授權失敗 | 停止並請求新決定；不要靜默「修復」環境 |

復原後寫下改了什麼，以及失敗**沒有**證明什麼。一次失敗的檢查只能證明該檢查沒有在這個輸入上通過；
它不能證明整個儲存庫或 Agent 已經損壞，也不能證明應該進行更大範圍的重寫。

## 真實工作中的復原與停止條件

長任務中斷後，不要無條件地傳送「繼續」。請依照以下順序處理：

1. **凍結新的副作用。** 狀態不明時，不要排隊另一項寫入、外部請求、安裝、刪除或部署。
2. **檢查最後已知狀態。** 讀取檢查點、git status、相關 diff、最後的命令輸出和真實目標路徑。
3. **分類斷點。** 標為輸入缺失、範圍漂移、驗證失敗、基礎設施／逾時、權限或未知。
4. **選擇一項有邊界的動作。** 優先做唯讀探針，或對最小切片進行冪等重試；一次只改變一個變數。
5. **更新檢查點。** 記錄新的證據，以及下一條切片是否仍然有效。
6. **停止或交接。** 如果原因仍未知、重試預算已用完或目標已改變，就交付受阻交接，不要繼續堆疊編輯。

只有在部分狀態不安全、容易誤導或維護成本太高時才回滾。回滾前先保留失敗證據；不要為了取得
看起來乾淨的工作樹而丟棄使用者已有的修改。如果部分產物安全且有資訊價值，就保留它，並標為 partial 或
unverified。

停止規則可以寫得很直白：

> 沒有新證據、沒有新授權，或沒有穩定目標，就不自動繼續。

這條規則在上下文壓縮、模型容量錯誤、長時間執行的命令、工作樹發生變化，或提示詞要求另一個結果時尤其
重要。對話摘要可能保留意圖，卻不一定保留準確的檔案狀態、程序狀態或外部副作用。

## 預期產物：另一個人可以執行的交接

即使結果受阻，一條完整的切片也會留下這些產物：

1. **切片卡：** 結果、依賴、範圍、證據、預算和停止條件。
2. **檢查點：** 最後確認狀態、目標身份、變更檔案、命令結果和下一項動作。
3. **實現 diff 或明確的無變更記錄：** 實際移動了什麼。
4. **驗證記錄：** 準確命令、環境、退出狀態、輸出和檢查範圍。
5. **失敗記錄：** 失敗輸入、可觀察訊號、已嘗試恢復，以及為何另一輪重試安全或不安全。
6. **交接說明：**

~~~text
status：passed / partial / blocked / unverified
done：[有證據支持的宣告]
changed：[準確路徑或 none]
evidence：[連結或產物路徑]
not_proven：[未出現的執行時、外部、視覺、安全或使用者宣告]
risks：[剩餘副作用或假設]
next：[一項有邊界的動作]
owner：[個人或團隊]
~~~

交接是切片的一部分，不是「真正的工作」結束後才補的文書。沒有它，下一位就得從漫長的聊天記錄重建
狀態，還可能重複已經發生的動作。

## 反思

離開本章前，寫下一項目前仍然大到無法交給別人的任務。哪一條第一切片能最早產生有意義的
證據？哪項動作、輸入或決定必須明確排除在範圍外？如果在這條切片後中斷，什麼記錄能讓別人
不靠猜測繼續？

## 遷移任務

從另一個領域選擇一項真實但低風險的任務，並寫3到7張切片卡：

- **工程：** 新增一個只讀端點和一個顯示固定夾具的介面。第一條切片排除認證、分析和部署。
- **研究：** 用來源表、不確定性欄位和邊界清楚的結論回答一個窄問題。在來源核查前，不要把搜尋
  結果稱為已驗證事實。
- **行銷：** 把一份已核准的產品上下文改成面向特定受眾的草稿，再設計一項可審查的實驗。排除發布和
  即時受眾資料。
- **Skill 設計：** 寫清一個觸發條件、輸入結構、允許動作、預期輸出、失敗路徑和複核日期。在規劃
  練習中，不要安裝或呼叫未經審查的外部 Skill。

讓一名同事，或一個全新的 Agent 上下文，在沒有口頭解釋的情況下審查這些卡。他們要找出
一個隱藏假設和一個缺少的驗收訊號。直接修改切片卡，不要依賴審查者的記憶。

## 驗收清單

- [ ] 我能用一句話說出第一項使用者或審查者可以觀察到的結果。
- [ ] 我能區分橫向計劃、檔案順序計劃、垂直切片和發現探針。
- [ ] 每條切片都有 depends_on、provides_to、依賴檢查和明確寫出的非目標。
- [ ] 每條切片都有強於「Agent 說它完成了」的證據規則。
- [ ] 我在任何不可逆動作前都設定了檔案／動作／變更預算和檢查點。
- [ ] 我能識別計劃何時因延後第一份有意義的證據而變得太大。
- [ ] 我能識別計劃何時因沒有可觀察行為或可審查介面而變得太小。
- [ ] 我能在逾時、範圍改變、缺少授權或目標未知時停止，而不自動堆疊編輯。
- [ ] 我能透過重新讀取狀態、一次只改變一個變數，從部分結果中復原。
- [ ] 我能在交接中區分 done、partial、blocked、unverified、not_proven 和 next。
- [ ] 在沒有本機執行記錄和審查證據前，我能說明本章實驗仍為 not_run。
