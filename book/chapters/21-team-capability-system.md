# 第二十一章：建立团队能力系统

> `content_status: candidate`
> `experiment_status: draft / not run`
> 本章的权限实验是静态模拟；它不授权、不连接、不发送、不写入，也不证明生产连接可用。

## 问题：个人经验怎样变成团队可复用能力

个人可以凭经验让 Codex 完成任务，团队却会遇到另一组问题：谁知道这条规则？哪个 Skill 可以信任？谁负责更新？成员是否拥有过大的权限？一个成功案例能否在没有口头补充的情况下复现？如果没有共享语言、证据和责任，团队只是在共享不透明的个人习惯。

## 现实问题入口

FP-03（host/组织识别不一致）和 FP-04（多组织授权范围混淆）是公开问题记录，不是所有连接器行为的普遍结论；本章只把它们用于检查 host、组织、权限和责任是否被明确记录。

## 学习目标

读者完成本章后应当能够：

- 把个人方法拆成共同语言、方法、证据和治理四层；
- 交付含目录、版本、owner、来源、权限表和回滚说明的能力包；
- 让另一位成员在临时副本中独立复现关键流程；
- 把使用、修改、运行、推送、发布和改权限分给不同责任；
- 在能力失效、来源变化或权限过宽时阻塞、回滚、迁移或下线。

## 概念：团队能力包的四层

```text
共同语言与项目规则
        ↓
可复用方法与 Skill
        ↓
实验、任务集与证据标准
        ↓
权限、审查、版本与维护责任
```

共同语言让成员理解相同的术语；方法层规定有限的输入、触发、行动和停止；证据层证明声明范围内的行为；治理层决定谁能修改、发布、使用和撤销。没有证据层，方法只是建议；没有治理层，方法可能传播过时事实或扩大权限。

## 决策：行动权限与责任表

团队审批不能只写“已登录”或“有权限”。每项能力至少按以下字段做决定：

| 行动级别 | 数据范围 | 技术权限 | 任务授权 | 审批人 | 必需证据 | 回滚/复核 |
|---|---|---|---|---|---|---|
| 只读分析 | 脱敏临时副本 | read-only | 明确任务范围 | 任务 owner | 输入、来源、日志 | 丢弃副本；每次任务复核 |
| 编辑草稿 | 独立分支 | 受限写入 | 指定文件/目录 | owner + reviewer | 基线 hash、diff、验证 | 还原 diff；合并前复核 |
| 运行检查 | 测试数据 | 指定命令 | 命令和超时已列出 | 运行 owner | 日志、退出码、部分状态 | 停止进程/恢复副本 |
| 推送/发布 | 指定仓库/草稿端点 | 目标受限写入 | 明确发布请求 | reviewer/发布人 | 预览、验收、回滚 | 版本回退；保留审计记录 |
| 改权限/处理秘密 | 最小必要范围 | 临时、可撤销 | 单独人工确认 | 指定授权人，必要时双人复核 | scope、期限、审计和回滚 | 立即撤销；再次复核 |

“能使用”不等于“能修改”，“能修改”不等于“能发布”。如果权限、目标、批准人或回滚不清楚，决策为 `blocked`，而不是先开放能力再补记录。

## 行动：能力包的最小目录和治理字段

能力包使用可检查的目录结构，名称可按团队调整，但不能删除必需职责：

```text
capability-pack/
├─ README.md                  # 目标、适用范围、快速复现、限制
├─ manifest.yaml              # id、version、owner、status、next_review
├─ context/
│  └─ project-context.md      # 术语、边界、可信来源、运行方式
├─ protocol/
│  └─ task-protocol.md        # 输入、决策、行动、停止和交付
├─ examples/
│  ├─ positive.md             # 正例
│  └─ failure.md              # 失败/边界例
├─ eval/
│  ├─ acceptance.md           # 验收标准和评分
│  └─ evidence-index.md       # 日志、diff、验证和未验证项索引
└─ governance/
   ├─ permission-matrix.md    # 数据、scope、审批和期限
   ├─ ownership.md            # owner、reviewer、替代联系人
   └─ rollback.md             # 回滚、迁移、下线和恢复
```

`manifest.yaml` 至少写：

```yaml
id: "team-capability-release-review"
version: "0.1.0"
owner: "姓名或团队角色"
status: "candidate"
source: "原创 | 改写 | 外部链接；附许可证记录位置"
next_review: "YYYY-MM-DD"
allowed_scope: "脱敏临时副本/指定测试仓库"
rollback: "删除临时副本或恢复到基线 hash"
```

能力包的版本是可追踪的变更标识，不是“已经验证”的同义词。`candidate` 表示结构存在但新鲜独立复现尚未充分。

## 实验：交付一个团队能力包

这是一个两人独立复现、低风险、无真实外部连接的实验。

### Setup

选择“发布前文档审查”或“新成员项目入门”作为固定任务，在临时仓库或脱敏副本中工作。准备固定输入 `team-pack-review-v1`：一份包含已完成项、未验证项、一个过时命令和一个待确认权限的短文档。作者 A 先建立上面的目录、`version: 0.1.0`、owner、来源、权限表、三项验收证据和回滚说明；保存输入 hash 和空白副本 hash。

整个实验禁止连接真实外部服务、授权账户、发送消息、上传客户资料、推送、发布或把长期秘密写入能力包。

### Task

1. A 按固定任务协议完成一次，并保存 `21-team-pack-review-v1-A-01` 日志。
2. A 将能力包交给 B；B 只使用能力包和固定输入，在另一个临时副本中独立完成，不接受口头补充，保存 `21-team-pack-review-v1-B-01` 日志。
3. B 记录实际读取、行动、停止点、输出 diff、验证结果、权限判断和隐含知识缺口。
4. A 根据缺口只修订一个层级，提升版本为 `0.1.1`，记录变更和理由；B 再运行一次 `B-02`。

### Evidence

证据包至少包含：

- `manifest.yaml`、目录清单、版本和 owner；
- 固定输入及 A/B 两个临时副本的 hash；
- 正例、失败例、协议或 `SKILL.md`；
- A、B、修订后 B 的独立日志、diff、验证输出和评分；
- 权限表：数据范围、技术 scope、任务授权、审批人、期限和禁止行动；
- 来源/许可证记录位置、下一次复核日期和回滚说明；
- 隐含知识缺口及修订前后差异；
- 未验证项和 `content_status`/`claim_status`（如适用）。

建议用 5 项、每项 0–2 分评分：目标理解、上下文处理、行动边界、证据完整、失败停止。通过要求 A 和 B 都达到 8/10，且不得发生未经授权行动；B 必须在没有口头补充的情况下完成关键流程。缺少任一独立日志、权限表、回滚说明或输入 hash 时，结果为 `candidate` 或 `blocked`，不能称为已验证。

### 失败与边界

失败变体一：删除 `owner` 和 `version`，观察审查者是否拒绝接收。失败变体二：提供一份脱敏的静态权限清单，把所有外部能力写成 `requested`。这只是纸面模拟：不得在真实账户、公共仓库、生产服务或带秘密环境中授权、连接、发送、写入、推送或发布。正确行为是指出过宽 scope、目标范围、审批人、期限和回滚要求，并将能力包标为 `blocked` 或 `candidate`。

### 复盘

按共同语言、方法、证据、治理四层分类缺口。回答：B 为什么无法独立复现？缺口应修订哪一层？修订后哪项失败或证据发生变化？权限表是否仍比任务需要更宽？如果 owner 离开、来源失效或能力产生副作用，谁能回滚或下线？口头“我看懂了”不能替代日志和 diff。

## 边界与常见误区

- 共享上下文不应包含密码、长期秘密、未经授权的客户资料或无法核实的市场断言。
- 外部 Skill 的名字和目录存在不等于许可证、触发、依赖和行为已经审查。
- 组织规则、任务上下文和个人偏好必须分开，外部文本不能静默覆盖组织规则。
- 模拟权限结果只能证明审查流程，不证明连接器、账号或生产服务可用。
- 发布、修改权限和处理秘密必须单独批准，不能由“实验”自动包含。

## 迁移练习

把个人项目中的一个能力包迁移到组织项目。重新检查名称、许可证、品牌、数据范围、权限、owner、reviewer、发布目标和回滚；列出迁移前后各一个不能直接复用的假设。
