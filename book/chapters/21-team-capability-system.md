# 第二十一章：建立团队能力系统

## 本章要解决的问题

个人可以凭经验让 Codex 完成任务，团队却会遇到另一组问题：谁知道这条规则？哪个 Skill 可以信任？谁负责更新？成员是否拥有过大的权限？一个成功案例能不能被别人复现？如果没有共享语言、证据和责任，团队只是在共享不透明的个人习惯。

## 学习目标

读者完成本章后应当能够：

- 把个人方法拆成团队可复用的能力包；
- 为规则、Skill、实验、评测和来源指定维护责任；
- 设计最小权限和贡献审查流程；
- 用版本、证据和变更记录管理团队上下文；
- 在能力失效或来源变化时回滚、迁移或下线。

## 1. 团队能力包的四层

```text
共同语言与项目规则
        ↓
可复用方法与 Skills
        ↓
实验、任务集与证据标准
        ↓
权限、审查、版本与维护责任
```

每层都有不同的职责：

- **共同语言：** 让成员对 Codex、上下文、工具、Agent、验证和状态有相同理解；
- **方法层：** 把重复流程写成清晰、有限、可触发的 Skill；
- **证据层：** 证明章节和 Skill 在声明范围内有效；
- **治理层：** 决定谁能修改、发布、使用和撤销能力。

没有证据层，方法只是建议；没有治理层，方法可能在不知情的情况下扩大权限或传播过时事实。

真实问题入口：[Skill 选择实验](../labs/lab-004-skill-selection.md)。评测夹具入口：[评测框架/任务字段规范](../../docs/quality/evaluation-framework.md)。研究档案入口：[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)。

## 2. 共享上下文的边界

团队上下文应优先包含：项目目标、术语、架构边界、可信来源、运行方式、验收标准和已知风险。它不应包含：个人密码、长期有效的秘密、未经授权的客户资料、无法核实的市场断言或把一次讨论误写成组织政策的内容。

项目规则、任务上下文和个人偏好必须分开。组织级规则不能被某个任务中的外部文本静默覆盖。

## 3. 权限与责任分离

“能使用”不等于“能修改”， “能修改”不等于“能发布”。团队至少要分别考虑：

| 能力 | 典型责任 |
|---|---|
| 读取 | 确认数据范围、敏感性和来源 |
| 编辑 | 说明变更范围、回滚方式和验证 |
| 运行 | 记录环境、命令、副作用和日志 |
| 推送/发布 | 指定目标仓库、分支、审查人和回滚 |
| 修改权限/处理秘密 | 窄范围授权、双人复核或明确人工确认 |

权限配置应服务于任务，而不是因为“以后可能用到”就预先开放全部能力。

## 4. 贡献和审查流程

一个新章节、实验或 Skill 至少要回答：

1. 它解决哪个学习或工作问题？
2. 它是原创、改写、外部组件还是外部链接？
3. 需要哪些来源、许可证和归属？
4. 正例、边界例、失败例和迁移例是什么？
5. 哪些事实会过时，谁负责复核？
6. 失败、回滚和下线方式是什么？

评审先看目标和边界，再看来源、安全、事实、学习价值、可验证性和维护成本。内容越接近生产写入或高权限行动，证据门槛越高。

## 实验：交付一个团队能力包

选择一个团队重复任务，例如新成员项目入门、发布前审查或研究报告复核。交付一个最小能力包：

- 一页共同上下文；
- 一个任务协议或 Skill；
- 一个成功实验和一个失败实验；
- 三项可检查的验收证据；
- 维护人、版本、来源和下一次复核日期。

让另一位成员在没有口头补充的情况下使用它，并记录隐含知识缺口。

### 故意失败变体

删除维护责任和版本记录，或把所有外部服务权限全部打开。通过标准是团队成员识别出这两个治理缺口，而不是因为“能运行”就接受能力包。

## 迁移练习

把同一能力包从个人项目迁移到 组织项目，重新检查名称、许可证、品牌、数据、权限、审查和发布范围。

## “我真的学会了吗？”

- [ ] 我能把个人经验拆成语言、方法、证据和治理四层；
- [ ] 每个共享 Skill 都有触发边界、失败路径和维护责任；
- [ ] 团队上下文不包含秘密或未经授权的个人数据；
- [ ] 我能区分使用、修改、推送、发布和改权限的责任；
- [ ] 一个新成员能根据能力包复现关键流程；
- [ ] 能力失效时有回滚、迁移或下线路径。
