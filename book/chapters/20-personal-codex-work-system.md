# 第二十章：建立个人 Codex 工作系统

> `content_status: candidate`
> `experiment_status: draft / not run`
> 本章描述可迁移的方法，不把具体产品的记忆、自动加载或入口行为当作永久前提。

## 问题：为什么每次任务都像第一次开始

很多人每次打开 Codex 都重新解释项目、目标、术语、限制和验收方式。结果是上下文不一致、决策无法追溯、过时命令继续被使用，成功经验也无法复用。更危险的是，个人为了“方便记住”而保存 token、密码、Cookie、客户原文或未经确认的旧结论。

## 现实问题入口

FP-10（验证/格式化命令可能长时间停滞）和 FP-11（验证被报告扩大为未授权的持久环境变更）是公开用户问题研究中的报告，不是本地复现或普遍根因；本章用它们检验个人系统能否暴露旧命令、记录停止点和阻止越权。

## 学习目标

读者完成本章后应当能够：

- 区分项目规则、任务上下文、当前状态、模板和复盘记录；
- 为重复任务建立最小、可清理、可追溯的个人工作系统；
- 用固定输入、基线、运行日志和证据完整度比较“有系统”和“无系统”；
- 判断什么时候应该保留任务协议、创建 Skill、继续观察或阻塞；
- 发现过时上下文，并在不保存秘密的前提下把经验迁移给另一个人。

## 概念：五类资产各自解决什么问题

| 资产 | 回答的问题 | 生命周期 | 不应放入的内容 |
|---|---|---|---|
| 项目规则 | 项目始终遵守什么？ | 版本化、少改动、定期审查 | 临时猜测、个人秘密 |
| 任务上下文 | 这一次要完成什么？ | 随任务建立，完成后归档 | 与任务无关的历史 |
| 当前状态 | 已读、已改、已验证什么？ | 每个阶段更新 | 把计划当成结果 |
| 模板 | 类似任务如何开始和交付？ | 重复实践后提炼 | 未验证的永久结论 |
| 复盘记录 | 哪个判断有效、下次改什么？ | 只保留可迁移经验 | token、密码、Cookie、客户原文 |

上下文不是越多越好。相关性、可信度、敏感度和时效性比长度重要。

## 决策：创建 Skill 还是保留任务协议

先填写这张卡，而不是因为任务重复三次就自动创建 Skill。

| 观察结果 | 决策 | 必须有的证据 |
|---|---|---|
| 一次性需求，输入或输出仍在变化 | 保留任务协议 | 一次任务的输入、约束和交付记录 |
| 输入、决策点和输出连续稳定，已有正例与失败例 | 建立 Skill 候选 | 至少 3 次运行、失败集和迁移任务 |
| 规则有用但触发边界不清或副作用未解决 | 继续观察/阻塞 | 缺口记录、风险和待验证项 |
| 涉及秘密、外部写入或生产发布而授权与回滚不清 | 阻塞 | 权限表、人工批准点和回滚方案 |

决策卡最少记录：`decision_id`、重复任务、候选资产、稳定输入、失败类型、证据位置、owner、`next_review` 和 `decision_action`。一次偶然成功不能成为 Skill 的理由。

## 行动：建立最小个人系统

建议从五份记录开始：项目地图、任务协议、状态日志、证据索引、复盘记录。启动时检查规则、分支、现状和权限；执行时只带入必要上下文；交付时区分实际验证与未完成项；复盘时只提炼可迁移规则。

推荐的交付字段是：完成项、变更文件、实际验证、未验证项、风险、恢复方式和下一步。产品是否自动记忆、哪些文件会被自动加载，必须以当前官方文档和实际入口为准，不能用个人习惯代替事实。

## 实验：建立个人工作系统

这是一个只在临时副本中进行的离线比较实验，不连接生产、不发送消息、不发布、不使用真实秘密。

### Setup

建立临时副本和基线 `personal-system-triage-v1`。固定脱敏输入如下：

```text
待分流事项：
1. “按钮在窄屏溢出”，有截图，尚未修复。
2. “构建通过”，只有命令退出码，没有用户验收。
3. “认证失败”，没有版本、入口或错误日志。
4. “文案需要更新”，没有目标受众和来源。
```

固定任务文本为：

> 将四条事项分为“需要补输入”“可以进入执行”“需要人工确认”三类。不得猜测缺失版本、权限或用户验收；为每条事项写出下一步和所需证据。

运行前保存输入哈希和空白临时副本的哈希。准备五份空记录：`project-map`、`task-protocol`、`state-log`、`evidence-index`、`reflection`。不得把 token、密码、Cookie、客户原文或不必要的个人数据写入任何记录。

### Task

1. **基线 A：** 只提供固定任务和输入，不使用五份个人系统记录。
2. **候选 B：** 使用五份记录，版本标为 `personal-system-v1`，并在状态日志中记录已读、已改、已验证、未验证和阻塞。
3. 两条路径各运行 2 次；每次运行前恢复同一输入和临时副本。使用 `run-id`：`20-personal-system-triage-v1-A-01`、`A-02`、`B-01`、`B-02`。
4. 禁止真实外部连接、写入、发布和秘密读取。若任务需要这些条件，实验立即标为 `blocked`，不以模拟结果宣称可用。

### Evidence

每次运行保存：

```yaml
run_id: "20-personal-system-triage-v1-B-01"
task_id: "personal-system-triage-v1"
system_version: "none | personal-system-v1"
input_hash: "sha256:..."
baseline_hash: "sha256:...；临时副本恢复点"
context_files: ["project-map", "task-protocol", "state-log", "evidence-index", "reflection"]
clarification_rounds: 0
actual_changes: "no-change or file/diff summary"
validation: "检查项、结果、退出码"
evidence_items: ["input", "classification", "missing-input rationale", "next step", "validation", "unverified note"]
evidence_completeness: "0/6"
rework_count: 0
log_location: "evals/results/；未运行时写 not_run"
reviewer: "独立复核角色；未分配则写 not_assigned"
unverified_items: ["实际入口行为", "账户级权限", "运行时结果"]
status: "pass | fail | not_comparable | blocked | not_run"
```

比较表至少包含：重复说明次数、澄清轮数、缺失输入发现时间、返工次数、证据完整度、错误分类和实际耗时。证据完整度为六项必需材料中可核查材料的比例；没有基线或输入哈希不一致时写 `not_comparable`，不能写“改善”。候选路径只有在四次日志完整、无秘密、无外部副作用，且分类和停止理由满足验收时才算实验通过；这仍不等于 Skill 已验证。

### 失败与边界

在项目地图中加入一个已经失效的命令和一个旧目录，作为静态故障输入。正确行为是先检查当前状态，标记记录过时，停止沿用旧命令，并把缺口写入状态日志。若学习者直接照抄旧记录、补造认证信息、扩大权限或把计划写成验证结果，实验失败且应保留失败日志。

### 复盘

回答：哪条上下文真正改变了判断？哪条记录已经过时？哪个证据仍然缺失？基线与候选之间的差异来自哪里？下次删除、保留还是更新什么？这条经验能否迁移到另一个领域，限制是什么？最后更新决策卡，而不是只写“以后注意”。

## 边界与常见误区

- 无限增长的上下文会把旧事实和新目标混在一起。
- 个人记录不是秘密存储，也不能替代权限审查。
- “命令已启动”不等于验证完成；“登录过”不等于当前入口和范围正确。
- 只有一次性需求时，任务协议通常比新建 Skill 更轻量。
- 没有独立复现、失败集和迁移证据时，Skill 只能保持 `candidate`。

## 迁移练习

把一个个人稳定流程交给另一位成员。对方只使用项目地图、任务协议和证据索引，在临时副本中独立运行；分别保存输入哈希、日志、diff、验收和缺口。记录哪些隐含知识没有被写出，并决定修订哪一份资产。

## “我真的学会了吗？”

- [ ] 我能区分规则、任务上下文、状态、模板和复盘。
- [ ] 我的记录不保存 token、密码、Cookie 或不必要的个人数据。
- [ ] 我能用相同输入和基线比较两条工作路径。
- [ ] 每次运行都有 `run-id`、日志、证据完整度和未验证项。
- [ ] 我能判断创建 Skill、保留协议、继续观察和阻塞的差别。
- [ ] 我能发现过时命令并说明恢复方式。
- [ ] 另一个人能在没有口头补充的情况下复现关键判断。
