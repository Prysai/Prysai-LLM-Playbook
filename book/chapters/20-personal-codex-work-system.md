# 第二十章：建立个人 Codex 工作系统

## 本章要解决的问题

很多人每次打开 Codex 都从头解释项目、目标、术语、限制和验收方式。短期看只是麻烦，长期会造成上下文不一致、决策无法追溯、成功经验无法复用，也让 Agent 更容易在旧假设上继续工作。

个人工作系统不是把所有历史对话都保存下来，而是有选择地管理上下文、模板、证据和复盘。

真实问题入口：[首次安全任务实验](../labs/lab-001-first-safe-task.md)。评测夹具入口：[评测框架/任务字段规范](../../docs/quality/evaluation-framework.md)。研究档案入口：[OpenAI Codex 官方基线](../../docs/research/openai-codex-baseline.md)。

## 学习目标

读者完成本章后应当能够：

- 区分项目规则、任务上下文、短期状态、模板和长期记忆；
- 为反复出现的任务建立最小可复用入口；
- 设计启动、执行、交付和复盘四个阶段的记录；
- 识别过时上下文和不应保存的秘密或个人数据；
- 在下一次任务中用更少的重复说明获得更好的证据。

## 1. 五种不同的上下文资产

| 资产 | 回答的问题 | 维护方式 |
|---|---|---|
| 项目规则 | 这个项目始终遵守什么？ | 版本化、少改动、由维护者审查 |
| 任务上下文 | 这一次要完成什么？ | 随任务建立，完成后归档 |
| 当前状态 | 已经读了什么、改了什么、验证了什么？ | 每个阶段更新 |
| 模板 | 类似任务的最小表达是什么？ | 通过重复实践后提炼 |
| 复盘记录 | 哪些方法有效、哪里失败、下次怎么改？ | 只保留可迁移的经验 |

它们不应混成一份无限增长的“万能上下文”。上下文越长，不代表越有用；无关、过时或敏感内容会降低判断质量。

## 2. 一个最小个人系统

建议从五个文件或记录开始：

1. **项目地图：** 目标、入口、可信文件、运行命令、已知边界；
2. **任务协议模板：** 目标、输入、约束、允许行动、验收、失败和交付；
3. **状态日志：** 已读取、已改变、已验证、未验证、阻塞和待确认；
4. **证据索引：** 测试、运行、来源、截图、差异和用户验收的位置；
5. **复盘记录：** 这次做出的判断、失败原因和可迁移改进。

这些文件不是为了让 Codex 代替你记忆，而是为了让下一个人或下一个会话能够检查你做过的判断。

## 3. 四阶段工作节奏

### 启动

先检查项目规则、当前分支、现状和任务协议。若任务目标、输入或权限不清楚，先缩小范围。

### 执行

每个切片只记录改变它所需的上下文。涉及外部副作用时保留确认点；出现失败时更新状态，不要只覆盖旧输出。

### 交付

交付格式至少包含完成项、变更文件、实际验证、未完成项、风险和下一步。把“计划过”与“实际完成”分开。

### 复盘

只提炼能够在新任务中使用的规则。不要把一次偶然成功写成永久事实；如果经验依赖某个模型、版本或工具，应记录来源和复核日期。

## 4. 什么时候应该创建 Skill

重复三次并不自动意味着需要 Skill。先问：

- 流程是否有稳定的输入、决策点和输出？
- 是否经常遗漏相同的检查？
- 是否存在项目特有的规则或风险？
- Skill 是否会减少重复说明，而不是增加无关上下文？
- 是否有正例、边界例、失败例和迁移任务可评估？

如果只是一次性任务，清晰的任务协议通常比新建 Skill 更轻量。

## 实验：建立个人工作系统

选择一个每周都会重复的低风险任务，例如周报整理、问题分流或文档更新。建立最小项目地图、任务协议、状态日志和证据索引，连续完成两次。比较：

- 重复说明是否减少；
- 输入缺失是否更早暴露；
- 交付证据是否更完整；
- 上下文是否出现过时或无关内容。

### 故意失败变体

在项目地图中保留一个已经失效的命令或旧目录，观察 Codex 是否先检查现状。通过标准是发现冲突并标记它，而不是照抄旧记录。

## 迁移练习

把个人系统中的一个稳定流程交给另一位成员。让对方只使用项目地图、任务模板和证据索引完成任务，再记录哪些隐含知识仍未被写出。

## “我真的学会了吗？”

- [ ] 我能区分规则、任务上下文、当前状态、模板和复盘；
- [ ] 我的个人系统不会保存 token、密码、Cookie 或不必要的个人数据；
- [ ] 每次交付都能找到实际证据，而不是只找到计划；
- [ ] 我能判断什么时候不该创建 Skill；
- [ ] 我能发现并更新过时的项目记录；
- [ ] 另一个人可以根据最小上下文复现关键判断。

## 稳定原则

本章讨论的是上下文管理和复盘方法，属于稳定层。具体文件名、产品入口和记忆功能是否存在，属于产品事实，应以当前官方文档和组织规则为准。
